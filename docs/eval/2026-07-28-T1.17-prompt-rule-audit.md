# 2026-07-28 — T1.17 extraction prompt: rule → pass coverage audit

The strip list for the extraction system prompt, and the evidence for every row.

**Policy applied** (plan §5, controller ruling 5): *strip a rule only on demonstrated full
subsumption by an existing deterministic pass or by the schema string the user message
already carries. Never edit a pass to justify a strip. On partial coverage, keep the rule.*

**Outcome:** 4 rules stripped, 1 stale statement corrected, ~44 rules kept. The prompt goes
from 35,665 characters / 163 lines (`sha256[:16] = 775ca7c45ed9a06a`) to 35,188 characters /
159 lines (`f59a62d1be7273a8`). That is a 1.3% reduction, not the near-total strip doc 05 §6's
"minimal rules" phrasing suggests — because the deterministic twins the doc assumes mostly do
not exist yet. The measured gaps are handed to T1.24b–e below rather than absorbed here.

Coverage verdicts were produced by running `clean_extraction` over constructed inputs, not by
reading the code. `filter_noise`'s `_NOISE_NAMES` and rule 2a's builtin set were compared
programmatically.

## Corrected, not stripped — the prompt contradicted the taxonomy

The memory-type paragraph said **"choose exactly one of these seven"** while `MEMORY_TYPES`
has been **nine** since T1.23, and the schema string has been offering all nine on every call.
It also forbade `debug`, `workflow` and `session` as "not valid types", but
`normalize_memory_type` now maps `workflow → procedural` and `session → episodic`.

The paragraph now defers the count to the schema and glosses all nine types; the stale
sentence is gone. T1.23's amendment (2026-07-27) explicitly deferred the prompt-side edit for
the widening to T1.17, so this is in lane. `memory_type` is not scored by the F1 bench, so the
change carries no measured F1 risk — and leaving a request whose prompt and schema disagree
about the vocabulary would have been the real defect.

## Shrinkable, deliberately not shrunk

Several kept rules carry worked examples that duplicate a pass's pattern list — rules 3, 3a,
9c-soft, 9f, 10, 12b, 15, 16, 16a, and Examples 4 and 5's lettered notes. Trimming them would
remove few-shot signal that is precisely the mechanism a *partial*-coverage rule relies on,
against a budget of roughly 1.6 flips on the tightest cell (gold `rel_pair`) and a hard
one-revision cap. The reduction is recorded here so a later task with a wider budget — most
naturally T1.24f, once the pass gaps below are closed — can take it deliberately.

## Handed to T1.24b–e as pass gaps (Tier-2)

Each is a prompt rule carrying work its named pass does not do. Closing one makes the
corresponding rule strippable under this same policy.

1. `filter_noise` — `_NOISE_NAMES` covers 10 of rule 2a's 28 builtins (18 listed above).
2. `filter_noise` / `filter_literals` — nothing filters config values or CSS/Tailwind tokens
   (rule 2b), nor suppresses the `USES` edge toward them.
3. No pass synthesises or re-orients `CAUSES` (rule 9h-dir).
4. Nothing downgrades a soft-dependency `DEPENDS_ON` to `USES` (rule 9c-soft).
5. `filter_noise`'s article guard deletes `the web app` instead of rewriting it to `web app`,
   so rules 4 and 7b work against each other in the current chain.
6. `rescue_happened_on`'s `_DATE_ISO_RE` cannot match the non-ISO forms rule 9f names.
