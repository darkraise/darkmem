# B6 — platform: assembly, auth, MCP door, jobs, events, backups

Reviewer findings for the 2026-11-20 audit, as returned. Summary first where the reviewer gave one, then one entry per finding. Index and verification status: `docs/2026-11-20-codebase-audit.md`.

**Counts:** 1 high, 9 medium, 12 low, plus 6 design critiques.

**Most important findings:**
1. **High — stuck repositories.** Cancelling an index run leaves the repo in `status='indexing'` permanently. The run handlers reset status only on `Exception`, and cancellation is not one (`api/routes/repos.py:373`, `services/job_runners.py:198`). Cancellation happens on every redeploy, on the `repo_sync` timeout, and on the task-cancel route. Every reindex door then refuses the repo until someone runs SQL by hand.
2. **Medium — login.** Login runs bcrypt directly on the event loop, and the lockout is checked before an `await` (`api/routes/auth.py:93-120`, `api/auth.py:41-46`). An unauthenticated caller sending concurrent attempts gets far more than 5 guesses and freezes the whole process while doing it.
3. **Medium — read-only worker.** MCP `memory_reason`, `memory_overview` and `document_search` call the model provider on the backup worker. The REST versions are refused there (`api/mcp/server.py:431,464,899`).

**Other medium findings:**
- MCP `code_symbol` very likely fails on every hit with `MissingGreenlet` (`server.py:1651`); one call would confirm it.
- The session dependency commits after the response is sent (`database.py:28-35`), so several config routes return 200 before their write is durable.
- A stale CORS fallback gives `localhost:3000` and `:5173` credentialed access (`main.py:926`).
- SSH backup destination `user`/`host` fields allow option injection (`backup_ship.py:946`).
- Every MCP request pays a fresh bcrypt, with no cache.
- A job's `min_interval_seconds` stays at whatever was first saved, so later code changes to the floor are ignored.
- Changing a job's config waits for any run in progress to finish.

**Checked and found sound:** HS256 pinning, token revocation, auth on every route, MCP refusing tools without a declared scope, the setup race, and secret masking.

- **B6-1** (high, bug, confirmed). Cancelling an index run (redeploy, `repo_sync` 1800 s timeout, task-cancel route) leaves the repo in `status='indexing'` forever, because the reset runs only on `except Exception`, so every reindex door answers 409 or `repo_busy` until someone fixes it with SQL. Remedy: At boot (non-read-only), reset `indexing`/`cloning` to `error`, and catch `CancelledError` in `_run_index` and the `repo_sync` per-repo block, reset the status in a fresh session, then re-raise. Where: backend/app/services/repo_manager.py:264-291, backend/app/api/routes/repos.py:373, backend/app/services/job_runners.py:198, backend/app/services/job_registry.py:391-393, backend/app/main.py:660,671, backend/app/services/task_registry.py:65-73, backend/app/api/mcp/server.py:1523-1550
- **B6-2** (medium, security, confirmed). Login runs bcrypt synchronously on the event loop, and the lockout check happens before an `await`, so concurrent unauthenticated attempts all pass the gate (far more than 5 guesses) and freeze the whole process for about 0.2 s each. Remedy: Run `verify_password`/`hash_password` via `asyncio.to_thread`, and count in-flight attempts per IP against the threshold before the first `await`. Where: backend/app/api/routes/auth.py:93-120, backend/app/api/auth.py:41-46
- **B6-3** (medium, bug, confirmed). MCP `memory_reason`, `memory_overview` and `document_search` call the LLM or embedder on the read-only backup worker, where the REST twins are refused by `refuse_when_read_only`. Remedy: Refuse these tools under `settings.read_only` with a `_degraded` envelope (or a refused-tool set in `ToolScopeMiddleware`), and add a REST/MCP read-only parity test. Where: backend/app/api/mcp/server.py:431-443,464-478,899-927, backend/app/services/memory.py:908, backend/app/services/memory_overview.py:398, backend/app/api/routes/memories.py:162, backend/app/api/routes/documents.py:1039
- **B6-4** (medium, bug, plausible). MCP `code_symbol` reads `s.file.file_path` through a default lazy relationship inside an AsyncSession, so every hit should raise `MissingGreenlet`; no test calls it, and one call would confirm. Remedy: Select `(CodeSymbol, CodeFile.file_path)` or route through `CodeQueryService.lookup_symbol`, and add a result limit. Where: backend/app/api/mcp/server.py:1636-1661, backend/app/models/code.py:75
- **B6-5** (medium, bug, confirmed). `get_session` commits after the response is sent (FastAPI 0.136 request scope), so routes without an explicit commit return 200 before the write is durable. Clients refetch stale values, and system-prompts updates the in-process cache before the commit. Remedy: Use `Depends(get_session, scope="function")` through one `SessionDep` alias (checking sub-dependency scope rules), or commit explicitly in the remaining writers. Where: backend/app/database.py:28-35, backend/app/api/routes/config.py:980-1011,1116-1167,1191-1212,1314-1330, backend/app/api/routes/auth.py:123,155-212
- **B6-6** (medium, security, confirmed). The CORS fallback grants credentialed cross-origin access to `localhost:3000/5173`, and CSRF and WebSocket protection rest only on `SameSite=Strict`, which ignores ports, so same-host pages can trigger body-less POSTs, read `/ws`, and (from `:3000`) read the JSON API. Remedy: Pass `settings.cors_origins` through with no fallback, add `CORS_ORIGINS=${CORS_ORIGINS:-[]}` to both compose files, and optionally check Origin on `/ws` and on cookie writes. Where: backend/app/main.py:924-930, docker-compose.yml (no CORS_ORIGINS), backend/app/api/auth.py:65-75, backend/app/api/websocket.py:78-97
- **B6-7** (medium, security, confirmed). SSH destination `user`/`host` go unvalidated into the ssh/scp argv ahead of `--`, so a value like `-oProxyCommand=…` executes commands in the app container on the next ship or inventory read. Remedy: In `_validate`, require a hostname/IP pattern for `host`, `^[A-Za-z0-9._-]+$` with no leading dash for `user`, and refuse newlines in `remote_dir`. Where: backend/app/services/backup_config.py:41-49,89-114, backend/app/services/backup_ship.py:946-947,1009-1017,1032-1033,1063,1076,1111
- **B6-8** (medium, performance, confirmed). Every stateless MCP HTTP request, and every keyed REST call, pays a fresh bcrypt (about 167 ms in the thread pool): a first tool call costs 4 verifies, and this latency is not counted in `duration_ms`. Remedy: Cache `sha256(token)` → principal for about 60 s in process, clear the entry in `revoke_key`, and re-check expiry on cache hits. Where: backend/app/api/mcp/auth.py:49-51, backend/app/services/api_keys.py:218-237
- **B6-9** (medium, weak-assumption, confirmed). `min_interval_seconds` is persisted into the `job:<key>` row on first save and read back from there, so raising a job's floor in code never takes effect on an existing install. Remedy: Stop persisting it and always read `Job.min_interval_seconds`, as `max_run_seconds` already works. Where: backend/app/services/job_registry.py:122-137,210-211,221-230,349, backend/app/api/routes/jobs.py:94
- **B6-10** (medium, bug, confirmed). `PUT /jobs/{key}` and `PUT /jobs/{key}/config` wait on the per-job run lock, so disabling or configuring a job blocks until a running job finishes (up to 6 h for `backup_ship`). Remedy: Guard config read-modify-write with a separate lock and merge `last_*` at save time, or answer 409 when the run lock is held, as trigger does. Where: backend/app/services/job_registry.py:506-513,542-545
- **B6-11** (low, bug, confirmed). Remedy: Wrap `job_key` and `error` in `html.escape`, and suppress repeats per job for a window. Where: backend/app/services/notifications.py:97,128-131, backend/app/services/job_registry.py:470-483

Remedy: Journal only on error or non-zero work, and return counts so `job_runs` carries them. Remedy: Move the reconciliations out of the LLM `try`, build a missing pipeline when an orchestrator is installed, and have `buffer_flush` report the skip.
