# B5 — documents, pages, blocks, work log, board

Reviewer findings for the 2026-11-20 audit, as returned. Summary first where the reviewer gave one, then one entry per finding. Index and verification status: `docs/2026-11-20-codebase-audit.md`.

**Counts:** high 1, medium 8, low 8.

**Top three:**
1. **High, silent content corruption.** `backend/app/services/document_parsers.py:435-450` counts lines with `splitlines()`, which also breaks on `\f`, `\v`, `\x85`, `\x1c`–`\x1e` and the Unicode line/paragraph separators; markdown-it breaks only on `\n`. Every block after such a character gets the wrong `char_span`, so `source` is sliced wrongly. The single-document block reads (`document_door.py:1176`, `page_door.py:250`) serve that wrong `source`, and the browser block editor (`block-editor.tsx:162,189`) pre-fills its edit box with it. One edit then overwrites the block with its neighbour's text. Existing documents need a forced reparse after the fix.
2. **Medium, stale search vectors.** Document block edits keep the old vector (`block_verbs.py:522,576`). If the embed after commit fails, the request returns 500 after the edit has landed, and the hourly sweep never repairs it because it only fills missing vectors.
3. **Medium, global page-write stall.** `page_attachments.py:216-217` takes the global attachment lock, then streams an upload of up to 50 MB inside an open transaction. When the hourly cleanup queues for the exclusive lock, every page write in every project waits. The Notion import holds the same lock for up to 900 s.

**Other medium findings:**
- A document edit re-embeds every block (5,000 at the cap). An unchanged re-push spends an avoidable embed call; `llm_fingerprint()` already gives the right answer when `dimensions` is set.
- `_PLACE` rewrites every block row on every block edit, and nothing reclaims the dead rows (autovacuum never runs here).
- `blocks.search_vector` and its GIN index have no reader; remove them.
- `document_revisions` keeps a full copy per filing with no limit.
- The block reads decompress the full stored `content` once per block (`_BLOCKS`).

**Low findings:**
- The PDF parser and pdfplumber can't be reached, since content is always text (dead code).
- `ingest_documents`, `file_documents_isolated` and two block-embedding helpers (`resolve_read_fingerprint`, `block_vectors`) have only test callers.
- Subtree rename journals no actor or API key.
- A malformed parent or after-block id on the document block routes returns 500.
- Document connections runs uncached, roughly 3–4 s at 1,132 blocks per view.
- The document list counts blocks for every document before applying its limit.
- One unembeddable block makes the sweep retry its whole batch row by row while a backlog exists.
- Four copies of the partition-registration helper.

Every compare-and-set and lock-order path checked out sound, as did zip handling and attachment serving. I didn't open the attachment archive/manifest/verify modules or the work-log and board route files.

- **B5-1** (high, bug, confirmed). `_line_offsets` uses `str.splitlines()`, which also breaks on `\f \v \x85 \x1c-\x1e U+2028 U+2029` while markdown-it breaks only on `\n`, so every `char_span` after such a character is shifted, `source` is sliced from the wrong text, and an SPA block edit seeded from that `source` overwrites the block with its neighbour's text. Remedy: Build offsets on `\n` only (as `board_parse.split_lines` does), add a parser test with U+2028 and `\f`, then force-reparse filed documents with `scripts/reparse_documents.py`. Where: backend/app/services/document_parsers.py:435-450, document_door.py:1176-1189, page_door.py:250-262, block_serializer.py:310-338, frontend/src/features/documents/components/block-editor.tsx:162,189-206
- **B5-2** (medium, bug, confirmed). A document block edit drops no vectors (`_drop_vectors` runs for pages only), so a failed embed after commit leaves the old-text vector forever, because the sweep only fills missing vectors, and the route answers 500 for a write that already landed. Remedy: Drop the touched block's vectors inside the savepoint for documents too when text or type changes, and report `blocks_embedded=0` instead of raising after commit. Where: backend/app/services/block_verbs.py:513-525,573-580, block_embedding_refresh.py:171-180, api/routes/documents.py:1243-1261
- **B5-3** (medium, weak-assumption, confirmed). Upload takes the global shared attachment lock, then streams up to 50 MB inside an open transaction (the Notion import holds the same lock for up to 900 s); once the hourly cleanup queues for the exclusive lock, every page write in every project blocks behind it. Remedy: Stream to `.part` with no lock or transaction, then take the shared lock only around `os.replace` + INSERT + COMMIT, and move the route's project SELECT after the stream. Where: backend/app/services/page_attachments.py:201-231, api/routes/page_attachments.py:74-87, page_import.py:297-366, page_attachment_cleanup.py:238-239
- **B5-4** (medium, performance, confirmed). Any content change re-embeds every block inline (about 157 batch calls and 5,000 single-row INSERTs at `MAX_BLOCKS`), and every `unchanged` re-push spends a real embed call that `llm_fingerprint()` makes unnecessary whenever `dimensions` is configured. Remedy: Reuse vectors for byte-identical block text across a re-file, use `llm_fingerprint()` when dimensions are set, and batch vector INSERTs through `unnest`. Where: backend/app/services/document_door.py:612-668, document_ingest.py:368-370, block_embeddings.py:128-162,267-309, llm.py:405-458
- **B5-5** (medium, performance, plausible). `_PLACE` rewrites `order_index`, `char_span`, `properties` and `parent_id` on every row of the tree on every verb; with `order_index`/`parent_id` indexed and autovacuum never running, each saved block on a large page leaves thousands of dead tuples and index entries (settle with `n_dead_tup` after a notes session). Remedy: Add `IS DISTINCT FROM` guards so `_PLACE` touches only rows whose values actually changed. Where: backend/app/services/block_verbs.py:188-202,527-540
- **B5-6** (medium, dead-code, confirmed). `blocks.search_vector` (stored generated tsvector) and `ix_blocks_search_vector` (GIN) have no reader in app, scripts or frontend, yet every block insert and non-HOT update pays `to_tsvector` plus GIN maintenance. Remedy: Drop the index and column in a new Alembic revision and update the two schema tests and the editor comment. Where: backend/migrations/versions/0001_baseline.py:1431-1436,1459, tests/test_notes_schema.py:235, tests/test_pages_schema.py:70, frontend/src/features/documents/components/block-editor.tsx:42
- **B5-7** (medium, weak-assumption, confirmed). `document_revisions` stores a full content copy (up to 1 MB) on every hash-changing put, with no prune and no delta, so mirror pushes and board edits grow it without bound. Remedy: Add owner-decided retention (newest N per document and/or younger than D days) and record the decision in CLAUDE.md's retention paragraph. Where: backend/app/services/document_ingest.py:380-393, repositories/documents.py:144-156, board_edit.py:92
- **B5-8** (medium, performance, plausible). `substring(content ...)` runs once per joined block row over a TOASTed, compressed `content`, so a large document pays roughly O(blocks × document size) decompression on every read (settle with `EXPLAIN (ANALYZE, BUFFERS)`). Remedy: Fetch `content` once and slice by span in Python, or set `STORAGE EXTERNAL` on `documents.content` and `pages.content`. Where: backend/app/services/document_door.py:1176-1189, page_door.py:250-262
- **B5-9** (low, performance, confirmed). markdown-it parses up to 1M characters synchronously on the single worker's event loop, and `MAX_BLOCKS` is enforced only after every block row is inserted (a 1 MB file can insert about 300k rows before the rollback). Remedy: Run the parse via `asyncio.to_thread` and check the draft count before `insert_blocks`. Where: backend/app/services/document_ingest.py:368-370, document_door.py:577-596, page_door.py:563
