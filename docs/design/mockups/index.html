G0 — Design guideline: doc 14 realised

Reference board, not a screen. Realises doc 14 §2 (theme substrate + token roles), §3 (the honesty-label vocabulary: verification badge, layer chip, overlay chips, both-sides dispute), §4 (the trace panel), and §7 (type scale, spacing, motion, accessibility, copy voice). It composes nothing from doc 13's screen inventory — this is the vocabulary the C0* and S* fragments reuse, never re-derive.

Known gap, flagged rather than papered over. Doc 14 §2/§9 fixes text-sm (14px) as the floor for all app text including badges and chips — compactness must come from padding and weight, never sub-floor type, "because a label carrying the system's central truth claim must not be the smallest text on the screen." The shared mockup.css chrome committed in Task 1 currently sizes .badge (12.5px), .layer-chip / .overlay-* (11.5px) and .state-chip (11px) below that floor. This board renders those classes as given rather than overriding shared chrome from within a single fragment — noted here as a doc-14-vs-asset gap for a follow-up mockup.css pass, not silently resolved.

Density (cozy), elevation (medium), and radius (rounded) are locked axes — pinned, no switcher UI (doc 14 §2). Doc 14 does not fix a numeric spacing scale beyond the built-ins' own defaults ("the mockup sub-phase places components on the grid the theme already fixes"); this board's own chrome is the concrete illustration in practice — page gap 32px, board padding 20px, board-body gap 14px, annotation indent 12px — not a separate doc-14-specified ramp.

3 — Motion & accessibility (doc 14 §7, §8)

Motion — a closed list of signal uses, nothing decorative
  • Live-feed row entrance (a new event arriving)
  • Pipeline stepper's phase advance
  • Badge rung-change transition — a single subtle emphasis pulse when a fact's rung changes under a live update (pulse-glow keyframe)
  • The existing particle/aurora backdrop, reserved for the unauthenticated threshold surfaces (login / setup)
Accessibility — part of the encoding, not a pass afterwards
  • Colour never carries meaning alone — every state pairs a token colour with an icon and a text label; fill style + border style + icon differ pairwise even with colour removed
  • Contrast of label text against its chip background meets WCAG AA at text-sm in both modes — checkable once per theme via the token mapping, not per screen
  • Badges are focusable; the expansion opens on focus as well as hover (Popover for the full origin list — a tooltip cannot hold interactive content)
  • Counts are always printed beside a bar or ramp cell, never shading alone (calendar heatmap, trace-panel arms)
  • All motion honours prefers-reduced-motion
Every non-motion, non-a11y note above is restated inline on the vocabulary examples below rather than collected separately — an annotation next to a treatment is what makes the rule checkable against the pixels, not a rule stated once and trusted to hold.

4 — Honesty visual vocabulary (doc 14 §3, §4)

4a — The verification badge: all four rungs
candidate expansion — "extracted signal, not yet corroborated — served labelled"
corroborated expansion — rendered verbatim from the wire, never re-assembled client-side (doc 12 badge.claim)
canonical reference string (doc 12 §4) — asserted by K distinct origins of kinds [X, Y], no known contradiction, as of T
human-ratified expansion — claim string + ", human-ratified" suffix + who/when, e.g. "asserted by 4 distinct origins of kinds [memory, code, human], no known contradiction, as of 2026-07-20, human-ratified — ratified by a.lee, 2026-07-21"
disputed expansion (two-sided form) — disputed: 2 origins assert X, 1 origin asserts not-X, as of T — see the split panel in 4d
corroborated code@a3f19c2 a code-originated corroborated fact also carries this distinct mark inside its expansion — {commit_sha, basis, file_path, symbol_key} (doc 14 §3.2; C01 formalises the full composition)
Visible label is the rung name, with confirmed shown as "human-ratified" — never the word "verified" anywhere in label, tooltip, or state copy (rule 2). Icons are semantic, never decorative: dashed circle is incompleteness, the merge glyph is multiple distinct origins converging, the person-check is "a human ratified this," the scales are two sides held in balance. A plain checkmark appears nowhere in the ladder.
Two badge non-rung treatments exist outside this ladder (C01 renders both in full): an L0 memory carries no verification badge at all — a lifecycle amber label instead — and a terminal superseded L3 article shows an amber superseded badge that replaces the rung. Neither is a fifth rung; the CHECK constraint stays exactly candidate | corroborated | disputed | confirmed.
4b — The layer chip
L0 · memory L2 · fact L3 · article
Surface-toned, monospace, no accent, no status colour — classification, not judgement (doc 14 §3.3). Always precedes the verification badge in a row's label cluster so the reading order is "what kind of thing → how well supported." L1 (the candidate graph) is never directly served, so no L1 chip renders on a served row (doc 12 §4) — it is omitted above rather than shown unused.
4c — Overlay chips: riding a rung, never becoming one
corroborated under-sourced expansion — "origin count dropped below N; will demote if not re-corroborated"
corroborated stale expansion — "synthesised before the latest verified change"
Overlays append after the badge and never replace, recolour, or restyle it — the row is still corroborated, claim string intact, while the demotion hysteresis runs (doc 14 §3.4, doc 08 §4.3). The dashed border is the shared "provisional/overlay" marker across the language — the same non-colour channel candidate uses.
4d — The both-sides dispute treatment
disputed: 2 origins assert X, 1 origin asserts not-X, as of T
disputed asserts X — cookie_secure defaults to enabled in production 2 origins · kinds [memory, code]
vs
disputed asserts not-X — cookie_secure is tri-state, unset by default 1 origin · kind [human]
Strictly equal visual weight both sides — same card treatment, same type, no comparative bar or "2 vs 1" scoreboard, because corroboration count does not adjudicate a dispute (doc 14 §3.5). Order is deterministic and epistemically neutral: the earlier-asserted side renders first, stable across reloads — never ordered by count or recency, since that would visually pick the winner the backend refuses to pick (doc 14 §9).
4e — The surfaced-exclusion strip
3 facts excluded by context conflict — active context chip env=prod by_context_conflict
2 rows excluded — outside the current project scope by_project
0 shown, 5 excluded — every candidate row was filtered by the active scope/context, never rendered as a bare empty
The strip sits between the query controls and the rows, persistent — not a toast — and the empty state is computed after it, so "0 shown, N excluded" can never render as "nothing found" (doc 14 §3.6, §5; invariant 14). Each chip expands to its reason and, where the cause is a user-held control, points at it.
4f — The trace-panel style
region 1 — request header query: "cookie_secure default" · sectioned (fused=false) · channels ran: [semantic, keyword] · weights: w_semantic=0.7, w_keyword=0.3, w_ppr=0
region 2 — exclusion strip (shared with 4e) 1 row excluded — by_status
region 3 — per-row label cluster
L2 · fact corroborated context: matched · provenance: LLM-guessed, not human-checked
region 4 — score breakdown (ledger, not narrative)
semantic0.78
keyword0.41
pprw=0 · inactive
rerank6.6 / 10
rrf_score is printed as the ordering signal, not a bar among the modality arms (doc 14 §4) — the per-modality score survives on the row but must not be misread as rank.
Field-for-field rendering of doc 07 §8's payload — ledger, not narrative; no generated "because" sentence (doc 14 §4, invariant 15). Arm bars use only the four non-caution chart members (--chart-1/2/3/5), never --chart-4, so a bar can never be misread as a caution signal. A w_* = 0 arm renders as an inactive, muted bar labelled "inactive" — never omitted (which would hide that the arm exists) and never a zero score (which would imply it ran and found nothing) — invariant 23.
