S21 — Activity · job board

The job-board module of Activity (doc 13 §6.1, doc 02 §5.3): the seven JobRegistry jobs with their cron schedule, last-run/next-run, and status; the per-job config gear dialog (cron expression, the min_interval_seconds floor, the max_run_seconds ceiling, and any config_schema fields); the manual trigger action; and the busy (HTTP 409) outcome when a trigger lands on a lock the scheduled loop already holds — it is never queued behind the running job. Each job's cron may be five-field (minute precision) or six-field (seconds-first, Quartz-style); next-run is computed from that expression via croniter.

Job board — empty (fresh install, no run history yet)

Honesty rule: empty says why, and here it cannot mean "no jobs." All seven jobs are registered in code at process startup (app/main.py) — the list itself can never legitimately render zero rows. The honest empty condition for this screen is a fresh install with no run history: every job exists and is scheduled, but none has fired yet, so last-run is never and next-run is the job's first computed tick. Rendering a fabricated "no jobs configured" state instead would misstate what this backend can produce (doc 14 §5's why-honesty rule, applied to a list that structurally cannot be absent).

Per-job config gear dialog — cron / floor / ceiling / config_schema

Opened from the gear on code_enrichment above. min_interval_seconds is the floor: the loop will not fire more often than this regardless of what the cron expression computes — here it caps a runaway six-field */30 * * * * * (every 30 seconds) down to once per 5 minutes. max_run_seconds is the ceiling on a single run's duration. Below those two, this job's own config_schema (a FieldDescriptor list) contributes two more bounded fields. PUT /api/v1/jobs/{key}/config validates every field against its declared type and min/max, rejects unknown keys, and writes under the same per-job lock the scheduled tick and manual trigger already share — a save can never race a running tick.

Six-field, seconds-first (Quartz-style): every 30 seconds. Five-field expressions (minute precision) are also accepted.

Manual trigger on a held lock — busy (HTTP 409), never queued

Honesty rule: busy is a protection, not a failure, and it is not a queue. trigger(key) acquires the same per-job asyncio.Lock the scheduled loop holds while a tick is running, so a manual run and a scheduled run can never race. A trigger that lands while the lock is held returns busy → HTTP 409 immediately — the request is discarded, never queued behind the in-flight run, and the human must retry once it finishes rather than stacking a second execution (doc 02 §5.3).
