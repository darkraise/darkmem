S29 — Settings · Maintenance

The Maintenance tab of Settings (doc 13 §7): three operator-facing modules — re-embed (backfilling memories/entities/code chunks missing a vector under the currently active embedder fingerprint, doc 04 §5), cleanup ops (one-click triggers for the orphan-entity, orphan-tag, and expired-memory JobRegistry jobs, plus a count-and-link-out to unresolved pipeline failures), and DB ops (per-fingerprint cache pruning and the Postgres-level housekeeping a heavy re-embed or cleanup pass leaves behind). Every trigger opens an inline confirmation before it runs — re-embed's confirms cost and duration (it only backfills missing rows, it deletes nothing), cleanup's and DB ops' confirm data loss.

Maintenance — empty (nothing currently needs attention)

Honesty rule: empty here cannot mean "modules unavailable." All three modules always exist — the empty condition is a healthy quiescent vault: every memory/entity has a row under the active fingerprint, zero unresolved pipeline_failures, and no cache to prune. Same discipline S21's job board applies to "no run history yet" (this board's sibling for the shared cleanup jobs): the honest empty state names what is actually absent, never fabricates "no maintenance available."

Maintenance — error

Honesty rule: error ≠ empty grid. GET /api/v1/reembed/obsolete-counts 503s when the pipeline has no active embedder yet (reembed.py's _resolve_fingerprint guard) — that surfaces as a named error, never as a quietly-zeroed card indistinguishable from the honest empty state above (invariant 14). Cleanup ops and DB ops do not depend on this read and stay usable; only the re-embed card is blocked.
Couldn't load re-embed status — pipeline not initialized GET /api/v1/reembed/obsolete-counts returned 503 Pipeline not initialized (no active embedder is configured yet, Settings → LLM). Cleanup ops and DB ops below are unaffected. Retry

Maintenance — populated (hero, both themes)

Every trigger below opens the same inline armed-confirmation shape before it runs (never a bare destructive click): re-embed's confirm names cost and duration only — the backfill upserts missing rows under the active fingerprint, it never deletes an existing vector, so its panel stays on the caution (--warning) token. The expired-memory sweep and the cache prune actually delete/drop rows, so their panels escalate to the conflict (--destructive) token — the same colour-by-consequence split doc 14 §3.1 uses for badges, reused here for a different kind of honesty signal (what happens if you click Confirm). VACUUM ANALYZE / REINDEX carry the illustrative tag: standard Postgres housekeeping surfaced here because it is where an operator would reach for it after a heavy re-embed or cleanup pass, not because a dedicated darkmem endpoint exists for either yet (only the cache prune and the three cleanup jobs are real routes today) — flagged rather than silently implied as shipped.

Re-embed — in-progress state (memories category running)

What POST /api/v1/reembed/memories actually broadcasts: pipeline.reembed_batch.progress events carrying {batch_id, category, current, total, processed, errors, state}, cycling started → progress → done (ReembedService). A second click on Re-embed memories while this runs is rejected with 409 already_running, never queued — the same per-category lock shape S21's job board uses, scoped to memories only: entities and code chunks stay re-embeddable concurrently, because the lock is per category, not global.
