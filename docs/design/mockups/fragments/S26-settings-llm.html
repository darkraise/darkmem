S26 — Settings · LLM

The flattened LLM configuration surface (doc 13 §7, doc 11, doc 04 §7): six inline purpose cards — embedding / extraction / classification / reasoning / summarization / reranker — each editing {model, base_url, api_key, api_kind, params, dimensions?, reasoning?} directly on the row, no indirection. The classification card carries the inline classifier_kind toggle (llm | local); the summarization card carries the three code-summarization buckets (symbol / module / overview). There is deliberately no provider/profile/ml-profile chrome — those management surfaces are removed with the flattening, shown struck through below rather than omitted silently. api_kind renders as a plain selector; every vendor auth/reasoning/structured-output quirk it selects resolves server-side (doc 11 §4) and is never re-implemented here. A save triggers the live-reload confirmation, because there are no LLM_* env vars and the change takes effect without a redeploy (invariants 18/19).

Settings · LLM — empty

Honesty rule: empty says why, and here it cannot mean "no purposes configured." All six purpose rows are written by the setup wizard's finalize step (app/services/llm_seed.py, doc 11 §7) before any authenticated route — Settings included — becomes reachable, and every seed defaults to the local Ollama install so a no-credentials fresh install still ends up with six live rows. So this grid cannot legitimately show zero cards for a running install. The one honest empty condition left is a config-integrity gap: the llm_purpose_configs table was reset (a DB restore, a re-run migration) without re-running the wizard's finalize step, so the six-row read genuinely comes back empty. The empty state names that condition and offers the one recovery action that actually fixes it, rather than inventing a picker over rows that do not exist.
No purpose rows found llm_purpose_configs read zero rows — the setup wizard's finalize step has not seeded this install (or the table was reset after it ran) This is not a "no purposes exist by design" state — every install needs all six rows to serve embedding, extraction, and chat calls at all.

No provider/profile chrome renders here, at any state — not even a disabled picker. darkmem is not an LLM proxy: each purpose is one row the operator edits directly, so the llm_providers / llm_profiles / ml_profiles tables and every *_ref column are dropped outright with this flattening (doc 04 §7, doc 11 §2). A profile picker over a schema with no profiles table would be scaffolding rendered as a feature (invariant 23, doc 13 §7) — so the honest move is deletion, not a greyed-out control that implies a capability this schema no longer has anywhere to store.

Save → live-reload confirmation

No LLM_* env vars exist — a save takes effect without a redeploy (invariants 18/19). On save the app constructs a fresh LLMOrchestrator from the current six purpose rows and swaps the in-process reference atomically; there is no second worker to notify and no shared external cache to invalidate (doc 11 §3, invariant 13 — single uvicorn worker is what makes the swap atomic without cross-worker coordination). The superseded client's connection pool drains rather than dropping in-flight calls.
