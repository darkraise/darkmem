S22 — Activity · Staged monitors

Doc 13 §6.1 stages two of Activity's six modules behind backends that do not exist yet: the buffer-depth monitor (needs memory_buffer, doc 04 §8.6) and the dream-run monitor (needs the consolidation job family, doc 08 §5). The other four — the five-phase stepper (S18), the live feed (S19), failure triage (S20), and the job board (S21) — already ship. Invariant 23 governs how a staged module is allowed to render: a live-looking panel bound to a table that never writes would read as either broken or as a shipped-capability claim, so it stays labelled staged until its signal exists — never a bare empty panel. To let this design still be reviewed in full, each module below appears twice: once as the honestly labelled staged placeholder that ships today's Activity, and once as its fully populated target design, so the whole target surface is visible without any board claiming it ships.

Buffer-depth monitor — staged

Why staged, not empty (invariant 23). memory_buffer does not exist yet — Tier-A capture still acks straight into the five-phase pipeline with no durable queue in front of it, so there is no pending/claimed/done/error data this panel could honestly show. A live-looking gauge here would either read as broken or imply the durable buffer already ships; the phase-labelled placeholder is the honest alternative doc 14 §5's staged pattern defines.

Buffer-depth monitor — populated target design (hero, both themes)

The full target surface, not a live claim (invariant 23). This is what the buffer-depth monitor renders once memory_buffer ships, visualised in full so the design can be signed off without this board implying the backend exists today — the staged board above is what actually ships until then.
The memory_buffer state machine (doc 04 §8.6). A captured memory lands pending the instant Tier A acks (202), before the five-phase pipeline claims it. A buffer_flush worker claims a batch with SELECT … FOR UPDATE SKIP LOCKED (fixing memobase's double-flush bug), flips it to claimed, then done once flushed — done rows are swept past a short retention window so the table never grows unbounded. A row whose attempts counter exceeds the retry threshold flips to error instead of retrying forever: a poison row, surfaced here and in Failure triage (S20) rather than silently looping.

Dream-run monitor — staged

Why staged, not empty (invariant 23). The consolidation job family — fact_lift, verification_recompute, contradiction_scan, memory_dream, topic_detection, article_synthesis (doc 08 §5) — has no registered JobRegistry rows yet, so there is no cron, no lock state, and no run history this panel could honestly show. Staging it here, labelled with what it is waiting on, is the same invariant-23 treatment as the buffer monitor above, not a second bare empty panel.

The per-action ledger a completed cycle leaves behind is the separate dream digest (S23).

Dream-run monitor — populated target design (hero, both themes)

The full target surface, not a live claim (invariant 23). This is the dream-run monitor's target design — the live view of a consolidation cycle in progress, distinct from the dream digest (S23), which is the reversible, grouped ledger a completed cycle leaves behind. The staged board above is what actually ships until the consolidation job family lands.
One worker, one dependency order, one lock per job (doc 08 §5/§5.1). The several jobs serialise through the same JobRegistry loop and single uvicorn worker every existing job already uses; "Dream now" runs them in dependency order — fact_lift → verification_recompute → contradiction_scan → memory_dream → topic_detection → article_synthesis — rather than firing them concurrently, and a manual trigger that lands on a lock the scheduled loop already holds returns busy (HTTP 409) instead of queueing behind it.
