S20 — Activity · Failure triage

The v1 failure triage module of the Activity shell (doc 13 §6.1): pipeline_failures rows — the same table derive_memory_failed_step and the code pipeline's derive_code_failed_step write into today — each naming its failed step and its reason, with a per-row retry (POST /api/v1/pipeline-failures/{id}/retry) and a header-level retry all (POST /api/v1/pipeline-failures/retry-all). A row whose attempts counter keeps climbing on the same failed step is surfaced as poison rather than left to retry unnoticed — the visual counterpart to the buffer-monitor's "attempts exceeded" poison state doc 13 §6.1 describes for the staged memory_buffer, applied here to the triage surface that already ships.

Failure triage — empty (healthy)

Healthy-empty, not "nothing here." Zero unresolved rows in pipeline_failures is a positive state, not an absence to explain away (doc 14 §5's third empty register: "a queue at zero"), so the copy states plainly that recent runs completed cleanly rather than rendering a bare blank indistinguishable from a broken triage list.

Failure triage — error (list failed to load)

Honesty rule: error ≠ empty list. A failed GET /api/v1/pipeline-failures request is not the same thing as "no failures" — conflating the two would hide real unresolved rows behind a healthy-looking empty state. The named failure keeps the last-known unresolved count visible and offers retry, matching the language's standard error treatment (doc 14 §5).

Each row names its failed step and its reason. Row 1–3 are ordinary, single-digit-attempt failures — a memory stuck on extraction, a memory stuck on content_embedding, a repo stuck on community_detection — each with the raw error_message shown verbatim (never summarised into a generic "failed").
