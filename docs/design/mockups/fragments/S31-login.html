S31 — Auth: Login, populated (hero, both themes)

Scope of this fragment. Realises doc 13 §2/§3's _guest layout route (/login) — the atmospheric glass card centred over the particle/aurora backdrop (doc 14 §2: "the login/setup flow's glass card over the interactive particle/aurora backdrop ... is the language's ceremonial register, reserved for the unauthenticated threshold surfaces"). The form mirrors the shipped login-card.tsx/login-form.tsx exactly: darkmem is single-admin, trust-on-first-use (doc 18 §3) — one password field, no username, because there is exactly one account to authenticate against. States: 4 boards — populated (this one, hero in both themes) / loading / error / rate-limited lockout.
Static still-frame — motion out of scope. The live component (particle-background.tsx) drifts particles continuously, links nearby nodes, and repels/links toward the cursor when interactive; it degrades to fewer particles with no cursor interaction on touch/low-core devices, and to exactly this kind of single frozen frame under prefers-reduced-motion (doc 14 §7 lists "the existing particle backdrop on the threshold surfaces" as one of the app's few closed motion-as-signal uses). This board renders that reduced-motion frame permanently — no canvas, no animation loop, no cursor listeners.
Token-derived, not hardcoded (mockup contract). The shipped component today hardcodes its palette (#818cf8, #22d3ee, ...). This board instead derives every backdrop colour from --primary / --chart-1 / --chart-5 / --info so the atmosphere already re-themes with an accent change — the same migration doc 14 §2's "no hardcoded hex in app components, ever" rule implies for the component itself, not yet done in frontend/src.

S31 — Auth: Login, rate-limited lockout

Per-IP lockout, honestly named as a distinct state, not another "invalid password" (doc 18 §3). Login rate limiting is per-IP with lockout — the client IP comes from X-Real-IP under a trusted proxy, never the spoofable leftmost X-Forwarded-For. The shipped LoginRateLimiter defaults (backend/app/services/login_rate_limit.py) are 5 failed attempts inside a 300-second window before a 5-minute lockout; a locked IP gets 429 with detail: "Too many failed login attempts; retry in {n}s" and a Retry-After header, checked before the DB is touched or any password hashed. Doc 18 §3 marks these thresholds target-new to move from code constants into tunable config rows, and lockouts as journaling to events (auth_lockout, also target-new) — today each failed attempt already writes an auth_login_failed audit row.
