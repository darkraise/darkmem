The project switcher and the context chip are two distinct controls, never one. The switcher (left, solid, a dot + project name) sets the project scope — the isolation boundary that rides into every query key (doc 13 §2). The chip (right, dashed-until-set) declares the optional session applies_when — the UI's equivalent of the X-Darkmem-Context header. Conflating them — e.g. letting a project named "production" silently imply env=prod — would silently exclude every dev-only fact from retrieval and surface an exclusion count the user never asked for: a quietly-lossy behaviour doc 13 §3 names explicitly. Rendered separately, each stays honest about what it does: switching project changes what data set is visible; setting or clearing the context chip changes which facts in that data set apply.
The chip's default state (not shown as the hero above) is unset — dashed border, no fill, label "no context declared". When unset, the backend falls back through its own precedence chain, down to the selected project's registry applies_when default at the lowest tier (doc 13 §3) — so a project still contributes a default, but only through that chain, never through the switcher masquerading as a context declaration.

C03 — switched-project variant: scope-refetch intent

Shown in one theme only (theme parity already demonstrated by the shared token system in the reference board above). Realises doc 13 §2's contract that the composite (project, status[, is_archived]) filter rides into the TanStack Query key, so switching the project switcher changes that key and every scoped view refetches against the new scope — never a client-side re-filter of an over-fetched set.
project: darkmem-core-backend → project: acme-storefront refetching
memories Memories list refetching
vaultFacts, vaultArticles, topics Knowledge tabs refetching
activityFeed, dreamDigest Activity refetching
overview, stats Dashboard calendar + tiles refetching
retrievalTrace why-retrieved trace (Memories) refetching
The context chip is untouched by this switch — it still reads "context: env=dev" exactly as before. That is the decoupling made visible: the switcher changed project and every key derived from it; nothing about the declared applies_when changed, because the two controls sit on independent axes (doc 13 §3). A design that tied them together would have to either clear the chip on every project switch (surprising) or carry a stale context into the new scope (also surprising) — keeping them separate avoids both failure modes.
