S27 — Settings · Jobs

The JobRegistry configuration surface (doc 13 §7, doc 02 §5.3) for the same seven registered jobs S21's Activity job board monitors — read here for editing rather than operating. This screen edits cron and enabled per job (PUT /api/v1/jobs/{key}) and any job-declared config_schema fields (PUT /api/v1/jobs/{key}/config); min_interval_seconds (the floor) and max_run_seconds (the ceiling) stay read-only registration constants here, exactly as they do on S21's gear dialog — there is no write path for either. Both writes share the job's asyncio.Lock with the scheduled loop, so a save can never race a running tick; a cron-only edit takes effect on the job's next scheduled tick, while flipping enabled restarts the loop immediately. Run history, the manual Trigger now action, and the busy (HTTP 409) outcome live on S21's Activity job board, not here.

Jobs configuration — empty (fresh install, no per-job overrides saved yet)

Honesty rule: empty says why, and here it cannot mean "no jobs." All seven jobs are registered in code at process startup (app/main.py) — the list itself can never legitimately render zero rows, same invariant as S21's empty board. The honest empty condition for a configuration surface is different from S21's "no run history": no config row exists yet for any job, so every field below is load_config's synthesized default (the job's default_cron, an implicit enabled switch, and each declared config_schema field's own default) rather than a persisted override — nothing is written until the first Save.

Jobs configuration — error

Honesty rule: error ≠ empty list. When the config-table read behind GET /api/v1/jobs fails, this Settings board raises a named error rather than returning zero rows indistinguishable from the genuinely-never-saved empty state above (invariant 14) — retry stays offered, and the cause is the failing thing, never the user (doc 14 §7 copy voice). The job registry itself, and every scheduled loop it runs, is unaffected on the server side while this Settings screen cannot read or edit it.
Jobs configuration error
Couldn't load job configuration — the config-table read failed The config rows keyed job:<key> could not be read, so cron/enabled/config_schema values cannot be shown or edited here. Scheduled ticks keep running server-side on their last-saved schedule regardless. Retry

Jobs configuration — populated (hero, both themes)

All seven registered jobs (doc 02 §5.3): repo_sync, code_enrichment, token_blocklist_cleanup, pipeline_failure_cleanup, graph_orphan_cleanup, tag_orphan_cleanup, expired_memory_cleanup. Each card's schedule section (cron + the enabled switch) is editable and saves through PUT /api/v1/jobs/{key}; the registration constants section (min_interval_seconds floor, max_run_seconds ceiling) is always read-only, the same treatment S21's gear dialog gives them — never depict them as editable. The config_schema section is editable and saves through PUT /api/v1/jobs/{key}/config only where a job declares fields: code_enrichment is the only one of the seven with a declared field (batch_size, default 5, min 1, max 100) — the other six honestly show "no fields declared" rather than an empty editable form. tag_orphan_cleanup below is shown switched off, to demonstrate that state: disabling stops its scheduled loop from restarting, but every field stays editable so it can be turned back on. Operational monitoring — last-run status, the manual Trigger action, the busy(409) outcome — is out of scope for this Settings board; see S21-populated / S21-config-dialog / S21-busy on the Activity job board.
