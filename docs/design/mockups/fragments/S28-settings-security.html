S28 — Settings · Security

The Security tab (doc 13 §7, doc 18): auth (the admin password-change form and the signed-in session's cookie-JWT state), tokens (the refresh/blocklist rotation state and the mass-revocation-by-iat rule a password change triggers), and TOFU status (the trust-on-first-use setup claim and the require_uninitialized gate it leaves behind). The panel also renders the LAN trust model honestly as the v1 committed posture (doc 18 §2: /mcp unauthenticated behind the Host allowlist only, /api/v1+/ws behind the human cookie, /setup as TOFU) and keeps the dormant ApiKey bearer path visibly Phase‑4, designed but not wired — every write today still passes api_key_id=None — so nothing on this screen ever overclaims a credential path that does not exist yet (invariant 23).

Security — empty (fresh install, just past the TOFU claim)

Honesty rule: empty says why, and here it cannot mean "no security config." Auth and TOFU status are never legitimately absent — the moment the setup wizard finalizes, admin_password_hash exists and require_uninitialized is already gating /setup. The honest empty condition for this screen is a fresh box with zero event history: no token rotations yet, no lockouts yet, the MCP allowlist still at its shipped default (localhost-only, MCP_ALLOWED_HOSTS unset). The TOFU status card below is this board's required verification surface (doc 13 §7) and it already reads claimed, never "empty" — a bootstrap outcome is not a list that can have zero rows.

Security — error

Honesty rule: error ≠ empty list, and it does not mean you were signed out. When the config/token_blocklist read behind this panel fails, the board raises a named error instead of quietly showing zero rows indistinguishable from the genuinely-fresh empty state above (invariant 14). Your own cookie session is unaffected — you are still authenticated, since reaching Settings already required it — this failure is scoped to the panel's own read, not to auth itself.

Security — populated (hero, both themes)

Five module cards: Auth (session state, password change, per-IP login rate limiting), Tokens (blocklist rotation, the three-exit lifecycle, cookie_secure's tri-state), Setup — trust-on-first-use (the required verification surface for this board), LAN trust model (the three doors of doc 18 §2, rendered as the shipped v1 posture, plus the live MCP_ALLOWED_HOSTS allowlist), and the dashed, muted programmatic ApiKey bearer card — every field and button inside it is disabled, because the api_keys table is dormant and unwired (doc 18 §5): this is a Phase‑4 activation item with a fixed design, not a toggle a v1 operator can flip.

LAN trust model v1 committed posture
darkmem trusts its LAN, authenticates its human, and attributes — but does not authenticate — its agents (doc 18 §1). Three postures, one service layer underneath all of them:
/mcpHost allowlist only, no credential
Unauthenticated by design (invariant 20). A foreign Host header gets 421, fixed by extending the allowlist — never by disabling the check.
localhost (always) 192.168.0.195:8000 * — disables the check entirely (explicit operator decision, not a fix)
/api/v1 + /wscookie JWT — the human door
The one authenticated door on this box; /ws rejects a missing/invalid/revoked token with close code 1008 before joining the broadcast set.
/setuptrust-on-first-use, open only until claimed
See the Setup card above — closes itself permanently the moment the first wizard run completes.
Programmatic ApiKey bearer Phase-4 · designed, not wired
The api_keys table exists in the schema but is dormant — every write on this box today still passes api_key_id=None. This card previews the fixed design (doc 18 §5) so no interim feature invents a second credential shape; it is not available in this deployment and every control below is disabled.
capture read admin ratify — never a scope, human cookie session only
Activates on the first genuine off-LAN need — an exposed deployment or the repo push-webhook receiver, whichever comes first — and is a recorded design, not a v1 commitment (doc 18 §5, invariant 23). The Host allowlist above stays on even after activation; a bearer key is defense in addition to it, never instead of it.
