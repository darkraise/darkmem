S18 — Activity: five-phase pipeline stepper

The per-memory module of the Activity shell (doc 13 §6.1, doc 02 §5.2): each captured memory's progress through content embed → extract-and-classify → entity embed → dedup → write, ending in one of three honest terminal states — completed, partial, or failed. A partial memory always names exactly which step broke, using pipeline_failures.failed_step's durable named-step vocabulary as derive_memory_failed_step resolves it — content_embedding, extraction, extraction_partial, vector_write, graph_write — never a collapsed batch pass/fail (invariant 14). The /ws payload (PipelineStatus) carries a different, shorter set of fields for the same four checkpoints — embed / extract / vector / graph, each resolving to ok / error / partial / skipped — which derive_memory_failed_step reads to produce the named step above; the two vocabularies are related, not identical. Entity embed and dedup (phases 3–4) are batch-level ANN operations that degrade gracefully on a miss rather than failing a single memory, so the named-failure vocabulary only ever points at phase 1 (content_embedding), phase 2 (extraction / extraction_partial), or one of phase 5's two savepoints (vector_write / graph_write).

S18 — pipeline stepper: running

The non-terminal state every memory starts in once claimed from the buffer (doc 02 §5.2: [*] → running : claimed from buffer). The pipeline broadcasts exactly one terminal pipeline.* event per memory, after all five phases finish (pipeline.py, the process_memory broadcast) — PipelineStatus (events.py) has no progress or current-phase field, and there is no pipeline.running / pipeline.progress event, so the client has no way to know which phase is currently executing. The stepper below renders every node pending — it is the decomposition the one eventual terminal broadcast resolves into, not a live per-phase progress bar.

S18 — pipeline stepper: partial (named failed step)

Honesty rule: a partial memory names its failed step — never a collapsed batch pass/fail. pipeline.partial fires whenever at least one checkpoint reports ok and at least one does not; the failed step is read off the same status dict the /ws payload carries, via derive_memory_failed_step — hard step errors (checked in phase order, first one wins) take priority over a merely degraded extraction. S18 — pipeline stepper: failed

Terminal — failed. pipeline.failed fires only when every checkpoint that actually ran reports non-ok — a single early failure whose later steps still land as skipped (not attempted) is not enough on its own; here content embedding and extraction both errored independently, so vector and graph write never ran. derive_memory_failed_step checks hard errors in phase order and the first one wins, so the named step is content_embedding even though extraction failed too.
