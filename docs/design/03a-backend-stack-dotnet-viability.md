# 03a — Backend Stack Viability: .NET

**Status:** design-phase research annex to doc 03 (Technology & stack decisions). Draft 2026-07-23.
Part of the unified target design — see `docs/design/README.md` for the frame and document map. This memo **re-examines the README's locked-frame decision 4 ("proven stack retained — Python/FastAPI") at the maintainer's request**. It is evidence feeding doc 03's backend-language ADR and may amend that locked decision; it does not itself change the frame. It re-opens only the *application language and runtime* question — the single-Postgres principle (doc 00 §7.1), per-fingerprint partitioning, the deterministic extraction post-processor, and the tree-sitter code graph (the moats, doc 00 §6) are held fixed, and the question is narrowly whether each can be re-expressed in C#/.NET without loss.

---

## 1. Question & scope

**The question is bounded: is .NET a *viable* backend for the target darkmem, where viable is a three-part test — (a) no hard blocker, (b) acceptable and mitigable residual risk, and (c) a net benefit large enough to justify rewriting a mature codebase.** All three must hold. A stack that clears (a) and (b) but fails (c) is technically possible and still the wrong choice; this memo keeps the three tests separate rather than collapsing "it can be done" into "it should be done."

**What is in scope is the backend only.** The React frontend is stack-independent — it speaks REST and WebSocket over HTTP and does not care whether the server is Python or C# — so it is out of scope and carries across either decision unchanged. What is in scope is every backend subsystem doc 02 names: the API and MCP front doors, the services layer (ingestion pipeline, retrieval, extraction/classification, code indexing, jobs, the LLM orchestrator), the repositories over one Postgres, and the deployment artifact.

**One material simplification is already banked: the ML stack is gone.** The 2026-05-01 LLM-only consolidation removed `torch`, `transformers`, `gliner`, and `rebel` from the core dependency set; they survive only as an optional `[ml]` extra, lazily imported behind `try/except` and gracefully degrading when absent. A .NET port therefore inherits **no Python-native machine-learning lock-in** — it must reproduce HTTP LLM calls, not a native ML runtime. This removes what would otherwise have been the single strongest argument for staying on Python, and it is why the question is worth asking at all in 2026 when it would not have been in early 2026.

**The frame this memo respects.** Whatever the language, darkmem stays one process over one Postgres with pgvector (doc 02 §2, §4). Nothing below proposes a second datastore, a broker, or a service split; the polyglot option in §8 is examined precisely *because* it strains that single-artifact principle, and is weighed against it rather than around it.

## 2. TL;DR — verdict and the decisive factors

**Verdict: viable, but only under conditions.** .NET clears test (a) — there is no hard blocker; every red-rated area has a concrete, named mitigation. It clears test (b): after the 2026-07-23 gap-closure spikes (§4.1) and the tree-sitter port investigation (§5.1.1), **21 of the 24 matrix rows are green, 3 are yellow, and none are red** — every remaining item (the tree-sitter grammar CI pipeline, Leiden parity/scale validation, the eval-harness rebuild) is bounded build/validation work, not a feasibility wall. Feasibility is settled. Test (c), whether the benefit justifies the rewrite, is genuinely open and turns on judgment calls only the maintainer can make (§10). The recommendation is therefore down to appetite, not feasibility: **feasibility is settled (no red remains); pursue .NET if the maintainer's appetite favours doing the rewrite now as the greenfield build.** Absent that appetite, the locked Python frame stands.

**Four factors decide it:**

1. **No hard blocker survives scrutiny; the risk concentrates in two areas.** The data layer, the API/LLM/jobs/deployment layer, and — correcting the raw inventory — the MCP transport are all overwhelmingly green and map close to 1:1 (the MCP surface keeps two small yellows, see factor 2). The genuine red flags were code indexing (tree-sitter language bindings) and community detection (Leiden). **The community-detection red has since been spike-cleared** (§5.2, `spikes/dotnet-graph/`): pure-managed Louvain + connectivity refinement + PPR works with no native dependency, leaving tree-sitter as the one significant remaining risk. It is mitigable; it is not a wall.

2. **The MCP concern was overstated: the transport is green, with two small known yellows.** The dependency inventory rated the FastMCP `/mcp` mount "HIGH friction — no first-party .NET equivalent." That is out of date: the official Microsoft-collaborated `ModelContextProtocol` C# SDK reached stable v1.4.1 (2026-07-09) and covers streamable-HTTP JSON-RPC, stateless mode, a subpath mount, and attribute-based tool registration — the transport itself is green. Two small yellows remain, both drawn from the matrix: the hand-written ~50–100-line Host/Origin-allowlist middleware (the SDK gives no MCP-transport-level allowlist), and a scoped-DI workaround (SDK issue #544) for header source-resolution. The residual work is genuinely small, so the surface is green overall — but it is green-with-two-yellows, not uniformly green.

3. **One real gap reintroduces native interop; the graph, once feared to need it, does not.** Tree-sitter on .NET means depending on a single-maintainer binding plus self-compiling roughly a dozen grammars per platform — the remaining native-interop concern and the highest-bus-factor part a spike must still prove out. Community detection, by contrast, was proven to run in *pure managed* C# (§5.2), so the feared native igraph dependency is avoided entirely.

4. **The upside is specific and the cost is a full rewrite.** In its favour: the team's primary strength is C#/.NET, the sibling **darkcloud** project already ships a .NET 10 single-file Kestrel service on a 4-core/4 GB homelab LXC, and Npgsql's strong typing eliminates the asyncpg `CAST`/`IndeterminateDatatypeError` bug class outright. Against it: a full rewrite of a large, tuned codebase, and the eval harness (doc 17) must be rebuilt before parity can be *measured* — and doc 00 §7.2 forbids shipping anything without a before/after number.

## 3. What darkmem's backend actually depends on

**Stripped to load-bearing dependencies, the backend is smaller than its `requirements.lock` suggests, and most of it is portable plumbing.** The honest "what must be replaced" list, grouped by how hard the replacement is:

**Clean 1:1 swaps (plumbing, no ecosystem lock-in).** FastAPI/Starlette/uvicorn → ASP.NET Core Minimal APIs on Kestrel. The hand-rolled multi-vendor LLM orchestrator is raw `httpx` with **no OpenAI SDK**, so it ports to raw `HttpClient` as plain logic. JWT/bcrypt auth, the CORS-only middleware, the `/ws` broadcast, and the custom cron `JobRegistry` are all ordinary application code over standard-library primitives. None of these fight an ecosystem.

**Postgres surface — portable, and one bug class disappears.** Async SQLAlchemy 2.0 over `asyncpg`, used mostly as a raw-SQL executor via `text()`; `pgvector` columns in per-fingerprint child tables; recursive CTEs; savepoints; FTS with `ts_rank`/`plainto_tsquery`; GIN over `technologies[]`; Alembic migrations. Every one of these is native PostgreSQL that Npgsql executes verbatim. The `CAST(:vec AS vector)` wrappers darkmem carries are an **asyncpg quirk, not a portable invariant** — Npgsql resolves types client-side, so they are dropped, not copied.

**The hard replacements (native, algorithm-specific).** Three items have no drop-in .NET peer: **tree-sitter** with its 33 language grammars (dynamic `language_*()` dispatch, PHP/TypeScript special cases); **Leiden community detection** via `python-igraph` + `leidenalg` for the code graph, plus **Louvain** for the memory graph; and the **numpy/scikit-learn numeric core** hidden inside the vector repository — `DBSCAN` clustering, vectorised cosine-similarity matrices, and 2-D eigen-projection of the memory graph. This last one is easy to miss because it does not look like a dependency; it looks like "the vector repo."

**Three inventory corrections, carried forward as accurate.** `FOR UPDATE SKIP LOCKED` is **absent today** — it is a doc-02 §11 target, not current surface, so there is nothing to port. **PageRank / Personalised PageRank is absent today** — also target-not-yet-built (doc 00 §7.1, doc 02 §4 both name it as target), so it is greenfield in either language. And the asyncpg `CAST` requirement, as above, is a driver quirk that must not be re-enshrined as a correctness rule.

## 5. The real risk areas, deep-dived

**Three things carry the weight of this decision: the tree-sitter language bindings, the igraph/Leiden gap (with converged PageRank alongside it), and the sunk-cost port surface of a tuned codebase. Everything else in §4 is engineering with a known answer.**

### 5.1 Tree-sitter multi-language bindings

**This is the highest-effort, highest-bus-factor dependency in the whole backend, and the concern that darkmem is "likely the biggest risk" is largely justified — but it should be aimed at the right sub-point.** The binding *itself* is fine: TreeSitter.DotNet v1.3.0 (MIT, 2026-01-22) wraps libtree-sitter with the exact Parser/Node/Query API darkmem uses, ships prebuilt natives for nine RIDs, and turns the PHP/TypeScript multi-entrypoint quirk — a documented gotcha in the Python code — into an ordinary constructor argument. The large pure-logic layer above the parse tree (`heritage_resolver`, `type_env`, `symbol_table`, `call_resolver`, import/binding resolvers, node-type sets) is dependency-free darkmem code that ports to C# as ordinary logic.

**The two genuine red flags are maintenance depth and grammar breadth.** On depth: the port would swap a broad, organisation-backed ecosystem of 33 independently versioned grammar packages for a single-maintainer hobby project (~31 stars, 26 commits, bus-factor of one) as the load-bearing dependency for the *entire* code-indexing subsystem. On breadth: the monolithic package bundles 28 grammars, of which roughly 21 cover darkmem's 33 — leaving exactly 12 absent per the binding's README: kotlin, lua, yaml, sql, zig, elixir, xml, regex, cmake, make, objc, and markdown (12/33 = 36% of the language surface, the top of the earlier range). Each gap means compiling and bundling a native parser per RID yourself, with no PyPI-style package to lean on; the Kotlin, YAML, SQL, and Markdown gaps in particular would hit real repositories.

**Mitigation is concrete but not free.** Adopt TreeSitter.DotNet rather than hand-rolling P/Invoke; budget explicitly to **vendor/fork the binding** (it is MIT, and libtree-sitter is stable) so that a maintainer walking away is an inconvenience, not a crisis; and stand up a **per-RID grammar build pipeline** (tree-sitter CLI + a C compiler in CI) for the 12 missing languages listed above. Re-verify per-language node-type names against whatever grammar versions the .NET binding bundles — they can differ silently from the Python-package versions and quietly change which nodes match. Roslyn is C#-only and is **not** a substitute for a 33-language uniform graph; treat tree-sitter as mandatory.

### 5.1.1 Can tree-sitter (and the grammars) be ported to pure C#? — the maintainer's question

**Yes it is possible; no it is not worth it — and the good news is you don't need it, because the grammar residual is a CI build step, not a feasibility wall.** This was investigated directly (2026-07-23, adversarially verified).

**A pure-managed port is a 12-18 person-month trap that never finishes.** No pure-managed tree-sitter runtime exists in .NET — or in *any* language; the only non-C runtimes are machine-transpiled (`tree-sitter-c2rust`, kept 1:1 with upstream so changes re-merge cheaply). `lib/src` is ~15-20k lines of pointer-heavy C11 — a GLR table interpreter, a graph-structured parse stack, incremental reparse, an error-recovery cost model, and the ~5k-line `query.c` S-expression matcher. Worse, grammars are not just data: **8 of your 12 missing grammars ship a hand-written C external scanner** that codegen cannot produce and a managed runtime would have to reimplement and then sync forever — markdown (~75 KB, two scanners), yaml (~52 KB), kotlin (~35 KB), elixir (~19 KB), plus lua, cmake, sql, xml. Only 4 (zig, regex, make, objc) are pure-generated and cheap. A hand port trades one bounded CI chore for a 12-18 PM build, a perpetual upstream-tracking tax, and an open-ended per-grammar scanner-porting problem. It is justified only under a hard *no-native-code* mandate (strict AOT, Blazor WebAssembly) — and even then you would auto-transpile or compile to WASM, never hand-port.

**The clean way to green #14 is a CI grammar-build pipeline, not a port.** Fork TreeSitter.DotNet and add a CI stage where a C toolchain compiles the 12 missing grammars per RID with tree-sitter's own build — a bounded, understood chore. The objection that *this dev box* has no C compiler is a non-issue: grammar compilation belongs in CI, not on a developer's machine, and the 21 grammars that already ship prove the per-RID-native pattern works. This adds **no new class of dependency**, so #14 is a build task, not a feasibility red.

**The tempting shortcuts don't pay off.** *WASM grammars* look like a zero-native escape but don't compose cleanly: grammar `.wasm` are Emscripten side-modules needing the tree-sitter core, and the core-in-WASM (`web-tree-sitter`) ships JS glue a .NET WASM host can't run. Genuinely-managed WASM engines do exist (WACS, dotnet-webassembly), and tree-sitter's own `wasm_store.c` already loads grammar `.wasm` via wasmtime's C API (production-proven in Zed) — but the practical routes either keep a native core + native wasmtime per RID, or are greenfield with an interpreter perf cost and *still* need a WASM toolchain in CI. *ANTLR* is truly pure-managed but covers only 8 of the 12 — it misses **yaml, make, and markdown**, exactly the indentation-significant, non-context-free languages tree-sitter only handles through those external scanners (regex exists only as a PCRE-parser proxy) — and it is a paradigm split: no S-expression queries, a per-grammar visitor with divergent rule names, no incremental parse, weaker error recovery. Two maintenance worlds, failing hardest where you need help most; grammars-v4's "sql" is also 20 dialect grammars, not one.

**Recommendation: the CI grammar pipeline (optionally shipping the high-value languages first), not a port.** It retires #14 with bounded, understood work and no new dependency class. Reach for WASM or ANTLR only under a hard zero-native deployment mandate; a full pure-C# port only under a single-uniform-managed-parser mandate. Neither is advisable otherwise.

### 5.2 Community detection (Leiden / Louvain) and converged PageRank — spike-cleared

**This was the memo's hardest 🔴 and the maintainer's named deal-breaker; a hands-on spike on 2026-07-23 cleared it, and in a better way than the research anticipated.** The original plan was to P/Invoke the native C igraph library for Leiden — but the dev box has .NET 10 with no C compiler and no CMake, there is no prebuilt igraph .NET binding, and no dedicated C# Leiden library, so the practical question became whether community detection is achievable in *pure managed C#* with no native interop. It is. A ~250-line managed spike (`spikes/dotnet-graph/`) implements multi-level **Louvain**, a **Leiden connectivity-refinement** pass (splitting disconnected communities — the guarantee Leiden adds over Louvain), and **PageRank/PPR**, and on a planted 3-community graph it recovers the structure exactly (modularity Q≈0.60), splits a forced-disconnected community back out, and concentrates PPR in a seed's community. No igraph, no CMake, no per-RID native bundling.

**This downgrades the community-detection risk from 🔴 to 🟡 and removes one of the two native-interop dependencies §7 worried about.** The pure-managed route is not merely feasible but *cleaner* than the igraph P/Invoke path — it keeps the single-artifact ethos with no native build step, and one code base serves both the code-graph Leiden refinement and the memory-graph Louvain. Converged / **Personalised PageRank** — absent from darkmem today (doc 00 §7.1, doc 02 §4 name it as target) and greenfield in either language — is confirmed trivial: a CSR power-iteration loop, PPR differing only in a concentrated teleport vector, giving full control of damping, teleport set, and convergence over a cached in-process snapshot.

**What the spike did *not* prove, and what remains before production.** The refinement implements Leiden's *connectivity* guarantee, not its full randomised refinement phase, so quality parity versus `leidenalg`'s `RBConfigurationVertexPartition` and behaviour at real darkmem graph scale still need validation; and results will not be bit-identical to the Python output (acceptable for a soft grouping signal, but any test pinning exact membership must tolerate it). The recommended stance is therefore: **build community detection in pure managed C# (Louvain + connectivity refinement + hand-rolled PPR), and validate quality and scale against the current Python outputs** — do not reach for native igraph unless that validation forces it.

### 5.3 The sunk-cost port surface

**The rewrite's real cost is not the plumbing; it is re-earning the tuning that makes darkmem good.** Three tranches of accumulated work sit on the line, and they port very differently:

**The ~40 deterministic extraction cleanup passes — the moat in doc 00 §6 — are portable logic.** They are pure functions over extracted entities and relations (fan-out, discriminator gating, REPLACES/CAUSES/temporal handling, literal and descriptor filters, the type-override maps). They translate to C# as ordinary code with no third-party dependency, but they are *load-bearing and tuned* — the entity/relation F1 gains are measured — so they must be ported faithfully and then re-validated, not paraphrased.

**The eval harness and `benchlib` are Python and must be re-implemented.** They are stdlib-only wrappers over app code — the bench-database lifecycle and the content-hash `sha256` LLM cache that lets extraction iterate without re-hitting a model, plus the F1 gold benchmark. There is no shortcut here: doc 00 §7.2 forbids shipping without a before/after number, and doc 17 makes the harness a first-class deliverable, so the harness has to exist in the new stack **before** parity with today can be claimed at all. The gold data itself (JSON) carries across unchanged.

**The tuned prompts are portable and are the cheapest tranche to move.** Extraction and classification prompts, the seed-forwarding scheme, and the vendor-quirk dispatch are strings and plain branching; they move verbatim. The reproducibility seed (`sha256(content)[:8]` as a 32-bit int) is a typed `ChatOptions.Seed` in .NET, so that behaviour actually gets cleaner. The net shape: **keep the prompts, port the cleanup passes faithfully and re-validate them, and rebuild the harness first** so "faithful" is a measured claim rather than a hope.

## 6. What .NET actively buys darkmem

**The case *for* is specific, not vibes, and it is strongest on team fit and operations.** Four concrete gains:

**Team strength and a proven precedent.** The team's primary strength is C#/.NET, and the sibling **darkcloud** project already ships a .NET 10 single-file Kestrel service on the exact target — a 4-core/4 GB Linux LXC on the homelab. Deployment, single-file publish, and Kestrel-on-a-small-box are not hypotheticals to prove; they are a pattern already running next door. This directly de-risks the deployment row of the matrix and lowers the ongoing-maintenance cost of the backend to the team's home turf.

**Npgsql eliminates a whole bug class rather than porting it.** The asyncpg `CAST`/`IndeterminateDatatypeError` pattern — a recurring, query-context-dependent runtime surprise that darkmem currently defends against with `CAST` wrappers scattered through raw SQL and enshrined as a cross-cutting invariant — simply does not exist under Npgsql, which resolves parameter types client-side and sends an explicit OID. The failure mode that remains (a mismatched CLR-inferred type) is an explicit per-parameter annotation that fails loudly and identically every time. That is a real reduction in a class of silent-correctness risk, not a lateral move.

**First-class async and a typed LLM surface.** ASP.NET Core is async-native with no greenlet bridge, and the LLM layer is where .NET quietly does *more* than the Python code: the reproducibility seed is a typed option, Anthropic's `x-api-key`/version auth is handled inside the official `Anthropic` SDK (beta as of 2026-07), and Ollama `think`/OpenAI `reasoning_effort` are typed knobs — so several vendor quirks darkmem hand-codes today become library concerns. The Microsoft.Extensions.AI ecosystem (stable `.OpenAI` 10.8.0) is available as an on-ramp if ecosystem tooling is ever wanted, though a faithful raw-`HttpClient` port keeps the single uniform code path darkmem deliberately chose.

**Footprint and startup.** Single-file self-contained publish needs no runtime installed on the box; Native AOT (reachable only on a Dapper/Npgsql, EF-free design) offers sub-100 ms startup and materially smaller images and memory. For a single-instance homelab deployment these are modest but real wins, and they align with darkmem's single-artifact ethos better than a Python interpreter + venv + wheel set. They also meet the maintainer's confirmed **one-image constraint** (backend + built frontend in a single Docker image, Postgres separate) most cleanly: Kestrel serving the built SPA from the same process is the idiomatic .NET pattern darkcloud already runs, whereas the Python path satisfies the same constraint by serving static files from FastAPI or co-packaging nginx in the image — achievable, but a shade less clean (doc 02 §8).

## 7. What it costs

**The case *against* is dominated by one fact: this is a full rewrite of a large, mature, tuned codebase, not a migration.** The costs, honestly:

**Re-earning parity is gated on rebuilding the harness first.** You cannot trust — or even measure — that the ported extraction matches today's until the eval harness exists in the new stack, and the harness is Python that must be re-implemented before the first parity number lands. Until then the ~40 cleanup passes are ported *on faith*, which is precisely the mode doc 00 §7.2 exists to forbid. This front-loads real work before any of it can be validated.

**One native-interop dependency re-enters a codebase whose ethos is one artifact.** tree-sitter (a forked binding plus a per-RID grammar toolchain) adds native-compilation and platform-bundling concerns that the Python stack currently gets for free from prebuilt wheels. This does not break the single-Postgres or single-*process* principles, but it does dent the single-*artifact* simplicity, and it adds a maintenance surface the team owns. Community detection, once feared to need native igraph, was spike-proven to run in pure managed C# (§5.2), so it adds no native dependency.

**The Leiden quality caveat is a permanent, not transient, cost.** The pure-managed community detection matches `leidenalg` closely but not bit-identically (a different implementation), so code-graph and (target) topic communities will differ from today's and will not be reproducible against the Python outputs. That is acceptable for community detection — communities are a soft signal — but it must be accepted knowingly, and any test that pins exact community membership has to be rewritten to tolerate it.

**Giving up Python's data-science iteration speed — weighed against the fact it was deliberately removed.** If machine learning ever re-enters darkmem (a local classifier, an ONNX head, an embedder fine-tune loop), Python's numpy/sklearn/transformers iteration speed is a genuine advantage that .NET does not match. The honest counterweight: the ML stack was *deliberately* removed on 2026-05-01, the design (doc 00, doc 02) treats classification as LLM-backed by default, and .NET can host ONNX if a head returns. So this is a real cost only under a future the current design has explicitly stepped away from — weigh it as a low-probability regret, not a live constraint.

## 8. Options

**Three options are on the table; each is stated with its trade-off, and the polyglot option is measured against the single-artifact principle rather than around it.**

**Option A — stay Python/FastAPI (the current locked frame).** Zero rewrite; the mature, tuned codebase and its harness stay intact; the moats keep working as-is. The cost is opportunity: the team operates on a stack that is not its primary strength, and it forgoes the Npgsql bug-class win and the darkcloud-proven deployment ergonomics. This is the safe default and the fallback if the Phase-0 spike (§9) fails.

**Option B — full .NET rewrite.** The whole backend moves to C#/.NET on the team's home turf, with the operational and typing gains of §6. The cost is §7 in full: a large rewrite, the harness rebuilt before parity can be measured, and two native-interop dependencies (tree-sitter, igraph) re-entering the artifact. This is coherent with the locked frame's *other* decision — that a from-scratch rebuild is already an accepted path (README decision 3) — so it is not as radical against the design phase as it first looks; it is the language axis of a rebuild the frame already sanctions.

**Option C — polyglot: .NET core plus a thin Python sidecar for tree-sitter, graph, and eval only.** This is tempting because it puts the two red areas (§5.1, §5.2) and the numeric core (§5.3) back on Python, where prebuilt wheels and `leidenalg`/`igraph`/`numpy` all just work, while the API/LLM/jobs/data layers get the .NET benefits. **But it directly dilutes the single-process/single-artifact simplicity that doc 02 §2 and §8 treat as load-bearing** — it introduces a second runtime, an inter-process boundary (HTTP or subprocess) on the code-indexing and community-detection paths, a second dependency set to lock and deploy, and a second thing to operate on the 4 GB LXC. It does not touch the single-Postgres moat, but it trades the clean "one box, one process" story doc 02 §8 sells for exactly the multi-service shape darkmem markets itself as *avoiding*. If a spike shows tree-sitter and igraph interop are genuinely intractable in-process, C is the escape hatch — but it should be a consequence of a failed spike, not a first choice, because it forfeits a principle the design explicitly values.

## 9. Recommendation & decision criteria

**Recommendation: treat .NET as viable — the 2026-07-23 gap-closure spikes (§4.1) and the tree-sitter port investigation (§5.1.1) turned every feasibility-uncertain row green and left no red.** The evidence firmly does not support ruling .NET out, and by the §4 matrix — post-closure — **21 of 24 rows are green, 3 yellow, 0 red**, the three yellows all bounded build/validation work (grammar CI pipeline, harness rebuild, Leiden validation). The open question is no longer feasibility; it is purely appetite for the rewrite.

**The remaining Phase-0 work is bounded and mostly done.** Of the three original de-risking items, two are cleared and the third is half-cleared: item 2 (community detection) and item 3 (pgvector round-trip) both passed live on 2026-07-23, and item 1's binding half passed — leaving only item 1's grammar pipeline, which is a CI build task (a C toolchain compiling 12 grammars per RID) rather than a quick spike, because this dev box has no C compiler:

1. **A tree-sitter multi-language parse in-process — ⚠️ binding proven 2026-07-23, grammar pipeline residual** (`spikes/dotnet-treesitter/`). TreeSitter.DotNet parsed C#/Python/PHP and ran an S-expression query with capture + `#eq?` predicate metadata across bundled grammars — the binding, the query engine, and even the PHP quirk are green. **What remains is the #14 residual:** self-compiling the 12 unbundled grammars (kotlin, lua, yaml, sql, zig, elixir, xml, regex, cmake, make, objc, markdown) per RID, which needs a C toolchain + CI pipeline this box lacks. This is the one item still gating 'all green.'
2. **Community detection + Personalised PageRank over a sample graph — ✅ done 2026-07-23** (`spikes/dotnet-graph/`). The pure-managed Louvain + Leiden-connectivity-refinement + PPR spike passed (planted structure recovered at Q≈0.60; a forced-disconnected community split back out; PPR localised to the seed's community), clearing the §5.2 red **without** native igraph. The remaining follow-up is quality/scale validation of the managed community detection against the Python outputs — a validation task, not a feasibility question.
3. **A pgvector per-fingerprint round-trip — ✅ done 2026-07-23** (`spikes/dotnet-data/`). Live against the dev Postgres: runtime child-table DDL with a sanitised slug, a **no-`CAST`** vector insert through Npgsql, and the `1-(embedding <=> $1)` cosine query all worked (top match sim=1.0) — the data-layer green holds end-to-end and the asyncpg-quirk correction is real in practice.

**What decides it now.** Feasibility is settled — the spikes and §5.1.1 leave no red — so the lever is appetite. To **stay on Option A (Python)**: the maintainer does not want a ~5-9 engineer-month rewrite now. To **commit Option B (.NET)**: the appetite favours the rewrite now as the greenfield build, the grammar CI pipeline and harness rebuild are accepted as early work items, and parity is measured (not assumed) once the harness exists.

**Coarse rewrite effort, if the spike passes and Option B proceeds.** These are order-of-magnitude, single-engineer ranges meant as a magnitude anchor for the appetite question (§10 Q1), not a commitment — the estimates are judgment/training-knowledge, not web-verified, and the two low-confidence tranches drive the spread:

| Tranche | Coarse effort | Confidence | What it covers |
|---|---|---|---|
| Plumbing / API front doors | 3–6 wk | High | ASP.NET Core Minimal APIs, the MCP mount + allowlist middleware, JWT/bcrypt auth, the `/ws` broadcast, the `JobRegistry` port, the deployment artifact — the §4 greens |
| Data layer | 2–4 wk | High | Npgsql + pgvector, per-fingerprint child tables, CTEs/FTS/savepoints, the DbUp chain + baseline cutover |
| Pipeline + ~40 cleanup passes | 6–12 wk | Medium | Faithful port and re-validation of extraction/classification, the deterministic cleanup passes, supersession, hybrid retrieval/RRF/rerank |
| Eval harness + `benchlib` rebuild | 2–4 wk | Medium | Bench-DB lifecycle, content-hash LLM cache, F1 gold bench — must exist before parity can be measured (doc 17) |
| Code indexing + graph interop | 6–12 wk | Low | tree-sitter binding fork + per-RID grammar pipeline (12 gaps), igraph P/Invoke (Leiden + Louvain), the numeric core (DBSCAN / cosine / eigen) |
| **Aggregate** | **~19–38 wk (≈5–9 mo)** | — | Sequential single-engineer; the two low-confidence tranches dominate the range, and the Phase-0 spike exists precisely to shrink them before the clock starts |

## 10. Open questions for the maintainer

**These are the decision points the evidence cannot settle — they are judgment calls, not research gaps, and they are what test (c) actually hinges on:**

1. **Appetite: rewrite now, or after the Python target ships?** The locked frame already accepts a rebuild (README decision 3). Is the appetite to make *this* rebuild the .NET one — paying the port cost once, on a greenfield — or to ship the Python target first and treat .NET as a later, separate migration? The §9 effort table sizes that port at roughly 5–9 engineer-months; the two paths have very different risk profiles and cannot both be cheap.

2. **Tolerance for native interop in a single-artifact system.** Is a forked tree-sitter binding plus a pinned igraph P/Invoke layer — each with per-RID native builds in CI — an acceptable standing dependency, given that the design otherwise prizes "one box, one process, one artifact"? If the answer is no, Option B is effectively off the table and the real choice is A versus a reluctant C.

3. **The bar: parity-with-today, or a clean-slate feature set?** Is the rewrite's success measured as *behavioural parity* with the current tuned pipeline (in which case the harness-first, faithful-port discipline of §5.3 is mandatory and expensive), or is it a clean-slate build of the doc-00 target where some current behaviours are intentionally *not* reproduced (in which case the sunk-cost port surface shrinks, and the calculus tilts toward B)?

4. **Acceptance of the Leiden non-determinism.** Is it acceptable that code-graph and (target) topic communities under the igraph P/Invoke route will differ from today's and will not be bit-reproducible against the Python outputs? This is a permanent property of the recommended mitigation, not a spike risk.
