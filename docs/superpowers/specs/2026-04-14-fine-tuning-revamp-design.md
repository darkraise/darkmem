# Fine-Tuning Revamp — Design

**Status:** Draft for review
**Author:** Brainstorming session 2026-04-14
**Supersedes (in part):** `docs/e2e/runs/2026-04-13-fine-tuning-plan.md`

## Goals and success criteria

Produce three production-ready fine-tuning corpora and four fine-tuned model families, plus a stubbed fourth corpus for a future documents pipeline.

**Corpora (≥10K each, on disk under `fine-tuning/data/v2/`):**

- **Extraction**: ≥10K examples with character-level entity spans, relation triplets, and a memory-type label per item. One source of truth feeds GLiNER, REBEL, and any future LLM extractor.
- **Memory classification**: ≥10K examples with one of seven memory-type labels (sharpened `reference` definition).
- **Embedding pairs**: ≥10K (query, positive) pairs anchored on the extraction corpus texts, two queries per source memory in question form and keyword form.
- **Document classification (stub)**: taxonomy defined, ~200 reference examples written, full generation deferred until the documents UI defines a real input distribution.

**Model lineup (9 models trained, qwen3.5:4b enters every eval as a prompted baseline):**

| Purpose | Trained models | Prompted baselines (no training) |
|---|---|---|
| Entities | GLiNER-large, GLiNER-small | qwen3.5:4b prompted via tool call |
| Relations | REBEL-large, mREBEL-base | qwen3.5:4b prompted via tool call |
| Memory classifier | DistilBERT, MiniLM, RoBERTa-large | qwen3.5:4b prompted (current best at 0.817) |
| Embedding | Qwen3-Embedding-0.6B, EmbeddingGemma-300M | bge-base-en-v1.5 + EmbeddingGemma-300M pretrained |

**Strict 1B-parameter cap on all *new* model candidates.** qwen3.5:4b is exempt because it is the existing production reasoning model, not a new candidate; it participates only as a prompted baseline this round.

**Success criteria (all must hold to declare the revamp complete):**

- Entity F1 ≥ 0.96, type accuracy ≥ 0.94 on the held-out test split (today: 0.904 / 0.901).
- Relation F1 ≥ 0.90, direction rate ≥ 0.95 (today: 0.654 / 1.000 — direction is fine, type/recall need lift).
- Memory classifier accuracy ≥ 0.90 on the existing 60-example gold set, with `reference` recall ≥ 0.70 (today: 0.817 best, `reference` 0.38).
- At least one fine-tuned embedder beats pretrained EmbeddingGemma's R@1 of 0.752 on the 270-query test set.
- Combined VRAM for the production stack (best entity + best relation + qwen3.5:4b + best classifier + best embedder) stays under 6 GB so the existing 8.5 GB GPU isn't blocked.

## Corpus architecture

**Three live corpora plus one stub, all under `fine-tuning/data/v2/`** (the existing `data/` stays in place during the audit):

```
fine-tuning/data/v2/
├── HANDOFF.md
├── shared/                  # 7K items, one row per memory, all three labelings
│   └── shared.jsonl
├── extraction/              # extraction-only top-up, 3K items
│   └── topup.jsonl
├── classification/          # memory-classifier-only top-up, 3K items
│   └── topup.jsonl
├── retrieval/               # embedding-pair top-up, 3K extra pairs
│   └── topup.jsonl
├── documents/               # stub: taxonomy + ~200 reference items
│   └── seed.jsonl
├── failed/                  # validator rejects, retried in later sessions
└── splits/                  # generated by build_splits.py, not hand-written
    ├── extraction_{train,val,test}.jsonl       # 8K / 1K / 1K (sourced from shared 7K + extraction top-up 3K)
    ├── classification_{train,val,test}.jsonl    # 8K / 1K / 1K (sourced from shared 7K + classification top-up 3K)
    ├── retrieval_train.jsonl                    # ~14K pairs (7K shared × 2 queries) + retrieval top-up (~3K) = ~17K total
    ├── retrieval_val.jsonl                      # 10% held back from retrieval_train, stratified by source domain
    └── retrieval_test.jsonl                     # symlink/copy of docs/e2e/scripts/retrieval_eval/queries.jsonl (270 fixed queries; passage pool stays gold.jsonl, 195 memories)
```

**Shared row schema (canonical source of truth):**

```json
{
  "id": "shared-00042",
  "domain": "technical|ai_coding|personal|knowledge|cross|noise",
  "text": "We switched from Celery to asyncio because Redis was the only remaining dependency.",
  "memory_type": "decision",
  "noise": false,
  "entities": [
    {"name": "Celery", "type": "framework", "start": 21, "end": 27},
    {"name": "asyncio", "type": "library", "start": 31, "end": 38},
    {"name": "Redis", "type": "database", "start": 47, "end": 52}
  ],
  "relationships": [
    {"source": "asyncio", "target": "Celery", "type": "REPLACES"}
  ],
  "queries": [
    {"form": "question", "text": "why did we move off Celery"},
    {"form": "keyword", "text": "Celery to asyncio migration rationale"}
  ]
}
```

Noise rows carry `noise: true`, an empty `entities` array, an empty `relationships` array, omit `queries` (a noise text is not a useful retrieval target), and use `memory_type` of the closest fit (typically `fact` for filler statements).

**Top-up row schemas:**

- **Extraction top-up row:** `{id, domain, text, memory_type, entities, relationships}` — no `queries`.
- **Classification top-up row:** `{id, domain, text, memory_type}` — no `entities`, no `relationships`, no `queries`. May carry an optional `pair_id` linking contrastive items.
- **Retrieval top-up row:** `{id, source_id, query, positive, query_kind}` where `source_id` references the shared row whose `text` was the seed for `positive`, and `query_kind` is one of `paraphrase`, `acronym`, `typo`, `code-switch`, `multi-sentence`, `hard-negative`. For `hard-negative`, `positive` may be omitted and `negative` is required instead.

Non-relevant fields are absent (not null) on top-up rows so converters can route them.

**Source distribution for the 7K shared base:**

| Domain | Shared (7K) | Why |
|---|---:|---|
| Technical | 2,000 | matches existing distribution; broadest entity/relation coverage |
| AI-assisted coding | 1,500 | high-density real darkmem use case |
| Personal | 1,500 | drives KB expansion to non-technical knowledge |
| Knowledge (general) | 1,500 | drives KB expansion to research/factual content |
| Cross-domain | 300 | mixed entities to teach the models to handle blends |
| Noise (zero entities) | 200 | trains all models to recognize non-extraction input |

**Per-purpose top-ups (3K each, target failure modes the prior evals exposed):**

- **Extraction top-up (3K)**: 1,000 direction-sensitive relation cases (REPLACES, IMPROVES_ON, BUILDS_ON), 800 multi-entity architectures (HAS_PART, COMMUNICATES_WITH), 600 long-tail entity types under-represented in the shared base, 400 hard noise items (entity-shaped strings that are not entities), 200 cross-paragraph relation cases.
- **Classification top-up (3K items)**: 1,000 items in contrastive `reference`/`fact` pairs (500 of each label, paired by topic — the eval's worst confusion), 800 items in contrastive `decision`/`architecture` pairs (400 of each, second-worst), 600 short ambiguous items, 600 multi-type items where the gold label requires reading the whole text. Note: "1,000 items in contrastive pairs" means 1,000 total items (e.g., 500 reference + 500 fact), not 1,000 pairs of 2 items each.
- **Retrieval top-up (3K)**: 1,500 pairs against shared rows the question/keyword forms didn't cover well (typos, acronyms, paraphrase, code-switched terminology), 1,000 hard negatives surfaced by running a baseline embedder over the shared base and flagging false-positive neighbors, 500 long-query forms (multi-sentence questions).

**Document classifier stub:** `documents/seed.jsonl` carries the proposed taxonomy (~12 labels: `article`, `paper`, `tutorial`, `reference_doc`, `news`, `recipe`, `manual`, `email`, `code`, `spec`, `legal`, `narrative`) and ~200 hand-written examples spanning each label. No training, no eval, just enough that a future session can extend without re-deciding the taxonomy. The future document classifier follows the same lineup pattern as the memory classifier (independent weights), with shared-encoder as a comparison condition.

## Taxonomy

**Memory types (7) — sharpened `reference`:**

`fact`, `decision`, `preference`, `problem`, `reference`, `architecture`, `milestone`.

`reference` is sharpened to require a citable source: a URL, a named publication, a documented standard, or an explicit citation. A bare assertion of fact without a source remains a `fact`. The classification top-up uses 1,000 contrastive `reference`/`fact` items (500 each, paired by topic) to teach the boundary explicitly.

**Entity types (~30, kept broad to support KB expansion):**

Technical: `technology`, `service`, `library`, `database`, `framework`, `protocol`, `algorithm`, `project`, `language`, `platform`, `infrastructure`.

AI-coding: `file`, `command`, `error`, `config`, `pattern`, `api`.

Personal: `person`, `place`, `organization`, `event`, `date`, `food`, `activity`, `goal`, `emotion`, `hobby`.

Knowledge: `concept`, `theory`, `publication`, `method`, `finding`, `claim`, `field`, `tool`.

GLiNER's conditional architecture lets us pass additional types at inference time with degraded but usable confidence, so this list is a baseline rather than a hard ceiling — adding `drug`, `disease`, `cuisine`, etc. for future KB domains does not require retraining.

**Relation types (~25, with a documented core 12):**

**Core 12 (first-class for production, REBEL trained on these):** `USES`, `DEPENDS_ON`, `REPLACES`, `IMPROVES_ON`, `IS_A`, `HAS_PART`, `COMMUNICATES_WITH`, `KNOWS`, `LOCATED_IN`, `HAPPENED_ON`, `CAUSES`, `RELATED_TO`.

**Extended set (best-effort, REBEL trained on these too but with lower per-type density):** `DEPLOYED_ON`, `PRODUCES`, `IMPLEMENTS`, `FIXES`, `CONFIGURES`, `EXTENDS`, `LIVES_IN`, `WORKS_AT`, `VISITED`, `FEELS_ABOUT`, `PLANS_TO`, `PREFERS`, `SUPPORTS`, `CONTRADICTS`, `BUILDS_ON`, `AUTHORED_BY`, `PUBLISHED_IN`, `APPLIES_TO`.

REBEL's vocabulary is fixed at training time, so adding new relation types later requires retraining. The core/extended split documents which relations the production pipeline can rely on versus which are best-effort.

## Generation workflow

Multi-session HANDOFF.md pattern, applied separately to the shared base and each top-up, with mechanical validation between batches.

**Batch unit.** One batch = 50 shared rows or 100 top-up items, written in one Claude Code session turn. Shared rows are heavier (text + 4 labelings) so the smaller batch keeps any single response inside a comfortable token budget. Each batch is appended to its target JSONL file in one `Write` call, never partial-appended.

**Session unit.** One session runs ~3–5 batches before context pressure makes outputs degrade. A session always:

1. Reads `HANDOFF.md` to find the next batch ID and resume offset.
2. Writes the batches.
3. Runs the validator script on the new batches.
4. Updates `HANDOFF.md` with the new completed-batch line and any items that failed validation and need rewriting in the next session.
5. Commits the new JSONL rows and HANDOFF update with a `data(fine-tune):` commit.

**Validator script — `fine-tuning/scripts/validate_v2.py`.** Mechanical checks only, no model calls:

- JSON well-formed, all required fields present.
- For every entity: `text[start:end] == entity["name"]` (offset integrity).
- For every relationship: `source` and `target` appear in the entity list, type is in the allowed type set.
- For every memory_type: in the allowed 7-type set.
- For every query pair: positive matches the source `text` byte-for-byte; the two query forms differ from each other (normalized Levenshtein ratio < 0.7 between the two queries) and don't quote the source verbatim (normalized Levenshtein ratio < 0.6 between any query and the source `text`). Thresholds live in `taxonomy_v2.yaml` so they can be tuned.
- For shared rows: at least one entity OR `noise: true`.
- For top-up rows: only the schema-allowed fields for that top-up type are present; foreign fields are a hard reject (not a warning), so the converter never sees ambiguous rows.

Invalid rows go to `failed/<batch-id>.jsonl` with the error message, get retried in a later session, and are excluded from training splits.

**HANDOFF.md responsibilities.** Located at `fine-tuning/data/v2/HANDOFF.md`, it contains:

- Current state per corpus (batches done, items written, items failed-and-pending).
- The next batch's exact target file, batch ID, target row count, and any topical focus (for top-ups: which failure mode this batch targets).
- The full schema spec and writing rules so a fresh session can resume without reading this design doc.
- A "do not modify" list (the existing 270-query test set, the 60-example classification gold set).
- The generation prompt template per corpus type.

**Audit-and-absorb (runs first, before any new generation):**

1. Sample 200 items each from `data/validated/all.jsonl`, `data/classification/train.jsonl`, `docs/e2e/scripts/retrieval_eval/train_pairs_5k.jsonl` using a fixed random seed.
2. Score each sample against the new schema using the validator plus a manual rubric (offset correct, entity types in new taxonomy, relation directions plausible, memory_type fits sharpened definition, query pairs natural).
3. Compute pass rate per corpus. If pass rate ≥ 60%, run the validator over the full source file and absorb everything that passes mechanical checks into `v2/`. If pass rate < 60%, do not absorb that corpus — it's faster to regenerate than fix. The 60% threshold reflects that fixing items below this rate exceeds the cost of writing them fresh, given the 200-item audit's confidence interval.
4. Audit results and absorbed counts get a writeup at `docs/e2e/runs/<audit-date>-data-audit.md` (filename uses the actual audit date) so the decision is reproducible.

Audited-and-absorbed items reduce the hand-write quota; they don't add to the totals.

**Per-purpose generation prompts.** Each prompt is short, lives in HANDOFF.md, and pins the contract:

- Shared base: "Write 50 memories in the {domain} domain. For each, output one JSON object with `text`, `memory_type`, `entities` with character offsets, `relationships` with `source`/`target`/`type`, and two `queries` (question and keyword form). Use these entity types: [list]. Use these relation types: [list]. Verify offsets before writing."
- Extraction top-up: "Write 100 memories that stress {failure_mode} (e.g., REPLACES direction). Output the extraction-only schema."
- Classification top-up: "Write 100 contrastive pairs of memories where one is `{type_a}` and the other is `{type_b}`. Output the classification-only schema."
- Retrieval top-up: "Read shared rows {offset}–{offset+99}. For each, write 1 hard query against the source memory using one of: {paraphrase, acronym, typo, code-switch, multi-sentence}."

**Total session budget.** Roughly:

- Audit-and-absorb: ~3 sessions.
- Shared base (7K rows ÷ 50 per batch ÷ 4 batches per session): ~35 sessions, possibly halved if the audit absorbs ~3,500 shared-eligible items.
- Extraction top-up (3K ÷ 100 ÷ 5): ~6 sessions.
- Classification top-up (3K ÷ 100 ÷ 5): ~6 sessions.
- Retrieval top-up (3K ÷ 100 ÷ 5): ~6 sessions.
- Document stub: ~2 sessions.
- **Total: ~58 sessions**, possibly ~40 after audit absorption. Spread across days/weeks.

## Model training plan

Each purpose has a shared eval harness that produces one comparison report. Production winners load into the extraction pipeline; runners-up stay on disk for future swaps.

**Entity extraction (2 models trained, qwen3.5:4b prompted baseline):**

| Model | Base | Method | Approx. params | Approx. VRAM |
|---|---|---|---:|---:|
| GLiNER-large | `urchade/gliner_multitask-large-v0.5` | full fine-tune | 200M | 0.4 GB |
| GLiNER-small | `urchade/gliner_small-v2.1` | full fine-tune | 50M | 0.15 GB |

Eval harness: `fine-tuning/scripts/eval_entity.py` reports per-type precision/recall/F1, type accuracy, span-level IoU, and latency on the 1K extraction test split. qwen3.5:4b runs as a third comparison condition via a structured-output prompt (existing extractor service).

**Relation extraction (2 models trained, qwen3.5:4b prompted baseline):**

| Model | Base | Method | Approx. params | Approx. VRAM |
|---|---|---|---:|---:|
| REBEL-large | `Babelscape/rebel-large` | full fine-tune | 400M | 0.8 GB |
| mREBEL-base | `Babelscape/mrebel-base` | full fine-tune | 250M | 0.5 GB |

Eval harness: `fine-tuning/scripts/eval_relation.py` reports per-type P/R/F1, direction rate, full-triplet exact-match, and latency. Direction rate stays the gating sub-metric for production.

**Memory classifier (3 models trained, qwen3.5:4b prompted baseline):**

| Model | Base | Method | Approx. params | Approx. VRAM |
|---|---|---|---:|---:|
| DistilBERT | `distilbert-base-uncased` | full fine-tune | 66M | 0.3 GB |
| MiniLM | `microsoft/MiniLM-L12-H384-uncased` | full fine-tune | 33M | 0.15 GB |
| RoBERTa-large | `roberta-large` | full fine-tune | 355M | 1.4 GB |

Eval harness: `fine-tuning/scripts/eval_classifier.py` reports per-type accuracy, macro-F1, confusion matrix, and `reference` recall specifically (the gating sub-metric). Run on the existing 60-example gold set plus the new 1K classification test split.

**Embedding (2 models trained, pretrained baselines):**

| Model | Base | Method | Approx. params | Approx. VRAM |
|---|---|---|---:|---:|
| Qwen3-Embedding-0.6B | `Qwen/Qwen3-Embedding-0.6B` | contrastive fine-tune | 600M | 0.5 GB |
| EmbeddingGemma-300M | `google/embeddinggemma-300m` | contrastive fine-tune | 300M | 0.3 GB |

Eval harness: existing `docs/e2e/scripts/retrieval_eval/run_finetuned.py`, extended to include the new corpora-trained checkpoints. Reports R@1, R@5, R@10, MRR@10 on the fixed 270-query test set. Pretrained EmbeddingGemma-300M (R@1 = 0.752) and bge-base-en-v1.5 (R@1 = 0.700) stay in the report as baselines.

**Hyperparameters per model.** Documented in `fine-tuning/config/training_v2.yaml`, one block per (purpose, model). Defaults follow the existing fine-tuning plan: GLiNER lr 1e-5 / bs 16 / 5 epochs, REBEL lr 5e-5 / bs 16 / 10 epochs, classifier lr 2e-5 / bs 32 / 5 epochs, embedder lr 2e-5 / bs 8 / 3 epochs.

**Training scripts.** Reuse the existing per-model scripts under `fine-tuning/scripts/` (`train_gliner.py`, `train_rebel.py`, `train_classifier.py`, `train_embedder.py`) with v2 paths.

**Converters.** One-pass scripts that transform the canonical `v2/splits/*.jsonl` into each model family's native format:

- `convert_to_gliner.py` → token-aligned BIO span format. Uses the base model's own tokenizer (not whitespace splitting) for alignment. Any row where a character-level span doesn't align cleanly to token boundaries (mid-subword entity, stripped whitespace, punctuation at boundary) is written to `failed/gliner_conversion/` with the reason, not silently dropped. Target: <1% conversion failure rate; higher failure rate blocks the training run and requires a schema review.
- `convert_to_rebel.py` → linearized triplet format with entity context. Handles entities that appear in multiple relationships by reusing the entity marker; preserves relation order by source position in the text.
- `convert_to_classifier.py` → `{text, label}` rows.
- `convert_to_embedding_pairs.py` → `{query, positive}` rows for InfoNCE. Hard negatives from the retrieval top-up expand to `{query, positive, negative}` rows that downstream training code can use with triplet loss or ignore for pure contrastive loss.

**Split determinism.** `build_splits.py` uses a fixed random seed (`42`, documented in the script's `--seed` default). Re-running the script over the same source files produces byte-identical splits. Splits are stratified by `domain` for extraction/classification, and by `source_id` (plus `query_kind` for top-up rows) for retrieval, so train/val/test share distribution.

**qwen3.5:4b prompted baseline runner — `fine-tuning/scripts/eval_baseline_qwen.py`.** Runs each eval harness's test split through the production `qwen3.5:4b` Ollama tag (Q4 quant, the same model already serving reasoning in the stack — no separate version pinned) with a task-specific structured-output prompt. Output goes into the same comparison report as the trained models. If qwen3.5:4b prompted beats every fine-tuned specialist on a purpose, that's a signal to revisit qwen3.5:4b QLoRA fine-tuning (currently deferred).

**Prompts for qwen3.5:4b baselines.** Versioned in `fine-tuning/config/prompts_v2.yaml` so changes are tracked and the comparison stays reproducible. All three tasks use Ollama's JSON mode (`format: "json"`) plus a temperature of 0.0, seed fixed to 42.

*Entity extraction — system prompt:*

```
You are an entity extractor for a knowledge graph. Given a memory text,
extract all named entities and return them as strict JSON.

Output format (no markdown, no commentary):
{"entities": [{"name": "<exact substring from text>",
               "type": "<one allowed type>",
               "start": <int>, "end": <int>}]}

Rules:
- "name" must be an exact substring of the input text (byte-for-byte)
- "start" and "end" are 0-indexed character offsets such that
  text[start:end] == name
- Allowed types: {ENTITY_TYPES}   (injected from taxonomy_v2.yaml)
- Extract specific named things only, not generic nouns
- Empty list is acceptable if no entities are present
- Do not invent entities; extract only what is explicitly in the text
```

*Entity extraction — user prompt:* `Text: {text}\n\nOutput the JSON now.`

*Relation extraction — system prompt:*

```
You are a relationship extractor for a knowledge graph. Given a memory
text and its extracted entity list, identify all relationships between
entities and return them as strict JSON.

Output format (no markdown, no commentary):
{"relationships": [{"source": "<entity name>",
                    "target": "<entity name>",
                    "type": "<relation type>"}]}

Rules:
- "source" and "target" must be entity names from the provided list
- Allowed relation types: {RELATION_TYPES}   (core 12 + extended,
                                              injected from taxonomy)
- Direction matters for these relation types:
    REPLACES:     source = the NEW thing,     target = the OLD thing
    IMPROVES_ON:  source = the improvement,   target = the baseline
    BUILDS_ON:    source = the derivative,    target = the foundation
    DEPENDS_ON:   source = the dependent,     target = the dependency
- Do not invent relationships; extract only what the text states or
  clearly implies
- Empty list is acceptable if no relationships are present
```

*Relation extraction — user prompt:* `Text: {text}\n\nEntities:\n{entity_list_formatted}\n\nOutput the JSON now.` Entity list is formatted one per line as `- {name} ({type})`.

*Classification — system prompt:*

```
You are a memory classifier. Classify the input memory into exactly one
of seven memory types.

Types:
- fact: an assertion about the world without a cited source
- decision: a choice that was made, including its rationale
- preference: a personal or team preference (X over Y)
- problem: an issue, bug, or open question
- reference: a citable source; requires a URL, named publication,
             documented standard, or explicit citation. A bare assertion
             without a source is "fact", not "reference".
- architecture: structural or relational description of a system's
                components and how they fit together
- milestone: an event, achievement, or deadline tied to a specific time

Output format (strict JSON, no markdown, no commentary):
{"memory_type": "<one of the 7 types>"}

Rules:
- Output exactly one type
- Prefer "fact" over "reference" unless a citable source is present
- Prefer "architecture" over "decision" when the text describes how
  components relate, rather than a choice being made
```

*Classification — user prompt:* `Memory: {text}\n\nOutput the JSON now.`

**Prompt freeze and iteration rule.** Once the baseline eval run starts, `prompts_v2.yaml` is frozen for that run. Any future prompt change requires re-running the baselines and producing a new comparison report — prompts are part of the eval configuration, not a tunable parameter during analysis.

**Total training time estimate:**

- Entity (2 models): ~25min + ~10min = ~35min
- Relation (2 models): ~2h + ~1h = ~3h
- Classifier (3 models): ~10min + ~5min + ~30min = ~45min
- Embedding (2 models): ~30min + ~30min = ~1h
- **Total: ~5.5h on the RTX 5060**, runnable in one overnight pass.

## Rollback and failure modes

**If no trained model beats the prompted baseline on a purpose:** keep qwen3.5:4b as the production extractor/classifier for that purpose and promote the QLoRA work for qwen3.5:4b out of deferred status. The specialist models stay on disk for future iteration but do not replace the baseline in production.

**If no fine-tuned embedder beats pretrained EmbeddingGemma-300M (R@1 0.752):** keep pretrained EmbeddingGemma in production. Investigate whether the training pair distribution matches the 270-query test distribution (a common cause of embedder fine-tune regressions), then iterate on the retrieval top-up rather than regenerating the whole corpus.

**If the GLiNER converter fails on more than 1% of rows:** stop the training pipeline, inspect the failures, and either tighten the generation rules (e.g., "entity spans must not span tokenization boundaries") or switch to a character-level GLiNER variant if one is available. Do not silently proceed with a lossy conversion.

**If the audit absorbs less than 10% of any existing corpus:** treat that source as discarded for the revamp; do not spend sessions trying to fix it.

**If the multi-session generation stalls (schema drift, validator rejection rate >20% for two consecutive sessions):** pause generation, schema-review the last 500 rows in that corpus, adjust `taxonomy_v2.yaml` or the HANDOFF.md prompts, and resume with the next batch. Do not rewrite earlier batches that already passed validation.

## Data lifecycle

The existing `fine-tuning/data/` directory is read-only during the revamp — audit sampling reads from it but never writes. After the revamp produces a shipped-and-evaluated set of models, the old `fine-tuning/data/` directory is archived to `fine-tuning/data/v1-archive/` for one release cycle, then deleted. The v2 directory becomes the canonical corpus location.
