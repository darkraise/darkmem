# The Progress board — a projection of the ledger, never a second store

**Date:** 2026-09-04. **Status:** design, awaiting owner review. **Scope:** the
Progress tab of `/projects/$project`, which the artifacts spec deliberately
left out (`2026-09-03-artifacts-workspace-revamp-design.md` §10).

## 1. The ruling this spec is built on, and the question it owes

The artifact-store spec's §7 ruled out "a task/issue/kanban model" on the
owner's own concession that it is heavier than the need and that the
**checkpoint + ledger pair** already covers the requirement. **The owner
reversed that on 2026-09-03** for the Progress surface: *"I want the progress
can be visually show on the project board"*, then *"Confirm!"* against the
explicit question "reverse §7 — build the task board".

Because the original ruling turned on **cost**, the reversal owes an honest
statement of what a board adds that the pair does not. §3 is that statement,
and it is the load-bearing section: if the answer were "nothing", the right
outcome would be to hand the reversal back rather than build.

## 2. What is actually in the corpus — measured, not assumed

Two files, two different jobs, and the split is already correct:

| File | Owns | Shape |
|---|---|---|
| `docs/planning/tasks/E*.md`, `M1-*.md`, `EH*.md` (8 files) | **Scope** | `# E3 — …` epic header with `**Goal:**`, `**Entry gate:**`, `**Done when:**`, `**Epic branch:**`; `## Lane A — …` lanes; `#### T3.01 — …` tasks; a backtick metadata line per task |
| `docs/planning/progress.md` | **State** | One markdown table, 312 rows, regenerated by `scripts/gen_progress.py` for the derived columns; Owner / Status / Commit / Review / Note are hand-edited |

The task metadata line is uniform and machine-readable:

    `Model: Opus 5` · `Effort: high` · `Size: M` · `Depends: —` · `Doc: 09 §4.1–§4.2` · `Tag: target-new` · `Gate: G-D (entry)`

`progress.md` carries a real status vocabulary — `todo`, `wip`, `blocked`,
`review`, `done`, `dropped` — each with a written rule, including the one that
matters most: **a task is never `done` with a failing check.**

**Measured status distribution today: 307 `done`, 2 `todo`, 2 `dropped`,
1 `blocked`.**

### 2.1 The finding that shapes the parsers

**The epic files' `- [ ]` done-when checkboxes are not maintained: 806
unchecked against 17 checked**, across a project that has shipped through
T3.28 and cleared G-C and G-F.

A board that derived task completion from checkbox state would report roughly
**2% done** for a project that is substantially complete. That is not a
cosmetic inaccuracy — it is a progress surface that is confidently wrong, which
is worse than no surface. So:

**Ruling for this spec: `progress.md`'s Status column is the ONLY completion
signal. Checkbox state is never read as status.** The checkboxes are a
per-task definition-of-done *checklist for the implementer*, and the board may
render them as such inside a task's detail, clearly labelled, never aggregated
into a percentage or a column.

## 3. What a board adds that the checkpoint + ledger pair does not

Answered honestly, because the original ruling turned on cost. **It adds no
new data at all.** Every field a board would show already exists: status,
owner, commit, review verdict, note, epic, lane, dependency, gate, model tier,
size. If the board's value were "records the work", the reversal would be
unjustified and §7 should stand.

What it adds is that **three questions currently answerable only by hand-joining
two files become one read**:

1. **"What can I start right now?"** Today that is a manual join: read a task's
   `Depends:`, resolve each dependency's row in a 312-row table, then check the
   *epic's* entry gate — and E3's header records that the gate rule is not
   uniform (G-D holds three named tasks shut and lets the rest of the epic
   through). Nothing computes this; a reader does it in their head, per task.
2. **"What is stopping us?"** `blocked` rows carry the reason in a free-text
   Note at the far right of a wide table. There is one today, and it is
   invisible unless you go looking.
3. **"Where is the work concentrated?"** Lanes and epics are structure in the
   *scope* file and merely a column in the *state* file, so per-lane shape —
   the thing a board is actually good at — is not visible anywhere.

That is the whole claim, and it is deliberately modest: **a board is a better
projection of a ledger that is already correct.** It is worth building because
it is cheap under §4, not because the ledger is failing.

## 4. The decision that makes it cheap: projection, never a store

**The board is read-only and derives entirely from the two files. It writes
nothing.** `progress.md` stays canonical, stays hand-edited, stays the thing a
merge commit touches.

This is what answers the original cost objection. A writable board would be a
**second store of task state**, which re-opens exactly the two-drifting-stores
disease the single-Postgres moat exists to avoid (invariant 1) — and it would
put task state in a database while the ledger that gates merges stays in git,
so the two would disagree within a week and neither would be trustworthy.

**Consequence to state plainly:** dragging a card will not be possible in v1.
Moving a task is editing `progress.md`. If that proves intolerable in use, the
follow-up is a *write-through* that edits the markdown and commits it — a
distinct project with its own ruling, not a v1 stretch goal.

## 5. Parsers — two, both against formats that exist

Neither parser invents a format. Both live under
`frontend/src/features/progress/` as pure functions over text, with the epic
and ledger documents fetched through the **existing** document door (they are
already filed: `docs/planning/progress.md` and `docs/planning/tasks/*.md` are
in the 475-document corpus), so this needs **no new backend route**.

### 5.1 `parseLedger(markdown)` → `LedgerRow[]`

The `progress.md` table. Locates the header row by its `| Task | Title |`
prefix rather than by line number, splits on `|`, and maps columns by header
name so a column added to the generator does not shift the parse. Rows whose
Task cell does not match `^T\d+\.\d+[a-z]?$` are skipped — the file also
carries per-epic summary tables, and matching those as tasks is the obvious
way to get this wrong.

Unknown status values are **surfaced, never coerced**: a row whose status is
not in the vocabulary renders in an `unrecognised` column with the raw string,
because silently bucketing it as `todo` would hide a typo in the file that
gates merges.

### 5.2 `parseEpics(markdown, filename)` → `Epic`

Epic header, `**Goal:**`, `**Entry gate:**`, `**Done when:**`, lanes, tasks,
the metadata line (each backtick pair split on the first `:`), and the
done-when checklist per task. `EH2-dotnet-migration.md` holds **zero** tasks by
design and must parse to an epic with an empty task list rather than failing —
a parser that throws on it takes the whole board down.

## 6. The board

**Columns are the status vocabulary**, in workflow order: `todo`, `wip`,
`blocked`, `review`, `done`, plus `dropped` collapsed behind a disclosure
(2 rows, and they are resolved). Not custom columns — the vocabulary is
written down and enforced socially already; inventing a second one guarantees
drift.

A card carries: task id, title, epic and lane, size and model tier, owner,
and — where present — commit sha, review verdict, and the Note. A `blocked`
card renders its Note **on the card**, not behind a click; that is finding 2
in §3 and the one thing the table genuinely hides.

**Grouping switches between Epic and Lane**, because those are the two real
structures in the scope file.

**Filters:** epic, lane, owner, status, model tier, and a text match over id
and title. Plus one derived filter that is the point of §3's finding 1:
**"startable"** — `todo`, every `Depends:` id resolving to `done` or
`dropped`, and the epic's entry gate not held. Gate state is read from the
epic header text, and where a gate holds only *named* tasks shut (E3's G-D
amendment), the board honours that rather than blanking the epic.

**A task's detail view** shows the done-when checklist from the epic file,
labelled as the implementer's checklist and explicitly **not** a progress
measure — with the 806/17 measurement stated in the UI copy, so a reader
cannot mistake an unchecked list for unfinished work.

## 7. What NOT to build

- **No writes.** §4.
- **No burndown, velocity, or estimate-vs-actual.** `Size` is S/M/L, there are
  no dates on tasks, and inventing a time axis from commit timestamps would
  produce a chart that looks quantitative and measures nothing.
- **No second status vocabulary**, and no mapping of these six onto a generic
  kanban set.
- **No checkbox aggregation into any percentage.** §2.1.
- **No new backend route.** The documents are already filed and readable.

## 8. Testing

Both parsers get golden tests against **the real committed files**, not
fixtures — the formats are only as stable as the corpus, so the corpus is the
fixture. Specifically pinned:

- the ledger's status distribution parses to the measured 307/2/2/1, so a
  parser that silently drops rows fails;
- `EH2` parses to an epic with zero tasks and does not throw;
- a row with an invented status lands in `unrecognised`, never in `todo`;
- the startable filter resolves E3's G-D amendment the way the epic header
  states — the three named tasks held, the rest of the epic open.
