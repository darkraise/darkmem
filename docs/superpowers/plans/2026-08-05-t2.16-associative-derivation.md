## 1. What is already true (measured against the tree at `c2758784`)

Every claim here was read out of the tree, not inferred from the plan corpus.

**The vocabulary exists and is closed.** `MEMORY_RELATION_TYPES` in
`backend/app/taxonomy.py:274` holds exactly the five stored types; `SUPERSEDES` sits in
`PROJECTED_MEMORY_RELATION_TYPES` (`taxonomy.py:285`) with a comment stating it is never a
normaliser output. `normalize_memory_relation_type` is a pure function of one raw string
(the purity is asserted in that module's own docstring, and it is load-bearing for the
replay clause below). `DERIVED_FROM` is cut for v1 (doc 06 §3.1, doc 08 §5.5).

**One derivation pass already writes into `memory_relations`, and T2.16 is the second.**
`memory_dream.apply_associate` (`app/services/memory_dream.py:923`) writes a single edge
per near-duplicate pair — `ELABORATES` when the LLM verdict is `subsumes`, otherwise
`RELATES_TO`. So T2.16 is **not** the first writer, and the plan below must not assume an
empty table or sole ownership of a row.

**The row is co-owned by passes, and that is the load-bearing fact of this task.**
`app/repositories/memory_relations.py` stores each pass's state under
`properties.dream.<pass_key>`:

| Function | Contract |
|---|---|
| `get_edge` / `pass_block_of` | read one pass's block off a row |
| `upsert_edge` | write this pass's block, merging rather than replacing |
| `write_pass_block` | restore a block; **never inserts** |
| `clear_pass_block` | remove this pass's block, returning `exclusive` |
| `delete_edge` | unconditional row delete |

`clear_pass_block` returns `True` only when nothing but this pass's block was ever on the
row — no sibling under `dream`, no other top-level key — and the `exclusive` flag is
computed **in the same statement** as the removal, so it describes the post-removal row
rather than a re-read a concurrent writer could have moved
(`memory_relations.py:185-200`).

**Why that matters more than it looks.** T2.16's Done-when says nothing about it, but
T2.17 ("strip-before-rewrite") is unimplementable without it: a strip that calls
`delete_edge` would destroy T2.12's near-duplicate block and T2.23's hygiene triage on any
row those passes share with this one. **The strip must be `clear_pass_block`, then
`delete_edge` only on `exclusive is True`.** This plan builds the strip that way so T2.17
inherits a correct one rather than repairing it.

**Self-healing is already structural, not code.** Doc 08 §5.5 and doc 04 §8.2 put composite
`(memory_id, project)` FKs with `ON DELETE CASCADE` on both endpoints, so a deleted
endpoint cannot leave a dangling edge and a cross-project edge is unrepresentable. T2.17's
second clause is therefore a **test** against the schema, not new code — worth stating here
so its executor does not write a redundant sweep.

**The fingerprint trap is known and already cost one task a round.** T2.12's own plan
(revision 3, finding F3) records that `llm_fingerprint()` returns the `model|0` sentinel
under a legal config, so a feature resolving the fingerprint that way runs green and inert
forever. `memory_dream.resolve_fingerprint` (`memory_dream.py:244`) resolves through a
canary `embed()` instead. T2.83 and T2.68 are two more tasks minted off the same sentinel.
**T2.16 must reuse `resolve_fingerprint`, never re-derive one.**

**Where the pass runs.** Inside the `memory_dream` job body. Invariant 15 forbids any
capture or retrieval path reaching it, and `tests/test_dream_jobs.py`'s family scan plus
`tests/test_communities.py`'s AST walk already enforce that shape for the family.

## 2. Scope boundary — what T2.16 does NOT do

- **It does not adjudicate truth.** A derived `CONTRADICTS` edge is a *signal into*
  fact-level dispute (doc 08 §4.2, §5.5), never a verdict. This pass writes an edge; it
  never touches `verification_status`, never calls the ladder, and never opens a
  `review_state`. T2.11's contradiction scan is a separate consumer and is currently
  **blocked** on an unqualified judge — T2.16 must not become a back door that supplies
  fact-level dispute while that gate is unmet.
- **It does not write `SUPERSEDES`.** Projected from `superseded_by`, never stored.
- **It does not delete or merge memories.** T2.12's rule stands.
- **It does not own the strip's *idempotence proof*.** That is T2.17. T2.16 builds the
  strip correctly; T2.17 proves re-derivation idempotent and endpoint deletion clean.
- **It does not add an LLM call.** All three signals are deterministic. If a candidate
  needs semantic adjudication, that is the near-duplicate pass's job, which already has
  one.

## 3. Design decisions, made executable

**D1 — One pass key, `associative_derivation`, distinct from T2.12's near-duplicate key.**
Two passes may legitimately assert the same `(source, target, rel_type)` triple; each keeps
its own block, and neither strip can erase the other's. Sharing a key would make T2.12's
unchanged-edge skip and this pass's strip fight over one dictionary.

**D2 — The signal→type mapping is explicit, deterministic, and total.** Doc 08 §5.5 names
three signals and five types without mapping one to the other. This plan proposes:

| Signal | Condition | Type |
|---|---|---|
| Contradiction | deterministic same-endpoint opposition (below) | `CONTRADICTS` |
| Entity overlap | Jaccard over shared entity ids ≥ `overlap_threshold` | `RELATES_TO` |
| Embedding proximity | cosine ≥ `proximity_threshold`, same fingerprint | `RELATES_TO` |

**`DEPENDS_ON` and `FOLLOWS` are deliberately NOT derived by this pass** — see §8, O1.
Deriving `FOLLOWS` from `created_at` ordering alone would assert narrative succession from
capture order, which is an artefact of when someone typed, not of what the statements say.
`DEPENDS_ON` has no deterministic signal at all among the three named. Writing either on a
guess would put a claim in the graph that nothing measured.

**D3 — Precedence, because one pair can fire two signals.** A pair that both overlaps and
contradicts is a contradiction, not a relation: `CONTRADICTS` wins outright, and the weaker
edge is not also written. Otherwise the hygiene and dispute surfaces would show one pair
twice under two names, and a curator would have to know which to believe.

**D4 — The contradiction signal is deterministic and narrow.** Same-endpoint opposition
only: both memories assert the same subject entity and the same relation family, with
opposed targets, over overlapping validity. It fires rarely and never on prose sentiment.
Anything wider needs the LLM scan (T2.11), which is blocked, and this pass must not
approximate it.

**D5 — Proximity resolves the fingerprint once per run through `resolve_fingerprint`, and
a run that cannot resolve one skips the proximity arm entirely** — it does not fall back to
a sentinel, and it does not compare vectors it cannot prove co-partitioned. Skipped is
reported in the outcome, not swallowed. This is invariant 2 and Done-when clause 2.

**D6 — Thresholds are `config` rows under the job's `config_schema`**, not module
constants: `overlap_threshold`, `proximity_threshold`, `derivation_batch`,
`derivation_enabled`. Done-when clause 1. The schema is validated by `set_config` (type +
min/max, unknown keys rejected), so an operator cannot set a threshold outside `[0,1]`.

**D7 — Reproducibility comes from determinism, not from a seed.** All three signals are
pure functions of stored columns, so a replay over the same corpus and the same config
yields the same edge set — no model call, no clock, no random. The one non-obvious hazard
is **iteration order**: candidate pairs must be ordered by a stable key (the ordered
`(source_id, target_id)` pair, as `order_pair` already does for T2.12) before the batch
bound is applied, or a different subset survives the cap on each run and "reproducible"
holds per-edge while failing per-run. Done-when clause 3.

**D8 — Edge direction is the ordered pair, not the discovery order.** `order_pair`
(`memory_dream.py:414`) already fixes this for the near-duplicate pass; reusing it means a
pair cannot appear as two rows depending on which memory the scan reached first.

## 4. Steps

Each step is independently committable and leaves the floor green.

1. **Config surface.** Add the four fields to `memory_dream`'s `config_schema` with
   defaults and bounds. Test: an out-of-range threshold is rejected; a partial update
   leaves siblings intact.
2. **Candidate generation — entity overlap.** A project-scoped SQL pass over
   `entities.memory_ids` producing ordered pairs with a shared-entity count and Jaccard
   score. Bounded by `derivation_batch`, ordered by the stable key.
3. **Candidate generation — proximity.** Same-fingerprint ANN over the resolved partition,
   reusing `resolve_fingerprint` and `seed_vectors`. Skips wholesale when unresolved.
4. **Candidate generation — contradiction.** The D4 same-endpoint scan.
5. **Merge, precedence, and the type decision.** Apply D3; produce one typed edge per pair.
6. **The writer.** `upsert_edge` with this pass's block; an unchanged-block skip mirroring
   `_edge_is_unchanged` so a stable pair does not journal every cycle into an append-only
   table.
7. **The strip.** `clear_pass_block` for every pair this run no longer asserts, then
   `delete_edge` only on `exclusive is True`.
8. **Journal.** One `consolidated` row per written edge, carrying the signal and the score
   that produced it, so the digest can explain *why* an edge exists.
9. **Wire into the dream cycle** behind `derivation_enabled`, and extend `DreamOutcome`
   with the derived/stripped/skipped counters.

## 5. Test plan — and how each negative is proven non-vacuously

`tests/test_memory_relation_derivation.py`. Every negative below is paired with a mutation
that must turn it red, per the runbook's "new invariant-bearing behaviour has a test that
fails if the invariant is removed".

- **Cross-fingerprint refusal.** Two memories embedded under different fingerprints are
  never paired by proximity. *Non-vacuity:* the same two memories under one fingerprint
  **are** paired — otherwise the test passes because nothing was ever a candidate.
- **Sentinel refusal.** With the fingerprint unresolvable, the proximity arm reports
  skipped and writes nothing; the overlap arm still runs. *Mutation:* resolving through
  `llm_fingerprint()` instead must fail this.
- **The strip does not destroy a sibling pass's block.** An edge carrying both T2.12's
  near-duplicate block and this pass's block, stripped by this pass, keeps the row and the
  sibling block. *Mutation:* replacing `clear_pass_block`+`exclusive` with `delete_edge`
  must fail this. **This is the single most important test in the file.**
- **The strip does delete a row it exclusively owns**, so stripping is not a no-op that
  leaves the graph growing forever.
- **Precedence.** A pair firing both contradiction and overlap yields exactly one edge,
  typed `CONTRADICTS`.
- **Replay.** Two runs over an unchanged corpus produce byte-identical edge sets *and* the
  second writes no journal row. *Non-vacuity:* a corpus change produces a different set.
- **Order stability under the cap.** With `derivation_batch` smaller than the candidate
  count, two runs select the same subset. *Mutation:* removing the ORDER BY must fail this.
- **No fact-layer write.** The pass writes no `verification_status`, opens no
  `review_state`. Asserted structurally (an AST scan over the new module), not by
  observation, because a call counter cannot show a negative.
- **Invariant 15.** The existing family scan still passes with the new module in the tree.

## 6. Risks

- **R1 — The overlap query is the whole-corpus join this epic keeps re-learning about.**
  `entities.memory_ids` is an array; a naive self-join is quadratic in project size. The
  candidate pass must be bounded and indexed, and the plan's executor should measure it on
  `darkmem_bench` before wiring it into a nightly job.
- **R2 — Edge volume.** Overlap at a low threshold can assert an edge between most pairs in
  a small project, which is true and useless. The threshold default should start
  conservative; the arm activation discipline (measure, then loosen) applies.
- **R3 — Co-ownership races.** Two passes writing the same row in one cycle is expected;
  the merge semantics of `upsert_edge` make it safe, but the executor must not "simplify"
  it into a whole-object write. That regression has already happened once, as T2.12's
  revision-3 finding F4.

## 8. Open questions

**O1 — `DEPENDS_ON` and `FOLLOWS` have no derivation, and the corpus does not supply one.**
Doc 08 §5.5 says the five types are derived "from entity overlap, embedding proximity, and
contradiction checks"; doc 06 §3.1 fixes the vocabulary and explicitly assigns the writers
to doc 08's passes. Neither maps a signal to `DEPENDS_ON` or `FOLLOWS`, and neither
deterministic signal carries the information those two types assert — dependency and
succession are claims about meaning, not about overlap or distance.

Three ways out, and **this plan does not pick one**:

1. Derive them and accept the guess — rejected here, because a graph edge nothing measured
   is exactly the shape invariant 14 exists to prevent.
2. Leave them stored-but-underived for v1 — the vocabulary keeps them for a future writer
   (an LLM pass, or the article layer), and T2.16 ships three signals and three types. This
   is what §3's D2 proposes.
3. Cut them from the vocabulary as `DERIVED_FROM` was cut — taxonomy-first, doc 06 §3.1's
   own precedent for a type with no writer.

**Option 3 would amend the design corpus, which makes this Tier-3 if the controller
prefers it.** Option 2 is a plan-local decision and needs no escalation. The reviewer
should rule which, because it changes whether T2.16 is a three-type or a five-type task.

**O2 — Does the near-duplicate pass's `RELATES_TO` collide with this pass's?** Both can
assert the same triple for different reasons. D1's separate pass keys make the *storage*
safe, but the hygiene queue reads edges and may now show one pair sourced two ways. Whether
that is correct (two independent reasons is stronger evidence) or noise (one pair, one row
in the queue) is a T2.23 surface question this plan flags rather than answers.
