([`docs/planning/reviews/2026-08-15-t2.131-plan-review.md`](../../planning/reviews/2026-08-15-t2.131-plan-review.md)).
**Still awaiting re-review; nothing here may be executed yet** (runbook §3 — Size L).

**What the review changed, so a reader can see the delta rather than reconstruct
it.** v1's §3.2 stated a mechanism the code refutes; v1's recommended route
claimed a project-spread the code cannot deliver; v1's conversion table was
measured against the wrong denominator; v1's target had no margin and its
recommended split landed *below* the bar. §§2–4 and §7 are rewritten. The

**What this plan is not:** it does not switch the audit's scored rule, move the

capture.

## 1. The target, and the margin v1 did not carry

Derived with the committed instrument, at the corpus's actual **k = 1**:

| n | point estimate | 95% upper bound | clears strict `< 0.01`? |
|---|---|---|---|
| 131 (today, unsimulated) | 0.0076 | 0.03574 | no |
| 300 (as originally suggested) | 0.0033 | 0.01573 | no |
| 467 (v1's route D, in expectation) | 0.0021 | **0.01012** | **no** |
| 473 (the derived minimum) | 0.0021 | **0.00999** | yes, by 1×10⁻⁵ |
| **490 (the target)** | 0.0020 | **0.00964** | yes |

**473 is the derived minimum and a bad target.** It clears by one part in a
hundred thousand and *prints* as `0.0100`, which against a strict `< 0.01` rule
reads as a tie scored as a pass — the precise shape this ledger exists to catch.
v1 also recommended a split landing at ~467 in expectation, which does not clear
at all. **Target 490 corroborations on the unsimulated pass**, and the report
states the bound to five decimals so the margin is visible.

The k = 1 assumption is not a convenience: the corpus has k = 1 because T2.129
armed it, and the arming is the only reason the audit is not vacuous. 299 is the
k = 0 window and is only ever the price of the meaningless version.

## 2. What converts — measured per claim, not per gate bucket

v1 divided memories by `gate_fired` bucket sizes. Those buckets count **facts**
and carry other groups' facts, so two of its three figures were wrong. Recounted
by distinct `claim_key` over the committed corpus:

| Group | Design | Memories per **claim** | Counts on the unsimulated pass? |
|---|---|---|---|
| `diversity` | 1 memory origin; the repo fixture's parsed import supplies the second origin *and* the second kind (N = 2) | **1.00** (101 → 101) + 1 distinct dependency | yes |
| `none` | 3 sessions inside one week, no gate fires, default N = 3 met exactly | **3.00** (96 → 32) | yes |
| `time_gap` | 2 sessions ≥ 7 days apart | 2.00 (36 → 18) | **no — 0** |

**Claims are not corroborations.** The two promoting groups hold **133** claims
and the audit counts **131** corroborations — a standing 2-claim shortfall at
today's size, unexplained and not introduced by this task. Sizing therefore uses
the *realized* conversion **131 ⁄ 133 = 0.985**, not 1.0, and Step 3 exists to
stop that gap growing silently with the corpus.

**`time_gap` must not be grown.** All 18 of its promotions exist only under the
simulated capture clock, and the target rides the unsimulated pass.

**+359 corroborations are needed → +364 promoting claims.**

## 3. The two blockers

### 3.1 The diversity arm cannot scale inside one repo — unchanged from v1, confirmed by review

`validate_diversity_group_against_fixture` refuses **two claims naming the same
dependency**, deliberately, since they would converge on one fact.
`repo_fixture.json` carries exactly **one** repo (101 imports, one per claim).
So +364 diversity claims inside it means a single stand-in service repo with
**465 distinct third-party dependencies** — not a repository anyone indexed, and
plausibility is the premise the corpus rests on (`corpus.json`'s `_notes`).

The ceiling is plausibility, not effort. Escaping it needs a **multi-repo
fixture**: `load_repo_fixture`, `REPO_FIXTURE_PATH` and `prepare`'s wiring all
assume one.

### 3.2 What actually threatens k = 1 — v1's mechanism was refuted

**v1 claimed a new capture carrying a REPLACES-family relation would arm a second
dispute and move the target to 628. The code refutes it, and the correction is
recorded rather than quietly swapped.**

- `inverse_replacement` arms on a **live inverse fact** in the same project —
  `subject_name`/`object_name` transposed, `rel_type` in the family,
  `expired_at IS NULL`, windows overlapping, a non-echo witness. A lone stray
  REPLACES edge satisfies none of that.
- **k = 2 is unreachable in any corpus the committed loader admits.** The loader
  refuses `wave != 1` outside the arming groups, so an accidental inverse pair
  lands whole in wave 1. There the veto is checked ahead of the count, the fact
  is disputed straight out of `candidate`, and it never emits the `corroborated`
  event the audit's numerator joins on
  (`_FALSE_PROMOTION_AUDIT_SQL` requires corroborated-then-disputed on a
  `(created_at, id)` tuple compare). It lands in neither numerator nor
  denominator.

**So the rule "no new capture carries a REPLACES-family relation" is kept, but
demoted from a k-guard to hygiene**, and the 473 → 628 scenario is withdrawn:
reaching it would require weakening a validator, which the constraints forbid.

**What does threaten the count is supersession, and it is a different function
than v1 said.** v1 framed it as a function of density; it is a function of
*REPLACES-emitting captures × same-project in-window candidates*. Under the
hygiene rule the base rate is structurally zero and density multiplies only the
blast radius of a rule failure. Two consequences an executor needs: a
supersession that fires silently removes a corroboration from the denominator
with no error, and **the exposure decays with the calendar** — the existing
June–July absolute dates begin leaving the 90-day window around **2026-08-31**,
so Step 3's reconciliation bites hardest when run promptly after authoring.

### 3.3 The blocker v1 missed entirely: diversity is locked to one project

`fact_lift.CODE_FACT_PROJECT` is the constant `"default"`, and `repositories`
carries no project column. Code-derived corroboration therefore only ever matches
facts in `default` — which is why all 101 existing diversity memories sit there.
Its own docstring states the consequence: a memory captured under a *different*
project asserting the same triple lifts to a **different** fact and the two do
not corroborate.

**v1's route B/D premise — that multi-repo diversity spreads projects — is
false.** More repos buy more distinct dependencies, which is what §3.1 needs;
they buy no spread at all. A spread-authored diversity claim would silently hold
at one origin per claim, refused by no validator (none reads project) and visible
only as a short count at Step 4.

**So the monoculture concern lands in the arm v1 thought relieved it**, and the
only lever for project spread is `none`, at 3× the memories.

## 4. The routes, re-costed against §2's measured conversion

+364 promoting claims, at 1.00 memories/claim for `diversity` (all necessarily in
`default`) and 3.00 for `none`:

| Split (diversity share of claims) | Diversity claims / captures | `none` claims / captures | Total captures | Corpus | Project spread |
|---|---|---|---|---|---|
| 100% | 364 / 364 | 0 / 0 | **364** | 610 (2.5×) | none — `default` reaches 465 |
| **70%** | **255 / 255** | **109 / 327** | **582** | **828 (3.4×)** | `none` only |
| 50% | 182 / 182 | 182 / 546 | 728 | 974 (4.0×) | more, at +146 captures |
| 0% | 0 / 0 | 364 / 1092 | 1092 | 1338 (5.4×) | maximal |

**Recommended: 70%.** 100% is cheapest and leaves `default` holding 465 of 610
claims with no spread anywhere. 0% buys spread at three times the authoring and
still leaves a corpus authored by one party. 70% keeps the cost near the cheap
end while putting 109 claims across new projects on the only arm that can carry
them.

**This is a judgement, not a derivation**, and it is the item the re-review should
push on hardest: the honest split depends on how many plausible service repos the
fixture can carry (§3.1) before the fixtures themselves look manufactured, and
that ceiling has not been set. **Step 0 sets it before authoring, not after.**

**Diversity captures land in `default` and that is not negotiable** (§3.3). The
disclosure in §6 says so rather than implying a spread the corpus does not have.

## 5. Steps

**Step 0 — Re-review of this plan, and two adjudications it must carry.**
(a) The **plausible-repo ceiling**: how many stand-in service repos, at what
dependency count each, before the fixture is manufactured — this sets §4's split.
(b) The **Done-when conflict** in I4 below. Nothing below starts first.

**Step 1 — Multi-fixture support.** Widen the loader to carry several repos with
their own ids; `validate_diversity_group_against_fixture` becomes per-repo. Two
properties the v1 one-liner did not state: each claim binds to **exactly one**
repo (its content names the subject repo, as every existing entry does), and
ambiguity across repos importing the same dependency is refused exactly as
ambiguity across dependencies is today. Tests first; the existing refusals must
keep biting per repo rather than globally.

**This modifies a validator, and T2.131's Done-when says every existing validator
passes *unmodified*.** It is a widening in letter — two claims naming one
dependency become admissible when seconded by different repos — and preserved in
substance, since distinct repo subjects make them distinct facts. **The conflict
is named here for adjudication at Step 0 and is not resolved by this plan.**

**Step 2 — Author the growth, in batches.** Each capture: plausible content, wave
1 (the loader enforces it; stating it as design is also what pins k), no
REPLACES-family relation. Diversity claims name a distinct dependency and their
subject repo, in `default`. `none` claims are three same-project captures with
distinct origins spanning **under 7 days**. Every validator green before the next
batch; commit per batch, since the corpus is one large mutable file.

**Growth content must not re-assert a control claim's triple.** `claim_key`
groups by key, not content, so a differently-keyed capture asserting the `echo`
claim's content in `ledger` would add an origin and **promote a designed
refusal** — and no validator refuses it. Batch review checks content, not just
keys.

**Step 3 — Reconciliation.** Assert authored promoting claims × 0.985 ≈ counted
corroborations, per project; 0 unexpected superseded rows outside the
blocked-hold group; k still exactly 1; and the echo and under-sourced controls
still at `candidate` (`_CONTROL_FACTS`, `CONTROL_OBJECT_NAMES`). Run promptly
after authoring, per §3.2's calendar decay.

**Step 4 — Both evidence passes.** Unsimulated first — it carries the target.
Report the bound to five decimals, the point estimate, and the at-the-bar pass
probability under both rules, with rule 2's latency/token twin. **Budget the
first run as live**: ~+582 uncached extraction calls against the gate-fixed
`deepseek-v4-flash`, and T2.129's author-vouched single-live-run caveat scales
with the corpus.

**Step 5 — Independent verdict** by a party that did not author the growth.

**Step 6 — Ledger and progress**, with §6's disclosure attached to the number.

## 6. The disclosure that travels with the result

Written before the number exists rather than after.

Reaching 490 makes the audit **decisive about a corpus its own measurer wrote**:
one authored dispute over ~490 authored corroborations. T2.130 already recorded
the limit — *a well-powered rule over authored evidence is a better instrument
measuring the same thing* — and this task sharpens the instrument without lifting
it.

**And the composition is more concentrated than v1 implied.** Diversity claims
cannot leave project `default` (§3.3), so at the recommended split `default`
holds ~356 of ~497 promoting claims. A future reader meeting "490
corroborations, bound 0.00964, CLEARS" must meet, in the same breath, that every
one was written to be counted and that most of them sit in one project against
one stand-in repository set.

This is not an argument against the route. The owner chose it, a settled bound
beats an unsettled one, and the alternative — switching the scored rule — remains
open and untaken.

## 7. Where this goes wrong quietly

v1's first row claimed a catch that does not exist: no validator inspects
extractor emissions, so a stray REPLACES edge is caught at run time or not at
all. Corrected.

| Failure | Catch |
|---|---|
| A capture carries a REPLACES-family relation | **No authoring-time catch exists.** Step 3's superseded-row count and k check, at run time. Under §3.2 it cannot move k, so the exposure is a withheld corroboration, not a wrong target |
| Density causes a supersession, a corroboration vanishes, the count is short with no error | Step 3's authored-vs-counted reconciliation, per project, run promptly (§3.2's calendar decay) |
| Growth content re-asserts a control claim's triple and promotes a designed refusal | Step 2's content check and Step 3's control assertion. No validator refuses it |
| Diversity claims authored outside `default` hold at one origin | Step 3's per-project reconciliation; nothing earlier sees it (§3.3) |
| Growth lands in `time_gap` and the unsimulated number does not move | §2; Step 4 runs unsimulated first |
| A unique `origin_key` per memory reaches the count while being one assertion relabelled | `validate_corroboration_design` unchanged; the diff must show no validator weakened beyond Step 1's adjudicated widening |
| The fixtures start looking manufactured | Step 0(a) sets the ceiling before authoring |
| The window is quoted without its `k`, or the bound printed as a tie | §1; the report prints k beside n and the bound to five decimals |
