## 2. Headline finding — the F1 gate is already green over a configuration nobody runs

This is the single most important thing in this plan and it changes the shape of the work.

The bench's cache key is:

```python
key = hashlib.sha256((content + "\x00" + system_prompt).encode("utf-8")).hexdigest()[:16]
```

(`backend/scripts/extraction_bench/run_bench.py:68`)

It covers the content and the **system** message. It does **not** cover the user message —
and the user message is where `EXTRACTION_SCHEMA` rides:

```python
p = (f"Return JSON matching this schema:\n{EXTRACTION_SCHEMA}\n\n"
     f"<content>\n{user}\n</content>\n\n" ...)
```

(`run_bench.py:76-78`)

`EXTRACTION_SCHEMA` is `_build_extraction_schema()`, evaluated at import against the live
`MEMORY_TYPES`. **T1.23 already widened `MEMORY_TYPES` from 7 to 9** (`episodic`,
`procedural` — verified: `len(MEMORY_TYPES) == 9` on this branch). The 36 cached raw
outputs were recorded on 2026-07-26 under the **7-type** schema string. The key did not
change, so they are still served.

**Consequence, stated plainly:** `./scripts/gate.sh`'s F1 gate is right now replaying
outputs produced by a request the code would no longer send. Every lane's merge gate has
been green over a stale configuration since T1.23 landed. This is exactly the failure T0.03
forbids, and it is Ruling 5's observation confirmed by measurement rather than inference —
the widening was not merely unmeasured, it is *unmeasurable* under the current key.

Two things follow:

- The cache-key widening (Step 4) is not a tidy-up. It is what makes the F1 gate mean
  anything after this task, and it is invariant-bearing: without it a future vocabulary or
  schema change silently reuses stale outputs again.
- Ruling 5's "separating them may be worth a step" is upgraded to **required**. Pass A
  (§7, Step 5) measures the widening + merge alone, with the system prompt byte-identical
  to T0.05's; Pass B measures the strip on top. Without that split, a regression at G-B is
  un-attributable between two changes, one of which (T1.23) has never been measured at all.

The task text and the rulings both frame the cost as "36 live calls per re-record". That

**`benchlib`'s LLM cache keys on the whole `messages` list.**

return _key("chat", [purpose, _purpose_identity(self.config, purpose), messages, sorted(kwargs.items())])

`backend/scripts/benchlib/retrieval/cache/` holds 550 entries; `smoke/cache/` holds 24.

**Position this plan takes:** T1.17 does **not** pay the 94 calls and does **not** re-run

## 5. What "strip the prompt to minimal rules" means operationally

Doc 06 §4 is the governing text: *"Spec §5 strips from the prompt every rule the cleanup
passes already enforce — the prompt becomes one canonical schema + content + reproducibility
seed + minimal rules."* Doc 11 §5 repeats it. T1.24f's Done-when adds the reciprocal:
*"No pass is a prompt instruction in disguise — the prompt stays minimal."*

Read literally, "strip every rule the passes already enforce" is a licence to delete most of
35KB in one commit and re-roll 36 outputs against a 2-flip budget. That is not a plan, it is
a coin toss. The strip policy this plan adopts:

> **Strip a rule only on demonstrated full subsumption by an existing pass. Never edit a
> pass to justify a strip. On partial coverage, keep the rule.**

Three reasons this is the right reading rather than a timid one:

1. **Lane boundary.** The passes belong to T1.24b–e (`Depends: T1.24a`), which have not
   run. A T1.17 that edits `extraction_clean.py` to cover a stripped rule is doing T1.24b's
   work under T1.17's budget, and T1.24f then measures a chain nobody reviewed.
2. **Asymmetry of what a pass can do.** A deterministic pass can drop, retype, redirect or
   dedup what the model emitted. It cannot invent an entity the model never mentioned —
   the rescue passes (`rescue_known_entities`, `rescue_file_path_entities`,
   `rescue_happened_on`) work from curated lists and spans, not from nothing. So a
   **precision-side** prompt rule (rules 2, 2b, 3, 4, 6) has a real deterministic twin,
   while a **recall-side** rule (9f `HAPPENED_ON`, 12b fan-out, 9j artifact typing) is only
   safe to strip where a pass genuinely synthesises the edge.
3. **A measured counter-example already exists.** Prompt rule 2a is a hard filter over 28
   language builtins (`str`, `int`, `float`, `bool`, `dict`, `tuple`, `bytes`, `object`,
   `vec`, `hashmap`, `option`, …). The pass that would have to carry it is `filter_noise`,
   whose `_NOISE_NAMES` set contains `string`, `type`, `list`, `map`, `set`, `none`, `null`
   and `number` — but **not** `str`, `int`, `float`, `bool`, `dict`, `tuple`, `bytes`,
   `object`, `vec`, `hashmap` or `option`. Verified by running the set. Stripping rule 2a
   today deletes a filter nothing else implements.

The audit that produces the strip list is Step 1, and it is free — zero model calls, one
reviewable table.

**Rules that stay under any reading** (the "minimal rules" residue): rule 1 (extract
specific named things), rule 5 (literal mention only), relationship rule 0 (the sixteen
types — this is the schema restated and belongs in the schema string, so the strip merges it
rather than deleting it), rule 6 on relationships (only relate entities in your list),
rule 11 (do not invent unsupported relations), rule 14 (weight calibration — nothing
downstream recomputes weight). These are semantic work only the model does; no pass can
recover them.

**Rules most likely to survive the audit despite having a same-named pass**: the direction
rules (relationship 2, 3, 4, 8, 9a–9e, 9h, 9i). `validate_directions` and
`validate_hosting_direction` swap only *unambiguously* wrong directions and deliberately
leave ambiguous ones alone (doc 06 §4, T1.24d: *"ambiguous ones are left alone"*). A
direction the pass declines to touch is a `rel_full` F1 loss the budget must absorb. The
audit should treat "the pass declines ambiguous cases" as **partial** coverage, not full.

## 6. Ruling 2 — the red window, and the rule that governs it

From the moment the bench's assembled request changes, `run_bench.py --algo-only` is red and
stays red until the live re-record completes. Two corrections to the naive reading:

- **The window opens at Step 4, not at the prompt edit.** Widening the cache key changes
  every key; pinning the merged gate changes every user message. Either alone kills all 36
  entries. The prompt edit (Step 6) merely deepens a window that is already open.
- **The window cannot be avoided, only bounded.** There is no ordering that keeps the gate
  green through this task, because the whole point is that the bench must send a different
  request than it sends today.

**The rule:** Steps 4 → 7 execute in **one uninterrupted working block** and land as one
merge unit. Nothing merges to `feat/e1-engine-core` while the window is open. Expected
duration is one working session; the live passes themselves are minutes of wall clock (36
calls, `pipeline_concurrency`-free, sequential in the bench's loop).

**What runs inside the window:** `cd backend && python -m pytest -q` (the backend floor is
unaffected — no test in it makes a live call, and the prompt-hash pin is updated in the same
step that edits the prompt), and the frontend floor if touched (it is not). `./scripts/gate.sh`
is run **once, at the end**, after the re-record. Running it mid-window produces a red F1
gate that carries no information; per runbook §4 that is not a licence to claim the
floor-exemption, which this task does not have.

**Cross-lane hazard, must be stated in the completion report.** The F1 cache is
machine-local and per-worktree (`backend/scripts/extraction_bench/.cache/`, gitignored).
Every other lane in `.worktrees/` will go red at the F1 gate the moment it picks up T1.17's
prompt change, and will stay red until it copies the new archive into its own `.cache/`.
Step 8 therefore commits the new cache as a dated archive and Step 9 documents the restore,
exactly as `docs/eval/2026-07-26-T0.05-extraction-baseline-cache/` is documented today.

### Step 2 — Extract the shared request-assembly seam in `ExtractionService`

- **Changes:** `backend/app/services/extraction.py`. Split `extract()` into three pieces
  with no behaviour change:
  - `build_extraction_request(content, *, system_prompt=None, with_classification=False)`
    → returns the assembled `messages`, the `seed`, and the `response_format`. This is the
    single definition of what the model is asked.
  - `extract_raw(...)` → dispatches through the orchestrator and returns the parsed raw
    dict (`_loads_extraction(response)`), **before** `clean_extraction`.
  - `extract(...)` → `clean_extraction(await self.extract_raw(...), content, relation_rescue=...)`.
  The prompt text and the schema are untouched in this step, so the assembled bytes are
  identical to today's.
- **Proof:** `tests/test_extraction_request_seam.py` pinning the sha256 of the assembled
  user message for both `with_classification=False` and `True` against the values captured
  immediately before the refactor. Plus the existing `tests/test_merged_extraction.py` and
  `tests/test_extraction.py` staying green unmodified.
- **Invariant:** T0.03 / doc 17 §3 — one shipping path, measured. Returning the **raw**
  dict is load-bearing: the F1 bench caches raw output so `--algo-only` can re-score the
  31 deterministic passes for free, which is the property T1.24a–e depend on. A seam that
  returned cleaned output would make every pass iteration cost 36 live calls.
- **Depends:** nothing.
- **Serialised:** before Steps 3 and 4.
- **Live calls:** 0.
- **Gate state:** green throughout. This step is independently mergeable if the window
  needs to be deferred.

### Step 3 — The reproducibility caveat as a real test (Ruling 4)

- **Changes:** `tests/test_extraction_reproducibility.py`, new. Four assertions, all
  offline against a fake orchestrator that records requests:
  1. **Same content + same gate state reproduces.** Two `build_extraction_request` calls
     with identical inputs produce byte-identical `messages` and an identical `seed`.
  2. **Flipped gate state legitimately differs.** `with_classification=True` vs `False`
     produce a **different user message** while the **seed is unchanged**. This is the half
     that stops a future agent "fixing" a correct non-reproduction: the non-identity is
     prompt-driven, and the seed is not the thing that varied.
  3. **The seed is content-derived and nothing else.** `_content_seed` over two different
     contents differs; over the same content under both gate states is equal.
  4. **The bench cache key separates gate states.** The key function (Step 4) returns
     different keys for the two gate states over the same content — so a cached output can
     never be served across a gate flip.
- **Proof / break-test:** delete the `seed=` forwarding in `build_extraction_request` and
  watch assertion 1 and 3 fail; restore. Collapse the cache key back to
  `content + "\x00" + system_prompt` and watch assertion 4 fail; restore. A guard nobody
  tried to break is a guard nobody tested.
- **Invariant:** invariant 18 / doc 17 §7 — determinism is engineered, and the gate-state
  caveat is carried, not papered over.
- **Depends:** Step 2 (and assertion 4 lands with Step 4).
- **Serialised:** no.
- **Live calls:** 0.
- **Docstring obligation:** the task says *"record that caveat in the test."* The module
  docstring states, in prose: re-extracting the same content under a different Phase-2 gate
  state (`classification_mode` flip, `classifier_kind` set or cleared) is **not**
  bit-identical even with the same seed, because the gate changes the prompt — a documented
  expected non-identity, not a bug (`CLAUDE.md`, doc 05 §6, doc 11 §5).

### Step 4 — Put `run_bench.py` on the shipping path, with both gate axes pinned (Ruling 3)

This is the step that makes the F1 number mean something. Five changes to
`backend/scripts/extraction_bench/run_bench.py`:

1. **Call the seam, not a hand-rolled prompt.** Replace the local `p = (...)` assembly and
   the direct `llm.chat_completion` with `ExtractionService.build_extraction_request` /
   `extract_raw`. The bench keeps its own `clean_extraction` call so the cache still stores
   raw output.
2. **Pin both gate axes explicitly.** The merged path fires only when the classifier is
   LLM-backed **and** `classification_mode == 'simple'` — pinning "the gate state" means
   pinning both. Concretely: `--gate merged` as the default (mapping to
   `with_classification=True`), with `--gate extract-only` available for T1.18's later use.
   The pinned values, the resolved model, and the two axes are **printed in the run header**
   so a pasted bench output is self-describing.
3. **Widen the cache key** to cover the full assembled request — system message *and* user
   message — so the schema string, the vocabulary width, and the merge gate all key. §2 is
   why. Keep the `[:16]` truncation and the flat `.cache/<key>.json` layout.
4. **Write a `manifest.json` into the cache directory** recording: the system-prompt
   sha256[:16], the schema sha256[:16], the gate state, the configured model, the git sha,
   and the record date. `--algo-only` **asserts the manifest matches the current assembly
   and exits non-zero with a readable message if not.** This converts the silent staleness
   of §2 into a loud red gate. It is the invariant-bearing guard of this step.
5. **Capture response metadata** (Ruling 6, and see §10 Q2): each cache entry becomes
   `{"raw": {...}, "meta": {"model": ..., "usage": {...}, "system_fingerprint": ...,
   "recorded_at": ...}}`, with a tolerant reader that accepts a bare raw dict as the legacy
   shape. This needs a small seam in `LLMOrchestrator.chat_completion`, which today returns
   only the content string (`llm.py:297`) and drops `data["model"]` and `data["usage"]`
   after `_log_usage`. Prefer an opt-in `return_meta: bool = False` returning
   `(content, meta)` over mutating the return type — 30-odd call sites read a `str`.

Also: **assert the configured extraction model equals the pinned `deepseek-v4-flash`** and
fail loud otherwise. The ledger fixes the model for parity and records that a run on
`-pro` is not comparable.

- **Proof:** `tests/test_extraction_bench_contract.py`, new, offline:
  - the bench's pinned gate state equals what `ProcessingPipeline`'s `can_merge` computes
    from `FEATURE_FLAGS_DEFAULTS["classification_mode"] == "simple"` and a `classifier_kind`
    of `None`/`llm` — i.e. the bench measures the **default shipping** configuration. Break
    it by flipping the pinned constant and watch it fail.
  - a manifest whose prompt fingerprint does not match the current prompt makes
    `--algo-only` exit non-zero.
  - two gate states over one content produce two distinct cache keys.
  - a legacy bare-dict cache entry is read without crashing, and an envelope entry returns
    the same raw payload.
- **Invariant:** T0.03 — the harness measures the shipping path, never a configuration
  nobody runs. Plus doc 17 §9: *"pipeline tests tolerate the gate-state caveat by pinning
  their gate configuration."*
- **Depends:** Step 2.
- **Serialised:** yes. **Opens the red window** (§6).
- **Live calls:** 0 (the code change itself; the cache is simply now empty).

## 8. Live-pass budget and the stopping rule (Ruling 6)

One pass = 36 live calls = 26 `gold.json` + 10 `gold_heldout.json`, against
`deepseek-v4-flash` at `https://api.deepseek.com/v1`.

| Pass | When | Calls | Purpose |
|---|---|---|---|
| A | Step 5, always | 36 | Widening + merge, prompt unchanged |
| B | Step 7, always | 36 | The strip, on top of A |
| Control | Case B only (§4) | 36 | Same-day reference under the old prompt |
| B′ | Contingency, at most once | 36 | One prompt revision after a B shortfall |

**Expected: 2 passes / 72 calls** in Case A with no shortfall. **Worst sanctioned case: 4
passes / 144 calls.**

**The stopping rule.**

1. A shortfall at Pass B triggers the `--diffs` triage **before** any edit. Classify each
   new miss and each new spurious against the Step-1 audit.
2. If the triage attributes losses to a **specific stripped rule**, the repair is to
   **restore that rule** — one prompt revision, one further pass (B′). If it attributes
   losses to a **pass gap** (a rule whose deterministic twin turns out to be partial), the
   repair is **not** T1.17's: keep the rule in the prompt and log a Tier-2 note naming the
   pass and the gap for T1.24b–e. Editing a pass is free to iterate (`--algo-only` re-scores
   at zero cost) but it is out of lane.
3. **At most one prompt revision.** If B′ still breaches a floor, **stop and report
   BLOCKED** with the numbers. Do not iterate a third time.

The reason for the hard cap is not cost — 36 DeepSeek calls are trivially cheap. It is that
`gold.json` is the same 26 items G-B measures. Iterating a prompt until the bench goes green
is tuning on the gate's own test; the held-out slice exists to catch exactly that, and the
ledger's rule is explicit: *never widen a bar to fit a result.* Two prompt variants is
engineering; five is overfitting with extra steps.

**Metadata capture is not an optional extra in this budget.** Every pass writes the served
`model` string and the usage envelope into its cache entries (Step 4.5). That retires half
of the recorded "no latency or token twin" gap on the new side and satisfies G-B's recorded
requirement that a shortfall attributed to a vendor-side model update is admissible only
with the metadata to show what was actually served. What it cannot retire is the **old**
side — see §4's note on the sibling lane.

## 10. Open questions I could not settle from the code and the docs

These are recorded rather than decided. Each names what I would do absent an answer, so the
plan is executable either way — but the answer may change the step.

**Q1 — What does T1.17 compare against if the 2026-07-26 baseline does not reproduce?**
Fully covered in §4. This is Tier 3 by runbook §5 (a gate's bar would have to change) and
this lane may not answer it. *Absent an answer:* execute Steps 1–7 with the control arm,
report both comparisons, and escalate rather than tick the Done-when box.

**Q2 — Is response-metadata capture T1.17's requirement or T1.50's?** The brief (Ruling 6)
frames it as an opportunity. The gate ledger frames it as a **requirement**: *"the runner
producing this gate's live F1 re-record must capture and record response metadata."* T1.17
**is** that runner — T1.24f's Verify is `--algo-only`, so the only live F1 record before
G-B is this one. This plan therefore treats it as in scope (Step 4.5), which costs a small
additive seam in `LLMOrchestrator`. *If the controller wants `LLMOrchestrator` untouched by
this lane*, the fallback is to capture the metadata in the bench by re-reading the raw
response — which the current return type makes impossible without duplicating the HTTP call,
so the honest fallback is "not captured", which reopens the ledger's gap. Flagging rather
than choosing silently.

**Q3 — Is preserving replayability of the committed T0.05 archive a requirement?** Widening
the cache key (Step 4.3) permanently unkeys the 2026-07-26 archive from the new code. I
found no doc requiring it to stay replayable: G-A is cleared, its evidence is archived at
`docs/eval/2026-07-27-T0.17-ga-evidence/`, and the prompt edit invalidates it regardless of
the key. *Absent an answer:* proceed, and record in the ledger that the archive is
replayable only at the pre-T1.17 commit. If someone does want a replayable historical probe,
say so **before** Step 4 — a compatibility shim after the fact is more expensive than a
`--legacy-key` flag added now.

**Q4 — Where exactly is the line between "minimal rules" and "rules the passes enforce"?**
Doc 06 §4 and doc 11 §5 state the principle; neither enumerates. §5 adopts "full subsumption
by an existing pass, demonstrated" and "keep on partial coverage". That is a judgement, and
a reviewer may legitimately want a more aggressive strip — the docs' language ("strip every
rule the passes already enforce") supports one. The disagreement is cheap to have at
Step 1's table and expensive to have after Pass B. *Absent an answer:* the conservative
reading, because it keeps the flip budget for irreducible re-rolls rather than spending it
on a deletion this lane chose.

**Q5 — Does the bench pin the default gate state or a deployed one?** The merged path fires
on `classification_mode == 'simple'`, read at runtime from the `config` row `feature_flags`,
which an operator can change. So there is no single "shipping" gate state — there is a
default one (`FEATURE_FLAGS_DEFAULTS`) and whatever a given install sets. This plan pins the
**default**, ties it to `FEATURE_FLAGS_DEFAULTS` with a test, and prints it in the run
header. That is defensible under T0.03 but it is a choice: an install running area-grained
classification takes the two-call path and the bench number does not describe it. *Absent an
answer:* pin the default and say so in the output.

**Q6 — Who pays for the retrieval eval's re-record?** §3's finding. T1.17 breaks ~94 cached
extraction calls and, more importantly, changes the ingested graph that the retrieval eval's
accuracy numbers were computed over. T1.50's task text does not mention inheriting a
destroyed baseline. *Absent an answer:* T1.17 records it as a Tier-2 amendment against
T1.50 and does not pay it. If the controller would rather the two live records happen in one
sitting (they share the same credentials and the same model pin), that is a scheduling
decision worth making before Step 5 rather than after Step 9.

**Q7 — Should the 7 → 9 widening be measurable *retrospectively*?** Pass A measures the
widening only as it exists *inside* the merged call. A clean single-variable measurement of
T1.23 alone would need a fifth pass (old prompt, extract-only gate, 9-type schema) — 36 more
calls. This plan does not budget it, because Pass A is a sufficient answer to "did the
widening break anything" and T1.23 shipped with the widening already active in the shipping
path. Recorded in case a reviewer wants the cleaner decomposition.
