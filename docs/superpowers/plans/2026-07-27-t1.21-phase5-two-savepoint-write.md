## 2. The `canonical_map` contract T1.20 landed (Ruling 1, quoted verbatim)

> `dict[tuple[str, str], str]`. Key `(name_lower, entity_type)` — name `.lower()`-ed, type a
> normalized `ENTITY_TYPES` value; together the `entities` uniqueness key. Value is the
> surviving entity's name, lowercase.
>
> **Only canonicalized names appear.** A name that stays distinct is *absent* rather than
> mapped to itself, so **`key in canonical_map` is the rewrite test** — not
> `map[key] != key`.
>
> Phase 5 resolves relation endpoints by the same key, recovering each endpoint's type from
> the same extraction's entity list built **before** the names are rewritten, and leaves an
> endpoint untouched when its type cannot be recovered.

The ordering clause is the subtle one, and the current code already honours it: the
`ent_types` map (`pipeline.py:490`) is built by a dict comprehension over
`extraction["entities"]` that **runs to completion before** the rewrite loop at `:494`
mutates any `entity["name"]`. Step 4 makes that ordering explicit and unbreakable rather than
incidental, and closes the one hole the contract does not cover: a name that appears under
**two** types in the same extraction (§4.3).

## 3. The boundary — what T1.21 delivers and what it does not (Ruling 3)

Three downstream tasks cover mechanisms that physically live inside savepoint B. Without an
explicit split, each will assume another did it. The rule for this plan: **T1.21 owns the
transactional structure, the call site, and the failure-state machinery; the dependents own
the semantics of what runs inside.**

| Mechanism | T1.21 delivers | The dependent delivers |
|---|---|---|
| Strip before rewrite (`delete_by_memory_id`) | Its **transactional position** relative to savepoints A and B (decision D1, §6), and that a strip failure is **visible in the per-memory status** rather than log-only | **T1.26**: the delete semantics — relation deleted only when no live memory asserts it, entity only when no live memory asserts it and no surviving relation references it, dangling `memory_ids` self-heal, re-extraction idempotence |
| `technologies` denorm | That the recompute happens **inside savepoint B**, in **one whole-column assignment** (never a partial update), from the entities written by that same savepoint | **T1.27**: lowercase, the GIN index and its use by the supersession query plan, `_TYPE_OVERRIDES` |
| Supersession | That `detect_supersessions` is **called inside savepoint B**, after `flush([mem_record])` so the technologies the detector reads are visible, and that its failure attributes to `graph`, not `vector` | **T1.36**: rules 1–6, the `(created_at, id)` tie-break, the per-target speculative gate, the atomic `status`+`superseded_by` flip, and **widening the trigger predicate from `REPLACES` to `REPLACES_FAMILY`** |
| Pipeline stepper UI | The wire contract: exactly one `pipeline.{completed,partial,failed}` per memory per batch, on **every** path including the escaped-exception path | **T1.45**: the UI that consumes it |
| Vault enqueue (`sources_changed`) | **Nothing.** Explicitly out of scope | **T2.47** (`Depends: T1.21, T2.02`, doc 05 §8.4). T1.21 must not emit a `sources_changed` event or add a provenance-no-op guard |

**On the supersession trigger predicate specifically.** Both the Phase-5 call-site guard
(`pipeline.py:656-659`, `r.get("type") == "REPLACES"`) and `detect_supersessions`'s own target
collection (`supersession.py:89-90`, `rel.get("type") != "REPLACES"`) are narrow today, while
doc 05 §8.2 and invariant 12 say the **REPLACES family** (`REPLACES`, `IMPROVES_ON`, legacy
`BUILDS_ON`, collapsed via `family_key`) should fire it. T1.21 **deliberately leaves both
narrow** and does not widen either — they are one behaviour in two files and must change
together, which is T1.36's job. This plan records it here so T1.36 inherits it as a known
open item rather than discovering it.

## 4. Defects found by reading the code

Five findings. Each is a step below. Two of them (4.1, 4.2) are the reason this task cannot be
"add tests and close".

### 4.1 A savepoint-B rollback expires `mem_record`, and the next attribute read raises `MissingGreenlet`

**The path.** Inside savepoint B, `mem_record.technologies = sorted(tech_names)`
(`pipeline.py:650`) dirties the ORM object; `await session.flush([mem_record])` (`:660`)
flushes it before supersession. If anything after that raises — `detect_supersessions`, the
flush itself, a constraint violation on the supersession `UPDATE` — SQLAlchemy rolls the
savepoint back and **expires the object**. Line 692 then reads `mem_record.project` to build
the `record_event` payload. Reading an expired attribute on an `AsyncSession` outside an
`await` triggers a synchronous lazy load and raises `MissingGreenlet`.

That exception escapes `_write_memory` entirely, is caught by `return_exceptions=True` in
`process_batch` (`:1013`), and is normalised to `{"embed": "unknown", "extract": "unknown",
"vector": "error", "graph": "error"}` — so **a graph failure is reported as a vector
failure**, the vector write is reported as failed even though it committed, and **no
`pipeline.*` broadcast is emitted for that memory at all**. That is a direct violation of the
task's own first and fourth Done-when boxes.

**Verified, not inferred.** Reproduced against `darkmem_test_5` with a two-column throwaway
table and no darkmem code in the loop, at
`<scratchpad>/probe_savepoint_expiry.py`:

```
loaded: A0 B0
caught: boom inside savepoint B
ACCESS RAISED: MissingGreenlet greenlet_spawn has not been called; can't call await_only() here.
ACCESS RAISED (a): MissingGreenlet greenlet_spawn has not been called; can't call await_only() here.
```

Both the explicit-`flush` and the no-explicit-`flush` variants reproduce, and the expiry
covers the **whole object** — the untouched column `b` raises just as the modified column `a`
does. So merely assigning `technologies` inside B is enough to arm it; the `flush` is not
required.

**Why the existing test does not catch it.** `test_pipeline_savepoint_decouple.py` fails
`create_relationship`, which runs at `:640` — *before* line 650 dirties `mem_record`. The
object is still clean at rollback, so nothing expires. The test passes and the bug survives.
This is exactly the class of hole the corpus exists to catch: a green suite over a broken
invariant.

### 4.2 A Phase-3 entity-cache DB failure escapes `process_batch` with no failure row (Ruling 2)

`_lookup_entity_embeddings` (`pipeline.py:309-320`) opens a session and calls
`repo.get_cached_entity_embeddings` with **no guard**. `_embed_entity_names`'s `try` covers
only `llm.embed_batch_chunked` (`:397-405`), and `process_batch`'s call site (`:913-917`) is
unguarded. A DB error in that read therefore propagates out of `process_batch` to the caller.

The consequence is not a mislabelled status — it is **no status at all**: the batch never
reaches the failure-derivation block, so **zero** `pipeline_failures` rows are written and
zero broadcasts fire. Every memory in the batch is invisible to triage. Same defect class as
T1.07's `UnboundLocalError`, which a 909-green backend floor missed and only benchlib caught.

**Ruling 2 asked whether this belongs to T1.21. It does, with a caveat worth acting on.**
The narrow fix — a `try` around the DB read in `_lookup_entity_embeddings`, degrading a cache
read failure into "everything is a miss" — is mechanically Phase 3's code and thus T1.19's
region. But T1.19 is merged, and reopening a done task to chase a pre-existing hole is worse
than assigning it here, which is the reason the controller gave. I agree with the assignment,
and I would go further: the narrow fix alone is **insufficient**, because it repairs one
call site of a general hole. `_resolve_classifier` is guarded, Phase 1 is guarded, Phase 4's
probes are guarded — but the guarding is per-site and a future phase edit re-opens it.

T1.21 should therefore ship **both halves**, and the second is the invariant-bearing one:

- **(a)** the local degradation in `_lookup_entity_embeddings` (a cache read failure is a
  miss, not a batch abort), and
- **(b)** a **batch-level backstop**: any exception escaping phases 1–4 is caught in
  `process_batch`, and every entry in the batch still gets a status dict, a
  `pipeline_failures` row and a `pipeline.failed` broadcast.

(b) is the one that makes "no memory ever leaves `process_batch` without a status" a property
rather than a coincidence, and it is unambiguously T1.21's because T1.21 owns the failure-state
machinery. See Step 7.

### 4.3 A name carrying two entity types in one extraction rewrites its relation endpoints under the wrong type

`ent_types` (`pipeline.py:490-493`) is a dict comprehension keyed by lowercased name. When one
extraction emits `{"name": "react", "type": "tool"}` and `{"name": "React", "type": "concept"}`,
the comprehension keeps whichever came last, and every relation endpoint named `react` is then
resolved under that single arbitrary type. If `("react", "concept")` is in `canonical_map` and
`("react", "tool")` is not, an endpoint that was really the `tool` gets rewritten anyway — the
exact cross-type rebinding Ruling 1's key design exists to prevent.

Ruling 1 says the endpoint is left untouched "when its type cannot be recovered". An ambiguous
name **is** a name whose type cannot be recovered, so the contract already implies the fix:
build `name_lower -> set[type]` and rewrite only when the set has exactly one member.

### 4.4 `store_crossrefs` early-returns on an empty list, so stale crossrefs survive a re-extraction

`vector.py:409-411`: `if not crossrefs: return`. The `DELETE FROM memory_crossrefs` that would
clear the previous run's rows sits *after* that guard. Doc 05 §8.3 specifies DELETE+INSERT. A
memory reprocessed after its neighbours were deleted (or after an embedder rotation moved it
into a sparse partition) keeps crossref rows pointing at similarities that no longer hold,
and nothing ever clears them. Crossrefs are named explicitly in T1.21's Done-when, so this is
in scope.

### 4.5 Smaller items, batched into the steps that touch their code

- A `delete_by_memory_id` failure is caught and **logged only** (`pipeline.py:529-535`); the
  new graph is then written on top of the old set. Idempotence breaks silently and the status
  says `graph=ok`. Invariant 14 says a failure surfaces. (Step 3.)
- `_write_memory`'s `flags` parameter is accepted and never read. Removing it changes a
  9-positional-argument signature that `test_pipeline_savepoint_decouple.py` calls positionally.
  (Step 1 absorbs that test, so the signature change is safe there.)
- A `KeyError` on a malformed entity dict at `:495` (`entity["name"]`) escapes `_write_memory`
  *before* the session opens, and is normalised to `vector=error, graph=error` although
  nothing was attempted. (Step 4.)
- The failure-derivation loop (`:1043-1067`) commits once **outside** the loop and is wrapped
  in one broad `except`, so a single bad row aborts the remaining memories' failure records.
  (Step 6.)
- On the savepoint-A-failure path, `record_event` falls back to `entry.get("project")`, and the
  entry dicts `process_batch` builds carry no `project` key — so the journal row for a failed
  memory has a null project and drops out of project-scoped timelines. (Step 6.)

## 5. The steps

Each step states what changes, which invariant it discharges, what proves it, and what it
depends on. Sized at roughly the corpus's `M` granularity. Every step ends green on both its
own test file and the repo floor; no step is allowed to land red.

Standing conventions for every step:

- Interpreter is `backend/.venv/bin/python`, run from `backend/`. There is no `python` on PATH.
- Tests go in `backend/tests/test_pipeline_savepoints.py` unless named otherwise, and follow
  the Phase-1/Phase-3 idiom: a real committing `async_sessionmaker(test_engine)`, helpers

  `cleanup`, `spy_partition_traffic`), only the embed and extraction calls mocked, and explicit

- Any step whose subject is an invariant must be proven by **breaking it on purpose**, watching

### Step 1 — Stand up `tests/test_pipeline_savepoints.py` and absorb the existing decouple test

**Depends:** nothing. **Must run first** — every later step's proof lands in this file.

**What changes.** Create `backend/tests/test_pipeline_savepoints.py` as the Phase-5 suite.
Move `test_graph_failure_keeps_embedding_and_records_graph_step` in from
`tests/test_pipeline_savepoint_decouple.py` and delete that file, so the behaviour has exactly

teardown that drops all of it.

Remove the unused `flags` parameter from `_write_memory` in the same commit, since this step
is already rewriting the only positional call site.

**Invariant discharged.** None directly — this is the harness. Its value is that the Verify

**Proof.** `timeout 600 .venv/bin/python -m pytest tests/test_pipeline_savepoints.py -q`

### Step 2 — Kill the `MissingGreenlet` escape after a savepoint-B rollback

**Depends:** Step 1. **Highest-risk step; do it before any other behaviour change**, because
every later forced-failure test in this suite runs straight into it.

**What changes.** Nothing that `_write_memory` reads *after* savepoint B may be an ORM
attribute on an object that savepoint B may have dirtied. Capture the values into plain locals
**before** entering savepoint B — at minimum `project`, which `record_event` needs — and use
the locals afterwards. Do not "fix" this by re-reading with an `await` inside the exception
handler: CLAUDE.md's async-session rule says roll back before mutating ORM objects in an error
handler, and an extra round-trip on the failure path is a second thing that can fail.

**Invariant discharged.** Honest partial results (14) — a graph failure must be attributed to
the graph step. Async session lifetime (11).

**Proof.** A test that monkeypatches `detect_supersessions` to raise, on a memory whose
extraction carries a `REPLACES` relation, and asserts: no exception escapes `_write_memory`;
`status["vector"] == "ok"`; `status["graph"] == "error"`; the content-embedding row is present
in the partition; and a `pipeline.failed`-or-`partial` broadcast was captured. **Break-test:**
revert the local-capture change and confirm the test fails with `MissingGreenlet`, not with an
assertion — the failure mode itself is the evidence.

Add the sibling case that fails `session.flush([mem_record])` directly, since it sits between
the technologies assignment and supersession and is the other arming point.

### Step 3 — Pin the savepoint boundary, and settle the strip's transactional position

**Depends:** Step 2. **Blocked on decision D1 (§6).**

**What changes.** Implement whichever position D1 selects for `delete_by_memory_id`, and make
a strip failure **visible**: it currently sets no status field, so a memory whose graph is now
a mix of two extractions reports `graph=ok`. At minimum it must degrade the step status and
populate `status["error"]`; the exact code (a new `failed_step` value versus reusing
`graph_write`) is decision D2.

**Invariant discharged.** Idempotent strip-before-rewrite (8) — the *placement* half only;
T1.26 owns the delete semantics. Honest partial results (14).

**Proof.** A forced-failure matrix over savepoints A and B, one test per point, each asserting
the full four-field status dict and the on-disk state:

| Forced failure at | Expect `vector` | Expect `graph` | On disk |
|---|---|---|---|
| `PostgresVectorRepository.upsert` | `error` | `skipped` | no embedding row, no entities |
| `create_entity` | `ok` | `error` | embedding row present, no entities |
| `upsert_entity_embedding` | `ok` | `error` | embedding row present, entity rolled back |
| `create_relationship` (the absorbed test) | `ok` | `error` | embedding row present |
| `detect_supersessions` (Step 2) | `ok` | `error` | embedding row present |
| `delete_by_memory_id` | `ok` | per D2 | per D1 |

Plus a test pinning D1's answer directly: seed a prior graph for the memory, force a
savepoint-B failure, and assert whether the prior graph survives. That test is the executable

### Step 4 — Make the `canonical_map` application match Ruling 1 exactly

**Depends:** Step 1. Independent of Steps 2/3 in logic, but shares the file.

**What changes.**

1. Replace the `ent_types` dict comprehension with a `name_lower -> set[type]` map, and rewrite
   a relation endpoint only when that set has exactly one member. An ambiguous name is a name
   whose type cannot be recovered, and Ruling 1 says leave it untouched (§4.3).
2. Keep the map's construction structurally before the rewrite loop and say why in one comment
   — the ordering is the contract's subtle clause and nothing else in the code signals it.
3. Keep `key in canonical_map` as the rewrite test; do not introduce `map.get(key, key)` or a
   `map[key] != key` comparison anywhere.
4. Guard the malformed-entity `KeyError` at `:495` so a bad extraction dict degrades to
   `extract=error` rather than to a mislabelled `vector=error` (§4.5).

**Invariant discharged.** Lowercase entity names + `display_name` (7); closed taxonomy (5) at
the point where the map is keyed on a normalized type.

**Proof.** Four tests.

- **Pre-rewrite type recovery.** An extraction where entity `postgresql`/`tool` canonicalizes
  to `postgres`, carrying a relation `postgresql -[RUNS_ON]-> linux`. Assert the relation's
  source endpoint is rewritten to `postgres`. **Break-test:** move the `ent_types` construction
  after the rewrite loop; the endpoint stops resolving (its type is now looked up under the
  already-rewritten name) and the test fails.
- **Absence means no rewrite.** A `canonical_map` containing a self-mapping entry
  (`("x","tool") -> "x"`) must be treated identically to absence; and a name absent from the
  map is never rewritten. This is the test that fails if someone reintroduces `map[key] != key`.
- **Type ambiguity.** One extraction emitting `react`/`tool` and `react`/`concept` with
  `canonical_map` populated for only one of them, plus a relation on `react`. Assert the
  endpoint is left untouched.
- **Cross-type non-collapse.** `("react","concept") -> "reactjs"` must not rename the `tool`
  entity named `react`.

Also assert here that a **canonicalized** entity writes no `properties.display_name` (the
surviving entity's own display casing must not be overwritten by a variant's), while a
**non-canonicalized** entity whose original casing differs does write one. That is invariant 7
and the current code is already correct; the test is what keeps it correct.

### Step 5 — Crossrefs: separate session, after the commit, and a real DELETE+INSERT

**Depends:** Step 1. **This is the one step that can run in a separate lane** — its code change
is in `app/repositories/vector.py`, not `pipeline.py`.

**What changes.** In `store_crossrefs`, run the `DELETE` unconditionally and skip only the
`INSERT` when the list is empty (§4.4). In `_write_memory`, normalise the `memory_id` at the
crossref boundary explicitly (invariant 9) rather than relying on `find_similar_memories`
happening to return strings and the `CAST(:related AS uuid[])` happening to accept them.

**Invariant discharged.** Async session lifetime (11) — the crossref session opens only after
the main transaction committed and released its locks. `memory_id` str/UUID drift (9). asyncpg
CAST (10) on the `unnest(CAST(:related AS uuid[]), CAST(:scores AS double precision[]))` params.

**Proof.**

- **Ordering.** Instrument the factory to record session open/close and the main `commit()`,
  and assert the crossref session opens strictly after the main commit. **Break-test:** hoist
  the crossref block inside the main `async with`; the ordering assertion fails.
- **Stale clearance.** Seed crossrefs for a memory, reprocess it with a similar-set that is now
  empty, assert `memory_crossrefs` for that memory is empty. Fails today.
- **A crossref failure does not change the status.** Force `find_similar_memories` to raise and
  assert the status dict is unchanged and the broadcast still fires — crossrefs are enrichment,
  not a pipeline step, and there is no `crossref` field in the status by design.

### Step 6 — Failure derivation and the broadcast, made per-memory and total

**Depends:** Steps 2 and 3 (their status semantics are what this asserts over).

**What changes.**

1. Wrap the record/resolve call **per memory** inside the loop so one memory's failure-row
   write cannot suppress the rest; keep one commit at the end.
2. Emit exactly one `pipeline.{completed,partial,failed}` per memory per batch on **every**
   path, including the `return_exceptions=True` normalisation path at `:1019-1028`, which today
   emits nothing. Decision D3 (§6) covers whether the broadcast moves to the batch level
   wholesale or the exception path gains its own.
3. Populate `record_event`'s `project` on the savepoint-A-failure path (§4.5) — carry `project`
   on the entry dicts `process_batch` builds, or read it from the memory row before the
   savepoints.

**Invariant discharged.** Honest partial results (14). `memory_id` str/UUID drift (9) at the
`UUID(mem_id_str)` boundary in the derivation loop.

**Proof.**

- A batch of three memories where the middle one's `_write_memory` raises: assert three status
  dicts returned, three `pipeline_failures` rows or resolutions, and three broadcasts.
- `_derive_outcome` truth-table test over all four step fields including `skipped`, `pending`
  and `unknown`, asserting `completed` / `partial` / `failed`, and asserting the durable
  `extracted` event's `outcome` equals the broadcast's suffix for the same memory — the journal
  and the wire may never disagree.
- A memory that failed on a previous run and succeeds now **resolves** its open
  `pipeline_failures` row (`resolved_at` set), which is the half of Done-when-3 that "records"
  alone does not cover.

### Step 7 — Honest degradation for an escaping phase exception (Ruling 2)

**Depends:** Step 6 (it reuses that step's per-memory derivation).

**What changes.** Both halves from §4.2:

- **(a)** guard the DB read in `_lookup_entity_embeddings` so a cache-read failure degrades to
  "all names are misses" — the DB cache is an optimisation, and its loss must cost latency, not
  correctness. Log at `warning` with the exception type, matching `_store_entity_embeddings`'s
  existing idiom two functions down.
- **(b)** a batch-level backstop in `process_batch`: an exception escaping phases 1–4 still
  produces, for every entry, a status dict, a `pipeline_failures` row and a `pipeline.failed`
  broadcast. `process_batch` returns a list the same length as `entries` on **every** path.

**Invariant discharged.** Honest partial results (14). No silent degradation.

**Proof.**

- Monkeypatch `PostgresGraphRepository.get_cached_entity_embeddings` to raise. Assert
  `process_batch` returns normally, the misses were embedded, and the graph was written —
  i.e. the run degrades to a cold cache. **Break-test:** remove the guard and confirm the test
  fails with the raw exception.
- Monkeypatch something in Phase 4 to raise outside the existing per-probe guard. Assert
  `len(result) == len(entries)`, one `pipeline_failures` row per entry, one broadcast per entry.
  This is the general property; it is what makes the guarantee survive the next phase edit.
- A property-style assertion reused across the suite: **for every test in this file, every
  entry passed to `process_batch` appears exactly once in the returned list and produces
  exactly one broadcast.** Implement it as a helper the tests call, not as a comment.

## 6. Decisions required before execution

These cannot be settled from the code and docs. Naming them is cheaper than discovering them
mid-execution (Ruling 5). **D1 blocks Step 3.** D2 and D3 have safe defaults and can be
resolved by the executing agent if no ruling arrives, provided the choice is logged.

### D1 — Where does `delete_by_memory_id` sit relative to the savepoints? *(blocking; possible Tier 3)*

**The conflict.** Doc 05 §8's flowchart is explicit: `W --> STRIP --> SA --> SB`. The strip
runs **before savepoint A, in the outer transaction**, which is exactly what the code does
today (`pipeline.py:529-535`). But the same section states the split exists so "a failure in B
rolls back only B", and with the strip outside, a savepoint-B failure leaves the memory with
**its prior graph deleted and no new graph written** — the outer `commit()` at `:696` makes the
deletion durable. A savepoint-A failure does the same. The strip is the one part of the write
that a failed write cannot undo.

**Reading 1 — keep it where the doc puts it.** The loss is recoverable: the failure is recorded
as `graph_write`, the triage surface offers a retry, and doc 05 §9 says the strip is precisely
what makes a re-run safe. Entities shared with other live memories are protected by
`delete_by_memory_id`'s own guards, so the blast radius is this memory's exclusive
contributions. Cost: a window in which the graph reflects neither extraction.

**Reading 2 — move it inside savepoint B.** The graph for a memory is then always exactly one
extraction's output, never an empty state nobody chose. Cost: contradicts doc 05 §8's flowchart,
and on a B failure the graph silently reflects the *previous* extraction, which is stale rather
than absent — arguably a worse kind of wrong, because it looks fine.

**Recommendation:** Reading 1 — keep the current position, and pin it with the Step-3 test so
the semantics are chosen rather than inherited. Reading 2 would require editing doc 05 §8's
flowchart, and per runbook §5 the corpus doc wins until a human decides otherwise. **If the
reviewer prefers Reading 2, that is a Tier-3 escalation and the executing agent must stop, not
implement it.**

### D2 — What does a strip failure do to the status? *(non-blocking)*

Today: logged, nothing else. Options: (a) set `graph=error` and skip savepoint B entirely —
strongest, because a graph written over an unstripped set is exactly the duplicate-by-type
accumulation the strip exists to prevent; (b) proceed but set `status["error"]` so the memory
lands in triage with `graph=ok`; (c) a new `failed_step` value such as `graph_strip`, which
touches the `pipeline_failures` vocabulary the T1.45 triage UI renders.

**Recommendation:** (a). It is the only option under which the graph on disk is always one
extraction's output. It costs a graph write that might have succeeded, which is the cheap
direction of the trade. (c) is attractive for triage legibility but adds a vocabulary value
that T1.45 has to render, which makes it a Tier-2 change; defer it.

### D3 — Does the `pipeline.*` broadcast move to the batch level? *(non-blocking)*

The broadcast lives in `_write_memory` and therefore cannot fire for a memory whose
`_write_memory` raised. Options: (a) centralise it in `process_batch` after the failure rows are
written, so it fires exactly once per memory on every path and the wire is consistent with the
triage list; (b) leave it in `_write_memory` and add a second emitter on the exception path.

**Recommendation:** (a). It makes "exactly one broadcast per memory per batch" checkable in one
place, and it orders the broadcast *after* the `pipeline_failures` row, so a UI that reacts to
`pipeline.failed` by fetching the failure list cannot race an unwritten row. The cost is a
changed emission order that a stepper UI might depend on — and T1.45 is not built yet, which
makes now the only cheap moment to change it. Log this as a Tier-2 note for T1.45 either way.

## 8. Scheduling — what serialises and what does not

**Steps 1, 2, 3, 4, 6 and 7 all edit `_write_memory` / `process_batch` in
`backend/app/services/pipeline.py`.** They must run **serialised in one lane**, in the order
given. This is the same reasoning the baseline schema uses: a single shared mutable artefact
with two concurrent editors conflicts every time, and here the conflicts are semantic (each step
changes the status-dict contract the next step asserts over), not merely textual.

The strict ordering constraints, stated as reasons rather than a list:

- Step 1 is first because it creates the file every later proof lands in, and because it removes
  the dead `flags` parameter while its only positional call site is being rewritten anyway.
- Step 2 precedes Step 3 because the forced-failure matrix in Step 3 includes failure points that
  hit the `MissingGreenlet` path; running that matrix first produces failures that look like
  status bugs and are not.
- Step 3 precedes Step 6 because Step 6 asserts over the status semantics Step 3 fixes.
- Step 6 precedes Step 7 because Step 7's backstop reuses Step 6's per-memory derivation.

**Step 5 is the exception and can run concurrently in a second lane.** Its production change is
confined to `app/repositories/vector.py::store_crossrefs`; its tests land in the shared test file,
so it should either be sequenced last within the main lane or land its tests in a
`tests/test_pipeline_crossrefs.py` of its own if it truly runs in parallel. If the controller
wants two lanes, that split is the one to make — but the saving is small and the merge cost is
real, so **one lane, eight sequential steps, is the recommendation.**

**Step 4 is the best candidate for a second lane if one is wanted anyway**: it touches lines
490–508, a contiguous region no other step edits, and its tests are self-contained. It still
shares the file, so it needs a rebase rather than a merge.
