## 1. What this task is, and what it is not

This is two independent rebuild-to-real workstreams sharing one task because they are the two
remaining EXPLORE/WORK-group destinations doc 13 §3 names as still demo-backed after T1.58's
flip (T1.58's own record-and-route table, §5, lists both "Chat" and "Memory Graph explorer" as
"renders fake data presented as real, unconditionally... T1.60 (todo)"). It is:

- **A UI-binding task against an established pattern.** T1.44 (Memories) and T1.65
  (`projectStore`/query-key registry) already built every vocabulary component and every piece
  of scaffolding this task needs (`LayerChip`, `LifecycleBadge`, `VerificationBadge`,
  `ExclusionStrip`, `WhyRetrievedTrace`, the `DEMO ? demo : real` route-split idiom, the
  project-scoped query-key registry). This task consumes that vocabulary; it does not invent a
  second one.
- **A route consolidation for Memory Graph**, resolving a real, confirmed navigation bug found
  during v1's planning pass (§4): the sidebar nav already links to `/memory-graph`, but that
  route currently serves 100% demo data while the *actually real* implementation sits, unlinked,
  at the orphaned `/unified-graph` path.
- **A one-line, mechanical backend fix** (§5) — the live chat SSE `sources` event omits the
  memory `id` that the same data already carries once persisted, breaking citation links during
  a live stream specifically.
- **Two small, targeted backend/frontend fixes to the graph entity overlay** (§4.5, new in this
  revision) — closing the amendment log's F8/F10/I1 assignment to this task, using the same
  "label the row, don't narrow the query" idiom the codebase already established for the
  analogous isolation-probe findings (T1.29d, T1.35a), not new retrieval logic.

It is explicitly **not**:

- **Retrieval-fusion surgery.** Doc 13 §4.1 (amended 2026-07-28, after v1's plan surfaced the
  finding and the controller confirmed it in code — see the doc's own text) now states plainly
  that Chat's reads "do not today ride the same ranking path as Memories," names the third
  implementation (`ChatService._search_memories` → `vector_repo.search` directly, no RRF, no
  trace), and assigns the convergence to **T2.58**. v1's finding is therefore already ratified
  into the doc; this plan does not reopen it, and does not attempt the convergence. §6 details
  what this plan does instead: satisfy the literal Done-when (layer, verification,
  superseded/stale labels on every cited row, across *all three* render sites — §6, corrected
  this revision) using data the existing chat retrieval already emits.
- **A community-detection or graph-layout rebuild.** `MemoryGraphExplorer`'s force/tree/circles
  layouts and topic-halo rendering are demo-fixture-only (`src/demo/explore.ts`'s
  `layoutGraph`/`scopeMemoryGraph` assume synthetic data shapes). Re-deriving that exact UI
  against live louvain-clustered data would be new algorithmic work well past this task's
  Done-when, which asks only that Memory Graph "reads the real graph with project scope applied
  in SQL." §4 explains the choice: keep the *already-real* `UnifiedGraphPage` implementation as
  the real branch, and keep `MemoryGraphExplorer` as the demo branch, exactly matching the
  `DEMO ? demo : real` idiom used everywhere else in the codebase, rather than rebuilding either
  side to match the other's UI.
- **Project-scoping the entity/relation graph itself** (F8's design half — distinct from F10's
  truncation bug). CLAUDE.md states entities are **not** memory-scoped; `memory_ids` on an
  entity legitimately spans every project that asserts it, and trimming that array would break
  the neighbour derivation that consumes it (the same reasoning the amendment log used to defer
  this as a design decision rather than a leak fix). §4.5 records the decision explicitly rather
  than silently declining it a second time.
- **A live-status re-join for persisted chat citations** (Important finding 3, fossilisation).
  Recorded as a known limitation (§6.1, §9) and proposed as a follow-on (Step 9's amendment
  log), not built here — the fix touches `app/api/routes/chat.py` and its response schema,
  neither in this task's original lane, on an already-`L`-sized task.
- **A fix for the second deferred query-key gap (`tags`).** T1.65 recorded `GET /tags` has no
  project filter on the backend at all. Neither Chat nor Memory Graph calls `useTags` anywhere
  (confirmed by grep — the only caller is `use-memory-api.ts`), so it stays `deferred`,
  unchanged, in `query-keys.ts`. This is a real gap but not this task's; recorded so the
  disposition reads as a decision, not an oversight.

### 4.4 Project scope, and the entity overlay's real mechanism (corrected this revision)

T1.65's `query-keys.ts` registry (verified by direct read, `unifiedGraph` entry) already records
the exact gap: `GET /graph/unified` accepts `?project=` since T1.29d (confirmed live —
`backend/app/api/routes/graph.py`'s `get_unified_graph` has always taken a `project: str | None
= Query(None)` param and passed it through to `GraphService.get_unified_graph`, which applies it
via `self._memory_scope(MemoryFilter(project=project) ...)` fed into
`vector_repo.get_louvain_clustered_vectors` — **a real SQL `WHERE` scope, not a client-side
filter**, confirmed by reading `app/services/graph.py:38-89`) — but `useUnifiedGraph` never
sends it. This is purely a frontend gap for the **memory-node** list; **no backend change is
needed for those nodes** to satisfy Done-when #2's "applied in SQL" — the SQL pushdown already
exists and only needs a caller.

- `hooks/api/use-graph-api.ts`'s `useUnifiedGraph` reads `useProjectStore((s) =>
  s.activeProject)` internally (same idiom T1.65's own `useMemories` retrofit used — the hook
  itself scopes, not each call site opting in) and appends `&project=${encodeURIComponent(
  project)}` to the URL. Its query key is rebuilt via `useProjectScopedKey("unifiedGraph",
  similarityThreshold, minClusterSize, includeEntities)`.
- `query-keys.ts`'s `unifiedGraph` entry moves from `{ kind: "deferred", reason: "..." }` to
  `{ kind: "auto" }`. The entity-overlay path (`include_entities=true`) is **not** covered by
  this same SQL pushdown, and this plan's own v1 was wrong to say it was: **v1 claimed the
  entity overlay was "scoped-by-construction," read only from the call site
  (`get_unified_graph`'s `if include_entities:` branch, which passes the already-scoped
  `memory_nodes`) and not from what `_fetch_entity_overlay` itself does.** Read directly
  (`app/services/graph.py:215-236`):

  ```python
  async def _fetch_entity_overlay(self, memory_nodes: list[dict]) -> tuple[list[dict], list[dict]]:
      ...
      memory_id_set = {m["id"] for m in memory_nodes}
      full_graph = await self.graph_repo.get_full_graph(limit=500)   # unscoped, no ORDER BY
      entities = [e for e in full_graph["entities"]
                  if any(mid in memory_id_set for mid in e.get("memory_ids", []))]
      ...
  ```

  `get_full_graph` (`app/repositories/graph.py:426`) is
  `SELECT id, name, entity_type, properties, memory_ids FROM entities LIMIT :limit` — **no
  project predicate, no status predicate, no `ORDER BY`, over the entire `entities` table**,
  followed by a Python membership filter against `memory_id_set`. Two consequences, and they are
  different findings:
  - **No cross-project entity *content* reaches the rendered overlay**, because an entity only
    survives the membership filter if one of its `memory_ids` is in the current (already
    project-scoped) `memory_nodes` set. This is the half v1's §4.4 got right, and it is still
    true.
  - **If the `entities` table has more than 500 rows, entities relevant to the current
    project's `memory_nodes` can be silently dropped before the membership filter ever runs**,
    because there is no `ORDER BY` and the query is not scoped to the rows that would matter —
    a fixed, arbitrary 500-row slice of the whole table is fetched first, and membership is
    tested only within that slice. This is an **under-return**, not a leak: a user sees fewer
    entities than actually apply, with zero error and zero UI signal. This is F10 (§4.5), not
    "scoped-by-construction," and v1's claim to the contrary is wrong and is corrected here.
- `tags` stays `deferred`, unchanged (§1).

### 4.5 F8 / F10 / I1 — dropped by v1, disposed of here

The 2026-07-27 amendment log entry assigns **F8** and **F10** to T1.60 as one decision (both
graph-explorer surfaces); T1.35a's 2026-07-28 entry records the isolation probe's **I1**
(id-only exposure, informational, not counted) as still owned by T1.60. v1 mentioned none of
these. Verified against the tree (not re-derived from the log text alone):

- **F8** — `GET /graph/full`, `GET /graph/entities`, `GET /graph/entities/{id}/neighbors`, and
  the `include_entities` overlay all return entity rows whose `memory_ids` arrays span every
  project and status in the corpus — confirmed: `get_full_graph`'s query above has no scope at
  all, and `get_entities`/`get_neighbors_by_id` (backing `/entities` and `/entities/{id}/
  neighbors`) are likewise unscoped by project or status, by the same "entities are not
  memory-scoped" design CLAUDE.md states. No memory *content* crosses through these routes —
  only entity identity and the fact that some memory somewhere (possibly foreign) asserts it.
  **This is the same fact I1 reports** (the isolation probe's Graph row: "0 / 0 / PASS (id-only
  exposure reported, not counted)" — `docs/planning/gate-ledger.md:389`).
  - **Decision (this revision, not deferred a second time):** entities and relations remain
    globally scoped, by design. CLAUDE.md is explicit that entities are not memory-scoped
    (uniqueness is `(name, entity_type)`, `memory_ids` spans every asserting memory), and the
    amendment log itself notes that trimming `memory_ids` would break the neighbour derivation
    that consumes it. Re-deriving a project-scoped entity graph would mean either splitting a
    shared entity per project (a schema change, out of this task's — and this tier's — reach)
    or filtering `memory_ids` per response (breaks neighbour derivation, per the log). Neither
    is this task's to do. **What this task does instead, satisfying the "at minimum surface it"
    bar:** the real Memory Graph page's entity-layer toggle gets an explicit, permanent caption
    — "Entities and their relationships are shared across every project; only memories
    themselves are project-scoped" — so a user turning on the entity overlay is told the true
    scope rather than left to assume the whole page is project-pure because the memory nodes
    are. This is a one-line UI addition, not a backend change, and it closes both F8's "surface
    it" bar and I1's parked question in the same motion (Step 4).
- **F10** — `_fetch_entity_overlay` under-returns silently, per §4.4's corrected mechanism.
  Unlike F8, this is **not** a design question — it directly bears on Done-when #2 ("Memory
  Graph reads the real graph with project scope applied in SQL"), because the entity-overlay
  path today applies **zero** SQL scope of any kind, not even a deterministic ordering, before
  truncating. **Decision: fix it, minimally, following the same idiom T1.29d/T1.35a already
  established for this exact class of gap — label the row (or here, the response) rather than
  attempt to narrow the underlying query.** Concretely (Step 3):
  - `PostgresGraphRepository.get_full_graph` gains one derived value: `truncated =
    len(entity_rows) >= limit` (a boundary check on the row count already fetched — no new
    query, no new round trip), returned alongside `entities`/`relations`.
  - `GraphService._fetch_entity_overlay` and `get_unified_graph` propagate it as
    `entities_truncated: bool` on the result dict. `/graph/unified` has **no declared
    `response_model`** (confirmed: `app/api/routes/graph.py`'s `get_unified_graph` route
    returns the service's raw dict directly), so this is additive with zero schema-file risk —
    `/graph/full`'s `FullGraphResponse` schema is untouched, and only `get_full_graph`'s
    internal return shape (not a public contract) changes.

## 5. Chat — the backend gap, and why it is one line, not fusion surgery

Read `ChatService._retrieve` (`backend/app/services/chat.py:211-270`) and `send_message`
(`:105-207`) side by side. Both build a per-memory dict via `**scope_labels(m)`
(`app/utils/scope_labels.py` — `{project, status}`, sourced from the same `memories` join
`PostgresVectorRepository.search` already performs), so **`project` and `status` already reach
both the live SSE `sources` event and the persisted `assistant_msg.context.memories`** — no
backend change needed for those two fields, matching the honesty labels' data requirement
directly (`status` is exactly what `LifecycleBadge` needs).

**The one real gap:** the live SSE event's dict (`_retrieve`'s `formatted_memories`, built at
`:254-264`) has no `id` key at all — only `index`. The *persisted* dict (`send_message`'s
`assistant_msg.context` construction, `:161-173`) does have `"id": str(m["memory_id"])`. So a
citation is clickable/labelable after a page reload but not during the live stream — a real,
narrow, mechanical inconsistency, not new retrieval logic.

**Fix (revised this pass — Minor finding on the missing-id default).** v1 proposed `"id":
str(m.get("memory_id", ""))`. The review is right that this is the wrong shape: `raw_memories`
comes from `PostgresVectorRepository.search()`, whose every row is a memory row keyed by its own
primary key — `memory_id` should be **structurally impossible** to be absent. A `.get(...,
"")` default converts "this should never happen" into a silently rendered, unclickable citation
with no error anywhere. Corrected fix: `"id": str(m["memory_id"])` — direct indexing, so a
missing `memory_id` raises immediately (surfacing in logs/tests as the real defect it would be)
rather than degrading into dead UI.

**Test.** `backend/tests/test_chat.py` already has a `TestChatService`-style class with a
`chat_service` fixture. Add a test that calls `ChatService._retrieve` (or drives it through
`send_message`'s SSE stream, matching whichever is more direct against the existing fixture
shape — decided at execution time) against a seeded memory and asserts the yielded `sources`
event's `memories[0]["id"]` equals the seeded memory's id as a string. **Mutation proof:** revert
the one-line addition, confirm the new test fails (`KeyError` or `None`), restore, confirm
green. **Second mutation proof (new this revision, for the fail-loud change itself):** construct
a `raw_memories` fixture row with `memory_id` deliberately absent from the dict and confirm
`_retrieve` raises `KeyError` rather than yielding a row with `id: ""` — proving the fail-loud
behaviour is real, not merely stated.

## 6. Chat — the honesty labels, concretely (revised: three render sites, not two)

### 6.1 What "layer, verification, and superseded/stale... on every cited row" means here

**Three** places currently render a citation, not two — v1 missed the third, and the review
found it by reading `chat-messages.tsx` rather than only `source-badges.tsx`:

1. The collapsible `SourceBadges` under every assistant message (both live-streaming and
   history-loaded).
2. (New, this task) a dedicated context panel matching doc 13 §4.1's "context panel that shows
   the retrieval context a turn used" module.
3. **(Missed by v1, added this revision) the inline citation chips substituted into the answer
   prose itself.** `chat-messages.tsx`'s `useMarkdownWithRefs`/`injectEntityBadges` replaces
   `[1]`, `[2]`, ... markdown references in the model's own answer text with a `MemoryBadge`
   component (`chat-messages.tsx:75-95`), rendering `mem.content` (truncated) with **no layer or
   lifecycle label at all** — confirmed by reading the component: its local `MemoryRef`
   interface (`index, id, content, source`) carries no `status`/`project`, and both call sites
   that build it (`AssistantMessage`, `StreamingMessage`, `chat-messages.tsx:319-327` and
   `:355-363`) map only those four fields, dropping whatever `scope_labels` already put on the
   underlying data. This is, verbatim, the failure invariant 14 and this task's own Done-when
   forbid: a citation rendered with no lifecycle signal at all, on the page this task exists to
   make honest. All three sites must carry the labels; Step 8 (was Step 6) now covers all three,
   not two.

Per §3's `MemoryRowData` mapping idiom (copied verbatim, not reinvented): every cited memory
row renders `layer: 0` (`LayerChip`) and `status` (`LifecycleBadge`, silent on `active`) always;
`VerificationBadge` renders only if `verification_status` is present, which it never is on the
real path today (no L2 vault yet in E1) — an honest absence, not a missing feature, matching
`RealMemoriesView`'s own documented choice verbatim.

**What "superseded/stale" actually ships as, stated plainly (Important finding, addressed this
revision).** Read `_retrieve` (`chat.py:223-227`): the scope it builds is `MemoryFilter(project=
context.get("project"), statuses=("active",), include_archived=False)` — chat's live retrieval
**never returns a superseded or archived row**. And the persisted snapshot (`send_message`,
`:161-173`) freezes `scope_labels(m)`'s output at write time, which — because it can only ever
have been written from a row that just passed the `statuses=("active",)` filter — can only ever
have been `"active"` at the moment of persistence. So under the data flow this task builds,
**`LifecycleBadge` rendering a non-trivial (superseded/deprecated) label on a chat citation is
not reachable through any normal path today.** This is not a reason to skip the badge — it is
still correct, still tested, and still the right vocabulary to reuse (§3) — but it should be
described honestly rather than as a feature with a live demonstration: **it is defensive
labelling that only becomes non-trivial if the SQL scope regresses** (the same failure mode
`_retrieve`'s own comment at `:219-222` warns about — "an archived, superseded or foreign-project
row that reaches this point has already reached the answer"). Step 8's test suite (§ below)
proves the badge *can* render a superseded label given a fixture that carries one — proving the
component wiring is live — while this section records that production traffic will not exercise
that branch under the current retrieval scope. See also the fossilisation finding immediately
below, which is the one path where a *superseded-after-the-fact* memory is genuinely reachable
in production, and where the current design still fails to show it.

**History citations fossilise (Important finding, recorded not fixed this revision).** The
persisted `assistant_msg.context.memories` dict is written once, at turn time, and never
revisited: `get_conversation`'s history read (`app/api/routes/chat.py`, backed by a plain
`SELECT * FROM messages ... ORDER BY created_at`) serves the stored JSON blob verbatim, with no
join back to `memories` for current status. So if a memory cited in turn N is later superseded,
every later view of turn N's citation still reads `status: "active"` — permanently, for the
life of that conversation. This is the production-reachable variant of v1's own §9-nominated
worst-case failure mode (a citation reading as confidently active when the underlying row no
longer is), and it is real, not hypothetical, once this task ships the labels this section
otherwise describes. **Decision: record it, do not fix it in this task.** A correct fix means a
live-status join at history-read time — new backend surface in `app/api/routes/chat.py` and its
response schema, neither in this task's stated lane, on a task that is already `Size: L` across
two independent surfaces. Step 9 files this as a Tier-1 amendment-log entry for a bounded
follow-up (re-deriving live status for cited memory ids when serving conversation history,
batched per conversation) rather than folding it in here under review pressure.
