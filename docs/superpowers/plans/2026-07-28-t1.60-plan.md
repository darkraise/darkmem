## 1. What this task is, and what it is not

This is two independent rebuild-to-real workstreams sharing one task because they are the two
remaining EXPLORE/WORK-group destinations doc 13 §3 names as still demo-backed after T1.58's
flip (T1.58's own record-and-route table, §5, lists both "Chat" and "Memory Graph explorer" as
"renders fake data presented as real, unconditionally... T1.60 (todo)"). It is:

- **A UI-binding task against an established pattern.** T1.44 (Memories) and T1.65
  (`projectStore`/query-key registry) already built every vocabulary component and every piece
  of scaffolding this task needs (`LayerChip`, `LifecycleBadge`, `VerificationBadge`,
  `ExclusionStrip`, `WhyRetrievedTrace`, the `DEMO ? demo : real` route-split idiom, the
  project-scoped query-key registry). This task consumes that vocabulary; it does not invent a
  second one.
- **A route consolidation for Memory Graph**, resolving a real, confirmed navigation bug found
  during this planning pass (§4): the sidebar nav already links to `/memory-graph`, but that
  route currently serves 100% demo data while the *actually real* implementation sits, unlinked,
  at the orphaned `/unified-graph` path.
- **A one-line, mechanical backend fix** (§5) — the live chat SSE `sources` event omits the
  memory `id` that the same data already carries once persisted, breaking citation links during
  a live stream specifically.

It is explicitly **not**:

- **Retrieval-fusion surgery.** Doc 13 §4.1 and doc 07's invariant 17 framing assert Chat "rides
  the same one ranking path as Memories." Reading the code shows this is not literally true
  today: `ChatService._search_memories` calls `PostgresVectorRepository.search` directly (a raw
  semantic-only ANN probe, no RRF, no keyword channel, no `MemoryResultTrace`), never
  `HybridSearchService.search_with_trace` — a third, independent retrieval implementation
  alongside `HybridSearchService` (used by `/memories/search`) and `MemoryService.reason`'s own
  bespoke type/tag-hint pass. Rewiring `ChatService` onto `HybridSearchService` would touch the
  shared ranking-path invariant directly — exactly the "retrieval fusion" category this tier is
  told to escalate on, not build silently under a Sonnet plan. **This plan does not do that.**
  §6 details the finding and what it does instead: satisfy the literal Done-when (layer,
  verification, superseded/stale labels on every cited row) using data the existing chat
  retrieval already emits, and flag the doc/code mismatch as a Tier-2 amendment proposal for the
  controller rather than quietly rewiring a shared invariant path or silently rendering
  confident-looking trace UI the backend cannot back.
- **A community-detection or graph-layout rebuild.** `MemoryGraphExplorer`'s force/tree/circles
  layouts and topic-halo rendering are demo-fixture-only (`src/demo/explore.ts`'s
  `layoutGraph`/`scopeMemoryGraph` assume synthetic data shapes). Re-deriving that exact UI
  against live louvain-clustered data would be new algorithmic work well past this task's
  Done-when, which asks only that Memory Graph "reads the real graph with project scope applied
  in SQL." §4 explains the choice: keep the *already-real* `UnifiedGraphPage` implementation as
  the real branch, and keep `MemoryGraphExplorer` as the demo branch, exactly matching the
  `DEMO ? demo : real` idiom used everywhere else in the codebase, rather than rebuilding either
  side to match the other's UI.
- **A fix for the second deferred query-key gap (`tags`).** T1.65 recorded `GET /tags` has no
  project filter on the backend at all. Neither Chat nor Memory Graph calls `useTags` anywhere
  (confirmed by grep — the only caller is `use-memory-api.ts`), so it stays `deferred`,
  unchanged, in `query-keys.ts`. This is a real gap but not this task's; recorded so the
  disposition reads as a decision, not an oversight.

## 4. Memory Graph — the route-consolidation finding and the decision

### 4.1 What exists, read from the code

| Route | Component | Data source | State |
|---|---|---|---|
| `/memory-graph` (`routes/_authenticated/memory-graph.tsx`) | `MemoryGraphExplorer` (`features/memory-graph/components/memory-graph-explorer.tsx`) | `useDemoMemoryGraph()` (`@/demo/hooks`) | **100% demo, no `DEMO` gate at all** — always fake, regardless of mode |
| `/unified-graph` (`routes/_authenticated/unified-graph.tsx`) | `UnifiedGraphPage` (inline in the route file) | `useUnifiedGraph()` (`hooks/api/use-graph-api.ts`) → `GET /graph/unified` | **Real, already backend-wired**, no `DEMO` gate either (always real) |

**Confirmed live navigation bug, not a hypothesis:** `routes/_authenticated.tsx:51`'s sidebar
nav entry is `{ label: "Memory Graph", href: "/memory-graph", icon: Waypoints }` — it already
points at the demo-only route. Nothing in the app links to `/unified-graph` (`grep -rn
"unified-graph" src/` outside the route file and the generated route tree returns nothing) — the
real implementation is unreachable from the product's own navigation.

### 4.2 Doc 13's authority on this

Doc 13 §3's route table (line 143): `` `/unified-graph` → `/memory-graph` | Memory entity graph
| exists today ``. Read together with §3's target nav map (one `MGRAPH["Memory Graph (exists
today)"]` destination under the EXPLORE group) and the confirmed nav-entry bug above, this reads
as: the capability exists today (real, at `/unified-graph`), and the route itself is meant to
live at `/memory-graph` going forward — exactly what the nav already assumes and the URL does
not yet deliver.

Doc 13 §4's module description for Memory Graph ("force/tree/community layouts, search,
navigator") matches `MemoryGraphExplorer`'s bespoke SVG UI far more closely than
`UnifiedGraphPage`'s 2D/3D-physics-graph UI. This plan does **not** attempt to reconcile that —
see §1's explicit exclusion. `UnifiedGraphPage` already has an analogous vocabulary (2D/3D view
modes as its own "layouts," the filter panel and cluster names as its own navigator-equivalent,
real louvain-clustered `cluster_names` as its own community detection, already surfaced via
`get_unified_graph`'s `include_entities`/`similarity_threshold`/`min_cluster_size` params), and
critically it is **already real, already backend-tested indirectly through the graph service,
and already has richer functionality** (mini-graph navigation, entity-relation detail panel,
`ChatOverlay` integration). Rebuilding `MemoryGraphExplorer`'s demo-fixture-only layout/community
math against live data would be new algorithmic scope this task's Done-when does not ask for.
Recorded as a documented, Tier-1 gap between the doc's literal module list and the shipped UI —
not silently absorbed, not silently ignored.

### 4.3 The decision

Keep both implementations, correctly gated, at one route:

- `routes/_authenticated/memory-graph.tsx` becomes `DEMO ? <MemoryGraphExplorer /> :
  <RealMemoryGraphPage />`, mirroring the `DEMO ? <DemoMemoriesPage /> : <RealMemoriesView />`
  idiom exactly. `RealMemoryGraphPage` is `UnifiedGraphPage`'s current implementation, relocated
  into this file (or into a new `features/memory-graph/components/real-memory-graph-page.tsx` if
  the file grows unwieldy — decided at execution time by size, not by this plan) with its
  `PageChrome` title/description updated from "Unified Graph" to "Memory Graph" (matching the
  demo branch's own copy, so switching `DEMO` does not change the page's own self-description).
- `routes/_authenticated/unified-graph.tsx` becomes a redirect: `beforeLoad: () =>
  redirect({ to: "/memory-graph" })` — preserves any external bookmark/link to the old path
  rather than 404ing it, at negligible cost.
- No file under `src/demo/**` changes. `MemoryGraphExplorer` and `useDemoMemoryGraph` are
  untouched.

### 4.4 Project scope — the deferred gap this task closes

T1.65's `query-keys.ts` registry (verified by direct read, `unifiedGraph` entry) already records
the exact gap: `GET /graph/unified` accepts `?project=` since T1.29d (confirmed live —
`backend/app/api/routes/graph.py`'s `get_unified_graph` has always taken a `project: str | None
= Query(None)` param and passed it through to `GraphService.get_unified_graph`, which applies it
via `self._memory_scope(MemoryFilter(project=project) ...)` fed into
`vector_repo.get_louvain_clustered_vectors` — **a real SQL `WHERE` scope, not a client-side
filter**, confirmed by reading `app/services/graph.py:38-89`) — but `useUnifiedGraph` never
sends it. This is purely a frontend gap; **no backend change is needed** to satisfy Done-when
#2's "applied in SQL" — the SQL pushdown already exists and only needs a caller.

- `hooks/api/use-graph-api.ts`'s `useUnifiedGraph` reads `useProjectStore((s) =>
  s.activeProject)` internally (same idiom T1.65's own `useMemories` retrofit used — the hook
  itself scopes, not each call site opting in) and appends `&project=${encodeURIComponent(
  project)}` to the URL. Its query key is rebuilt via `useProjectScopedKey("unifiedGraph",
  similarityThreshold, minClusterSize, includeEntities)`.
- `query-keys.ts`'s `unifiedGraph` entry moves from `{ kind: "deferred", reason: "..." }` to
  `{ kind: "auto" }`. The entity-overlay path (`include_entities=true`) is confirmed already
  scoped-by-construction: `_fetch_entity_overlay(memory_nodes)` derives entities from the
  already-project-scoped `memory_nodes` list, so it inherits the scope rather than needing its
  own filter (read at `app/services/graph.py:98-103`) — noted so this isn't mistaken for an
  unaddressed second gap.
- `tags` stays `deferred`, unchanged (§1).

## 5. Chat — the backend gap, and why it is one line, not fusion surgery

Read `ChatService._retrieve` (`backend/app/services/chat.py:211-270`) and `send_message`
(`:105-207`) side by side. Both build a per-memory dict via `**scope_labels(m)`
(`app/utils/scope_labels.py` — `{project, status}`, sourced from the same `memories` join
`PostgresVectorRepository.search` already performs), so **`project` and `status` already reach
both the live SSE `sources` event and the persisted `assistant_msg.context.memories`** — no
backend change needed for those two fields, matching the honesty labels' data requirement
directly (`status` is exactly what `LifecycleBadge` needs).

**The one real gap:** the live SSE event's dict (`_retrieve`'s `formatted_memories`, built at
`:254-264`) has no `id` key at all — only `index`. The *persisted* dict (`send_message`'s
`assistant_msg.context` construction, `:161-173`) does have `"id": str(m["memory_id"])`. So a
citation is clickable/labelable after a page reload but not during the live stream — a real,
narrow, mechanical inconsistency, not new retrieval logic.

**Fix:** add `"id": str(m.get("memory_id", ""))` to `formatted_memories`'s dict comprehension in
`_retrieve`. One line. No change to `_search_memories`, `_lookup_entities`, `MemoryFilter`
construction, or the LLM prompt-building path — the retrieval channel itself is untouched.

**Test.** `backend/tests/test_chat.py` already has a `TestChatService`-style class with a
`chat_service` fixture. Add a test that calls `ChatService._retrieve` (or drives it through
`send_message`'s SSE stream, matching whichever is more direct against the existing fixture
shape — decided at execution time) against a seeded memory and asserts the yielded `sources`
event's `memories[0]["id"]` equals the seeded memory's id as a string. **Mutation proof:** revert
the one-line addition, confirm the new test fails (`KeyError` or `None`), restore, confirm green.

## 6. Chat — the honesty labels, concretely

### 6.1 What "layer, verification, and superseded/stale... on every cited row" means here

Two places currently render a citation: the collapsible `SourceBadges` under every assistant
message (both live-streaming and history-loaded — the literal "every cited row" surface), and
(new, this task) a dedicated context panel matching doc 13 §4.1's "context panel that shows the
retrieval context a turn used" module. Both must carry the labels; building only one would leave
the other as an unlabelled citation — precisely the failure invariant 14 forbids.

Per §3's `MemoryRowData` mapping idiom (copied verbatim, not reinvented): every cited memory
row renders `layer: 0` (`LayerChip`) and `status` (`LifecycleBadge`, silent on `active`) always;
`VerificationBadge` renders only if `verification_status` is present, which it never is on the
real path today (no L2 vault yet in E1) — an honest absence, not a missing feature, matching
`RealMemoriesView`'s own documented choice verbatim.

### 6.2 Type plumbing (frontend-only, backend already emits the data — §5)

- `features/chat/hooks/use-chat-stream.ts`'s `ChatSources` interface gains `id?: string`,
  `project?: string`, `status?: MemoryStatus` on the `memories` array element (importing
  `MemoryStatus` from `@/hooks/api`).
- `hooks/api/use-chat-api.ts`'s `ChatMessage.context.memories` element gains `project?: string`,
  `status?: MemoryStatus` (already has `id`; `send_message`'s persisted dict already emits both
  via `scope_labels` — this is a type-completeness fix, not a wire change).

### 6.3 `SourceBadges` gains the label cluster

`features/chat/components/source-badges.tsx`'s per-memory row (currently: content, source icon,
match %, date, tags) gains a `LayerChip layer={0}` + `LifecycleBadge status={m.status}` pair
in the same position `MemoryRow` puts them (leading, before the content line), reusing the
existing `MemoryRef`-shaped prop rather than inventing a parallel type.

### 6.4 New `ChatContextPanel` — the real counterpart to `DemoContextPanel`

`features/chat/components/chat-context-panel.tsx` (new). Visually mirrors
`DemoContextPanel`'s contract (populated/empty/degraded header, per-row card) but is built over
real data: the live-streaming `stream.sources` while a turn is in flight, else the selected
historical `msg.context`, else "no context yet." Per row: `LayerChip` + `LifecycleBadge` (no
`VerificationBadge`, no `WhyRetrievedTrace` — §1's exclusion), plus an explicit honest caption
("L0 memories — no verification ladder applies yet") so the *absence* of a verification badge
reads as a stated fact about scope, not an omission. `degraded` stays `null` always for now
(chat's retrieval currently has no channel-failure signal to surface — recorded as a follow-on
gap, not fabricated).

### 6.5 The declined enhancement: project-scoping chat's retrieval

Considered and **declined for this task**. `ChatService._retrieve` already reads
`context.get("project")` for scoping (`:224`), so wiring `RealChatPage`'s `handleSend` to pass
`useProjectStore().activeProject` as `context.project` would be a small addition. Declined here
because: (a) doc 13 §3's explicit list of views the project switcher scopes ("Memories, the
vault, Review, the timeline, the calendar, and the dashboard") does not name Chat; (b) Chat's
`context` dict is a different concept from `contextStore`'s `applies_when` session declaration —
the two `"context"` names arriving at nearly the same seam is exactly the kind of conflation
T1.65's Ruling 3 warns against, and this task's own Done-when does not require it. Recorded as a
Tier-2 amendment-log candidate for the controller, not silently done or silently ignored.

## 9. Falsification pass

**Step most likely to be wrong: Step 1's route consolidation.** The decision to keep
`UnifiedGraphPage`'s implementation (rather than rebuilding `MemoryGraphExplorer`'s UI against
live data) is a judgement call about which of two doc-13 signals wins — "exists today as
`/unified-graph`" (favours keeping `UnifiedGraphPage`) versus the §4 module list's literal
"force/tree/community... navigator" wording (favours `MemoryGraphExplorer`'s shape). This plan
resolved it toward the lower-risk, already-real, already-richer implementation and treated the
module-list mismatch as a recorded gap rather than a blocker (§4.2). **Evidence that would flip
this call:** if a reviewer determines doc 13 §4's module list is binding on the shipped UI (not
just descriptive), or if product intent specifically wants the topic-halo/community-navigator
visual language live, the correct fix is not this plan's Step 1 but a new, larger task to port
`MemoryGraphExplorer`'s layout/community logic onto `get_unified_graph`'s real louvain output —
which is a materially bigger, more algorithmic piece of work than anything in this plan and
should be sized and planned separately rather than folded in here under time pressure.

**Second-most-likely candidate:** Step 6's decision to render `ChatContextPanel` with `degraded:
null` always (no channel-failure signal). `ChatService._retrieve` swallows both
`_search_memories` and `_lookup_entities` failures into empty lists with a `logger.warning`
(`chat.py:229-244`) rather than surfacing a flag the frontend could render as "degraded" — so
today a failed retrieval channel during a chat turn looks identical to "nothing relevant found,"
which is arguably its own smaller honesty gap this plan does not close (recorded as a candidate
follow-on, not fixed, since adding a failure-signal to `_retrieve`'s return shape edges toward
the same retrieval-path territory §1 declines to enter).

**The silent failure mode this plan considers most dangerous:** a citation that renders with a
confident-looking label set (`LayerChip` + no lifecycle badge, reading as "current, verified
active memory") when the underlying row was actually superseded but the `status` field failed to
propagate through some code path this plan's grep-based inventory missed — i.e., `LifecycleBadge`
silently rendering nothing not because the memory is genuinely active, but because `status` came
back `undefined` from an untyped or dropped field somewhere in the SSE/persisted-context chain.
This is exactly why Step 6's mutation proof removes the badge line and re-asserts on a
`superseded` fixture specifically, rather than only testing the happy "active, no badge" path —
a test that only ever exercises `active` rows would pass identically whether the wiring is
correct or entirely absent, which is the "guard that cannot fail" trap the brief's Ruling 7 names.

## 10. Size call

**L stands.** Two structurally independent surfaces (Memory Graph's route consolidation +
project-scope wiring, and Chat's full real-page build-out + honesty-label wiring + a backend
fix), seven steps, touching two route files, four-plus new/rewritten components, a backend
service method, and the shared query-key registry. Neither half alone would be more than `M`
(Memory Graph is genuinely close to `M` on its own — Steps 1–2 total one `M` and one `S`), but
Chat's four steps (3–6) are collectively larger than Memory Graph's two, and the honesty-label
requirement (§6, §9) is exactly the kind of cross-surface consistency work (two render sites,
live-vs-persisted parity, an explicit absence-is-honest test) that inflates a `rebuild` task past
`M` even without touching a cross-cutting backend invariant. No split is recommended: both
halves are independently small enough to execute in one sitting each, and splitting them into
two tasks would not reduce total risk, only add a second task-boundary and a second round of
floor/gate bookkeeping for two pieces of work that already share nothing but a task id.
