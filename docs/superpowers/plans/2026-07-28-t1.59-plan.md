**v1's central REST-gap ruling was factually wrong (Finding 1, Blocking) — re-verified
directly against the code, not taken on the reviewer's word.**

v1 claimed `get_code_graph` "returns only `{nodes, edges}`; nothing computes or serves
community membership or traced processes over REST," and that this bounded Step 3 to omit
community colouring and the Processes panel. Reading `backend/app/services/code_query.py`'s
`get_code_graph` (lines 217–296) and the two writers that populate what it reads shows this is
wrong:

- `CommunityDetector.detect()` (`backend/app/services/community_detector.py`) writes one
  `code_graph_nodes` row per Leiden community — `kind='community'`, `key=compose_key(...)`,
  `properties={community_id, size}` (lines 175–189) — and one `code_edges` row per member,
  `edge_type='member_of'`, `source_kind='symbol'`, `target_kind='community'` (lines 197–207).
- `ProcessTracer.trace()` (`backend/app/services/process_tracer.py`) writes one
  `code_graph_nodes` row per traced process — `kind='process'`, `properties={entry_kind,
  entry_file}` (lines 227–236) — one `entry_point_of` edge per entry point (lines 238–245),
  and one `step_in_process` edge per step **with `properties={step: N}`, N assigned in
  traversal order** (lines 247–264).
- `get_code_graph`'s own SQL is unfiltered by kind on both tables:
  `SELECT key, kind, label, properties, ... FROM code_graph_nodes WHERE repo_id = :repo_id`
  (line 253) and `SELECT source_key, target_key, edge_type, properties FROM code_edges WHERE
  repo_id = :repo_id ORDER BY edge_type, (properties->>'step')::int NULLS LAST, source_key,
  target_key` (lines 281–286) — **the `ORDER BY` even sorts `step_in_process` edges by their
  step number already**, ready to consume in order with no client-side re-sort needed.
  `community` and `process` nodes, and `member_of`/`entry_point_of`/`step_in_process` edges,
  are in the response today, generically shaped as `{id, label, kind, properties?}` /
  `{source, target, type, properties?}` — nothing filters them out.

**What is actually true: the REST route serves the raw substrate for both features; what is
missing is client-side derivation from the generic node/edge shape into the demo's typed
`DemoCodeCommunity`/`DemoCodeProcess` shape — not a backend gap.** Concretely, the shapes line
up almost exactly:

- `DemoCodeCommunity {id, label, chart}` (`frontend/src/demo/types.ts:426-431`) ← a
  `kind='community'` node's `{id: key, label}` plus a client-assigned `chart` index (1–5, cycled
  by encounter order — the real backend has no equivalent field, this one value is a rendering
  choice, not fabricated data, exactly as the demo's own `chart` field already is: a colour-ramp
  index, not a claim about the data).
- `DemoCodeProcess {id, label, steps: string[]}` (ordered node ids) ← a `kind='process'`
  node's `{id: key, label}` plus the `step_in_process` edges targeting that process key, whose
  `source_key`s are already SQL-ordered by `properties->>'step'`.
- `mermaidForProcess(process, graph)` (`frontend/src/demo/explore.ts:312-327`) takes exactly a
  `DemoCodeProcess` (ordered `steps`) and a `graph` (for node-name lookup) — **it is directly
  reusable once real data is shaped into this form, no rewrite needed.**

So doc 13 §4.2's "community colouring" and "the Processes panel with Mermaid export" **do not
need cutting**. v1's Step 3 would have shipped an honest-copy notice ("not available without a
REST endpoint for communities/processes — tracked against T1.42d") that would have been false
the entire time community and process nodes sat, unused, inside the same response the honest
notice was reacting to. §3-new and the revised Step 3 replace that disposition entirely.

**What T1.42d's still-open Tier-3 escalation actually is, and why it does not block this.**
T1.42d (done, `progress.md` line 141) escalated that `code_communities` and `code_processes` —
**the two MCP tools**, which return purpose-built, pre-shaped community/process payloads with
richer structure than a flat node/edge dump — have no REST twin. That escalation is still open
and this plan does not close it; it is a real, narrower gap (a dedicated, richer
`GET /code/graph/{repo_id}/communities`-shaped endpoint would still be a nice-to-have, and
would let the frontend drop this task's derivation code). But it does **not** mean "no
community/process data reaches the frontend over REST" — it reaches it today, generically,
through the one graph endpoint every other Code Graph feature already binds to. Conflating "no
REST twin for the MCP tool" with "no REST-servable data at all" was v1's error. Step 7 logs the
correction in the amendment log so the next reader of T1.42d's escalation sees the distinction,
not a second, contradictory finding.

## 3. The REST-capability disposition for Code Graph — **rewritten in full (Finding 1)**

Doc 13 §4.2 names "the Processes panel with Mermaid export" and "community colouring" as
features to preserve. §1.3 above established, against the code, that both are servable today
from the one existing `GET /code/graph/{repo_id}` response — the substrate is there, generically
shaped; what is missing is a client-side derivation step, not a backend endpoint.

**This plan now requires Step 3 to build that derivation, not omit the two features.**
Concretely:

- A new pure function, `deriveCommunities(nodes, edges) → DemoCodeCommunity[]`-shaped list:
  filter nodes to `kind === "community"`, look up each one's members via edges where
  `type === "member_of"` and `target === community.id`, assign a stable `chart` index (1–5,
  cycling by first-encounter order — a rendering choice, not a data claim, no more fabricated
  than the demo's own `chart` field already is).
- A new pure function, `deriveProcesses(nodes, edges) → DemoCodeProcess[]`-shaped list: filter
  nodes to `kind === "process"`, collect edges where `type === "step_in_process"` and
  `target === process.id`, **already delivered in step order by the backend's own `ORDER BY`**
  (§1.3) — no client-side sort required, just a map from edge to `source` (the step's node id).
- `mermaidForProcess` is reused as-is (imported from `@/demo/explore`, or promoted alongside
  the other pure math per the shared-type decision below) — it already takes exactly this
  shape.
- Community colouring in `code-canvas.tsx`/`code-graph-tab.tsx` binds to the derived list the
  same way it binds to the demo's `graph.communities` today; per-node `n.community` in the real
  case comes from walking the derived communities' membership rather than a field the node
  itself carries (the real node has no `community` property — only the `member_of` edge
  establishes it), which the two derivation functions above already resolve.

**This restores Done-when box 2 ("Code Graph reads the real graph") to its full doc-13 scope —
no narrowing.** Community colouring and the Processes panel with Mermaid export ship in real
mode. Step 7 logs a **corrective** Tier-2 amendment (not the "narrows the feature" one v1
would have logged): the T1.42d Tier-3 escalation remains open but is understood as an MCP-tool
REST-twin gap for `code_communities`/`code_processes` specifically (richer, purpose-built
payloads), separate from and non-blocking for the frontend's own derivation off the existing
flat graph endpoint. A future task *could* add typed REST endpoints to retire this task's
derivation functions, but nothing here requires it, and this plan does not propose one
unilaterally.

**What genuinely still has no REST path, and is correctly left honestly unbound:** nothing new
surfaces here beyond what Step 3 already flagged for other reasons (see the revised Step 3,
below, on `code-inspector.tsx`'s `buildFileSource`).

- **The shared-type-vs-separate-component decision — v2 correction to v1's recommendation
  (Finding 4).** v1 recommended promoting `code-explorer.tsx`/`code-inspector.tsx`/
  `code-filters.tsx`/`file-tree.ts` to a shared, demo-independent type (option 1) because it

  It synthesizes fictional file contents — declaration lines and call-derived "body statements"
  — from graph structure, not from any stored source. Retyping this file to accept a
  demo-independent graph shape would still leave it calling a function that **fabricates
  source code text under a real file's path** the moment it is pointed at real data — an
  honesty violation of exactly the kind doc 13 §4.2's read-only/no-fabrication posture and this
  repo's general no-silent-drop discipline exist to prevent, and worse than the "empty panel"
  failure mode v1 was already worried about in §3, because here the panel would render
  something, just something false.

  **v2 disposition: `code-inspector.tsx` is removed from the promotion-candidate list
  entirely.** The real Code Graph's inspector panel must **not** reuse `buildFileSource` in any
  form (ported, retyped, or wrapped). Bind it instead to `useCodeSymbolDetail`'s real
  `source_code` field (`code_query.py` lines 143/175/195 — `CodeSymbol.source_code`, a genuine
  stored column) for the *selected symbol*, not a synthesized whole-file view. This is
  honestly a narrower capability than the demo's per-file pseudo-source view (one symbol's real
  snippet vs. an invented whole file with invented inter-symbol prose) — the real inspector
  panel says so if the executing lane judges it needs saying, matching this plan's own
  no-silent-narrowing discipline (§3's community/process principle, applied here to source
  display instead).

  **v2 disposition on `code-explorer.tsx`/`code-filters.tsx`/`file-tree.ts`: promotion (option
  1) still stands, with one required widening (also Finding 4).** These three import only

  what the real graph actually emits.** `community_detector.py`'s own symbol-eligibility filter

**Size:** S. **Files:** new `frontend/tests/code-real-mode.spec.ts`. **Depends:** Steps 2, 3,

**Why this step exists.** `npm run test:e2e -- code` matches exactly two specs today
(`code-index-debt.spec.ts`, `code-wiki-empty.spec.ts`), and both are correctly in

3 — and its own capstone Verify would still never execute one line of the real bindings it was

**How the new spec authenticates.** `auth.spec.ts` is the only current spec that logs into the

(`/api/v1/auth/me`, `/api/v1/setup/status`) via `page.route` — any other real REST call (every
one this task's components make) would still hit the real backend without a real JWT cookie
and 401. `seedAuth()` cannot make a real-mode data-bound test pass; it exists for a different
kind of test (pure client-side rendering with every backend call intercepted), which is not
what this step needs.

```ts
test.describe("code section — real mode", () => {
  test.beforeAll(() => {
    if (!process.env.E2E_ADMIN_PASSWORD) {
      throw new Error("E2E_ADMIN_PASSWORD must be set — this spec never soft-skips for a missing credential.")
    }
    seedAdminPassword()
  })
  // each test: page.goto("/login"), fill password, sign in — mirrors auth.spec.ts exactly
})
```

**Do not reuse the `isVisible({ timeout }).catch(() => false))` soft-skip idiom (explicit
instruction, and independently the right call here).** That idiom exists in the other specs
because, pre-login, elements are genuinely never reachable and the spec has no way to become
authenticated — soft-skipping is the least-bad option available to them. This spec is
different: it logs in for real, so every assertion after a successful login is against an
element that either is or is not correctly rendered — a real assertion failure is the correct
signal, not a skip. Use plain `await expect(locator).toBeVisible()` (Playwright's own
auto-wait/retry already handles timing) everywhere in this spec. Reusing the deprecated idiom
here would hand T1.64 — which exists specifically to retire this pattern — a freshly-written
instance of the exact defect it is chartered to remove.

login:

- `/code/repositories` renders `RealRepositoriesView`, not `RepositoriesTab` — assert the
  presence of a real-mode-only affordance (e.g., the "Add repository" action Step 2 adds) and
  the absence of any demo-fixture repo name (the demo fixture's repo names are enumerable from
  `src/demo/data.ts` or equivalent — assert none of them appear in the real page).
- `/code/graph` renders `RealCodeGraphView`, not `CodeGraphTab` — same demo-name-absence
  assertion, plus assert the honest empty state (e.g. "no repositories indexed yet" / "select a
  repo") renders correctly against a dev stack with no repos configured for this project.
- `/code/wiki` renders `RealWikiView`, not `WikiTab` — same pattern, plus a network-level
  extension of Step 4's mutation guard: attach `page.on("request", req => { if
  (req.url().includes("/code/wiki") && req.method() !== "GET") throw new Error(...) })` for the
  duration of the test, proving the read-only invariant end-to-end against the real backend,
  not just against a mocked `apiFetch`.

  **Deliberately out of scope for this spec, stated rather than silently assumed:** rendering
  of actual indexed graph nodes/edges, actual wiki module content, and actual community/process
  data against a real, fully-indexed repository. Provisioning a real indexed repo inside a
  Playwright run means cloning a repo and running the full `code_pipeline.py` sequence (14

  indexed real repo (e.g., seeding one small fixture repo once per CI run, cached), that is

**Verify.** `npm run test:e2e -- code` (now matches three specs: the two existing demo-fixture

## 5. Falsification pass (revised — the Step 3 risk changed shape, and Finding 2's risk is
now the standing one)

**Step most likely to be wrong (revised): Step 3's `graph-derive.ts` grouping logic, not the
shared-type-vs-separate-component split v1 worried about.** v1's split concern (whether
promoting `code-explorer.tsx`/`code-filters.tsx`/`file-tree.ts` stays purely additive against
`code-tabs.test.tsx`'s existing demo-mode assertions) still applies and the fallback is
unchanged (a separate real component, if the retype is not purely additive). But this
revision's new work — `deriveCommunities`/`deriveProcesses` — is untested code this plan is
asking the executing lane to write from a read of the writer services, not from having run
them against real data. The evidence that would show it wrong: running Step 3's
`graph-derive.test.ts` fixtures against edge cases the writer code implies but this plan's
author did not exhaustively enumerate — e.g., a symbol that is a member of zero communities
(possible: `CommunityDetector` only stores communities with `len(members) >= 2`, so a symbol in
a singleton community has no `member_of` edge at all and must render as community-less, not
crash), or a process whose `step_in_process` edges include a step pointing at a symbol that is
itself a member of a different community (both are legitimately independent, the derivation
functions must not assume disjointness). If `graph-derive.test.ts`'s fixtures do not include
these cases, that is this plan's own author under-covering the step it flagged as riskiest —
the executing lane should treat "did I write a fixture for a zero-membership node and a
cross-referenced process step" as the concrete falsification check, not just "does the happy
path derive correctly."

**Second-most-likely candidate (elevated from a "second" to a standing risk by Finding 2):**
Step 5's real-mode spec silently degrading back toward the exact failure Finding 2 found, if a
future edit to `playwright.config.ts` accidentally adds `code-real-mode.spec.ts` to
`DEMO_FIXTURE_SPECS` (an easy one-line mistake — the array is a flat list of filenames with no
structural signal distinguishing "needs real auth" from "needs demo fixtures") or if the spec
itself regresses back to the `isVisible`/soft-skip idiom under future maintenance pressure. Both
would silently restore the green-but-empty state this whole revision exists to close, with no
test failure marking the regression — the Verify command would still pass, just meaninglessly,
exactly as it does today. There is no automated guard against this in the current plan; the
executing lane should consider whether a comment at the top of `code-real-mode.spec.ts`
explaining *why* it must never move into `DEMO_FIXTURE_SPECS` (mirroring the explanatory
comments already in `auth.spec.ts` and `playwright.config.ts` itself) is sufficient, or whether
a lint/CI check asserting real-mode specs and their assertions never regress to the soft-skip
idiom is worth a follow-up task. This plan does not require the latter, but names it as an open
question for the controller.

**Third candidate, unchanged from v1:** the auto-provision "when" timestamp proxy in Step 2
(`created_at` standing in for a field the real backend does not carry) — stated as an open call
in Step 2, unaffected by this revision.

**The silent failure mode this plan considers most dangerous, unchanged from v1:** the Wiki's
read-only invariant being violated with no visible symptom unless Step 4's mutation-proven guard
exists and stays proven. Step 5 now adds an independent, network-level check of the same
invariant against the real backend, which raises the bar for this failure mode to survive
undetected (two independent guards, one mocked/unit, one e2e/real, would both need to be
removed or defeated simultaneously) — but does not eliminate it as a risk category, only makes
it more expensive to reintroduce silently.
