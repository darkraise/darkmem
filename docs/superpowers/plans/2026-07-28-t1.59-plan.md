## 2. The ruling on `/repos` (T1.46's deferred question, closed here)

**Delete the route — after porting its real, working logic, not instead of it.**

Reasoning, both halves:

1. **Per T1.46's own framing, unreachable means delete.** §1.4's evidence is exhaustive
   (router registration, nav config, every `Link`/`navigate` call site, the one Playwright
   spec) and unambiguous: nothing in the running application ever sends a user to `/repos`.
   Leaving an orphaned route alive is exactly the "renders fake data presented as real" shape
   T1.58's own record-and-route table (§5 of that plan) exists to name for *other* surfaces —
   here it is worse, because this orphan is not fake, it is a **second, silently-more-capable
   implementation** of a surface the in-nav route also claims to own, which is a
   maintenance/consistency hazard independent of demo-vs-real (two Reindex dialogs, two repo
   lists, two Wiki views, drifting against each other under nobody's ownership).
2. **Deleting it blind would be a regression, not a cleanup.** §1.4's capability table shows
   the legacy page's create/edit/delete/reindex/task-list/Wiki wiring is real, tested-shape
   (it already drives the exact backend contracts doc 13 §4.2 asks for), and in the Wiki
   case, is the **only** existing implementation of the read-only invariant this task's own
   ruling repeats. Deleting the file without carrying that logic into the in-nav Code section
   would mean T1.59 ships *less* real functionality than exists in the tree today, which is
   the opposite of "bind to live data."

So the disposition is sequenced: **salvage first (Steps 1–4), delete after (Step 5)** — never
the reverse. This is a Tier-1 amendment to log in Step 6 (closes T1.46's deferred question;
task-local, no other epic file affected).

## 3. The REST-gap disposition for Code Graph (bounds Step 3)

Doc 13 §4.2's Code Graph decision names "the Processes panel with Mermaid export" and
"community colouring" as features to preserve from "the code-graph revamp." Both read fields
(`graph.processes`, `graph.communities`, per-node `community`) that only exist in the demo
data shape; `GET /code/graph/{repo_id}` does not compute or serve either, and the two MCP
tools that do (`code_processes`, `code_communities`) have no REST twin — an already-escalated,
still-open Tier-3 finding from T1.42d.

**This plan does not build a REST route to close that gap** — that is new backend surface
area outside this task's Depends chain and outside a Sonnet-tier lane's authority to decide
unilaterally on a still-open Tier-3 item (runbook §5: "the corpus doc wins until a human
decides otherwise"). **The real Code Graph view built in Step 3 binds every REST-backed
feature (nodes, edges, layout switcher, camera controls, symbol browser, command-palette
search, blast-radius risk buckets) and honestly omits the two that are not** — no fabricated
community assignment, no fabricated process list, no panel rendered empty-and-unlabelled as
if it were simply "no data yet" (that would misrepresent a structural gap as a data gap,
which is exactly invariant 23's scaffolding-not-substrate failure). The panel/toggle for
"colour by community" and the Processes sidebar section are either hidden entirely in real
mode or replaced with an honest one-line note ("not available without a REST endpoint for
communities/processes — tracked against T1.42d"); Step 3 leaves the exact copy/hide choice to
the executing lane, since it is a doc-14 visual-language call this doc does not own, but
requires *some* honest state, never silence.

**This narrows Done-when box 2** ("Code Graph reads the real graph") to: nodes, edges, and
every REST-backed derivative of them. Step 6 logs this as a Tier-2 amendment (the change
reaches beyond this task — it is the concrete instance of T1.42d's still-open finding, and
the next reader of that finding should see it has already cost a real feature cut, not just a
documentation gap).

### Step 2 — Repositories: extend `RealRepositoriesView` to the full doc-13 §4.2 surface

**Size:** M. **Files:** `frontend/src/features/code/components/real-repositories-view.tsx`,
new `frontend/src/features/code/components/real-reindex-dialog.tsx`, new

executing lane's call), `frontend/src/features/code/__tests__/real-repositories-view.test.tsx`.
**Depends:** Step 1 (schemas).

- **Live phase label.** When `repo.status === "indexing"`, render `repo.status_message` as
  the current-phase line. This is already live data with no new plumbing: `code_pipeline.py`
  broadcasts `repo.indexing_progress` on every one of ~13 named phases ("Parsing files...",
  "Building structure graph...", … "Generating wiki..."), and `lib/websocket.ts` already maps
  that event (and every other `repo.*` event) to `invalidateQueries({queryKey: ["repos"]})`

  `PhaseTicker`**, and that reduction is a fact about the backend, not a shortcut: the demo
  renders a full 14-entry list with `done`/`current`/`pending`/`skipped` states known in
  advance, because demo data invents the whole plan; the real backend only ever broadcasts the
  *current* tick's label, with no forward-looking phase list to render as "pending." Do not

  "indexing — <label>" rather than implying a multi-step progress bar the data does not
  support.
- **Reindex.** `real-reindex-dialog.tsx`, typed against the real `Repo`/`ReindexInput`

  already committed to `ListSurface`/`RepoRow` cards, per T1.46; match that idiom, do not
  reintroduce a table).
- **Auto-provision registration state.** `app/services/repo_provision.py:95` writes

  `staleCause`/`STALE_CAUSE_MARKER` string-parsing idiom already in this file) and render an

  auto-provisioned" timestamp distinct from `created_at` — using `created_at` as that date is

- **Task list.** Port `RepoTaskList`/`useRepoTasks`/`useCancelTask` from `repos.tsx` — live,

### Step 3 — Code Graph: build the real view, honestly bounded by §3's REST gap

**Size:** L (the largest single step — 941-line demo component, genuine layout-math reuse
decision, the REST-gap disposition to implement, not just state). **Files:** new
`frontend/src/features/code/components/real-code-graph-view.tsx`, new
`frontend/src/features/code/lib/graph-layout.ts` (or wherever the executing lane lands the
promoted layout math — see below), possibly-edited `code-canvas.tsx`/`code-explorer.tsx`/
`code-inspector.tsx`/`code-filters.tsx`/`lib/file-tree.ts` (only if their prop types are
promoted to a shared, non-demo shape — see the decision below), new
`frontend/src/hooks/api/use-code-api.ts` addition (`useCodeFiles(repoId)` wrapping
`GET /code/files/{repo_id}`, currently unused), `frontend/src/routes/_authenticated/
code_.graph.tsx`. **Depends:** Step 1 is not required; independent of Steps 2 and 4.

- **The central decision, stated for the executing lane to make with full information, not
  pre-decided here.** `code-canvas.tsx` imports rendering helpers (not just types) from
  `@/demo/explore.ts` (`layoutGraph`, `chartVar`, and others); `code-explorer.tsx`/
  `code-inspector.tsx`/`code-filters.tsx`/`lib/file-tree.ts` import only *types*
  (`DemoCodeGraph`, `DemoCodeNode`, `CodeNodeKind`). Two paths, and this plan does not force
  one:
  1. **Promote a shared, demo-independent graph type** (e.g. `features/code/types.ts`:
     `{id, label, kind, ...}` node / `{source, target, type}` edge — a strict subset of what
     `CodeGraphData` already is) and a demo-independent copy of `layoutGraph`'s pure math
     (force/tree/circles positioning does not need to know what a "community" is — it needs
     node/edge counts and ids). Both demo and real branches then share
     `code-canvas.tsx`/`code-explorer.tsx`/`code-inspector.tsx`/`code-filters.tsx`/
     `file-tree.ts` unmodified in behaviour, retyped against the shared shape. This is the
     option that shrinks the demo-import count (§1.2's (a)) and avoids ~900 lines of
     duplication, but it touches five files the demo branch also depends on and risks
     regressing `code-tabs.test.tsx`'s existing demo-mode assertions if the retype is not
     purely additive.
  2. **Build `real-code-graph-view.tsx` as a separate, smaller component** that reuses only
     `useCodeGraph`/`useCodeSymbolDetail`/`useBlastRadius`/`useCodeFiles`, with its own
     simpler canvas/tree/inspector, and leaves the demo files completely untouched. Lower
     regression risk, more duplicated code, and does not reduce the demo-import count at all.

## 5. Falsification pass

**Step most likely to be wrong: Step 3's shared-type-vs-separate-component split.** This
plan recommends promoting `code-explorer.tsx`/`code-inspector.tsx`/`code-filters.tsx`/
`file-tree.ts` to a shared, demo-independent type while leaving `code-canvas.tsx` demo-only
with a separate real renderer — but this recommendation was made from reading import lists and
line counts, not from attempting the retype. The evidence that would show it wrong: attempting
the shared-type promotion and finding `code-tabs.test.tsx`'s existing demo-mode assertions
(`code-tabs.test.tsx` renders `RepositoriesTab`/`CodeGraphTab`/`WikiTab` directly against real
demo fixtures) start failing, which would mean the "purely additive retype" assumption was
wrong and the coupling runs deeper than the grep-visible import list suggests. If that
happens, the fallback is this plan's option (2) — a fully separate real component reusing none
of the demo files' internals — and the executing lane should take it rather than force option
(1) through a failing test suite.

**Second-most-likely candidate:** the auto-provision "when" timestamp call in Step 2 (using
`created_at` as a proxy for "when this repo was auto-provisioned," since the real backend has
no dedicated field the demo's fixture date implies exists). This is stated as an open call in
Step 2 deliberately rather than resolved here, and a reviewer should check whether the
executing lane's actual choice over- or under-claims precision the data does not support.

**The silent failure mode this plan considers most dangerous:** the Wiki's read-only
invariant being violated in a form that produces no visible symptom and no test failure unless
the specific guard in Step 4 exists and is mutation-proven. A well-intentioned later edit —
"we're already touching the empty-state CTA, let's just call the reindex mutation directly
instead of making the user go through a dialog" — would look like a UX simplification, would
compile, would typecheck, and would pass every existing test that only checks the wiki
*renders*, while quietly turning "browsing the Wiki page can trigger backend work" into the
exact failure doc 13 §4.2 and this task's own ruling forbid. Nothing except a test that
explicitly asserts zero non-GET `apiFetch` calls across every interaction with the mounted
component — proven capable of failing, per GLOBAL §7's "a guard that cannot fail is worse than
no guard" — would catch it. Step 4 specifies that test and its mutation proof for exactly this
reason; if the executing lane drops the mutation-proof half under time pressure, this is the
risk that reopens silently.

## 6. Size call

**L stands, no split recommended.** The three surfaces are one doc-13 §4.2 decision ("The
three code surfaces consolidate under one Code section with tabs") sharing one repo-selector
idiom and one underlying `useRepos`/`useCodeGraph` data model; splitting them into separate
tasks would not reduce risk (Step 3's REST-gap disposition and Step 4's invariant guard are
each self-contained regardless of whether the other two ship in the same task) and would
recreate the exact partial-binding state T1.46 already shipped as a known, accepted interim
(Repositories bound, Graph/Wiki still demo) — landing all three together is what actually
retires that interim rather than extending it under a new name. Six steps, three of them
(2/3/4) independent and parallelisable by sub-lane if a future wave wants to split execution
labor without splitting the task; Step 3 is the largest single unit by a wide margin (a
941-line demo component to rebuild against, plus the REST-gap disposition to design and
implement, not just state) and is the step a reviewer should scrutinise hardest.
