# T3.02 — `article_synthesis` productive runs

> **For agentic workers:** REQUIRED SUB-SKILL: `superpowers:executing-plans`.
> Steps use checkbox (`- [ ]`) syntax.

**Task:** `T3.02`, `Size: L`, `Model: Opus 5`, `Gate: G-D (label)`.
**Design:** doc 09 §4.2, §4.3. **Runbook §3** forbids executing an `L` task
directly, which is why this exists.

**Revision 1, 2026-08-11 — not yet reviewed.**

**Goal.** Give `article_synthesis` a real body: eligible subject in (T3.01),
one stored article out, synthesised from verified facts only, journalled so a
bad article is traceable to its fact set. It is the first consumer of the
`synthesis` LLM purpose, which has been seeded and inert since day one.

**What this task must not do.** It must not label anything grounded. The
entailment pass that measures coverage is `T3.03`; until it exists, no article
has a measured coverage, so no article may claim one. See D3 — this is the
decision most likely to be got wrong, because the status column will happily
accept `corroborated`.

## The inherited clause is already settled — do not re-decide it

T3.02's task text says the `ln(1+x)` damping in `article_eligibility._priority`
"either adopts the deviation explicitly (amending doc 09 §4.1, a Tier-3 move)
or drops the damping. Decide on purpose, not by inheriting."

**That decision was made on 2026-08-10 by ruling R-D and it is not this task's
to reopen.** Doc 09 §4.1 now carries the damping as its stated stance, with the
reasoning recorded there, and `_priority`'s docstring already presents it as
§4.1's formula rather than as an undocumented deviation. Both were verified in
the tree on 2026-08-11.

Re-deciding it here would be re-litigating a ratified Tier-3 ruling — which
§4.1 explicitly warns against ("a retune moves the `w_*` rows, never the
damping, or it is silently re-litigating this decision under cover of a
measurement"). The task text is stale and is amended in the same commit as this
plan. **Nothing about the formula changes in this task.**

## Decisions to make before coding, not during

**D1 — the exclusion is a `WHERE`, not a filter.** The done-when says
"excluded at the query, not filtered from the draft", and the distinction is
the whole safety property rather than a performance note. A filter applied to a
draft means the *model already saw* the disputed fact and may have written a
sentence its citation no longer supports; the sentence survives the filter
because the filter removes facts, not prose. So disputed and candidate facts
must never be loaded. The predicate, from doc 09 §4.2:

```
verification_status IN ('corroborated', 'confirmed')
AND expired_at IS NULL
AND <not disputed>
```

`disputed` is a `verification_status` value, so the `IN` clause already excludes
it; the third line is therefore **not** redundant belt-and-braces but a guard on
the *contradiction* flag — a `corroborated` fact carrying
`contradiction_suspected_at` is under an open suspicion a human has not yet
adjudicated, and doc 09's "an article states settled understanding" is exactly
what that is not. Confirm against `verification_ladder` before writing the SQL;
if the flag turns out to be excluded some other way, say so in the report
rather than dropping the clause silently.

**D2 — the hub cap ranks by `confidence × read-heat × recency`, and read-heat
is computed at job time.** Doc 09 §4.2 fixes both. `K` is a `config` row
defaulting to 40. Read-heat is "the aggregated read signal of the subject's
facts and any existing article, computed at job time, never a stored heat
column that would go stale" (§4.1) — `access_stats.py` already owns that
computation for the eligibility scan and must be reused, not reimplemented.

**D3 — what status a synthesised article gets, before T3.03 exists.**
`candidate`, with `review_state='open'`. Not `corroborated`, and not a null
review state.

The reasoning, because the column will accept anything: doc 09 §4.3 makes
coverage the gate — "an article below a `config` coverage threshold does not
ship as `corroborated`, it sets `review_state='open'`". An article with **no
measured coverage** is not above the threshold; it is unmeasured, which is the
same serving outcome and a different reason. Writing `corroborated` because
nothing has yet said otherwise is precisely the confident-but-wrong failure the
layer exists to prevent, and `ux_knowledge_articles_live` would happily hold it.

So: every article this task writes is `candidate` + `review_state='open'`, and
that is **permanent behaviour for an unmeasured article**, not scaffolding
T3.03 deletes. T3.03 adds the measurement that can *raise* it.

**D4 — `confidence` stays NULL until coverage is measured.** Doc 09 §4.3:
"coverage ... *is* the article's stored `confidence`". No coverage, no
confidence. A default of 0.0 would read as "measured, and terrible"; NULL reads
as "not measured", which is true. Assert it.

**D5 — the journal payload names the fact set, not the article's prose.** The
done-when is "every run journals its inputs so a bad article is traceable to
its fact set". Write-time minimization (CLAUDE.md, events journal) applies with
its usual force: journal the **fact ids** in ranked order, `K`, the config
values in force, the subject key, and the model/purpose — never the draft text.
The article row holds the prose; the journal answers "which facts produced it".
Ids also stay honest about facts later invalidated, which prose would not.

Event type: reuse an existing `EVENT_TYPES` member. Widening the closed
vocabulary is taxonomy-first work (doc 04 §8.1) and this task does not need it
if an existing value fits — check `consolidated` and the topic family before
concluding otherwise. **If none fits, stop and say so**; do not invent a value
at a call site.

**D6 — the three inherited seams, and which of them this task actually
closes.** T2.95's review named three (T3.02's task text). Treat them as three
separate steps with separate verification, because they fail differently:

- **Seam 1 (`list_open_articles` serves the raw status).** Real and this task's,
  because this task is what first puts a row in that queue. Route it through
  `fact_badge.row_labels` and widen both enforcement scans to the `status`
  spelling — they quantify over `verification_status` and are blind to it.
- **Seam 2 (`served_status`'s `gate=` parameter, unforwarded by `row_labels`).**
  Articles currently route to an unconditionally-closed groundedness gate.
  **Opening it is *not* this task's work under the M1 split** — the gate opens
  on G-D's qualification record, G-D is not cleared, and T3.02's own text says
  the grounded label waits. Forward the parameter so the seam is no longer a
  hole; leave the gate closed. Making it *open* is an activation for whoever
  owns the G-D clearance, and this plan says so rather than doing it.
- **Seam 3 (a minted fact record must not light an article).** Keep and extend
  T2.95's test now that the article path is reachable.

Seam 2 is where this plan most expects to be wrong; if review disagrees, that
is the clause to argue.

**D7 — the runner is a body for the registered job, not a new job.** T2.14
registered `article_synthesis` with its cron, lock and config schema. This task
replaces `PlaceholderJobRunner` and changes nothing about the registration.
`tests/test_dream_jobs.py` asserts the placeholder type; that assertion moves
from "is a placeholder" to "is not a placeholder" for this member only, and the
other remaining placeholder (there is one) keeps its assertion.

**D8 — invariant 15 binds.** `article_synthesis` is a dream-job family member,
so no capture or retrieval path may reach it. The source scan already fails the
build if one does; do not add a synchronous "synthesise now" door in this task.

## Steps

- [ ] **Step 1 — the fact-gathering query.** `article_synthesis.py`: given a
      subject key and project, return the ranked, capped fact set. D1's `WHERE`,
      D2's ranking and `K`. No LLM call, no writes. Tests: a disputed fact and a
      candidate fact are absent from the returned set *and* absent from the
      emitted SQL's result under a direct DB assertion; an expired fact is
      absent; a hub subject returns exactly `K`; ranking order is stable.
      **Mutation drill:** flip the `IN` clause to include `candidate` and prove
      a test reddens.
- [ ] **Step 2 — grouping and the draft call.** Group by `rel_type` and
      `applies_when` (doc 09 §4.2), build the `synthesis`-purpose prompt, and
      parse the response into prose plus per-sentence candidate fact ids. The
      call goes through the orchestrator like every other purpose; forward
      `seed = sha256(content)[:8]` per the reproducibility rule. Tests against a
      stubbed LLM: the prompt carries only the gathered facts; a response whose
      cited ids are not in the input set is refused rather than stored (the
      model must not invent a citation); an unparseable response fails the run
      without writing.
- [ ] **Step 3 — the article write.** One row per subject, `candidate` +
      `review_state='open'` (D3), `confidence` NULL (D4), `fact_set_hash` over
      the verified fact set, `applies_when`/`learned_in` aggregated from the
      supporting facts. Respect `ux_knowledge_articles_live` — one live article
      per `(project, subject_key)`; a re-run supersedes rather than colliding.
      **Supersession lineage is T3.05's**; here, assert the constraint is not
      violated and defer the debounce.
- [ ] **Step 4 — the journal.** D5's payload, one row per run per subject.
      Test: the payload names every input fact id in ranked order and contains
      no substring of the draft prose.
- [ ] **Step 5 — the runner.** Replace the placeholder; drive Step 1–4 for each
      subject `select_for_synthesis` returns, bounded by `synthesis_budget`
      (T3.01's budget, D7). Test: a budget of 2 synthesises 2 subjects and not
      the third; one subject's failure does not abort the others, and the failed
      one journals its failure.
- [ ] **Step 6 — seam 1.** Route `list_open_articles` through `row_labels`;
      widen both enforcement scans to the `status` spelling. Test: an article
      written by Step 3 appears in the review queue with a *served* status, and
      the scan reddens when the routing is removed.
- [ ] **Step 7 — seam 2.** Forward `gate=` through `row_labels`. The gate stays
      closed (D6). Test: an article's served groundedness label is withheld with
      its reason, and no code path can open it without a qualification record.
- [ ] **Step 8 — seam 3 + the floor.** Extend T2.95's "a minted fact record must
      not light an article" test now that articles exist. Run
      `./scripts/gate.sh`.
