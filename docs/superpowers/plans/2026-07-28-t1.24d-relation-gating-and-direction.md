## 2. Binding constraints on every step

1. **No model call enters the chain.** `clean_extraction` is pure
   `list[dict] -> list[dict]` and `test_whole_chain_makes_zero_model_calls`
   enforces it. This is what makes the F1 bench free to iterate. Any step that
   wants a semantic judgement must get it from a regex or a curated table, never
   from a model.
2. **The anti-fitting standard binds** (ratified, amendment log 2026-07-27,
   T1.24b/T1.24c). A curated entry or pattern justified only by the set it is
   measured on is not evidence. A `+0.030` entity-F1 gain was declined on exactly
   these grounds. Every new pattern this task adds must be justifiable
   **independently of `gold.json`** — ideally transcribed from an artifact written
   before either gold set (the frozen extraction prompt, `CLAUDE.md`'s ratified
   supersession rules, doc 06's own text). Held-out numbers are reported as
   prominently as gold in every step that measures.
3. **Held-out independence is already partly spent.** `gold_heldout.json` was not
   blind to T1.24c's design. Treat a held-out gain as corroboration, never as proof,
   and say so when reporting.
4. **Stage boundaries.** Stage 3 (`_rescue_relations*`) is T1.25's and is done.
   Stage 5 (`_drop_uses_when_*`, `_dedup_by_target_predicate`,
   `_fan_out_coordinated`, the second `_filter_event_edges`, `_drop_unlinked_dates`)
   is T1.24e's. §8 draws that line explicitly.
5. **Cross-cutting invariants** (`CLAUDE.md`) that Stage 4 touches: the closed
   taxonomy (every emitted relation type must survive `normalize_relation_type`);
   the `REPLACES` family (`REPLACES` / `IMPROVES_ON` / legacy `BUILDS_ON` collapse
   via `family_key`, and adding a replacement-family member means editing
   `REPLACES_FAMILY`); and the supersession contract downstream — a `REPLACES` edge
   that escapes Stage 4 is what triggers `detect_supersessions`, so a false positive
   here silently flips a live memory to `superseded`. That last one is why this task
   is Opus tier: its failure mode is data loss in the default `active` view, not a
   crash.
6. **Relaxing any of those is a Tier-3 amendment.** Stop and escalate; do not
   work around.

Stage 4 the situation is worse, and it is now quantified rather than asserted.

Entity dimensions moved 0.000 for every pass, as expected — Stage 4 writes only
`relationships`.

**"Memories changed" is the load-bearing column, not the F1 delta.** It counts
memories whose entity list or relationship list differs at all when the pass is
removed, so a pass that changes output without changing the score still registers.
Seven of the ten passes register zero on both corpora: **deleting them entirely
produces bit-identical output on all 36 memories.**

Three consequences the executing agent must carry:

- **"Relation F1 does not regress" is satisfiable by deleting 70% of this stage.**
  It is a necessary condition and nothing more. It cannot detect a change to seven
  of the ten passes this task owns, in either direction. A green bench is evidence
  of *nothing measured*, not of *no regression* — the same distinction the
  controller drew for Stage 3 (amendment log, 2026-07-27, T1.25).
- **The three passes the corpus does see are exactly the ones least at risk.**
  `remap_to_valid_entities` is structural plumbing; `downgrade_future_to_mentions`
  and `drop_date_misuse` each move one memory. The gates whose failure mode is a
  false supersession — the two `REPLACES` gates and the two direction validators —
  are invisible to the bench, which is precisely where the consequence lives.
- **G-B must not cite F1 as evidence for Stage 4**, on the same reasoning already
  applied to Stage 3 and already added to T1.50. Recording this is Step 8's job.

### 3.1 The substitute guard

Since the bench cannot see the stage, the guard has to be built. Three mechanisms,
each cheap and each independently reversible:

1. **Per-gate behavioural tests** in `tests/test_relation_gating.py`, hand-authored
   from each pass's docstring and the doc 06 §4 S4 box it implements — not sampled
   from `gold.json`. This is the primary guard and is what "each gate individually
   tested" means.
2. **Mutation proof on every invariant pin.** For each pin, break the pass on
   purpose, observe the specific test fail, restore, observe it pass, and record
   both outputs. Runbook §4 requires this for invariant-bearing behaviour; here it
   is also the only way to know a test is not vacuously green against a pass the
   corpus never exercises. A guard nobody tried to break is a guard nobody tested.
3. **Whole-chain output identity across both corpora.** Any step that is meant to
   be behaviour-preserving proves it by capturing `clean_extraction` output for all
   36 memories before and after and diffing entities, relationships, types, weights
   and `properties` — not by comparing four F1 numbers. T1.25 used exactly this and
   it is the reason its refactor could be called behaviour-preserving rather than
   argued to be. **The comparison must be order-insensitive** while
   `_fan_out_coordinated` still iterates a `set` (§8).

### Step 2 — The two REPLACES gates, individually tested

**Size:** M. **Depends on:** Step 1. **Serialised:** yes.

This is the highest-consequence pair in the stage: a `REPLACES` edge that escapes
here reaches `detect_supersessions` and flips a live memory out of the `active`
view. Both gates are invisible to the bench (§3), so the tests are the only guard.

**What changes.** Tests only. `_gate_replaces_selection` and
`_gate_replaces_requires_verb` are not modified in this step.

**Tests to write**, each named for the behaviour, not the function:

*`_gate_replaces_selection`* — "chose X over Y" is `IMPROVES_ON`, not `REPLACES`:
- Each verb in `_SELECTION_RE` (`chose`/`choose`/`chosen`/`picked`/`selected`/
  `went with`/`going with`/`opted for`/`preferred`) crossed with each comparator
  (`over`/`instead of`/`rather than`/`versus`/`vs`) downgrades a `REPLACES` to
  `IMPROVES_ON`. Parametrise; do not write forty literal tests.
- A migration verb anywhere in the content **suppresses** the downgrade
  (`_MIGRATION_RE` in the `or` branch) — pin this, because it is the gate's
  documented escape hatch and it is currently document-scoped (§9, open question 1).
- Non-`REPLACES` types pass through untouched.
- Content with neither cue is a no-op.
- The pass does not mutate its input (every other stage file pins this per pass;
  keep the convention).

*`_gate_replaces_requires_verb`* — an unsupported `REPLACES` becomes `RELATED_TO`:
- Every alternative in `_REPLACE_EVIDENCE_RE` spares the edge. Parametrise over the
  alternatives read out of the pattern so a future edit to the regex without a
  matching test edit is caught.
- Bare rewrite phrasing with no replacement verb downgrades to `RELATED_TO` — the
  docstring's own example ("all writes now go through the event bus").
- `IMPROVES_ON` and `BUILDS_ON` phrasings spare the edge, since they are in the
  evidence set and in `REPLACES_FAMILY`.
- The downgrade target is `RELATED_TO`, the taxonomy's unknown-relation fallback,
  and it survives `normalize_relation_type`.

**Mutation proof (required).** For each gate, break it on purpose and record the
failure: (a) make `_gate_replaces_selection` return `relationships` unchanged —
the selection tests must fail; (b) invert `_gate_replaces_requires_verb`'s early
return so it downgrades when evidence *is* present — the evidence tests must fail.
Restore, re-run, record both outputs in the report.

**Invariant discharged.** `REPLACES` is reserved for real migrations; the
supersession trigger is not minted from a selection or from a bare rewrite.

### Step 3 — The temporal trio, individually tested

**Size:** M. **Depends on:** Step 2. **Serialised:** yes.

**What changes.** Tests only.

*`_suppress_temporal_edges`* — the closest-mention-pair rule is the subtle part and
the reason this pass has a bug class of its own:
- A `RELATED_TO` whose endpoints are joined only by a temporal connector
  (`after`/`before`/`since`/`following`/`prior to`/`then`/`once`/`later`) is
  dropped; parametrise the connectors.
- A causal verb in the same span **rescues** the edge (`_CAUSAL_BETWEEN_RE` wins).
- Only `RELATED_TO` and `CAUSES` are candidates; `USES` with a temporal connector
  survives.
- **The closest-pair rule specifically:** a subject that recurs (the project name,
  typically) must be evaluated on its nearest mention, not its first. Build a case
  where the first mention spans an unrelated temporal window and the nearest one
  does not, and pin that the edge survives. This is the documented reason the pass
  is written the way it is, and it is exactly the behaviour a naive rewrite would
  lose.
- Note for the executing agent, to be confirmed not assumed: the span search uses
  `re.escape(s)` as a **bare substring**, unlike `_entity_matches`, which uses a
  word boundary. Whether `postgres` therefore matches inside `postgresql` here is
  §9 open question 3 — **write the characterisation test for whatever the current
  behaviour is, and do not change it in this step.**

*`_downgrade_future_to_mentions`*:
- Each `_FUTURE_RE` alternative triggers; parametrise.
- Only `USES`/`IMPLEMENTS`/`EXTENDS`/`DEPENDS_ON` downgrade, and the weight is
  clamped to `min(weight, 0.5)`.
- A target mentioned *before* the future marker is not downgraded — the zone runs
  from the marker to end of content. Pin this as characterisation; its coarseness
  is §9 open question 2.

*`_drop_date_misuse`*:
- A bare ISO date as source or target of anything other than `HAPPENED_ON` is
  dropped, in both endpoint positions.
- `HAPPENED_ON` with a date target survives.
- A name that merely *contains* a date (`2026-05-12 outage`) is not dropped —
  `fullmatch`, not `search`. This one is worth an explicit test: it is the
  difference between dropping a misuse and destroying every dated event edge.

**Mutation proof.** Break each of the three (respectively: return input unchanged;
drop the `min()` weight clamp; swap `fullmatch` for `search`) and record which test
fails. The `fullmatch → search` mutation is the most valuable of the nine in this
plan — it is a one-word change that the bench cannot see and that would silently
delete event edges in production.

**Invariant discharged.** A date is only ever a `HAPPENED_ON` target; a temporal
adjacency is not a claim; a plan is not a usage.

### Step 4 — Direction validation, and the ambiguity half of the criterion

**Size:** M. **Depends on:** Step 3. **Serialised:** yes.

The Done-when reads "unambiguously wrong directions swap; ambiguous ones are left
alone". Both halves need tests; the second half is the one that is easy to skip and
the one whose absence would let a future "improvement" start guessing.

**What changes.** Tests, plus one small code change (below).

*`_validate_directions`*:
- Each `_REPLACES_PATTERNS` entry (`switched from X to Y`, `migrated from X to Y`,
  `replaced X with Y`, `replacing X with Y`, `chose X over/instead of Y`, `picked`,
  `went with`, `decided to use`) swaps a wrong-direction edge and leaves a
  right-direction edge alone. Parametrise over the pattern list itself so adding a
  pattern without a test is caught.
- Same for `_IMPROVES_PATTERNS` (`improves on/upon/over`, `is better than`,
  `builds on`).
- **Ambiguity, three distinct cases, each its own test.** No swap when: only one
  endpoint matches its swapped role; when an endpoint matches *both* its expected
  and its wrong role (the `and not src_matches_expected` guard); and when no pattern
  matches the content at all.
- **Word-boundary matching**, the documented regression: `postgres` must not match
  inside `postgres 17`, because a bare substring makes both the expected and
  wrong-direction predicates true and triggers a spurious swap. `_entity_matches`
  exists for this; pin it with a test that fails if the `\b` anchors are removed.
- Relation types outside the two families pass through untouched.

*`_validate_hosting_direction`*:
- Hardware on the source side swaps; hardware on the target side does not.
- **Both endpoints hardware is ambiguous and must not swap** — the current
  condition (`src in _HARDWARE_TOKENS and tgt not in _HARDWARE_TOKENS`) already
  encodes this. Pin it.
- Neither endpoint hardware: no swap.
- Only `DEPLOYED_ON` is a candidate; `RUNS_ON` never appears here because
  `normalize_relation_type` rewrites it upstream — pin that too, since the coupling
  to `LEGACY_RELATIONSHIP_TYPE_MAP` is invisible in this file.
- The pass shares `_HARDWARE_TOKENS` with `_snap_hardware_types` deliberately.
  Assert the shared identity (`is` on the frozenset, or membership equality) so a
  future edit to one list cannot silently decouple the two.

**Code change.** `_validate_directions` assigns `swapped = True` and never reads it.
Remove the dead variable. This is a pure deletion with no behavioural effect; prove
that with the §3.1 whole-chain identity check rather than asserting it. Keep it in
this step's commit, not a separate cleanup commit — it is one line inside the
function the step is already about.

**Mutation proof.** Break the ambiguity guard (drop `and not src_matches_expected
and not tgt_matches_expected`) and confirm an ambiguity test fails; break
`_entity_matches` back to a bare `in` and confirm the `postgres 17` test fails.

**Invariant discharged.** A direction swap is a deterministic consequence of an
explicit source-text pattern, never a guess. This is the half of the moat that
protects `REPLACES` orientation, which Stage 5's rescue-first tie-break then
arbitrates.

### Step 5 — Remap, and the reachability adjudication of `drop_edges_to_negated`

**Size:** M. **Depends on:** Step 4. **Serialised:** yes. **This step may end in
BLOCKED or in a Tier-2 amendment; read §9 open question 4 before starting.**

`remap_to_valid_entities` is the one Stage-4 pass with real corpus weight
(−0.045 gold rel_full, −0.022 held-out). `drop_edges_to_negated` is its neighbour in
box D1 and appears, on the evidence below, to be unreachable.

**What changes.** Tests; a code change only if the adjudication concludes one is
needed, and only under the conditions in §9.

*`remap_to_valid_entities`* tests:
- An edge whose endpoint survived shaping under a different name is rewritten onto
  the survivor via `_build_name_remap` (trailing-suffix strip, acronym expansion).
- An edge whose endpoint did not survive is dropped.
- A self-edge (`src == tgt` after remap) is dropped.
- The type is normalised through the closed taxonomy on the way out — an unknown
  relation becomes `RELATED_TO`, a legacy name is rewritten (`RUNS_ON` →
  `DEPLOYED_ON`).
- It reads `raw_entities`, not `entities`, for the remap source. This is the
  binding T1.24a put in the registry declaration; pin it, because reading the
  shaped list instead would lose exactly the mappings the pass exists for.

*`drop_edges_to_negated`* — adjudicate reachability. **Evidence already gathered
(2026-07-28, read-only probes):**

1. Removing the pass changes nothing on either corpus: 0 / 26 and 0 / 10 memories.
2. A constructed negation case (`"We run darkmem on postgres without redis."` with a
   hallucinated `redis REPLACES postgres`) produces identical output with and
   without the pass. Instrumenting the state at the pass's own index shows
   `negated_names == {"redis"}` but the relationship list already contains no edge
   touching `redis` — **`remap_to_valid_entities`, one position earlier, has already
   deleted it**, because `_remap_relationships` requires both endpoints to be in
   `valid_names` and a negation-only entity was dropped from `entities` back in
   Stage 1.
3. The structural argument for "never reachable": for the pass to fire, an endpoint
   string must be in `valid_names` **and** in `negated_names` simultaneously.
   `negated_names` is populated by `_filter_negation_only`, which removes those
   entities; the only way one returns is a Stage-2 rescue. `_rescue_known_entities`
   and `_rescue_relation_endpoints` are both negation-aware and decline.
   `_rescue_happened_on` adds dates. That leaves `_rescue_file_path_entities`,
   which is **not** negation-aware — but a probe of that route also fails to reach
   the pass, because `_filter_noise` drops file paths in Stage 1 *before*
   `_filter_negation_only` ever sees them, so a negated file path can never enter
   `negated_names` in the first place.

**What the step must do.** Try hard to falsify the unreachability claim by

### Step 7 — Declare Stage 4's internal orderings as data

**Size:** M. **Depends on:** Step 6. **Serialised:** yes.

T1.24a's premise is that a load-bearing order is declared in `ORDERING_CONSTRAINTS`
and validated at import, not left to the sequence happening to be right. Stage 4
currently declares none, yet it has at least two orderings that are load-bearing —
one of which Step 5 has already demonstrated changes behaviour.

**What changes.** `ORDERING_CONSTRAINTS` in `app/services/extraction_clean.py` gains
`RunsBefore` entries, each with a `why` string that states the mechanism. Candidates,
each to be **individually demonstrated before it is declared** — a constraint that
cannot be broken into a failure is a comment, not a contract:

1. `remap_to_valid_entities` before `gate_replaces_selection` (and thus before the
   rest of the stage). Every downstream gate keys on endpoint *names*
   (`_HARDWARE_TOKENS` membership, `_entity_matches`, event-name lookup); before the
   remap those names are the model's raw strings, so a gate would compare against a
   vocabulary that no longer exists downstream.
2. `gate_replaces_selection` before `validate_directions`. The selection gate
   rewrites `REPLACES` → `IMPROVES_ON`, and `validate_directions` chooses
   `_REPLACES_PATTERNS` vs `_IMPROVES_PATTERNS` on that very type. Reversing the two
   applies the wrong pattern family, and the two families assign the source/target
   roles in **opposite** order (`"target","source"` vs `"source","target"`), so the
   reversal does not merely miss a swap — it can invert a correct edge.
3. Possibly `remap_to_valid_entities` before `drop_edges_to_negated` — **only if**
   Step 5 found the pass reachable. If it is unreachable, declaring an ordering
   constraint on it would encode a fiction; say so instead.

**Test that proves it.** For each declared constraint, three tests in the idiom
`tests/test_pass_registry.py` already uses for the four existing constraints:
a positive (the property holds in the shipped registry), a demonstration (a swapped
registry produces the specific wrong output, shown with a concrete input), and a
contract test (`validate_registry` raises `RegistryContractError` on the swapped
order). The middle one is what makes it a measured claim rather than an assertion.

**Registry-count note.** This step adds constraints, not passes, so the pinned count
stays 31 and no `PASS_FIXTURES` entry is needed. If the executing agent finds a
reason to split a gate into two passes, §5's deliberate-update rule applies and the
pin moves in the same commit.

**Invariant discharged.** Stage 4's order is contract. Two of its orderings can
invert a `REPLACES` if reversed, which is a silent-correctness failure of exactly
the class this epic's registry exists to make impossible.

### Step 9 — CONDITIONAL: sentence-scoping the document-scoped gates

**Size:** M. **Depends on:** Step 8. **Serialised:** yes, last. **Do not start this
step unless Steps 1–8 are complete and green, and do not treat it as required.**

Four of the gates evaluate their regex against the **entire memory content** and
then apply the verdict to **every** edge in the memory:

| Pass | Scope today |
|---|---|
| `_gate_replaces_selection` | one `_SELECTION_RE` hit anywhere downgrades every `REPLACES`; one `_MIGRATION_RE` hit anywhere spares every one |
| `_gate_replaces_requires_verb` | one evidence verb anywhere spares every `REPLACES` |
| `_downgrade_future_to_mentions` | the future zone runs from the first marker to end of content |
| `_validate_directions` | `pattern.search(content)` takes the first match in the document and applies its roles to every `REPLACES`/`IMPROVES_ON` edge |

On a single-claim memory this is correct. On a multi-claim memory it is a false
positive or a false negative waiting to happen, and the failure is silent.

**The justification, and why it is not fitting.** `CLAUDE.md`'s supersession section
already ratifies exactly this refinement for exactly this problem: the speculative
gate is "scoped per target: only the sentences mentioning that `REPLACES` target are
checked for `SPECULATIVE_REPLACES_MARKERS` ... falling back to the whole text only
when no sentence mentions the target — an unrelated speculative aside elsewhere in
the memory does not suppress a definitive replacement." That rule was written before
either gold set and lives in a document this task did not author. Porting it to
Stage 4's gates is the same class of justification as T1.24c's `_ARTIFACT_HEAD_NOUNS`
(transcribed verbatim from the frozen extraction prompt) and clears the anti-fitting
standard by construction rather than by measurement. `_suppress_temporal_edges`
already does the local-window thing, so the idiom exists inside this very file.

**But it is a behaviour change with real risk**, and §3 says the bench cannot see
three of the four passes. So the step is gated:

**Preconditions — all four must hold before any of it lands:**
1. Steps 1–8 complete, committed, green, with the per-pass ablation recorded.
2. Each gate is rescoped **separately**, in its own commit, so any one is revertible
   in one `git revert`.
3. Each rescoping ships with hand-authored multi-claim test cases written **before**
   the change and drawn from the mechanism, not from `gold.json` — a memory carrying
   one definitive migration and one unrelated selection; one carrying a definitive
   migration and an unrelated future plan; one carrying two `REPLACES` claims in
   opposite orientations.
4. Bench on both sets at or above §5's baseline after each individual commit, with
   held-out reported as prominently as gold, and every changed memory enumerated.

**Stop conditions.** Abandon the step and revert if: any dimension drops on either
set; the "fall back to whole text when no sentence mentions the endpoint" clause
turns out not to transfer cleanly (the supersession detector has an entity name to
scope on, and `_downgrade_future_to_mentions` may not); or the change requires a
sentence splitter more elaborate than the `_split_clauses` helper this file already
has, which would be new machinery inside a task that owns none.

**If the step is skipped**, say so explicitly in the report with the reason. Skipping
is a legitimate outcome — the gates are correct on single-claim memories and the
epic has a bar against unfalsifiable improvements, not a quota of them. Record the
coarseness as a finding for T1.24f either way.

**Invariant discharged.** A gate's verdict is scoped to the claim it judges.

## 9. What cannot be settled from the code and the docs

These four are surfaced deliberately rather than decided silently. Items 1–3 are
inputs to the conditional Step 9; item 4 gates Step 5's outcome.

**1. Is `_gate_replaces_selection`'s document-scoped migration escape hatch
intended?** As written, one migration verb anywhere in the memory spares *every*
`REPLACES`, including one that a selection phrase two sentences away should have
downgraded. Doc 06 §4 says only "reserve `REPLACES` for real migrations" and does not
state a scope. `CLAUDE.md`'s supersession gate resolves the same ambiguity in favour
of per-target sentence scoping, but that is a different subsystem's rule. **Cannot be
settled from the corpus**: the gate changes zero memories on both gold sets, so there
is no measurement that would distinguish the readings. Needs a controller ruling, or
a gold memory that carries both cues — which nobody has authored.

**2. Is `_downgrade_future_to_mentions`'s to-end-of-content zone intended?** A future
marker in the first sentence downgrades every subsequent `USES`/`IMPLEMENTS`/
`EXTENDS`/`DEPENDS_ON` edge in the memory, however far away. This is the one gate of
the four with corpus signal (one gold memory, −0.012 rel_full when removed), so a
rescoping is at least *measurable* — but a single memory is not enough to
discriminate, and tuning against it would be fitting to one row of the answer key,
which the ratified standard forbids.

**3. `_suppress_temporal_edges` matches endpoint names as bare substrings**
(`re.escape(s)` into `re.finditer`), while `_validate_directions` deliberately uses
word-boundary matching via `_entity_matches`, with a comment recording the
`postgres` / `postgres 17` regression that forced it. Whether the temporal pass's
looser matching is deliberate (it is measuring a *span* between mentions, where a
substring hit may be acceptable) or is the same latent bug in a second place cannot
be told from the code or doc 06. Step 3 characterises the current behaviour; it does
not change it. Unifying the two is a candidate for Step 9 and needs a ruling.

**4. If `drop_edges_to_negated` is unreachable, what is the right resolution?**
Three options, none decidable from the corpus, and this lane should take none of them
unilaterally:
   - **Move it before `remap_to_valid_entities`.** Superficially obvious, and
     probably wrong: before the remap, edge endpoints are the model's raw strings,
     while `negated_names` holds *shaped* names (`_filter_negation_only` runs after
     `_normalize_names`). The two vocabularies only coincide by luck, which is why
     `_build_name_remap` exists at all. A pre-remap position would fire
     inconsistently, which is worse than never firing.
   - **Make `_rescue_file_path_entities` negation-aware**, closing the one rescue
     path that is not. That is a **Stage 2 change and belongs to T1.24c**, which is
     merged — reaching into it is outside this task's lane.
   - **Record it as intentional defence-in-depth** and leave it. Legitimate: it costs
     one list comprehension, and Stage 3 is in the same corpus-invisible state
     without anyone proposing its removal.

   The decision affects doc 06 §4's S4 box D1, which credits the behaviour to the
   pass that does not perform it, so it is at least a doc correction. **Report the
   finding, log the Tier-2 amendment, and let the controller choose.** If the finding
   is instead that the doc is *wrong* rather than merely imprecise, that is Tier 3 —
   stop and escalate.
