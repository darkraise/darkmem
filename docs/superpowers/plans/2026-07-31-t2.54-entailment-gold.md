entailment gold into a gate-eligible one: **at least 241 live pairs** (the 41 legacy

eligibility lock would no longer refuse this gold for any composition reason — while

## Ruling 1 — where 200 real `l2-fact` premises come from, and whether bench-lifted facts are "real"

**Ruling: premises are harvested from `knowledge_triples` rows minted by the shipping
`fact_lift` over the retrieval corpus ingested into an assigned bench database, and
these count as real `l2-fact` premises for §11's purposes.** The measured chain: ~73
distinct triples in the warm extraction cache (M6) → an expected 60–75 open facts
after one lift pass at the default salience bar of 1 → each premise supporting up to 4
pairs (cap, below) → capacity ≥ 240 `l2-fact` pairs against a need of 121.

The argument, not the assumption:

1. **§11's stated worry is representativeness, and the bench route is the *more*
   representative one.** The two consumers this variant qualifies (the veto, doc 08
   §4.2; the entailment pass, doc 09 §4.3) hand the judge premises that are literally
   `knowledge_triples.fact` texts — terse `fact_sentence` clauses over lowercased
   canonical names, with no validity window rendered (M10). T2.25's hand-authored
   premises are one-to-two-sentence prose — *richer than anything production will ever
   show the judge*. A gold whose premise mass is bench-lifted `fact_sentence` output
   matches the production premise distribution **by construction**, because it is
   produced by the identical code path (`extraction → clean → dedup → fact_lift →
   fact_sentence`). The only synthetic residue is the corpus *content*, and that same
   corpus is already the harness's standing stand-in for production content in every
   other gate measurement (the F1 bench, the retrieval eval, G-B).
2. **The alternative reading is unsatisfiable and inverts the roadmap.** "Real" as
   "from the production database" fails on a measured fact: `darkmem` has no schema on
   this machine (M1) — there is no production deployment anywhere yet; the schema
   freeze *is* the first such deploy. Under that reading G-D and G-C sit behind the
   homelab cutover, while doc 20 sequences the cutover behind the gates. A reading
   that makes both remaining gates unopenable by definition is not a reading of §11,
   it is a deadlock — and the E2 amendment log already rejected the equivalent
   deadlock reading once ("§11 says once *Layer 2* is live, and Layer 2 is
   `knowledge_triples`, whose producer is T2.10 in this epic").
3. **Honesty is preserved by disclosure, not by the name.** The provenance value stays
   `l2-fact` (the vocabulary is closed and the eligibility lock keys on it), and
   LABELLING.md gains its precise definition: *a premise verbatim-equal to a
   `knowledge_triples.fact` minted by `fact_lift` in the recorded harvest run*, with
   the harvest manifest (Ruling 2) naming the database, corpus sha, gate config and
   git sha. Nothing about where the facts came from is hidden from T2.41 or from G-D's
   ledger entry.

**Tier: 2, with owner ratification required before T2.41 runs `--gate`** (stop-and-ask
item S1). This is an interpretation of an ambiguous word, not a contradiction of a doc
sentence — §11's own sentence ("seeded from real synthesis drafts and real block
answers") is about the *hypothesis* side; the `l2-fact` premise requirement entered
through the 2026-07-31 amendment chain, which explicitly routed its residual questions
to this task. Nothing in doc 17 has to change, so Tier 3 is not triggered — but
because the ruling decides what a gate may open on, it is surfaced for a human yes
rather than merely logged. **Rejected alternatives:** waiting for production facts
(deadlock, above); hand-writing premises "in the shape of" fact texts (that is
precisely the synthetic-only composition §11 rejects, wearing a costume); ingesting
the owner's real working notes into the bench DB (would put real private content in a
committed gold file; also unmeasurable for drift).

## Ruling 2 — the `l2-fact` anchor: `fact_key` + verbatim `fact_sentence` equality + a committed harvest manifest

**Ruling: the anchor is by deterministic identity, not by row id — three checks, all
enforced in the loader, all database-free.** An `l2-fact` pair must carry a `fact_key`
object: `{triple_key, subject_name, rel_type, object_name, project}`. The loader
(`entailment_gold.py`) validates, for every live `l2-fact` pair:

1. **Key self-consistency:** `compute_triple_key(project, subject_name, rel_type,
   object_name) == triple_key` — imported from `app.services.triple_key`, never
   re-implemented (parity-by-import, the same discipline `fact_lift` itself argues
   for).
2. **Verbatim text equality:** `pair["premise"] == fact_sentence(subject_name,
   rel_type, object_name)` — imported from `app.services.fact_lift`. This is the
   direct analogue of the `corpus_key` verbatim-equality check.
3. **Manifest membership:** `triple_key` appears in the committed harvest manifest
   `benchlib/entailment/l2_harvest.json` (Step 1's output). A `fact_key` on a
   non-`l2-fact` pair, or an `l2-fact` pair without one, is refused exactly as
   `corpus_key` is scoped today.

Checks 1–2 alone are satisfiable by anyone willing to *compute* them — `fact_sentence`
is a pure function — so they close accidental drift but not deliberate typing. The
manifest closes the typing hole: it is produced only by the harvest script *from the
bench database after a real lift run*, and it is **reproducible** — warm cache →
byte-identical extraction → identical canonicalisation → identical `triple_key` set —
so T2.41 (or any auditor) re-runs the harvest and diffs the manifest's sorted,
timestamp-free `facts` section byte-for-byte. Forging it requires editing a committed
artifact whose regeneration procedure is one command; that is a deliberate lie with a
one-command detector, which is the strongest posture available without a database
dependency in the test floor.

**The failure mode, named:** the text-equality anchor is brittle against any future
change to `fact_sentence`'s rendering — and that brittleness is the *feature*. If
`fact_sentence` ever changes, every `l2-fact` pair fails loader check 2 loudly, the
suite goes red, and the pairs are re-adjudicated under retire-and-replace — identical
to how corpus drift is handled today. The rejected id-anchor fails the opposite way:
`knowledge_triples.id` values die with every `DROP SCHEMA` on a disposable bench
database, so an id anchor dangles **silently** the week after it is written, verifying
nothing forever after. Silent-verification-of-nothing is the defect class this corpus
exists to prevent; loud brittleness is the correct trade. Drift is caught by the
existing floor: `test_entailment_gold.py` runs the loader over the committed gold on
every `pytest` invocation of the benchlib suite, and a mutation test (Step 2) proves
each of the three checks actually bites.

**Effect on T2.25's pins:** none at anchor-landing time — the anchor lands with
`l2-fact` still 0 and the pinned zeros intact. The pins move only in the same commits
that append `l2-fact` pairs (Step 4), each a visible diff of
`DOCUMENTED_PROVENANCE_COUNTS`, exactly as T2.25's docstring promised ("the first real
harvest … is a visible diff, never a silent relabel"). The `synthesis-draft` pin stays
at zero throughout — T3.02 has not run.

The `--gate` eligibility lock inherits all three checks for free, because it loads the
gold through `load_entailment_gold` — a pair that fails the anchor never reaches the
`l2-fact` count. One enforcement point, two beneficiaries.

## Ruling 3 — how 200+ pairs get labelled credibly, and what the human owner personally does

The circularity to avoid is precise: *the verification judge* (deepseek-v4-flash under
identity `66df91cee44d2415`, or any successor) must contribute nothing to any label.
The protocol below never calls it — no DeepSeek model labels anything, `DEEPSEEK_API_KEY`
is absent from every labelling step's environment (M8 makes this the default), and the
machine check is stated below. Authors and adjudicators are Claude-family Fable-tier
agents: a different model family from the judge under test, doing a different task
(construction under stated rules, and blind three-way labelling against LABELLING.md —
not "ask the judge"). That breaks the tight loop (gold labelled by the model being
graded); the residual loop (gold labelled by *some* model) is closed by construction
anchoring and by the human, as follows.

**Layer 1 — construction determines most labels.** Five of the eight slices admit
exactly one lawful verdict (`SLICE_VERDICTS`): a `value-swap` pair *is* `contradicted`
by construction, a `weakening` pair *is* `entailed`. For those, the label is a
property of the construction the rationale documents, not a judgment call. The
judgment mass concentrates in `temporal`, `direction`, `overreach` — which is exactly
where the edge rulings (window, reversal, exclusive-slot) give a decision procedure to
cite by name.

**Layer 2 — two independent blind passes over every live pair.** A small tool (Step 2)
exports the gold with `verdict`, `rationale` and `slice_tags` stripped. Two Fable
agents, separately dispatched with no access to each other's output or to the recorded
labels, three-way-label every live pair (the 41 legacy pairs included — this is their
LABELLING.md-mandated re-adjudication). Merge rule: both passes agree with the
recorded label → flip `label_source` to `adjudicated`; any disagreement (between
passes, or with the recorded label) → the pair enters the owner's escalation queue
untouched. Both passes' raw agreement rates are recorded in LABELLING.md's history
section. Expected escalation volume: T2.25 measured 41/41 blind agreement; at 241
pairs with a harder mix, plan for 5–20 escalations.

**Layer 3 — the human owner, doing three things, ~1.5 to 2.5 hours in one sitting:**

1. **Adjudicate the escalation queue** (est. 5–20 pairs × ~2 min ≈ 10–40 min). Wrong
   label → retire-and-replace; ambiguous rule → fix LABELLING.md first, then
   re-adjudicate every pair in the affected slice (rule-then-pairs, the order the
   handoff already mandates).
2. **The inter-label consistency resample, as a real measurement:** a seeded,
   slice-stratified random sample of **37 live pairs** (⌈15% × 241⌉ = 37), blind
   (stripped export), three-way labelled by the owner personally. **Bar, stated now,
   before any sample is drawn: agreement ≥ 0.95.** At n=37 that means at most one
   disagreement (36/37 ≈ 0.973 passes; 35/37 ≈ 0.946 fails). The bar is this tight
   because gold noise eats the judge's bar directly: a 5% label-error rate bounds a
   perfect judge's measured precision near 0.95 — the gate bar — so the gold's own
   error budget must sit well inside it. (~45–60 min at ~1.5 min/pair.)
   On failure: classify each disagreement (rule ambiguity vs labelling error), apply
   the rule-then-pairs procedure, then draw a **fresh** seeded sample and repeat. Two
   consecutive failures → stop; see Blockers (B4).
3. **Ratify the stop-and-ask decisions** (S1–S4, below; ~15–30 min, can precede
   execution).

**Judge-blindness, machine-checked, not just promised:** at task end (Step 7),
(a) `benchlib/entailment/cache/` is still empty (M7 baseline), and (b) the run ledger
contains **zero** `judge_qualification_attempt` rows whose `gold_sha256` matches any
committed state of the grown gold file. The attempt counter keys on the gold's bytes,
so the grown gold arriving at T2.41 with `gold_touching_attempts: 0` is the
mechanical proof this task never showed the judge its own exam.

**Rejected alternatives:** owner labels all 241 (the gold standard, but ~6–8 hours of
one human's time against a protocol that concentrates the same assurance into the
disagreement set plus a measured sample; kept available as S3 if the owner prefers);
model-proposed/human-ratified with the human only on disagreements *without* a random
resample (leaves correlated two-pass errors invisible — the resample is what measures
them); single blind pass (no inter-labeller measurement at all, and the Done-when
names one).

## Ruling 4 — composition independence from the judge's known errors, and the fate of the contacted 41

The judge's published defect is reversal-exclusivity over-application (M12). Both
stuffing the set with that boundary and steering around it are contamination. Two
rules, both stated here — before any pair exists — and both verifiable after the fact:

**Rule A — composition is a function of pre-judge data only.** The 200 new pairs'
slice targets are T2.25's slice proportions (fixed 2026-07-30, before the judge
existed) scaled to 200 by largest-remainder rounding, ties broken alphabetically
(content-blind):

| slice | T2.25 | exact ×200/41 | target |
|---|---|---|---|
| verbatim | 4 | 19.51 | 20 |
| paraphrase | 6 | 29.27 | 29 |
| weakening | 5 | 24.39 | 24 |
| temporal | 6 | 29.27 | 29 |
| direction | 5 | 24.39 | 25 |
| overreach | 6 | 29.27 | 29 |
| value-swap | 5 | 24.39 | 24 |
| unrelated | 4 | 19.51 | 20 |
| **sum** | 41 | | **200** |

(197 floors + 3 remainders: verbatim .51, unrelated .51, then the .39 three-way tie →
alphabetically `direction`.) Near-misses 131/200 = 65.5%, matching T2.25's 65.9% —
the majority-of-growth requirement holds without anyone choosing it post-hoc. Within
`direction`, the contradicted/unsupported split is **not quota'd**: it falls out of
the reversal rule applied to each constructed pair, because a quota on exactly the
judge's error boundary would be tuning by another name. Premise assignment is
mechanical: a seeded shuffle (seed committed in the manifest header) of the
(premise × feasible-slice) grid; an author may skip an infeasible assignment only
with a recorded reason in the pair-authoring log, so curation is visible, not silent.
**Verification after the fact:** the declared slice counts diff against this table;
the manifest's seed re-derives the assignment order; the skip log accounts for every
deviation; and this plan file — committed before any pair — is the timestamped
statement of the rule.

**Rule B — the contacted 41 stay live, but the gate must clear on virgin pairs too.**
The 41 were contacted twice by identity `66df91cee44d2415`, whose prompt froze at
fixture-pass and was never edited afterwards — contact without response is not tuning,
so retiring sound, blind-adjudicated, corpus-anchored labels would trade real assurance
for theatre. **But** the likely path to a passing gate is a prompt fix for
reversal-exclusivity, and any such fix is written by someone who has read the 41's
per-pair verdicts — re-measuring the fixed judge on those pairs is fit-to-test for
them specifically. So: the ≥ 200 new pairs are grown as a set **no judge identity has
ever contacted**, and the Tier-2 amendment below binds T2.41 to report every barred
metric on both populations — all live pairs, and the never-contacted subset — with
**the gate verdict required to hold on both**. Stated now, before any number exists.
This is strictly conservative: if the judge is unchanged, both populations are clean;
if it changed, the virgin subset is the one the fix cannot have been fitted to.
**Rejected alternatives:** retiring the 41 (`retired` means *wrong*, and these are
not; it would also silently delete the only human-scale fully-cross-checked core);
excluding contacted pairs only from the metric the fix targeted (unauditably baroque);
a per-pair `contacted_by` field in the gold schema (duplicates what the ledger +
git history already prove — the attempt rows carry `gold_sha256` and identity, and
pair membership per sha is derivable from history).

## The open question, settled — the real-proportion floor

The `>= 1` floor lets a 199-synthetic/1-real set pass mechanically. **Settled, as a
Tier-2 amendment (draft row below): `gate_eligibility` gains a proportion floor —
`l2-fact` pairs must be ≥ 50% of live pairs — and the pinned composition tests
additionally require every slice except `temporal` to carry at least one live
`l2-fact` pair.** Why these numbers, argued from the consumers rather than invented:
production premises for both E2 consumers are ~100% `fact_sentence` texts, so the gold
premise mass should be majority-real; but a 100% floor is wrong because `temporal`
pairs **cannot** be real today — measured fact M10, `fact_lift` never renders a
validity window — and the windowed-premise slice guards the veto's window semantics,
which must stay represented. 50% is the highest round floor that leaves room for the
29 temporal pairs plus the hand-authored mirrors the slice constructions need
(feasibility arithmetic: 121 of 241 = 50.2% required; non-temporal new-pair capacity
171; premise capacity ≥ 4 × 60 = 240 at the expected harvest, ≥ 124 at the worst
acceptable one). The per-slice-representation requirement lives in the pinned tests
(where slice-coverage assertions already live), not in `gate_eligibility` — the lock
stays a small, legible predicate and keeps surfacing raw counts, never a collapsed
boolean. This is a *tightening* of a gate-eligibility condition, elaborating §11's
stated intent — no doc sentence changes, so Tier 2, surfaced for ratification as S2
rather than escalated as Tier 3.
