## Ruling 1 — where 200 real `l2-fact` premises come from, and whether bench-lifted facts are "real"

governing text is now doc 17 §11's clause *"What 'real' means, ruled 2026-07-31"*
(landed in `2034d2a`), which this plan cites and does not restate:** "real" governs
the **premise distribution, not the authorship or the database of origin** — a
`claim-fact` premise is real when minted by the production code path (extraction →
`fact_lift` → `fact_sentence`) and byte-anchored to the `knowledge_triples` row that
produced it, whatever corpus was ingested. Bench-lifted facts qualify; hand-authored
premises do not, however faithfully they imitate the shape. The owner weighed the
production-snapshot route explicitly and **declined it** (private memory content
committed permanently into a repo contemplating publication — git history survives
any later removal). The clause also states what the ruling does *not* license — a
hand-authored premise self-declaring `provenance: l2-fact` — so Ruling 2's anchor
work is unchanged and remains the enforcement of the clause's own terms.

Operationally: premises are harvested from `knowledge_triples` rows minted by the
shipping `fact_lift` over the **bench corpus** ingested into an assigned bench
database. The measured chain: ~73 distinct triples in the warm extraction cache
(M6) → an expected 60–75 open facts after one lift pass at the default salience bar
of 1 → each premise supporting up to 4 pairs (cap, below) → capacity ≥ 240 `l2-fact`
pairs against an authoring target of 130.

*The argument below is retained as the escalation record — what was weighed and why —

## Ruling 2 — the `l2-fact` anchor: `fact_key`, byte-equality to the minted fact, and a committed harvest manifest

**Ruling: the anchor is by deterministic identity, not by row id — three checks, all
enforced in the loader, all database-free.** An `l2-fact` pair must carry a `fact_key`
object: `{triple_key, subject_name, rel_type, object_name, project}`. The loader
(`entailment_gold.py`) validates, for every live `l2-fact` pair:

1. **Manifest resolution, manifest as source of truth:** the pair's `triple_key`
   resolves to exactly one row in the committed harvest manifest
   `benchlib/entailment/l2_harvest.json` (Step 1's output), and the pair's
   `fact_key` fields (`subject_name`, `rel_type`, `object_name`, `project`)
   byte-equal that row's stored fields. The pair never gets to self-supply the
   authoritative values — the manifest row is what `fact_lift` actually minted.
2. **Verbatim premise binding, in bytes:** `pair["premise"] ==
   manifest_row["fact"]`. Byte equality against the *minted* text, not against a
   recomputation from the pair's own fields — a recomputation would accept
   `"Darkmem stores memories"` for a fact minted as `"darkmem stores memories"`,
   because `compute_triple_key` canonicalises names before hashing while
   `fact_sentence` lowercases only the predicate, so cased fields can pass a
   key-plus-recompute check with a premise `fact_lift` never produced. This is the
   direct analogue of the `corpus_key` verbatim-equality check.
3. **Manifest self-consistency, validated once per load:** for every manifest row,
   `compute_triple_key(project, subject_name, rel_type, object_name) ==
   triple_key` and `fact_sentence(subject_name, rel_type, object_name) == fact` —
   both imported from `app.services`, never re-implemented (parity-by-import, the
   same discipline `fact_lift` itself argues for). This pins the manifest to the
   shipping identity and rendering functions, so drift in either fails the floor
   loudly.

A `fact_key` on a non-`l2-fact` pair, or an `l2-fact` pair without one, is refused
exactly as `corpus_key` is scoped today. Checks 1–3 close accidental drift; the
typing hole — someone hand-writing a plausible manifest row — is closed by the
manifest being **reproducible**: warm cache → byte-identical extraction → identical
canonicalisation → identical `triple_key` set, so re-running the harvest and diffing
the manifest's sorted, timestamp-free `facts` section byte-for-byte detects a forged
row in one command. **That detector only exists if someone is obliged to run it**, so
it is bound in twice: Step 1's test runs the harvest twice in-process and asserts the
two `facts` sections byte-identical, and the T2.41 amendment row below makes the
re-harvest-and-diff a mandatory part of `--gate` evidence. Forging the manifest then
requires a deliberate lie against a scheduled one-command detector — the strongest
posture available without a database dependency in the test floor.

**A deliberate divergence, named:** `l2-fact` anchors are validated *inline* in
`load_entailment_gold` (the manifest is a required committed sibling in
`entailment/`, so the loader can read it directly and the floor inherits the check on
every run), while corpus-derived pairs keep the separate
`validate_gold_against_corpus` cross-file path — the retrieval corpus belongs to
another subsystem and stays an explicitly-invoked cross-file validation. Two
mechanisms, one per artifact ownership boundary; collapsing them would couple the
loader to a file another lane owns.

**The failure mode, named:** the text-equality anchor is brittle against any future
change to `fact_sentence`'s rendering — and that brittleness is the *feature*. If
`fact_sentence` ever changes, every `l2-fact` pair fails loader check 2 loudly, the
suite goes red, and the pairs are re-adjudicated under retire-and-replace — identical
to how corpus drift is handled today. The rejected id-anchor fails the opposite way:
`knowledge_triples.id` values die with every `DROP SCHEMA` on a disposable bench
database, so an id anchor dangles **silently** the week after it is written, verifying
nothing forever after. Silent-verification-of-nothing is the defect class this corpus
exists to prevent; loud brittleness is the correct trade. Drift is caught by the
existing floor: `test_entailment_gold.py` runs the loader over the committed gold on
every `pytest` invocation of the benchlib suite, and a mutation test (Step 2) proves
each of the three checks actually bites.

**Effect on T2.25's pins:** none at anchor-landing time — the anchor lands with
`l2-fact` still 0 and the pinned zeros intact. The pins move only in the same commits
that append `l2-fact` pairs (Step 4), each a visible diff of
`DOCUMENTED_PROVENANCE_COUNTS`, exactly as T2.25's docstring promised ("the first real
harvest … is a visible diff, never a silent relabel"). The `synthesis-draft` pin stays
at zero throughout — T3.02 has not run.

The `--gate` eligibility lock inherits all three checks for free, because it loads the
gold through `load_entailment_gold` — a pair that fails the anchor never reaches the
`l2-fact` count. One enforcement point, two beneficiaries.

## Ruling 3 — how 200+ pairs get labelled credibly, and what the human owner personally does

The circularity to avoid is precise: *the verification judge* (deepseek-v4-flash under
identity `66df91cee44d2415`, or any successor) must contribute nothing to any label.
The protocol below never calls it — no DeepSeek model labels anything, `DEEPSEEK_API_KEY`
is absent from every labelling step's environment (M8 makes this the default), and the
machine check is stated below. Authors and adjudicators are Claude-family Fable-tier
agents: a different model family from the judge under test, doing a different task
(construction under stated rules, and blind three-way labelling against LABELLING.md —
not "ask the judge"). That breaks the tight loop (gold labelled by the model being
graded); the residual loop (gold labelled by *some* model) is closed by construction
anchoring and by the human, as follows.

**Layer 1 — construction determines most labels.** Five of the eight slices admit
exactly one lawful verdict (`SLICE_VERDICTS`): a `value-swap` pair *is* `contradicted`
by construction, a `weakening` pair *is* `entailed`. For those, the label is a
property of the construction the rationale documents, not a judgment call. The
judgment mass concentrates in `temporal`, `direction`, `overreach` — which is exactly
where the edge rulings (window, reversal, exclusive-slot) give a decision procedure to
cite by name.

**Layer 2 — two independent blind passes over every live pair.** A small tool (Step 2)
exports the gold with `verdict`, `rationale` and `slice_tags` stripped. Two Fable
agents, separately dispatched with no access to each other's output or to the recorded
labels, three-way-label every live pair (the 41 legacy pairs included — this is their
LABELLING.md-mandated re-adjudication). Merge rule: both passes agree with the
recorded label → flip `label_source` to `adjudicated`; any disagreement (between
passes, or with the recorded label) → the pair enters the owner's escalation queue
untouched. Both passes' raw agreement rates are recorded in LABELLING.md's history
section. Expected escalation volume: T2.25 measured 41/41 blind agreement; at 241
pairs with a harder mix, plan for 5–20 escalations.

**Layer 3 — the human owner, doing three things, ~3 to 3.5 hours in one sitting
(S4, accepted 2026-07-31):**

1. **Adjudicate the escalation queue** (est. 5–20 pairs × ~2 min ≈ 10–40 min). Wrong
   label → retire-and-replace; ambiguous rule → fix LABELLING.md first, then
   re-adjudicate every pair in the affected slice (rule-then-pairs, the order the
   handoff already mandates). Replacement pairs go through the same Step-5 blind
   adjudication as everything else, and **the resample is drawn only after all
   replacements have settled** — sampling a still-moving set measures nothing.
2. **The inter-label consistency resample, as a real measurement with honest power —
   design ratified by the owner 2026-07-31 (S3): n = 93 with a bar of at most 1
   disagreement.** The arithmetic: if the true label-error rate were 5%, P(≤ 1 error
   in 93) = 0.95^93 + 93·0.05·0.95^92 ≈ 0.050 — so a pass certifies the error rate
   below 5% at ~95% confidence, which is what "the gold's noise sits inside the
   judge's 0.95 bar" actually requires; the owner accepted the extra ~1–1.5 h over
   the 15%-letter minimum deliberately, on exactly that reasoning. Blind (stripped
   export), seeded, three-way labelled by the owner personally. Stratification is by
   **gold verdict class**, stated now and content-blind: a full census of
   gold-`contradicted` pairs first, then gold-`unsupported`, remainder
   gold-`entailed` proportionally — because the failing bar (contradiction
   precision) is damaged exactly by errors in those two classes. (~2–2.5 h at
   ~1.5 min/pair.)
   On failure: classify each disagreement (rule ambiguity vs labelling error), apply
   the rule-then-pairs procedure, then draw a **fresh** seeded sample and repeat.
   Two consecutive failures → stop; see Blockers (B4).
3. ~~Decide the stop-and-ask items~~ — **already done**: S1–S4 were all decided
   2026-07-31 (see the decision record below), so the sitting reduces to items 1
   and 2.

**Judge-blindness — an in-lane tripwire plus procedural evidence, stated at its real
strength.** The Step-7 machine check — `benchlib/entailment/cache/` still empty (M7
baseline) and zero `judge_qualification_attempt` rows in **this checkout's** ledger
matching any committed grown-gold sha — proves only that *this lane's* processes made
no counted gold contact: both substrates are gitignored and per-checkout, so a fresh
clone reads 0 regardless of history, and `qualification_probe` is an ungated door
that writes no attempt row. The controls that actually carry the weight are
procedural, and they are made auditable rather than asserted: `DEEPSEEK_API_KEY` is
exported **only inside Step 1's harvest process** (whose calls are
extraction/classification, never the `verification` purpose) and every other step's
dispatch runs keyless; the Step 4/5/6 dispatch briefs are **committed** under
`.superpowers/sdd/T2.54-entailment-gold-labelling/`, so what every author and
labeller had in context is on the record (see also Rule A's brief-content rule); and
the grown gold reaching T2.41 with `gold_touching_attempts: 0` in the shared ledger
remains a necessary condition even though it is not a sufficient one.

**Rejected alternatives:** **n = 37 at ≤ 1 disagreement** (⌈15% × 241⌉, the
Done-when's letter — decided against by the owner 2026-07-31: a gold with a true 5%
label-error rate passes it **44%** of the time and a pass certifies only < 12.2%
error at 95% confidence, so it cannot hold the error budget inside the judge's 0.95
bar; recorded here so a later reader does not take the cheaper path without
re-deciding); owner labels all 241 (the gold standard, but ~6–8 hours of one human's
time against a protocol that concentrates the same assurance into the disagreement
set plus a measured sample); model-proposed/human-ratified with the human only on
disagreements *without* a random resample (leaves correlated two-pass errors
invisible — the resample is what bounds them, which is why its size is 93, not 37);
single blind pass (no inter-labeller measurement at all, and the Done-when names
one).

## Ruling 4 — composition independence from the judge's known errors, and the fate of the contacted 41

The judge's published defect is reversal-exclusivity over-application (M12). Both
stuffing the set with that boundary and steering around it are contamination. Two
rules, both stated here — before any pair exists — and both verifiable after the fact:

**Rule A — composition is a function of pre-judge data only.** The 200 new pairs'
slice targets are T2.25's slice proportions (fixed 2026-07-30, before the judge
existed) scaled to 200 by largest-remainder rounding, ties broken alphabetically
(content-blind):

| slice | T2.25 | exact ×200/41 | target |
|---|---|---|---|
| verbatim | 4 | 19.51 | 20 |
| paraphrase | 6 | 29.27 | 29 |
| weakening | 5 | 24.39 | 24 |
| temporal | 6 | 29.27 | 29 |
| direction | 5 | 24.39 | 25 |
| overreach | 6 | 29.27 | 29 |
| value-swap | 5 | 24.39 | 24 |
| unrelated | 4 | 19.51 | 20 |
| **sum** | 41 | | **200** |

(197 floors + 3 remainders: verbatim .51, unrelated .51, then the .39 three-way tie →
alphabetically `direction`.) Near-misses 131/200 = 65.5%, matching T2.25's 65.9% —
the majority-of-growth requirement holds without anyone choosing it post-hoc. Within
`direction`, the contradicted/unsupported split is **not quota'd and not judged at
authoring time either**: Step 3 pre-classifies every member of the closed
`RELATIONSHIP_TYPES` table as reversal-exclusive or not in LABELLING.md — a
per-relation semantic fact, decidable from the relation's meaning alone, before any
pair exists — so a `direction` pair's verdict falls out mechanically from which
relation the seeded assignment handed its author. A quota, or a per-pair judgment
call, on exactly the judge's error boundary would be tuning by another name.
Premise assignment is mechanical: a seeded shuffle (seed committed in the manifest
header) of the (premise × feasible-slice) grid; an author may skip an infeasible
assignment only with a recorded reason in the pair-authoring log, so curation is
visible, not silent.

**Freezing counts is not enough — content exposure is controlled too.** Nothing in a
count table stops an author or blind labeller from *carrying the judge's error
analysis in context* and steering pair content at the boundary. So the Step 4, 5 and
6 dispatch briefs contain **exactly**: LABELLING.md, the harvest manifest, the target
table, and the assignment procedure — and **must not contain** M12, T2.26's eval
report (`docs/eval/2026-07-31-judge-qualification.md`), this plan, or any description
of what any judge gets wrong. The briefs are committed (Ruling 3), so compliance is
checkable by reading them, not by trusting this sentence.

**Verification after the fact:** the declared slice counts diff against this table;
the manifest's seed re-derives the assignment order; the skip log accounts for every
deviation; the committed briefs show what every author saw; and this plan file —
committed before any pair — is the timestamped statement of the rule.

**Rule B — the contacted 41 stay live, but the gate must clear on virgin pairs too.**
The 41 were contacted twice by identity `66df91cee44d2415`, whose prompt froze at
fixture-pass and was never edited afterwards — contact without response is not tuning,
so retiring sound, blind-adjudicated, corpus-anchored labels would trade real assurance
for theatre. **But** the likely path to a passing gate is a prompt fix for
reversal-exclusivity, and any such fix is written by someone who has read the 41's
per-pair verdicts — re-measuring the fixed judge on those pairs is fit-to-test for
them specifically. So: the ≥ 200 new pairs are grown as a set **no judge identity has
ever contacted**, and the Tier-2 amendment below binds T2.41 to report every barred
metric on both populations — all live pairs, and the never-contacted subset — with
**the gate verdict required to hold on both**. Stated now, before any number exists.
This is strictly conservative: if the judge is unchanged, both populations are clean;
if it changed, the virgin subset is the one the fix cannot have been fitted to.
**Rejected alternatives:** retiring the 41 (`retired` means *wrong*, and these are
not; it would also silently delete the only human-scale fully-cross-checked core);
excluding contacted pairs only from the metric the fix targeted (unauditably baroque);
a per-pair `contacted_by` field in the gold schema (duplicates what the ledger +
git history already prove — the attempt rows carry `gold_sha256` and identity, and

17 §11's new clause states the requirement itself): `gate_eligibility` gains a
proportion floor — `l2-fact` pairs must be ≥ 50% of live pairs — and the pinned
composition tests additionally require every slice except `temporal` to carry at
least one live `l2-fact` pair.** Why these numbers, argued from the consumers rather than invented:
production premises for both E2 consumers are ~100% `fact_sentence` texts, so the gold
premise mass should be majority-real; but a 100% floor is wrong because `temporal`
pairs **cannot** be real today — measured fact M10, `fact_lift` never renders a
validity window — and the windowed-premise slice guards the veto's window semantics,
which must stay represented. 50% is the highest round floor that leaves room for the
29 temporal pairs plus the hand-authored mirrors the slice constructions need.
**The authoring target is ≥ 130 `l2-fact` pairs (53.9%), deliberately above the 121
the floor arithmetically requires**: at exactly 121/241, retiring just two `l2-fact`
pairs leaves 119/239 = 49.8% and strands gate eligibility on a routine
retire-and-replace; at 130, up to 19 `l2-fact` retirements survive the floor.
Feasibility: non-temporal new-pair capacity 171 ≥ 130; premise capacity ≥ 4 × 60 =
240 at the expected harvest, and the worst acceptable harvest is **33 premises**
(⌈130/4⌉ = 33 → capacity 132). The per-slice-representation requirement lives in the
pinned tests (where slice-coverage assertions already live), not in
`gate_eligibility` — the lock stays a small, legible predicate and keeps surfacing
raw counts, never a collapsed boolean.

**The temporal exemption carries a sunset trigger and a disclosure.** Trigger: the
moment any producer renders validity windows into fact text (a `fact_sentence`
change, or doc 08 §3.2's window passes becoming reachable from a temporally-qualified
Layer 1), the exemption is re-argued — and mechanically cannot be missed, because the
loader's manifest self-consistency check pins `fact_sentence`'s rendering and fails
the floor loudly on exactly that change. Disclosure, owed to T2.41: `temporal`'s
windowed hand-authored premises are unrepresentative of *today's* production premise
distribution (production holds no windowed facts), on a slice where the judge already
erred (5/6, M12). They are retained anyway, on purpose: the veto's half-open window
semantics are contract, and the gold must guard them for the day windowed facts
exist — but the gate report must carry this caveat rather than let the slice read as
production-representative.

This floor was a *tightening* of a gate-eligibility condition, elaborating §11's
stated intent — Tier 2, and the reviewer concurred with that tiering. It is now
ratified and carried by §11's own clause ("≥ 50% of live pairs per variant must
carry such premises … a `199 synthetic / 1 real` set must not pass"), so Step 2
implements settled corpus text, not a plan proposal.
