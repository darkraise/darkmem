## 2. The interface T1.34 already fixed — quoted verbatim (Ruling 1)

T1.34's report (`scratchpad/reports/T1.34-report.md`, "Ruling 4 — the interface T1.42a must
honour") specified this task's terminal seam before this task was planned. It is quoted here
in full because an executing agent must build the chain **into** it, not beside it.

> **This is the section T1.42a's plan needs.** The chain resolves *precedence*; this slot
> resolves *meaning*. The seam between them is two functions in
> `backend/app/services/rank_fusion.py`:
>
> ```python
> declared_context_from_wire(
>     raw: Mapping[str, object] | None,
>     provenance: ContextProvenance = ContextProvenance.HUMAN,
> ) -> DeclaredContext | None
>
> row_context_from_applies_when(
>     applies_when: Mapping[str, object] | None,
>     provenance: ContextProvenance = ContextProvenance.HUMAN,
> ) -> RowContext | None
> ```
>
> What T1.42a owes this slot:
>
> 1. **Run doc 12 §5's precedence and hand over the winner only.** Per-call `context` arg >
>    `X-Darkmem-Context` header > `projects.properties.applies_when_default` > nothing. Pass
>    the winning raw mapping to `declared_context_from_wire`; pass **nothing declared** as
>    `None` or `{}`, both of which return `None`.
> 2. **`None` is the only representation of "undeclared".** `DeclaredContext({})` raises
>    `ValueError`. There is deliberately no vacuous declared context, because one would be
>    indistinguishable from no declaration while still being a live object — the exact way an
>    undeclared context starts rendering as a default (T1.65). A declaration that is
>    *declared and matched nothing* is a real `DeclaredContext` on
>    `ContextComposition.declared` with every row `neutral`; the two states are different
>    facts about the request and the envelope carries which one happened.
> 3. **`DeclaredContext` has no `project` field and `project` is not a context axis.** The
>    isolation boundary and the context hint are different axes; the project scope must not be
>    fed in as a context. Pinned by `test_a_declared_context_is_not_the_project_scope`.
> 4. **Carry the `provenance: human|llm_guessed` marker per row.** An LLM-guessed row
>    `applies_when` is displayed provenance only — it never boosts and never excludes (doc 01
>    §3.4), which this slot enforces, not the caller.
> 5. **Axes.** `env`, `version`, `situation`. Values are normalised (`strip().lower()`) at
>    the seam; unknown axes are preserved on the label but ignored by matching. Closed-vocabulary
>    normalisation of `env`/`situation` remains doc 06's discipline and is *not* implemented
>    here — a later task owns it, and this slot will inherit it for free because it compares
>    normalised strings.

And its composition API, for the E2/E3 task that eventually consumes what this chain
produces:

> ```python
> partition_by_context(rows, declared, row_contexts, weights) -> ContextComposition
>     # step 2: stamps every row, drops conflicts, tallies excluded_by_context_conflict
> apply_context_boost(rows, *, preserve_order=False) -> list[dict]
>     # step 4: multiplies rrf_score (or score) by each row's stamped boost
> ```

T1.34 additionally ruled that **only `env` and `situation` can produce a conflict, while a
`version` difference is neutral** — both doc 07 §6 and doc 12 §5 treat `version` as a free
string compared app-side, and `15` vs `15.3` must not silently delete the right answer. That
is `CONFLICT_AXES = frozenset({"env", "situation"})` at `rank_fusion.py:196`. **T1.42a must
not re-derive, re-normalise, or re-validate any of this.** The chain's only output is the
winning raw mapping and which tier produced it; `declared_context_from_wire` owns everything
after that.

### The two consequences of quoting this that a step must actually enforce

- **`None`, never `{}`, never a default.** The wire echo of an undeclared context is
  `null`. Not an empty object, not the project name, not `{"env": null}`. Step 12 pins this
  three ways, because it is the single thing T1.65 is built to guard.
- **`project` is not an axis.** The chain reads `project` (to look up the tier-3 default) but
  must never *emit* it into the declaration it hands over. Step 11 pins this with a test that
  fails if `project` reaches `declared_context_from_wire`'s `raw`.

## 3. The relationship to T1.33's envelope: **extend, do not wrap and do not replace** (Ruling 5)

"One envelope shape across every surface" is the first Done-when box, and T1.33 landed a
working envelope four commits ago. Two envelopes would violate the box on day one, so the
relationship must be stated, not left to the implementer.

**Decision: T1.33's `RetrievalEnvelope` becomes the retrieval *specialisation* of one shared
base, by subclassing. It is neither wrapped nor replaced.**

```
app/schemas/envelope.py          (new, this task)
    PageInfo             {limit, offset, total, next_offset|null}
    ContextEcho          {declared: {axes…}|null, declared_by: "arg"|"header"|"project_default"|null,
                          provenance: "human"}
    ResponseEnvelope     {schema_version: int, partial: bool, excluded: dict[str,int],
                          page: PageInfo|null, context: ContextEcho|null}

app/schemas/retrieval_trace.py   (existing, T1.33 — gains a base class, loses nothing)
    RetrievalEnvelope(ResponseEnvelope)  {query, channels, reranked, weights}
    MemoryResultTrace                    unchanged
```

Why this and not the alternatives:

- **Wrapping** (`{"envelope": {...}, "retrieval": RetrievalEnvelope}`) would produce exactly
  the two-envelope outcome Ruling 5 forbids, and would break `PaginatedMemoryResponse`'s
  `envelope` field that T1.33 just shipped and T1.44/T1.61 read.
- **Replacing** would delete a tested, shipped contract to re-land it under a new name, for
  no behavioural gain, on the exact request path E1's honesty gate measures.
- **Subclassing** means there is literally one class defining `excluded`, `partial`, `page`
  and `schema_version`. `PaginatedMemoryResponse.envelope: RetrievalEnvelope | None` keeps
  validating; the field simply gains the inherited keys. Step 2 adds a drift test that fails
  if a second class ever declares `excluded` or `partial` independently.

**Two sub-decisions this forces, both stated now so no step guesses:**

1. **`excluded` keys stay an open `dict[str, int]` keyed by reason name, not doc 12 §4's
   fixed `{by_project, by_status, by_context_conflict}` triple.** T1.33 already logged this as
   a Tier-2 amendment: the real key set today is filter-name-shaped
   (`memory_type`, `source`, `technologies`, `tags`, `not_found`) because the T1.29-series
   pushdown scopes project/status in SQL, so a foreign row is never fetched to be counted, and
   `by_context_conflict` has no implementation because the four-layer composition does not
   exist. **T1.42a inherits that ruling and does not reserve decorative always-zero keys** —
   an always-zero honesty counter is worse than an absent one, because it reads as evidence.
   See §8, Tier-3 candidate 1: the doc and the tree disagree and the executing agent must not
   resolve it silently.
2. **`page` is added to the envelope while `PaginatedMemoryResponse`'s existing top-level
   `total`/`limit`/`offset` stay.** Retiring the trio is a breaking change to a shape the
   frontend reads; it belongs to **T1.42b** ("pagination and error shapes are uniform"), after
   T1.58 binds. Step 4 lands `page` and a test asserting the two agree, so the retirement is a
   deletion rather than a re-derivation.

## 5. Defects and gaps found by reading the code

Five. Each becomes a step or an open question.

### 5.1 The REST door never resolves `source`, and `MemoryCreate` erases the evidence

`routes/memories.py:73-76` and `:209-215` resolve `origin_key` and `project` and nothing
else. `MemoryCreate.source: str = "api"` (`schemas/memory.py:48`) means a caller who omits
`source` and a caller who explicitly sends `"api"` are indistinguishable by the time the
route body runs. That is the same defect the task's own text names for `memory_batch_add`,
present on two REST paths, un-mitigated.

Note that `origin_key` resolution consumes `source` (`resolve_origin_key(..., source=…)`), so
today every REST-captured memory's `origin_key` is `unknown:api:<project>` regardless of the
`X-Darkmem-Client` header the caller sent. Fixing the source chain therefore **changes
`origin_key` values on the REST door** — not because `origin_key`'s own logic changed, but
because its input did. Step 7 pins this as intended and Step 6 proves the resolver itself is
untouched. This is the single most important thing for a reviewer to check.

### 5.2 There is no error envelope, and `apiFetch` depends on the current one

`app/main.py` registers no exception handlers. FastAPI returns `{"detail": "..."}` for
`HTTPException` and `{"detail": [ {...}, ... ]}` for a 422. `frontend/src/lib/api.ts:41-47`
reads `error.detail` and interpolates it into `new Error(...)` — so a 422 today produces an
error message that is a stringified array. Any error-envelope change must keep `detail`
populated with a string until T1.58/T1.42b bind the frontend, or it silently degrades every
error message in the UI.

### 5.3 The two doors return different memory rows

`app/utils/serialization.py:memory_to_dict` (MCP) emits 15 keys. `MemoryResponse` (REST)
emits 22. Missing from the MCP row: **`project`, `status`, `superseded_by`, `technologies`,
`confidence`, `related_memories`, `trace`**. `project` and `status` are the isolation and
lifecycle labels; doc 12 §4 requires a lifecycle label on every memory row and doc 07 §7
requires a `superseded`/`deprecated` row to be labelled and reachable through
`superseded_by`. An MCP agent today cannot tell an active memory from a superseded one.

This predates T1.42a and is a live invariant-14 hole on the unauthenticated door. It is
in scope: "one envelope shape across every surface" is meaningless if the rows inside differ.

### 5.4 The MCP degradation envelope exists on exactly one tool

`code_search` returns `{"status": "unavailable", "reason": …, "results": []}`
(`api/mcp/server.py:447`). Doc 12 §3 generalises this to the whole surface: caller error
raises, recoverable unavailability returns a typed shape. No other tool implements it. The
memory tools raise `ValueError` for not-found (correct) and have no degradation path at all
(the embedder being unconfigured surfaces as an exception).

### 5.5 The `projects` table has no reader, no writer, and no model

`0001_baseline.py:306` creates `projects(name, display_name, properties jsonb, created_at)`.
Nothing in `backend/app` selects from it or inserts into it, and there is no ORM model. Tier 3
of the context chain — `projects.properties.applies_when_default` — is therefore structurally
present and permanently empty. Step 12 lands the read side and a test proving an absent row
yields `None`; the writer is a gap for another task (§8, Tier-2 item 1).

### Step 3 — `partial` is derived from `channels`, never assigned

**Changes.** `ResponseEnvelope.partial` becomes a computed value, not a settable field: on
`RetrievalEnvelope` it is `any(c.failed for c in channels.values())`; on a bare
`ResponseEnvelope` (a surface with no channels) it is `False`. Implement as a Pydantic
computed field so no constructor can set it to a value contradicting the channels.

**Test proves.** A `RetrievalEnvelope` with `semantic: ChannelStatus(ran=True, failed=True)`
reports `partial=True`; an attempt to construct one with `partial=False` alongside a failed
channel either raises or is ignored — assert which. Pair with an assertion against the
existing `tests/test_hybrid_search_degradation.py` behaviour so a one-sided channel failure
is now visibly partial on the wire.

**Invariant.** Invariant 14 (honest partial results). The failure mode this closes is a
degraded result rendering as complete. Break-it check: make `partial` a plain `bool = False`
field, watch the test fail, restore.

**Depends.** 2. **Parallel:** no.

### Step 5 — The error envelope, on both doors

**Changes.**
- `app/schemas/envelope.py` gains `ErrorEnvelope{schema_version, error: {code, message,

- `app/main.py` registers three handlers: `HTTPException`, `RequestValidationError`, and a
  catch-all `Exception` handler that returns a 500 in the same shape without leaking the

- `detail` is a **string mirror** of `error.message` on every shape, including the 422 —
  which today emits a list into a field `frontend/src/lib/api.ts:44` interpolates as a

- MCP: generalise §5.4's degradation shape into `{"schema_version", "status": "unavailable",

  **Caller error still raises** (doc 12 §3) — a bad UUID or a not-found id is not a

**Test proves.** Every 4xx and 5xx from `/api/v1/memories/*` carries `error.code`,
`error.message` and a string `detail`; a 422 from a malformed body does too; the catch-all

**Invariant.** Done-when 1's "**including error shapes**" clause — the one most easily
under-scoped to success responses.

**Depends.** 2. **Parallel:** yes, with step 4.

### Step 6 — Make `resolve_client_source` door-agnostic — the shared-resolution-code step

**Ruling 3 applies to this step and step 7. Read them together.**

**Changes.** `client_identity.py` is refactored so resolution takes a headers mapping rather
than only an MCP `ctx`:

```python
def resolve_client_source(explicit_source, ctx=None, *, headers=None, fallback=FALLBACK_SOURCE) -> str
def resolve_source_agent(explicit_agent, ctx=None, *, headers=None) -> str | None
```

`_request_from_ctx(ctx)` still supplies the headers when `ctx` is given, so **every existing
MCP call site keeps working unchanged**. `fallback` generalises the sentinel: an explicit
value equal to the door's own fallback counts as *unspecified*, which is the live
`explicit != FALLBACK_SOURCE` rule with the constant parameterised.

**`resolve_origin_key` is not touched.** Not its signature, not its body, not its docstring.

**Test proves.**
- `tests/test_client_identity.py`'s existing 17 tests pass **unmodified** — this is the
  regression proof for the refactor.
- New: the same header/UA/fallback ladder resolves identically whether driven by `ctx` or by
  a bare `headers` dict.
- New: `fallback="api"` makes an explicit `"api"` count as unspecified while an explicit
  `"mcp"` wins, and vice versa — the sentinel really is per-door.
- **`origin_key` guards (Ruling 3):** `tests/test_origin_key.py` runs unmodified; plus an
  assertion in `test_envelope.py` that `inspect.signature(resolve_origin_key)` is unchanged,
  and that two successive calls with no declared origin and identical `(source, project)`
  return the **same** string — the per-request-random prohibition (doc 05 §12), re-asserted at
  the exact moment the neighbouring function is being edited.

**Invariant.** `origin_key`'s merge-to-one fallback. A per-request random here would
counterfeit independence and make every E2 corroboration count a fiction.

**Depends.** 1. **Parallel:** yes, with steps 11–12, after step 2.

### Step 7 — `MemoryCreate.source` becomes `str | None = None`; the door owns the fallback

**Changes.** `schemas/memory.py:48`: `source: str | None = None`. The default moves to the
two REST doors (`"api"`) and the two MCP doors (`"mcp"`), applied by
`resolve_client_source(..., fallback=…)`. This deletes the erasure at its root rather than
working around it, which is why the MCP batch path's raw-dict discipline can stay as
belt-and-braces instead of being the only defence.

Feasibility checked: `memories.source` is `VARCHAR(100) NOT NULL`
(`0001_baseline.py:137`), but nothing constructs a `MemoryCreate` without an explicit
`source` except the two front doors, and `buffer_flush.py:564` already writes
`row.source or "api"`. `services/memory.py:123,207` pass `data.source` straight through, so
the doors must resolve before calling the service — which they will.

**Test proves.**
- `MemoryCreate(content="x").source is None` — absent is representable.
- A memory created through each door with no `source` and no headers lands `"api"` (REST) /
  `"mcp"` (MCP) in the database.
- **Ordering guard:** the door resolves `source` **before** `origin_key`, so
  `resolve_origin_key(source=…)` never receives `None`. Asserted by checking no stored
  `origin_key` contains the substring `"None"` and that a REST capture with
  `X-Darkmem-Client: dashboard` gets `origin_key == "unknown:dashboard:<project>"`, not
  `unknown:api:<project>`.
- **Recorded behaviour change:** REST-door `origin_key` values now reflect the resolved
  source. `origin_key`'s own logic is unchanged (step 6's signature and determinism
  assertions); its *input* is now correct. Log as a Tier-2 amendment.

**Invariant.** The absent-vs-explicit distinction, structurally.

### Step 10 — The pre-validation proof: a test that fails if resolution is post-hoc (Ruling 2)

**This step writes no production code. It exists because "a test that would fail post-hoc" is
a stronger requirement than "a test that passes", and a step that bundles it with the
implementation will produce the weaker one.**

**The discriminator.** A test asserting "an omitted `source` picks up the header" passes under
a post-hoc implementation too, because both an omitted `source` and an explicitly-`"api"`
`source` arrive at the route as the string `"api"`. The discriminating case is **both in one
batch**:

| Entry | Header `X-Darkmem-Client: dashboard` | Correct (pre-validation) | Post-hoc (reads `validated.entries[i].source`) |
|---|---|---|---|
| `{"content": "a"}` | present | `dashboard` | `dashboard` |
| `{"content": "b", "source": "api"}` | present | **`api`** | `dashboard` |

A post-hoc implementation cannot produce different answers for the two, because validation has
already made them identical. On the MCP door the same table holds with `"mcp"` in place of
`"api"`, which is the sentinel rule already recorded in `CLAUDE.md`.

**Changes.** Two tests in `tests/test_envelope.py`, one per door, asserting the "Correct"
column. Plus the mutation procedure, executed and its output recorded in the completion
report:

1. Replace the raw-dict loop with `entry.source`-based resolution after
   `MemoryBatchCreate(...)`.
2. Run the two tests. **They must fail.** Record the failure output.
3. Restore. Run again. Record the pass.

**Known limitation to state in the test's docstring, not to hide.** One post-hoc form
*would* survive this test: resolving from `entry.model_fields_set` after validation, since
Pydantic records which fields the caller actually supplied. The raw-dict form is still the
contract because (a) the MCP tool signature is `entries: list[dict]` — there is no model to
interrogate before `MemoryBatchCreate` builds one, and (b) `model_fields_set` is a Pydantic
implementation detail that a later schema change (a `default_factory`, a model validator
that assigns `source`) silently breaks, whereas the raw dict is what the caller actually
sent. Say this in the docstring so a reviewer meets it as a known alternative rather than as
a hole.

### Step 11 — The context resolution chain

**Changes.** New `backend/app/api/context_resolution.py`:

```python
DECLARED_CONTEXT_HEADER = "x-darkmem-context"

def resolve_declared_context(
    explicit: Mapping[str, object] | None,
    *,
    headers: Mapping[str, str] | None = None,
    project_default: Mapping[str, object] | None = None,
) -> tuple[DeclaredContext | None, str | None]
```

Returns the `DeclaredContext | None` from `declared_context_from_wire` **and** which tier won
(`"arg"` / `"header"` / `"project_default"` / `None`), because "nothing declared" and
"declared and matched nothing" are different facts the envelope must be able to state
(§2, quoted point 2).

Rules:
- Precedence is doc 12 §5's exactly: arg > header > project default > nothing. A tier that
  yields an empty mapping falls through to the next; a tier that yields a non-empty mapping
  wins outright and lower tiers are **not** merged into it.
- The header value is a **compact JSON object** (`{"env":"prod","version":"15"}`). See §7,
  Open question 2 — doc 12 §5 names the header but never fixes its encoding.
- A malformed header is **ignored, logged at debug, and falls through** — never raises.
  Resolution must not fail a read, the same rule `resolve_client_source` follows.
- The chain never emits `project` into the mapping it hands over, even though it reads
  `project` to find the tier-3 default.

**Test proves.** All four tiers in precedence order; a tier yielding `{}` falls through; a
malformed header falls through without raising; a header carrying `{"project":"x"}` does not
put `project` into the declaration (fails if it does); `resolve_declared_context(None)`
returns `(None, None)`; and every non-`None` return is a `DeclaredContext` produced by
`declared_context_from_wire`, never constructed directly.

**Invariant.** `project` is not a context axis (T1.34 ruling 3, T1.65's guard).

**Depends.** 2, 6 (for the headers-mapping idiom). **Parallel:** yes, with 7–10.

## 7. What this plan could not settle

Four. None was resolved silently; each needs a controller ruling before the step that depends
on it executes.

### Open question 1 — the REST door's terminal fallback, and whether the sentinel is per-door

Doc 12 §5 fixes the chain as "explicit arg (literal `mcp` counts as unspecified) >
`X-Darkmem-Client` > User-Agent > `mcp`" and describes it throughout as the MCP door's
mechanism — the section's own diagram is captioned for the stateless MCP server. The task's
Done-when nonetheless demands the chain "tested end to end on **both** doors", and the REST
door's live default is `"api"`, not `"mcp"`.

Three readings, all defensible:

1. **Per-door fallback and per-door sentinel** (what steps 6–9 build): REST falls back to
   `"api"` and treats an explicit `"api"` as unspecified; MCP falls back to `"mcp"` and treats
   an explicit `"mcp"` as unspecified.
2. **One fallback, `"mcp"`, everywhere** — literal doc compliance, but it labels every
   unattributed HTTP capture as having come from MCP, which is a false attribution on the
   `source` column the UI filters and colours by.
3. **REST resolves the header and UA but keeps `"api"` as a non-sentinel default** — an
   explicit `"api"` then wins over the header, and a caller who copies the old default masks
   detection. This is precisely the failure the `mcp` sentinel exists to prevent, so it seems
   wrong, but it is the smallest change.

Reading 1 is recommended and is what the steps assume. **It is not what the doc says**, and it
changes stored `source` values on the REST door for any caller sending `X-Darkmem-Client`.
Flagging rather than choosing, per Ruling 6.

### Open question 2 — the `X-Darkmem-Context` header's encoding

Doc 12 §5 names the header, fixes its precedence rank, and fixes the axes, but never says how
a `{env, version, situation}` object is encoded into one HTTP header value. Two candidates:

- **Compact JSON** — `X-Darkmem-Context: {"env":"prod","version":"15"}`. One parser shared
  with the per-call `context` argument, which is already a JSON object. Recommended, and what
  step 11 assumes.
- **RFC 8941 structured-field dictionary** — `X-Darkmem-Context: env=prod, version="15"`.
  More header-idiomatic, more robust to proxies, but a second parser and a second escaping
  story for a `version` string that is deliberately free-form.

The choice binds doc 15's SDKs and browser extension and T3.14's `declareContext` verb, so it
should be ruled on rather than defaulted into.

### Open question 3 — does the 202 capture ack get the envelope? (bears directly on Ruling 4)

Done-when 1 says "one envelope shape across **every** surface". `CaptureAck` is
`{id, status:"accepted"}` — a flat singleton with no `items`, no pagination, and no
exclusions. Two readings:

- **Minimal** (what step 15 assumes): the ack gains `schema_version` and stays flat. The
  envelope's list-shaped fields do not apply to a singleton, and `{data:…, envelope:…}` on
  every singleton response is a large breaking change to every route the frontend reads.
- **Uniform**: every response body becomes `{schema_version, data, envelope}`. Genuinely one
  shape, and genuinely a rewrite of every REST consumer.

This is not academic. **T1.14 flipped `POST /memories` to a buffered 202 ack while
`frontend/src/hooks/api/use-memory-api.ts:67` still calls `apiFetch<Memory>("/memories")`** —
typed to receive a `Memory`, with no `wait_process` parameter. It is masked only because demo
mode defaults on, and **T1.58 removes that mask**. T1.42a is where the ack's wire shape is
fixed; T1.58 is where the frontend binds to it. Whichever reading the controller picks, the
answer is the type T1.58 will write, so it should be decided here rather than discovered
there. The backend-only lane must **not** edit `frontend/` — it records the target shape.

### Open question 4 — is `POST /memories/search`'s bare list acceptable through this task?

It returns `list[MemoryResponse]` with nowhere to put an envelope, which is why T1.33 wired
`with_trace` only on `/search/paginated`. Step 14 resolves the context chain on it but does
not echo it, deferring the return-type change to T1.42b. If the controller reads Done-when 1
as binding on this route inside T1.42a, step 14 grows a breaking change to a route the
frontend calls (`use-memory-api.ts:122`) and should be split into its own step.
