### 2.1 The seam T2.55 inherits

`compose()` returns an **ordered, total, deterministic** `list[ComposedRow]`. T2.55's
grouping is a pure regroup of that list and adds nothing to this module.

What T2.55 inherits, stated as guarantees it may rely on:

- **Keys are namespaced** (`"fact:<uuid>"`, `"memory:<uuid>"`, `"article:<uuid>"`), so
  `grouped_under` can name a fact unambiguously and a memory key can never be mistaken for
  the fact key it is nested under. Without this, a grouping map keyed on bare ids is the
  invariant-9 failure mode wearing a different hat.
- **The order is total and reproducible** — the final tie-break is the key, so two runs
  over the same candidates give byte-identical order. Grouping over a non-deterministic
  input would produce non-deterministic groups.
- **Nothing is dropped for its verification status.** Every candidate handed in either
  survives to the output or is counted in `excluded` under a named reason. T2.55's
  "names its constituent evidence without counting it again" therefore has a complete set
  to work from.
- **`ComposedRow` carries no `grouping` key.** T2.43 deliberately does **not** emit
  `{grouped_under: null, relation: null}`: emitting the key would claim a grouping pass
  ran. T2.55 adds the key when it adds the pass (invariant 23).
- The provenance query T2.55 needs already exists and is **not** called here:
  `FactSourceRepository.memory_sources_for_fact` (`app/repositories/fact_sources.py:476`).

### 2.2 The seam T2.56 inherits

- Both output shapes are **projections of the same ordered list**. The sectioned shape is

## 3. The design decisions, made executable

### D1 — The keyspace: namespaced composition keys, minted once

**Decision. The composition's merge key is `f"{id_kind}:{raw_id}"`, minted by one
function, `composition_key`, where `id_kind` comes from a closed set and `raw_id` is
`str()`-normalised at admission. `rank_fusion.normalize_row_id` is never used for a
cross-layer merge and `rrf_fuse` is never called on cross-layer rows.**

The failure this prevents is not hypothetical arithmetic about UUID collisions. It is
structural, and it has three faces:

1. `normalize_row_id` reads `memory_id` **or** `id`. A fact row carries `id`; a memory row
   carries `memory_id`. Both resolve to a bare UUID string in **one shared keyspace** with
   nothing marking which table it came from. Two objects that happen to share a key merge
   into one fused row with summed RRF mass — silently, because `rrf_fuse` has no notion of
   an unexpected merge.
2. The far more likely accident is the reverse: a caller normalises a fact row to
   `{"memory_id": …}` to make an existing helper work, and the fact is now indistinguishable
   from a memory downstream. A namespaced key makes that unrepresentable.
3. Downstream consumers (T2.55's `grouped_under`, doc 07 §8's `id` + `id_kind` pair) need to
   name a specific object in a specific space. A bare id cannot.

Shape:

```python
LAYERS: frozenset[str] = frozenset({"L0", "L2", "L3"})   # L1 is not directly served
ID_KINDS: frozenset[str] = frozenset({"memory", "fact", "article"})
LAYER_BY_ID_KIND = {"memory": "L0", "fact": "L2", "article": "L3"}

def composition_key(id_kind: str, wire_id: str) -> str:
    if id_kind not in ID_KINDS:
        raise ValueError(...)
    if not isinstance(wire_id, str) or not wire_id:
        raise TypeError(...)          # normalisation happened at the adapter, not here
    return f"{id_kind}:{wire_id}"
```

**`str()` is spelled exactly once, in the adapter, and `composition_key` refuses a
non-`str`.** Revision 2 normalised in two places — the adapter *and* `composition_key` —
which meant T2's named mutation (delete the adapter's `str()`) could be absorbed by the
other site and the drill would pass while the guard was gone. One normalisation point, one
drill, one thing to break.

`ComposedRow` carries **both**: `key` (internal, namespaced) and `id` + `id_kind` (the wire
pair doc 07 §8 defines). The wire `id` is the bare string, so doc 12 serialises an id a
client can look up. `key == f"{id_kind}:{id}"` is asserted, so the two can never drift.

**Invariant 9 is normalised at admission, not at the merge.** Every adapter runs
`str(raw_id)`. A `UUID` object and its `str` therefore mint the same key and merge into one
row. This is the boundary CLAUDE.md names, moved one step earlier than `rrf_fuse` does it,
because at admission we still know which space the id came from.

**L1 is absent from `LAYERS` on purpose.** Doc 07 §8: "L1 candidate graph is not directly
served". A vocabulary that admitted `L1` would let a candidate-graph row be served as a
composed result.

### D2 — The cross-layer merge is rank-based, not score-based

**Decision. Each channel's already-fused output is treated as one ranked list. Every row is
stamped with `channel_rank` — its 1-based position in its own channel's ordered output —
and the cross-layer ordering signal is that rank, never a comparison of two channels'
`rrf_score` magnitudes.**

The argument is doc 07 §3's own, applied one level up. §3 rejects "folding raw magnitudes
into one weighted sum … because it forces a min-max normalisation per modality that is
brittle to outliers and re-tunes every time a channel is added". Two channels' `rrf_score`
values **are** raw magnitudes from two different fusions with two different weight splits
(memory 0.7/0.3, facts 0.5/0.5). Comparing them directly is exactly the design §3 rejects,
wearing the name of the design §3 chose.

Rank is the one currency §3 recognises as cross-modality comparable. So:

- `cross_layer_rrf = 1.0 / (RRF_K + channel_rank)`, `RRF_K` imported from `rank_fusion` —
  **not** redeclared. `code_query.py`'s private `RRF_K = 60` is the standing example of what
  redeclaring costs, and CLAUDE.md records that no task owns closing that drift. This task
  will not open a third.
- Per-channel list weights are **module constants at 1.0**, not config rows (accepted at
  controller level, 2026-08-02). The reason belongs *beside the constants*, as a comment,
  because it is the kind of thing a later reader will otherwise "improve": **a config row
  nobody may tune is an operator-visible claim that tuning is sanctioned**, which is the
  same class of overclaim as shipping a knob for a feature that does not exist. Doc 07 §11
  permits tuning only against the harness, and no task owns measuring a cross-layer channel
  weight (§8 O3). Constants say what is true — these are equal and nobody has measured
  otherwise.
- With equal weights, `cross_layer_rrf` is a pure function of `channel_rank`. It is carried
  in the trace so §3's currency is visible, and its docstring says plainly that it is
  derived, so nobody reads it as an independent signal.

A row appears in exactly one channel, so no row ever sums contributions from two — the
cross-layer merge is a **union under namespaced keys**, and the ordering is a weighted
rank interleave. That is what doc 07 §5 step 1's "keyed by object id in its own space"
means operationally.

### D3 — "Within the same relevance band", defined so the rule cannot go inert

**Decision. `band` is the row's rank in whatever relevance ordering is currently
authoritative: `channel_rank` when the reranker did not run, and the **dense** rank over
`rerank_score` when it did. Two rows share a band exactly when the active relevance signal
ranks them equal.**

This is the one definition that makes doc 07 §5's phrase operational without a magic
number and without dissolving:

- It is **derived, never tuned.** No config row can widen or narrow a band.
- It is **integer and exact.** A tolerance-based band (`|a − b| < ε`) is not transitive, so
  it is not a strict weak ordering, and `sorted` over it returns an arbitrary permutation.
  That trap is why bands are ranks and not score windows.
- It **survives the reranker.** Rerank scores are `llm_score / normalizer` over LLM integers
  0–10, and the unscored tail is all `0.0` (`app/services/reranker.py:82-90`), so ties are
  the common case and the band is wide precisely where relevance is least discriminating —
  which is where an epistemic tie-break earns its keep.
- It does **not** make the multipliers inert, because the multipliers act **on** the band
  rather than inside it (D5). *Revision 2 claimed the opposite and was wrong; §8 O2 states
  the geometry that refutes it.*

**The authoritative signal is chosen once per request, never per row.** This is the
guarantee that keeps the comparator a strict weak ordering, and it is worth stating
explicitly because the definition above reads as if it could vary. `compose()` receives
either a `rerank_scores` mapping or nothing; that single fact selects the signal for the
**whole** result set. So two rows in one response are never compared under different
signals, and the sort stays transitive. Enabling `reranker_enabled` mid-corpus therefore
changes the order of *subsequent* requests, not the internal consistency of any one of
them — the flag is a per-request input, and the envelope's `reranked` field already
records which signal a given response was built under, so two responses ordered
differently are self-describing rather than mysterious.

**Two consequences of the reranked signal, both named rather than discovered.**

1. **The unscored tail collapses into one band.** `RerankerService` scores only the top 40
   and gives the rest `setdefault("rerank_score", 0.0)` (`reranker.py:82-90`), so under a
   rerank every row past 40 is ranked equal by the active relevance signal. That band is
   therefore ordered by tier, then `weighted_score`, then `key` — the epistemic ladder
   orders exactly the region where the relevance signal has said nothing. That is the
   correct reading of D3's rule rather than an accident of it, but it is a wide band and a
   reader must not be surprised by it.
2. **"Unscored" is kept distinct from "scored zero", which `RerankerService` conflates.**
   `compose()` treats a key *missing* from the `rerank_scores` mapping as the unscored
   tail and places it in a single terminal band **below** every scored band, including a
   genuine `0.0`. A row the model looked at and rated 0 is a different fact about the world
   from a row the model never saw, and collapsing the two would let a bounded budget
   masquerade as a verdict. §6 T14b pins the distinction.

### D4 — The ordering rule, numerically

**Decision. The composed order is the ascending sort on**

```
(band, -tier, key)
```

**where `tier` is a pure lookup over the closed verification vocabulary and `key` is the
namespaced composition key. `weighted_score` is *not* a sort term — it produces the band
(D5) and rides into the trace, and comparing two channels' weighted magnitudes directly is
the cross-modality comparison D2 rejects.**

The tier table:

| `verification_status` | `tier` | Layer |
|---|---|---|
| `confirmed` | 4 | L2 / L3 |
| `corroborated` | 3 | L2 / L3 |
| `candidate` | 2 | L2 / L3 |
| `disputed` | 1 | L2 / L3 |
| *(none — memory carries lifecycle instead)* | 0 | L0 |

Four things this table is careful about:

- **It is a lookup, not a computation.** An unknown status **raises**; there is no
  `.get(status, default)`. A silent fallback tier would be the read path assigning a
  verification meaning, which is invariant 15's line. The CHECK is
  `candidate | corroborated | disputed | confirmed` (doc 04 §8.3), so an unknown value
  cannot exist and raising costs nothing; doc 09's terminal `superseded` article is not
  servable, so it never arrives, and if one ever does the failure is loud (§8 O5).
- **`under-sourced` is not a tier.** Doc 08 §4.3 makes it a `review_state`/label overlay on
  a still-`corroborated` fact, explicitly not a fifth `verification_status`. It rides
  through as a label and does not move the row. Demoting it would be recomputing a label.
- **L0 sits at the bottom, and doc 07 §5 puts it there**: "a verified fact outranks a raw
  candidate of equal query-relevance because the maintainer's priority is TRUTH", and cold
  start serves candidates "above nothing".
- **`disputed` sits below `candidate`** (ruled Tier-1 and upheld, 2026-08-02). Doc 07 §5
  line 200 makes `disputed` a *sub-state* of the `candidate → corroborated → confirmed`
  ladder, not a fourth rung the decision line forgot, so its sort position is unspecified
  rather than contradicted. §8 O1 carries the full argument, including the alternative that
  invariant 15 forbids.

**`key` is the sole tie-break**, chosen because it is input-independent: an insertion-order
tie-break would make the served order depend on the order a caller happened to list its
channels. Because it is now reached **unconditionally** whenever band and tier agree — and
not, as in revision 2, only when two rows happened to tie exactly on a float — the drill
below cannot be silently rerouted by an asymmetric fixture.

**The trap the drill must avoid, named now because §6 depends on it.** `key` sorts
`"article:…" < "fact:…" < "memory:…"` alphabetically, and that ordering *accidentally
agrees* with the tier order in the two obvious fixtures (fact-beats-memory,
high-article-beats-low-fact). A test built only from those would pass with the `-tier` term
deleted. The one available cross-channel disagreement is **a `confirmed` fact against a
`candidate` article in the same band**: tier says fact first, `key` says article first.

### D5 — Where the reranker and the multipliers sit, and what they may move

**Decision. The deterministic multipliers act *on* the band, not beside it: at step 4 each
channel is re-ranked by its own weighted score, and `band` is recomputed as the row's
ordinal position in that re-ranked channel. A multiplier can move a row from one band to
another; it can never change a row's tier and never reorders within a band.**

Sequence inside `compose()`:

1. merge (D1, D2) → provisional `band = channel_rank` from the channel's own order
2. label + tier + `applies_when` partition with its tally (D6); exclusions drop rows
3. if rerank scores were supplied → `band` := dense rank over `rerank_score`, and step 4
   rescales only (doc 07 §3's `preserve_order` rule)
4. `weighted_score = base × rank_fusion_factor(signals, weights) × context_boost`.
   **If not reranked:** re-sort each channel by `weighted_score` and set `band` to the
   row's 1-based position in its own re-sorted channel — gaps left by step 2's exclusions
   close here, so a channel that lost its rank-2 row does not leave a hole.
5. sort on D4's `(band, -tier, key)`

Conflict exclusion sits at step 2, before the rerank, exactly as doc 07 §5 requires, so no
model call is spent scoring a row that will be excluded — and the count is still surfaced.

**Why "on the band" rather than revision 2's "inside the band" — the geometry.** `band` is
unique within a channel, so a `(band, tier)` cell holds **at most one row per channel**.
A per-row scalar therefore cannot move a row relative to any same-channel neighbour at any
magnitude: a 1000× importance factor cannot lift a memory past the memory one rank above
it. Revision 2's within-band confinement made every arm and the context boost order-inert
on the default path, which quietly repealed doc 07 §6 — whose Match treatment is literally
"rank **boost**" — and left §11's sanctioned tuning path unable to produce the measured
win T2.30, T2.31, T2.35 and T2.50 exist to find. Re-ranking the channel by the weighted
score gives the multipliers **rank authority**, which is exactly the authority §6 names.

**What this preserves, unchanged.** The hard rule is untouched and is now *stronger* than a
score-primary sort could make it: a multiplier changes which band a row occupies, never its
tier and never its order within a band, so a memory boosted into band 1 still sits below a
band-1 confirmed fact at any weight. D2's argument survives too — the re-rank happens
**inside one channel**, where the magnitudes are commensurable, and the cross-channel
comparison is still rank and only rank.

**Why not the coarse-band alternative** (score buckets, quantiles, or rank groups), which
is the other way to give multipliers room:

- A bucket width or quantile count is a magic number with no measurement behind it —
  precisely what §11 forbids and what D3's rank-based band was chosen to avoid.
- Buckets have cliffs. Two rows either side of a boundary are ordered by tier though their
  relevance differs by ε, while two rows at opposite ends of one bucket are treated as
  equal. The boundary, not the evidence, decides.
- Quantiles make the band depend on result-set size, so the same two rows compare
  differently in a `limit=10` and a `limit=50` query — a genuine non-monotonicity, and
  worse than the inertness it would fix.
- And they would still give the multipliers only *score* authority inside a bucket, which
  re-opens "a big enough weight distorts the ladder" at bucket scale rather than closing it.

**No double application, verified.** `HybridSearchService.search_with_trace` never calls
`_apply_rank_fusion_factor` (`hybrid_search.py:60-93`); only `pipeline.semantic_search`
does, and the composition does not go through it. The composition is the sole applier on
its own path.

**Arms whose signal is absent are already no-ops.** `arm_factor` returns exactly `1.0` when
a signal is missing (`rank_fusion.py:140-142`), so `heat`/`recency` — which have no
fact-side counter until T2.65 — simply do not touch fact rows, with no special-casing. The
consequence is worth naming: activating a memory-side arm re-ranks the memory channel and
therefore moves the interleave, which is a real, measurable effect and the point of F1.

**The context boost is applied exactly once.** It is read off the stamped `ContextOutcome`
and folded into `weighted_score`; `rank_fusion.apply_context_boost` is **not** called.
Revision 2 did both, which multiplied the boost in twice. `apply_context_boost` is also the
wrong tool here for a second reason — it sorts on `rrf_score`/`score`, keys this module does
not order by.

### D9 — Code search cannot enter: a four-part mechanism, argued

The Done-when is "a test asserts code search **cannot** enter the composition". A test that

### D10 — Purity boundary

`compose()` is **pure**: no session, no clock, no LLM. It takes candidate lists, a weights
mapping, an optional declared context, and an optional `rerank_scores: Mapping[key, float]`.
`LayerCompositionService` is the impure half: it runs the two channels, batches the
counterpart read, optionally calls the reranker, and assembles the envelope.

**How `rerank_scores` is derived — specified, because revision 2 left it to the
implementer and the shipped path could not have produced D3(2)'s distinction.**
`RerankerService` slices its own head at 40, stamps the *tail* through
`setdefault("rerank_score", 0.0)`, and returns `(reranked_head + tail)[:top_k]` with
`top_k` defaulting to **10** (`reranker.py:86-98`). Derived naively from that return, no key
is ever missing, D3(2)'s terminal band is dead code, T14b guards a distinction the shipped
path cannot produce — and the `[:10]` truncation silently drops rows, colliding head-on with
T9's nothing-is-dropped guarantee. So the service derives the mapping itself:

```
RERANK_WINDOW = 40
window  = candidates[:RERANK_WINDOW]          # the composition slices, not the reranker
scored  = await reranker.rerank(query, window, top_k=len(window))
assert len(scored) == len(window)             # nothing truncated
scores  = {key_of(row): float(row["rerank_score"]) for row in scored}
```

Three properties this buys, each pinned by §6 T21:

- **The tail is never read.** Submitting only the window makes `RerankerService`'s internal
  `tail` empty, so no `setdefault` row can reach the mapping.
- **Nothing is truncated.** `top_k=len(window)` makes `[:top_k]` a no-op, and the length
  assertion says so rather than trusting it.
- **Keys past the window are genuinely absent**, so D3(2)'s terminal band is live and T14b
  is a real distinction rather than a guard over an unreachable state.

**A total rerank failure degrades to the deterministic order.** `RerankerService`'s outer
handler stamps **every** document `0.0` and returns them in input order — indistinguishable
from a model that rated everything 0. Serving that as a rerank would collapse the whole
window into one band and order it by tier alone, which is a large silent behaviour change
out of an outage. So the service treats an all-zero mapping as **no usable signal**, returns
`rerank_scores=None`, and the envelope reports `reranked=False` (§6 T22). That is
invariant 14's no-silent-degradation applied to the one signal that can fail quietly.

Related defect, **reported not fixed**: `RerankerService` also returns `0.0` from a
*per-document* failure (`reranker.py:70-71`), so within the window "asked and failed" is
indistinguishable from "asked and rated 0". The all-zero guard covers the total-outage case;
the per-document case needs a sentinel in `RerankerService` itself, which is not this task's
file. §8 O9.

This is `verification_ladder.py`'s own split (`decide` at `:307-322` — "No I/O, no session,
and no clock" — applier at `:575`), kept in one module for the same reason it is. It makes
every ordering, tier and keyspace test a fast pure-function test, which is what lets §6's
mutation drills be run cheaply and often.

## 8. Open questions, each with a stance

### O1 — **RULED, 2026-08-02.** `disputed` sits below `candidate`, and it is Tier-1

Raised as a possible Tier-3 and **closed as Tier-1**. Doc 07 §5 line 200 reads "the ladder
is **candidate → corroborated → confirmed** with a **disputed** sub-state" — so `disputed`
is explicitly *orthogonal* to the three rungs, not a fourth rung §5's decision line omitted.
The decision line ranks only the three named values, and §5 says separately that a disputed
row is served labelled with both sides. Its sort position is therefore **unspecified**
rather than contradicted, which is a decision to record, not a corpus conflict to stop on.

**On the merits, three things carry the placement, and the third is the one a later reader
will otherwise re-litigate.**

1. **Under-claiming is the corpus's stated posture** (spec preamble; doc 08 §4's "the ladder
   is built to under-claim"). A disputed fact carries a *known* contradiction. Ranking it
   beneath an uncontradicted candidate is the under-claiming direction; ranking it above
   would hand back confidence doc 08 §4.2's absolute veto just removed.
2. **The cost is bounded, because §5 already guarantees the row is never suppressed.** It
   still appears, labelled, with both sides. Ordering last among facts is not filtering, and
   §6 T9 pins that nothing is dropped for its status.
3. **The alternative is not implementable within invariant 15.** The natural counter-proposal
   is that a disputed fact should *retain its pre-dispute rung* — a disputed-from-corroborated
   row outranking a disputed-from-candidate one. It cannot: `verification_status` is a single
   column, so the moment a corroborated fact is disputed the prior rung is **gone from the
   row**. Recovering it would mean a per-row read of the verification journal to reconstruct
   what the label used to be — which is retrieval *computing* a verification label rather
   than reading one, the exact line invariant 15 draws. The placement is not merely preferred
   over the alternative; the alternative is unavailable to this layer.

### O2 — **RE-OPENED and RE-ANSWERED, 2026-08-02.** The multipliers act *on* the band

Revision 2's answer — confine the multipliers to within-partition reordering — was
**accepted on an incomplete presentation and is now withdrawn**. The Fable review supplied
the geometry that refutes it, and the geometry is short enough to restate in full:

> `band = channel_rank` is unique within a channel, so a `(band, tier)` cell holds at most
> one row per channel. A per-row scalar cannot move a row relative to a same-channel
> neighbour at any magnitude — a 1000× arm factor cannot lift a memory past the memory one
> rank above it, and a 50× context boost cannot either. The only pairs a within-band term
> could order are fact-versus-article at equal rank *and* equal tier, plus rerank ties.

So on the default path — `reranker_enabled` is off — every arm and the context boost were
**order-inert at every magnitude**. That is not a conservative choice; it is three failures
at once. It repeals doc 07 §6, whose Match treatment is literally "rank **boost**". It
hollows out §11's sanctioned tuning path, because a knob whose magnitude cannot change the
order can never produce the measured retrieval win T2.30, T2.31, T2.35 and T2.50 exist to
find. And it would have gone live the moment T2.58 converged Chat onto this path.

**The answer: give the multipliers rank authority instead of score authority.** At step 4
each channel is re-sorted by its own `weighted_score` and `band` is recomputed from that
position (D5). A multiplier now moves a row between bands — monotonically in its weight —
while the hard rule stays absolute, because a multiplier still never changes a tier and
never reorders within a band. Doc 07 §6's word is implemented as the thing it says.

**Why not the coarse band** the controller floated as the alternative: a bucket width or
quantile count is a magic number §11 forbids; buckets have cliffs, so a boundary rather
than the evidence decides two rows' order; quantiles make the band depend on result-set
size, so the same pair compares differently at `limit=10` and `limit=50`; and a bucket
would still hand the multipliers only score authority inside it, re-opening "a big enough
weight distorts the ladder" at bucket scale. The full argument is in D5.

Blast radius today remains nil — every weight is 0 — which is why steps 1–5 were cleared to
run while step 6 was blocked. **What a reviewer should now check** is T15's half (a): that
a raised weight demonstrably moves a row across bands. Revision 2's design would have
failed exactly that assertion, and nothing in revision 2's test plan asked for it.

### O3 — **ACCEPTED, 2026-08-02.** Cross-layer channel weights are constants, not config rows

Doc 07 §3 names "fact/article weights" as config rows; §11 says every ranking multiplier
defaults to "the today-equivalent no-op" and is tuned only against the harness, never by
intuition. A channel that does not exist today has no today-equivalent, and **no task owns
measuring a cross-layer channel weight** — T2.44's `--arm` covers the `rank_fusion_factor`
arms, and T2.30/T2.31/T2.35/T2.50 own arm activation. **Stance: ship equal module constants
at 1.0.** A config row nobody owns tuning is a knob that will be turned by intuition, which
is exactly what §11 forbids. **Recommendation to the controller:** either extend T2.44's
`--arm` to ablate a channel weight, or mint a task; promoting the constants afterwards is a
one-line change and a new envelope `weights` entry.
