### 2.1 The seam T2.55 inherits

`compose()` returns an **ordered, total, deterministic** `list[ComposedRow]`. T2.55's
grouping is a pure regroup of that list and adds nothing to this module.

What T2.55 inherits, stated as guarantees it may rely on:

- **Keys are namespaced** (`"fact:<uuid>"`, `"memory:<uuid>"`, `"article:<uuid>"`), so
  `grouped_under` can name a fact unambiguously and a memory key can never be mistaken for
  the fact key it is nested under. Without this, a grouping map keyed on bare ids is the
  invariant-9 failure mode wearing a different hat.
- **The order is total and reproducible** — the final tie-break is the key, so two runs
  over the same candidates give byte-identical order. Grouping over a non-deterministic
  input would produce non-deterministic groups.
- **Nothing is dropped for its verification status.** Every candidate handed in either
  survives to the output or is counted in `excluded` under a named reason. T2.55's
  "names its constituent evidence without counting it again" therefore has a complete set
  to work from.
- **`ComposedRow` carries no `grouping` key.** T2.43 deliberately does **not** emit
  `{grouped_under: null, relation: null}`: emitting the key would claim a grouping pass
  ran. T2.55 adds the key when it adds the pass (invariant 23).
- The provenance query T2.55 needs already exists and is **not** called here:
  `FactSourceRepository.memory_sources_for_fact` (`app/repositories/fact_sources.py:476`).

## 3. The design decisions, made executable

### D1 — The keyspace: namespaced composition keys, minted once

**Decision. The composition's merge key is `f"{id_kind}:{raw_id}"`, minted by one
function, `composition_key`, where `id_kind` comes from a closed set and `raw_id` is
`str()`-normalised at admission. `rank_fusion.normalize_row_id` is never used for a
cross-layer merge and `rrf_fuse` is never called on cross-layer rows.**

The failure this prevents is not hypothetical arithmetic about UUID collisions. It is
structural, and it has three faces:

1. `normalize_row_id` reads `memory_id` **or** `id`. A fact row carries `id`; a memory row
   carries `memory_id`. Both resolve to a bare UUID string in **one shared keyspace** with
   nothing marking which table it came from. Two objects that happen to share a key merge
   into one fused row with summed RRF mass — silently, because `rrf_fuse` has no notion of
   an unexpected merge.
2. The far more likely accident is the reverse: a caller normalises a fact row to
   `{"memory_id": …}` to make an existing helper work, and the fact is now indistinguishable
   from a memory downstream. A namespaced key makes that unrepresentable.
3. Downstream consumers (T2.55's `grouped_under`, doc 07 §8's `id` + `id_kind` pair) need to
   name a specific object in a specific space. A bare id cannot.

Shape:

```python
LAYERS: frozenset[str] = frozenset({"L0", "L2", "L3"})   # L1 is not directly served
ID_KINDS: frozenset[str] = frozenset({"memory", "fact", "article"})
LAYER_BY_ID_KIND = {"memory": "L0", "fact": "L2", "article": "L3"}

def composition_key(id_kind: str, raw_id) -> str:
    if id_kind not in ID_KINDS:
        raise ValueError(...)
    key = str(raw_id)
    if not key:
        raise ValueError(...)
    return f"{id_kind}:{key}"
```

`ComposedRow` carries **both**: `key` (internal, namespaced) and `id` + `id_kind` (the wire
pair doc 07 §8 defines). The wire `id` is the bare string, so doc 12 serialises an id a
client can look up. `key == f"{id_kind}:{id}"` is asserted, so the two can never drift.

**Invariant 9 is normalised at admission, not at the merge.** Every adapter runs
`str(raw_id)`. A `UUID` object and its `str` therefore mint the same key and merge into one
row. This is the boundary CLAUDE.md names, moved one step earlier than `rrf_fuse` does it,
because at admission we still know which space the id came from.

**L1 is absent from `LAYERS` on purpose.** Doc 07 §8: "L1 candidate graph is not directly
served". A vocabulary that admitted `L1` would let a candidate-graph row be served as a
composed result.

### D2 — The cross-layer merge is rank-based, not score-based

**Decision. Each channel's already-fused output is treated as one ranked list. Every row is
stamped with `channel_rank` — its 1-based position in its own channel's ordered output —
and the cross-layer ordering signal is that rank, never a comparison of two channels'
`rrf_score` magnitudes.**

The argument is doc 07 §3's own, applied one level up. §3 rejects "folding raw magnitudes
into one weighted sum … because it forces a min-max normalisation per modality that is
brittle to outliers and re-tunes every time a channel is added". Two channels' `rrf_score`
values **are** raw magnitudes from two different fusions with two different weight splits
(memory 0.7/0.3, facts 0.5/0.5). Comparing them directly is exactly the design §3 rejects,
wearing the name of the design §3 chose.

Rank is the one currency §3 recognises as cross-modality comparable. So:

- `cross_layer_rrf = 1.0 / (RRF_K + channel_rank)`, `RRF_K` imported from `rank_fusion` —
  **not** redeclared. `code_query.py`'s private `RRF_K = 60` is the standing example of what
  redeclaring costs, and CLAUDE.md records that no task owns closing that drift. This task
  will not open a third.
- Per-channel list weights are **module constants at 1.0**, not config rows. §8 O3 argues
  why, and names what would have to be true to promote them.
- With equal weights, `cross_layer_rrf` is a pure function of `channel_rank`. It is carried
  in the trace so §3's currency is visible, and its docstring says plainly that it is
  derived, so nobody reads it as an independent signal.

A row appears in exactly one channel, so no row ever sums contributions from two — the
cross-layer merge is a **union under namespaced keys**, and the ordering is a weighted
rank interleave. That is what doc 07 §5 step 1's "keyed by object id in its own space"
means operationally.

### D3 — "Within the same relevance band", defined so the rule cannot go inert

**Decision. `band` is the row's rank in whatever relevance ordering is currently
authoritative: `channel_rank` when the reranker did not run, and the **dense** rank over
`rerank_score` when it did. Two rows share a band exactly when the active relevance signal
ranks them equal.**

This is the one definition that makes doc 07 §5's phrase operational without a magic
number and without dissolving:

- It is **derived, never tuned.** No config row can widen or narrow a band.
- It is **integer and exact.** A tolerance-based band (`|a − b| < ε`) is not transitive, so
  it is not a strict weak ordering, and `sorted` over it returns an arbitrary permutation.
  That trap is why bands are ranks and not score windows.
- It **survives the reranker.** Rerank scores are `llm_score / normalizer` over LLM integers
  0–10, and the unscored tail is all `0.0` (`app/services/reranker.py:82-90`), so ties are
  the common case and the band is wide precisely where relevance is least discriminating —
  which is where an epistemic tie-break earns its keep.
- It does **not** go inert when an arm is activated, because the multipliers act inside the
  band rather than on it (D5).

### D4 — The ordering rule, numerically

**Decision. The composed order is the ascending sort on**

```
(band, -tier, -weighted_score, key)
```

**where `tier` is a pure lookup over the closed verification vocabulary and `key` is the
namespaced composition key.**

The tier table:

| `verification_status` | `tier` | Layer |
|---|---|---|
| `confirmed` | 4 | L2 / L3 |
| `corroborated` | 3 | L2 / L3 |
| `candidate` | 2 | L2 / L3 |
| `disputed` | 1 | L2 / L3 |
| *(none — memory carries lifecycle instead)* | 0 | L0 |

Four things this table is careful about:

- **It is a lookup, not a computation.** An unknown status **raises**; there is no
  `.get(status, default)`. A silent fallback tier would be the read path assigning a
  verification meaning, which is invariant 15's line. The CHECK is
  `candidate | corroborated | disputed | confirmed` (doc 04 §8.3), so an unknown value
  cannot exist and raising costs nothing; doc 09's terminal `superseded` article is not
  servable, so it never arrives, and if one ever does the failure is loud (§8 O5).
- **`under-sourced` is not a tier.** Doc 08 §4.3 makes it a `review_state`/label overlay on
  a still-`corroborated` fact, explicitly not a fifth `verification_status`. It rides
  through as a label and does not move the row. Demoting it would be recomputing a label.
- **L0 sits at the bottom, and doc 07 §5 puts it there**: "a verified fact outranks a raw
  candidate of equal query-relevance because the maintainer's priority is TRUTH", and cold
  start serves candidates "above nothing".
- **`disputed` sits below `candidate`.** The corpus is silent on this one placement; §8 O1
  records the argument and flags it for the reviewer. In short: doc 08 §4.2 makes a single
  non-echo contradiction an *absolute veto*, and ranking a vetoed claim above an un-vetoed
  candidate would be the read path handing back confidence the ladder just took away. It is
  still **served**, labelled, with both sides — ordering last among facts is not suppression.

**`-weighted_score` and `key` are the two tie-breaks, and their order matters.**
`weighted_score` (D5) carries the multipliers' effect and orders within a band+tier group.
`key` is the last resort, chosen because it is input-independent: an insertion-order
tie-break would make the served order depend on the order a caller happened to list its
channels.

**The trap the drill must avoid, named now because §6 depends on it.** `key` sorts
`"article:…" < "fact:…" < "memory:…"` alphabetically, and that ordering *accidentally
agrees* with the tier order in the two obvious fixtures (fact-beats-memory,
high-article-beats-low-fact). A test built only from those would pass with the `-tier` term
deleted. The one available cross-channel disagreement is **a `confirmed` fact against a
`candidate` article in the same band**: tier says fact first, `key` says article first.
§6 T5 is built on exactly that fixture and on nothing else, and §6 records the mutation.

### D5 — Where the reranker and the multipliers sit, and what they may move

**Decision. Steps 3 and 4 run in doc 07 §5's order, and the deterministic multipliers
reorder *within* the band+tier partition, never across it.**

Sequence inside `compose()`:

1. merge (D1, D2) → `band = channel_rank`
2. label + tier + `applies_when` partition with its tally (D6)
3. if rerank scores were supplied, recompute `band` as the dense rank over `rerank_score`
4. `weighted_score = base × rank_fusion_factor(signals, weights) × context_boost`, where
   `base` is `cross_layer_rrf` when not reranked and `rerank_score` when reranked
5. sort on D4's key

Conflict exclusion sits at step 2, before the rerank, exactly as doc 07 §5 requires, so no
model call is spent scoring a row that will be excluded — and the count is still surfaced.

**The interpretive point, stated so a reviewer can overrule it.** Doc 07 §3 says the
multipliers "reorder if not reranked"; doc 07 §11 says the verification-status ordering is
"a hard rule … not a tunable". Under a score-primary sort those two cannot both hold: a
large enough `w_importance` would lift a memory over a confirmed fact, and the hard rule
would be exactly as hard as its weight. This plan reads §3's "reorder" as written for the
single-channel pipeline, where no epistemic partition existed to cross, and confines the
multipliers to within-partition reordering in the cross-layer path. §8 O2 records the
reading, its blast radius (nil today — every arm is at 0 and provably inert) and what a
contrary ruling would change (one sort key, one test).

**`preserve_order` after a rerank falls out rather than being special-cased.** With
`band` recomputed from `rerank_score`, the rerank's verdict *is* the band order; the
multipliers can only order rows the reranker itself ranked equal. `apply_context_boost` is
therefore always called with `preserve_order=True` from the composition — it rescales,
and this module sorts.

### D6 — Context matching cross-layer, and why the existing partition helper cannot be reused

**Decision. The composition runs its own context partition over `match_context`, keyed by
the namespaced composition key. `rank_fusion.partition_by_context` is not called.**

`partition_by_context` looks a row's context up with `normalize_row_id(row)`
(`app/services/rank_fusion.py:400-403`) — the bare-id key. Handed cross-layer rows it would
resolve a fact's context from a memory's entry whenever the two ids coincided, which is the
very collision D1 exists to prevent. `match_context` itself takes no id
(`rank_fusion.py:328`) and is reused verbatim, as are `ContextOutcome`, `ContextMatch` and
`ContextProvenance` — the composition adds a key function, not a second matcher.

This is a **latent** defect in `partition_by_context`, not a live one: today only memory
rows reach it and it has no production caller at all. §8 O4 recommends the note; this task
does not edit `rank_fusion.py`.

The tally lands in `RetrievalEnvelope.excluded["by_context_conflict"]`, unconditionally,
even when zero — doc 07 §8's rule, and the case a suppressed count hides.

### D7 — The envelope's channels are namespaced, and that discharges T2.42's open note

**Decision. Envelope channel keys are `"<layer_name>.<arm>"`.**

```
memory.semantic   memory.keyword
fact.keyword      fact.name       fact.semantic   (ran=False, owner T2.33)
article.semantic  (ran=False, owner T3.02)
```

`FactChannelTrace.channel_status()`'s docstring states the problem and assigns it here: its
keys are unqualified, `RetrievalEnvelope.channels` is flat, and a naive merge overwrites the
memory channel's `keyword` entry — so a **memory keyword outage disappears from
`RetrievalEnvelope.partial`**, which is `any(channel.failed …)`. That is a silent
degradation of the no-silent-degradation flag itself. §6 T11 is the drill.

The two deferred arms are present with `ran=False`, never omitted, for the reason
`facts_channel.py:145-166` already gives: an absent key makes "this channel has no such
modality" indistinguishable from "the composition never asked", and marking a deferred
writer `failed` would put it into `partial`, which is a different lie.

No schema change: `RetrievalEnvelope.channels` is `dict[str, ChannelStatus]`.

### D8 — The counterpart is read from the journal, through **one** reader

**Decision. `latest_verified_evidence(session, fact_ids)` is extracted from
`review_queue._latest_verified_evidence` into a small shared module,
`app/services/verified_evidence.py`; `review_queue` delegates to it; the composition calls
it. The deterministic scan is never called.**

Two readers of the same journal shape is how this epic's three ranking implementations
happened (`rank_fusion.py`, `code_query.py`'s own `RRF_K`, Chat's none — recorded in
T2.58's own task text as "the count is the point"). One reader, two callers.

The read is one batched `DISTINCT ON (object_id)` over `events` with
`CAST(:ids AS uuid[])` — the asyncpg CAST rule, already satisfied by the statement being
moved. Behaviour is unchanged; only its home moves. The delegation edit in `review_queue.py`
is one line and is logged as a Tier-1 amendment (§9). If that file is contended when this
step executes, the fallback is to leave `review_queue` untouched and have it import the
shared function under its old private name — never to fork the query.

**Rendering, honouring what T2.64 recorded.** `dispute_label(row, evidence)` returns one of
three shapes, and the three are distinguishable:

| Case | Shape |
|---|---|
| not disputed | `dispute: None` |
| disputed, block present | `{review_state, counterpart: {subject, rel_type, object, id}, rule, witness_origin, enumeration: "first_finding"}` |
| disputed, block absent | `{review_state, counterpart: None, counterpart_absent: "no_finding_recorded"}` |

- `enumeration` is copied **verbatim** from the payload and never re-derived. The composition
  emits **no count and no total** — a `contradiction_count` key would let a renderer say
  "the only contradiction", which the value `first_finding` exists to forbid.
- `counterpart_absent` says "no scan produced one here". It never says "no counterpart
  exists". The three absence causes (recovery, caller-overridden verdict, dispute predating
  T2.64) are not distinguishable from the journal, so the label does not pretend to
  distinguish them.
- **Both sides are rendered in the same shape.** The fact's own side comes from the channel
  row's `subject_name` / `rel_type` / `object_name`; the counterpart's comes from
  `counterpart_subject` / `counterpart_rel_type` / `counterpart_object`. A reader cannot
  tell which side is "ours" from the shape alone — §6 T7 pins that symmetry, because a
  rendering that privileges one side by shape has silently picked a winner.

### D9 — Code search cannot enter: a four-part mechanism, argued

The Done-when is "a test asserts code search **cannot** enter the composition". A test that
merely declines to pass code rows in asserts nothing. Four mechanisms, each covering the
next one's blind spot:

**(a) Closed admission vocabulary and typed adapters.** `compose()` accepts only
`LayerCandidate` instances, minted by `memory_candidate()`, `fact_candidate()` and
`article_candidate()`. `LayerCandidate.__post_init__` validates `id_kind ∈ ID_KINDS` and
`layer == LAYER_BY_ID_KIND[id_kind]`. There is **no** code adapter, and `"code"` is not in
`ID_KINDS`. A code row cannot be minted, so it cannot be admitted.

**(b) The guard raises; it never skips.** A non-`LayerCandidate` in the input raises
`TypeError` naming the offending item. This is the load-bearing half. A filter that skipped
unknown rows would be indistinguishable from a code row that entered and ranked low —
`rrf_fuse`'s `continue` at `rank_fusion.py:77-78` is the existing example of exactly that
silence, and it is why this module does not delegate to it.

**(c) An AST source scan over `app/`.** No module may reference a code-search symbol
together with the composition, with an allowlist, a `len(paths) > 100` vacuity floor, and an
in-suite negative control that calls the **real** predicate on a synthesised violation.
Template: `tests/test_communities.py:1387-1449` (AST, not line-based — it catches
parenthesised imports and split dotted strings, and exempts docstrings so this plan's own
prose does not trip it). Tokens: `code_query`, `CodeQueryService`, `search_code`,
`code_chunk_embeddings`, `CodeSymbol`, `blast_radius`.

**(d) The real producer's real output is refused.** The test feeds
`CodeQueryService.search_code`'s **actual return value** — not a hand-written dict — into
`compose()` and asserts it raises. Hand-writing the row shape would rot the moment
`code_query.py` changes, and would test a transcription rather than the tree.

**Why the four together are "cannot" and not "did not".** (a) makes an unlabelled row
unrepresentable; (b) makes a mislabelled one loud; (c) makes it impossible for the
composition to *obtain* code rows without a visible, failing edit; (d) proves (a) and (b)
fire on the shape the live door actually emits. Removing any one leaves a hole the others
name: without (c) someone writes `code_candidate()`; without (d) the vocabulary is closed
around a shape nobody checked; without (b) the closure is a silent filter.

Doc 07 §2's structural argument still stands underneath all four — the
`code_chunk_embeddings__<slug>` partitions carry no FTS column, code search is gated by
repository rather than project, and no query joins the two graphs — but a structural
argument is not an assertion, which is why the mechanism above exists.

### D10 — Purity boundary

`compose()` is **pure**: no session, no clock, no LLM. It takes candidate lists, a weights
mapping, an optional declared context, and an optional `rerank_scores: Mapping[key, float]`.
`LayerCompositionService` is the impure half: it runs the two channels, batches the
counterpart read, optionally calls the reranker, and assembles the envelope.

This is `verification_ladder.py`'s own split (`decide` at `:307-322` — "No I/O, no session,
and no clock" — applier at `:575`), kept in one module for the same reason it is. It makes
every ordering, tier and keyspace test a fast pure-function test, which is what lets §6's
mutation drills be run cheaply and often.

## 8. Open questions, each with a stance

### O1 — Where `disputed` sits in the tier ladder *(corpus silent)*

Doc 07 §5 orders `confirmed`/`corroborated` above `candidate` and never places `disputed`;
doc 08 §4 gives it a sub-state but no rank. **Stance: `disputed` sits below `candidate` and
above L0 memory.** Doc 08 §4.2 makes one non-echo contradiction an absolute veto, so ranking
a vetoed claim above an un-vetoed candidate re-adds confidence the ladder just removed, and
the corpus's tiebreak is to under-claim. It is still served, labelled, with both sides. This
is silence rather than contradiction, so it is a decision logged as Tier-1 (§9), not an
escalation — but if the reviewer reads §5's enumeration as *exhaustive* rather than partial,
it becomes Tier-3 and step 4 is gated.

### O2 — Multipliers reorder within the partition, not across it *(two clauses pull)*

Doc 07 §3: the multipliers "reorder if not reranked". Doc 07 §11: the verification ordering
is "a hard rule … not a tunable". Under a score-primary sort both cannot hold. **Stance: D5
— the multipliers order within band+tier.** Blast radius today is nil: every arm is at 0 and
provably inert (`tests/test_ranking_arms_zero.py`), so no served order differs under either
reading. A contrary ruling changes one sort key and one test (T15). Recorded here rather
than escalated because the reading satisfies both sentences simultaneously, which is what
"not a contradiction" means — but it is the single place in this task where a reviewer
should look hardest.

### O3 — Cross-layer channel weights are constants, not config rows

Doc 07 §3 names "fact/article weights" as config rows; §11 says every ranking multiplier
defaults to "the today-equivalent no-op" and is tuned only against the harness, never by
intuition. A channel that does not exist today has no today-equivalent, and **no task owns
measuring a cross-layer channel weight** — T2.44's `--arm` covers the `rank_fusion_factor`
arms, and T2.30/T2.31/T2.35/T2.50 own arm activation. **Stance: ship equal module constants
at 1.0.** A config row nobody owns tuning is a knob that will be turned by intuition, which
is exactly what §11 forbids. **Recommendation to the controller:** either extend T2.44's
`--arm` to ablate a channel weight, or mint a task; promoting the constants afterwards is a
one-line change and a new envelope `weights` entry.

### O4 — `rank_fusion.partition_by_context` is latently wrong cross-layer

It keys its context map on `normalize_row_id` (the bare-id key). It has no production caller
today, so this is latent. **Stance: do not edit `rank_fusion.py` here** (arms and their
territory belong to other tasks); the composition supplies its own key function (D6) and
T13 pins the behaviour. **Recommendation:** a one-line note beside `partition_by_context`
naming it the memory-space version, folded into whichever task next touches that file.

### O5 — Doc 09's terminal `superseded` article status has no tier

Doc 07 §8's article enum is the four-value verification vocabulary; doc 09 adds a terminal
`superseded`. **Stance:** a `superseded` article is not servable, so doc 09's predicate keeps
it out and D4's raise is the loud backstop. If E3 serves one, the tier table gains a row and
nothing else changes. Stated so E3 can contradict it rather than discover it.

### O6 — The envelope's channel keys now have two conventions

`memory.py`'s existing traced path emits flat `semantic`/`keyword`; the composition emits
namespaced `memory.semantic` etc. (D7). Both are correct for their own surface and they must
not both survive. **Stance:** T2.56 converges them when it owns the output shapes, and
T2.58 inherits the converged form. Named here so it is a scheduled convergence, not a drift.
Whoever converges must check `frontend/` for a reader of the flat keys.

### O7 — The composition ships with no productive caller

T2.56 and T2.58 are its consumers, and both are behind this task. This is the same situation
T2.45's O3 already normalised in this epic (a primitive landing ahead of its caller).
Honesty requirement: the module docstring names its consumers and their gate, and the
envelope's `article.semantic` / `fact.semantic` entries report `ran=False` rather than being
omitted — nothing here is claimed as spent that is not (invariant 23).

### O8 — `HybridSearchService.search_code` is dead code, and it is a live hazard

It has **zero callers** anywhere in `app/` or `tests/` (`hybrid_search.py:128-146`), it
duplicates `CodeQueryService.search_code`, and it sits on the very class the composition
consumes for L0 — so it is the shortest available path by which code rows could reach a
memory-side caller. Deleting it is outside this task's lane. **Reported for routing**, not
fixed. D9(c)'s scan tokens include `search_code`, so the composition cannot reach it.
