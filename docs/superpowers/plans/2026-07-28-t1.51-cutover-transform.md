# T1.51 — Cutover transform + carried-set column map

**Step-level plan.** Written 2026-07-28 for `docs/planning/tasks/E1-engine-core.md`
§ T1.51 (`Model: Opus 5` · `Effort: high` · `Size: L` · `Depends: T0.12c, T1.01,
T1.23` · `Doc: 19 §4` · `Tag: target-new` · `Gate: G-B`).

Runbook §3 requires a step-level plan before an `L` task is executed. **This
document is the plan only — no production code was written and no file other
than this one was touched.**

`risks-and-lanes.md` row "The cutover destroys data" calls T1.51–T1.54 *"the only
unrecoverable step in the plan, and the first draft had no task for it at all"*.
Doc 19 §4 makes the same point structurally: a memory row is unrecoverable user
data, everything else is a derivation. So this plan is written for a reader whose
job is to refuse it. Every claim it makes about Postgres behaviour was
**measured** (§7) rather than asserted, and every disposition names the source
that fixes it.

**The real `darkmem` database was not touched, read, connected to, or named as a
DSN at any point while this plan was written.** The five behavioural probes in §7
ran against a throwaway `cutprobe` schema inside `darkmem_test_3`, which was
dropped when they finished.

---

## 1. What this task is, and the three things it is not

T1.51 owns **one thing**: a reviewable, re-runnable, one-time transform that
moves the carried set out of a *restored copy* of today's homelab database
(Alembic revision `0006`) into a fresh database built from `0001_baseline.py`,
plus the explicit table-by-table disposition that says what is **not** moved and
why.

It is **not**:

| Not this | Owner | Why the boundary matters |
|---|---|---|
| Re-extracting the graph, embeddings, `technologies`, crossrefs | **T1.52** | T1.51 lands `technologies = '{}'` deliberately (§4). A plan that also rebuilt the graph would make the two tasks' verification counts indistinguishable. |
| Running the rehearsal, the `pg_dump`/restore drill, the restore timing | **T1.53** | T1.51 *consumes* a restored legacy database as an input DSN. It never produces one, and it never runs `pg_dump`. |
| Executing the real cutover, applying the `schema-frozen` tag, filling the freeze date | **T1.54** | The freeze is an event T1.54 triggers after G-B clears. T1.51 must not write a freeze date anywhere, including in the schema inventory. |

A fourth boundary, from the brief's ruling 4: **T1.51 may not edit
`0001_baseline.py`.** The schema is unfrozen and serialises through one owner per
epic. §12 records the one place this plan came close to wanting a baseline change
and why it did not need one.

## 2. Binding constraints on every step

1. **The source is a restored copy, never production.** The transform opens its
   source connection with `default_transaction_read_only=on` set as a connect
   option, so an attempted write fails at the *database*, not at code review. It
   additionally refuses to start when the source and target DSNs resolve to the
   same database, or when the source database is named exactly `darkmem`. These
   are structural guards, not documentation.
2. **The carried set is exactly five tables** — `memories`, `tags`,
   `memory_tags`, `conversations`, `messages` (T1.51's own text: "the carried set
   itself — memories, tags, conversations"; doc 19 §9.1's stance list agrees).
   Widening it is an amendment, not an implementation detail.
3. **Lineage moves verbatim or the run aborts.** No code path may write
   `superseded_by = NULL` or coerce `status` to `'active'`. §6 makes this
   structurally enforced and mutation-proven.
4. **No `::varchar(n)` casts anywhere in the transform.** An over-length value
   raises `string_data_right_truncation` on a plain insert — loud. An explicit
   `::varchar(n)` cast **silently truncates** instead. The one construct that
   converts a loud failure into a silent one is banned by name.
5. **No `COALESCE` on `origin_key`, ever** (§5).
6. **`memories.technologies` and `search_vector` are rebuilt, not carried**
   (doc 19 §4). `technologies` lands `'{}'`; `search_vector` is omitted from the
   insert and the FTS trigger populates it (measured, §7 probe 2).
7. **The transform artifact is a secret.** A dump of the `0006` database contains
   `llm_providers.api_key`, `llm_purpose_configs.api_key` and every
   repository auth token as a `config` row (`app/services/repo_manager.py:161`
   writes `Config(key=repo.auth_token_ref, value={"token": ...})`). No dump,
   fixture, or captured verification report may be committed, and no test fixture
   may embed a real key.
8. **asyncpg needs CAST on raw-SQL params.** The transform is raw SQL by design.
   Every bound parameter Postgres cannot infer takes an explicit `CAST` —
   `CAST(:id AS uuid)`, `CAST(:status AS memory_status)`, `CAST(:meta AS jsonb)`
   — per the standing invariant. Note this is a *parameter* rule and does not
   license rule 4's banned width casts.

### 3.4 The `audit_log → events` transform is declined, on evidence

Doc 19 §4 keeps it as *"a convenience taken only if the mapping is trivial …
skipped without loss otherwise"*. It is not trivial. Three blockers, all read off
the baseline:

1. `events.object_type` is `TEXT NOT NULL` and `audit_log` has no column that
   maps to it. Synthesising `'memory'` for every row is manufacturing a value,
   and `audit_log.memory_id` is nullable, so it is not even reliably true.
2. `events.id` is `BIGINT GENERATED ALWAYS AS IDENTITY` — source ids cannot
   carry, so nothing that referenced them could be reconstructed anyway.
3. `events` is `PARTITION BY RANGE (created_at)` and the baseline creates only
   the current and next month. Every historical month in `audit_log` needs its own
   `events_ensure_partition(...)` call first, or the insert raises *"no partition
   of relation events found for row"*.

Doc 19 §4's own escape clause applies: `events` is authoritative from the cutover
forward either way. **Decision: skipped, recorded, not attempted.** If a later
task wants the history, it is a separate task with its own partition-preflight,
not a bullet inside T1.51.

### 3.5 `config` cannot be bucketed as one table

This is the finding with the most surface area, and doc 19 §9.1 does not close
it — it rules only that *job-state rows* are dropped. The table is a key-value
grab-bag mixing four unrelated classes of thing. Enumerated from the key
constants in `backend/app/`:

| Key class | Example keys | Recommended disposition | Consequence if the recommendation is wrong |
|---|---|---|---|
| Job state | `job:repo_sync`, `job:buffer_flush`, … | **Drop** (doc 19 §9.1, explicit) | None. `JobRegistry` recreates them at runtime. |
| Auth root | `admin_password_hash`, `admin_password_changed_at` | **Drop** | **Load-bearing, and the ordering is a trap.** `/api/v1/setup/*` is gated by `require_uninitialized`, which 403s once `admin_password_hash` exists. Doc 19 §4 requires re-running the wizard for LLM config. Carrying the hash therefore makes the wizard unreachable and the target instance has **no LLM config and no supported way to write one**. If a later ruling wants the hash carried, it must be carried *after* finalize, never with the transform. |
| Secrets | repo auth tokens, keyed by `repositories.auth_token_ref` | **Drop**, because `repositories` is not carried either (§3.2) — an orphan token row would be unreachable | The operator re-enters tokens when re-declaring repos. Flagged so nobody "helpfully" carries the token rows without the repo rows. |
| Runtime settings and honesty state | `feature_flags`, `flag_measurements`, `repo_allowlist`, `system_prompts`, `theme_settings`, `repos_default_local_path`, `code_index_debt`, wiki caches | **Drop** | The two that matter: `get_feature_flags_dict` merges DB **over** defaults, so a carried `feature_flags` row silently overrides every target default for a key whose meaning changed in the rebuild; and `flag_measurements` is T1.57's *never-populated* honesty bar — carrying a stale one would assert a measured win that was never measured under the target. `system_prompts` and `theme_settings` are genuinely operator-authored and their loss is real but small; §13 records it as an open question rather than deciding it silently. |

**Recommended stance: carry nothing from `config`.** The plan proceeds on that
stance; §13 lists it as the one disposition a reviewer should actively confirm
rather than accept.

### 3.6 Closure — the 13 target tables with no source row

Not a bucket; listed so a reviewer's sweep terminates. These are born empty and
nothing carries into them: `projects`, `events`, `memory_relations`,
`memory_access_stats`, `memory_communities`, `memory_community_members`,
`memory_buffer`, `fact_sources`, `knowledge_articles`, `article_citations`,
`project_repositories`, `documents`, `blocks`.

**One exception the transform must handle: `projects`.** It is populated by lazy

structurally — which is precisely why it would go unnoticed. The transform seeds
it from `SELECT DISTINCT project FROM memories` as step 5 of the load.

### 4.3 The sequence, which is the easiest thing here to get wrong

`tags.id` is `SERIAL` on both sides. Carrying ids verbatim leaves `tags_id_seq`
at 1 while rows occupy 1..N. **The first tag created after the cutover then
collides on the primary key.** The failure is loud when it happens and it happens
*after* verification is green — it is a production break that a count-based
check cannot see. The transform runs, in the same transaction as the load:

```
SELECT setval('tags_id_seq', COALESCE((SELECT max(id) FROM tags), 1), (SELECT count(*) > 0 FROM tags))
```

⚠ **`setval` is non-transactional and is not rolled back.** If the transaction
aborts after this statement, the sequence stays advanced. The consequence is a
gap in tag ids on the next successful run — harmless, but it must be stated so a
reviewer is not surprised by the one thing in this transform that survives a
rollback.

## 5. `origin_key` — NULL means *no origin*, not *one origin*

Every carried row lands `origin_key = NULL`. The arithmetic rule, which is the
whole point of the column:

> The corroboration signal is `COUNT(DISTINCT origin_key)`. SQL's
> `COUNT(DISTINCT x)` **skips NULLs**, so a fact whose only sources are carried
> memories has **zero** distinct origins — not one, and emphatically not N.

That is the correct outcome and it is the T1.11 rule applied to history: history
is not evidence of independence. A memory captured before `origin_key` existed
carries no information about which session produced it, so it may not contribute
to an independence count.

**The two ways to get it backwards, both silent:**

1. `COUNT(DISTINCT COALESCE(origin_key, source_ref))` or
   `… COALESCE(origin_key, id::text)` — mints a distinct origin per row and
   inflates every historical fact's independence to N. This is the failure the
   brief names, and it is a one-word edit away from correct.
2. `COUNT(DISTINCT COALESCE(origin_key, 'unknown'))` — collapses to exactly 1,
   which reads defensible ("merges to one origin") but still counts history as
   evidence.

Doc 19 §4's phrasing is *"unknown identity merges to one origin — undercount,
never manufacture agreement"*, which describes T1.11's **live capture** fallback
(`'unknown:' ‖ source ‖ ':' ‖ project`, a real written value). Carried rows are
the stricter case: nothing is written at all, so nothing is counted. The brief
fixes this reading and it binds.

**What T1.51 can and cannot assert.** T1.51 can assert, and will:
`SELECT count(*) FROM memories WHERE origin_key IS NOT NULL` = 0 after load. It
**cannot** test the corroboration arithmetic, because `fact_sources` has no
writer in E1 and the counting query does not exist yet. Constraint 5 (no
`COALESCE` on `origin_key`) is recorded here and routed to **T1.11** (the writer)
and **T2.03** (the verification ladder, which owns `N`); the guard test belongs
where the arithmetic lands. Claiming otherwise would be a plan absorbing a
sibling's work.

## 6. Supersession lineage — how it fails, and what it says

`status` and `superseded_by` move in **one statement**, verbatim. Three layers
enforce it, in order of when they fire.

**Layer 1 — the pre-flight, which is the useful error.** The Postgres error names
one row and aborts everything, which is a bad debugging experience over a
production dump. So before any write, the transform runs against the source and
prints every offending row:

- `status = 'superseded' AND superseded_by IS NULL` — impossible at `0006`
  (the CHECK exists there too, per A.4) but checked anyway, because the input is
  a restored dump and a dump is not the schema.
- `superseded_by` pointing at an id absent from `memories` — a dangling pointer
  the source's `ON DELETE SET NULL` should have prevented.
- A `superseded_by` cycle. Chains are shallow in practice; a cycle is unloadable
  and must be reported, not worked around.

Each failure prints the offending memory ids and the run stops with a non-zero
exit. **It never repairs.**

**Layer 2 — the CHECK, which is the backstop.** `chk_superseded_has_pointer` is
`CHECK (status != 'superseded' OR superseded_by IS NOT NULL)` and it is evaluated
per row, immediately. Measured (§7 probe 4), the exact message is:

```
ERROR:  new row for relation "memories" violates check constraint "chk_superseded_has_pointer"
DETAIL:  Failing row contains (5555…, no pointer, …, superseded, null, …)
```

So even if the pre-flight is wrong, a transform that dropped a pointer cannot
commit. That is what "fails loudly rather than dropping the pointer" means
here: the loudness is structural, not a code convention.

**Layer 3 — the mutation proof.** Per the definition of done, a guard that was
not tried is a guard that was not tested. The test file injects a
`superseded_by = NULL` coercion into the load path, asserts the load raises
`CheckViolation` (not a swallowed warning, not a skipped row), then restores and
asserts it passes. Same for a "coerce status to active on FK failure" branch.

**The self-FK forces the load's shape, and this is the design's load-bearing
decision.** `fk_memories_superseded_by` is **not** declared `DEFERRABLE` in the
baseline, so `SET CONSTRAINTS ALL DEFERRED` does not apply. Measured:

- A single `INSERT … SELECT` carrying an intra-statement forward reference
  **succeeds** — non-deferrable FK triggers fire at end of *statement* (§7
  probe 1).
- A row-at-a-time insert of the same forward reference **fails** with
  `violates foreign key constraint "fk_memories_superseded_by"` (§7 probe 3).

Therefore: **the `memories` load is one `INSERT … SELECT` statement, never a
batched or row-wise loop.** Batching is what a naive streaming implementation
reaches for first, and it breaks on any pair whose pointer crosses a batch
boundary — non-deterministically, depending on batch size and row order. This is
§11.1's most-likely-wrong step.

To make one statement possible over an arbitrarily large source, the transform
streams source rows into **unlogged staging tables inside the target database**
(`cutover_stage_memories`, etc. — no constraints, no triggers, no FKs), then does
the transform and the constrained load as one `INSERT … SELECT` per carried
table. Staging also gives the verification a same-database "before" side to
compare against, with no cross-database join.

Rejected alternative: `postgres_fdw`. It needs `CREATE EXTENSION` (a schema
change the baseline does not declare, which the brief's ruling 4 makes a finding
rather than an edit) and a foreign server carrying credentials.

this task to verify.

| # | Question | Result |
|---|---|---|
| 1 | Does a single `INSERT … SELECT` carry an intra-statement forward self-FK reference? | **Yes.** `INSERT 0 2`, both rows loaded, the superseded row pointing forward at a row inserted later in the same statement. |
| 2 | Does a plain `INSERT` preserve a historical `updated_at`, and does the FTS trigger fire on insert? | **Yes to both.** `updated_at` came back as `2020-06-01`/`2020-07-01` verbatim; `search_vector IS NOT NULL` on every row. |
| 3 | Does a row-at-a-time forward reference fail? | **Yes, loudly.** `ERROR: insert or update on table "memories" violates foreign key constraint "fk_memories_superseded_by"`. |
| 4 | Does dropping the pointer on a superseded row fail? | **Yes, loudly.** `ERROR: new row for relation "memories" violates check constraint "chk_superseded_has_pointer"`. |
| 5 | Does *any* `UPDATE` bump `updated_at` through the trigger? | **Yes** — a no-op `SET content = content` moved `updated_at` from `2020-01-01` to now. |

Probe 5 is the one with consequences outside T1.51; it is §11.2.

## 8. Re-runnability, concretely

**What makes a second run safe: it refuses to be a second run against a dirty
target.** The transform's pre-flight asserts the target's five carried tables are
**empty**. If they are not, it stops and names the non-empty table.

This is the same contract the baseline itself already carries — *"the baseline is
not re-runnable as a diff; it is re-runnable from empty"* — and it is what T1.53's
rehearsal actually needs: each rehearsal pass drops and recreates the target from
`0001_baseline.py`, restores a fresh copy of the source dump, and runs the
transform against a clean pair. Re-runnable means *re-runnable from empty*, not
*idempotent against arbitrary prior state*.

**Rejected: `INSERT … ON CONFLICT (id) DO UPDATE`.** It looks like the
idempotence-friendly choice and it is a trap: an upsert is an `UPDATE`, which
fires `touch_updated_at` (measured, probe 5), so re-running the transform would
silently rewrite every carried memory's `updated_at` to `now()` and destroy the
history the task exists to preserve. `ON CONFLICT DO NOTHING` is worse — it makes
a partially-loaded target look complete.

**A supported reset, so nobody hand-rolls one.** A `--reset` flag deletes the
five carried tables in FK order (`memory_tags`, `messages`, `memories`,
`conversations`, `tags`) inside the same transaction as the subsequent load, then
proceeds. It refuses to run when the target holds any `entities`,
`entity_relations` or embedding-partition rows — that means T1.52 has already run
and a reset would silently orphan a graph whose `memory_ids` point at rows about
to be deleted.

**What a half-finished run leaves behind, precisely:**

| Failure point | Target state |
|---|---|
| Pre-flight fails | Untouched. Nothing was opened for write. |
| Staging load fails | Only `cutover_stage_*` unlogged tables exist, and the transaction that created them rolls back. Nothing in the carried tables. |
| Transform/load fails (CHECK, FK, width, anything) | **Nothing.** The whole staging + transform + load + `setval` + `projects` seed runs in **one transaction**. |
| Process killed mid-transaction | Postgres rolls back on connection loss. An idle-in-transaction connection may hold locks until it times out; the runner sets `idle_in_transaction_session_timeout` so this self-clears. |
| Aborted *after* `setval` | The sequence stays advanced (§4.3). This is the **only** durable residue of a failed run, and it is harmless — a gap in tag ids. |

Stating "nothing" is only honest because the transform commits once. A design
that committed per table would leave a partially-carried database that passes no
check and looks like a smaller corpus.

## 9. The steps

### Step 1 — Layout and the read-only source guard

Create `backend/scripts/cutover/` as a package (`preflight.py`, `stage.py`,
`transform.py`, `verify.py`, `__main__.py`), following the `benchlib` precedent —
a one-time operational tool does not belong in `app/services/`, which is the code
the running application serves (invariant 23). The test lives at
`backend/tests/test_cutover_transform.py`, importing the package via the same
`sys.path` insert `tests/test_isolation_rules.py` already uses. This matters:
`pyproject.toml` sets `testpaths = ["tests"]`, so a test placed under
`scripts/cutover/tests/` would **not** be collected by the floor. It also makes
the task's stated Verify command literally correct.

Land the three source guards from constraint 1 first, with tests: the read-only
connect option (a write attempt on the source raises), same-database refusal, and
the `darkmem` name refusal.

**Verify:** `timeout 600 .venv/bin/python -m pytest tests/test_cutover_transform.py -q`

### Step 2 — Pre-flight, as a standalone read-only pass

Twelve assertions, all read-only, all naming their offending rows:

1. Source `alembic_version.version_num = '0006'` (§4.1's name-reuse trap).
2. Source table set matches A.1's 26 names — a source that is not the schema this
   map was written against stops the run.
3. Target carried tables are empty (§8), unless `--reset`.
4. Target `alembic_version` is the baseline revision and `alembic history` is one
   revision (the freeze has not happened; T1.54 owns that).
5. No `status='superseded' AND superseded_by IS NULL` in the source.
6. No dangling `superseded_by`.
7. No `superseded_by` cycle.
8. `api_keys` count is 0.
9. `knowledge_triples` count is 0.
10. `memory_type` histogram: every non-NULL value is in `MEMORY_TYPES`.
11. Orphan check: every `memory_tags.memory_id`/`tag_id` and every
    `messages.conversation_id` resolves within the source.
12. Row counts for the five carried tables, captured as the run's expected
    totals.

Output is a JSON report to a path the operator names — **never** committed, and
it carries no `config` values, so no secret enters it.

**Verify:** the same pytest command; the pre-flight tests build small fixture
databases and assert each check fires on its own injected defect.

### Step 3 — Staging

Stream the five source tables into unlogged `cutover_stage_*` tables in the
target, with a server-side cursor and a bounded fetch size. No transform here —
staging carries source column names verbatim so the transform is auditable as a
single readable `SELECT` list.

### Step 4 — Transform and load, one transaction, one statement per table

Five `INSERT … SELECT` statements in the order of §3.1, then `setval`, then the
`projects` seed, then `DROP TABLE cutover_stage_*`, then one `COMMIT`.

The `memories` statement is where the column map of §4.1 lives, written out in
full with every column named on both sides — no `SELECT *`, no positional insert.
Constraint 4 (no `::varchar(n)`) and constraint 8 (CAST bound params) apply here.

**Verify:** a test that loads a fixture pair containing a forward-pointing
supersession, a NULL `memory_type`, an `emotions` payload, and a tag id at the
sequence boundary, then asserts every §4.1 row.

### Step 5 — Verification, and its own tests

§10 in full, emitted as a JSON report and as a non-zero exit on any mismatch.

### Step 6 — The mutation proofs

Per §6 layer 3 and GLOBAL §6: commit before mutating, then break each guard on
purpose, watch the test fail, restore, watch it pass, and clear `__pycache__`.
Three guards get this treatment: the pointer-drop coercion, the status coercion,
and the batched-insert regression (change the `memories` load to a loop and
assert the forward-reference test fails).

### Step 7 — Floor, amendment log, commit

Run the task's Verify command, then `pytest -q`, then
`pytest scripts/benchlib/tests -q` (GLOBAL §4 — the floor does **not** collect

reflowing the table. Commit as
`feat(cutover): transform the carried set onto the baseline`, `Task: T1.51` in

## 10. The verification, and the four things a count cannot see

The task's stated method is counts, and counts are necessary. They are **not
sufficient**, and naming the gap is part of the deliverable.

**What counts do detect:** missing rows, extra rows, a table loaded into the
wrong table, a filtered `WHERE` clause left in the transform, a partial load.

**What a count cannot detect, and what covers it instead:**

| Defect a count is blind to | Why counts pass | Cover |
|---|---|---|
| **Column-to-column misassignment.** `llm_summary` → `flags`, or `summary` and `content` swapped. Both are text/jsonb, both non-empty, the row count is identical. | The transform inserts N rows either way. | **Per-column checksums**: `md5(string_agg(col::text, '\|' ORDER BY id))` computed on the staging side under the source name and on the target side under the target name, for every carried column. Equality is a value-level proof, not a cardinality one. |
| **A column NULLed wholesale.** Every `emotions` lands NULL because a rename was mistyped and the target column simply never got written. | Rows still count. | Per-column **NULL count and distinct count** parity, alongside the checksum. A checksum alone over an all-NULL column is stable and looks fine in isolation. |
| **Timestamp drift.** A timezone or interval shift on `created_at` moves the supersession window and the tie-break. | Counts identical, and a *text* checksum can false-pass or false-fail depending on the session `TimeZone` GUC. | Checksum timestamps as `extract(epoch from col)`, **never** `col::text`. Two sessions with different `TimeZone` settings render the same instant differently; two sessions with the *same wrong* setting render a shifted instant identically. |
| **Lineage pointing somewhere else.** The CHECK proves `superseded ⇒ pointer non-null`. It proves nothing about *where* the pointer points. | Every count and both status counts match. | Compare the `(id, superseded_by)` **pair set** as a checksum, plus a per-`status` breakdown, source vs target. |

**Three positive assertions the transform's own design requires:**

- `technologies = '{}'` on **100%** of carried rows — proves a stale derivation
  was not carried.
- `search_vector IS NOT NULL` on **100%** of carried rows — proves the FTS
  trigger fired. If it had not, carried rows would be invisible to hybrid
  search's keyword arm while the semantic arm still returned them: RRF silently
  degraded, no error anywhere.
- `origin_key IS NULL` on **100%** of carried rows (§5).

**And one snapshot, for T1.52's sake.** Before any backfill runs, capture
`(id, memory_type, importance, confidence, updated_at, status, superseded_by)`
for every carried row into an artifact. §11.2 is why.

## 11. Falsification pass

### 11.1 The step most likely to be wrong: the shape of the `memories` load

Step 4's requirement that the `memories` load be **one statement** is the
constraint an implementer is most likely to break, because every instinct about
loading a large table says *batch it*. A batched load works perfectly on every
small fixture, works on most of a real corpus, and fails on exactly those
supersession pairs whose pointer crosses a batch boundary — so the failure is
non-deterministic in batch size and row order.

**Evidence that would show it:** probe 3 already shows the failure mode
(`violates foreign key constraint "fk_memories_superseded_by"`), and it is loud.
The regression test is the one in step 6: change the load to a loop, assert the
forward-reference fixture fails. If that test passes with a batched load, the
fixture does not contain a boundary-crossing pair and the test is worthless.

Runner-up: the `tags_id_seq` `setval` (§4.3), which is easy to forget entirely
and whose failure is deferred to the first post-cutover tag write.

### 11.2 The silent failure mode that matters most: T1.52 overwrites four carried columns

**This is the finding I consider most dangerous, and it is not in T1.51's own
code at all.**

`ProcessingPipeline.process_batch` Phase 5, savepoint A
(`app/services/pipeline.py`) unconditionally executes, for every memory it
processes:

```
mem_record.memory_type = resolved_memory_type          # normalize_memory_type(entry_type or extracted)
mem_record.importance  = float(extracted_importance)   # when extraction emits one
mem_record.confidence  = estimate_confidence(content, resolved_memory_type)
```

T1.52's backfill re-extracts every carried memory through this exact path.
Therefore:

- **`memory_type`** — a carried `insight` or `profile` becomes `fact`
  (no legacy-map entry, so it falls through to the default), and a carried NULL
  becomes `fact` outright. The careful decision in §4.1 not to rewrite the column
  is undone one task later.
- **`importance`** — the carried value is replaced by the extractor's. This is
  the column T2.30 activates as a ranking arm; its history is gone before anyone
  measures it.
- **`confidence`** — recomputed from content.
- **`updated_at`** — any ORM mutation is an `UPDATE`, and `touch_updated_at`
  fires (measured, probe 5). Every carried memory's `updated_at` becomes the
  backfill's wall-clock time.

**Why it is silent.** Nothing errors. The row counts match. `pipeline_failures`
stays empty. The extraction bench holds tolerance, because it runs against
`gold.json` and not against the carried corpus. Every check T1.52's Done-when
names comes back green while four columns of unrecoverable history have been
overwritten, and the only way to notice is to have kept a snapshot — which is why
§10 requires one and why the snapshot must be taken by T1.51, before T1.52 exists
to take it.

A fifth column is in the same family and worth naming separately: **`status` /
`superseded_by` are not frozen after T1.51 either.** T1.52's re-extraction runs
`detect_supersessions`, and the rebuilt graph may emit a `REPLACES`-family
relation the old extractor did not. Candidates within the 90-day window can
therefore be flipped to `superseded` after the cutover. That is *legitimate new
derivation*, not a bug — but "lineage carries verbatim" is true at T1.51's
boundary and not after, and a reviewer comparing the source dump to a
post-backfill database will see a diff and be right to ask.

**Routing.** These are recorded as amendments against **T1.52** (which must
either preserve the four columns or state the overwrite as intended) and
**T1.53** (whose rehearsal must diff lineage before and after the backfill and
report the delta rather than assume zero). T1.51's own obligation is the
snapshot and this record.

### 11.3 Runner-up silent mode: an empty `technologies` that nobody notices

If the cutover completes and the backfill never runs — or runs partially —
every carried memory sits with `technologies = '{}'`. Consequences, all
silent: supersession's overlap predicate (rule 3) matches nothing, so no carried
memory can ever supersede another; the retrieval technology filter returns empty;
and the hybrid semantic arm still works, so the system *feels* fine. Nothing logs
and nothing errors.

The cover is T1.52's own "a partial backfill is visibly partial" Done-when, plus
T1.51's positive assertion that `technologies` is empty on 100% of rows — which
makes the state a *known, asserted* condition on the way in rather than a
discovery on the way out.

## 12. Size call

**One `L`, with one named condition.**

The design decisions are now made and written down, which is most of what made
this task an `L`. What remains is four modules and a test file — roughly 700–900
lines of code plus tests — with no algorithmic difficulty and no new subsystem.
The five behavioural unknowns that could have expanded it (self-FK statement
semantics, insert-time trigger behaviour on both triggers, the CHECK's failure
text, the `updated_at` bump) are measured in §7 rather than left to discovery.

**The condition.** If the controller rules that **any** `config` key-class must
be carried (§3.5 — repository auth tokens and `system_prompts` are the two live
candidates), T1.51 gains a second column map *and* a credential-handling surface
with its own review requirements, and it should split:

- **T1.51** — the five carried tables, the bucket enumeration, the verification.
- **T1.51b** — the `config`-row disposition, per key-class, including secret
  handling and the `admin_password_hash`/wizard ordering trap.

On the recommended stance (carry nothing from `config`), no split is needed.

Two things this plan deliberately did **not** absorb, and which would each have
pushed it past one `L`: the `audit_log → events` transform (§3.4, declined on
three concrete blockers, per doc 19 §4's own escape clause), and any
`repositories` carry (§3.2).
