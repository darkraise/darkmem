## 1. What this task is, and the three things it is not

T1.51 owns **one thing**: a reviewable, re-runnable, one-time transform that
moves the carried set out of a *restored copy* of today's homelab database
(Alembic revision `0006`) into a fresh database built from `0001_baseline.py`,
plus the explicit table-by-table disposition that says what is **not** moved and
why.

It is **not**:

| Not this | Owner | Why the boundary matters |
|---|---|---|
| Re-extracting the graph, embeddings, `technologies`, crossrefs | **T1.52** | T1.51 lands `technologies = '{}'` deliberately (§4). A plan that also rebuilt the graph would make the two tasks' verification counts indistinguishable. |
| Running the rehearsal, the `pg_dump`/restore drill, the restore timing | **T1.53** | T1.51 *consumes* a restored legacy database as an input DSN. It never produces one, and it never runs `pg_dump`. |
| Executing the real cutover, applying the `schema-frozen` tag, filling the freeze date | **T1.54** | The freeze is an event T1.54 triggers after G-B clears. T1.51 must not write a freeze date anywhere, including in the schema inventory. |

A fourth boundary, from the brief's ruling 4: **T1.51 may not edit
`0001_baseline.py`.** The schema is unfrozen and serialises through one owner per
epic. §6's rejection of `postgres_fdw` is the one place this plan came close to
wanting a baseline change — it needs a `CREATE EXTENSION` the baseline does not
declare — and the staging-table design is why it did not need one.

## 2. Binding constraints on every step

1. **The source is a restored copy, never production.** The transform opens its
   source connection with `default_transaction_read_only=on` set as a connect
   option, so an attempted write fails at the *database*, not at code review. It
   additionally refuses to start when the source and target DSNs resolve to the
   same database, or when the source database is named exactly `darkmem`. These
   are structural guards, not documentation.
2. **The carried set is exactly five tables** — `memories`, `tags`,
   `memory_tags`, `conversations`, `messages` (T1.51's own text: "the carried set
   itself — memories, tags, conversations"; doc 19 §9.1's stance list agrees).
   Widening it is an amendment, not an implementation detail.
3. **Lineage moves verbatim or the run aborts.** No code path may write
   `superseded_by = NULL` or coerce `status` to `'active'`. §6 makes this
   structurally enforced and mutation-proven.
4. **No `::varchar(n)` casts anywhere in the transform.** An over-length value
   raises `string_data_right_truncation` on a plain insert — loud. An explicit
   `::varchar(n)` cast **silently truncates** instead. The one construct that
   converts a loud failure into a silent one is banned by name.
5. **No `COALESCE` on `origin_key`, ever** (§5).
6. **`memories.technologies` and `search_vector` are rebuilt, not carried**
   (doc 19 §4). `technologies` lands `'{}'`; `search_vector` is omitted from the
   insert and the FTS trigger populates it (measured, §7 probe 2).
7. **The transform artifact is a secret.** A dump of the `0006` database contains
   `llm_providers.api_key`, `llm_purpose_configs.api_key` and every
   repository auth token as a `config` row (`app/services/repo_manager.py:161`
   writes `Config(key=repo.auth_token_ref, value={"token": ...})`). No dump,
   fixture, or captured verification report may be committed, and no test fixture
   may embed a real key.
8. **asyncpg needs CAST on raw-SQL params.** The transform is raw SQL by design.
   Every bound parameter Postgres cannot infer takes an explicit `CAST` —
   `CAST(:id AS uuid)`, `CAST(:status AS memory_status)`, `CAST(:meta AS jsonb)`
   — per the standing invariant. Note this is a *parameter* rule and does not
   license rule 4's banned width casts.
9. **No custom asyncpg type codecs on the source or staging connections, and the
   session GUCs are pinned on every connection the run opens.** Both halves were
   measured (§7 probes 6–7) and both exist because carried values pass through
   Python on the source→staging leg.
   - *Codecs.* Under asyncpg's **default** codecs a `jsonb` value round-trips as
     an opaque `str` and is byte-identical after the round trip, including a
     30-digit integer. Install a `json.loads`/`json.dumps` codec — which a
     transform author reaches for to "work with dicts" — and
     `{"prec": 1.000000000000000000000000001}` comes back as `{"prec": 1.0}`,
     because Postgres stores `jsonb` numerics as arbitrary-precision `numeric`
     and a Python `float` is a double. Measured, §7 probe 6. The transform
     therefore treats every carried value as opaque: no codec registration, no
     `json.loads`, no `datetime` arithmetic, no re-encoding. Values are read and
     written back unexamined.
   - *GUCs.* Every connection sets `TimeZone='UTC'`, `DateStyle='ISO, MDY'`,
     `extra_float_digits=3` and `bytea_output='hex'` before any aggregate runs.
     This matters because §10's source↔staging parity check compares strings
     produced by **two different sessions on two different databases**: a
     `timestamptz` rendered as text under `TimeZone='UTC'` and under
     `'Asia/Tokyo'` gives different md5s for the same instant (measured, §7
     probe 7). §10 uses `extract(epoch …)` for timestamps for the same reason,
     but pinning the GUCs removes the whole class rather than one member of it.

### 3.4 The `audit_log → events` transform is declined, on evidence

Doc 19 §4 keeps it as *"a convenience taken only if the mapping is trivial …
skipped without loss otherwise"*. It is not trivial. Three blockers, all read off
the baseline:

1. `events.object_type` is `TEXT NOT NULL` and `audit_log` has no column that
   maps to it. Synthesising `'memory'` for every row is manufacturing a value,
   and `audit_log.memory_id` is nullable, so it is not even reliably true.
2. `events.id` is `BIGINT GENERATED ALWAYS AS IDENTITY` — source ids cannot
   carry, so nothing that referenced them could be reconstructed anyway.
3. `events` is `PARTITION BY RANGE (created_at)` and the baseline creates only
   the current and next month. Every historical month in `audit_log` needs its own
   `events_ensure_partition(...)` call first, or the insert raises *"no partition
   of relation events found for row"*.

Doc 19 §4's own escape clause applies: `events` is authoritative from the cutover
forward either way. **Decision: skipped, recorded, not attempted.** If a later
task wants the history, it is a separate task with its own partition-preflight,
not a bullet inside T1.51.

### 3.5 `config` cannot be bucketed as one table

This is the finding with the most surface area, and doc 19 §9.1 does not close
it — it rules only that *job-state rows* are dropped. The table is a key-value
grab-bag mixing four unrelated classes of thing. Enumerated from the key
constants in `backend/app/`:

| Key class | Example keys | Recommended disposition | Consequence if the recommendation is wrong |
|---|---|---|---|
| Job state | `job:repo_sync`, `job:buffer_flush`, … | **Drop** (doc 19 §9.1, explicit) | None. `JobRegistry` recreates them at runtime. |
| Auth root | `admin_password_hash`, `admin_password_changed_at` | **Drop** | **Load-bearing, and the ordering is a trap.** `/api/v1/setup/*` is gated by `require_uninitialized`, which 403s once `admin_password_hash` exists. Doc 19 §4 requires re-running the wizard for LLM config. Carrying the hash therefore makes the wizard unreachable and the target instance has **no LLM config and no supported way to write one**. If a later ruling wants the hash carried, it must be carried *after* finalize, never with the transform. |
| Secrets | repo auth tokens, keyed by `repositories.auth_token_ref` | **Drop**, because `repositories` is not carried either (§3.2) — an orphan token row would be unreachable | The operator re-enters tokens when re-declaring repos. Flagged so nobody "helpfully" carries the token rows without the repo rows. |
| Runtime settings and honesty state | `feature_flags`, `flag_measurements`, `repo_allowlist`, `system_prompts`, `theme_settings`, `repos_default_local_path`, `code_index_debt`, wiki caches | **Drop** | The two that matter: `get_feature_flags_dict` merges DB **over** defaults, so a carried `feature_flags` row silently overrides every target default for a key whose meaning changed in the rebuild; and `flag_measurements` is T1.57's *never-populated* honesty bar — carrying a stale one would assert a measured win that was never measured under the target. `system_prompts` and `theme_settings` are genuinely operator-authored and their loss is real but small; §13 records it as an open question rather than deciding it silently. |

**Recommended stance: carry nothing from `config`.** The plan proceeds on that
stance; §13 lists it as the one disposition a reviewer should actively confirm
rather than accept.

### 3.6 Closure — the 13 target tables with no source row

Not a bucket; listed so a reviewer's sweep terminates. These are born empty and
nothing carries into them: `projects`, `events`, `memory_relations`,
`memory_access_stats`, `memory_communities`, `memory_community_members`,
`memory_buffer`, `fact_sources`, `knowledge_articles`, `article_citations`,
`project_repositories`, `documents`, `blocks`.

**One exception the transform must handle: `projects`.** It is populated by lazy
registration on capture (`INSERT … ON CONFLICT DO NOTHING`). Carried rows never
go through capture, so after a cutover `memories` would reference N distinct
projects while `projects` holds zero rows. There is no FK, so nothing breaks
structurally — which is precisely why it would go unnoticed. The transform seeds
it from `SELECT DISTINCT project FROM memories` as step 5 of the load.

**The seed is `ON CONFLICT (name) DO NOTHING`, and the reason is the `--reset`
path.** `projects_pkey` is `PRIMARY KEY (name)` (read from the catalog), and
`--reset` (§8) deletes only the five carried tables — `projects` is not one of
them, so its rows survive a reset. A bare `INSERT` would then raise a PK
violation on the second run: loud, but a *spurious* failure that tells the
operator nothing and invites deleting `projects` by hand. `DO NOTHING` is
correct rather than merely convenient, because the row it declines to write is
byte-identical to the row already there — `projects.name` is the whole key.

The residue `DO NOTHING` leaves is a **stale project row**: a project that
existed in an earlier reset's carried set and does not appear in this one. It is
inert (no FK, nothing reads a project row that no memory references) and §10's
positive assertions state it explicitly rather than leaving it to be discovered:
every `DISTINCT memories.project` has a `projects` row, and any `projects` row
no memory references is **reported, not deleted**. Deleting it would be the tool
silently removing a row it did not create.

### 4.3 The sequence, which is the easiest thing here to get wrong

`tags.id` is `SERIAL` on both sides. Carrying ids verbatim leaves `tags_id_seq`
at 1 while rows occupy 1..N. **The first tag created after the cutover then
collides on the primary key.** The failure is loud when it happens and it happens
*after* verification is green — it is a production break that a count-based
check cannot see. The transform runs, in the same transaction as the load:

```
SELECT setval('tags_id_seq', COALESCE((SELECT max(id) FROM tags), 1), (SELECT count(*) > 0 FROM tags))
```

⚠ **`setval` is non-transactional and is not rolled back.** If the transaction
aborts after this statement, the sequence stays advanced. The consequence is a
gap in tag ids on the next successful run — harmless, but it must be stated so a
reviewer is not surprised by the one thing in this transform that survives a
rollback.

## 5. `origin_key` — NULL means *no origin*, not *one origin*

Every carried row lands `origin_key = NULL`. The arithmetic rule, which is the
whole point of the column:

> The corroboration signal is `COUNT(DISTINCT origin_key)`. SQL's
> `COUNT(DISTINCT x)` **skips NULLs**, so a fact whose only sources are carried
> memories has **zero** distinct origins — not one, and emphatically not N.

That is the correct outcome and it is the T1.11 rule applied to history: history
is not evidence of independence. A memory captured before `origin_key` existed
carries no information about which session produced it, so it may not contribute
to an independence count.

**The two ways to get it backwards, both silent:**

1. `COUNT(DISTINCT COALESCE(origin_key, source_ref))` or
   `… COALESCE(origin_key, id::text)` — mints a distinct origin per row and
   inflates every historical fact's independence to N. This is the failure the
   brief names, and it is a one-word edit away from correct.
2. `COUNT(DISTINCT COALESCE(origin_key, 'unknown'))` — collapses to exactly 1,
   which reads defensible ("merges to one origin") but still counts history as
   evidence.

Doc 19 §4's phrasing is *"unknown identity merges to one origin — undercount,
never manufacture agreement"*, which describes T1.11's **live capture** fallback
(`'unknown:' ‖ source ‖ ':' ‖ project`, a real written value). Carried rows are
the stricter case: nothing is written at all, so nothing is counted. The brief
fixes this reading and it binds.

**What T1.51 can and cannot assert.** T1.51 can assert, and will:
`SELECT count(*) FROM memories WHERE origin_key IS NOT NULL` = 0 after load. It
**cannot** test the corroboration arithmetic, because `fact_sources` has no
writer in E1 and the counting query does not exist yet. Constraint 5 (no
`COALESCE` on `origin_key`) is recorded here and routed to **T1.11** (the writer)
and **T2.03** (the verification ladder, which owns `N`); the guard test belongs
where the arithmetic lands. Claiming otherwise would be a plan absorbing a
sibling's work.

## 6. Supersession lineage — how it fails, and what it says

`status` and `superseded_by` move in **one statement**, verbatim. Three layers
enforce it, in order of when they fire.

**Layer 1 — the pre-flight, which is the useful error.** The Postgres error names
one row and aborts everything, which is a bad debugging experience over a
production dump. So before any write, the transform runs against the source and
prints every offending row:

- `status = 'superseded' AND superseded_by IS NULL` — impossible at `0006`
  (the CHECK exists there too, per A.4) but checked anyway, because the input is
  a restored dump and a dump is not the schema.
- `superseded_by` pointing at an id absent from `memories` — a dangling pointer
  the source's `ON DELETE SET NULL` should have prevented.
- A `superseded_by` cycle. Chains are shallow in practice; a cycle is unloadable
  and must be reported, not worked around.

Each failure prints the offending memory ids and the run stops with a non-zero
exit. **It never repairs.**

**Layer 2 — the CHECK, which is the backstop.** `chk_superseded_has_pointer` is
`CHECK (status != 'superseded' OR superseded_by IS NOT NULL)` and it is evaluated
per row, immediately. Measured (§7 probe 4), the exact message is:

```
ERROR:  new row for relation "memories" violates check constraint "chk_superseded_has_pointer"
DETAIL:  Failing row contains (5555…, no pointer, …, superseded, null, …)
```

So even if the pre-flight is wrong, a transform that dropped a pointer cannot
commit. That is what "fails loudly rather than dropping the pointer" means
here: the loudness is structural, not a code convention.

**Layer 3 — the mutation proof.** Per the definition of done, a guard that was
not tried is a guard that was not tested. The test file injects a
`superseded_by = NULL` coercion into the load path, asserts the load raises
`CheckViolation` (not a swallowed warning, not a skipped row), then restores and
asserts it passes. Same for a "coerce status to active on FK failure" branch.

**The self-FK forces the load's shape, and this is the design's load-bearing
decision.** `fk_memories_superseded_by` is **not** declared `DEFERRABLE` in the
baseline, so `SET CONSTRAINTS ALL DEFERRED` does not apply. Measured:

- A single `INSERT … SELECT` carrying an intra-statement forward reference
  **succeeds** — non-deferrable FK triggers fire at end of *statement* (§7
  probe 1).
- A row-at-a-time insert of the same forward reference **fails** with
  `violates foreign key constraint "fk_memories_superseded_by"` (§7 probe 3).

Therefore: **the `memories` load is one `INSERT … SELECT` statement, never a
batched or row-wise loop.** Batching is what a naive streaming implementation
reaches for first, and it breaks on any pair whose pointer crosses a batch
boundary — non-deterministically, depending on batch size and row order. This is
§11.1's most-likely-wrong step.

To make one statement possible over an arbitrarily large source, the transform
streams source rows into **unlogged staging tables inside the target database**
(`cutover_stage_memories`, etc. — no constraints, no triggers, no FKs), then does
the transform and the constrained load as one `INSERT … SELECT` per carried
table. Staging also gives the verification a same-database "before" side to
compare against, with no cross-database join.

Rejected alternative: `postgres_fdw`. It needs `CREATE EXTENSION` (a schema
change the baseline does not declare, which the brief's ruling 4 makes a finding
rather than an edit) and a foreign server carrying credentials.

## 7. Measured Postgres behaviour, 2026-07-28

Probes 1–5 ran against a throwaway `cutprobe` schema in `darkmem_test_3`,
reproducing the baseline's `memories` shape — the enum, both triggers, the CHECK
and the self-FK. Probes 6–9 were added by the revision and ran against a
throwaway `revprobe` schema in `darkmem_test_2`. Both schemas were dropped
afterwards and the residue count was checked at 0. **These are measurements of
Postgres, not verifications of a step**; the steps in §9 are for whoever executes
this task to verify.

| # | Question | Result |
|---|---|---|
| 1 | Does a single `INSERT … SELECT` carry an intra-statement forward self-FK reference? | **Yes.** `INSERT 0 2`, both rows loaded, the superseded row pointing forward at a row inserted later in the same statement. |
| 2 | Does a plain `INSERT` preserve a historical `updated_at`, and does the FTS trigger fire on insert? | **Yes to both.** `updated_at` came back as `2020-06-01`/`2020-07-01` verbatim; `search_vector IS NOT NULL` on every row. |
| 3 | Does a row-at-a-time forward reference fail? | **Yes, loudly.** `ERROR: insert or update on table "memories" violates foreign key constraint "fk_memories_superseded_by"`. |
| 4 | Does dropping the pointer on a superseded row fail? | **Yes, loudly.** `ERROR: new row for relation "memories" violates check constraint "chk_superseded_has_pointer"`. |
| 5 | Does *any* `UPDATE` bump `updated_at` through the trigger? | **Yes** — a no-op `SET content = content` moved `updated_at` from `2020-01-01` to now. |
| 6 | Does a `jsonb` value survive a Python-mediated round trip? | **Codec-dependent.** Under asyncpg's **default** codecs: 3 rows in, 3 identical `::text` back, **0 mismatches** — including `{"big": 123456789012345678901234567890}`. Under a `json.loads`/`json.dumps` codec: **1 mismatch**, `{"prec": 1.000000000000000000000000001}` → `{"prec": 1.0}`. The 30-digit integer survived even there, because a Python `int` is arbitrary-precision; it is **decimal precision beyond a double**, not integer magnitude, that is lost. Constraint 9. |
| 7 | Does the `TimeZone` GUC change a timestamp checksum? | **Yes for text, no for epoch.** `md5(string_agg(ts::text …))` differs between `TimeZone='UTC'` and `'Asia/Tokyo'`; `md5(string_agg(extract(epoch from ts)::text …))` is identical. Constraint 9 and §10. |
| 8 | Does `string_agg(col::text …)` see a NULL-position swap? | **No, and neither do the two checks beside it.** Two 3-row tables, one with `('x', NULL, 'y')` and one with `(NULL, 'x', 'y')`, produce the **same** md5, the **same** NULL count (1), the **same** distinct count (2) and the same row count. `md5(string_agg(COALESCE(col::text,'␀') …))` differs. §10. |
| 9 | What does the checksum of a wholly-NULL column return? | **`NULL`.** `string_agg` over all-NULL input returns NULL, so `md5(...)` is NULL — and a client-side `None == None` compares **equal**, which is the F2/F6 failure wearing a second hat. The `COALESCE` form returns a real hash (`0ab1000c…`) for the same input. §10 compares only the `COALESCE` form, and treats a NULL checksum as a hard error. |

Probe 5 is the one with consequences outside T1.51; it is §11.2. Probes 6 and 9
are the two that changed the verification design, and neither was reachable from
reading the plan — they had to be run.

## 8. Re-runnability, concretely

**What makes a second run safe: it refuses to be a second run against a dirty
target.** The transform's pre-flight asserts the target's five carried tables are
**empty**. If they are not, it stops and names the non-empty table.

This is the same contract the baseline itself already carries — *"the baseline is
not re-runnable as a diff; it is re-runnable from empty"* — and it is what T1.53's
rehearsal actually needs: each rehearsal pass drops and recreates the target from
`0001_baseline.py`, restores a fresh copy of the source dump, and runs the
transform against a clean pair. Re-runnable means *re-runnable from empty*, not
*idempotent against arbitrary prior state*.

**Rejected: `INSERT … ON CONFLICT (id) DO UPDATE`.** It looks like the
idempotence-friendly choice and it is a trap: an upsert is an `UPDATE`, which
fires `touch_updated_at` (measured, probe 5), so re-running the transform would
silently rewrite every carried memory's `updated_at` to `now()` and destroy the
history the task exists to preserve. `ON CONFLICT DO NOTHING` is worse — it makes
a partially-loaded target look complete.

**A supported reset, so nobody hand-rolls one.** A `--reset` flag deletes the
five carried tables in FK order (`memory_tags`, `messages`, `memories`,
`conversations`, `tags`) inside the same transaction as the subsequent load, then
proceeds.

### 8.1 `--reset` is the one path where this tool can destroy real data

Everything else in this plan either refuses to start or aborts a transaction.
`--reset` deletes rows on purpose, so its guard is the only thing standing
between a mistaken re-run and unrecoverable loss. **It is specified here at
length because it is the highest-severity surface in the task, not because it is
the largest.**

**The window that makes the original guard insufficient.** The first draft
refused only when `entities`, `entity_relations` or the embedding partitions held
rows — a proxy for "T1.52 has already run". Between the transform completing and
the backfill producing its first entity, all three are empty, so the refusal
never fires. If the application is up in that window — and **nothing in T1.51,
T1.52 or T1.54 says it is not**, which is the actual defect — users capture new
memories, conversations and messages into the target. A `--reset` run then
deletes those captures, reloads the dump, and **every check in §10 comes back
green**, because §10 compares the target against the staging copy of the dump and
the new rows were never in the dump. Green report, real loss, no error anywhere.

**The guard, and why it is an id-set difference rather than a timestamp.** The
review proposed refusing when a carried-table row is newer than the staging
snapshot's max timestamps. That is directionally right and it is not the
strongest check available. At `--reset` time staging is already populated (§9
step 3 precedes step 4), so the transform can ask the exact question instead of a
proxy for it: **is there a row in the target that is not in the dump?**

Both of these run after staging and before the first `DELETE`, and either one
refuses the run:

1. **Unknown rows.** For each of the five carried tables, count target rows whose
   key does not appear in the corresponding `cutover_stage_*` table. A non-zero
   count means the target holds rows this dump never contained. Exact — it
   catches a post-cutover capture whose `created_at` was backdated, which a
   max-timestamp comparison does not, and it catches a reset pointed at a
   *different* dump, which nothing else here would.
2. **Edited rows.** For rows present in both, count those whose target
   `updated_at` is later than the staging row's. A post-cutover **edit** to a
   carried memory keeps its id, so check 1 cannot see it; the edit is destroyed
   by the reload just the same.

The refusal names the offending ids and exits non-zero. The override is an
explicit `--i-know-rows-will-be-lost` flag that must be given **together with**
the row count the tool just reported, so it cannot be pasted from a previous run
into a situation with a different count.

**The derivation-present refusal, corrected against the catalog.** The review
noted the refusal list omits `memory_crossrefs`. Reading
`pg_constraint` on a database migrated to the baseline shows the omission is
wider than that: **five base tables** carry an `ON DELETE CASCADE` FK into
`memories(id)` — plus the `memory_embeddings__<slug>` children, whose FK comes
from the table template rather than the baseline — so deleting a memory silently
deletes their rows too.

| Table | FK into `memories` | In the original refusal list? |
|---|---|---|
| `memory_tags` | `ON DELETE CASCADE` | carried — deleted deliberately |
| `memory_crossrefs` | two FKs, both `CASCADE` | **no** (the review's finding) |
| `memory_access_stats` | `ON DELETE CASCADE` | **no** |
| `memory_relations` | two composite FKs, both `CASCADE` | **no** |
| `memory_community_members` | `ON DELETE CASCADE` | **no** |
| `memory_embeddings__<slug>` | `ON DELETE CASCADE` (table template) | yes |

`entities.memory_ids` and `entity_relations.memory_ids` are arrays, not FKs, so
they are *not* cascaded — they are left dangling, which is the case the original
list was written for. Both failure shapes are real and they are different:
cascaded rows vanish, array-referenced rows survive pointing at nothing.

So `--reset` refuses when **any** of these hold a row: `entities`,
`entity_relations`, `memory_crossrefs`, `memory_access_stats`,
`memory_relations`, `memory_community_members`, or any
`memory_embeddings__<slug>` partition. It names which. `memory_communities`
survives as a parent whose members were cascaded away, so the refusal report
mentions it even though it is not itself a refusal trigger.

**What a reset does not delete.** `projects` (§3.6 — hence the
`ON CONFLICT DO NOTHING` seed and the stale-row report) and `tags_id_seq`, which
is non-transactional and stays advanced (§4.3). Both are stated so the operator
is not surprised by residue after a reset that reported success.

**What a half-finished run leaves behind, precisely:**

| Failure point | Target state |
|---|---|
| Pre-flight fails | Untouched. Nothing was opened for write. |
| Staging load fails | Only `cutover_stage_*` unlogged tables exist, and the transaction that created them rolls back. Nothing in the carried tables. |
| Source↔staging parity fails (§10.1) | **Nothing**, and this gate deliberately runs before the first carried-table write. |
| Transform/load fails (CHECK, FK, width, anything) | **Nothing.** The whole staging + transform + load + verification + `setval` + `projects` seed runs in **one transaction**. |
| Staging↔target parity or a positive assertion fails (§10.2, §10.3) | **Nothing.** This row exists because of the revision: verification now runs *inside* the transaction and *before* the `setval`, so a value-level mismatch aborts rather than reporting on a committed database. |
| A post-seed assertion fails (§10.4) | The load rolls back; the sequence stays advanced (below). |
| Process killed mid-transaction | Postgres rolls back on connection loss. An idle-in-transaction connection may hold locks until it times out; the runner sets `idle_in_transaction_session_timeout` so this self-clears. |
| Aborted *after* `setval` | The sequence stays advanced (§4.3). This is the **only** durable residue of a failed run, and it is harmless — a gap in tag ids. |

Stating "nothing" is only honest because the transform commits once. A design
that committed per table would leave a partially-carried database that passes no
check and looks like a smaller corpus.

## 9. The steps

### Step 1 — Layout and the read-only source guard

Create `backend/scripts/cutover/` as a package (`preflight.py`, `stage.py`,
`transform.py`, `verify.py`, `__main__.py`), following the `benchlib` precedent —
a one-time operational tool does not belong in `app/services/`, which is the code
the running application serves (invariant 23). The test lives at
`backend/tests/test_cutover_transform.py`, importing the package via the same
`sys.path` insert `tests/test_isolation_rules.py` already uses. This matters:
`pyproject.toml` sets `testpaths = ["tests"]`, so a test placed under
`scripts/cutover/tests/` would **not** be collected by the floor. It also makes
the task's stated Verify command literally correct.

Land the three source guards from constraint 1 first, with tests: the read-only
connect option (a write attempt on the source raises), same-database refusal, and
the `darkmem` name refusal.

**Verify:** `timeout 600 .venv/bin/python -m pytest tests/test_cutover_transform.py -q`

### Step 2 — Pre-flight, as a standalone read-only pass

Thirteen assertions, all read-only, all naming their offending rows:

1. Source `alembic_version.version_num = '0006'` (§4.1's name-reuse trap).
2. **Source table set, as a subset-plus-pattern check — not set equality.** All
   26 of A.1's names are present; every *extra* table matches one of the four
   per-fingerprint child-family prefixes (`memory_embeddings__%`,
   `entity_embeddings__%`, `code_chunk_embeddings__%`,
   `entity_embedding_cache__%`); any other extra stops the run and is named.
   Set equality is wrong and would false-abort on **every genuine source**: A.1
   deliberately excludes the runtime-minted child tables (§3.2 says so itself)
   because it was extracted from a freshly migrated database with zero
   fingerprints registered, and the real homelab database has them. The risk a
   false abort creates is not the abort — it is the ad-hoc loosening an operator
   applies under time pressure at 2am, which is how a genuinely foreign table
   gets waved through. The four prefixes are enumerated rather than accepting a
   bare `%\_\_%`, because the child names are minted by `child_table(parent,
   fingerprint)` against exactly four known parents; a wildcard would also admit
   any hand-made `something__backup`.
3. Target carried tables are empty (§8). Under `--reset` this assertion is
   replaced, and **the replacement splits across two moments** because half of it
   needs staging, which does not exist yet at pre-flight time: the
   derivation-present refusal (§8.1's seven-table list) runs **here**, and §8.1's
   two dump-membership checks run **after staging and before the first
   `DELETE`**. Running the cheap refusal first means an obviously-unsafe reset
   stops before the run pays for a staging load.
4. Target `alembic_version` is the baseline revision and `alembic history` is one
   revision (the freeze has not happened; T1.54 owns that).
5. No `status='superseded' AND superseded_by IS NULL` in the source.
6. No dangling `superseded_by`.
7. No `superseded_by` cycle.
8. `api_keys` count is 0.
9. `knowledge_triples` count is 0.
10. `memory_type` histogram: every non-NULL value is in `MEMORY_TYPES`.
11. Orphan check: every `memory_tags.memory_id`/`tag_id` and every
    `messages.conversation_id` resolves within the source.
12. Row counts for the five carried tables, captured as the run's expected
    totals.
13. **Sanitized repository inventory** — not an assertion but an emission, and it
    closes open question 3. `repositories` is not carried (§3.2); the operator
    re-declares it by hand before T1.54, and today that re-declaration is
    guesswork against a database that is about to be replaced. The pre-flight is
    already reading the source, so it emits, per repository row: `name`, `url`,
    `provider`, `default_branch`, `local_path`, `auto_sync`, and a **derived
    boolean** `has_auth_token` = `auth_token_ref IS NOT NULL`. That turns the
    re-declaration into a checklist that also says which repos need a token
    re-entered. **It emits no token and no `auth_token_ref` value** — the token
    itself lives in a `config` row keyed by that ref
    (`app/services/repo_manager.py:161`), and the ref is the pointer to it, so
    neither goes in a report the operator will save to a file. Constraint 7
    binds this line as much as any other.

Output is a JSON report to a path the operator names — **never** committed, and
it carries no `config` values and no `auth_token_ref`, so no secret enters it.

**Verify:** the same pytest command; the pre-flight tests build small fixture
databases and assert each check fires on its own injected defect.

### Step 3 — Staging, then the source↔staging parity gate

Stream the five source tables into unlogged `cutover_stage_*` tables in the
target, with a server-side cursor and a bounded fetch size. No transform here —
staging carries source column names verbatim so the transform is auditable as a
single readable `SELECT` list, and so the parity check below compares like with
like.

**Then, before anything is written to a carried table, run §10.1's source↔staging
parity check.** This is the first gate for a reason: the source→staging leg is
the only place in the run where a carried value passes through Python, and a
defect there lands **identically** in staging and in the target, so every later
check agrees with itself and passes. Failing here means nothing was written to a
carried table at all — the cheapest possible place to stop.

### Step 4 — Transform, load and verify, all inside one transaction

The runtime order inside the single transaction is:

| # | Action | Why here |
|---|---|---|
| 0 | Under `--reset` only: §8.1's two dump-membership checks, then the five `DELETE`s in FK order | The checks need staging, so they cannot live in the pre-flight; the `DELETE`s share this transaction so a later abort restores the target |
| 1 | Five `INSERT … SELECT` statements in the order of §3.1 | §6 — one statement per table, never batched |
| 2 | **§10.2 staging↔target parity + §10.3 positive assertions** | **Before** the residue-producing `setval`, so a value-level mismatch aborts with the target and the sequence both untouched |
| 3 | `setval('tags_id_seq', …)` | §4.3 |
| 4 | `projects` seed, `ON CONFLICT (name) DO NOTHING` | §3.6 |
| 5 | §10.4's post-seed assertions (sequence high-water, project coverage) | They verify 3 and 4, so they follow them |
| 6 | `DROP TABLE cutover_stage_*` | Staging is the before-side of steps 2 and 5; it cannot be dropped before them |
| 7 | one `COMMIT` | |

**This ordering is the revision's Blocking fix.** The original sequenced the
verification *after* the drop and the commit, which pointed §10's staging↔target
checksums at tables that no longer existed. The likely in-flight repair — repoint
at the source post-commit, or quietly downgrade to counts — would have eroded the
exact value-level proof this task exists to provide.

Moving it inside the transaction also upgrades the design rather than merely
fixing it: **a checksum mismatch now aborts the load** instead of writing a
report about a database that has already committed. §8's failure table gains a
row, and its "Nothing" answer becomes true for verification failures too.

Position 2 is deliberately ahead of the `setval`, and that is finer-grained than
the review asked for. `setval` is non-transactional and is not rolled back
(§4.3; independently measured by the review as its probe P7). Verifying
first means a value-level abort leaves **literally zero** residue, rather than
the advanced-sequence residue §4.3 documents. The residue is harmless either way;
having the tool leave none on its most likely abort path is worth one line of
ordering.

The `memories` statement is where the column map of §4.1 lives, written out in
full with every column named on both sides — no `SELECT *`, no positional insert.
Constraint 4 (no `::varchar(n)`) and constraint 8 (CAST bound params) apply here.

**Verify:** a test that loads a fixture pair containing a forward-pointing
supersession, a NULL `memory_type`, an `emotions` payload, and a tag id at the
sequence boundary, then asserts every §4.1 row; plus a test that injects a
value-level corruption between staging and load and asserts the **transaction
aborts** and the carried tables are empty afterwards.

### Step 5 — The reports, after the commit

Two artifacts, both read-only against the committed state:

1. The verification JSON report — every §10 check, with its measured values, not
   just a pass/fail. A run that exits non-zero has already aborted in step 4; this
   report is the record of a green run.
2. **The §10.5 pre-backfill snapshot**, taken here rather than inside the
   transaction so it describes state that actually committed. It is a pure read,
   so a failure to write it is safely re-runnable.

### Step 6 — The mutation proofs

Per §6 layer 3 and GLOBAL §6: commit before mutating, then break each guard on
purpose, watch the test fail, restore, watch it pass, and clear `__pycache__`.
Three guards get this treatment: the pointer-drop coercion, the status coercion,
and the batched-insert regression (change the `memories` load to a loop and
assert the forward-reference test fails).

Run the task's Verify command, then `pytest -q`, then
`pytest scripts/benchlib/tests -q` (GLOBAL §4 — the floor does **not** collect

`feat(cutover): transform the carried set onto the baseline`, `Task: T1.51` in

## 10. The verification: two legs, not one

The task's stated method is counts, and counts are necessary. They are **not
sufficient**, and naming the gap is part of the deliverable.

**What counts do detect:** missing rows, extra rows, a table loaded into the
wrong table, a filtered `WHERE` clause left in the transform, a partial load.

**The structural point the first draft missed.** Data reaches the target over
**two** legs — source→staging (Python-mediated) and staging→target (pure SQL) —
and the original verification only covered the second. A defect on the first leg
corrupts staging and target *identically*, so a staging↔target comparison is a
corrupted value agreeing with itself. Every check passes, T1.53's rehearsal is
green, and altered data reaches production with no channel left to notice it.
The fix is cheap and needs no cross-database join: run the same aggregates **on
the source connection** and compare the resulting strings client-side. That is
§10.1; §10.2 is the leg that was already there.

### 10.1 Source↔staging parity — the leg that was unverified

Runs after staging and **before the first carried-table write** (§9 step 3).
Staging carries source column names verbatim, so this is a like-for-like
comparison of the same column under the same name in two databases.

Per carried table, per carried column, computed on both connections and compared
as strings in Python:

- the `COALESCE`-guarded checksum of §10.2's spec,
- the NULL count, the distinct count, the row count.

Both connections have the GUCs of constraint 9 pinned before any aggregate runs,
because these two aggregates execute in **different sessions on different
databases** — the one place in this plan where the review's `TimeZone` concern is
not hypothetical (measured, §7 probe 7).

**What this catches that nothing else can:** a codec or driver round-trip defect.
The concrete measured instance (§7 probe 6) is a `jsonb` numeric losing precision
through a Python `float` — `1.000000000000000000000000001` → `1.0` — which
constraint 9 also prevents at the root by banning custom codecs. Belt and
braces is right here: constraint 9 is a rule an implementer can forget, §10.1 is
a check that fails if they do.

*A correction to the review's own reasoning, recorded because the plan should not
carry a wrong mechanism even in support of a right finding.* The review named
"integers above 2^53 in `metadata` corrupt silently" as the example. Measured,
that does not happen: under asyncpg's default codecs `jsonb` round-trips as an
opaque `str` with zero mismatches, and even under a `json` codec a 30-digit
integer survives, because Python integers are arbitrary-precision. The real loss
is decimal precision beyond a double, and it is codec-conditional. **The
finding's conclusion and its fix are both correct; only the mechanism needed
restating.**

### 10.2 Staging↔target parity — value-level, and NULL-position-aware

Runs inside the load transaction, after the five loads and before the `setval`
(§9 step 4). What a count cannot detect, and what covers it:

| Defect a count is blind to | Why counts pass | Cover |
|---|---|---|
| **Column-to-column misassignment.** `llm_summary` → `flags`, or `summary` and `content` swapped. Both are text/jsonb, both non-empty, the row count is identical. | The transform inserts N rows either way. | Per-column checksums (spec below) computed on the staging side under the source name and on the target side under the target name. Equality is a value-level proof, not a cardinality one. |
| **A column NULLed wholesale.** Every `emotions` lands NULL because a rename was mistyped and the target column never got written. | Rows still count. | Per-column **NULL count and distinct count** parity, alongside the checksum. |
| **Timestamp drift.** A timezone or interval shift on `created_at` moves the supersession window and the tie-break. | Counts identical, and a *text* checksum can false-pass or false-fail on the `TimeZone` GUC (measured, §7 probe 7). | Checksum timestamps as `extract(epoch from col)`, **never** `col::text` — plus the pinned GUCs of constraint 9. |
| **A NULL-position swap.** A join-shift moves a value from row A to row B and NULLs row A. | **Measured (§7 probe 8): the checksum, the NULL count *and* the distinct count all match.** Three of this table's own covers fail at once. | The `COALESCE` sentinel below. |
| **Lineage pointing somewhere else.** The CHECK proves `superseded ⇒ pointer non-null`. It proves nothing about *where* the pointer points. | Every count and both status counts match. | Compare the `(id, superseded_by)` **pair set** as a checksum, plus a per-`status` breakdown. |

**The checksum spec, in one line:**

```
md5(string_agg(COALESCE(<expr>, '␀'), '|' ORDER BY <key>))
```

where `<expr>` is `extract(epoch from col)::text` for a timestamp and `col::text`
otherwise, `<key>` is `id` — or `(memory_id, tag_id)` for `memory_tags`, which
has no `id` — and `␀` is any sentinel outside the column's value domain.

Three things about that line are load-bearing, and two of them are measured:

1. **`COALESCE` is not cosmetic.** `string_agg` *skips* NULL rows, so without it
   the aggregate cannot see where the NULLs were (§7 probe 8). With it, the
   checksum becomes a value-**and**-position proof.
2. **`COALESCE` is also what makes a NULL result impossible.** `string_agg` over
   an all-NULL column returns NULL, so `md5(...)` is NULL — and a client-side
   `None == None` compares **equal** (§7 probe 9). A wholly-NULLed column would
   pass a naive comparison on both sides. The guarded form returns a real hash
   for the same input. Additionally: **a NULL checksum from either side is a hard
   error, never a pass.**
3. **`ORDER BY` is mandatory.** An unordered `string_agg` is non-deterministic
   over a table of any size and would produce false mismatches that look like
   corruption.

With §10.1 and this section in place, I know of no remaining count-or-checksum-
blind defect class on the carried set. That is the review's assessment and this
revision's measurements agree with it.

## 11. Falsification pass

### 11.1 The step most likely to be wrong: the shape of the `memories` load

Step 4's requirement that the `memories` load be **one statement** is the
constraint an implementer is most likely to break, because every instinct about
loading a large table says *batch it*. A batched load works perfectly on every
small fixture, works on most of a real corpus, and fails on exactly those
supersession pairs whose pointer crosses a batch boundary — so the failure is
non-deterministic in batch size and row order.

**Evidence that would show it:** probe 3 already shows the failure mode
(`violates foreign key constraint "fk_memories_superseded_by"`), and it is loud.
The regression test is the one in step 6: change the load to a loop, assert the
forward-reference fixture fails. If that test passes with a batched load, the
fixture does not contain a boundary-crossing pair and the test is worthless.

Runner-up: the `tags_id_seq` `setval` (§4.3), which is easy to forget entirely
and whose failure is deferred to the first post-cutover tag write.

### 11.2 The silent failure mode that matters most: T1.52 overwrites eight carried columns

**This is the finding I consider most dangerous, and it is not in T1.51's own
code at all.** The review confirmed it at the code level and found it
**under-inclusive** in one direction and **overstated** in another. Both
corrections are below, because a control sized against a wrong surface is a
control that misses.

`ProcessingPipeline.process_batch` Phase 5, savepoint A
(`app/services/pipeline.py:607–620`) executes, for every memory whose Phase-1
embed succeeded and whose row exists:

```
if llm_classification:
    mem_record.classified_type = llm_classification.get("hall") or None
    mem_record.summary         = llm_classification.get("summary") or None
    mem_record.emotions        = llm_classification.get("emotions") or None
    mem_record.flags           = llm_classification.get("flags") or None

mem_record.memory_type = resolved_memory_type          # normalize_memory_type(entry_type or extracted)
mem_record.importance  = float(extracted_importance)   # when extraction emits one
mem_record.confidence  = estimate_confidence(content, resolved_memory_type)
```

T1.52's backfill re-extracts every carried memory through this exact path.
**Eight** carried columns are in the blast radius, not four:

| Column | Condition | Effect on a carried row |
|---|---|---|
| `updated_at` | **unconditional** | Any ORM mutation is an `UPDATE` and `touch_updated_at` fires (measured, probe 5). Becomes the backfill's wall-clock time. |
| `confidence` | **unconditional** | Recomputed from content by `estimate_confidence`. |
| `memory_type` | unconditional *assignment*, but see below | Value depends on T1.52's invocation shape. |
| `importance` | when extraction emits one | Replaced by the extractor's. This is the column T2.30 activates as a ranking arm; its history is gone before anyone measures it. |
| `classified_type` | when the classification dict is truthy | Overwritten — **or nulled**, see below. |
| `summary` | as above | Overwritten or nulled. |
| `emotions` | as above | Overwritten or nulled. |
| `flags` | as above | Overwritten or nulled. |

**The under-inclusion (the review's finding).** The four enrichment renames
`classified_type` / `summary` / `emotions` / `flags` are precisely the columns
§4.1 goes to the trouble of renaming from `llm_*`, and doc 19 §4 puts them in its
*carries* bullet — so they are carried-then-clobbered in exactly the same shape as
the four originally named. Worse, the assignments are `… .get(x) or None`: a
classifier that returns an **empty** field does not leave the carried value
alone, it **writes NULL over it**. An empty string, an empty list and a missing
key are all falsy, so the destructive case is not exotic. Neither the original
C-01 nor the original §10 snapshot covered these columns, which means the diff
C-01 mandates could not have seen the loss it was written to catch. Both are
widened in this revision (§10.5).

**The overstatement (the review's correction the other way).** C-01's prose read
as a uniform loss of `memory_type`. It is not:
`resolved_memory_type = normalize_memory_type(memory_type or extracted_type)`,
and `normalize_memory_type` returns its argument unchanged for any value already
in `MEMORY_TYPES` — so for a row whose type is one of the nine, the assignment is
an **identity**. The damage concentrates on NULL and out-of-vocabulary values.
And §9 assertion 10 already stops the run on any out-of-vocabulary non-NULL
value, so the residual unconsented surface on this column is **NULL rows**.

**One qualification neither C-01 nor the review stated, and it decides which of
the two readings applies.** `memory_type or extracted_type` means the identity
result holds **only if T1.52 passes the carried `memory_type` as the entry
type**. If the backfill invokes the pipeline without it, `memory_type` is `None`,
the extractor's own label wins, and a carried in-vocabulary value can be rewritten
to a *different* in-vocabulary value — silently, and with none of the
out-of-vocabulary pre-flight protection. T1.52 does not exist yet, so this plan
cannot resolve it; C-01's preserve-or-accept obligation covers both shapes, and
the widened snapshot detects either.

**The severity call is unchanged** by the correction, because `updated_at` and
`confidence` are destroyed on every row unconditionally regardless of how
`memory_type` resolves.

**Why it is silent.** Nothing errors. The row counts match. `pipeline_failures`
stays empty. The extraction bench holds tolerance, because it runs against
`gold.json` and not against the carried corpus. Every check T1.52's Done-when
names comes back green while eight columns of unrecoverable history have been
overwritten, and the only way to notice is to have kept a snapshot — which is why
§10 requires one and why the snapshot must be taken by T1.51, before T1.52 exists
to take it.

A fifth column is in the same family and worth naming separately: **`status` /
`superseded_by` are not frozen after T1.51 either.** T1.52's re-extraction runs
`detect_supersessions`, and the rebuilt graph may emit a `REPLACES`-family
relation the old extractor did not. Candidates within the 90-day window can
therefore be flipped to `superseded` after the cutover. That is *legitimate new
derivation*, not a bug — but "lineage carries verbatim" is true at T1.51's
boundary and not after, and a reviewer comparing the source dump to a
post-backfill database will see a diff and be right to ask.

**Routing.** These are recorded as amendments against **T1.52** (which must
either preserve the eight columns or state the overwrite as intended — and for
the four enrichment columns specifically, must decide whether an empty classifier
result **retains** the carried value instead of nulling it), **T1.53** (whose
rehearsal must diff lineage and the eight columns before and after the backfill
and report the delta rather than assume zero), and **T1.54** (whose Done-when
must carry the diff on the *real* run — C-11). T1.51's own obligation is the
widened snapshot of §10.5 and this record.

### 11.3 Runner-up silent mode: an empty `technologies` that nobody notices

If the cutover completes and the backfill never runs — or runs partially —
every carried memory sits with `technologies = '{}'`. Consequences, all
silent: supersession's overlap predicate (rule 3) matches nothing, so no carried
memory can ever supersede another; the retrieval technology filter returns empty;
and the hybrid semantic arm still works, so the system *feels* fine. Nothing logs
and nothing errors.

The cover is T1.52's own "a partial backfill is visibly partial" Done-when, plus
T1.51's positive assertion that `technologies` is empty on 100% of rows — which
makes the state a *known, asserted* condition on the way in rather than a
discovery on the way out.

## 12. Size call

**One `L`, with one named condition.**

The design decisions are now made and written down, which is most of what made
this task an `L`. What remains is four modules and a test file — roughly
900–1100 lines of code plus tests — with no algorithmic difficulty and no new
subsystem. The nine behavioural unknowns that could have expanded it (self-FK

failure text, the `updated_at` bump, jsonb codec round-tripping, GUC-sensitive
checksums, `string_agg`'s NULL handling in two forms) are measured in §7 rather

**The revision did not change the size call, and it was worth checking.** It
added a second checksum leg on the source connection, an expanded `--reset`
guard, four columns and an artifact spec on the snapshot, and a tightened
pre-flight — perhaps 150–250 lines concentrated in `verify.py` and `preflight.py`,
plus one test class. That is the upper end of one `L`, not a second one: no new
module, no new dependency, and the hardest part (knowing *what* to check and
why) is now written down rather than discovered. The reordering of §9 step 4 is
free — it moves existing calls.

On the recommended stance (carry nothing from `config`), no split is needed.
