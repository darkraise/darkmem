## 1. What this task is, and the three things it is not

It is one posture change with a deployment artifact attached. The app becomes the network
edge: one image carries FastAPI **and** the built SPA, nginx leaves the shipped topology,
`trust_proxy_headers` defaults **off**, and the login rate limiter keys on the transport
peer. Both IP-source strategies stay live and tested, because the nginx-in-image fallback
(doc 03 §3.2) and the exposed-deployment horizon (doc 18 §9) each restore the header path —
so the posture is a state machine, and a change of posture must be a config flip, not a
rewrite.

**It is not the exposed-deployment work.** T4.03 owns re-enabling the header strategy under
an operator TLS proxy and enforcing `cookie_secure`. This task's obligation toward T4.03 is
narrow and total: leave the header path alive, tested, and reachable by flipping one
setting. Nothing in this plan may delete that branch.

**It is not the `ApiKey` activation.** Doc 18 §5 gates it on the first genuine off-LAN
need. Serving the SPA from the API origin does not create one.

**It is not a security-header or caching redesign.** nginx's header set, gzip policy and
cache-control rules are absorbed *as they are* (§4.2). Absorbing them verbatim is what
makes the fallback reversible; improving them here would make the two postures diverge,
which is the one thing doc 18 §4 forbids.

## 4. The five decisions this plan makes

### 4.1 The SPA is served by a `StaticFiles` subclass mounted at `/`, never by an `@app.get` catch-all

The obvious implementation — `@app.get("/{full_path:path}")` returning `index.html` — adds
an `APIRoute`, and both enumeration suites in §3 will fail it: no `EXPECTED_STATUS` row, no
parity classification. Adding rows to satisfy them would be worse than the failure, because
it would assert that the SPA is a REST capability with a two-door disposition, which is
nonsense.

Decision: `app.mount("/", SPAFiles(directory=…, html=False), name="spa")`, registered
**last**, where `SPAFiles` subclasses `starlette.staticfiles.StaticFiles`. A `Mount` is not
an `APIRoute`; both suites skip it, and the SPA never enters the OpenAPI schema.

Three behaviours the subclass must carry, each measured against the installed Starlette
(**1.3.1**, FastAPI 0.140.0):

1. **Deep links.** `StaticFiles(html=True)` does *not* solve this. Read at
   `starlette/staticfiles.py`: on a miss in html mode it looks for `404.html` and
   otherwise `raise HTTPException(status_code=404)`. `frontend/dist` contains only
   `assets/`, `favicon.svg` and `index.html` — no `404.html` — so a hard refresh on
   `/settings` or `/memories/<id>` would 404. The subclass catches the 404 from
   `get_response` and re-serves `index.html`.
2. **Reserved prefixes must stay honest 404s.** Because the mount is last and matches
   everything, an unknown `/api/v1/typo` would otherwise fall through to the SPA and return
   `index.html` with **200**. Before falling back, the subclass re-raises the 404 for a
   request path whose first segment is `api`, `health`, `ws` or `mcp`. The re-raised
   `HTTPException` propagates to `app`'s registered `StarletteHTTPException` handler and
   comes back as the T1.42a error envelope with `error.code == "not_found"` — asserted by
   test, not assumed. (`/docs`, `/redoc` and `/openapi.json` need no entry: `FastAPI.__init__`
   registers them as exact-path Starlette `Route`s — verified, `type(r).__name__ == "Route"`
   — ahead of every included router, so they match before the mount and nothing under them
   falls through. Being `Route` rather than `APIRoute` is also why the two enumeration
   suites in §3 have never had to classify them.)
3. **Cache-control.** `/assets/*` is content-hashed and gets
   `public, max-age=31536000, immutable`; every `index.html` response gets `no-cache`.
   These are nginx's existing rules moved, not new policy. Omitting them produces the
   classic post-deploy white screen: a cached `index.html` referencing hashed chunks the
   new image no longer contains.

**The directory may be absent, and that must not break the app.** `StaticFiles.__init__`
raises when `check_dir=True` and the directory does not exist — and `backend/tests` runs
with no built SPA, as does host-side dev. So the wiring is a function,
`mount_spa(app, directory) -> bool`, in a new module `backend/app/api/spa.py`, called from
`main.py` with the resolved directory and returning False (mount skipped, logged at INFO)
when it is absent. Tests drive both branches against a `tmp_path` fixture holding a fake
`index.html` and `assets/app.js`, so the test never has to run `npm run build` and never
imports the production path constant it exists to defend.

**The cost of that tolerance is the most dangerous silent failure in this task** — see
§10.2 — and Step 4 pays for it with a build-time `RUN test -f`.

### 4.2 nginx's response duties are absorbed verbatim, in the app

Removing the nginx container removes four things that are currently invisible because they
have always been someone else's job. Each is re-created in the app with the same values:

- **Security headers.** A middleware emitting exactly nginx's four `always` headers
  (`X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`,
  `Referrer-Policy: strict-origin-when-cross-origin`, and the CSP string verbatim from
  `frontend/nginx.conf`). Copied character-for-character so the fallback build and the
  app-as-edge build present the same policy.
- **gzip.** `GZipMiddleware(minimum_size=1024)`, matching nginx's `gzip_min_length 1024`.
  This is not cosmetic: the measured cold-load payload is 5.2 MB across 92 files, whose
  largest chunk alone is 1.72 MB raw against 461 kB gzipped. **Measured safety check:**
  Starlette 1.3.1's `gzip.py` defines
  `DEFAULT_EXCLUDED_CONTENT_TYPES = ("text/event-stream",)`, so the two SSE endpoints
  (`app/api/routes/chat.py:142`, `app/api/routes/analytics.py:53`) are excluded
  automatically and the middleware cannot stall them. That is read from the installed
  source, not assumed from the docs.
- **Cache-control** — §4.1(3).
- **The 25 MB request cap** — §4.4, the one item this plan flags as contestable.

**Middleware order is specified, because Starlette applies `add_middleware` in reverse:**
the last added is outermost. Add security-headers first, then GZip, so GZip is outermost
and compresses a body whose headers are already set. Leave the existing `CORSMiddleware`
call exactly where it is; moving it changes preflight behaviour and is not this task's.

### 4.3 nginx's *artifacts* are kept and relabelled, not deleted

`frontend/nginx.conf` is the only written record of the header, gzip and cache policy the
app now re-implements, and doc 03 §3.2 keeps nginx-in-image as a labelled fallback with a
named trigger. Deleting the file would leave §4.2's middleware as the sole source of a
policy whose whole point is that two postures agree on it.

Decision: **keep `frontend/nginx.conf` and `frontend/Dockerfile`**, add a header comment to
each naming them the doc 03 §3.2 fallback and stating that the default build does not use
them, and remove them from `scripts/build-push.sh` and both compose files so nothing builds
or ships them by default. Counter-argument a reviewer should weigh: an unbuilt Dockerfile
rots, and invariant 23 dislikes inert artefacts presented as live. The label is what makes
it honest — it is a recorded fallback with a stated trigger, which is exactly the category
invariant 23 permits, and the alternative (git history) is not something an operator taking
the fallback in eighteen months will find.

### 4.4 The request-body cap is re-created in the app — and this is the step most likely to be cut

Removing nginx removes `client_max_body_size 25m` and puts nothing in its place: neither
uvicorn nor Starlette caps a request body by default, and nothing in `backend/app` reads
`content-length` (grepped). The app-as-edge build would therefore accept an unbounded POST
where today's build returns 413 at the proxy — a regression introduced by this task, on the
door this task is making the network edge.

Decision: a small middleware that rejects a request whose `Content-Length` exceeds
25 MB with the existing `413 payload_too_large` envelope (the code is already in
`_HTTP_ERROR_CODES`, evidence that the shape was anticipated). The limit matches nginx's
exactly, so behaviour is preserved rather than tightened.

**Named honestly as the weakest step in the plan**, in two ways. (a) It is the one step no
*Done when* box requires, so a reviewer may reasonably cut it and route it to E4 as a named
gap; if cut, that must be recorded, not silently dropped, because the regression is real.
(b) A `Content-Length` check does not bound a chunked request that sends no
`Content-Length`. Bounding those needs body-stream accounting, which is materially more
code and more risk. The step therefore closes the ordinary case and **must say so in its
own comment** rather than implying a complete cap. Do not let this step grow into a
streaming-limit implementation inside T1.62.

### 4.5 One image, built from a repo-root context, keeping the existing image name

The image must contain a Node build of `frontend/` and the Python runtime, so the build
context has to include both trees; a context of `./backend` cannot see `frontend/`.

- **`Dockerfile` moves to the repo root** as a three-stage build: `web` (node:20-alpine,
  `npm ci`, `npm run build`), `builder` (the existing Python venv build, unchanged), and
  `runtime`, which additionally does `COPY --from=web /app/dist ./web`.
- **A root `.dockerignore` is mandatory, not tidiness.** With the context at the root and
  no ignore file, the daemon receives `backend/.venv` (431 MB) and
  `frontend/node_modules` (542 MB) — about 973 MB of measured, useless context, plus
  `.git` and every worktree under `.worktrees/`. Note that `backend/.dockerignore` and
  `frontend/.dockerignore` **stop applying** once the context is the root: Docker resolves
  a single `.dockerignore` at the context root. Their contents must be merged into the new
  root file, not left in place and assumed to work. Getting this wrong is silent — the
  build still succeeds, just enormous, and `frontend/node_modules` leaking into the `web`
  stage can shadow `npm ci`'s own install with a host-built, wrong-platform tree.
- **`entrypoint.sh` moves to the repo root beside the Dockerfile**, and its
  `.gitattributes` LF rule moves with it (`entrypoint.sh text eol=lf` is already
  path-agnostic — confirm it still matches, and keep the Dockerfile's existing
  `sed -i 's/\r$//'` belt-and-braces line).
- **The image keeps the name `darkraise/darkmem-api`.** It is now slightly historical, but
  renaming orphans every pinned `DARKMEM_VERSION` tag an operator already deployed, for no
  functional gain. Record the naming in a compose comment.

## 5. The IP-source ladder — four layers, and the one that no unit test can see

The task's *Done when* box says the leftmost `X-Forwarded-For` is read in **no** posture,
proven by test. Satisfying that honestly means knowing every layer that can decide what
`request.client.host` is.

### 5.1 Layer 1 — the socket

Under `network_mode: host`, the container shares the host's network namespace, so the
transport peer is the real LAN client (or the LAN NAT). This is the property the whole flip
rests on. **It is coupled to host networking and that coupling must be written into the
compose file as a comment**, because a later move to bridge networking changes where the
peer address comes from and could collapse every client into one rate-limit bucket. This
plan does not assert what bridge networking would do — it is not measured here — only that
it must be measured before any such move.

### 5.2 Layer 2 — the ASGI server

**This is the layer the task text does not mention and the existing tests cannot reach.**
Read from the installed uvicorn **0.51.0**:

- `uvicorn/config.py:219` — `proxy_headers: bool = True`. **On by default.**
- `uvicorn/config.py:356` — `forwarded_allow_ips` defaults to `"127.0.0.1"`.
- `uvicorn/config.py:525` — `if self.proxy_headers: self.loaded_app = ProxyHeadersMiddleware(...)`.
- `uvicorn/middleware/proxy_headers.py` — when the immediate peer is trusted, the
  middleware **overwrites `scope["client"]`** from `X-Forwarded-For`.

So with today's `entrypoint.sh` (`exec uvicorn app.main:app --host 0.0.0.0 --port 8000`),
any request arriving **from loopback** can set its own `request.client.host` by sending an
`X-Forwarded-For` header. On the homelab box loopback is not an empty set: local agents
reach `/mcp` and the REST API on `127.0.0.1`. A local process could therefore rotate the
rate-limiter's bucket key per attempt and never lock out — the exact attacker-keyed-bucket
failure doc 18 §4 describes, reintroduced one layer below the code that correctly refuses
it.

In fairness to uvicorn: `_TrustedHosts.get_trusted_client_address` walks the XFF list in
**reverse** and returns the first untrusted hop, so this is not literally "reads the
leftmost". For a single-valued header, though, leftmost and rightmost are the same value
and the client supplies it. The property doc 18 §4 fixes — *with no proxy, the socket wins*
— is broken either way.

**Decision: `entrypoint.sh` passes `--no-proxy-headers`.** Verified present in the
installed uvicorn's CLI (`--proxy-headers / --no-proxy-headers`), and `config.py:525` shows
the flag prevents the middleware from being installed at all. `--forwarded-allow-ips ""`
would be a weaker second-best; do not use it instead.

### 5.3 Why the task's own Verify command cannot catch 5.2

`tests/test_client_ip_attribution.py` calls `_client_ip` against a `_FakeRequest`, and even
an end-to-end pytest through httpx's ASGI transport never runs uvicorn's middleware — it
speaks ASGI to the FastAPI app directly. **No test runnable under `pytest` can observe
layer 2.** That is why this plan's verification carries two things the task text does not
ask for: an artefact-level assertion that `entrypoint.sh` contains `--no-proxy-headers`
(Step 5), and a live differential proof through real uvicorn on the throwaway stack
(§9.4). A guard that cannot fail is worse than no guard; a unit test that cannot see the
layer it purports to defend is the same defect wearing a green tick.

### 5.4 Layer 3 — the application strategy selector

`_client_ip` in `auth.py`, unchanged in structure. `trust_proxy_headers` selects: on →
`X-Real-IP`, then the **rightmost** XFF hop; off → `request.client.host`. Both branches stay.
This task changes the **default** and the tests, not the function body.

### 5.5 Layer 4 — the limiter

`login_rate_limit.py` never inspects the request. Nothing changes. Its module comment does
say the caller derives the key "honoring a trusted X-Forwarded-For", which becomes
posture-dependent rather than false; adjust that sentence only, and leave the rest of the
comment alone (GLOBAL §10).

### 5.6 The test matrix the *Done when* box actually requires

Four rows, parametrised over posture, in `tests/test_client_ip_attribution.py`. Every row
carries a **positive** assertion alongside the negative one, because in the app-as-edge
posture "the leftmost value was not returned" passes vacuously — the function ignores
headers entirely — and a vacuous assertion reads as evidence while proving nothing:

| # | Posture | Headers | Socket | Must equal | Must not equal |
|---|---|---|---|---|---|
| 1 | trust **on** | `XFF: 203.0.113.9, 198.51.100.4`, `X-Real-IP: 198.51.100.4` | `10.0.0.5` | `198.51.100.4` | `203.0.113.9` |
| 2 | trust **on** | `XFF: 203.0.113.9, 198.51.100.4` (no X-Real-IP) | `10.0.0.5` | `198.51.100.4` | `203.0.113.9` |
| 3 | trust **off** | `XFF: 203.0.113.9, 198.51.100.4`, `X-Real-IP: 198.51.100.4` | `10.0.0.5` | `10.0.0.5` | `203.0.113.9` **and** `198.51.100.4` |
| 4 | trust **off** | no headers at all | `10.0.0.5` | `10.0.0.5` | — |

Row 3's second "must not" is what keeps the app-as-edge row non-vacuous: it fails if the
posture switch is deleted, not merely if the leftmost is preferred. Rows 1–2 are today's
tests with distinct values substituted (today's row 1 uses `1.2.3.4` leftmost and
`203.0.113.7` for both X-Real-IP and rightmost, so the assertion cannot distinguish "read
X-Real-IP" from "read the rightmost hop" — a third value is needed and this matrix supplies
it).

**Mutation proofs, both required** (Step 10):

- `parts[-1]` → `parts[0]` in `auth.py:71`: rows 1–2 must fail (row 1 fails only because
  the X-Real-IP branch is also removed in the same mutation, so run the leftmost mutation
  against row 2 specifically as well).
- Delete `if settings.trust_proxy_headers:` so the header branch always runs: row 3 must
  fail. This is the mutation that proves the app-as-edge row can fail at all.
- Revert `config.py`'s default to `True`: the flipped `test_config_settings` case must fail.

GLOBAL §6 applies to all three: commit before mutating, and clear `__pycache__` after each
size-preserving edit.

## 6. The sequencing constraint: the flip cannot land before the image

Flipping `trust_proxy_headers` off while `darkmem-ui` is still the shipped edge is a
security regression, not a neutral intermediate. Under today's prod compose, nginx proxies
`/api` to `127.0.0.1:8000` over host networking, so with the flag off every browser login
resolves to `request.client.host == "127.0.0.1"` — one shared bucket for the entire LAN.
Five failed attempts from anyone would then lock out everyone: a trivial lockout DoS.

Two consequences bind the plan:

1. **Within the lane**, the flip (Step 7) is the last content step, after the image and the
   compose surface exist. The T1.58 plan reached the same shape for the same reason.
2. **This is the strongest argument against splitting the task** (§10.3). A split that
   shipped the trust flip in one task and the image in another would have to leave that
   regression standing between them.

## 7. The step sequence

Ten steps. Steps 1–3 touch only `backend/app`; Steps 4–6 touch only deployment artefacts;
they are structurally independent and could run in parallel sub-lanes. Step 7 must land
after Step 6. Steps 8–10 depend on everything.

### Step 1 — Serve the SPA from the app

**Size:** M. **Files:** new `backend/app/api/spa.py`; `backend/app/main.py`;
`backend/app/config.py`; new `backend/tests/test_spa_edge.py`. **Depends:** nothing.

- `spa.py`: `SPAFiles(StaticFiles)` per §4.1 — 404-to-`index.html` fallback, reserved-prefix
  re-raise for first segments `api`, `health`, `ws`, `mcp`, and the two cache-control rules.

## 9. The live verification, specified

The task says "a clean `docker compose up -d` boot with `/health` 200". Run naively on this
machine, that command is destructive. This section is the recipe.

### 9.1 Why the naive command is destructive — measured, not theoretical

- `docker compose ls` reports a running project named **`darkmem`**, config file
  `/root/repositories/darkmem/docker-compose.dev.yml`, one container
  **`darkmem-postgres-1`**, service name **`postgres`**, volume **`darkmem_postgres_data`**,
  publishing `127.0.0.1:5433`.
- The prod compose defines a service also named **`postgres`**. Compose derives the project
  name from the directory, so `docker compose up -d` run from `/root/repositories/darkmem`
  targets project `darkmem`, sees an existing container for service `postgres` with a
  different config, and **recreates it** — dropping the `5433` publish the four sibling
  lanes' numbered test and bench databases are reached through, mid-run.
- `127.0.0.1:5432` is **already occupied** by an unrelated `postgres` container from another
  project on this host. The prod compose's Postgres runs on host networking at the default
  port 5432, so it collides.
- `:8000` was free at measurement time (`ss -ltn` showed only 5432 and 5433), but a sibling
  lane can start `start_dev_server.sh` at any moment.

### 9.2 The throwaway-stack recipe

Two deviations from the shipped compose, both documented, both in an override file kept in
the lane's scratchpad and **not committed**:

1. Postgres on port **5544** — `command: [postgres, -c, max_connections=120, -c,
   listen_addresses=127.0.0.1, -c, port=5544]`, `DB_PORT=5544` on the app service, **and
   the healthcheck changed to `pg_isready -U darkmem -p 5544`**. Forgetting the healthcheck
   is the trap: `pg_isready` defaults to 5432, the check never goes healthy,
   `depends_on: service_healthy` blocks the app forever, and the artifact looks broken when
   only the override is.
2. `image: darkmem-local:t162` with the locally built tag, so the run tests the new image
   rather than whatever `darkraise/darkmem-api:latest` happens to be on the host.

```bash
# pre-flight: refuse to start if :8000 is taken by a sibling lane
ss -ltn | grep -q ':8000 ' && { echo "port 8000 busy — abort"; exit 1; }

cd /root/repositories/darkmem/.worktrees/lane-e
timeout 1800 docker build -t darkmem-local:t162 .

export DB_PASSWORD=... JWT_SECRET=$(openssl rand -hex 32) COOKIE_SECURE=false
timeout 600 docker compose -p darkmem-t162-verify \
  -f docker-compose.yml -f "$SCRATCH/t162-verify.override.yml" up -d
```

**`-p darkmem-t162-verify` is not optional and is the single most important token in this
section.** It scopes the containers *and* the volumes
(`darkmem-t162-verify_postgres_data`, `darkmem-t162-verify_repo_data`), so nothing this run
does can reach `darkmem_postgres_data`.

**Teardown, mandatory, before reporting:**
`docker compose -p darkmem-t162-verify down -v`, then confirm with `docker ps` that
`darkmem-postgres-1` is still up and `docker volume ls` still shows
`darkmem_postgres_data`.

### 9.3 The assertions

1. `curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:8000/health` → **200** (the
   task's own bar; LLM unreachable is `degraded` at 200, which is correct per doc 19 §6).
2. `GET /` → 200, `content-type: text/html`, body contains `<div id="root">`. Then extract
   the first `/assets/*.js` from that HTML and fetch it → 200. **This second fetch is the
   assertion that the SPA is really in the image** (§10.2); `/health` alone cannot tell.
3. `GET /settings` → 200 and the same index body — the deep-link guarantee.
4. `GET /api/v1/definitely-not-a-route` → 404, JSON, `error.code == "not_found"`, not HTML.
5. `curl -H 'Accept-Encoding: gzip' -sI` the large asset → `content-encoding: gzip`.
6. `GET /` carries the four security headers.
7. §9.4, below.

### 9.4 The differential proof for layer 2 — the sharpest check in this plan

Read from the code: `POST /api/v1/setup` is TOFU-open on a fresh database
(`require_uninitialized`), takes `{"password": "<8..128 chars>"}`, and journals an
`auth_setup` `events` row whose payload carries
`{"ip": request.client.host}` — via `setup.py`'s socket-only `_client_ip`
(`setup.py:304`, called at `setup.py:344`). So the socket peer becomes observable from
outside the process, with no password to set up first.

```bash
curl -s -X POST http://127.0.0.1:8000/api/v1/setup \
  -H 'content-type: application/json' \
  -H 'X-Forwarded-For: 9.9.9.9' \
  -d '{"password":"correct-horse-battery-staple"}'

docker exec darkmem-t162-verify-postgres-1 psql -U darkmem -d darkmem -t -c \
  "SELECT payload->>'ip' FROM events WHERE event_type='auth_setup';"
```

**Expected: `127.0.0.1`.** With `--no-proxy-headers` absent it is `9.9.9.9`.

Run it **both ways**: once against the shipped entrypoint, and once with a compose
`command:` override that re-enables proxy headers. The second run must produce `9.9.9.9`.
That differential is the only proof in this task that the layer-2 guard can fail, and it
costs a container restart, not a rebuild. A run that shows `127.0.0.1` both times means the
test is not measuring what it claims — investigate rather than report green.

## 10. Falsification pass

### 10.1 The step most likely to be wrong: Step 1, the mount

Two independent ways it goes wrong, and both are the kind that look fine locally.

**(a) The route-type trap.** The natural implementation is `@app.get("/{full_path:path}")`.
That adds an `APIRoute`, and §3 shows two live-router enumerations that will reject it:
`test_rest_conformance.py` demands an `EXPECTED_STATUS` row for every `APIRoute`, and
`test_door_parity.py` demands a `PARITY_TABLE` classification plus a matching row in
`docs/two-door-parity.md`. The evidence that would show this early is running those two
suites in Step 1's own Verify — which is why they are named there rather than left to the
floor. The failure is loud, so the risk is not that it ships; the risk is that an executor
"fixes" it by adding table rows, which quietly asserts that the SPA is a REST capability.

**(b) The reserved-prefix set.** Get it wrong and unknown `/api/v1/*` paths return
`index.html` with **200** — a silent-200 where the contract says 404 envelope. The evidence
is assertion 4 in §9.3 and its unit twin in Step 1. Note the residual: a POST to an unknown
*non-reserved* path returns **405** from `StaticFiles`, not 404. That is a real behaviour
change from nginx (which returned the SPA for any method) and this plan accepts it —
recorded here so a reviewer can overrule rather than discover it.

**Runner-up:** Step 4's root `.dockerignore`. A missing or thin one still builds, just
slowly, and a leaked `frontend/node_modules` into the `web` stage can shadow `npm ci`'s
platform-correct install with the host's tree. The evidence is the "transferring context"
size in the build output — which is why Step 4's Verify asks for that number explicitly.

### 10.2 The most dangerous silent failure: the image ships without its SPA, and everything stays green

Because `mount_spa` must tolerate an absent directory (§4.1 — backend tests and host-side
dev run with no build), an image whose `web/` copy failed boots **perfectly**. Migrations
run, the pipeline initialises, `/health` returns 200, the container healthcheck passes, the
compose stack reports healthy, every backend test passes, and the only symptom is that the
UI 404s — discovered by a human, on the homelab box, after the cutover.

Three layers of defence, deliberately not one:

1. **Build-time.** `RUN test -f web/index.html && test -d web/assets` in the runtime stage
   (Step 4). This converts the failure from silent-runtime to loud-build, and it is the
   cheapest of the three.
2. **Boot-time.** `mount_spa` logs at INFO when it mounts and at **WARNING** when it skips,
   naming the directory it looked in. A skipped mount in a production image must not be a
   silent INFO line.
3. **Verification-time.** §9.3 assertion 2 fetches an actual `/assets/*.js` referenced by
   the served index, so the check fails if the directory exists but is empty — which
   `test -f index.html` alone would not catch.

**What this plan deliberately does not do:** add an `spa` key to `/health`. `/health` is
doc 19 §6's liveness and dependency surface with a fixed status policy, and widening it to
carry a packaging fact is a contract change T1.62 has no mandate for. If a reviewer wants
runtime detectability beyond the WARNING log, that is a Tier-2 amendment against doc 19,
not a quiet addition here.

**Runner-up silent mode:** the layer-2 rewrite of §5.2. It is more severe (a security
property, not a packaging one) but less likely to survive this plan, because §9.4's
differential proof is specifically built to catch it. It earns second place only because
§5.3 shows the task's stated Verify command cannot see it — so if §9.4 is skipped for time,
this becomes the most dangerous mode by a wide margin. **Do not skip §9.4.**

### 10.3 What would falsify the "no split" call

If the executing lane finds that the root-context Dockerfile plus `.dockerignore` plus the
two compose files plus `build-push.sh` cannot be verified without the SPA-serving work
landing first — i.e. if Steps 4 and 6 turn out not to be independent of Steps 1–3 after all
— then the artifact half and the edge half are one unit and the task is larger than one
`L`, not splittable. The evidence would be Step 4's Verify failing for a reason that lives
in `backend/app`. Conversely, if a reviewer proposes splitting along the flip, §6 is the
refutation: the intermediate state is a lockout DoS.

## 11. Size call

**`L` stands. No split.**

Ten steps across three subsystems that do not normally meet: `backend/app` (the SPA mount,
three middlewares, the settings default), the deployment artefacts (one Dockerfile, one
`.dockerignore`, the entrypoint, two compose files, the build script), and the security
posture (the strategy default, its four-row test matrix, three mutation proofs, and a live
differential proof through real uvicorn). Four new or rebuilt test files. The single
largest unit is Step 4, whose build-context change silently invalidates both existing
`.dockerignore` files.

It is not *bigger* than one `L`: no step is bounded by anything outside the lane's control,
there is no human labelling, no gold set, and no live model call. It is at the upper end of
one `L` and should be executed as one lane, in the §8 order.

The split a scheduler would naturally propose — flip the trust posture in one task, ship the
image in another — is refuted by §6: the intermediate state locks the whole LAN out of login
after five failed attempts from any client. The other conceivable split, "SPA serving" versus
"compose/Dockerfile", fails the value test: neither half is independently shippable, since
serving the SPA from an image nobody builds is dead code, and an image with no SPA in it is
the §10.2 failure by construction.
