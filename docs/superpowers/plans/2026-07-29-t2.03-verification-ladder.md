## 3. The Done-when items, made executable

### D1 — "Promotion is a pure function of the ladder inputs — reproducible on replay"

- One pure function: `decide(current_status, profile, config, *,
  open_contradiction) -> LadderDecision`. No I/O, no session, **no clock** —
  the time-gap gate reads `OriginProfile.max_cross_origin_gap`, which is
  computed only from stored timestamps relative to each other
  (`fact_sources.py:212–231`).
- The inputs are exactly: the fact's current `verification_status`, the
  `OriginProfile` snapshot, the `LadderConfig` values, and the contradiction
  verdict. Nothing else may be read.
- **Test (replay):** serialise a decision's inputs to plain data, re-run
  `decide` from the deserialised inputs, assert the identical `LadderDecision`.
  Run the same profile through twice; assert equality. `recompute_fact` twice
  on an unchanged fact: second run is a no-op and journals nothing (the
  repository's no-op guard, `knowledge_triples.py:371`, plus the decision's
  determinism).
- **Test (purity — the clock-displacement kill vector).** *Review finding I1.*
  The three assertions above are **all survivable by a `decide()` that reads the
  wall clock**: a mutant firing the time gate on `now() - earliest.first_seen >=
  7 days` instead of on the cross-origin gap returns identical output on two
  runs milliseconds apart and across a serialise/deserialise round trip. Every
  stated assertion stays green while the property the clause exists to protect
  is gone. So purity gets a vector that **kills that specific mutant**: two
  attributable same-kind origins with **hard-coded absolute timestamps ~400 days
  in the past**, 1 day apart — no gate fires, N=3, K=2, **no promotion**. The
  distance-from-now mutant sees 400 days ≥ 7 and promotes, so it goes red. The
  same pair 10 days apart promotes under both, which is the control. Every
  timestamp in the replay serialisation is a **fixed ISO literal**, never
  derived from a test-runtime `now()` — a `now()`-relative fixture re-introduces
  exactly the coupling the vector exists to detect.
- **Test (ceiling):** for every constructed profile — including one with a
  `human`-kind dominant origin and arbitrarily many diverse origins —
  `decide` never returns `confirmed`; the machine-target type does not admit
  it. Belt-and-braces: forcing the applier toward `confirmed` hits T2.01's
  refusal (`ValueError`), asserted by test. **The same test asserts `decide`
  never returns `disputed` as a machine target either** (*review M2*): the
  `Literal` excludes it, but Python does not enforce annotations at runtime, so
  the exclusion is asserted rather than assumed.
- **Test (orthogonality):** `recompute_fact` on a fact with belief columns set
  leaves `valid_at`/`invalid_at`/`expired_at` bit-identical; recomputing an
  `expired`-yet-`confirmed` fact holds `confirmed` and touches no timestamp.

### D2 — "N and the diversity rule read from `config`, defaults stated"

- One `config` row, key `verification_ladder`, merged over code defaults with
  the `get_feature_flags_dict` pattern (`feature_flags.py:13–21`):
  `corroboration_n_default = 3`, `corroboration_n_diverse = 2`,
  `corroboration_time_gap_days = 7`. The defaults are **the same objects** as
  `fact_sources.py:111–113`'s constants (imported, not re-typed), so the two
  layers cannot drift.
- The diversity rule itself (kinds differ, or ≥ gap-days across two distinct
  **attributable** origins) stays where T2.02 built it; T2.03 parameterises it
  (Step 1) so config values flow in without duplicating the rule.
- **Test:** absent row → defaults; a row that **tightens** (`n_default: 4`,
  `gap_days: 14`) is honoured; defaults equal the T2.02 constants; the
  decision actually changes when config changes (promotion at 3 origins under
  default N, not under `n_default: 4`).
- **Test (all three parameters, at the decision, not at the dataclass).**
  *Review finding I2.* The tests above pin `n_default` only, so a mutant that
  ignores the `time_gap_days` or `n_diverse` argument in
  `required_origin_count_for` and keeps reading the module constant survives
  every one of them — T2.02's suite is identical under the delegation, and a
  tightening assertion read off the returned `LadderConfig` proves the value was
  *parsed*, never that it was *used*. So each parameter is asserted **through a
  changed promotion outcome**:
  - `time_gap_days: 14` with two same-kind origins 10 days apart → the gate no
    longer fires, N=3, K=2 does **not** promote (under the default 7 it does).
  - `n_diverse: 3` with two diverse-kind origins → N=3, K=2 does **not**
    promote (under the default 2 it does).
  - `n_default: 4` with three same-kind same-day origins → no promotion.
- **Unknown and malformed keys** (*review M4*): an unrecognised key in the row
  is ignored with a warning naming it, and a value of the wrong type falls back
  to its default with a warning — the row is operator-edited with no schema in
  front of it, so a typo must degrade to the conservative bar rather than raise
  inside a recompute.

### D3 — "Loosening either requires a G-C measurement (T2.40), not an edit"

- Direction-of-error enforcement in the reader, mirroring
  `get_measured_flags` (`feature_flags.py:37–59`): the shipped defaults are
  **floors**. A `config` value looser than its floor (`n_default < 3`,
  `n_diverse < 2`, `time_gap_days < 7`, or `n_default < n_diverse`) is
  **clamped back to the floor** with a loud warning naming T2.40 — unless that
  parameter is listed in a `ladder_measurements` `config` row, the analogue of
  `flag_measurements`: nothing in the codebase writes it, and its only
  intended writer is T2.40's gate-clearing process recording a ledger entry.
  Clamping (not raising) is chosen so a bad row degrades to the conservative
  bar instead of taking the recompute down.
- **Test:** a loosened row without a measurement entry leaves the *effective*
  values at the floor (asserted via the decision: 2 same-kind, same-day
  origins do not promote even with `n_default: 2` in the DB) and logs the
  warning; the same row *with* a measurement entry is honoured. **Break the
  guard on purpose:** remove the clamp, watch the first test fail, restore,
  watch it pass — recorded in the completion report.
- **Test (the clamp covers all three parameters, and permission is
  per-parameter).** *Review finding I2, second half.* A clamp applied to
  `n_default` alone survives the test above — and a row carrying
  `time_gap_days: 0` would then manufacture the N=2 gate out of two
  **same-second** origins, which is precisely the counterfeit corroboration
  T2.02's doctrine exists to forbid. Likewise, a measurements reader that
  treats the row's mere *presence* as blanket permission passes both stated
  tests. So:
  - `time_gap_days: 0`, no measurement → clamped to 7; a same-day attributable
    pair does **not** promote.
  - `n_diverse: 1`, no measurement → clamped to 2.
  - **Mixed row**: loosen two parameters, list only one in
    `ladder_measurements` → the listed one is honoured and the unlisted one is
    clamped, in the same decision. This is the test that separates
    per-parameter permission from blanket permission.
- **The ordering violation clamps unconditionally** (*review M3*):
  `n_default < n_diverse` inverts the ladder — the fallback bar sitting below
  the gated bar means firing a gate would *raise* N — and no measurement can
  make that coherent, so unlike the three floors it is **not** unlockable by a
  `ladder_measurements` entry. Stated here so the asymmetry is a decision
  rather than an omission.

### D4 (binding via doc 04 §8.3, not a checkbox) — `confidence` is aggregated, recomputed alongside `verification_status`

The corpus fixes the **properties** ("aggregated support/quality estimate,
recomputed with `verification_status`, never a single-source guess" — doc 04
§8.3; doc 08 §4.1) but no formula. The formula is therefore stated **here,
before implementation**, and pinned by property tests:

```
support    = min(K, N) / N          # K = distinct origin count (bucket included), N = required N
confidence = min(0.90, 0.40 + 0.40 * support + 0.10 * (1 if diverse-or-time-gate fired else 0))
```

- Properties pinned by test: **row-count invariance** (ten rows from one
  origin score identically to one row), **monotone non-decreasing** in
  distinct origins, **capped at 0.90** (the machine never claims certainty —
  the badge's honest-claim doctrine, doc 08 §4.1), fully deterministic.
- **Exact-value vectors, not properties alone** (*review M1*). All four
  properties above are survived by a coefficient typo: `0.04 * support` is
  monotone, capped, row-invariant and deterministic while every confidence in
  the system is wrong. So the formula is pinned by exact values —
  K=0 → `0.40`; K=2, N=3 → `0.6667`; K=3, N=3 → `0.80`; any gate-fired K ≥ N →
  `0.90` — including the vector that **crosses the N-shift**, which is the
  case most likely to be got wrong: two same-kind origins score `0.6667` at
  N=3, and adding a third origin of a different kind flips N to 2 and the
  score to `0.90`.
- **Contradiction deliberately does not enter the formula.** A
  contradiction-blocked hold with K ≥ N and a fired gate therefore carries
  `0.90`. That is intended, not emergent: `confidence` is doc 04 §8.3's
  *aggregated support* estimate, and a dispute is a fact about adjudication,
  which lives on the verification and `review_state` surfaces that T2.04 owns.
  Recorded here because "high confidence on a blocked fact" reads as a bug to
  anyone who has not seen this sentence.
- Confidence is written **in the same UPDATE** as the status (Step 4), so the
  two can never drift, and belief columns are untouched — writing
  status+confidence together is verification-axis-only and does not violate
  T2.01's no-both-axes contract (`knowledge_triples.py:1–9`), which is about
  the two *axes*, not two columns of one axis.
- **The `confirmed` case needs a status-free write path** (*review finding
  I3*). Step 3 holds `confirmed` while still refreshing confidence, but
  `set_verification_status` **raises on `confirmed` before any read or write**
  (`knowledge_triples.py:338–347`, pinned by
  `test_knowledge_triples.py:482–488`), so the applier can never reach it by
  passing the current status back in. Resolution, fixed here rather than
  improvised at Step 4: the `confidence` keyword is accepted with
  **`status=None`**, meaning *write confidence only, change no status, journal
  nothing* — no transition occurred, so the no-op journal guard's contract is
  preserved by construction rather than by a second code path. The `confirmed`
  hold and the `disputed` hold both take that route; `candidate` and
  `corroborated` holds may take either, since passing the unchanged status is
  already a journal no-op. T2.01's refusal is untouched and its tests stay
  green unedited.
- The constants are cheap to revise now — the table has zero production rows
  (no producer until T2.10) — and revising them later is an amendment, not a
  refactor. The executor records the formula decision as an amendment-log row
  in `E2-truth-core.md` (Tier 2: T2.06's journal evidence, T2.36's badge and
  the review queue's ranking all read this number).

## 5. Risks

| Risk | Why it bites | Mitigation |
|---|---|---|
| Widening into the six adjacent tasks | Doc 08 §4 describes the whole ladder in one section | §2's table is the boundary; every seam is named with its owner; review checks the diff against it |
