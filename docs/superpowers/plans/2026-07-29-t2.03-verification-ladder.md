## 3. The Done-when items, made executable

### D1 — "Promotion is a pure function of the ladder inputs — reproducible on replay"

- One pure function: `decide(current_status, profile, config, *,
  open_contradiction) -> LadderDecision`. No I/O, no session, **no clock** —
  the time-gap gate reads `OriginProfile.max_cross_origin_gap`, which is
  computed only from stored timestamps relative to each other
  (`fact_sources.py:212–231`).
- The inputs are exactly: the fact's current `verification_status`, the
  `OriginProfile` snapshot, the `LadderConfig` values, and the contradiction
  verdict. Nothing else may be read.
- **Test (replay):** serialise a decision's inputs to plain data, re-run
  `decide` from the deserialised inputs, assert the identical `LadderDecision`.
  Run the same profile through twice; assert equality. `recompute_fact` twice
  on an unchanged fact: second run is a no-op and journals nothing (the
  repository's no-op guard, `knowledge_triples.py:371`, plus the decision's
  determinism).
- **Test (ceiling):** for every constructed profile — including one with a
  `human`-kind dominant origin and arbitrarily many diverse origins —
  `decide` never returns `confirmed`; the machine-target type does not admit
  it. Belt-and-braces: forcing the applier toward `confirmed` hits T2.01's
  refusal (`ValueError`), asserted by test.
- **Test (orthogonality):** `recompute_fact` on a fact with belief columns set
  leaves `valid_at`/`invalid_at`/`expired_at` bit-identical; recomputing an
  `expired`-yet-`confirmed` fact holds `confirmed` and touches no timestamp.

### D2 — "N and the diversity rule read from `config`, defaults stated"

- One `config` row, key `verification_ladder`, merged over code defaults with
  the `get_feature_flags_dict` pattern (`feature_flags.py:13–21`):
  `corroboration_n_default = 3`, `corroboration_n_diverse = 2`,
  `corroboration_time_gap_days = 7`. The defaults are **the same objects** as
  `fact_sources.py:111–113`'s constants (imported, not re-typed), so the two
  layers cannot drift.
- The diversity rule itself (kinds differ, or ≥ gap-days across two distinct
  **attributable** origins) stays where T2.02 built it; T2.03 parameterises it
  (Step 1) so config values flow in without duplicating the rule.
- **Test:** absent row → defaults; a row that **tightens** (`n_default: 4`,
  `gap_days: 14`) is honoured; defaults equal the T2.02 constants; the
  decision actually changes when config changes (promotion at 3 origins under
  default N, not under `n_default: 4`).

### D3 — "Loosening either requires a G-C measurement (T2.40), not an edit"

- Direction-of-error enforcement in the reader, mirroring
  `get_measured_flags` (`feature_flags.py:37–59`): the shipped defaults are
  **floors**. A `config` value looser than its floor (`n_default < 3`,
  `n_diverse < 2`, `time_gap_days < 7`, or `n_default < n_diverse`) is
  **clamped back to the floor** with a loud warning naming T2.40 — unless that
  parameter is listed in a `ladder_measurements` `config` row, the analogue of
  `flag_measurements`: nothing in the codebase writes it, and its only
  intended writer is T2.40's gate-clearing process recording a ledger entry.
  Clamping (not raising) is chosen so a bad row degrades to the conservative
  bar instead of taking the recompute down.
- **Test:** a loosened row without a measurement entry leaves the *effective*
  values at the floor (asserted via the decision: 2 same-kind, same-day
  origins do not promote even with `n_default: 2` in the DB) and logs the
  warning; the same row *with* a measurement entry is honoured. **Break the
  guard on purpose:** remove the clamp, watch the first test fail, restore,
  watch it pass — recorded in the completion report.

### D4 (binding via doc 04 §8.3, not a checkbox) — `confidence` is aggregated, recomputed alongside `verification_status`

The corpus fixes the **properties** ("aggregated support/quality estimate,
recomputed with `verification_status`, never a single-source guess" — doc 04
§8.3; doc 08 §4.1) but no formula. The formula is therefore stated **here,
before implementation**, and pinned by property tests:

```
support    = min(K, N) / N          # K = distinct origin count (bucket included), N = required N
confidence = min(0.90, 0.40 + 0.40 * support + 0.10 * (1 if diverse-or-time-gate fired else 0))
```

- Properties pinned by test: **row-count invariance** (ten rows from one
  origin score identically to one row), **monotone non-decreasing** in
  distinct origins, **capped at 0.90** (the machine never claims certainty —
  the badge's honest-claim doctrine, doc 08 §4.1), fully deterministic.
- Confidence is written **in the same UPDATE** as the status (Step 4), so the
  two can never drift, and belief columns are untouched — writing
  status+confidence together is verification-axis-only and does not violate
  T2.01's no-both-axes contract (`knowledge_triples.py:1–9`), which is about
  the two *axes*, not two columns of one axis.
- The constants are cheap to revise now — the table has zero production rows
  (no producer until T2.10) — and revising them later is an amendment, not a
  refactor. The executor records the formula decision as an amendment-log row
  in `E2-truth-core.md` (Tier 2: T2.06's journal evidence, T2.36's badge and
  the review queue's ranking all read this number).

**Step 1 — Parameterise the threshold rule in `fact_sources` (pure refactor).**

*Verify:* `cd backend && python -m pytest tests/test_fact_sources.py -q` —
green with **zero test edits**.

**Step 2 — `LadderConfig`: defaults, reader, floor clamp, measurement gate (D2, D3).**
New module `app/services/verification_ladder.py`, config half:
`LADDER_CONFIG_KEY = "verification_ladder"`, a frozen `LadderConfig`
dataclass whose defaults are imported from `fact_sources`,
`get_ladder_config(session)` (merge → validate → clamp-with-warning per D3),
`LADDER_MEASUREMENTS_KEY = "ladder_measurements"` with a reader modelled on

*Verify:* `cd backend && python -m pytest tests/test_verification_ladder.py -q`
(new file, config tests from §3 D2/D3).

**Step 3 — `LadderDecision` + `decide()` — the pure core (D1, D4, ceiling).**
Same module. `LadderDecision` (frozen): `fact_id`, `current_status`,
`target_status`, `outcome` (`promote | demote | hold`), `origin_count`,
`required_n`, `gate_fired` (`diversity | time_gap | none`), `source_kinds`,
`contradiction_blocked`, `confidence`. Rules:

- `confirmed` → hold status (machine never moves it; confidence still
  recomputed — the human row is a dominant origin and remains countable).
- `disputed` → hold entirely (entry and recovery are T2.04's).
- `open_contradiction=True` → promotion blocked, `contradiction_blocked=True`;
  the `disputed` write is T2.04's, not here.
- else K ≥ N → `corroborated`; K < N → `candidate` (immediate demotion;
  hysteresis is T2.46's, interposed at the applier via the `demote` outcome).
- `target_status` is typed as `Literal["candidate", "corroborated"]`-plus-hold;
  `confirmed`/`disputed` are unrepresentable as machine targets.

Tests: promotion at N under each of the three shapes (diverse kinds → N=2;
same-kind ≥7 days across two attributable origins → N=2; three same-kind
same-day origins → N=3); the anonymous bucket counts toward K but never
lowers N (reusing T2.02's semantics through the parameterised rule); replay
determinism; the ceiling; the confidence properties (D4).
*Verify:* `cd backend && python -m pytest tests/test_verification_ladder.py -q`.

**Step 4 — `recompute_fact` applier + the confidence write path.**
Extend `set_verification_status` with an optional keyword `confidence`
(one UPDATE writing both verification-axis columns; journal semantics
unchanged — event on status change only, payload unchanged, T2.01's tests
must stay green without edits). `recompute_fact(session, fact_id, *,

row, calls `decide`, applies through the repository, returns the

last-source-withdrawal is T2.47's, not triggered from here).
*Verify:* `cd backend && python -m pytest tests/test_verification_ladder.py
tests/test_knowledge_triples.py -q`.
