## 3. Design decisions the brief demands, each settled

### D1 — Three verdicts, not two

The judge emits exactly `{"entailed", "contradicted", "unsupported"}` — the gold's own
vocabulary. The binary grounded/ungrounded is **derived at scoring time** via the imported
`GROUNDED_VERDICTS`, never re-declared. Reasons: (a) the veto consumer's truth-critical
number is precision on `contradicted` specifically, and T2.25's reviewer warned that a
judge collapsing `unsupported` into `contradicted` manufactures disputes invisibly to any
binary aggregate; (b) doc 17 §6 says the veto consumer "inherits the same qualification on
the contradiction verdict"; (c) a two-way judge could not serve consumer 1 at all. The
scorer reports the full 3×3 confusion matrix (plus an `invalid` prediction column), binary
entailed-precision/recall, contradiction-precision/recall, and the per-slice table T2.25's
report §7.3 asks for.

A model response that fails to parse into one of the three verdicts is scored as
`invalid`: it is never an acceptance (cannot create a false accept) and always a miss for
the gold class (hurts recall). Invalid counts are reported, not folded away.

### D2 — The judge lives in `app/services`, and the harness measures that exact code

"One judge, three consumers" is only true if the qualification measures the same prompt,
parser, and call construction the consumers will run. So the judge — prompt, parsing,
seed derivation, verdict types — is `app/services/verification_judge.py`, and benchlib
drives it through the orchestrator seam exactly as `full_context.py` drives the reasoning
purpose. Benchlib contains only what is harness-shaped: scoring, eligibility, report,
recorder, runner. Nothing in `app/` imports benchlib (unchanged rule).

### D3 — The bars: three `config` rows, defaults stated here, before any number

Doc 17 §6 names the rows and the starting values; doc 17 §11 confirms they are
"conservative starting `config` values". Defaults (code) with DB-over-defaults merge, one
`config` row per bar, keyed exactly:

| Row key | Default | Meaning |
|---|---|---|
| `groundedness_gate_precision_bar` | `0.95` | precision on `entailed` (binary accept) |
| `groundedness_gate_recall_bar` | `0.90` | recall on `entailed` |
| `contradiction_precision_bar` | `0.95` | precision on `contradicted` — the veto consumer "inherits the same qualification" (doc 17 §6), so it inherits the same conservative value |

Granularity arithmetic at today's 41 pairs, stated before the run so the reader can
recheck rather than trust (T2.25 report §7.1's method):

- 17 gold-entailed. A perfect-recall judge accepts 17; one false accept → 17/18 ≈ 0.944
  < 0.95. **The precision bar is "zero false accepts" at this size.**
- Recall 16/17 ≈ 0.941 ≥ 0.90; 15/17 ≈ 0.882 < 0.90. **At most one false reject.**
- 10 gold-contradicted. One false contradiction among 11 → 10/11 ≈ 0.909 < 0.95.
  **Zero false contradictions.**

That is a statement about the set being too small for a stable number — exactly why the
gate waits on T2.54 — not about the bars being too strict. The defaults are **not**
retuned by this task under any interim result (doc 17 §8: bar changes follow the tuning
protocol with their own recorded runs).

The bench runner reads the code defaults (the bench context has no operator DB) and stamps
the bars in effect into its output. The app-side guard reads the merged DB-over-defaults
values at enforcement time — so an operator who *raises* a bar above the recorded
measurement flips the judge back to unqualified, which is the correct direction of
surprise.

### D4 — Qualification is computed, never remembered; model swap is detected

Doc 17 §11: "re-qualification required after any `verification`-purpose model swap", and
the qualification result "is recorded against the model identity" (§6). Mechanism:

- **Judge identity** = the resolved `verification` purpose's
  `{model, base_url, api_kind, dimensions, reasoning, params}` (the same field set
  `caching_llm._KEYED_CONFIG_FIELDS` already uses; `api_key` excluded — rotating a
  credential is not a model swap) **plus `prompt_version` plus
  `prompt_sha = sha256(system prompt text + user-message template)[:16]`** **[N2]**.
  The template (`PREMISE:\n{premise}\n\nHYPOTHESIS:\n{hypothesis}`) is equally
  behaviour-shaping prompt text sent on every call — hashing only the system prompt
  would leave it silently editable under an unchanged identity, so both are folded in.
  The `prompt_sha` is what makes a prompt change a judge change *mechanically*: an edit
  to either text without a version bump still changes the identity hash, so an
  undisclosed edit cannot produce a same-identity report or record — the version field
  remains the human-readable disclosure, the text hash is the enforcement. (The verdict
  *parser* stays outside the hash deliberately: it is code under the version-bump duty
  and git review, not prompt text.) Whole identity hashed as
  `sha256(canonical JSON)[:16]`; both `prompt_version` and `prompt_sha` appear in the
  report.
- **Qualification record** = a committed JSON artifact at
  `backend/app/services/verification_qualification.json` carrying the identity (and its
  hash), the measured metrics, the gold's version/counts/provenance, **the gold file's
  content hash (`gold_sha256`) and the gate run's ledger `run_id`** so record ↔ ledger ↔
  gold bind to one another **[I1]**, `gate_eligible`, git sha, timestamp. **T2.26 ships no
  artifact** — the file is absent until a `--gate` run (T2.41's) writes one, and that
  absence is **test-pinned** on this branch (the reserved-provenance zero-pin idiom from
  T2.25): the first record is a deliberate diff that must consciously edit a test
  **[I1]**. Absent record ⇒ unqualified.
- **The canonical record can only be minted against the canonical gold** **[I1]**:
  `write_qualification_record` (and the runner's `--gate` branch) refuse to write the
  real `QUALIFICATION_RECORD_PATH` unless the run's resolved `gold_path ==
  entailment_gold.GOLD_PATH`. `--gate --gold /anywhere/easy_gold.json` therefore cannot
  produce a record the app-side guard honours; rehearsal runs pair a fixture gold with a
  non-default `--record-path` and stay fully testable.
- **`qualification_state(...)`** recomputes at read time: record present AND
  `gate_eligible` AND record identity hash == hash of the *currently resolved* purpose
  config AND recorded metrics clear the *currently merged* bars. Any failure yields
  `qualified=False` with machine-readable reasons, and the comparison **fails closed**: a
  record whose `entailed_precision` (or any bar-governed metric) is absent or `None` is
  unqualified, never treated as passing **[m4]**. A production model swap changes the
  resolved config, the hash stops matching, and every consumer is refused — detected, not
  remembered.

### D5 — "Enforced in code, not by policy": five layers, each with a test

The gate ledger assigns the ship-*path* enforcement to T3.03 ("enforced in code (T3.03)").
T2.26's third Done-when is satisfiable now because T2.26 owns the *mechanism* that path
must pass through, and makes bypassing it a build failure:

1. **The only public verdict door is gated.** `VerificationJudge.judge(...)` checks
   `qualification_state` and raises `JudgeNotQualifiedError` when unqualified. Today it
   refuses unconditionally (no record exists) — an L3 article cannot obtain even one
   "entailed" verdict, let alone ship as grounded.
2. **The ungated door is named for what it is.** `qualification_probe(...)` exists so the
   harness can measure an unqualified judge (the chicken-and-egg is real); its name is the
   warning label.
3. **A source scan over `backend/app`** (dream-jobs-scan idiom, with the file-count floor
   and a negative control) fails the build if any module other than
   `verification_judge.py` dispatches `chat_completion` on the `"verification"` purpose or
   calls `qualification_probe`. So T2.11/T3.03 physically cannot reach the purpose except
   through the gated door.
4. **Invariant 15 scan:** no module under `app/api` or the capture/retrieval services
   imports `verification_judge` (allowlist: empty today). Mirrors
   `test_no_app_code_reaches_a_family_job`.
5. **The record cannot be minted sideways** **[I1]**: the canonical-gold coupling and the
   test-pinned absence of the record file (D4) close the path where a rehearsal `--gate`
   run against an easy gold flips every consumer to qualified.

Each guard gets the break-it-watch-it-fail-restore-it proof (runbook §4).

One residual, stated honestly (accepted by the review as such, not a finding): nothing
built here can force a *future* ship path to call the judge at all — that half is the
ledger's "enforced in code (T3.03)". What T2.26 makes true is that any path which does
obtain verdicts can only obtain them through the gated door, and the door refuses below
the bar.

### D6 — Interim vs gate-opening, drawn mechanically

The line the brief demands, in code rather than prose:

- **Default mode** (`python scripts/benchlib/run_judge_qualification.py`, this task's
  Verify) measures the judge and emits the dated report + **two ledger rows — the
  write-ahead intent row, then the scored row referencing it** (N1's mechanism: the
  ledger is append-only, so the intent marker that must precede gold contact can never
  be updated in place into the scored row; folding them into one line would be a
  reversion to write-behind counting) — report and scored row both stamped
  `gate_eligible: false` with reasons **computed from the gold file itself**. The exact
  predicate **[I3]**, stated here so its boundaries are conscious choices:

  ```
  eligible ⇔ live_pairs >= 200
           ∧ declared_provenance_counts["l2-fact"] >= 1
           ∧ (no live pair has label_source == "author")
  ```

  and eligibility output always surfaces the **actual counts**, never a bare boolean —
  `l2-fact: 1/200` must be visible in the reasons, the report and the `--gate` output, so
  a barely-eligible composition is legible to T2.41's human adjudication **[I3]**. The
  `>= 1` floor is deliberately the *minimum decodable* reading of §11's synthetic-only
  rejection: it blocks the named vector (a grown-but-still-synthetic set) mechanically,
  while the adequacy of, say, 1-real-in-200 is T2.41's adversarial call — the runner
  hands it the numbers, and §7 routes the open question of a real proportion floor (plus
  the missing provenance *anchor* for `l2-fact` pairs, which today is a self-declared
  field with no verbatim-content check like the corpus pairs have) as a Tier-2 note to
  T2.54 **[I3]**. The report's first line is an INTERIM banner naming T2.54 and T2.41.
- **`--gate` mode** (T2.41's Verify) refuses up front — before any model call — unless
  all three eligibility conditions pass. Only this mode writes
  `app/services/verification_qualification.json`. Therefore G-D structurally cannot be
  claimed, and the app-side judge cannot become qualified, on today's gold — no matter
  what the interim numbers say. T2.26 tests the refusal against the real gold file.
- The interim numbers still land in `gate-ledger.md` under G-D (fourth Done-when) as an
  explicitly-labelled interim block; the Bar cells are filled (bars stated before the gate
  run); Measured/Verdict cells stay `—` for T2.41.

### D7 — Determinism

The judge forwards `seed = _content_seed(premise + "\n" + hypothesis)` on every call —
the same doctrine as extraction (CLAUDE.md "Reproducibility"), same helper, honoured by
DeepSeek. Temperature 0 rides the purpose `params` (doc 17 §6: "temperature 0, structured
verdict"). The prompt is versioned (`JUDGE_PROMPT_VERSION`), folded into the identity
(D4); the disk cache already keys on purpose config + messages, so prompt or model changes
miss instead of replaying stale answers. Two consecutive warm runs must reproduce the
reproducible-metrics JSON block byte-for-byte (retrieval-eval convention; latency
excluded).

### D8 — Cost (doc 11 §6's Tier-C bound) and the twin

`TwinningOrchestrator` with a dedicated cache dir
(`scripts/benchlib/entailment/cache/`, gitignored like the retrieval cache). Since the
fixture stage (D9) probes through the same judge, its samples must not blend into the
gold measurement — the twin's own never-merge-populations doctrine, one level up. So
**two declared latency channels**: `fixture_call` (~9 samples, below the 20-sample
percentile floor and reported unpowered, which is honest and expected) and `judge_call`
(the 41 gold samples, powered), `declared_channels=("fixture_call", "judge_call")`.
**Tokens likewise split**: the runner snapshots `llm.tokens.as_dict()` at fixture-stage
end and reports gold-pass usage as final-minus-snapshot; **the doc 11 §6 cost bound —
tokens-per-claim — is computed over the gold pass only**, with the fixture stage's cost
rendered as its own labelled line (plumbing overhead, not part of the per-claim bound a
consumer would pay). The twin's per-purpose totals carry both, as they must; the
report's split is what keeps the bound honest. The ledger row goes through a sanctioned
recorder built on `EvalRun`, so the no-twin-no-accuracy guard bites.

### D9 — The prompt freezes before first gold contact, and the freeze is code **[C1]**

The gold was built before the judge so the judge cannot be tuned to it. The prompt
encodes the *task semantics* from `entailment/LABELLING.md` — verdict definitions,
implicature-is-not-contradiction, evaluation-time, entailment's asymmetry — which is
specifying the task the consumers also need, not leaking answers (the review explicitly
cleared this). The leakage risk is elsewhere: a sanity gate evaluated *inside* the gold
run licenses "debug, fix, re-run" loops in which every retry is a full live pass over the
gold, and the natural fix for a high-invalid run is a prompt edit — prompt iteration
informed by live gold outputs. Those 41 pairs persist append-only into T2.54's ≥ 200 set,
so a prompt shaped against them would contaminate roughly a fifth of what T2.41 measures.
So the discipline is restructured into the runner itself:

- **Sanity fixtures, not gold, absorb live plumbing shakeout.** A committed fixture file
  `scripts/benchlib/entailment/sanity_pairs.json` with **≥ 3 pairs per verdict class**
  (≥ 9 total), authored fresh for this purpose, never drawn from gold, never counted by
  the gold loader or the drift guard **[m2]**. Fixtures carry `{id, premise, hypothesis,
  note}` — no expected-verdict comparison in the gate, so they measure parseability and
  class diversity, not correctness.
- **The fixture stage runs inside the runner, before any gold call.** Predicate:
  fixture invalid-rate < 10% (at 9 fixtures: zero invalids) AND ≥ 2 distinct valid
  verdict classes emitted. A failure aborts the run **before the first gold pair is
  sent** — the discipline is code, at a cost of ~9 extra live calls.
- **Prompt and parser freeze at fixture-pass** — i.e., before first gold contact. Prompt
  edits during fixture shakeout are free and uncontaminating.
- **The in-run gold sanity backstop remains** (same predicate over the gold pass), but a
  trip after gold contact permits **transport/IO fixes only** (timeouts, auth, encoding,
  cache pathing). Any prompt or verdict-mapping edit after gold contact **must bump
  `JUDGE_PROMPT_VERSION`** (a new judge identity, D4) and be disclosed in the report and
  ledger as gold-contaminating.
- **Gold-touching attempts are counted intent-first and across identities** **[N1]**.
  The marker is written **before** the first gold call, not after a graceful abort: once
  the fixture stage passes and the gold file is loaded, the runner appends an intent row
  (`kind: "judge_qualification_attempt"`, the identity hash, `prompt_sha`,
  `gold_sha256`, timestamp) to the ledger and only then sends the first gold pair. A
  crash, kill, or transport exception mid-pass therefore still leaves its marker — the
  untidy failures a live API makes likely are exactly the ones counted, and the cached
  gold responses they leave behind are accounted for. `gold_touching_attempts` on a
  scored run = the count of intent rows **for the same `gold_sha256` across all
  identity hashes** (its own intent row included) — keying on the gold, not the
  identity, so a disclosed `JUDGE_PROMPT_VERSION` bump cannot reset the counter and a
  contaminated re-run can never report `gold_touching_attempts == 1`. The scored ledger
  row carries its own intent row's id, so completed and abandoned attempts stay
  distinguishable. Published in the report, the ledger row, and the G-D interim block.
  **How to read the number**, stated in the report itself: intent rows count gold
  *contacts*, including warm cache replays (7.3's verification rerun legitimately
  pushes the committed value to 2 on one live pass) — over-counting is the safe
  direction, and each contact's live-vs-replay nature is reconstructible from its
  scored row's twin (the `judge_call` live/cache populations). And the counter is
  **scoped per gold version**: it keys on `gold_sha256`, so it legitimately resets when
  T2.54 grows the gold, while the old-sha intent rows persist in the append-only ledger
  — inherent to per-file-hash keying, not a covert reset, and T2.41 must read the
  number per gold version accordingly.
- Exactly one counted run; its number is reported whatever it is. No re-run-until-pass;
  judge improvement is a future recorded tuning run (doc 17 §8).

The judge prompt, written once from LABELLING.md, versioned as `JUDGE_PROMPT_VERSION = 1`
(system message; the user message is `PREMISE:\n{premise}\n\nHYPOTHESIS:\n{hypothesis}`):

```
You are a strict natural-language-inference judge. Given a PREMISE (a stored
fact) and a HYPOTHESIS (a claim), return exactly one verdict:

- "entailed": the premise alone makes the hypothesis true. A hypothesis that
  is strictly weaker than the premise (less precise, a subset of what the
  premise asserts) is still entailed. Use only the premise — never outside
  knowledge or plausibility.
- "contradicted": the premise and the hypothesis cannot both be true. This
  includes: a different value in a slot the premise fills exclusively; a
  present-tense claim of a state whose validity window the premise explicitly
  closes; an explicit negation; a reversed relation when the relation is
  exclusive in direction.
- "unsupported": neither of the above. A hypothesis that adds anything the
  premise does not assert (extra hosts, versions, causes, quantifiers,
  vendors) is unsupported, not entailed — even if plausible. A hypothesis the
  premise merely implicates but does not assert is unsupported, not
  contradicted. A time-anchored premise neither entails nor contradicts an
  un-anchored "currently" claim unless the window decides it.

Judge only what the texts assert. Respond with JSON:
{"verdict": "entailed" | "contradicted" | "unsupported", "reason": "<one sentence>"}
```

Call construction: `chat_completion("verification", messages,
response_format={"type": "json_object"}, seed=_content_seed(premise + "\n" + hypothesis))`.
Parsing: `json.loads` with a fallback scan for a bare verdict token; anything not mapping
to exactly one verdict → `valid=False, verdict=None`.

  the match rule **[I2]**. The two-line negative control proves the indirection bypass
