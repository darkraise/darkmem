## 3. Design decisions the brief demands, each settled

### D1 — Three verdicts, not two

The judge emits exactly `{"entailed", "contradicted", "unsupported"}` — the gold's own
vocabulary. The binary grounded/ungrounded is **derived at scoring time** via the imported
`GROUNDED_VERDICTS`, never re-declared. Reasons: (a) the veto consumer's truth-critical
number is precision on `contradicted` specifically, and T2.25's reviewer warned that a
judge collapsing `unsupported` into `contradicted` manufactures disputes invisibly to any
binary aggregate; (b) doc 17 §6 says the veto consumer "inherits the same qualification on
the contradiction verdict"; (c) a two-way judge could not serve consumer 1 at all. The
scorer reports the full 3×3 confusion matrix (plus an `invalid` prediction column), binary
entailed-precision/recall, contradiction-precision/recall, and the per-slice table T2.25's
report §7.3 asks for.

A model response that fails to parse into one of the three verdicts is scored as
`invalid`: it is never an acceptance (cannot create a false accept) and always a miss for
the gold class (hurts recall). Invalid counts are reported, not folded away.

### D2 — The judge lives in `app/services`, and the harness measures that exact code

"One judge, three consumers" is only true if the qualification measures the same prompt,
parser, and call construction the consumers will run. So the judge — prompt, parsing,
seed derivation, verdict types — is `app/services/verification_judge.py`, and benchlib
drives it through the orchestrator seam exactly as `full_context.py` drives the reasoning
purpose. Benchlib contains only what is harness-shaped: scoring, eligibility, report,
recorder, runner. Nothing in `app/` imports benchlib (unchanged rule).

### D3 — The bars: three `config` rows, defaults stated here, before any number

Doc 17 §6 names the rows and the starting values; doc 17 §11 confirms they are
"conservative starting `config` values". Defaults (code) with DB-over-defaults merge, one
`config` row per bar, keyed exactly:

| Row key | Default | Meaning |
|---|---|---|
| `groundedness_gate_precision_bar` | `0.95` | precision on `entailed` (binary accept) |
| `groundedness_gate_recall_bar` | `0.90` | recall on `entailed` |
| `contradiction_precision_bar` | `0.95` | precision on `contradicted` — the veto consumer "inherits the same qualification" (doc 17 §6), so it inherits the same conservative value |

Granularity arithmetic at today's 41 pairs, stated before the run so the reader can
recheck rather than trust (T2.25 report §7.1's method):

- 17 gold-entailed. A perfect-recall judge accepts 17; one false accept → 17/18 ≈ 0.944
  < 0.95. **The precision bar is "zero false accepts" at this size.**
- Recall 16/17 ≈ 0.941 ≥ 0.90; 15/17 ≈ 0.882 < 0.90. **At most one false reject.**
- 10 gold-contradicted. One false contradiction among 11 → 10/11 ≈ 0.909 < 0.95.
  **Zero false contradictions.**

That is a statement about the set being too small for a stable number — exactly why the
gate waits on T2.54 — not about the bars being too strict. The defaults are **not**
retuned by this task under any interim result (doc 17 §8: bar changes follow the tuning
protocol with their own recorded runs).

The bench runner reads the code defaults (the bench context has no operator DB) and stamps
the bars in effect into its output. The app-side guard reads the merged DB-over-defaults
values at enforcement time — so an operator who *raises* a bar above the recorded
measurement flips the judge back to unqualified, which is the correct direction of
surprise.

### D4 — Qualification is computed, never remembered; model swap is detected

Doc 17 §11: "re-qualification required after any `verification`-purpose model swap", and
the qualification result "is recorded against the model identity" (§6). Mechanism:

- **Judge identity** = the resolved `verification` purpose's
  `{model, base_url, api_kind, dimensions, reasoning, params}` (the same field set
  `caching_llm._KEYED_CONFIG_FIELDS` already uses; `api_key` excluded — rotating a
  credential is not a model swap) **plus `prompt_version`** — a prompt change is a judge
  change. Hashed as `sha256(canonical JSON)[:16]`.
- **Qualification record** = a committed JSON artifact at
  `backend/app/services/verification_qualification.json` carrying the identity (and its
  hash), the measured metrics, the gold's version/counts/provenance, `gate_eligible`, git
  sha, timestamp. **T2.26 ships no artifact** — the file is absent until a `--gate` run
  (T2.41's) writes one. Absent record ⇒ unqualified.
- **`qualification_state(...)`** recomputes at read time: record present AND
  `gate_eligible` AND record identity hash == hash of the *currently resolved* purpose
  config AND recorded metrics clear the *currently merged* bars. Any failure yields
  `qualified=False` with machine-readable reasons. A production model swap changes the
  resolved config, the hash stops matching, and every consumer is refused — detected, not
  remembered.

### D5 — "Enforced in code, not by policy": four layers, each with a test

The gate ledger assigns the ship-*path* enforcement to T3.03 ("enforced in code (T3.03)").
T2.26's third Done-when is satisfiable now because T2.26 owns the *mechanism* that path
must pass through, and makes bypassing it a build failure:

1. **The only public verdict door is gated.** `VerificationJudge.judge(...)` checks
   `qualification_state` and raises `JudgeNotQualifiedError` when unqualified. Today it
   refuses unconditionally (no record exists) — an L3 article cannot obtain even one
   "entailed" verdict, let alone ship as grounded.
2. **The ungated door is named for what it is.** `qualification_probe(...)` exists so the
   harness can measure an unqualified judge (the chicken-and-egg is real); its name is the
   warning label.
3. **A source scan over `backend/app`** (dream-jobs-scan idiom, with the file-count floor
   and a negative control) fails the build if any module other than
   `verification_judge.py` dispatches `chat_completion` on the `"verification"` purpose or
   calls `qualification_probe`. So T2.11/T3.03 physically cannot reach the purpose except
   through the gated door.
4. **Invariant 15 scan:** no module under `app/api` or the capture/retrieval services
   imports `verification_judge` (allowlist: empty today). Mirrors
   `test_no_app_code_reaches_a_family_job`.

Each guard gets the break-it-watch-it-fail-restore-it proof (runbook §4).

### D6 — Interim vs gate-opening, drawn mechanically

The line the brief demands, in code rather than prose:

- **Default mode** (`python scripts/benchlib/run_judge_qualification.py`, this task's
  Verify) measures the judge and emits the dated report + one ledger row, both stamped
  `gate_eligible: false` with reasons **computed from the gold file itself**:
  `live_pairs < 200`, `l2-fact provenance count == 0` (doc 17 §11's synthetic-only
  rejection), `author-labelled live pairs present` (§11's maintainer-adjudication stance;
  T2.54 flips every survivor to `adjudicated`). The report's first line is an INTERIM
  banner naming T2.54 and T2.41.
- **`--gate` mode** (T2.41's Verify) refuses up front — before any model call — unless
  all three eligibility conditions pass. Only this mode writes
  `app/services/verification_qualification.json`. Therefore G-D structurally cannot be
  claimed, and the app-side judge cannot become qualified, on today's gold — no matter
  what the interim numbers say. T2.26 tests the refusal against the real gold file.
- The interim numbers still land in `gate-ledger.md` under G-D (fourth Done-when) as an
  explicitly-labelled interim block; the Bar cells are filled (bars stated before the gate
  run); Measured/Verdict cells stay `—` for T2.41.

### D7 — Determinism

The judge forwards `seed = _content_seed(premise + "\n" + hypothesis)` on every call —
the same doctrine as extraction (CLAUDE.md "Reproducibility"), same helper, honoured by
DeepSeek. Temperature 0 rides the purpose `params` (doc 17 §6: "temperature 0, structured
verdict"). The prompt is versioned (`JUDGE_PROMPT_VERSION`), folded into the identity
(D4); the disk cache already keys on purpose config + messages, so prompt or model changes
miss instead of replaying stale answers. Two consecutive warm runs must reproduce the
reproducible-metrics JSON block byte-for-byte (retrieval-eval convention; latency
excluded).

### D8 — Cost (doc 11 §6's Tier-C bound) and the twin

`TwinningOrchestrator` with a dedicated cache dir
(`scripts/benchlib/entailment/cache/`, gitignored like the retrieval cache). Tokens
accrue under the `verification` purpose; latency records one declared channel,
`judge_call`, with live/cache populations split (41 samples ≥ the 20-sample percentile
floor, so a cold run's p50/p95 are powered). The report renders tokens per claim (mean)
and the run total — the measured cost bound doc 11 §6 asks for — and the ledger row goes
through a sanctioned recorder built on `EvalRun`, so the no-twin-no-accuracy guard bites.

### D9 — One scored run; the prompt is written once, from LABELLING.md, before scoring

The gold was built before the judge so the judge cannot be tuned to it. The prompt
encodes the *task semantics* from `entailment/LABELLING.md` — verdict definitions,
implicature-is-not-contradiction, evaluation-time, entailment's asymmetry — which is
specifying the task the consumers also need, not leaking answers. Discipline, pre-stated:

- Plumbing is validated only against the stub-LLM tests and, live, against **4 sanity
  pairs authored fresh for this purpose** (committed as fixtures, never drawn from gold).
- Exactly one scored run counts. Its number is reported whatever it is. No prompt edits
  after the first scored run within this task; a poor interim number is a finding for the
  ledger, and judge improvement is a future recorded tuning run (doc 17 §8).
- Pre-stated plumbing-sanity criteria (a failure here is a harness defect to fix *before*
  the counted run, not tuning): invalid-verdict rate < 10%, and at least two distinct
  verdict classes emitted across the 41 pairs.

The judge prompt, written once from LABELLING.md, versioned as `JUDGE_PROMPT_VERSION = 1`
(system message; the user message is `PREMISE:\n{premise}\n\nHYPOTHESIS:\n{hypothesis}`):

```
You are a strict natural-language-inference judge. Given a PREMISE (a stored
fact) and a HYPOTHESIS (a claim), return exactly one verdict:

- "entailed": the premise alone makes the hypothesis true. A hypothesis that
  is strictly weaker than the premise (less precise, a subset of what the
  premise asserts) is still entailed. Use only the premise — never outside
  knowledge or plausibility.
- "contradicted": the premise and the hypothesis cannot both be true. This
  includes: a different value in a slot the premise fills exclusively; a
  present-tense claim of a state whose validity window the premise explicitly
  closes; an explicit negation; a reversed relation when the relation is
  exclusive in direction.
- "unsupported": neither of the above. A hypothesis that adds anything the
  premise does not assert (extra hosts, versions, causes, quantifiers,
  vendors) is unsupported, not entailed — even if plausible. A hypothesis the
  premise merely implicates but does not assert is unsupported, not
  contradicted. A time-anchored premise neither entails nor contradicts an
  un-anchored "currently" claim unless the window decides it.

Judge only what the texts assert. Respond with JSON:
{"verdict": "entailed" | "contradicted" | "unsupported", "reason": "<one sentence>"}
```

Call construction: `chat_completion("verification", messages,
response_format={"type": "json_object"}, seed=_content_seed(premise + "\n" + hypothesis))`.
Parsing: `json.loads` with a fallback scan for a bare verdict token; anything not mapping
to exactly one verdict → `valid=False, verdict=None`.

Interim-run judge config (recorded as the identity; the ledger fixes the model):
`{model: "deepseek-v4-flash", base_url: "https://api.deepseek.com/v1", api_kind:
"deepseek", api_key: $DEEPSEEK_API_KEY, params: {"temperature": 0, "max_tokens": 256,
"thinking": {"type": "disabled"}}}` — mirrors the `deepseek-flash-extraction` seed's
quirk handling (`llm_seed.py:108`).
