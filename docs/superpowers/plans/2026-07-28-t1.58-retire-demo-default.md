## 4. The auth path, concretely

### 4.1 What "works against the real backend end to end" means here

Unchanged from v1 — four flows, each already wired at the code level (§1):

1. **Logged-out first load.** `/` with no auth cookie and `DEMO=0` redirects to `/login`
   before the component renders (`_authenticated.tsx`'s `beforeLoad`).
2. **Login.** Real admin password → `useLogin` → `authAdapter.login` →
   `POST /api/v1/auth/login` → cookie-JWT issued, `isAuthenticated` flips, navigates to `/`.
3. **Session persistence across reload.** `zustand/persist`-backed, TTL-cached
   `checkAuth()` re-verify (60s).
4. **Logout and 401 handling.** Blocklists the token's `jti`, clears the cookie;
   `apiFetch`'s `handleUnauthorized()` forces a redirect on any subsequent 401.

### 4.2 What the e2e spec must assert — and the corrected exit-code claim (I1)

**v1 claimed `npm run test:e2e -- auth` "matches nothing and exits 0 … exactly the
silent-green failure mode." Measured this revision: `npx playwright test auth --list`
prints `Error: No tests found.` and exits 1.** The second half of the task's own Verify is
loud-red today, not silent-green — the opposite of what v1 stated as fact without running
it. This matters because it inverts the risk story: a controller reading v1 would believe
the Verify already half-passes vacuously; it does not, it fails hard, for an unrelated
reason (no spec file), until Step 4's spec exists.

`tests/auth.spec.ts` does not exist. The new spec must not use `seedAuth()` (that helper
exists specifically to bypass this flow) and must assert, against the real dev backend:

- a fresh, unauthenticated context navigating to `/` lands on `/login`, not `/`
- submitting the wrong password shows the inline error and does not navigate
- submitting the right password navigates to `/` and the authenticated shell renders
- a reload of `/` stays authenticated (no bounce to `/login`)
- logout returns to `/login`, and a subsequent direct navigation to `/` bounces back

### 4.5 Seeding, the rate limiter, and Ruling 1 (I4, Open question 1 closed)

**Ruling 1** (env-var e2e password, seeding in scope, fail-loud) is upheld; this revision
closes the two riders the review required.

**(a) The seeding mechanism is a direct DB write, stated explicitly and scoped.**
`/api/v1/setup/*` 403s once `admin_password_hash` exists (`require_uninitialized`), so
against an already-initialized dev stack there is no HTTP path to set a *known* password —
seeding must write the `config` table directly:

```sql
UPDATE config
SET value = jsonb_build_object('hash', :bcrypt_hash)
WHERE key = 'admin_password_hash';
UPDATE config
SET value = jsonb_build_object('ts', extract(epoch from now())::bigint)
WHERE key = 'admin_password_changed_at';
```

`:bcrypt_hash` is computed the same way the app does (`bcrypt.hashpw`, `backend/app/api/
auth.py:32`) from `E2E_ADMIN_PASSWORD`, via a small seed script
(`frontend/tests/helpers/seed-admin.ts` calling out to the backend interpreter, or a
`backend/scripts/e2e_seed_admin.py` — either is acceptable, Step 4 picks one and states
which in its commit body). **This explicitly and knowingly overwrites the shared dev
stack's real admin password** — the second `UPDATE` matters as much as the first: without
it, the owner's existing session token (`iat` before the overwrite) would keep working even
though the password changed underneath them, which is the actual, subtler danger version of
"clobbers the owner's password" (a silent partial corruption, not just an inconvenience).
Stamping `admin_password_changed_at` makes the clobber loud — any live session is
immediately logged out — rather than silently leaving stale trust in place. This ruling
authorizes exactly that: the seed script requires `E2E_ADMIN_PASSWORD` set (no default,
never silently generated) and only ever `UPDATE`s an existing row (never inserts — it must
not be able to run initial setup itself, which would be a second, different capability).

**(b) `gate.sh --full` goes structurally red without the credential and a live stack —
recorded, not discovered.** `scripts/gate.sh:174` runs `npm run test:e2e` (every spec, no
filter) inside `--full`. Once `auth.spec.ts` exists and is fail-loud by design, `--full` on
any machine without `E2E_ADMIN_PASSWORD` and a running dev stack goes red for an
environmental reason. Step 7's amendment log carries a Tier-2 row naming this explicitly for
the gate ledger / T1.64 handoff, so it is read as a known consequence rather than found cold
by whoever next runs `--full`.

**(c) The rate limiter is a stated design input for the spec itself.** Measured live:
`LoginRateLimiter(max_failures=5, window_seconds=300, lockout_seconds=300)`, in-memory,
keyed per IP, one bucket through the vite proxy for every request the spec issues. The spec
must:
- attempt the wrong password **at most once** per test run (the suite needs exactly one
  wrong-password assertion; repeated dev-loop re-runs within 300s share the same bucket, so
  budget conservatively — one wrong attempt per run leaves 4 of headroom before a lockout,
  enough for a couple of accidental re-runs but not a `--watch` loop),
- on a failed login, **distinguish HTTP 429 (lockout) from a normal wrong-password 401** in
  its own assertion/error message, so a lockout reads as "rate-limited, wait or restart the
  backend" rather than a false "wrong-password assertion failed",
- and the spec's own doc comment records the escape hatch: the limiter is in-memory, so
  restarting the backend process clears it immediately (no manual unlock needed, but also no
  persistence across restarts to rely on).
