## 4. The auth path, concretely

### 4.1 What "works against the real backend end to end" means here

Four flows, each already wired at the code level (§1) and each needing an assertion in the
new e2e spec:

1. **Logged-out first load.** Navigate to `/` with no auth cookie and `DEMO=0`.
   `_authenticated.tsx`'s `beforeLoad` reads `useAuthStore.getState().isAuthenticated`
   (persisted in `localStorage`, defaults `false`) and redirects to `/login` before the
   component ever renders — no flash of the authenticated shell.
2. **Login.** On `/login`, submit the real admin password. `useLogin` → `authAdapter.login`
   → `POST /api/v1/auth/login` → backend verifies against `Config[admin_password_hash]`,
   issues a JWT, calls `set_auth_cookie` (`HttpOnly`, `SameSite`, `Secure` only in
   `environment=production` per `cookie_secure`'s tri-state). `onSuccess` flips
   `useAuthStore.isAuthenticated = true` and the route navigates to `/`.
3. **Session persistence across reload.** `isAuthenticated` is `zustand/persist`-backed
   (`localStorage`), so a reload does not immediately bounce to `/login`; the guard trusts
   the cached flag until `AUTH_VERIFY_TTL_MS` (60s) elapses, then calls `checkAuth()`
   (`GET /auth/me`) to confirm the cookie is still valid server-side.
4. **Logout and 401 handling.** Logout blocklists the token's `jti` and clears the cookie;
   `apiFetch`'s `handleUnauthorized()` catches any subsequent 401 (an expired or blocklisted
   token) and forces a single redirect to `/login`, guarded against a 401 burst by
   `handling401`.

### 4.2 What the e2e spec must assert

`tests/auth.spec.ts` does not exist — `npm run test:e2e -- auth` currently matches nothing
and exits 0 having tested zero assertions, which is exactly the silent-green failure mode
the `progress.md` T1.64 row already flagged for this suite generally. The new spec must not
use `seedAuth()` (that helper exists precisely to *bypass* this flow for other specs) and
must assert, against the real dev backend:

- a fresh, unauthenticated context navigating to `/` lands on `/login`, not `/`
- submitting the wrong password shows the inline error and does not navigate
- submitting the right password navigates to `/` and the authenticated shell renders
- a reload of `/` stays authenticated (no bounce to `/login`)
- logout returns to `/login`, and a subsequent direct navigation to `/` bounces back to
  `/login` (proving the cookie was actually cleared server-side, not just the client flag)

### 4.3 The blocking precondition this task must actually fix

`progress.md`'s T1.58 amendment rows (2026-07-27, tier 2, and the paired T1.44 row) record:
**"T1.58 may not claim 'real mode is the default' while creating a memory through the UI is
broken."** Confirmed live, not inherited on faith: `use-memory-api.ts:97` still calls
`apiFetch<Memory>("/memories", …)`, typed to receive a full `Memory`, with no `wait_process`
parameter — but T1.42a (now `done`) shipped `POST /memories` as a 202 `CaptureAck` by default.
`memory-editor-dialog.tsx` imports `useDemoStore` unconditionally and has never called this
hook at all.

**This is a required step (§6, Step 3), not optional scope**, because Done-when box 1 ("real
mode is the default") is falsified on day one of the flip if the one write path anyone
notices — creating a memory from the UI — silently fails or silently does nothing.

**What is explicitly not required:** the **edit** half of the same dialog. `PUT
/memories/{id}` exists and returns a plain `MemoryResponse`, but no `useUpdateMemory` hook
exists anywhere in the tree, and — unlike create — no amendment row assigns editing to this
task. Building it is low-risk (no ack-shape ambiguity, unlike create) but is scope this task
was not asked to carry. **Recommendation, stated as a plan decision rather than assumed:**
gate only the create path for real; in real mode, disable the "Save changes" edit action with
inline copy ("editing isn't wired to the backend yet") rather than either building an unowned
feature or leaving a Save button that silently writes to a demo store nobody is looking at.
This is a Tier-2 finding for §7, not a silent scope grab.

### 5.2 Why "renders fake data presented as real" is the correct description, not "renders nothing"

The brief's framing — empty state is more honest than silent nothing — actually understates
the Chat/Code/Knowledge/Settings-tail risk: these do not go empty, they keep rendering
**fabricated content with no visual distinction from real content**, because the components
never call a real endpoint at all and the demo store is not itself gated. A user who has just
been told "you're now talking to the real backend" (the whole point of this task) sees
plausible-looking chat threads, repositories, and facts that are entirely fictional. This is
worse than an honest empty state and is exactly invariant 14's "silent-authority" failure mode
in `CLAUDE.md`, applied to demo data rather than a partial retrieval result.

**This plan's position:** T1.58 cannot fix these surfaces (their binding tasks own that,
per the brief's own scope line), but it must not silently flip the default while they exist.
Step 5 covers the mitigation available within this task's lane: an honest, cheap ceiling — a
demo-data banner injected once, in `_authenticated.tsx`'s shell (a file already touched by
this task), that reads the *unbound-surface list* and shows "this section is still showing
sample data" on the affected routes only. This is deliberately small (a route-name check
against a constant list this plan names, not a mechanism) and is offered as a recommendation
for controller ruling, not committed as mandatory — see §7 Open question 2.

## 6. The step sequence

Six steps. Steps 1–2 can land as separate, independently revertable commits (lint config;
flag flip is a no-op without them, see ordering note). Steps 3–4 must land **before** the flag
flip is live for anyone testing against it, because they fix the two concrete defects the
flip would otherwise expose immediately. Step 5 is a controller-ruled optional addition.
Step 6 is the closing verification and must run last.

**Serialisation.** 1 → 2 (lint) is independent of 3 → 4 (create path + auth spec) and could
run in a parallel sub-lane, but both must land before the actual `DEMO` default flip commits,
so the plan treats them as one serial chain to keep the executing agent from flipping the
default early. Step 5 depends on 4. Step 6 depends on everything.

### Step 3 — Fix the memory-create blocking precondition

**Size:** M. **Files:** `frontend/src/hooks/api/use-memory-api.ts`,
`frontend/src/features/memories/components/memory-editor-dialog.tsx`. **Depends:** nothing
(independent of Step 1/2). **Must land before Step 2 is live for testers**, per §4.3.

- Add a discriminated response type for `POST /memories`:
  `CaptureAck{schema_version, id, status:"accepted"}` (the default) and keep `Memory` as the
  201 shape when `wait_process=true`. `useCreateMemory` accepts an optional
  `{ waitProcess?: boolean }` and its `mutationFn` passes `?wait_process=` accordingly,
  typed as `CaptureAck | Memory`. Default call site omits `wait_process` (202, the common
  case) so the mutation resolves fast and the UI does not block on pipeline completion —
  matching what `CaptureAck`'s own docstring describes as the intended caller pattern.
- `memory-editor-dialog.tsx`: the create branch (`!memory`) calls `useCreateMemory` for real
  when `!DEMO`, `addMemory` (unchanged) when `DEMO`. Remove the unconditional `useDemoStore`
  import from the top of the file; import it only inside the demo branch's closure, or keep
  the import (component-scoped, not module-scoped conditional) but ensure the real branch
  never touches it — either is acceptable, state which was chosen in the commit body.
- The footer copy `"submit → 202 Accepted (mock)"` becomes conditional: real mode shows
  `"submit → 202 Accepted"` (no "(mock)"), demo mode keeps the current text.
  A footer that still says "(mock)" against a real backend is a small but real instance of
  the same silent-authority problem §5.2 names at surface scale.
- Edit branch (`memory` set): in real mode, the "Save changes" button is disabled with
  `title="Editing isn't wired to the backend yet"` rather than calling `updateMemory` against
  a demo store nobody renders. Demo mode is unchanged.

**Test.** A new `memory-editor-dialog.test.tsx` case (extending the existing test file, which
currently only exercises demo mode): with `DEMO=false` (module-mocked, mirroring

idiom), submitting the create form calls the real mutation (mock `apiFetch`, assert the
request body and that no demo-store action fired) and the edit form's save button is

**Verify.** `npm test -- memory-editor-dialog`.

## 7. What this plan could not settle

### Open question 1 — where does the e2e auth spec get a real admin password?

`darkmem`'s setup is trust-on-first-use: the admin password is set once via
`/api/v1/setup/*` and stored as a bcrypt hash in `Config`. Every existing e2e spec either
avoids the real auth path (`seedAuth()`) or soft-skips when the backend isn't in its expected
state (`setup-wizard-refresh.spec.ts`). Nothing in the repo documents how an e2e run is
supposed to obtain a **known** password for a **login** test — as opposed to a **setup**
test, which gets to choose the password itself. Two options, neither committed by anything
existing:

1. **An env var the harness sets** (`E2E_ADMIN_PASSWORD`), read by both the spec and whatever
   seeds the dev stack's admin account before the run. Requires a seeding step this plan does
   not own (a fixture script, or a documented manual precondition).
2. **The spec runs setup itself first** (drive `/setup` with a password it controls, then
   immediately test login with that same password) — self-contained, no external secret, but
   duplicates `setup-wizard-refresh.spec.ts`'s territory and only works against a genuinely
   uninitialized backend, which the dev stack will not be after the first run.

Step 4 assumes option 1 and flags it explicitly; a controller ruling should pick one before
that step executes.

### Open question 2 — does the unbound-surface banner (Step 5) belong to this task at all?

The brief's item 4 wants an honest accounting of what breaks, and §5.2 argues the Chat/Code/
Knowledge/Settings-tail failure mode is worse than an empty state. But building a shared
mitigation inside `_authenticated.tsx` is exactly the kind of small mechanism that is easy to
underscope (which routes, which nested tabs, does it need to know about `/settings`'s
in-page tab state) and easy for a later binding task to trip over (T1.59 landing Code binding
would need to remember to remove Code from the list). The alternative — leave each surface's
honest-empty-state to its own binding task, which already has a Done-when about it — is
simpler and matches "each binding task removes its **own** surface's demo imports" from the
brief's framing. **Recommend striking Step 5** unless the controller specifically wants the
interim mitigation; this plan does not treat it as required for Done-when.

## 8. Falsification pass

The step most likely to be wrong: **Step 3's claim that gating only the create half of
`memory-editor-dialog.tsx` (and disabling edit) satisfies the recorded blocking
precondition.** The amendment log's exact words are "creating a memory through the UI is
broken" — narrowly about create — but the dialog is one component serving both flows, and a
reviewer could reasonably read "real mode is the default" (Done-when box 1) as requiring the
whole dialog to be real, not half-real-half-disabled. If that reading wins, Step 3 grows a
`useUpdateMemory` hook and a real edit path, which is not large (the `PUT` endpoint is a
plain synchronous `MemoryResponse`, no ack-shape ambiguity) but was deliberately kept out of
this plan's Step 3 estimate.

**Evidence that would show this is wrong:** if, during execution, the amendment log or a
controller ruling explicitly extends the precondition to editing, or if a downstream task
(T1.44's own scope, re-read) turns out to already claim the edit half implicitly. Neither was
found during this plan's research — `progress.md`'s T1.44 row describes search and the
why-retrieved trace only, never the editor dialog — so the narrow reading is what this plan
commits to, but it is the single most contestable call in the whole plan and is named here
rather than left for a reviewer to discover independently.

Second-most-likely candidate, briefly: **the "no owning task" claim for Knowledge (§2.1)**
rests on a grep across three task files; if a fourth planning doc (a spec under
`docs/superpowers/specs/`, or doc 13 itself elsewhere) assigns it and this plan's search
missed the phrasing, the Tier-2 finding is a false alarm. The grep covered the literal
component/file names, which is a narrower net than a semantic search would be.

## 9. Size call

**L stands, and is if anything tight.** Six steps, two of which (3 and 4) are genuinely
non-mechanical: Step 3 touches a wire-shape mismatch across a backend contract this plan had
to read code to characterise correctly, and Step 4 authors a new e2e spec against an
underspecified precondition (§7, Open question 1) that this plan could not fully close.
Step 1 looks small but required actually running eslint to discover the rule's true state —
skipping that measurement (i.e., trusting the task text's "add a warn-mode rule") would have
produced a plan that added a second, conflicting rule block. **No split is recommended**: the
six steps share one purpose (make the default flip safe to throw) and splitting further would
scatter a single reviewable unit across multiple task ids for no isolation benefit — none of
the steps are independently valuable without the others landing in the same wave (a flipped
default with a broken create path is worse than not flipping it; a fixed create path behind
the old default fixes nothing anyone will notice).
