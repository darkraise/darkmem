## 4. The auth path, concretely

### 4.1 What "works against the real backend end to end" means here

Unchanged from v1 — four flows, each already wired at the code level (§1):

1. **Logged-out first load.** `/` with no auth cookie and `DEMO=0` redirects to `/login`
   before the component renders (`_authenticated.tsx`'s `beforeLoad`).
2. **Login.** Real admin password → `useLogin` → `authAdapter.login` →
   `POST /api/v1/auth/login` → cookie-JWT issued, `isAuthenticated` flips, navigates to `/`.
3. **Session persistence across reload.** `zustand/persist`-backed, TTL-cached
   `checkAuth()` re-verify (60s).
4. **Logout and 401 handling.** Blocklists the token's `jti`, clears the cookie;
   `apiFetch`'s `handleUnauthorized()` forces a redirect on any subsequent 401.

### 4.2 What the e2e spec must assert — and the corrected exit-code claim (I1)

**v1 claimed `npm run test:e2e -- auth` "matches nothing and exits 0 … exactly the
silent-green failure mode." Measured this revision: `npx playwright test auth --list`
prints `Error: No tests found.` and exits 1.** The second half of the task's own Verify is
loud-red today, not silent-green — the opposite of what v1 stated as fact without running
it. This matters because it inverts the risk story: a controller reading v1 would believe
the Verify already half-passes vacuously; it does not, it fails hard, for an unrelated
reason (no spec file), until Step 4's spec exists.

`tests/auth.spec.ts` does not exist. The new spec must not use `seedAuth()` (that helper
exists specifically to bypass this flow) and must assert, against the real dev backend:

- a fresh, unauthenticated context navigating to `/` lands on `/login`, not `/`
- submitting the wrong password shows the inline error and does not navigate
- submitting the right password navigates to `/` and the authenticated shell renders
- a reload of `/` stays authenticated (no bounce to `/login`)
- logout returns to `/login`, and a subsequent direct navigation to `/` bounces back

### 4.3 The blocking precondition this task must actually fix (B2, rebuilt around the real surface)

`progress.md`'s T1.58 amendment rows record: "T1.58 may not claim 'real mode is the
default' while creating a memory through the UI is broken." **v1's Step 3 did not fix
this.** It typed `useCreateMemory` correctly but wired the create branch into
`MemoryEditorDialog`, which:

- renders only inside `DemoMemoriesPage` (demo-only — `routes/_authenticated/memories.tsx`
  branches `DEMO ? <DemoMemoriesPage /> : <RealMemoriesView />`, and `RealMemoriesView` has
  **no create action of any kind** — confirmed by reading the file), and
- is otherwise reached only via the ungated `/memories/$memoryId` detail route, which (§0,
  §5) is itself broken for real ids.

So after v1's Step 3: the hook's type would be fixed, a dialog no real-mode user can reach
would gain a dead `!DEMO` branch, and creating a memory through the real UI would still be
impossible. **Done-when box 1 stays false.** This revision replaces Step 3 with Step 2,
rebuilt around the components real mode actually renders:

- **Create.** `CreateMemoryDialog` (`features/memories/components/create-memory-dialog.tsx`)
  already exists, is complete, and already calls `useCreateMemory` for real — it is dead
  code only because nothing renders it. `RealMemoriesView` gets a "Create memory" button
  (mirroring `DemoMemoriesPage`'s existing one) that opens it. This is wiring an existing,
  working component into its real-mode host, not building a new one.
- **The ack-shape type**, as v1 planned: a discriminated `CaptureAck | Memory` return type
  on `useCreateMemory`, with an optional `{ waitProcess?: boolean }` param passed through as
  `?wait_process=`.
- **M1 (202-buffered create UX), closed by a decision v1 left open:** the general
  `useCreateMemory` hook still defaults `wait_process` to unset/false (matches
  `CaptureAck`'s own docstring intent — non-blocking is the common caller pattern). But

### 4.5 Seeding, the rate limiter, and Ruling 1 (I4, Open question 1 closed)

**Ruling 1** (env-var e2e password, seeding in scope, fail-loud) is upheld; this revision
closes the two riders the review required.

**(a) The seeding mechanism is a direct DB write, stated explicitly and scoped — corrected
this round after a re-review caught the `changed_at` write silently no-op'ing on the most
common stack state.** `/api/v1/setup/*` 403s once `admin_password_hash` exists
(`require_uninitialized`), so against an already-initialized dev stack there is no HTTP
path to set a *known* password — seeding must write the `config` table directly:

```sql
-- Hash: UPDATE-only, on purpose (§ below) — but the script must check the affected
-- row count and fail loudly if it is 0, never silently no-op.
UPDATE config
SET value = jsonb_build_object('hash', :bcrypt_hash)
WHERE key = 'admin_password_hash';
-- rowcount check happens in the script, not in SQL — see prose below.

-- changed_at: a true upsert, mirroring app/api/routes/auth.py's own change-password
-- logic (SELECT, then UPDATE if present else INSERT — this is the ON CONFLICT
-- equivalent). admin_password_changed_at is written ONLY by that route, never by
-- setup, so on a stack that was initialized but never had its password changed
-- through the UI this row does not exist yet, and an UPDATE-only statement here
-- would match zero rows and silently do nothing.
INSERT INTO config (key, value)
VALUES ('admin_password_changed_at', jsonb_build_object('ts', extract(epoch from now())::bigint))
ON CONFLICT (key) DO UPDATE SET value = EXCLUDED.value;
```

`:bcrypt_hash` is computed the same way the app does (`bcrypt.hashpw`, `backend/app/api/
auth.py:32`) from `E2E_ADMIN_PASSWORD`, via a small seed script
(`frontend/tests/helpers/seed-admin.ts` calling out to the backend interpreter, or a
`backend/scripts/e2e_seed_admin.py` — either is acceptable, Step 4 picks one and states
which in its commit body). The script itself, not the SQL alone, is what makes both halves
correct:

- **The hash `UPDATE`'s guard is the affected-row count, checked by the script, not the
  statement's absence of an `INSERT`.** `UPDATE ... WHERE key = 'admin_password_hash'`
  matching zero rows means the stack was never initialized (`admin_password_hash` doesn't
  exist yet) — the script must detect that (the driver reports rows-affected; asyncpg's
  `execute()` return value or a `RETURNING key` clause both work) and **exit non-zero with
  a clear message** ("stack not initialized — run setup first, this script only seeds an
  existing admin account") rather than silently doing nothing. The never-insert guard is
  correct and stays — the script must not be able to run initial setup itself, which is a
  different capability with different consequences — but "never insert" and "never silently
  no-op" are two different guarantees, and the original design only had the first.
- **The `changed_at` write is a true upsert** (`INSERT ... ON CONFLICT DO UPDATE`, or the
  script's own SELECT-then-branch mirroring the app's pattern at
  `routes/auth.py:154-160` exactly) precisely because it is legitimately missing on a
  never-changed stack, and that is the common case for a stack that was only ever
  initialized through setup. **This explicitly and knowingly overwrites the shared dev
  stack's real admin password** — the `changed_at` write matters as much as the hash write:
  without it (or with it silently no-op'ing, which is what the pre-this-round design did
  whenever the row didn't exist), the owner's existing session token (`iat` before the
  overwrite) would keep working even though the password changed underneath them — the
  actual, subtler danger version of "clobbers the owner's password" (a silent partial
  corruption, not just an inconvenience), and precisely the failure mode this co-write
  exists to close. An UPDATE-only second statement closes it only when the row already
  exists; the upsert closes it unconditionally. This ruling authorizes exactly that: the
  seed script requires `E2E_ADMIN_PASSWORD` set (no default, never silently generated),
  never inserts the hash row, and always writes the `changed_at` row one way or another.

**(b) `gate.sh --full` goes structurally red without the credential and a live stack —
recorded, not discovered.** `scripts/gate.sh:174` runs `npm run test:e2e` (every spec, no
filter) inside `--full`. Once `auth.spec.ts` exists and is fail-loud by design, `--full` on
any machine without `E2E_ADMIN_PASSWORD` and a running dev stack goes red for an
environmental reason. Step 7's amendment log carries a Tier-2 row naming this explicitly for
the gate ledger / T1.64 handoff, so it is read as a known consequence rather than found cold
by whoever next runs `--full`.

**(c) The rate limiter is a stated design input for the spec itself.** Measured live:
`LoginRateLimiter(max_failures=5, window_seconds=300, lockout_seconds=300)`, in-memory,
keyed per IP, one bucket through the vite proxy for every request the spec issues. The spec
must:
- attempt the wrong password **at most once** per test run (the suite needs exactly one
  wrong-password assertion; repeated dev-loop re-runs within 300s share the same bucket, so
  budget conservatively — one wrong attempt per run leaves 4 of headroom before a lockout,
  enough for a couple of accidental re-runs but not a `--watch` loop),
- on a failed login, **distinguish HTTP 429 (lockout) from a normal wrong-password 401** in
  its own assertion/error message, so a lockout reads as "rate-limited, wait or restart the
  backend" rather than a false "wrong-password assertion failed",
- and the spec's own doc comment records the escape hatch: the limiter is in-memory, so
  restarting the backend process clears it immediately (no manual unlock needed, but also no
  persistence across restarts to rely on).
