### 1.1 The isolation gap, and the ruling that closes it

The baseline made cross-project **`memory_relations`** edges unrepresentable with *composite*
FKs, and says so in its own comment (`0001_baseline.py:354–356`):

> The endpoint FKs are COMPOSITE on `(memory_id, project)`, which is what makes a
> cross-project edge unrepresentable rather than merely forbidden.

`memory_community_members` did not get that treatment: no `project` column, and a plain
`memory_id UUID REFERENCES memories(id)`. No CHECK constraint can express the predicate (it
needs a subquery), and a trigger is DDL.

**Controller ruling (2026-08-02): the schema change is in scope for T2.18's execution
round, which runs after T2.42 merges and takes baseline ownership for its round.** So the
plan no longer routes around the gap — it closes it (Steps 6–7).

**One composite FK is not enough.** The reviewer is right and the original amendment
request was wrong. With `project` on the members table and only
`(memory_id, project) REFERENCES memories(id, project)`, this row is still representable:

| `community_id` | `memory_id` | `project` | Why it survives |
|---|---|---|---|
| `C_A` (a project-**A** community) | `M_B` | `B` | memory-side composite FK holds — `(M_B, B)` is a real `memories` row; the plain `community_id` FK holds — `C_A` exists. Membership is cross-project anyway. |

Unrepresentability needs **both** composite FKs:

```sql
project      TEXT NOT NULL,
FOREIGN KEY (memory_id,    project) REFERENCES memories(id, project)          ON DELETE CASCADE,
FOREIGN KEY (community_id, project) REFERENCES memory_communities(id, project) ON DELETE CASCADE
```

which requires `memory_communities` to carry `UNIQUE (id, project)` — trivially satisfiable,
exactly as `memories_id_project_key` is, and `0001_baseline.py:166–173` documents that very
pattern. With both live, `members.project` must equal the memory's project *and* the
community's project, so those two are equal by transitivity. That is unrepresentability in
the DDL, not in the write path.

**The ruling carries a cost, and it is not small (§4.3, §9 Step 7).** With both FKs live, a
`PUT /memories/{id}` that changes `project` on any memory holding a membership row raises
an FK violation — and after the first nightly run that is most active memories. A live
endpoint starts erroring unless the execution deletes the memory's membership rows first.

## 3. The projection — nodes, edges, weights

### 3.1 Nodes

`memory_community_members` keys on `memory_id`, so **nodes are memories** and edges must be
memory-to-memory. Nothing else is representable.

### 3.2 Eligibility, cited

```
status = 'active' AND is_archived = false AND (expires_at IS NULL OR expires_at > now())
```

Doc 06 §7's lifecycle diagram states two thirds of it directly: `Grow --> Decay: member
memories superseded / expired out`. Three consequences:

- **`superseded` and `deprecated` are both excluded** by the single `status = 'active'`
  predicate — `deprecated` is downstream of `superseded` in the lifecycle (`CLAUDE.md`,
  Domain model), so "superseded out" covers it.
- **Expiry is by timestamp, not by sweep.** `expired_memory_cleanup` is periodic, so an
  expired-but-unswept row is `status='active'` with a past `expires_at`. Testing status
  alone would let it into a topic, which "expired out" forbids. This clause is the
  load-bearing half of the predicate; T4 pins it.
- **`is_archived = false` (added in round 1's amendment, F6).** Doc 06 §7 is silent on
  archiving, so the decision is argued rather than cited. Archiving is a user gesture
  meaning "get this out of my way", and topics are an *organizing and browsing* surface
  (doc 09 §3, doc 13) rather than a retrieval arm — surfacing archived memories as topic
  members through T2.20 would directly contradict the gesture. The schema agrees: the
  baseline already treats `status = 'active' AND is_archived = false` as the canonical live
  set, building `ix_memories_project_live` on exactly that predicate and calling it "live
  rows in this project" (`0001_baseline.py:194–197`). Matching it means the projection's
  node scan is servable by an index that already exists for this shape. T4 gains an
  archived case.

`status` is the `memory_status` enum; the predicate uses the literal, so no bound param and
no `CAST(:status AS memory_status)` is required.

### 3.3 Edges — the four candidates, and why one wins

| Candidate | Verdict |
|---|---|
| **(A) Shared entities** via `entities.memory_ids` | **Chosen.** Extraction always runs (`CLAUDE.md`, Pipeline terminology), so every ingested memory contributes; `ix_entities_memory_ids` carries the fan-out; the semantics ("two memories talk about the same things") is exactly what a topic is. |
| **(B) Shared `memories.technologies`** | Rejected as *redundant*, not wrong. `technologies` is by construction the subset of a memory's entities whose type ∈ `TECH_TYPES` (`relations.py:43`), so (B) ⊂ (A) — it adds no edge (A) lacks and drops every non-tech topic (people, papers, concepts, events). |
| **(C) `memory_relations` rows** | Rejected *for v1 on evidence*: the table has zero writers (§1). Its writer is `memory_dream`, T2.12, still a placeholder. A projection rooted here is the empty graph. Doc 06 §7's diagram label `relations` means **entity** relations, not this table. §3.6 keeps the seam. |
| **(D) `memory_crossrefs`** | Rejected on three grounds, the third disqualifying. (i) Not project-scoped: `find_similar_memories` filters by fingerprint, not project. (ii) It is a top-5 kNN — an arbitrary density knob, not a semantic statement. (iii) **The table carries no fingerprint column**, so rows written under different embedders coexist with incomparable cosine scales; building weights from it is the closest thing to a cross-fingerprint comparison the schema permits, and invariant 2 forbids exactly that reasoning. |
| **(E) Two-hop entity-relation paths** | Rejected for v1. It multiplies both density and the cross-project reach surface (`entity_relations` is global too), and on a hub-heavy graph makes modularity a function of the relation extractor's recall rather than of topical structure. Revisit only with a metric (§10 O-3). |

### 3.4 Weights — the decision that dominates the output

An unweighted projection makes two memories sharing one incidental `concept` as connected
as two sharing eight specific tools. Worse, in darkmem's own corpus a hub entity
(`postgres`, `darkmem`, `python`) is asserted by hundreds of memories, and a single hub
injects a **clique** of `n(n−1)/2` unit-weight edges. Leiden's modularity is weight- and
degree-sensitive; one such clique collapses a project into a single blob — reaching the
degenerate output the fallback exists to signal, while reporting success.

**Weight:**

```
w(u,v) = Σ_{e ∈ shared(u,v),  2 ≤ n_e ≤ hub_cap}  1 / (n_e − 1)
```

where `n_e` is the number of *eligible, in-project* memories asserting `e`.

Two mechanisms, each with its own job:

1. **`1/(n_e − 1)` — Newman's collaboration-projection normaliser.** Each entity
   contributes a total of exactly `n_e/2` weight spread over its clique instead of
   `n_e(n_e−1)/2`. A rare entity shared by two memories contributes `1.0` to that one pair;
   a 100-asserter hub contributes `~0.01` to each of its 4 950 pairs. Specificity buys
   connection; ubiquity does not. A *ranking* fix.
2. **`hub_cap` — a hard drop above a size.** Normalisation fixes the score but not the
   cost: a 500-asserter entity still materialises 124 750 rows before any weight is
   applied. A *materialisation* bound, not interchangeable with (1).

`n_e` is counted **after** restricting to the project's eligible node set. An entity that is
a hub across the whole install but is asserted by three memories inside this project is
*specific to this project* and should weigh like a rare entity here.

Entity **types are not filtered** in v1 — including the `concept`/`entity` fallback sink.
Filtering them is plausible but there is no metric to justify it (§10 O-3), and dropping the
sink would silently delete every topic in a non-technical project. The excluded-type set is
a config knob defaulting to empty so a future tuning run can move it without a code change.

### 3.5 The projection query

One statement, bounded, deterministically ordered. **The reviewer executed this against a
seeded fixture and confirmed its output**: `w(m1,m2) = 1.5`, foreign-project endpoints
absent, expired-but-unswept absent, and `HAVING count(*) >= 2` correctly dropping a global
entity with only one in-project asserter.

```sql
WITH eligible AS MATERIALIZED (
    SELECT id
    FROM memories
    WHERE project = CAST(:project AS text)
      AND status = 'active'
      AND is_archived = false
      AND (expires_at IS NULL OR expires_at > now())
),
asserted AS MATERIALIZED (
    SELECT e.id AS entity_id, el.id AS memory_id
    FROM entities e
    JOIN LATERAL unnest(e.memory_ids) AS u(mid) ON TRUE
    JOIN eligible el ON el.id = u.mid
    WHERE e.entity_type <> ALL (CAST(:excluded_types AS text[]))
),
sized AS (
    SELECT entity_id, count(*) AS n
    FROM asserted
    GROUP BY entity_id
    HAVING count(*) >= 2 AND count(*) <= CAST(:hub_cap AS int)
)
SELECT a.memory_id AS u, b.memory_id AS v, sum(1.0 / (s.n - 1)) AS w
FROM asserted a
JOIN asserted b ON b.entity_id = a.entity_id AND a.memory_id < b.memory_id
JOIN sized s ON s.entity_id = a.entity_id
GROUP BY a.memory_id, b.memory_id
ORDER BY a.memory_id, b.memory_id
```

Four properties this query must keep:

- **`AS MATERIALIZED` on `eligible`.** Same lesson the buffer-claim CTE records in
  `CLAUDE.md`: a plain sub-select lets the planner re-execute it per outer row. The cost
  here is quadratic re-evaluation against `memories` rather than an over-wide claim, but the
  fix and the reason not to "simplify" it are identical.
- **`a.memory_id < b.memory_id`.** Undirected dedup in the join — no `DISTINCT` pass, no
  self-loop.
- **`ORDER BY` — kept, but the rationale is corrected (round 1, minor).** Round 1 justified
  it by claiming unordered input makes two runs of the same binary disagree. §1.2 measured
  that and it is **false for leidenalg 0.12.0**: `seed=0` gave one partition across ten
  shuffled edge orderings. The ordering stays for three honest reasons — reproducible
  debugging (a diffable projection dump), stable label tie-breaking (§6.4 ranks on ordered
  input), and cross-version hygiene, since the determinism measured here is a property of
  one library version and not a documented guarantee. **T7 no longer relies on it** (§12).
- **Every bound param is CAST.** `:project` → `text`, `:hub_cap` → `int`,
  `:excluded_types` → `text[]`. asyncpg cannot infer these, least of all the array in a
  `<> ALL` (invariant 10).

### 3.6 The composition seam

`build_projection()` returns a `Projection` dataclass and is written so a second edge arm
(T2.12's `memory_relations`, or (E)) is a *union with weight addition* over the same node
set, not a redefinition. Adding an arm means adding a `SELECT u, v, w` producer and one
merge; it touches neither the detector, the repository, nor the transaction shape.

## 4. Isolation — what holds, where, and against which door

### 4.1 The four write-path mechanisms

**M1 — The node set is closed under project.** `eligible` filters on `project`, and every
downstream identifier is an *index into* the ordered node list, never a raw UUID. Leiden
returns a membership vector over `[0, |N|)`; a memory outside the project has no index, so
the partition cannot name it. This closes the naive-join trap: `entities.memory_ids` reaches
other projects, but `JOIN eligible` happens *before* the self-join, so a foreign memory is
never an `asserted` row and therefore never an edge endpoint.

**M2 — The member write derives its rows from a join on project equality.** Not
`INSERT … VALUES (:cid, :mid)`, but:

```sql
INSERT INTO memory_community_members (community_id, memory_id)   -- + project, after Step 6
SELECT c.id, m.id
FROM memory_communities c
JOIN jsonb_to_recordset(CAST(:rows AS jsonb)) AS d(memory_id uuid) ON TRUE
JOIN memories m ON m.id = d.memory_id AND m.project = c.project
WHERE c.id = CAST(:community_id AS uuid)
```

The row's *existence*, not merely its acceptance, depends on `m.project = c.project`.

**M3 — A silent drop becomes a loud abort.** M2 alone would *drop* a foreign row rather than
reject it, which is what inv. 14 forbids. The repository compares the statement's `rowcount`
against the candidate count and raises on any shortfall, aborting the project's write
transaction (§5) so the previous run survives.

*Corrected in round 1 (minor).* A shortfall has **two** causes, and conflating them
mislabels a benign event as a violation. Phase R's snapshot is read before Phase W's
transaction opens, so a memory can be deleted or moved out of the project in between — a
read-to-write race. Aborting is right in both cases (the rewrite would be built on stale
input), but the journal must distinguish them: on a shortfall the repository re-queries the
missing candidate ids and journals `stale_snapshot` when they are absent or now in another
project, `cross_project_violation` only when a foreign row genuinely reached the candidate
list. Only the second is a defect.

**M4 — A post-write assertion inside the same transaction**, over the whole project's
membership rather than one insert:

```sql
SELECT count(*) FROM memory_community_members mm
JOIN memory_communities c ON c.id = mm.community_id
JOIN memories m ON m.id = mm.memory_id
WHERE c.project = CAST(:project AS text) AND m.project <> c.project
```

Non-zero raises and rolls back the project rewrite.

**M4 is deliberately temporary.** Once Step 6's composite FKs are live, no row M4 looks for
can exist, so M4 becomes an assertion with no reachable failure — untestable dead code, and
runbook §4 has no way to prove a guard that cannot fire. It is therefore **removed in
Step 6**, in the same commit that lands the constraint replacing it, and its test (T1) is
replaced by T17's direct proof that the database rejects the row. Through Steps 3–5 it is
the only DB-level backstop and carries its own killing mutation (§12 T1).

### 4.2 What M1–M4 do and do not prove

They make a cross-project member **unproducible by the detection path**. Until Step 6 they
do not make it unrepresentable **by the table**. Step 6 closes that; §1.1 states the exact
constraint pair, and T14/T17 assert both the shape and the behaviour.

### 4.3 The door M1–M4 never see (F2)

Every mechanism above is detection-path-only. **`PUT /memories/{id}` can change a memory's
`project` after detection has committed its membership rows** —
`MemoryUpdate.project` (`schemas/memory.py:92`) flows through `routes/memories.py:182` and
`services/memory.py:255` into `relational.py`'s generic `setattr`. So:

1. Detection commits: community `C_A` in project A, member row for memory `M`.
2. A caller `PUT`s `{"project": "B"}` on `M`.
3. `M` is now in project B while still a member of a project-A community.

**This is producible today by a supported API call with no SQL access at all.** Round 1's
"a hand-written `INSERT`" framing materially understated it, and the violation persists
until the next nightly rewrite. Two corrections to the finding as relayed, both verified:

- **The door is REST only.** MCP `memory_update` does not expose `project` —
  `api/mcp/server.py:265–271` builds its field dict from `content`/`tags`/`memory_type`
  alone, and `services/memory.py:270` says so in a comment. `server.py:273` is the shared
  call into `MemoryService`, not an MCP project field.
- **The choke point already exists.** `MemoryService.update_memory` is where both doors
  land and it *already* branches on a project change (`services/memory.py:279–281`,
  registering the new project). Step 7 is an addition to an existing, correctly-placed
  branch rather than a new interception point.

**One ordering detail decides whether Step 7 works.** That existing branch runs *after*
`memory_repo.update`, which calls `session.flush()`. With Step 6's composite FK live, **the
flush itself raises** — control never reaches the existing branch. The membership delete
must therefore run **before** `memory_repo.update`, not inside the branch that looks like
its natural home.

Step 7's behaviour: on a project change (compared against the memory's current project, so
a no-op write does not evict a memory from its topic), delete that memory's
`memory_community_members` rows before the update flushes. Deleting is the correct
semantic, not a workaround — doc 06 §7's lifecycle already has memories decaying out of
communities, and a memory that leaves project A has genuinely left A's topic space. It is
the same shape as `CLAUDE.md`'s demote-before-delete rule: clear the dependent rows first,
or the constraint aborts the operation.

`memory_relations` carries the identical latent exposure (composite FKs, no `ON UPDATE`
action, so a project change on a memory with relations raises) and has never surfaced it
only because the table has zero rows. Worth recording; not T2.18's to fix.

## 5. Atomicity, and why this ordering cannot reproduce T1.21

### 5.1 The T1.21 lesson in this task's terms

T1.21's defect was ordering: the graph strip ran *outside* the savepoint that wrote the
replacement, so a write failure left the memory with **no** graph on either path — worse
than either the old or the new state. `CLAUDE.md` records the fix as "the strip and the
write are one atomic replace".

The analogous defect here is exact and easy to write: `DELETE FROM memory_communities WHERE
project = :p`, then run Leiden, then Leiden times out or raises → the project has **zero**
topics, having had a good set a moment earlier. The existing `CommunityDetector` avoids it
only incidentally (it deletes after the partition attempt, and its timeout branch still
writes); it is not a stated property there and would not survive a refactor.

### 5.2 The three phases

**Phase R — read (own session, read-only, then released).** Build the projection for
project `P`. No locks held past this point.

**Phase C — compute (no database connection at all).** `igraph.Graph` construction and
`leidenalg.find_partition(..., seed=0)` in an executor under `asyncio.wait_for`. On
`TimeoutError` → the single-community fallback. On the import guard failing or any other
exception → **abort this project, write nothing, journal the failure, continue.**

**Phase W — write (one transaction, one project).**

```
BEGIN
  DELETE FROM memory_communities WHERE project = :p        -- members cascade
  INSERT communities (id = new_id(), project, label, properties)
  INSERT members  (M2's join-derived statement, M3's rowcount check)
  M4's cross-project assertion                             -- removed at Step 6
  record_event(consolidated / topic)                       -- own SAVEPOINT, never raises
COMMIT
```

**Why this cannot reproduce T1.21:** the `DELETE` is unreachable without a completed
partition already in hand. Every fallible step — the library import, the graph build, Leiden
itself, the timeout — lives in Phase C, which holds no transaction and touches no row. The
strip and the rewrite are the same transaction, so any failure inside Phase W rolls both
back and the *previous* run's communities survive intact, ids and all. The only outcomes are
"the new complete set" and "the old complete set". T5 and T9 assert both directions.

### 5.3 One transaction per project, not one per run

- A whole-run transaction would hold write locks on every project's community rows for up to
  `max_run_seconds` (900 s on the placeholder registration). A `SELECT` reader is unaffected
  under MVCC; any other writer of these tables is not, and the lock footprint grows with
  install size for no benefit.
- One project's bad graph would abort every other project's good result.
- Doc 06 §7 says "delete-and-rewrite **per project**", and the churn contract is per-project
  by construction.

**What a partial run leaves:** projects already committed carry their new communities;
projects not yet reached carry their previous run's. Every project is internally consistent;
none is torn. Stale is not corrupt — the next run rewrites it, and the journal records which
projects a run reached, so a partial run is visible rather than inferred.

### 5.4 What a concurrent reader sees

Under READ COMMITTED, `DELETE`+`INSERT` in one transaction means a reader sees either the
complete old set or the complete new set — never a mix, never a community with no members.

**One non-obvious caveat.** A reader issuing *two* statements — "list communities", then
"list members" — can straddle the commit and join an old community id against new member
rows, yielding an empty result that looks like an empty topic. Not a defect of the rewrite;
a defect of reading it in two round trips. The repository therefore exposes
`list_with_members(project)` as a **single joined query**, and that is the documented read
contract handed to T2.19/T2.20/T2.21/T2.39.

## 6. Fallbacks, bounds, and the label

### 6.1 The three fallbacks

| Trigger | Behaviour | `properties.fallback` |
|---|---|---|
| `igraph`/`leidenalg` import fails | **Write nothing. Delete nothing.** Log a warning, journal a skip, return a no-op outcome. | — (no rows written) |
| Connected node count `< 3` ("tiny graph", matching the code precedent's threshold) | One community over the connected nodes, if there are ≥ 2; otherwise none. | `tiny_graph` |
| Leiden exceeds `leiden_timeout_seconds` | One community over the connected nodes. | `timeout` |

*Framing softened in round 1.* Doc 06 §7's diagram routes timeout and tiny-graph to the
fallback and is simply **silent** on import failure; round 1 called the import row
"deliberately different from the diagram", which overstates a gap-fill as a departure. It is
neither a conflict nor a Tier-3 item — and the code precedent this task was told to
generalise already does exactly this (`community_detector.py:24–29`: warn and return 0). The
reasoning stands on its own: a missing library means **no information was computed**, so
collapsing a project into one topic would fabricate a result, and deleting the previous
run's good topics to write it would be T1.21 from another direction. A one-line doc 06 §7
clarification can ride the amendment log.

"Connected nodes" rather than "all eligible nodes" is also deliberate: a memory sharing no
entity with anything is not topically related to anything, and sweeping it into an
everything-community asserts a relationship the projection says does not exist.

### 6.2 Membership is not a partition — stated, not implied

Two classes of eligible memory get no membership row: isolated nodes (no qualifying shared
entity), and members of Leiden communities below `min_community_size` (2, matching the code
precedent's `if len(members) < 2: continue`). A community of one is not a topic. T8 pins
this so it cannot drift into a catch-all.

### 6.3 Bounds

- `hub_cap` (default 200) — §3.4; the materialisation bound.
- `max_projection_edges` (default 2 000 000) — counted with a cheap aggregate *before*
  materialising the edge list. Over the cap: **skip the project with a loud journal entry**,
  leaving the previous run intact. Silently truncating to the top-N edges would change the
  clustering semantics with no error and no symptom — the failure shape `index_debt` exists
  to prevent on the code side.
- Large-graph tightening, mirroring the code precedent's `is_large` branch: above
  `large_graph_nodes` (10 000), `resolution` rises to 2.0 and `n_iterations` drops to 3.
- `leiden_timeout_seconds` (default 60, matching the precedent).

**A limitation written down rather than papered over.** `asyncio.wait_for` around
`loop.run_in_executor` **does not cancel the running thread** — `leidenalg` keeps burning CPU
to completion after the await returns. The timeout bounds the *await*, not the work. The real
bound on runaway CPU is `hub_cap` + `max_projection_edges` limiting graph size before Leiden
starts. Mitigation: a dedicated single-thread executor per run, shut down with
`cancel_futures=True`, so a leaked computation cannot starve the default executor asyncio
also uses for other blocking calls. The existing `CommunityDetector` has the same property;
this plan names it (§10 O-4) rather than fixing it.

### 6.4 The label — deterministic, no model call

Rank each community's asserted entities by (count of asserting members DESC, global `n_e`
ASC — more specific wins a tie, then `name` ASC). Take the top 3; join their display forms.

- Ranking, dedup and tie-breaking use the lowercase `entities.name`; **rendering** uses
  `properties.display_name` when present, falling back to `name` (invariant 7).
- **Collisions matter although nothing enforces uniqueness.** With no
  `UNIQUE (project, label)`, a collision does not silently merge rows the way the code
  detector's composed key could (`community_detector.py:174–177`). It does something
  subtler: it makes the journal's reference-by-label (§6.5) and doc 09's pin-suggestion diff
  ambiguous. Resolution is deterministic — append the next-ranked entity, and only if still
  colliding append a stable ordinal derived from the sorted member-id list.
- `properties` carries provenance: `{"dominant_entities": [{"name","display_name","type","members","n_e"}], "size", "fallback", "resolution", "edge_count", "hub_cap"}`.

Why the label is T2.18's and not T2.19's — **upheld on review**: doc 06 §7's flowchart puts
`label = dominant entities` inside the `Insert` box (line 351) and `report_string` in a
separate downstream `Report` box, and line 380 requires each detection run to journal
referencing communities **by label**, which is impossible unless detection labels. Doc 06
§10's pin-suggestion contract is likewise "keyed on stable dominant-entity labels, not
churning ids". Proceed with the T2.19 wording amendment and its log row (§10 O-2).

### 6.5 Journalling

One `events` row per project per run:

- `event_type='consolidated'`, `object_type='topic'` — **both already in the closed
  vocabularies** (§1), so nothing needs widening.
- `object_id = NULL`. Ids churn; a value here would create the durable reference doc 04 §8.4
  forbids.
- `project = P`.
- `payload = {"communities": [{"label", "size"}], "node_count", "edge_count", "community_count", "unassigned_count", "fallback", "duration_ms", "skipped_reason"}` — **no community id anywhere.** T12 asserts this by re-reading the ids just written and
  asserting none appears as any payload value.
- `record_event` runs inside Phase W's transaction, in its own SAVEPOINT, and never raises
  into the caller.

### 7.2 T2.53 — scheduling the job body

```python
# app/services/memory_community_detection.py
TOPIC_DETECTION_CONFIG_SCHEMA: list[FieldDescriptor]

async def run_topic_detection(
    session_factory, *,
    batch_size: int = 5,

    **knobs,

```

`run_topic_detection` takes a **session factory**, not a session, because §5.3 needs one
transaction per project; this matches `_make_lift_runner`/`_make_recompute_runner`
(`dream_jobs.py:162–231`). `detect_for_project` is the single-project unit tests drive
directly.

**The project source, stated (F5).** The rotating cursor iterates:

```sql
SELECT project FROM (
    SELECT DISTINCT project FROM memories
    WHERE status = 'active' AND is_archived = false
      AND (expires_at IS NULL OR expires_at > now())
    UNION
    SELECT DISTINCT project FROM memory_communities
) p
WHERE project > CAST(:after_project AS text) OR CAST(:after_project AS text) IS NULL
ORDER BY project LIMIT CAST(:batch_size AS int)
```

Two deliberate choices:

- **Not the `projects` registry.** `project_registry.register` never raises by design
  (`project_registry.py:41–53`: "capture must not fail because the registry write did"), so
  a failed registry write leaves a project holding memories and no registry row. Iterating
  the registry would skip that project **silently and forever** — a silent-miss mode the
  corpus's own module docstring predicts. Deriving from `memories` cannot drift. Calling
  `backfill()` at run start would also close it, at the cost of a write on a read path;
  deriving is cheaper and needs no write.
- **The `UNION` with `memory_communities` is not redundant.** If every memory in project P
  becomes superseded or archived, P has no eligible memories — so a memories-only iteration
  would never visit it again and P's stale topics would linger forever, surfacing dead
  memories through T2.20 browsing. Including projects that still hold community rows means
  P gets visited, produces an empty projection, and the `DELETE` clears it. T18 pins this.

`after_project` + `ORDER BY project` is the cursor; T2.53 persists `last_project` into the
job's `config` row.

**`TOPIC_DETECTION_CONFIG_SCHEMA` keeps the placeholder's `batch_size` key, default (5) and
maximum (100) verbatim**, meaning "projects per run". Not incidental — `dream_jobs.py`'s own
docstring warns that `JobRegistry.set_config` merges `{**cfg.config, **partial}` and never
drops a key, so a schema swap that renames `batch_size` orphans any persisted value
silently. T2.09 and T2.10 both solved it by keeping the key. New knobs (`hub_cap`,
`leiden_timeout_seconds`, `min_community_size`, `max_projection_edges`, `resolution`) are
additions, never renames.

## 11. Generalise, subclass, or sibling?

**Sibling module, plus a ~30-line shared kernel.**

| | code side | memory side |
|---|---|---|
| Scope key | `repo_id` | `project` |
| Node identity | composed string keys | UUIDs |
| Edges | stored `code_edges` rows, unweighted | derived, weighted, no stored edge |
| Storage | `code_graph_nodes` + `member_of` edges | two dedicated tables |
| Rewrite | delete-by-kind, then upsert | delete-and-rewrite in one transaction |
| Label source | dominant directory | dominant entities |

A base class fixing all six would be six abstract methods around fifteen lines of shared
code — the "abstraction that fits neither graph" the brief warns about. Subclassing
`CommunityDetector` is worse: it is constructed as `(session, repo_id)` and every method
reads the code graph.

But pure duplication is also wrong, and `CLAUDE.md` names why: `code_query.py` declares its
own `RRF_K = 60` rather than using `rank_fusion.py`, "the two constants can drift and **no
task owns closing that**". Two independent `find_partition(..., seed=0, timeout=60)` call
sites are the same defect in advance. So the provably-common kernel — import guard, graph
build, bounded seeded partition — moves to `app/utils/leiden.py` and both callers use it
(Steps 2, 9). Everything above it stays two modules sharing nothing.

If a reviewer defers Step 9, the drift must be recorded with an owner rather than created
silently.

## 12. Test plan

**The organising principle.** Doc 17 §7 bans pinning membership because Leiden is not
bit-identical across implementations (a measured −0.4 % modularity / 98.4 % partition
agreement residual). The way to get teeth anyway is to **split the system at the
projection/clustering boundary**: the projection is fully deterministic and gets exhaustive
value-level assertions; the clustering gets structural and invariant assertions only.

### 12.1 What round 1 got wrong, and the fix (F1)

Round 1's clustering-side tests had **no teeth at all**. The reviewer demonstrated it by
mutation rather than by reading: replace the Leiden call with `partition = [0] * n_nodes` —
the constant single-blob output §3.4's entire weighting scheme exists to prevent — and **all
fifteen tests still passed**. T7 passed because a constant is perfectly deterministic; T8
because isolated nodes are excluded by the orchestrator, not by Leiden; T10 and T11 because
they *expect* a single community. The clustering mechanism could be deleted outright and the
suite stayed green.

T7's two named breaking mutations were also empirically false, which §1.2 reproduced:
removing `seed=0` and dropping §3.5's `ORDER BY` both leave leidenalg 0.12.0 producing one
distinct partition, so T7 passed under both and its runbook §4 break-the-guard proof could
not have been honoured as written.

The fix is **T16**, and it is legal under doc 17 §7 because it asserts a *structural
property*, never a membership list: a fixture of two entity-disjoint clusters must yield **at
least 2 communities**. Disconnected components can never be merged by a modularity maximiser
— merging them adds no internal edges while increasing the expected-edges penalty, so it
strictly lowers modularity — which is why this cannot flake. §1.2 measured 50/50 unseeded
runs holding it. The constant-partition mutation kills T16 immediately, which is exactly the
proof runbook §4 demands.

**T7 is reframed to its own declared fallback**: community count plus size multiset, keeping
its idempotent-rerun assertions (no orphaned member rows, prior ids gone), which do have
teeth. It no longer claims `seed=0` or `ORDER BY` as breaking mutations, and no longer
depends on them.
