## 3. The projection — nodes, edges, weights

Doc 06 §7 says "a project-scoped projection of the memory graph" and diagrams
`memories -> entities -> relations`. That is a description. This section makes it a
definition.

### 3.1 Nodes

`memory_community_members` keys on `memory_id`, so **nodes are memories** and edges must be
memory-to-memory. Nothing else is representable.

### 3.2 Eligibility, cited

```
status = 'active' AND (expires_at IS NULL OR expires_at > now())
```

Doc 06 §7's lifecycle diagram states the rule directly: `Grow --> Decay: member memories
superseded / expired out`. Two consequences the citation forces:

- **`superseded` and `deprecated` are both excluded** by the single `status = 'active'`
  predicate — `deprecated` is downstream of `superseded` in the lifecycle (`CLAUDE.md`,
  Domain model), so "superseded out" covers it.
- **Expiry is by timestamp, not by sweep.** `expired_memory_cleanup` is periodic, so an
  expired-but-unswept row is `status='active'` with a past `expires_at`. Testing status
  alone would let it into a topic, which "expired out" forbids. The `expires_at` clause is
  the load-bearing half of the predicate and T4 exists to pin it.

`status` is the `memory_status` enum; the predicate uses the literal, so no bound param and
no `CAST(:status AS memory_status)` is required.

### 3.3 Edges — the four candidates, and why one wins

| Candidate | Verdict |
|---|---|
| **(A) Shared entities** via `entities.memory_ids` | **Chosen.** Extraction always runs (`CLAUDE.md`, Pipeline terminology), so every ingested memory contributes; `ix_entities_memory_ids` carries the fan-out; the semantics ("two memories talk about the same things") is exactly what a topic is. |
| **(B) Shared `memories.technologies`** | Rejected as *redundant*, not wrong. `technologies` is by construction the subset of a memory's entities whose type ∈ `TECH_TYPES` (`relations.py:43`), so (B) ⊂ (A) — it adds no edge (A) lacks and drops every non-tech topic (people, papers, concepts, events). Its only advantage is being project-local for free, which §5 obtains anyway. |
| **(C) `memory_relations` rows** | Rejected *for v1 on evidence*: the table has zero writers (verified §1). Its writer is `memory_dream`, T2.12, still a placeholder. A projection rooted here is the empty graph and would produce no topics at all. Note that doc 06 §7's diagram label `relations` means **entity** relations, not this table. §3.6 keeps the seam for it. |
| **(D) `memory_crossrefs`** | Rejected on three grounds, and the third is disqualifying. (i) Not project-scoped: `find_similar_memories` filters by fingerprint, not project, so crossrefs already bridge projects. (ii) It is a top-5 kNN — an arbitrary density knob, not a semantic statement. (iii) **The table carries no fingerprint column**, so rows written under different embedders coexist with incomparable cosine scales. Building edge weights from it is the closest thing to a cross-fingerprint comparison the schema permits, and invariant 2 forbids exactly that reasoning. |
| **(E) Two-hop entity-relation paths** (`A ⊨ X`, `X→Y`, `B ⊨ Y`) | Rejected for v1. It multiplies both density and the cross-project reach surface (`entity_relations` is global too), and on a hub-heavy graph it makes modularity a function of the relation extractor's recall rather than of topical structure. Revisit only with a metric (§10 O-3). |

### 3.4 Weights — the decision that dominates the output

An unweighted projection makes two memories sharing one incidental `concept` as connected
as two sharing eight specific tools. Worse, in darkmem's own corpus a hub entity
(`postgres`, `darkmem`, `python`) is asserted by hundreds of memories, and a single hub
injects a **clique** of `n(n−1)/2` unit-weight edges. Leiden's modularity is weight- and
degree-sensitive; one such clique collapses a project into a single blob — reaching the
degenerate output that the fallback exists to signal, while reporting success.

**Weight:**

```
w(u,v) = Σ_{e ∈ shared(u,v),  2 ≤ n_e ≤ hub_cap}  1 / (n_e − 1)
```

where `n_e` is the number of *eligible, in-project* memories asserting `e`.

Two mechanisms, each with its own job:

1. **`1/(n_e − 1)` — Newman's collaboration-projection normaliser.** Each entity
   contributes a total of exactly `n_e/2` weight spread over its clique instead of
   `n_e(n_e−1)/2`. A rare entity shared by two memories contributes `1.0` to that one pair;
   a 100-asserter hub contributes `~0.01` to each of its 4 950 pairs. Specificity buys
   connection; ubiquity does not. This is a *ranking* fix.
2. **`hub_cap` — a hard drop above a size.** Normalisation fixes the score but not the
   cost: a 500-asserter entity still materialises 124 750 rows before any weight is
   applied. `hub_cap` is a *materialisation* bound and is not interchangeable with (1).

`n_e` is counted **after** restricting to the project's eligible node set, not globally.
That is deliberate: an entity that is a hub across the whole install but is asserted by
three memories inside this project is *specific to this project* and should weigh like a
rare entity here.

Entity **types are not filtered** in v1 — including the `concept`/`entity` fallback sink.
Filtering them is a plausible tuning move but there is no metric to justify it (§10 O-3),
and dropping the sink would silently delete every topic in a non-technical project. The
excluded-type set is exposed as a config knob defaulting to empty so a future tuning run
can move it without a code change (convention 9).

### 3.5 The projection query

One statement, bounded, deterministically ordered:

```sql
WITH eligible AS MATERIALIZED (
    SELECT id
    FROM memories
    WHERE project = CAST(:project AS text)
      AND status = 'active'
      AND (expires_at IS NULL OR expires_at > now())
),
asserted AS MATERIALIZED (
    SELECT e.id AS entity_id, el.id AS memory_id
    FROM entities e
    JOIN LATERAL unnest(e.memory_ids) AS u(mid) ON TRUE
    JOIN eligible el ON el.id = u.mid
    WHERE e.entity_type <> ALL (CAST(:excluded_types AS text[]))
),
sized AS (
    SELECT entity_id, count(*) AS n
    FROM asserted
    GROUP BY entity_id
    HAVING count(*) >= 2 AND count(*) <= CAST(:hub_cap AS int)
)
SELECT a.memory_id AS u, b.memory_id AS v, sum(1.0 / (s.n - 1)) AS w
FROM asserted a
JOIN asserted b ON b.entity_id = a.entity_id AND a.memory_id < b.memory_id
JOIN sized s ON s.entity_id = a.entity_id
GROUP BY a.memory_id, b.memory_id
ORDER BY a.memory_id, b.memory_id
```

Four properties this query must keep, each for a stated reason:

- **`AS MATERIALIZED` on `eligible`.** Same lesson the buffer-claim CTE records in
  `CLAUDE.md`: a plain sub-select lets the planner re-execute it per outer row. Here the
  cost is quadratic re-evaluation against `memories`, not an over-wide claim, but the fix
  and the reason to not "simplify" it are identical.
- **`a.memory_id < b.memory_id`.** Undirected dedup in the join, so no `DISTINCT` pass and
  no self-loop.
- **`ORDER BY` is not cosmetic.** `seed=0` buys reproducibility only if the *input* is
  identical. Unordered edge rows, or a node index assigned from a `set`/`dict` iteration,
  make two runs of the same binary disagree and turn T7 into a flake. Node indices are
  assigned from a separately ordered `SELECT id FROM eligible ORDER BY id`.
- **Every bound param is CAST.** `:project` → `text`, `:hub_cap` → `int`,
  `:excluded_types` → `text[]`. asyncpg cannot infer these, least of all the array in a
  `<> ALL` (invariant 10).

### 3.6 The composition seam

`build_projection()` returns a `Projection` dataclass and is written so a second edge arm
(T2.12's `memory_relations`, or (E)) is a *union with weight addition* over the same node
set, not a redefinition. Adding an arm means adding a `SELECT u, v, w` producer and one
merge; it does not touch the detector, the repository, or the transaction shape.

## 4. Structural isolation — why a cross-project community is not producible

Four independent mechanisms, listed weakest to strongest, and then an honest statement of
what is *still* representable at the DDL level.

**M1 — The node set is closed under project.** `eligible` filters on `project`, and every
downstream identifier is an *index into* the ordered node list, never a raw UUID. Leiden
returns a membership vector over `[0, |N|)`; a memory outside the project has no index, so
it cannot be named by the partition. This closes the naive-join trap the brief names:
`entities.memory_ids` reaches other projects, but the `JOIN eligible` happens *before* the
self-join, so a foreign memory is never an `asserted` row and therefore never an edge
endpoint.

**M2 — The member write derives its rows from a join on project equality, rather than
checking one.** The insert is not `INSERT … VALUES (:cid, :mid)`; it is:

```sql
INSERT INTO memory_community_members (community_id, memory_id)
SELECT c.id, m.id
FROM memory_communities c
JOIN jsonb_to_recordset(CAST(:rows AS jsonb)) AS d(memory_id uuid) ON TRUE
JOIN memories m ON m.id = d.memory_id AND m.project = c.project
WHERE c.id = CAST(:community_id AS uuid)
```

The equality `m.project = c.project` is a *join condition that produces the row*. A member
row whose memory's project differs from its community's project is not a row this statement
can emit, however corrupted the candidate list is. It is a stronger statement than a
`WHERE` filter over a values list only in that the row's existence, not merely its
acceptance, depends on the equality.

**M3 — A silent drop is converted into a loud abort.** M2 alone would *drop* a foreign row
rather than reject it, which is the failure mode this corpus most dislikes. The repository
therefore compares the statement's `rowcount` against the candidate count and raises on any
shortfall, aborting the project's write transaction (§5) so the previous run survives
untouched. Silent truncation is what "no silent degradation" (inv. 14) forbids.

**M4 — A post-write assertion inside the same transaction.** Before commit:

```sql
SELECT count(*) FROM memory_community_members mm
JOIN memory_communities c ON c.id = mm.community_id
JOIN memories m ON m.id = mm.memory_id
WHERE c.project = CAST(:project AS text) AND m.project <> c.project
```

Non-zero raises and rolls back the whole project rewrite. This catches a violation
introduced by *any* writer of these tables, not only this one, for as long as the rewrite
runs.

**What remains representable, stated plainly.** M1–M4 make a cross-project member
unproducible **by the write path**. They do not make it unrepresentable **by the table**: a
hand-written `INSERT INTO memory_community_members …` against the shipped DDL still
succeeds. The mechanism that would close that is the one the baseline already used for
`memory_relations` — `project TEXT NOT NULL` plus
`FOREIGN KEY (memory_id, project) REFERENCES memories(id, project) ON DELETE CASCADE` — and
it is a baseline edit this lane may not make. **Escalated as §10 O-1.** The plan claims
exactly what it proves and no more.

## 5. Atomicity, and why this ordering cannot reproduce T1.21

### 5.1 The T1.21 lesson, restated in this task's terms

T1.21's defect was ordering: the graph strip ran *outside* the savepoint that wrote the
replacement, so a write failure left the memory with **no** graph on either path — worse
than either the old state or the new one. `CLAUDE.md` records the fix as "the strip and the
write are one atomic replace".

The analogous defect here is exact and easy to write: `DELETE FROM memory_communities WHERE
project = :p`, then run Leiden, then Leiden times out or raises → the project has **zero**
topics, having had a good set a moment earlier. The existing `CommunityDetector` avoids it
only incidentally (it deletes after the partition attempt, and its timeout branch still
writes); it is not a stated property there, and it would not survive a refactor.

### 5.2 The three phases

**Phase R — read (own session, read-only, then released).**
Build the projection for project `P`. No locks held past this point.

**Phase C — compute (no database connection at all).**
`igraph.Graph` construction and `leidenalg.find_partition(..., seed=0)` in an executor
under `asyncio.wait_for`. On `TimeoutError` → the single-community fallback result. On the
import guard failing or any other exception → **abort this project, write nothing, journal
the failure, continue to the next project.**

**Phase W — write (one transaction, one project).**

```
BEGIN
  DELETE FROM memory_communities WHERE project = :p        -- members cascade
  INSERT communities (id = new_id(), project, label, properties)
  INSERT members  (M2's join-derived statement, M3's rowcount check)
  M4's cross-project assertion
  record_event(consolidated / topic)                       -- own SAVEPOINT, never raises
COMMIT
```

**Why this cannot reproduce T1.21:** the `DELETE` is not reachable without a completed
partition result already in hand. Every fallible step — the library import, the graph
build, Leiden itself, the timeout — lives in Phase C, which holds no transaction and
touches no row. The strip and the rewrite are the same transaction, so any failure inside
Phase W rolls both back and the *previous* run's communities survive intact, ids and all.
The only outcomes are "the new complete set" and "the old complete set". T5 and T9 assert
both directions.

### 5.3 One transaction per project, not one per run

Per project, because:

- A whole-run transaction would hold write locks on every project's community rows for up
  to `max_run_seconds` (900 s on the placeholder registration) — a `SELECT` reader is
  unaffected under MVCC, but any other writer of these tables is not, and the lock
  footprint grows with install size for no benefit.
- One project's bad graph would abort every other project's good result.
- Doc 06 §7 says "delete-and-rewrite **per project**", and the churn contract is
  per-project by construction.

**What a partial run leaves:** projects already committed carry their new communities;
projects not yet reached carry their previous run's. Every project is internally
consistent; none is torn. Stale is not corrupt — the next run rewrites it, and the journal
(§6) records which projects a run actually reached, so a partial run is visible rather than
inferred.

### 5.4 What a concurrent reader sees

Under READ COMMITTED, `DELETE`+`INSERT` in one transaction means a reader sees either the
complete old set or the complete new set — never a mix, and never a community with no
members.

**One non-obvious caveat, and its mitigation.** A reader issuing *two* statements — "list
communities", then "list members" — can straddle the commit and join an old community id
against new member rows, yielding an empty result that looks like an empty topic. This is
not a defect of the rewrite; it is a defect of reading it in two round trips. The
repository therefore exposes `list_with_members(project)` as a **single joined query**, and
that is the documented read contract handed to T2.19/T2.20/T2.21/T2.39.

## 6. Fallbacks, bounds, and the label

### 6.1 The three fallbacks

| Trigger | Behaviour | `properties.fallback` |
|---|---|---|
| `igraph`/`leidenalg` import fails | **Write nothing. Delete nothing.** Log a warning, journal a skip, return a no-op outcome. | — (no rows written) |
| Connected node count `< 3` ("tiny graph", matching the code precedent's threshold) | One community over the connected nodes, if there are ≥ 2 of them; otherwise no community. | `tiny_graph` |
| Leiden exceeds `leiden_timeout_seconds` | One community over the connected nodes. | `timeout` |

The import-failure row is deliberately different from doc 06 §7's diagram, which routes
only *timeout* and *tiny graph* to the fallback. A missing library means **no information
was computed**; collapsing a project into one topic on that basis would be a fabricated
result, and deleting the previous run's good topics to write it would be T1.21 again from a
different direction. Not-running is the honest outcome. T9 pins it.

"Connected nodes" rather than "all eligible nodes" is also deliberate: a memory sharing no
entity with anything is not topically related to anything, and sweeping it into an
everything-community asserts a relationship that the projection says does not exist.

### 6.2 Membership is not a partition — stated, not implied

The brief asks which it is. **It is not.** Two classes of eligible memory get no membership
row: isolated nodes (no qualifying shared entity), and members of Leiden communities below
`min_community_size` (2, matching the code precedent's `if len(members) < 2: continue`). A
community of one is not a topic. T8 pins this so it cannot drift into a catch-all.

### 6.3 Bounds

- `hub_cap` (default 200) — §3.4; the materialisation bound.
- `max_projection_edges` (default 2 000 000) — counted with a cheap aggregate *before*
  materialising the edge list. Over the cap: **skip the project with a loud journal
  entry**, leaving the previous run intact. Silently truncating to the top-N edges would
  change the clustering semantics with no error and no symptom — the same failure shape
  `index_debt` exists to prevent on the code side.
- Large-graph tightening, mirroring the code precedent's `is_large` branch: above
  `large_graph_nodes` (10 000), `resolution` rises to 2.0 and `n_iterations` drops to 3.
- `leiden_timeout_seconds` (default 60, matching the precedent).

**A limitation that must be written down, not papered over.** `asyncio.wait_for` around
`loop.run_in_executor` **does not cancel the running thread** — `leidenalg` keeps burning
CPU to completion after the await returns. The timeout bounds the *await*, not the work.
The real bound on runaway CPU is `hub_cap` + `max_projection_edges` limiting graph size
before Leiden ever starts. Mitigation in this plan: a dedicated single-thread executor per
detection run, shut down with `cancel_futures=True`, so a leaked computation cannot starve
the default executor that asyncio also uses for other blocking calls. The existing
`CommunityDetector` has the same property today; this plan does not fix that, it names it
(§10 O-4).

### 6.4 The label — deterministic, no model call

For each community, rank the entities its members assert by (count of asserting members
DESC, global `n_e` ASC — more specific wins a tie, then `name` ASC). Take the top 3; join
their display forms.

- Ranking, dedup and tie-breaking use the lowercase `entities.name`; **rendering** uses
  `properties.display_name` when present, falling back to `name` (invariant 7 — lowercase
  on disk, casing in `display_name`).
- **Collisions matter here even though nothing enforces uniqueness.** There is no
  `UNIQUE (project, label)`, so a collision does not silently merge rows the way the code
  detector's composed key could (`community_detector.py:174–177`). It does something
  subtler: it makes the journal's reference-by-label (§6.5) and doc 09's pin-suggestion
  diff ambiguous. Resolution is deterministic — append the next-ranked entity, and only if
  still colliding append a stable ordinal derived from the sorted member-id list.
- `properties` carries the provenance: `{"dominant_entities": [{"name","display_name","type","members","n_e"}], "size": …, "fallback": …, "resolution": …, "edge_count": …, "hub_cap": …}`.

Why the label is T2.18's and not T2.19's: doc 06 §7's flowchart puts
`label = dominant entities` **inside** the `Insert` box and `report_string` in a separate
downstream `Report` box, and §7's prose splits them the same way ("labelled from dominant
entities, **and** enriched with an LLM `report_string` off the hot path"). It is also load
bearing for two things that must work before T2.19 exists: the journal references
communities by label, and doc 06 §10's pin-suggestion contract is "keyed on **stable
dominant-entity labels**, not churning ids". A NULL label at detection time leaves both
with nothing to key on. See §7.1 and §10 O-2.

### 6.5 Journalling

One `events` row per project per run:

- `event_type='consolidated'`, `object_type='topic'` — **both already in the closed
  vocabularies** (§1), so nothing needs widening and there is no taxonomy-first ordering
  constraint on this commit.
- `object_id = NULL`. Ids churn; putting one here would create precisely the durable
  reference doc 04 §8.4 forbids.
- `project = P`.
- `payload = {"communities": [{"label", "size"}], "node_count", "edge_count", "community_count", "unassigned_count", "fallback", "duration_ms", "skipped_reason"}` — **no
  community id appears anywhere.** T12 asserts this by construction: it re-reads the ids
  just written and asserts none of them appears as any value in the payload.
- `record_event` runs inside Phase W's transaction, in its own SAVEPOINT, and never raises
  into the caller (`events.py`).

## 7. The two seams, as interfaces

### 7.1 T2.19 — labelling refinement + `report_string`

T2.19 never imports the detector and never touches the transaction shape. It goes through
the repository:

```python
# app/repositories/memory_communities.py
async def list_with_members(session, project: str) -> list[CommunityRow]
async def get_by_label(session, project: str, label: str) -> CommunityRow | None
async def set_report(session, community_id: UUID, *, label: str | None,
                     report_string: str | None) -> None
```

`get_by_label` is the seam that makes the churn survivable: because ids churn but labels are
derived deterministically from dominant entities, T2.19 can carry a prior run's
`report_string` forward across a rewrite by looking up the previous label, rather than
regenerating every report on every run. Without it, T2.19 pays an LLM call per community
per night forever.

**Boundary, stated exactly:** T2.18 writes `label` (deterministic, no model call) and
`properties`; it never writes `report_string` and never calls a model. T2.19 writes
`report_string` and may overwrite `label` with a refined one. That narrows T2.19's stated
"Labelling + `report_string`" to "label refinement + `report_string`" — a Tier-2 amendment,
surfaced as §10 O-2.

### 7.2 T2.53 — scheduling the job body

```python
# app/services/memory_community_detection.py
TOPIC_DETECTION_CONFIG_SCHEMA: list[FieldDescriptor]

async def run_topic_detection(
    session_factory, *,
    batch_size: int = 5,
    after_project: str | None = None,
    **knobs,
) -> DetectionOutcome            # .projects_processed, .last_project, .communities, .skipped

async def detect_for_project(session, project: str, **knobs) -> ProjectOutcome
```

`run_topic_detection` takes a **session factory**, not a session, because §5.3 needs one
transaction per project; this matches `_make_lift_runner`/`_make_recompute_runner`
(`dream_jobs.py:162–231`) exactly. `detect_for_project` is the single-project unit the
tests drive directly.

`after_project` + `ORDER BY project` is a rotating cursor so a large install does not starve
its later projects; T2.53 persists `last_project` into the job's `config` row.

**`TOPIC_DETECTION_CONFIG_SCHEMA` keeps the placeholder's `batch_size` key, default (5) and
maximum (100) verbatim**, meaning "projects per run". This is not incidental —
`dream_jobs.py`'s own docstring warns that `JobRegistry.set_config` merges
`{**cfg.config, **partial}` and never drops a key, so a schema swap that renames
`batch_size` orphans any persisted value silently. T2.09 and T2.10 both solved it by
keeping the key; T2.18 does the same, and T2.53 inherits a schema with nothing to strip.
The new knobs (`hub_cap`, `leiden_timeout_seconds`, `min_community_size`,

## 11. Generalise, subclass, or sibling?

**Sibling module, plus a ~30-line shared kernel.** Not a subclass, and not a shared
`CommunityDetector`.

The two graphs disagree on everything a base class would have to fix:

| | code side | memory side |
|---|---|---|
| Scope key | `repo_id` | `project` |
| Node identity | composed string keys | UUIDs |
| Edges | stored `code_edges` rows, unweighted | derived, weighted, no stored edge |
| Storage | `code_graph_nodes` + `member_of` edges | two dedicated tables |
| Rewrite | delete-by-kind, then upsert | delete-and-rewrite in one transaction |
| Label source | dominant directory | dominant entities |

A base class fixing all six would be six abstract methods wrapped around fifteen lines of
shared code — the "abstraction that fits neither graph" the brief warns about. Subclassing
`CommunityDetector` is worse still: it is constructed as `(session, repo_id)` and every
method reads the code graph.

But *pure* duplication is also wrong here, and `CLAUDE.md` names why: `code_query.py`
declares its own `RRF_K = 60` rather than using `rank_fusion.py`, "the two constants can
drift and **no task owns closing that**". Two independent `find_partition(..., seed=0,
timeout=60)` call sites are the same defect in advance. So the provably-common kernel — the
import guard, the graph build, and the bounded seeded partition — moves to
`app/utils/leiden.py` and both callers use it (Step 2, Step 7). Everything above it stays
two modules that share nothing.

If a reviewer prefers to defer Step 7, the plan still works — but then the drift must be
recorded somewhere with an owner, rather than created silently.

## 12. Test plan

**The organising principle.** Doc 17 §7 bans pinning membership because Leiden is not
bit-identical across implementations (a measured −0.4 % modularity / 98.4 % partition
agreement residual). The way to get teeth anyway is to **split the system at the
projection/clustering boundary**: the projection is fully deterministic and gets exhaustive
value-level assertions; the clustering is not and gets only structural and invariant
assertions. Every number this suite pins comes from the projection side; nothing on the
clustering side asserts *which* memories share a community.

One distinction the plan relies on and should be checked by the reviewer: doc 17 §7 forbids
pinning membership *in the test file* — a hard-coded expected member list, which breaks when
the library version changes. T7 instead compares **two runs of the same binary in the same
process** to each other. That is determinism-within-an-implementation, which `seed=0` plus
§3.5's `ORDER BY` guarantees, and it is exactly what the residual measurement says is
*not* at risk. If a reviewer judges even that too tight, the documented fallback is to
assert the community count and the size multiset instead.

| # | Assertion | Mutation that makes it fail |
|---|---|---|
| T1 | No member row's memory has a project other than its community's, after a run on a corpus where two projects share an entity row | Drop `m.project = c.project` from M2's join |
| T2 | A globally-shared entity does not bridge projects: a run for A creates no member for B's memories, and no community mixes them | Drop `project` from the `eligible` CTE — the specific naive-join trap |
| T3 | The repository raises when handed a candidate list containing a foreign-project memory id | Remove M3's rowcount check (the row is dropped silently and the test passes without it) |
| T4 | Only `active` and unexpired memories appear in any member row; the expired-but-unswept row is excluded | Drop `expires_at > now()`, or relax `status = 'active'` |
| T5 | **T1.21 guard.** With the member insert patched to raise, the previous run's communities are byte-identical afterwards — same ids, same member sets | Move the `DELETE` outside Phase W's transaction, or commit between DELETE and INSERT |
| T6 | Running detection for project A leaves project B's community ids untouched | Drop `WHERE project = :p` from the DELETE |
| T7 | Two runs on an unchanged corpus produce an identical partition (frozenset of frozensets of member ids); no orphaned member rows; the first run's ids are gone | Remove `seed=0`, or drop §3.5's `ORDER BY` so edge order varies |
| T8 | An isolated memory is in **no** community and the run still succeeds; membership is not a partition of the eligible set | Sweep unassigned nodes into a catch-all community |
| T9 | **Second T1.21 guard.** With the `igraph` import monkeypatched to fail, the run writes nothing **and deletes nothing** | Make the import guard delete-then-return |
| T10 | Tiny graph (2 memories, 1 shared entity) → exactly one community of 2, `properties.fallback == 'tiny_graph'` | Raise the min-node threshold without routing to the fallback |
| T11 | Zero timeout → exactly one community over the connected nodes, `properties.fallback == 'timeout'` | Make the timeout branch write nothing after the delete |
| T12 | Exactly one `consolidated`/`topic` event per project per run; `object_id IS NULL`; **none of the just-written community ids appears as any value in the payload** | Put a community id in `object_id` or in the payload |
| T13 | No file under `app/` outside the detector imports `app.services.memory_community_detection`; plus a synthetic offender the scan catches | Import the detector from `pipeline.py` |
| T14 | Reflecting the live schema, the only FK referencing `memory_communities(id)` is `memory_community_members.community_id` | Any later baseline round adding a durable FK to a churning id |
| T15 | In the projection, a pair sharing only a 100-asserter entity has strictly less weight than a pair sharing only a 2-asserter entity | Replace the weight with a constant `1.0` |

Each of T3, T5, T9, T12, T13 is invariant-bearing, so per runbook §4 each must be proven by
breaking the guard on purpose, watching the test fail, restoring it, and watching it pass —
recorded in the completion note.

**Fixtures.** All seeding is direct SQL against `memories` and `entities` — no pipeline run,
no embedder, no model call, so the suite is offline and fast. `entities.memory_ids` is
populated by hand, which is also what lets T1/T2 construct the cross-project entity that
does not otherwise occur naturally.
