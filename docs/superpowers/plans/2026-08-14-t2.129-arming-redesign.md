# T2.129 — arming redesign: make the armed fact reach the audit's numerator

**Status:** plan, awaiting Fable review and owner go. Size L, so nothing here is
executed before both.
**Branch:** `feat/t2.129-gc-corpus` (head `9b7d2283` at authoring time).
**Owning task:** T2.129. **Gate:** G-C.

## 1. What happened, and what is actually broken

Pass 1 (2026-08-14, `docs/eval/2026-08-14-t2.129-arming/bench-run-pass1.txt`)
ran live end to end and split:

- **The census half worked.** 148 corroborations in the window against a
  decidability floor of 20 and a band that ends at 100; all three gate buckets
  powered and clearing; both designed refusals still at `candidate`.
- **The arming half fired and still did not reach the numerator.** The
  deterministic detector produced a real dispute on live rows, both directions,
  rule `inverse_replacement`, witness `codex:ee5c67b3`. But the subject fact was
  never journalled `corroborated`, so the audit's `disputed_after` arm is 0 and
  that zero is still inoperability rather than measured precision.

The measured cause: a claim needs three sessions to corroborate by count, and
the three wave-1 sessions all assert one replacement in one project, so
`detect_supersessions` retires each in favour of the next. `supersession_hold`
then blocks promotion of a fact **one** of whose memory sources is superseded.
The fact holds at `candidate` with `supersession_blocked` journalled — inside
G-C's eligible denominator, never its numerator — and the dispute lands with no
corroboration to join to.

**Neither the veto nor the blocker is wrong. The corpus content is wrong, and
the corpus is the only side of this that may move.** No bar moves, no ladder
predicate moves, no threshold moves.

## 2. The repair, and why it works — verified in code, not inferred

Move the arming captures **outside the supersession look-back window** so
`detect_supersessions` never fires on them. Four links, each checked against
the tree rather than assumed:

1. **The window's anchor is real wall-clock, not the memory's own date.**
   `detect_supersessions(..., now=None)` sets `reference = now or
   datetime.now(timezone.utc)` and `cutoff = reference - 90d`
   (`supersession.py:177-178`, `SUPERSESSION_WINDOW_DAYS = 90` in
   `relations.py:123`). The pipeline's call site (`pipeline.py:762`) **omits
   `now`**. So a capture dated far enough back is outside the window at ingest
   however the corpus orders it — the check that makes this repair possible at
   all, and the one that would have killed it had the anchor been the new
   memory's date.
2. **The corpus's declared date is what Phase 5 sees.**
   `ingest._create_memory_rows` overwrites the server stamp with the entry's
   `created_at` before its commit, and `process_batch` — which runs supersession
   in Phase 5 — opens its own sessions afterwards. The backdate is therefore in
   place before the detector reads it.
3. **Clearing supersession clears the blocker.** `detect_supersession_hold`
   returns `None` exactly when no memory source of the fact is superseded, and
   `adjudicate_supersession_hold` is that `None` test. It is a single detector
   with no other input, so nothing else can hold the promotion.
4. **Backdating the sources does not push the corroboration out of the
   measurement window.** Both windows are 90 days, which looks self-defeating,
   but they key on different columns: supersession reads `memories.created_at`,
   while every G-C metric windows on `events.created_at` (`promotion_metrics.py`
   — `p.created_at >= :since AND p.created_at <= :until` throughout). The
   `corroborated` row is journalled at recompute time, which is inside the
   window whatever the sources' dates. **This is the crux of the whole repair
   and the first thing a reviewer should try to break.**

Arithmetic, so the destination is stated before the run: one genuine false
promotion against 148 in-window corroborations is `1/148 = 0.0068`, under the
`0.01` bar, decidable because 148 > 100. This is why the census had to clear 100
first — the two halves of T2.129 only work together, exactly as `2af1c099`
claimed. **If the run instead yields a rate at or above 0.01, the bar does not
move; the finding is recorded red.**

## 3. What must move, and the trap inside it

All **five** arming entries, both waves — not just wave 1.

| key | group | wave | current date | project |
|---|---|---|---|---|
| `wh-trino-1` | `armed_subject` | 1 | 2026-06-10 | warehouse |
| `wh-trino-2` | `armed_subject` | 1 | 2026-06-12 | warehouse |
| `wh-trino-3` | `armed_subject` | 1 | 2026-06-15 | warehouse |
| `wh-trino-4` | `armed_subject` | 2 | 2026-07-06 | warehouse |
| `wh-rollback` | `armed_counterpart` | 2 | 2026-07-20 | warehouse |

**Moving wave 1 alone reproduces the failure one step later.** `wh-rollback`
asserts `hive REPLACES trino`, so its supersession targets carry `trino`; with
`wh-trino-4` left inside the window it becomes a lawful candidate and is
retired, one source of the fact is superseded again, and the hold re-blocks
after the corroboration rather than before it. That would look like a *new*
defect while being the same one.

Relative order and the gaps between captures are preserved, so nothing that
reads the timeline changes meaning. The proposed shift is a uniform −150 days
(2026-06-10 → 2026-01-11, …, 2026-07-20 → 2026-02-20), which puts the newest
arming capture 175 days before the 2026-08-14 run — 85 days of margin against
the 90-day cutoff, and still outside it for any run after 2026-05-21.

**The arming project is isolated**, so the shift touches nothing else:
`warehouse` contains exactly these five entries, and the other five corpus
memories mentioning trino or hive sit in `default` and `ledger`, which
supersession cannot reach across (condition 1 is same-project).

## 6. Where this goes wrong quietly

- **The audit clears for the wrong reason.** If the corroboration lands but the
  dispute does not, the rate is `0/149` and reads *better* than pass 1 while
  being just as inoperable. Step 3's catch (d) is what separates them; a green
  rate alone must never be reported as a cleared audit.
- **A date shift silently changes a census bucket.** The arming project is
  isolated and the shift is uniform, but `simulate_capture_time_provenance`
  writes these dates into `fact_sources.created_at`, which the time-gap gate
  reads. The arming subject promotes by count (three distinct origins), not by
  time gap, so it should not matter — *should* is why step 1's catch compares
  the census group counts against pass 1 rather than trusting the argument.
- **The fix becomes clock-dependent.** Fixed dates recede from the window
  forever, so this is safe going forward; it would break only under a simulated
  clock. Step 2's assertion is what makes that fail loudly instead of silently
  re-blocking.
- **The margin gets eaten by a future edit.** Someone adding an arming entry
  later will date it near the others' era without knowing why. Step 2's message
  is where that reader is told.

## 7. Residuals — what this does not achieve

- It does **not** make G-C clear. It makes one arm of the false-promotion audit
  *operable*. The gate's verdict is step 5's to report and the owner's to rule
  on.
- The numerator it produces is **one** fact. A rate computed from a single
  numerator event is decidable but not precise, and the report must say so
  rather than presenting `0.0068` as a measurement of the system's false-
  promotion behaviour.
- The LLM `contradiction_scan` remains off the veto (T2.109) and still dead-ends
  on the unqualified judge, so the `disputed_after` arm stays judge-free and the
  `rejected_after` arm stays human-gated. This plan changes neither.
