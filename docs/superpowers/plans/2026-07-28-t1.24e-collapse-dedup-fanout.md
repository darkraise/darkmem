### 3.1 `dedup_by_target_predicate` is a **net negative** on this corpus

The `+0.015` is not noise and is not a rounding artefact. Traced on `e14`:

```
content : The gateway's JWT auth follows RFC 7519 and signs tokens with RS256.
gold    : gateway USES jwt | jwt IMPLEMENTS rfc 7519 | jwt USES rs256

into the pass:   JWT   -USES-> RS256        weight 0.8   rescue=False   (LLM)
                 gateway -USES-> RS256      weight 0.6   rescue=True    (rescue)
dropped     :    JWT   -USES-> RS256                     <- the gold edge
```

Both compete for key `(rs256, USES)`. The rescue-first tie-break keeps the rescue
triple and drops the gold one. Grammatically the subject of "signs tokens with
RS256" is *the gateway's JWT auth*, whose head is `JWT auth`; the rescue anchored
on the possessive modifier `gateway` instead. That is precisely failure mode 1 in
the pass's own docstring — subject anchoring — so **on the single case in the
whole corpus where the rescue-first rule fires, it makes the pass do the opposite
of what it was built to do.**

> **Corrected during execution.** This paragraph originally attributed the losing
> triple to `_rescue_relations` (adjacency). The whole-corpus snapshot diff shows
> its properties are `{"rescue": true, "subject_tracked": true}`, so the emitter is
> `_rescue_relations_subject_tracking`. The argument is unchanged — that pass also
> infers the subject from position rather than from a directional pattern — but the
> attribution was wrong and is recorded rather than quietly amended.

Four tie-break variants, measured (§4 recipe, both sets):

| Variant | gold `rel_full` | held-out `rel_full` |
|---|---|---|
| V1 current — rescue-tagged first, then weight | 0.857 | 0.950 |
| V2 direction-grounded rescue first, then weight | **0.883** (+0.026) | 0.950 (0.000) |
| V3 rescue-first for the REPLACES family only | 0.883 (+0.026) | 0.950 (0.000) |
| V4 weight only (pre-fix behaviour) | 0.883 (+0.026) | 0.950 (0.000) |

**The corpus cannot distinguish V2 from V4** — which is the trap. V4 reverts the
recorded wrong-direction-REPLACES fix outright, and the corpus would rate that
identical to a principled narrowing. Step 4's justification is therefore
structural, not numeric; §5 shows the direct experiment that separates them.

### Step 2 — The two collapse passes, individually tested

**Size:** M. **What changes:** tests only.

*`_drop_uses_when_replaces_exists`* — pair-based, direction-agnostic by design:
`USES` dropped when a `REPLACES` covers the same unordered pair in either
direction; every `REPLACES_FAMILY` member (`REPLACES`, `IMPROVES_ON`, legacy
`BUILDS_ON`) triggers the drop, parametrised over the frozenset itself so adding
a member without a test is caught; self-loops ignored; non-`USES` types
untouched; no `REPLACES` anywhere is a no-op returning the input list.

*`_drop_uses_when_deployed_on_exists`* — direction-**sensitive**, the deliberate
asymmetry with the pass above and the one a rewrite would flatten: `A USES B` +
`A DEPLOYED_ON B` collapses; `A USES B` + `B DEPLOYED_ON A` does **not**. Pin
both, and pin that the surviving edge is the `DEPLOYED_ON`.

**Mutation proof (required).** (a) Make `_drop_uses_when_replaces_exists` compare
ordered pairs instead of `frozenset` — the reverse-direction test must fail.
(b) Make `_drop_uses_when_deployed_on_exists` compare `frozenset` instead of the
ordered pair — the asymmetry test must fail. Both are one-word changes the bench
cannot see (§3: one memory and zero memories respectively). Restore, re-run,
record both outputs, then clear `__pycache__` per GLOBAL §6.

### Step 3 — The tie-break against the real wrong-direction case

**Size:** M. **What changes:** tests only. `_prefer_relation` is not touched here.

This is Done-when 1 and ruling 4. The existing `test_rescue_outranks_weight_in_
the_tie_break` in `tests/test_relation_rescue.py` calls `_prefer_relation` with
two bare dicts and no content — it proves the ordering rule, not that the rule
fixes anything. Keep it (it is T1.25's unit pin) and add the end-to-end case:

- `test_the_rescue_wins_the_real_wrong_direction_replaces` — the §5 case, driven
  through `clean_extraction` from raw LLM-shaped output plus real content.
  Asserts `pgvector -REPLACES-> qdrant` survives and `darkmem -REPLACES-> qdrant`
  does not.
- `test_weight_alone_would_have_kept_the_backwards_edge` — the counterfactual
  that makes the first test non-vacuous. Run the same input through a registry
  whose dedup uses a weight-only preference and assert the backwards edge
  survives. Without this, the first test cannot distinguish "the tie-break fixed
  it" from "any ordering would have".
- `test_the_wrong_direction_edge_reaches_supersession_without_the_tie_break` —
  states the consequence in the test name: a surviving `darkmem REPLACES qdrant`

  database; the point is the recorded reason the fix exists.

**Mutation proof.** Set `_prefer_relation` to weight-only and confirm exactly the
first and third tests fail while the counterfactual still passes.

### Step 4 — Narrow the tie-break to the claim it can actually support

**Size:** M. **What changes:** `app/services/extraction_clean.py`, plus the one
unit test in `tests/test_relation_rescue.py` that pins the unscoped form.
**Tier-2 amendment.**

§3.1 measured that rescue-first fires exactly once across 36 memories and fires
wrong. The justification for changing it is **structural and independent of
`gold.json`**, and the +0.026 is corroboration:

`_prefer_relation`'s docstring justifies rescue-first with "those are
regex-grounded against the source text so their direction is structurally more
trustworthy than the LLM's". Read the three rescue emitters and that premise holds
for exactly one of them:

| Emitter | Stamps | How it picks the source |
|---|---|---|
| `_rescue_relations` (adjacency) | `{"rescue": True}` | closest preceding entity, with a clause-subject fallback — a **guess** |
| `_rescue_relations_subject_tracking` | `{"rescue": True, "subject_tracked": True}` | the tracked clause subject — a **guess** |
| `_rescue_relations_replaces` | `{"rescue": True, "pattern": <label>}` | a **directional pattern** (from-X-to-Y, Y-supersedes-X, …) |

Only the third grounds *direction* in a pattern; the first two ground *adjacency*
and infer direction from position. Preferring their guessed subject over the
LLM's is not what the recorded fix claimed, and it re-introduces the very subject
anchoring the dedup exists to correct.

**The change:** introduce a named predicate — direction-grounded means a rescue
triple carrying a pattern label — and let it, not bare `rescue`, win the
tie-break; weight decides otherwise. Pin with a test that every
`_rescue_relations_replaces` emission carries the label, so a future edit that
drops it fails loudly instead of silently losing the tie-break.

**What must still hold after the change**, and is the acceptance for this step:
Step 3's three tests pass unchanged (V2 preserves the recorded fix — verified in
§5, the winning triple carries `pattern="from-to"`); gold rises to `0.883` and
held-out is unmoved at `0.950`; `e14` is the only memory whose output changes on
either set; no entity dimension moves.

**If any of that fails to reproduce during execution, do not proceed with the
step** — revert to V1, keep Steps 1–3 and 5–8, and report the narrowing as a
declined finding with its measurement. A narrowing that cannot be shown to
preserve the recorded fix is not an improvement.

### Step 5 — Fan-out determinism

**Size:** S. **What changes:** one word in `_fan_out_coordinated`, plus tests.

`for member in g` iterates a `set[str]`, so the emission order of a coordinated
group is decided by per-process string hash randomisation. Reproduced in §5:
two distinct orderings across four seeds on both `e10` and `h3`, identical sets.
Fix is `sorted(g)`.

Two tests, because one alone is not a guard:

- `test_fan_out_emits_coordinated_members_in_a_stable_order` — in-process,
  asserts the minted edges come out in ascending member order. Cheap, but under
  the unfixed code it can pass by luck on a given seed, so it is not the guard.
- `test_the_whole_chain_output_order_is_stable_across_hash_seeds` — the real
  guard. Runs `clean_extraction` over the same input in two subprocesses with
  different `PYTHONHASHSEED` and asserts the output **lists** are equal, not the
  sets. This is the property doc 17 §7 and `CLAUDE.md`'s reproducibility contract
  actually claim, and it is what the seed forwarding protects by a different
  route. Bound it with a timeout and use the running interpreter.

**Mutation proof.** Revert `sorted(g)` to `g` and confirm the cross-seed test
fails; restore and confirm it passes. Clear `__pycache__` afterwards — the
mutation is size-changing, but GLOBAL §6 applies to the step either way.

**Re-measure both gold sets after this step.** Sets are unaffected in principle;
prove it rather than assert it.

### Step 6 — Fan-out runs last, and its output survives dedup

**Size:** S. **What changes:** tests only. This is Done-when 2.

`ORDERING_CONSTRAINTS` already carries the `RunsBefore("dedup_by_target_
predicate", "fan_out_coordinated")` entry and `validate_registry` checks it at
import, so a bad reorder cannot be imported. The constraint proves the *order*;
these tests prove the *reason*:

- `test_fan_out_mints_a_multi_source_set_for_one_target_predicate` — a coordinated
  subject group produces several sources for one `(target, predicate)` and all of
  them reach the final output.
- `test_dedup_after_fan_out_would_collapse_the_set` — the counterfactual: run a
  registry with the two swapped and assert the multi-source set collapses to one
  edge. This is why the constraint exists, stated as an executable fact rather
  than as the `why=` string.
- `test_the_ordering_constraint_is_enforced_at_import` — build a registry with the
  two swapped and assert `validate_registry` raises `RegistryContractError`.

### Step 7 — The second `filter_event_edges`, and `drop_unlinked_dates`

**Size:** M. **What changes:** tests only. This is Done-when 3.

Ruling 3 is explicit that a test proving the pass runs twice is not the
deliverable. The deliverable is an edge the **first run could not have seen**,
and §5 verified one exists:

- `test_the_second_event_filter_catches_an_edge_fan_out_minted` — the §5 case.
  Assert the illegal `migration -DEPENDS_ON-> pgbouncer` is absent from the full
  chain's output, **and** that it is present in the pre-fan-out state, so the test
  is about creation order rather than about the filter being idempotent.
- `test_the_first_event_filter_could_not_have_seen_it` — the asymmetry, which is
  the actual proof. Drop only the Stage-4 occurrence: output unchanged. Drop only
  the Stage-5 occurrence: the illegal edge survives. A single pass placed at
  either position alone is therefore not sufficient, which is what
  `StraddlesPivot` encodes.
- `test_removing_either_occurrence_breaks_the_straddle_constraint` — both
  single-occurrence registries fail `validate_registry`.

*`_drop_unlinked_dates`* (invisible to the corpus, §3, so tests are the only
guard): a date entity with no `HAPPENED_ON` pointing at it is dropped; one with a
`HAPPENED_ON` survives; a non-date entity is never dropped; a name that merely
*contains* a date is not dropped (`fullmatch`, not `search`); matching is
case- and whitespace-insensitive on the target side.

**Mutation proof.** (a) Delete the Stage-5 `filter_event_edges` entry — the first
two tests must fail. (b) Swap `_drop_unlinked_dates`'s `fullmatch` for `search` —
the contains-a-date test must fail. (b) is the highest-value mutation in this
plan: a one-word change the bench rates at exactly 0.000 that would delete every
dated event entity in production.
