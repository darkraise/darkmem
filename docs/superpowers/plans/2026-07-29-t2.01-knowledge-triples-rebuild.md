## 1. What is already true (measured, not assumed)

The baseline migration **already lands the rebuilt DDL**. T0.12b/T0.12c created
`knowledge_triples` and `fact_sources` in their target shape, with all four
indexes and the `verification_status` CHECK. Verified by reading
`backend/migrations/versions/0001_baseline.py:452–536`.

So T2.01 is **not** a schema task. The DDL is done; the semantics are not.

### 1.1 The finding that reshapes this task

**The ORM model and the repository SQL still describe the *old* demo schema.**
They were never migrated when the baseline rebuilt the table underneath them.

| Layer | Declares | Reality in the baseline |
|---|---|---|
| `app/models/graph.py:52` `KnowledgeTriple` | `subject`, `predicate`, `object`, `valid_from`, `valid_to`, `source_memory_id` | `subject_name`, `object_name`, `rel_type`, `valid_at`, `invalid_at`, `expired_at` |
| `app/repositories/graph.py:722–780` | `INSERT/SELECT` over `subject, predicate, object, valid_from, valid_to` | none of those columns exist |
| `app/services/knowledge_graph.py` (215 lines) | `_slugify` endpoints, free-form predicates | closed `rel_type`, lowercase soft-ref names |

Every one of those queries would fail at runtime with `UndefinedColumnError`.
Nothing catches it because **the service has zero callers** — confirmed by grep
across `backend/app`. The backend suite is green *because* the code is dead, not
because it works. This matches the darkmem memory recorded 2026-07-22
(`bc8e6791`): the table is untested demo scaffolding, and wiring it is a rebuild
that keeps only the name.

**Consequence for sequencing:** the first step is a *deletion*, not a build. A
rebuild that leaves three drifted layers in place invites a future caller to
import the stale model and get a runtime error the suite cannot see.

section, and it would be easy to build all of it here and call it T2.01.

## 3. The three Done-when items, made executable

### D1 — "The two axes are independently queryable and independently transitioned"

The belief axis is `(valid_at, invalid_at, expired_at)`; the verification axis is
`verification_status`. Independence means a transition on one **never** writes
the other.

- Repository methods split by axis: `close_window()` / `expire()` on belief,
  `set_verification_status()` on verification. No method writes both.
- Live is exactly `expired_at IS NULL` — one predicate, one helper, never
  re-spelled inline at call sites.
- Test: expire a `confirmed` fact, assert `verification_status` is still
  `confirmed`; dispute a live fact, assert its window is untouched.

### D2 — "A confirmed-but-expired fact is representable and renders as such"

This is the cell the orthogonality claim lives or dies on.

- Write a fact, set `verification_status='confirmed'` **by direct SQL in the
  fixture** (see Step 5 — the repository method refuses `confirmed` by design),
  then `expired_at=now()`.
- Assert it persists, is excluded from the live view, and is returned by an
  as-of query for a time inside its window.
- "Renders as such" is a **read-model** obligation: the row must carry both
  facts distinguishably. No UI in this task — T2.36 owns the Facts tab. This
  narrows the plain reading of the acceptance criterion, so it is logged as an
  amendment row in `E2-truth-core.md` rather than left as a private
  interpretation (runbook §5).

### D3 — "`triple_key` identity is stable across re-derivation"

`triple_key` is `uuid5` over the canonicalised lowercase names **and the
project** (doc 04 §8.3). Stability means deriving the same fact twice yields the
same key, so the partial-unique on
`triple_key WHERE expired_at IS NULL AND invalid_at IS NULL` recognises it.

- One pure function, `compute_triple_key(project, subject_name, rel_type, object_name)`.
- Test: same inputs in different casing/whitespace → identical key; a different
  `project` → a different key (a typo'd project splits fact identity, which is
  the stated reason the `projects` registry exists in T2.07).

## 4. Steps

Each step is one commit, each leaves the floor green.

**Step 1 — Delete the drifted demo layer.**
Remove `app/services/knowledge_graph.py`, the `KnowledgeTriple` ORM model and its
`models/__init__.py` exports (lines 8 and 31), and the triple section of
`app/repositories/graph.py`.

**The deletion boundary in `graph.py` is the banner
`# ── knowledge_triples / temporal graph ──` at line 690 through end of file
(864)** — that is `upsert_entity_simple` (692) through `get_triple_stats` (842).
Nothing above line 690 is touched.

**These live methods sit immediately above the cut and must survive** — an
earlier draft of this plan named a range that would have deleted them, which
would have broken pipeline Phase 5, the hourly `graph_orphan_cleanup` job, and
supersession:

| Line | Method | Why it is load-bearing |
|---|---|---|
| 537 | tail of `delete_by_memory_id` | the Phase-5 atomic strip's entity-orphan guard (CLAUDE.md invariant) |
| 566 | `prune_orphan_entities` | the sweep `graph_orphan_cleanup` runs hourly |
| 602 | `technologies_for_memory` | the denorm read supersession depends on |
| 625 | `get_entities_by_memory_id` | live reader |
| 646 | `get_relations_between` | live reader |
| 681 | `get_stats` | live reader |

*Verify:* the check must prove the **absence of the old shape**, not just the
absence of two identifiers — a grep for `KnowledgeTriple` matches neither the
lowercase table name nor the drifted column names, so it would pass with broken
methods still in the file. All three must hold:
1. `rg -n 'valid_from|valid_to|\bpredicate\b' backend/app/repositories/graph.py` → no matches
2. `rg -n 'knowledge_triples' backend/app` → matches only the new belief-axis
   module and `embedder_registry.py`'s partition template (which legitimately stays)
3. `cd backend && python -m pytest -q` green

**Step 2 — `compute_triple_key`, pure and tested (D3).**
One function, no I/O. Canonicalise (lowercase, collapse whitespace), then
`uuid5` over `(project, subject_name, rel_type, object_name)`.
*Verify:* new `tests/test_triple_key.py`.

**Step 3 — The ORM model rebuilt against the real table.**
A model matching `0001_baseline.py:462–487` exactly — every column, correct
nullability (`fact` and `reference_time` NOT NULL; the three temporal columns
nullable). Endpoint ids are plain `UUID` columns with **no `ForeignKey`** — the
soft-reference doctrine of doc 04 §8.3; adding an FK here breaks
invalidate-not-delete against the aggressive entity sweeps.

**`id` is minted by `app/utils/ids.py:new_id()` (UUIDv7, doc 04 §2) — never
`uuid.uuid4`.** The baseline gives `id` no server default, so id generation is
entirely the application's obligation. The old model defaulted to `uuid4`, and a
rebuilt model that repeats that would pass the reflection test below (which
checks columns, not Python-side defaults) while breaking a doc-04 decision and
fragmenting the PK B-tree.

*Verify:* a test that reflects the live table and asserts the model's column set
and nullability match it, so this drift cannot silently recur; plus an assertion
that a minted id is UUID **version 7**.

**Step 4 — The belief-axis repository (D1, D2).**
`insert_open()`, `close_window()`, `expire()`, `get_live()`, `as_of(t)`. Raw SQL
carries `CAST(:id AS uuid)` on every bound param (invariant 10). Ids come from
`new_id()` as in Step 3. Invalidation is a re-save on the retained row — no
`DELETE` statement may appear in this module.

**Where the stale-on-arrival vs disjoint-window decision lives:** this
repository exposes **primitives only** — `insert_open()` inserts, and it does
**not** decide whether an existing open row on the same `triple_key` should be
closed first. Doc 08 §5 assigns the two temporal passes to `fact_lift`, which is
T2.10's; an `insert_open()` that unconditionally closed the prior open row would
break the disjoint-window case by closing a legitimately coexisting belief.
T2.01 gives T2.10 `close_window()` + `insert_open()` and the ordering contract
between them; T2.10 owns the branch.

*Verify:* `tests/test_knowledge_triples.py` covering D1 and D2, plus disjoint
windows leaving two live rows, and stale-on-arrival driven **by the test** as
`close_window()` then `insert_open()` — proving the ordering satisfies the
partial-unique. The partial-unique must never be the thing that fails.

**Step 5 — Verification-status storage, inert (D1's other half).**
`set_verification_status()` writing only that column, rejecting values outside
the CHECK's four, and **refusing `confirmed`** — doc 08 §4 makes human
ratification the only path, and T2.05 owns it. A machine-callable path to
`confirmed` is the failure this epic is built to prevent, so the refusal lands
now rather than being added later.

**The refusal and D2's fixture are deliberately on different paths.** D2 needs a
`confirmed` row, and this method will not produce one. The D2 fixture writes the
column by **direct SQL**, standing in for the human door T2.05 will build. That
is not a workaround: it is the point — the only way to reach `confirmed` is
outside the machine-callable surface.

*Verify:* a test asserting the refusal, and that no other column moves.

**Step 6 — Journal the transitions.**
Every belief and verification transition writes an `events` row through
`record_event`, with `object_type='fact'` (already in `OBJECT_TYPES`,
`events.py:80`).

Exact `event_type` values and their vocabulary status — checked against
`app/services/events.py:53–74`:

| Transition | `event_type` | Status |
|---|---|---|
| belief withdrawn (`expire()`) | `expired` | **already present** (`events.py:57`) |
| verification status set | `verified` | **already present** (`events.py:60`) |
| belief window closed (`close_window()`) | `invalidated` | **NEW — must be added to `EVENT_TYPES` in this same commit** |

`invalidated` is the only widening, and it is needed because closing a validity
window is not expiry: doc 08 §3.1 keeps a window-closed row **live**
(`expired_at IS NULL`), so reusing `expired` would make the two
indistinguishable in the journal. Taxonomy-first per CLAUDE.md: the value lands
in `EVENT_TYPES` before its emitter.

**Payload carries before/after status**, which is T2.06's stated contract, so
G-C metrics remain derivable from the journal by SQL without a rework.

**Deconfliction with T2.03/T2.06:** T2.01 journals only transitions its own
repository methods perform, which today no producer calls. When T2.03 lands the
Tier-C recompute, **the recompute becomes the sole journaller of verification
transitions** and these emitters are subordinate to it — otherwise the same
transition is counted twice in G-C's metrics. That hand-off is T2.03's to make;
recording it here so it is not discovered later.

*Verify:* a test asserting one event per transition with the right
`event_type`/`object_type` and a before/after payload.
