## 2. Binding constraints on every step

1. **The pipeline is not modified.** `app/services/pipeline.py` is out of lane and
   its behaviour is correct for its own purpose. Every preservation this task
   performs happens *outside* `process_batch`, on rows it has already written.
2. **`0001_baseline.py` is not modified.** The backfill introduces no table. Its
   durable state lives in `config` (where job state already lives, per
   `CLAUDE.md`) and in the report directory.
3. **No cross-fingerprint reads.** The residue predicate names exactly one
   `memory_embeddings__<slug>` partition, resolved from the single non-retired
   `embedders` row. Two non-retired rows abort the run rather than producing a
   residue count with no defined meaning.
4. **asyncpg needs `CAST` on raw-SQL params.** Every bound `uuid`, `jsonb` and
   `timestamptz` in the restore and residue statements is cast explicitly.
5. **The diff runs on every drain, not only on T1.54's.** A snapshot nobody
   diffs is an artifact, not a control (T1.51 §10.5). T1.52 ships the diff *and*
   makes it the terminal step of its own drainer, so T1.53's rehearsal and
   T1.54's real run both exercise the same code path rather than a documented
   intention.
6. **No report artifact is committed.** The snapshot and the diff carry `summary`
   and `flags` — user data. Constraint 7 of T1.51's plan applies unchanged.
7. **Every guard must be provable by breaking it.** Runbook §4 and the brief's
   ruling 7: the tests that defend the preserve/accept partition list the columns
   **literally** and never import `spec.SNAPSHOT_COLUMNS` or a
   `PRESERVED_COLUMNS` constant from the module under test. A test that imports
   the constant it exists to defend passes for any value of that constant.

## 4. Measured behaviour, 2026-07-28

Five probes. All ran against `darkmem_test_2` at `0001_baseline.py` head, on the
dev-compose Postgres. Two of the five **correct T1.51's plan**, and the
corrections change the design rather than the prose.

### Probe 1 — a scoped `DISABLE TRIGGER` preserves `updated_at` and leaves the FTS trigger alone

```
BEGIN;
ALTER TABLE memories DISABLE TRIGGER memories_touch_updated_at;
UPDATE memories SET importance = 0.9 WHERE id = '1111…';
ALTER TABLE memories ENABLE TRIGGER memories_touch_updated_at;
COMMIT;
```

Measured:

```
            step             |       updated_at       | importance
-----------------------------+------------------------+------------
 after scoped-disable update | 2020-01-02 03:04:05+00 |        0.9

     step      |          tgname           | tgenabled
---------------+---------------------------+-----------
 trigger state | memories_fts_update       | O
 trigger state | memories_touch_updated_at | O
```

The named form suppresses only `memories_touch_updated_at`. `memories_fts_update`
stays enabled (`tgenabled = 'O'`), which is why this and not
`session_replication_role = replica` is the mechanism: the latter would also
disable the FTS trigger and every FK constraint trigger on the table, and it
needs a privilege the homelab role may not have. `ALTER TABLE … DISABLE TRIGGER`
needs only table ownership.

### Probe 2 — the disable is transactional

```
BEGIN; ALTER TABLE memories DISABLE TRIGGER memories_touch_updated_at; ROLLBACK;
→ trigger after aborted disable | memories_touch_updated_at | O
```

A crash inside the restore window cannot leave the trigger disabled. This is what
makes §5.5's mechanism acceptable at all — the failure mode of "the process died
holding the trigger off" does not exist.

### Probe 3 — a plain `UPDATE` moves `updated_at` to wall clock

```
after plain update | 2026-07-28 05:31:49.554686+00
```

Baseline confirmation. The trigger works; the column is destroyed by any ordinary
write.

### Probe 4 — **`updated_at` is NOT unconditionally destroyed** (corrects T1.51 §11.2)

T1.51's plan lists `updated_at` as damaged "unconditional[ly]". Measured against
the real ORM, through savepoint A's exact assignment shape:

| Scenario | Carried `confidence` | Value SQLAlchemy loaded | `UPDATE` emitted | `updated_at` moved |
|---|---|---|---|---|
| A — all-identity assignment | `0.75` | `0.75` | **0** | **no** |
| B — identity in intent | `0.9` | `0.8999999761581421` | 1 | **yes** |
| C — identity in intent | `0.85` | `0.8500000238418579` | 1 | **yes** |
| D — identity in intent | `0.5` | `0.5` | **0** | **no** |

SQLAlchemy's unit of work emits no `UPDATE` at all when every assigned attribute
compares equal to the loaded one, so no statement reaches the trigger and
`updated_at` survives. The damage is **conditional on at least one assigned value
differing**.

### Probe 5 — but `confidence` is `real`, and that makes the "identity" case unreachable for half the value set

`memories.confidence` is `real` (float4); `importance` is `double precision`.
`estimate_confidence` returns exactly one of `{0.5, 0.75, 0.85, 0.9}`. Only `0.5`
and `0.75` are representable exactly in binary32. A stored `0.9` loads back as
`0.8999999761581421`, the estimator hands back `0.9`, SQLAlchemy sees a change,
and emits:

```
UPDATE memories SET updated_at=now(), confidence=$1::FLOAT WHERE memories.id = $2::UUID
```

The value written round-trips to the identical float4 bits. **This is a no-op
write that SQLAlchemy cannot see is a no-op, and it destroys `updated_at`.**

Two consequences that decide the design:

1. On a real corpus, `updated_at` damage is broad — but for a reason nobody
   would find by reading the code, and *not* the reason C-01 gives. A reviewer
   checking "did `confidence` change?" as a proxy for "was this row rewritten?"
   would measure **zero** on exactly the rows that lost `updated_at`.
2. The `UPDATE` statement writes `updated_at=now()` **in its own SET list**
   (the model carries `onupdate=func.now()` at `app/models/memory.py:53`, in
   addition to the `memories_touch_updated_at` trigger). So `updated_at` cannot
   be preserved by suppressing the trigger during `process_batch` — the ORM puts
   `now()` there explicitly. Restore-after (§5.5) is the only mechanism that
   works, and this is the evidence for it.

### Probe 5b — the empty-classifier null, reproduced

Savepoint A's exact shape with `{"hall": "", "summary": "", "emotions": [], "flags": []}`:

```
UPDATE memories SET updated_at=now(), classified_type=$1::VARCHAR, summary=$2::VARCHAR,
       emotions=$3::JSONB, flags=$4::JSONB WHERE memories.id = $5::UUID
enrichment after: classified_type=None summary=None emotions=None flags=None
```

Carried `('decision', 'carried summary', ['calm'], ['verified'])` → all four
NULL. The review's `… .get(x) or None` finding is confirmed exactly as stated.

## 5. The preserve-or-accept decision — the centre of this task

The brief requires this stated explicitly, per column, with a reason for each.
The governing test is not "does the column change" but **"does the column hold
user intent that nothing can regenerate?"** Doc 19 §4 draws the same line: a
memory row is unrecoverable user data; a derivation is regenerable and a migrated
copy of an old derivation would be *wrong* under the target.

The decisive evidence is which columns are writable through a door. Read from
`app/schemas/memory.py`:

- `MemoryCreate` exposes `memory_type` and `importance`. It has **no**
  `confidence`, `classified_type`, `summary`, `emotions` or `flags` field.
- `MemoryUpdate` exposes `content`, `tags`, `memory_type`, `importance`,
  `metadata`, `expires_at`, `is_archived`, `project`, `status`. Nothing else.

So `memory_type` and `importance` carry user intent; the other six do not.

### 5.1 The table

| Column | Decision | Reason |
|---|---|---|
| `updated_at` | **PRESERVE**, except on rows whose `status`/`superseded_by` changed | User-visible "last edited" history, unrecoverable, and destroyed by a write that changes nothing on disk (probe 5). Re-deriving machine columns is not a user edit, so the honest value after the backfill is the carried one. The carve-out is §5.6: a supersession flip *is* a user-visible state change, and freezing `updated_at` across it would make the row claim it was last touched in 2020 while it had just vanished from the active view. |
| `importance` | **PRESERVE** | Writable at create *and* update — explicit user intent. Overwritten by the extractor's number whenever extraction emits one. T2.30 later activates it as a ranking arm; its history would be gone before anyone measured it. |
| `memory_type` | **PRESERVE**, by invocation | Writable at create and update. Preserved by passing the carried value as the entry's `memory_type`, which makes `normalize_memory_type(memory_type or extracted_type)` an identity for any of the nine `MEMORY_TYPES`. See §5.2 for the residual. |
| `confidence` | **ACCEPT the loss** | Unreachable from every door; a pure function of `(content, memory_type)`. Content carries verbatim and `memory_type` is preserved, so the recomputed value is the *correct* value under the target's estimator and any difference is a source-side estimator difference we want corrected. Reported, never assumed zero. |
| `classified_type` | **ACCEPT the overwrite, REFUSE the null** | Doc 19 §4 puts LLM enrichment squarely in "rebuild the derived state" — a value produced by the old model under the old vocabulary is wrong under the target. But an *empty* classifier result is not a rebuild; it is a deletion with no replacement (probe 5b), and it is strictly worse than keeping the old derivation. |
| `summary` | **ACCEPT the overwrite, REFUSE the null** | As above. |
| `emotions` | **ACCEPT the overwrite, REFUSE the null** | As above. |
| `flags` | **ACCEPT the overwrite, REFUSE the null** | As above. |
| `status` | **ACCEPT, and REPORT per row** | The re-extraction runs `detect_supersessions`, and the rebuilt graph may emit a `REPLACES`-family relation the old extractor missed. A flip inside the 90-day window is *legitimate new derivation*. Restoring it would suppress a correct result. |
| `superseded_by` | **ACCEPT, and REPORT per row** | Same, and it must move atomically with `status` or `chk_superseded_has_pointer` aborts. Restoring one without the other is how this constraint gets violated. |
| `id` | n/a | The snapshot join key. |

Not in the snapshot but in the same family:

| Column | Decision | Reason |
|---|---|---|
| `technologies` | **REBUILD, and assert the transition** | T1.51 asserts it is empty on 100% of carried rows on the way in. T1.52 asserts it is non-empty on exactly the rows whose extraction produced a `TECH_TYPES` entity. This is the cover for T1.51 §11.3's "empty `technologies` nobody notices". |
| `search_vector` | untouched | Already populated by the FTS trigger at load, and probe 1 confirms the scoped disable leaves that trigger enabled. |
| `origin_key` | untouched, asserted still NULL | The backfill must not manufacture one. T1.11's rule applied to history. |

### 5.2 The residual on `memory_type`, and why it is accepted

Passing the carried type makes the assignment an identity for in-vocabulary
values, and T1.51's pre-flight already aborts the whole cutover on any
out-of-vocabulary non-NULL value, so an operator has already seen the histogram.
The residual is **rows whose carried `memory_type` is NULL**: `memory_type or
extracted_type` falls through to the extractor's own label, and the row gains a
classification it never had.

This is **accepted, and counted**. A NULL `memory_type` means "unclassified"; the
target pipeline classifies every ingest, so assigning one is the system doing its
job. Nothing is destroyed because there was nothing there. But the count is
reported (`memory_type_gained: N`) because it is also the operator's independent
check that the pre-flight histogram and the post-backfill state agree.

### 5.3 The asymmetry on the four enrichment columns, argued rather than assumed

Retaining a carried `flags = ['verified']` when the new classifier returns
nothing preserves a *stale* assertion. That is a real cost and I am not pretending
otherwise. Three reasons the retain still wins:

1. **The columns feed nothing load-bearing.** Grepped across `app/services/` and
   `app/repositories/` at `2e16fe2`: the only non-pipeline reference to
   `classified_type` is inside `classification_llm.py`, which *produces* it.
   `Memory.summary`, `Memory.emotions` and `Memory.flags` have no consumer in any
   ranking, filtering, retrieval or supersession path. They are display surfaces.
2. **A stale value is recoverable; a NULL is not.** Re-running the backfill over
   a retained value replaces it. Re-running over a NULL cannot restore what was
   there.
3. **The empty result is ambiguous at the column.** "The classifier found no
   flags" and "the classifier returned an empty field because the call degraded"
   are indistinguishable from `flags IS NULL` alone. The `or None` in savepoint A
   resolves that ambiguity by accident, in the destructive direction. Recording
   the decision is the point; the direction is the lesser question.

If a reviewer disagrees on direction, the fix is one line in the restore pass and
the tests in §8 pin the chosen direction literally, so the disagreement is
visible rather than latent.

### 5.4 Why the pipeline is not changed

Making savepoint A coalesce instead of overwrite would change ordinary ingest:
today, re-ingesting a memory whose classifier legitimately clears its summary
*does* clear the column, and that is right. Encoding cutover semantics in the hot
path would make a one-time migration's requirements permanent, and it is out of
lane besides. The compensation belongs to the caller that has the "before" — and
T1.52 is the only caller that ever will.

### 5.5 The mechanism: a restore pass, per batch, inside one transaction

For each drained batch, immediately after `process_batch` returns and before the
next batch is claimed:

```
BEGIN;
ALTER TABLE memories DISABLE TRIGGER memories_touch_updated_at;

UPDATE memories m SET
    importance      = s.importance,
    classified_type = COALESCE(m.classified_type, s.classified_type),
    summary         = COALESCE(m.summary,         s.summary),
    emotions        = COALESCE(m.emotions,        s.emotions),
    flags           = COALESCE(m.flags,           s.flags),
    updated_at      = s.updated_at            -- assigned LAST, and see below
FROM (…snapshot rows for this batch, unnest with explicit CASTs…) s
WHERE m.id = s.id;

ALTER TABLE memories ENABLE TRIGGER memories_touch_updated_at;
COMMIT;
```

Four things about this statement are load-bearing:

- **`updated_at` is set explicitly**, not merely left alone. Probe 5 shows the
  ORM writes `now()` into its own SET list, so the trigger is only half the
  problem; the restore has to overwrite the wall-clock value the pipeline already
  committed. The `DISABLE TRIGGER` is what stops *this* statement from bumping it
  again.
- **`COALESCE(m.col, s.col)`**, not `s.col`. A non-NULL post-backfill value is
  the new derivation and is kept. Only a NULL is refilled. This is §5.1's
  "accept the overwrite, refuse the null", expressed in one operator.
- **`importance = s.importance` unconditionally**, because there is no ambiguity:
  the carried value is user intent and the extractor's is not.
- **`status` and `superseded_by` are absent from the SET list.** They are read
  for the report and never written.

Per-batch rather than once at the end, because a drain interrupted after batch 40
of 200 must leave batches 1–40 already restored. A single restore at the end
makes the whole preservation contingent on the run finishing, which is exactly
the property "resumable after interruption" exists to deny.

**Batch-boundary caveat to write into the code as the one comment this task
needs:** the restore runs after `process_batch` has committed, so between the two
there is a window in which the rows hold wall-clock `updated_at`. That window is
bounded by one batch and is closed by the next resume, because the residue
predicate (§6.1) re-drains any memory that is not both embedded and
failure-free — and the restore is idempotent under `COALESCE` plus an unchanged
snapshot. Re-running the restore over an already-restored batch is a no-op that
writes the same values.

### 5.6 The cross-batch write, which makes a per-batch restore insufficient on its own

Read at `app/services/supersession.py:192`, `detect_supersessions` ends with:

```
await session.execute(
    update(Memory).where(Memory.id.in_(old_ids))
                  .values(status="superseded", superseded_by=new_memory_id)
)
```

The rows it writes are **not** the memory being processed — they are *other*
memories, any of which the drain may have finished and restored several batches
earlier. That UPDATE fires `memories_touch_updated_at` (and SQLAlchemy Core's
`onupdate`), so a batch-40 memory can move a batch-3 memory's `updated_at` back
to wall clock long after batch 3's restore ran.

Two consequences the implementer must not discover the hard way:

1. **A final restore sweep over the whole carried set is required after the drain
   reaches fixpoint**, in addition to the per-batch restore. The per-batch pass
   exists for resumability (§5.5); the terminal sweep exists for this. Neither
   replaces the other: drop the per-batch pass and an interrupted run leaves
   everything unrestored; drop the sweep and every supersession victim keeps a
   wall-clock `updated_at`.
2. **The sweep must skip rows whose `status`/`superseded_by` differ from the
   snapshot.** Those rows really did change, visibly, and restoring their
   `updated_at` would assert they did not. They go to the diff's "new derivation"
   bucket carrying both the lineage change and the moved timestamp, as one
   reported fact rather than two.

Neither T1.51's plan nor its review names this path. It is the reason §9.1 puts
the restore's *placement*, not its SQL, at the top of the falsification list.

**What was checked and is safe.** The crossref pass (`pipeline.py:769–786`) runs
after `session.commit()` but still inside the per-memory coroutine that
`process_batch` awaits, and `store_crossrefs` (`vector.py:473`) touches only
`memory_crossrefs` — never `memories`. `_record_batch_outcomes` writes only
`pipeline_failures`. So "after `process_batch` returns" is late enough for
everything except supersession, and supersession is handled by the sweep.

## 6. The drain: resumability without a new table

### 6.1 The residue predicate, which is the resume state

There is no cursor and no lease. "Not yet backfilled" is computed from the
database, as the **union** of:

```
(a)  memories with no row in memory_embeddings__<slug> for the single
     non-retired fingerprint
(b)  memories with an unresolved pipeline_failures row where
     pipeline_name = 'memory_ingest'
```

(a) covers everything that never reached savepoint A. (b) covers savepoint-B
failures — a memory whose vector landed but whose graph write failed has an
embedding row and would be invisible to (a) alone. `resolve` is a no-op when no
row exists (`pipeline_failures.py:223`), so a fully-successful memory matches
neither clause and is never re-drained.

Why this and not a cursor: a cursor is a second source of truth about what is
done, and a cursor that disagrees with the database is precisely the "reported
complete while partial" failure this task must prevent. A predicate cannot
disagree with the database because it *is* the database.

Bounds, so a permanently-failing row cannot spin: the drain runs passes until the
residue reaches a **fixpoint** — a pass that drains rows and leaves the residue
count unchanged stops, and the stuck set is reported by id. `pipeline_failures`
already carries `attempts`; the drainer does not add a second attempt counter.

Fingerprint resolution aborts unless `SELECT count(*) FROM embedders WHERE
retired_at IS NULL` is exactly 1. Zero means nothing has embedded yet, which is
the legitimate cold-start case and makes the residue "all carried rows"; two or
more means the embedder rotated mid-drain and a residue count spanning
partitions has no defined meaning (`CLAUDE.md`: no cross-fingerprint joins).

### 6.2 Why not `memory_buffer` / `buffer_flush`

Read and rejected. `buffer_flush` **materialises** a `memories` row from a
`memory_buffer` capture (`buffer_flush.py:590`) — it is the other half of a
capture that has not landed yet. Carried memories already exist as `memories`
rows with load-bearing `created_at`, `id` and lineage. Routing them through the
buffer would either mint duplicates or require a "row already exists" special
case inside the buffer's claim path, which is a Tier-A correctness surface this
task has no business touching.

### 6.3 Where it runs, and the invariant-15 tension

Doc 19 invariant 15 says "the backfill and every new maintenance arm are Tier-C
jobs **under the one registry**". T1.52's own Done-when says only "off the hot
path and resumable" — it does not say `JobRegistry`, unlike T1.13, which says so
explicitly.

**Decision: an operator-run CLI at `backend/scripts/cutover/backfill.py`, not a
registered job.** A permanently-registered cron job for a one-time migration
would keep waking forever after the cutover, and registering it means editing
`app/main.py`'s nine-job list, which four live sibling lanes also touch. "Off the
hot path" is satisfied — the drain is in no request path and runs at the
pipeline's own `pipeline_concurrency`.

This is a **Tier-1 amendment** (a doc-level reading, no behaviour at stake) and
§11 records it for the controller. It is stated rather than quietly resolved
because doc 19's wording and the task's wording genuinely differ.

## 7. Verification: three legs, and one of them is the only real one

### 7.1 Leg 1 — carried-row counts match the dump

`SELECT count(*)` per carried table against the counts T1.51's
`cutover-verification-<stamp>.json` already recorded, plus the invariants the
backfill must not break:

```
memories total                        == transform's staged count
memories with origin_key IS NOT NULL  == 0
memories with search_vector IS NULL   == 0
memories with status='superseded' AND superseded_by IS NULL == 0
tags / memory_tags / conversations / messages counts unchanged
```

This leg is real but **weak**, and the plan says so: it is green in the failure
mode this whole task is about.

### 7.2 Leg 2 — the `pipeline_failures` residue is bounded and triaged

Report, per `failed_step`, the unresolved `memory_ingest` rows with their
`error_message` and `attempts`, and exit non-zero if the residue exceeds an
operator-supplied `--max-failures`. **No default that permits silence**: the flag
is required, so "bounded" is a number the operator wrote down rather than one the
tool chose.

`pipeline_failures` is in T1.51's DROPPED bucket, so the target starts empty and
the residue is entirely this run's. That is what makes the count interpretable.

### 7.3 Leg 3 — the snapshot diff, which is the only leg that can see the real failure

This is the leg the brief demands and the reason the other two are not enough.
`backfill.py` reads the `cutover-snapshot-<stamp>.jsonl` T1.51 wrote and, for
every memory, compares all eleven columns to the live row. Output:
`cutover-backfill-diff-<stamp>.json`, plus a human-readable summary on stdout.

The diff classifies every difference into exactly one of three buckets, and the
run **fails** on the first:

| Bucket | Columns | Expected count | On non-zero |
|---|---|---|---|
| **Violation** | `updated_at`, `importance`, `memory_type` (for non-NULL carried values), and any of the four enrichment columns that went non-NULL → NULL | **0** | exit non-zero, name the ids |
| **Expected re-derivation** | `confidence`; the four enrichment columns overwritten non-NULL → non-NULL; `memory_type` on rows whose carried value was NULL | any | reported with counts, never asserted zero |
| **New derivation** | `status`, `superseded_by`, and `updated_at` **on those same rows only** | any | reported per row with the id, so a reviewer diffing the dump is answered rather than surprised. The moved timestamp travels with the lineage change as one fact (§5.6), never as a separate unexplained delta |

The "expected" bucket is reported with real numbers rather than swallowed,
because a `confidence` diff of zero would itself be suspicious — probe 5 predicts
the on-disk value is often unchanged while the row *was* rewritten, and a
reviewer needs both numbers to see that.

**Why this belongs to T1.52 and not to T1.54.** T1.54's Done-when now carries the
real-corpus diff (C-11), but a Done-when box is an instruction to a human. If the
diff is a tool that runs as the drainer's terminal step, then T1.53's rehearsal
and T1.54's real run both execute it because they ran the drainer, not because
someone remembered. That is the difference between a control and an artifact.

### 7.4 Leg 4 — the F1 evidence, and what it is not

Per the task text and doc 19 §4: an extraction-bench run on the target
configuration against the gold set, holding the T0.05 tolerance.

```
cd backend
cp -r /root/repositories/darkmem/backend/scripts/extraction_bench/.cache \
      <worktree>/backend/scripts/extraction_bench/
timeout 1800 .venv/bin/python scripts/extraction_bench/run_bench.py --algo-only
```

**There is no F1 number against the carried corpus** — the homelab data carries
no gold annotations, so that figure is not computable. Saying so is part of the
deliverable, because "the bench is green" is the single most misleading piece of
evidence this task produces: it is green *by construction* while every carried
column is being overwritten.

If `--algo-only` wants a live call, **stop and report** (GLOBAL §4): the cache key
changed, which means the system prompt moved, which is T1.17's and nobody else's.

## 8. The steps

Seven steps. Each ends at a commit; each names what proves it.

### Step 1 — The residue predicate and the fingerprint guard

New `backend/scripts/cutover/backfill.py` with, so far, only: fingerprint
resolution (abort unless exactly one non-retired row, cold start = all rows) and
`outstanding(target) -> list[UUID]` implementing §6.1's union.

*Proves:* `tests/test_cutover_backfill.py` — a memory with an embedding row and
no failure row is not outstanding; the same memory with an unresolved
`memory_ingest` failure **is**; a memory with neither is; two non-retired
`embedders` rows abort with a message naming both fingerprints.

### Step 2 — The entry builder, with the carried `memory_type`

Build `process_batch` entries from `Memory` rows, mirroring
`analytics.py:_reprocess_batch`: `memory_id`, `content`, `source`, `tags`,
`memory_type` (the **carried** value), `created_at`.

*Proves:* a test asserting the built entry's `memory_type` equals the row's, with
the assertion written as a literal (`assert entry["memory_type"] == "decision"`)
rather than `== m.memory_type`, which would pass if the builder dropped the field
and the row happened to be NULL.

### Step 3 — The restore pass

§5.5's statement, per batch, in its own transaction with the scoped
`DISABLE TRIGGER`. All params cast (`CAST(:ids AS uuid[])`,
`CAST(:emotions AS jsonb[])`, `CAST(:updated_at AS timestamptz[])`).

*Proves:*
- `updated_at` survives a batch whose `confidence` moved from `0.9` (probe 5's
  case, seeded literally as `0.9` so the float4 round-trip is exercised).
- `importance` is restored over an extractor-supplied value.
- A carried `summary` survives an empty classifier result.
- A post-backfill non-NULL `summary` is **kept**, not reverted to the carried one
  — the `COALESCE` direction, asserted in both directions.
- Re-running the restore over an already-restored batch changes nothing.
- The trigger is back at `tgenabled='O'` afterwards, read from `pg_trigger`.
- **The terminal sweep (§5.6).** A memory restored in an early batch, then
  superseded by a later one, ends with its carried `updated_at` only if the sweep
  runs — so the test drives two batches where the second supersedes a member of
  the first, and asserts the first row's `updated_at` after the sweep. Written
  without the sweep, that assertion fails; that is the point of writing it.
- **The sweep's carve-out.** A row whose `status` changed is left with its
  wall-clock `updated_at`, asserted positively (not merely "not restored").

### Step 4 — The drain loop, bounded and resumable

Claim `outstanding()` in batches of `embedding_batch_size`, call `process_batch`,
run Step 3's per-batch restore, recompute the residue, repeat to fixpoint, then
run Step 3's terminal sweep once. Persist
`config['job:cutover_backfill']` after each batch with the run id, timestamps,
and — critically — a `status` field **computed from the residue query**, never
from a counter.

*Proves:* a drain killed mid-run (simulated by raising inside batch 2 of 3)
leaves batches already drained restored, and a second invocation drains exactly
the remainder and no more. A row that fails every attempt appears in the stuck
set and does not loop.

### Step 5 — The three verification legs and the diff

§7.1–7.3, as `verify_backfill(target, snapshot_path, max_failures) -> report`,
called as the drainer's terminal step and also runnable standalone
(`--verify-only`) so T1.53 and T1.54 can re-run it against a database they did
not drain.

*Proves:*
- The three-bucket classification, with a fixture whose rows exercise one of each.
- **The violation bucket is non-zero when the restore is removed.** This is the
  mutation proof and the single most important test in the task: comment out the
  restore call, run the drain, assert the diff exits non-zero naming
  `updated_at` and `importance`. A diff that stays green with the restore
  disabled is a diff that proves nothing.
- `--max-failures` is required; omitting it is an argparse error, asserted.

### Step 6 — "Visibly partial", asserted as a property

The run's terminal output and the persisted `config` row say `INCOMPLETE` with
the residue count whenever `outstanding()` is non-empty, on **every** exit path
including the exception path, and the process exit code is non-zero.

*Proves:* three tests — clean completion says `COMPLETE` and exits 0; a run with
one permanently-stuck row says `INCOMPLETE (1 outstanding)` and exits non-zero;
a run that raises mid-drain still writes `INCOMPLETE` before propagating. The
third is the one that matters, because "reported complete after a crash" is the
shape of the failure.

### Step 7 — Floor, bench, amendment log, commit

Backend floor, benchlib suite, the `--algo-only` bench with the warm cache
copied in, the amendment rows from §11 appended to the epic file's log (own rows
only, no reflow), and the commits.

## 9. Falsification pass

### 9.1 The step most likely to be wrong: Step 3, the restore pass

Not because the SQL is hard, but because **its correctness depends on when it
runs relative to writes it does not issue**. §5.6 already found one such write
that invalidates the obvious design: supersession updates *other* memories'
rows, so a per-batch restore is silently undone by a later batch, and the fix is
a terminal sweep the naive implementation does not have.

The reason this is still the likeliest step to be wrong is that §5.6 is a
*discovered* instance of a general hazard, and I have no proof it is the only
one. Any future write to `memories` from anywhere inside the drain — a job that
boots alongside it, a `technologies` recompute that grows a second caller, a
later task adding an enrichment arm — reopens it, and the symptom is a single
column on a subset of rows, which reads as a flaky test.

**Evidence that would show it:** Step 5's mutation proof run *with* the restore
and the sweep enabled. A non-zero violation bucket on a clean run means an
unaccounted writer, and the correct response is to find it rather than to move
the sweep later and re-run until green. The concrete check is to log every
`UPDATE memories` statement during a full test drain (the `before_cursor_execute`
listener used for probe 4 does exactly this) and confirm the set of writers is
`{savepoint A, detect_supersessions, the restore itself}` and nothing else.

Two writers were checked and cleared while writing this plan: the crossref pass
(`pipeline.py:769`) touches only `memory_crossrefs`, and `_record_batch_outcomes`
touches only `pipeline_failures`.

Runner-up: §6.1's residue predicate. Clause (a) names one partition, and if the
implementer resolves the fingerprint **once at start-up** rather than per pass, a
mid-drain embedder rotation silently makes the residue query read the wrong
table — reporting `COMPLETE` against a partition nothing is being written to any
more.

### 9.2 The silent failure mode I consider most dangerous

Not the eight-column overwrite — that one is now loud, because §7.3 fails the run
on it. The dangerous one is **the restore pass running correctly against the
wrong snapshot**.

`write_snapshot` names its file `cutover-snapshot-<UTC stamp>.jsonl` and T1.53's
rehearsal will produce several of them in the same report directory across
repeated runs. If the drainer globs the directory and takes the newest, or the
operator passes a path by hand, then a restore driven by a *rehearsal* snapshot
over the *real* corpus writes plausible-looking values from a different database
into `importance`, `updated_at` and the four enrichment columns — and every
check in §7 passes, because the diff compares against the same wrong snapshot it
restored from. Row counts match. The residue is empty. The violation bucket is
zero *because* the two halves agree with each other.

It is silent in the strongest sense available: the control and the corrective
action read from the same file, so a wrong file makes them agree.

**The cover, which Step 5 must implement and not merely mention:** the snapshot
path is a required argument with no globbing and no default, and before the first
batch the drainer asserts that the snapshot's id set is **exactly** the target's
`memories` id set — not a subset, not a superset, equal — and aborts naming the
symmetric difference otherwise. A snapshot from another run of the same corpus
would pass that check only if the corpora are genuinely identical, in which case
the values are equally valid. A rehearsal snapshot over the real corpus fails it
on the first row.

### 9.3 Third: the diff that cannot fail

Per the brief's ruling 7 and the five dead guards found this session — if
`verify_backfill` compares the snapshot to a live read that happens to be sourced
from the same JSONL, or if the test fixture's snapshot is generated *by* the
backfill rather than *before* it, the diff is structurally incapable of reporting
a violation. Step 5's mutation proof is the only thing that distinguishes a
working diff from a decorative one, which is why it is written as a required
step and not as a nice-to-have.

## 10. Size call

**One `L`, and it should stay `L`.**

The reasoning, in both directions as the brief asks. Arguments for `M`: the
drainer is one module, there is no schema change, the pipeline is untouched, and
`analytics.py:_reprocess_batch` already shows the invocation shape.

Arguments for `L`, which win:

1. **Four distinct mechanisms under one name** — the residue predicate, the
   restore pass, the drain loop with its fixpoint bound, and the three-leg
   verification with its diff. Runbook §3's `L` definition is exactly "several
   mechanisms under one name".
2. **The restore pass is invariant-bearing surgery on committed rows** using a
   trigger-suppression window. It needs the probe evidence in §4 before a line of
   it is written, and it needs mutation proof after.
3. **The verification is the deliverable, not the trimming.** Three legs, a
   three-bucket diff, and a mutation proof that the diff can fail. That is more
   test design than most `M` tasks have implementation.
4. It is the last gate before irrecoverable user data moves. `risks-and-lanes.md`
   calls T1.51–T1.54 the only unrecoverable step in the plan.

**Not larger than one `L`, and no split proposed.** A split along
drain / verify would put the restore pass on one side and the diff that proves it
worked on the other, and the two are only meaningful together — the mutation
proof in Step 5 needs Step 3's code to disable. Splitting would produce two
tasks each of which passes its own tests while the pair is broken.
