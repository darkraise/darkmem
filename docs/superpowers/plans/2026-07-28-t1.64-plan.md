## 1. What T1.64 is, and the four things it is not

It is: (a) a new, disposable-database API e2e harness with one documented entry point;
(b) a disposition call — port, replace, or retire — on `docs/e2e/scripts/`; (c) getting
the five E1-satisfiable honesty specs to actually run rather than silently skip; (d) the
`no-restricted-imports` warn→error flip, corrected against what is actually true today;
(e) wiring `scripts/gate.sh --full` to invoke the result.

**It is not** the other three honesty specs. `veto-absolute` needs the contradiction
veto (E2/T2.04), `human-only-confirmed` needs ratification (E2/T2.05), and
`withheld-not-grounded` needs grounded answering (EH1/T1.09) — none of that code exists
on this branch, and per the runbook's entry-gate rule those epics are not startable
until E1 clears G-B. The task's own Done-when already narrows to five; this plan does
not widen it back to eight.

**It is not F2–F11's flow coverage.** `docs/planning/e2e-test-plan.md`'s coverage table
assigns each flow a distinct **owning task** (F2→T1.26, F5→T1.37, F6→T2.38, F7→T3.08,
F8→TH1.16, F10→T3.12, F11→T1.38) — several of which (T2.38, T3.08, TH1.16, T3.12) are
epics ahead of E1 and not startable yet. T1.64 builds the harness those tasks populate;
it does not populate it on their behalf. What T1.64 does add, and must, is **one** flow
test proving the harness is not vaporware (§2.4) — F1, whose owning feature (capture +
`buffer_flush`) already shipped earlier in E1.

**It is not a rewrite of T1.58's Ruling 4.** `seedAdminPassword()`'s hardcoded target —
the shared dev stack's `darkmem` database, on purpose, never overridable by env — stays
exactly as T1.58 left it, for a reason stated there and not revisited here: a human
operator validating a real, persistent, wizard-configured deployment is a different
scenario from a disposable per-run database, and the two should not be conflated onto
one flag. What changes is that **a second, independent path now exists** for anyone who
does not have that persistent stack — see §2.2. Nobody's file is edited to make this
true; a new script is added beside it.

**It is not the frontend demo-import sweep.** 81 of the 90 current violations (§5) are
real, unfinished feature work spread across Chat, Memory Graph, Code, Knowledge,

tier, no business doing in one pass across six unrelated features. §5 says exactly what

## 2. Decision 1 — the database posture (the load-bearing one)

### 2.1 What the suite itself uses

**Decision: the API e2e suite lives at `backend/scripts/e2e/`, targets `darkmem_test`
(the same database pytest uses, per `docs/planning/e2e-test-plan.md`'s own three-database
table: "`darkmem_test` … Used by: Backend unit + API e2e" — this is not a new
allocation, it is the doc's stated intent, unbuilt until now), and gets there by
**booting its own server**, not by assuming one is already running.**

Reused, not reinvented — `backend/scripts/benchlib/bench_db.py` already has the exact
shape needed (read in full at `2e16fe2`… confirmed unchanged at `4bb0eeb`): override
`DATABASE_URL` before any `app.*` import, `DROP SCHEMA public CASCADE` +
`CREATE SCHEMA public`, then `alembic upgrade head` in a subprocess so Alembic's own
`asyncio.run` never collides with the caller's event loop. `backend/scripts/e2e/e2e_db.py`
is the same three functions against `TEST_DATABASE_URL` instead of `BENCH_DATABASE_URL`.

New, because nothing existing does it: `backend/scripts/e2e/stack.py`, which

1. calls `e2e_db.reset()`,
2. spawns `uvicorn app.main:app --host 0.0.0.0 --port <port>` as a subprocess with
   `DATABASE_URL` pointed at the just-reset database, in its own session
   (`start_new_session=True`, mirroring `gate.sh`'s own `setsid` discipline) so it can be
   torn down as a group,
3. polls `GET /health` until 200 or a bounded timeout, then
4. seeds the admin account through the **real front door**:
   `POST /api/v1/setup` with `{"password": "<generated>"}` and nothing else. Read at
   `backend/app/api/routes/setup.py:308-344`: *"Password is the only required block"* —
   `body.llm` is `Optional`, guarded by `if body.llm is not None:`. A fresh
   `darkmem_test` has no `admin_password_hash` row (`e2e_db.reset()` just dropped the
   schema), so `require_uninitialized` passes and this call succeeds with no LLM
   configuration at all. This is materially simpler than
   `frontend/tests/helpers/seed-admin.ts`'s raw `UPDATE config …` — that script exists
   only because the shared dev stack is **already** initialized with an unknown
   password, which is not this database's situation.
5. returns `(process, base_url, password)` to the caller, and tears the process group
   down on `__exit__` / a signal handler, matching `gate.sh`'s `cleanup()` trap.

`backend/scripts/e2e/run_e2e.py` is **the one documented entry point**: it calls
`stack.boot()`, runs `pytest backend/scripts/e2e/tests -q` with `E2E_BASE_URL` and
`E2E_ADMIN_PASSWORD` set from the booted stack, tears the stack down in a `finally`, and
exits with pytest's return code. `backend/scripts/e2e/README.md` states this in one
paragraph, matching `docs/e2e/README.md`'s "Quick Start" shape but truthfully: `python
scripts/e2e/run_e2e.py` and nothing else needs to be true first — no fresh deployment, no
pre-set password, no already-running server. **This is the concrete answer to "what
happens on a machine where none of that is set up": the suite performs the drop, the
migrate, the boot and the seed itself, every run, so "nothing is set up" is the normal
starting condition, not a failure mode.**

### 2.2 What fixes the live Playwright failure — REVISED (Blocking B1)

**The original §2.2 was wrong, and the review is right about why.**
`seed-admin.ts` hardcodes `database="darkmem"` (T1.58 Ruling 4, "never
overridable by env" — read again this revision, unchanged at
`a891aad`). `auth.spec.ts` calls `seedAdminPassword()` unconditionally
in `beforeAll` (line 21, re-read this revision — unchanged). The
disposable stack this plan's §2.1 boots serves `darkmem_test`
(`TEST_DATABASE_URL`), never `darkmem`. So the seed write **never
reaches the database the booted stack reads**, full stop — there is no
sense in which it is "a no-op write to the same value," because it is
not a write to the *stack's* database at all. On this machine `darkmem`
has zero relations (re-confirmed this revision:
`docker exec darkmem-postgres-1 psql -U darkmem -d darkmem -c "\dt"` →
"Did not find any relations"), so the original claim was not merely
unverified, it was falsified by the same source excerpt this plan's §1
quotes three paragraphs earlier. Withdrawn.

`seedAdminPassword()`'s `UPDATE` statement has its own `affected == 0` guard, which is
exactly what fires against an uninitialized `darkmem` — zero tables means zero rows
affected, and the process exits 1 inside `beforeAll` ("stack not initialized — run setup
first"). That is the failure the original dispatch named and this revision's B1 finding
reproduces exactly, not merely reports secondhand.

**This is not a defect in T1.58's reasoning** (§1) — it is a machine that never ran
`docker compose up` and `alembic upgrade head` against `darkmem`, which the shared-stack
design was never going to survive on its own. But now that §2.1 has built a
boot-a-disposable-stack mechanism, the honest move is to make it available to Playwright
too, as an **alternative**, not a replacement:

**Decision: `stack.py` gains a `--keep-running` mode** (`python -m
backend.scripts.e2e.stack --keep-running --port 8000 --password <pw>`), which does
steps 1–4 of §2.1 and then blocks instead of tearing down. `vite.config.ts`'s dev proxy
already hardcodes `http://localhost:8000` (`frontend/vite.config.ts:36-38`) — measured,
unchanged — so no frontend config edits are needed; the disposable stack binds the same
port the proxy already expects. This part of the original design survives the review
unchanged.

**What changes, per B1: the specs must not call `seedAdminPassword()` against a
disposable stack, and this is resolved at the call site, not at `seed-admin.ts`.**
The reviewer's own framing is the ruling this revision follows: *"Ruling 4 governs the
helper's target, not whether a spec calls it"* — so a spec declining to seed when an
env var declares the stack disposable is within Ruling 4's bounds, not a rewrite of it.
`seed-admin.ts` is **not edited**; its hardcoded `darkmem` target, and the reason for
it (a human-operated, real, wizard-configured deployment — §2.3), stand exactly as
T1.58 left them.

**Decision: `stack.py --keep-running` exports `E2E_DISPOSABLE_STACK=1` into the
environment of whatever it launches or is launched alongside**, and `auth.spec.ts` /
`code-real-mode.spec.ts` gain a one-line guard at the top of `beforeAll`:

```ts
test.beforeAll(() => {
  if (!PASSWORD) { throw new Error(/* unchanged */) }
  if (!process.env.E2E_DISPOSABLE_STACK) {
    seedAdminPassword()
  }
})
```

Against a **disposable** stack (`E2E_DISPOSABLE_STACK=1`), the guard skips the call
entirely — the stack was already seeded with `PASSWORD` through the real
`POST /api/v1/setup` door at boot (§2.1 step 4), so there is nothing left to overwrite,
and no call ever reaches `seed-admin.ts`'s hardcoded `darkmem` target to mismatch
against. Against the **shared, persistent** dev stack (the env var unset, T1.58's
original use case), both specs behave exactly as they do today: `seedAdminPassword()`
runs, targets `darkmem`, and overwrites that stack's real password — unchanged,
untouched, still Ruling 4's scenario.

**The concrete recipe, documented in `backend/scripts/e2e/README.md` and referenced
from `docs/planning/e2e-test-plan.md`'s "two things must be true" paragraph:**

```
# terminal 1 — disposable, migrated, seeded backend on :8000
python -m backend.scripts.e2e.stack --keep-running --port 8000 --password <pw>
# terminal 2 — E2E_DISPOSABLE_STACK=1 is exported by stack.py into a
# .env-e2e file it writes on boot and this line sources, so a human
# does not have to remember to set it by hand
source backend/scripts/e2e/.env-e2e && E2E_ADMIN_PASSWORD=<pw> VITE_DEMO=0 \
    npx playwright test tests/auth.spec.ts tests/code-real-mode.spec.ts
```

**`scripts/gate.sh --full`'s own "playwright e2e" step adopts this**, closing the loop so
the fix is not merely documented but exercised on every `--full` run — see §6.2. This is
the one place this plan **does** touch `gate.sh`, and it is additive (one boot before the
existing `npm run test:e2e` call, one teardown after), not a rewrite of T1.58's or T0.16's
work.

**This is a Tier 2 change beyond what the original plan proposed** — a new env-var
contract on two existing spec files, not merely new files beside them — and per runbook
§5 it is surfaced here for controller re-clearance before Step 3 of §7 executes, not
silently substituted. See §10, Finding B1.

### 2.3 Why not repoint the shared stack instead

Considered and rejected: migrating `darkmem` in place (`alembic upgrade head` against the
real database) would make `auth.spec.ts` pass without any new code. Rejected because
`darkmem` is the one database CLAUDE.md says nothing automated ever touches, and a
Playwright helper migrating it is exactly the kind of automation that rule exists to
forbid — the *value* of the shared-stack path is that it is a human-operated, real
deployment, and migrating it from a test helper erases that distinction the same run it
was meant to protect.

### 2.4 The one flow test that proves the harness is not empty — REVISED (Important I1)

A suite with zero tests satisfies "`gate.sh --full` invokes it" while proving nothing —
the exact "green but empty" class this session has already found five times. F1
(capture, doc 17 §9 / e2e-test-plan.md coverage table) is the one flow whose owning
feature has already shipped in E1 (`memory_buffer` + `buffer_flush`, referenced
throughout `CLAUDE.md`'s domain model), so it is the one flow T1.64 can honestly write
without waiting on a task this task doesn't depend on.

**The original design here was the single worst defect the review found, and the one
most likely to survive an honest execution undetected.** As originally written, this
was *one* test with a module-level `pytest.skip("no live embedder configured …")`
gating the whole file before any assertion ran. On this machine — the only one that
runs the gate — that skip always fires, `run_e2e.py` exits 0, `gate.sh --full` prints
the "API e2e suite" step green, and not one API-level assertion has ever executed. That
is amendment 2026-07-27's Playwright finding ("all 7 skip and the step still exits 0 …
not e2e evidence") rebuilt inside the task chartered to close it, and every individual
line in the original plan was honestly worded — the aggregate was still a green gate
proving nothing.

The skip was also broader than the environment actually forces it to be. **Measured
live by the review**: against a freshly booted stack with zero LLM config,
`POST /api/v1/memories` → 202 accepted; `buffer_flush` drains the buffer; the memory row
lands (`status='active'` in the row itself) while `pipeline_failures` separately
records a `content_embedding` failure ("All connection attempts failed") for that
memory id — the write survives, the failure is recorded, not silently dropped
(`derive_memory_failed_step`, read this revision at `backend/app/services/pipeline.py`,
confirmed present and reached from the buffer-flush claim path, not only the bulk
content-embed path CLAUDE.md's Phase 1 description covers). **Capture → buffer → flush
→ row-lands is fully assertable with no embedder reachable at all; only the
appears-in-search leg needs one.**

**Revised design: `test_f1_capture.py` splits into three ordered tests, not one
function behind a module-level skip:**

1. **`test_capture_lands_in_buffer`** — `POST /api/v1/memories` (or the buffered-capture
   endpoint, confirmed against `memory_buffer.py` at execution time), asserting 202 and
   a returned memory id (`buffered_memory_id`, minted at accept per `memory_buffer.py`'s
   own documented contract — "the memory id is minted at accept, not at flush"). **Runs
   unconditionally** — a Tier-A accept needs no embedder.
2. **`test_buffer_flush_lands_row_or_records_failure`** — triggers `buffer_flush`
   through the jobs API (`POST /api/v1/jobs/buffer_flush/trigger`), **tolerating a 409
   busy** (closes Minor M2 — the review hit this live: the registry's own scheduled loop
   held the lock on its first manual trigger attempt; poll/retry rather than fail on
   409), then reads the `memories` row **directly from the database**
   (`darkmem_test_1`/`darkmem_bench_1` per this lane's convention — never assumed via an
   API response) and asserts **either** `status = 'active'` (embedder was reachable)
   **or** a `pipeline_failures` row naming `content_embedding` exists for that memory id
   (embedder was not reachable) — both are valid, provable pipeline outcomes; the test
   distinguishes them instead of treating "not active" as a bare failure. **Runs
   unconditionally.**
3. **`test_capture_appears_in_search`** — `POST /api/v1/memories/search` for the
   captured content, asserting the row appears. **This is the only leg that may skip**,
   and the skip is now *data-driven*, not a static pre-guess: it fires only when test 2
   actually recorded a `content_embedding` failure for this run, and the skip message
   embeds that recorded reason verbatim —
   `pytest.skip(f"content embedding failed this run: {failure.error} (pipeline_failures,
   memory {memory_id}) — search cannot be proven without a reachable embedder")`. This
   supersedes the original's static "check the same way `run_bench.py --algo-only`
   checks its own cache" analogy (Minor M3 — that analogy was inexact; `--algo-only`
   never probes an embedder at all) with something stronger: the skip reason is the
   *actual* error the real pipeline produced this run, not a guess made before the
   pipeline ran, so a mocked "pass" would have to fabricate a `pipeline_failures` row
   to fake it, not just delete a line.

**`run_e2e.py`'s exit contract changes to match `gate.sh`'s own exit-2 precedent.**
`gate.sh`'s own doc line is explicit: "`GATE BLOCKED` (exit 2) means a missing
toolchain, not a red gate." `run_e2e.py` runs pytest with `--junitxml=<tmp>/results.xml`,
parses the result summary after the subprocess returns, and if **every** collected test
skipped (`skipped == total > 0`), overrides pytest's own exit code to **2** — BLOCKED,
never green — instead of propagating pytest's 0. Because tests 1 and 2 above never skip
on this machine (neither needs an embedder), an all-skipped run can now only happen if
the stack itself failed to boot or every test errored out before running, which is
exactly the condition that should block a gate claim, not pass one silently. A real
failure (test 1 or 2 failing outright) still propagates pytest's non-zero code
unchanged — only the "everything skipped" case is remapped, and only to a *stricter*
exit, never to a looser one.

This closes I1 as the review named it: the failure mode most likely to survive an
honest execution is now structurally harder to reach — the two unconditional legs mean
a "green, zero assertions executed" gate claim is no longer reachable on this machine at
all, only a "green, two of three legs proven, one named-and-explained skip" claim is,
which is what G-B is actually entitled to say here.

### 2.5 F1 coverage — REST *and* MCP, `origin_key` asserted against the row, not "if the door sets one" (Important I2)

`docs/planning/e2e-test-plan.md`'s F1 row is explicit: *"A capture through REST **and**
through MCP lands in the buffer, flushes, and appears in search with its `origin_key`
intact."* The original plan's test was REST-only, and its `origin_key` assertion —
"asserting … an `origin_key` echoed back if the door sets one" — was guard-shaped: a
conditional written to look like it could fail, in the exact class of construct this
task exists to retire.

**Verified against this tree, independently, this revision — and the finding is
sharper than either the task text or the review's framing states:**

- `origin_key` **does** have a writer. `resolve_origin_key()`
  (`backend/app/api/mcp/client_identity.py`) is reached from both doors —
  `backend/app/api/routes/memories.py:_resolve_request_origin_key` for REST,
  `backend/app/api/mcp/server.py`'s `memory_add` for MCP — and landed in commit
  `4adf3e5` ("feat(capture): resolve origin_key at the front door"), well before this
  plan's base commit. `resolve_origin_key` **never returns `None`**: it returns either a
  declared identity (`f"{source}:{declared}"`) or the coarse fallback
  (`f"unknown:{source}:{project}"`) — every write through either door sets `origin_key`,
  always. **`CLAUDE.md`'s "No writer yet" line is stale**, not current; this is a doc
  correction outside this plan's own file, flagged for the controller (§10).
- Because it is never `None`, "if the door sets one" was never going to evaluate false in
  either direction — the conditional could not fail, matching this task's own definition
  of the defect class it retires.
- **A second, independent problem the "echoed back" wording assumed away: neither door's
  response ever carries `origin_key` at all.** `MemoryResponse`
  (`backend/app/schemas/memory.py`) has no `origin_key` field; MCP's `memory_add` full-dict
  response (`_memory_to_dict`, `app/utils/serialization.py`) derives its field list from
  `MemoryResponse.model_fields`, so it inherits the same omission. There is nothing to
  echo back from either API surface as written — asserting on a response field that does
  not exist would either not compile against the real schema or silently assert on `None`
  forever, which is the same "cannot fail" shape one layer further down.

**Revised test design — `test_f1_capture.py` now covers both doors and asserts
`origin_key` the only way it is actually observable:**

1. REST leg (§2.4's `test_capture_lands_in_buffer` / `..._or_records_failure`) —
   additionally asserts the row's `origin_key` **by querying `memories` directly**
   (a DB read against `darkmem_test_1`/`darkmem_bench_1`, never an API response field,
   since neither door surfaces the column) and asserts it matches
   `resolve_origin_key`'s documented fallback shape for an unattributed REST call —
   `unknown:api:<project>` — proving the REST door actually resolves and writes it, not
   merely that the column is nullable.
2. **New: `test_mcp_capture_lands_in_buffer_and_flushes`** — drives the MCP `memory_add`
   tool against the same booted stack (a real MCP call over the harness's live server,
   not a mocked tool invocation), repeats the buffer→flush→row assertions of §2.4's
   tests 1–2 for this second door, and asserts `origin_key` the same way (DB read),
   expecting the fallback shape `unknown:mcp:<project>` — **different** from the REST
   leg's `unknown:api:...`, which is the actual proof the two doors resolve
   independently rather than sharing one accidental path.
3. The search leg (§2.4's `test_capture_appears_in_search`) is exercised once, after
   whichever leg's flush actually landed a row `active` this run — F1's "appears in
   search" clause does not require proving it twice per door, only that the mechanism
   this task built proves it at least once for real.

**Coverage-table disposition:** F1's owning task (T1.13) is closed, so this plan records
the row as satisfied by T1.64 **in full** — REST, MCP, and `origin_key` all covered by a
DB-level assertion — rather than "proof of life" with an orphaned remainder. §6 (the
inclusion record) gains this row.

## 3. Decision 2 — `docs/e2e/scripts/` is retired, not ported

Read in full: 14 scripts, 1591 lines, a shared `lib/client.py` + `lib/assertions.py`, and
`docs/e2e/README.md`'s own stated prerequisites: *"Fresh darkmem deployment — server
running, no admin password set, empty database"*, backend at `localhost:8000`, frontend
at `http://host.docker.internal:3636`, Ollama reachable. `env.sh` hardcodes
`DARKMEM_BACKEND_DIR=/workspace/darkmem/backend` — a path that does not exist on this
machine (the repo is at `/root/repositories/darkmem`) and is evidence the scripts were
authored against a different, containerized environment than this one.

Three reasons this is **retired**, not ported or reused in place:

## 4. Decision 3 — the dead soft-skip guards, file by file

### 4.1 The mechanism, confirmed from the installed package, then reproduced live

`frontend/node_modules/playwright-core/types/types.d.ts:14513-14520`:

```ts
isVisible(options?: {

   * @deprecated This option is ignored.
   * [locator.isVisible([options])](...) does not wait for
```

Playwright **1.60.0** is the installed version (`node_modules/@playwright/test/package.json`).

### 4.4 The general replacement idiom

Playwright's own recommended replacement for a dead `isVisible({timeout})` guard is

mechanism Playwright already provides for this. `setup-wizard-refresh.spec.ts` is the one
file that needs the explicit `waitFor` form, because nothing else in that test re-checks
`passwordField`.

## 6. Decision 5 — `scripts/gate.sh --full`, and the port-hygiene gap this pass found

### 6.1 What gate.sh does today, read in full

No `no-restricted-imports`, no lint step at all (`grep -n lint scripts/gate.sh` — zero
hits, confirmed). The `--full` block runs exactly two things: the retrieval eval, then

the right task to close it rather than leave a third false doc sentence behind it.

### 6.2 The wiring this task adds

Two new `run_gate` calls inside the existing `if [ "$FULL" -eq 1 ]; then … fi` block,
using the same `setsid` + `STARTED_PGIDS` + `cleanup()` trap the file already has — no
new hygiene mechanism, just two more users of the one that exists:

```bash
run_gate "API e2e suite" 900 "$BACKEND" \
    env -C "$BACKEND" \
        TEST_DATABASE_URL="${TEST_DATABASE_URL:-postgresql+asyncpg://darkmem:darkmem@localhost:5433/darkmem_test}" \
        "$PY" scripts/e2e/run_e2e.py

run_gate "playwright e2e" 1800 "$FRONTEND" \
    env -C "$FRONTEND" \
        E2E_DISPOSABLE_STACK=1 \
        E2E_ADMIN_PASSWORD="$("$PY" -c 'import secrets; print(secrets.token_urlsafe(16))')" \
        npm run test:e2e
```

The second call's own script (or a thin wrapper it calls first) boots `stack.py` in
`--keep-running` mode with that same generated password before invoking `playwright
test`, and tears it down after — matching §2.2's revised recipe (`E2E_DISPOSABLE_STACK=1`
set here so `auth.spec.ts` / `code-real-mode.spec.ts` take the disposable-stack branch of
their `beforeAll` guard and never call `seedAdminPassword()` against `darkmem`), now
exercised on every `--full` run instead of only when a human follows the README by hand.
Because `run_e2e.py` already tears its own stack down before returning, and the
playwright step boots and tears down its own separately, the two never run concurrently
against the same port.

**The port check — REVISED (Important I3).** The original design,
`ss -ltn | grep -q ':8000\|:3636\|:3637'`, false-REDs on any normal dev machine:
`playwright.config.ts` sets `reuseExistingServer: !process.env.CI`, so a developer's own
`vite` on `:3636` legitimately survives a local `--full` run, and a dev backend on
`:8000` (`start_dev_server.sh`) is documented normal state — `ss`+`grep` cannot
distinguish "leaked by this run" from "was already there." Withdrawn.

**Revised: snapshot-and-diff, not a bare listener check.** Immediately before the
`--full` block starts, capture the listening state of the three ports
(`ss -ltn | grep -E ':8000|:3636|:3637'`, stored to a variable/temp file — call it
`PORTS_BEFORE`); after the block finishes and both new `run_gate` calls have completed
their own teardown, re-capture (`PORTS_AFTER`) and diff. A port present in
`PORTS_AFTER` but **not** in `PORTS_BEFORE` is a genuine leak from this run and fails the
gate loudly; a port present in both was already bound by something this run did not
start and is left alone, silently, exactly as it was before the run. This makes the
doc's existing "`scripts/gate.sh --full` verifies no listener remains on the dev ports
before exiting zero" sentence true for a developer's normal machine state, not only for
a pristine CI box.

**The step most likely to be wrong now: the disposable-stack Playwright guard (§2.2,
Step 3, B1's fix).** This revision's own weakest link is the same shape as the
original's — a design read from source rather than exercised against a live process —

against it is execution, not planning. If `E2E_DISPOSABLE_STACK`'s propagation from

`seedAdminPassword()`, shared-stack pass with it called) — not by reading the code and
asserting it should work, which is exactly the failure mode this paragraph exists to
flag before it repeats.

**The silent failure mode this plan considers most dangerous — REVISED, and now
structurally harder to reach (I1).** The original single-skip design meant the F1 test's
explicit skip could quietly become an unexplained mock and nobody would notice, because
the *whole test* lived behind one guess made before the pipeline ran. The revised design
(§2.4) removes that shape: two of three tests execute unconditionally and their
assertions read the real `memories` row and the real `pipeline_failures` table, so a
mocked embedder bypassing the real pipeline would have to fabricate **both** a plausible
row state **and** a plausible `pipeline_failures` entry (or its absence) to fake a pass —
not merely delete a skip line. The one remaining skip (`test_capture_appears_in_search`)
is now data-driven off test 2's actually-recorded outcome rather than a static
pre-guess, so a reviewer can check that the skip message names a real
`pipeline_failures.error` value rather than a canned string. The guard against a mock is
still not a test that checks "did this test call the real embedder" — that would import
the same seam it exists to prove is real — it remains runbook §6's review discipline, now
applied to a harder target than a single conditional.
