## 1. What T1.64 is, and the four things it is not

It is: (a) a new, disposable-database API e2e harness with one documented entry point;
(b) a disposition call — port, replace, or retire — on `docs/e2e/scripts/`; (c) getting
the five E1-satisfiable honesty specs to actually run rather than silently skip; (d) the
`no-restricted-imports` warn→error flip, corrected against what is actually true today;
(e) wiring `scripts/gate.sh --full` to invoke the result.

**It is not** the other three honesty specs. `veto-absolute` needs the contradiction
veto (E2/T2.04), `human-only-confirmed` needs ratification (E2/T2.05), and
`withheld-not-grounded` needs grounded answering (EH1/T1.09) — none of that code exists
on this branch, and per the runbook's entry-gate rule those epics are not startable
until E1 clears G-B. The task's own Done-when already narrows to five; this plan does
not widen it back to eight.

**It is not F2–F11's flow coverage.** `docs/planning/e2e-test-plan.md`'s coverage table
assigns each flow a distinct **owning task** (F2→T1.26, F5→T1.37, F6→T2.38, F7→T3.08,
F8→TH1.16, F10→T3.12, F11→T1.38) — several of which (T2.38, T3.08, TH1.16, T3.12) are
epics ahead of E1 and not startable yet. T1.64 builds the harness those tasks populate;
it does not populate it on their behalf. What T1.64 does add, and must, is **one** flow
test proving the harness is not vaporware (§2.4) — F1, whose owning feature (capture +
`buffer_flush`) already shipped earlier in E1.

**It is not a rewrite of T1.58's Ruling 4.** `seedAdminPassword()`'s hardcoded target —
the shared dev stack's `darkmem` database, on purpose, never overridable by env — stays
exactly as T1.58 left it, for a reason stated there and not revisited here: a human
operator validating a real, persistent, wizard-configured deployment is a different
scenario from a disposable per-run database, and the two should not be conflated onto
one flag. What changes is that **a second, independent path now exists** for anyone who
does not have that persistent stack — see §2.2. Nobody's file is edited to make this
true; a new script is added beside it.

**It is not the frontend demo-import sweep.** 81 of the 90 current violations (§5) are
real, unfinished feature work spread across Chat, Memory Graph, Code, Knowledge,
Activity, Settings and Dashboard — work this task has no mandate to do and, at Sonnet
tier, no business doing in one pass across six unrelated features. §5 says exactly what
T1.64 does and does not fix.

## 2. Decision 1 — the database posture (the load-bearing one)

### 2.1 What the suite itself uses

**Decision: the API e2e suite lives at `backend/scripts/e2e/`, targets `darkmem_test`
(the same database pytest uses, per `docs/planning/e2e-test-plan.md`'s own three-database
table: "`darkmem_test` … Used by: Backend unit + API e2e" — this is not a new
allocation, it is the doc's stated intent, unbuilt until now), and gets there by
**booting its own server**, not by assuming one is already running.**

Reused, not reinvented — `backend/scripts/benchlib/bench_db.py` already has the exact
shape needed (read in full at `2e16fe2`… confirmed unchanged at `4bb0eeb`): override
`DATABASE_URL` before any `app.*` import, `DROP SCHEMA public CASCADE` +
`CREATE SCHEMA public`, then `alembic upgrade head` in a subprocess so Alembic's own
`asyncio.run` never collides with the caller's event loop. `backend/scripts/e2e/e2e_db.py`
is the same three functions against `TEST_DATABASE_URL` instead of `BENCH_DATABASE_URL`.

New, because nothing existing does it: `backend/scripts/e2e/stack.py`, which

1. calls `e2e_db.reset()`,
2. spawns `uvicorn app.main:app --host 0.0.0.0 --port <port>` as a subprocess with
   `DATABASE_URL` pointed at the just-reset database, in its own session
   (`start_new_session=True`, mirroring `gate.sh`'s own `setsid` discipline) so it can be
   torn down as a group,
3. polls `GET /health` until 200 or a bounded timeout, then
4. seeds the admin account through the **real front door**:
   `POST /api/v1/setup` with `{"password": "<generated>"}` and nothing else. Read at
   `backend/app/api/routes/setup.py:308-344`: *"Password is the only required block"* —
   `body.llm` is `Optional`, guarded by `if body.llm is not None:`. A fresh
   `darkmem_test` has no `admin_password_hash` row (`e2e_db.reset()` just dropped the
   schema), so `require_uninitialized` passes and this call succeeds with no LLM
   configuration at all. This is materially simpler than
   `frontend/tests/helpers/seed-admin.ts`'s raw `UPDATE config …` — that script exists
   only because the shared dev stack is **already** initialized with an unknown
   password, which is not this database's situation.
5. returns `(process, base_url, password)` to the caller, and tears the process group
   down on `__exit__` / a signal handler, matching `gate.sh`'s `cleanup()` trap.

`backend/scripts/e2e/run_e2e.py` is **the one documented entry point**: it calls
`stack.boot()`, runs `pytest backend/scripts/e2e/tests -q` with `E2E_BASE_URL` and
`E2E_ADMIN_PASSWORD` set from the booted stack, tears the stack down in a `finally`, and
exits with pytest's return code. `backend/scripts/e2e/README.md` states this in one
paragraph, matching `docs/e2e/README.md`'s "Quick Start" shape but truthfully: `python
scripts/e2e/run_e2e.py` and nothing else needs to be true first — no fresh deployment, no
pre-set password, no already-running server. **This is the concrete answer to "what
happens on a machine where none of that is set up": the suite performs the drop, the
migrate, the boot and the seed itself, every run, so "nothing is set up" is the normal
starting condition, not a failure mode.**

### 2.2 What fixes the live Playwright failure

`frontend/tests/auth.spec.ts` and `frontend/tests/code-real-mode.spec.ts` both assume a
server is already running against an already-initialized database with a password
`seedAdminPassword()` can overwrite via `UPDATE config … WHERE key =
'admin_password_hash'` — a statement whose own `affected == 0` branch already predicts
this failure mode ("stack not initialized — run setup first"). **Measured, this session,
against the shared dev stack:**

```
$ docker exec darkmem-postgres-1 psql -U darkmem -d darkmem -c "\dt"
Did not find any relations.
```

Zero tables. `seedAdminPassword()`'s `UPDATE` affects zero rows, its own guard fires,
and the process exits 1 inside `beforeAll` — the failure the dispatch names, reproduced
exactly as described, not merely reported secondhand.

**This is not a defect in T1.58's reasoning** (§1) — it is a machine that never ran
`docker compose up` and `alembic upgrade head` against `darkmem`, which the shared-stack
design was never going to survive on its own. But now that §2.1 has built a
boot-a-disposable-stack mechanism, the honest move is to make it available to Playwright
too, as an **alternative**, not a replacement:

**Decision: `stack.py` gains a `--keep-running` mode** (`python -m
backend.scripts.e2e.stack --keep-running --port 8000 --password <pw>`), which does
steps 1–4 of §2.1 and then blocks instead of tearing down. `vite.config.ts`'s dev proxy
already hardcodes `http://localhost:8000` (`frontend/vite.config.ts:36-38`) — measured,
unchanged — so no frontend config edits are needed; the disposable stack binds the same
port the proxy already expects. **The concrete recipe, documented in
`backend/scripts/e2e/README.md` and referenced from
`docs/planning/e2e-test-plan.md`'s "two things must be true" paragraph:**

```
# terminal 1 — disposable, migrated, seeded backend on :8000
python -m backend.scripts.e2e.stack --keep-running --port 8000 --password <pw>
# terminal 2
E2E_ADMIN_PASSWORD=<pw> VITE_DEMO=0 npx playwright test tests/auth.spec.ts tests/code-real-mode.spec.ts
```

`auth.spec.ts` and `code-real-mode.spec.ts` themselves are **not edited** — they already
read `E2E_ADMIN_PASSWORD` from the environment and call `seedAdminPassword()`, which
still overwrites whatever password is on the target database; against a stack booted by
`stack.py` with that same password, the overwrite is a no-op write to the same value and
the specs pass unchanged. **This is the reason the fix needs no change to T1.58's files
at all**: `seedAdminPassword()`'s contract ("overwrite the target's admin password to a
known value") is satisfied by either target, shared or disposable — only the operator's
choice of which stack to point it at changes, and that choice is now documented instead
of assumed.

**`scripts/gate.sh --full`'s own "playwright e2e" step adopts this**, closing the loop so
the fix is not merely documented but exercised on every `--full` run — see §6.2. This is
the one place this plan **does** touch `gate.sh`, and it is additive (one boot before the
existing `npm run test:e2e` call, one teardown after), not a rewrite of T1.58's or T0.16's
work.

### 2.3 Why not repoint the shared stack instead

Considered and rejected: migrating `darkmem` in place (`alembic upgrade head` against the
real database) would make `auth.spec.ts` pass without any new code. Rejected because
`darkmem` is the one database CLAUDE.md says nothing automated ever touches, and a
Playwright helper migrating it is exactly the kind of automation that rule exists to
forbid — the *value* of the shared-stack path is that it is a human-operated, real
deployment, and migrating it from a test helper erases that distinction the same run it
was meant to protect.

### 2.4 The one flow test that proves the harness is not empty

A suite with zero tests satisfies "`gate.sh --full` invokes it" while proving nothing —
the exact "green but empty" class this session has already found five times. F1
(capture, doc 17 §9 / e2e-test-plan.md coverage table) is the one flow whose owning
feature has already shipped in E1 (`memory_buffer` + `buffer_flush`, referenced
throughout `CLAUDE.md`'s domain model), so it is the one flow T1.64 can honestly write
without waiting on a task this task doesn't depend on.

`backend/scripts/e2e/tests/test_f1_capture.py`: against the booted stack,
1. `POST /api/v1/memories` (or the buffered-capture endpoint, whichever
   `memory_buffer` actually fronts — confirmed at execution time, not guessed here),
   asserting 201/202 and an `origin_key` echoed back if the door sets one;
2. trigger (or wait out) `buffer_flush`'s cron — the job registry's `min_interval_seconds`
   floor means this may need a manual `trigger("buffer_flush")` call through the jobs API
   rather than a real-time wait, which the execution step must check against
   `JobRegistry`'s actual trigger contract;
3. `POST /api/v1/memories/search` for the captured content, asserting the row appears.

This one test needs a live embedder to reach search (Phase 1 of the pipeline). Per
`docs/planning/gate-ledger.md`'s G-B entry ("this machine can make zero live model
calls" — Ollama unreachable, no API keys set), **this test is expected to be
unrunnable, not merely unwritten, on this machine**, exactly as the extraction bench's
`--algo-only` mode already accepts for the same reason. The execution step must not
paper over this with a mock embedder that bypasses the real pipeline — that would prove
the harness works against a fake, not the real Phase 1–5 path. The honest disposition,
stated up front rather than discovered mid-implementation: **write the test to skip
loudly** (`pytest.skip("no live embedder configured — G-B is blocked on this machine for
the same reason", allow_module_level=...)` or equivalent), naming the reason, not
swallowing it — an explicit, named skip is not the soft-skip failure mode this task
exists to close; an *unexplained* one would be.

## 3. Decision 2 — `docs/e2e/scripts/` is retired, not ported

Read in full: 14 scripts, 1591 lines, a shared `lib/client.py` + `lib/assertions.py`, and
`docs/e2e/README.md`'s own stated prerequisites: *"Fresh darkmem deployment — server
running, no admin password set, empty database"*, backend at `localhost:8000`, frontend
at `http://host.docker.internal:3636`, Ollama reachable. `env.sh` hardcodes
`DARKMEM_BACKEND_DIR=/workspace/darkmem/backend` — a path that does not exist on this
machine (the repo is at `/root/repositories/darkmem`) and is evidence the scripts were
authored against a different, containerized environment than this one.

Three reasons this is **retired**, not ported or reused in place:

1. **It is a manual, one-shot QA runbook, not a repeatable harness**, by its own stated
   precondition ("no admin password set, empty database" — i.e. run this once against a
   deployment about to go live, not every merge). Retrofitting drop-and-migrate onto it
   would change its actual purpose, not merely its plumbing.
2. **The path it hardcodes is already stale** on this machine, which is direct, measured
   evidence the assumption "point it at whatever's running" does not survive a second
   environment, let alone a CI-shaped one.
3. **Its flow coverage is already spoken for**, piecemeal, by the owning tasks in
   `e2e-test-plan.md`'s coverage table (§1). Porting all 14 phases wholesale into
   `backend/scripts/e2e/tests/` in this one task would silently absorb T1.26's, T1.37's,
   T2.38's, T3.08's, TH1.16's, T3.12's and T1.38's work — exactly the scope-creep this
   plan's §1 boundary section exists to refuse.

**Recorded disposition:** `docs/e2e/scripts/` is retired. `docs/e2e/README.md` gains a
one-paragraph header stating it is superseded by `backend/scripts/e2e/` for automated
runs and is retained only as a manual pre-cutover QA reference (its own stated purpose),
with a pointer to the new suite. The scripts themselves are **not deleted** — they are a
readable, if stale, checklist of what a "fresh deployment" smoke pass once covered, and
deleting them would erase that reference for no gain. `docs/e2e/test-plan.md` and
`ui-test-plan.md` (the broader manual runbooks, Phase 0-16 / U1-U24) are untouched —
disposition was asked only for `scripts/`, and those two documents describe a superset
this task has no mandate over.

## 4. Decision 3 — the dead soft-skip guards, file by file

### 4.1 The mechanism, confirmed from the installed package, then reproduced live

`frontend/node_modules/playwright-core/types/types.d.ts:14513-14520`:

```ts
isVisible(options?: {
  /**
   * @deprecated This option is ignored.
   * [locator.isVisible([options])](...) does not wait for
   * the element to become visible and returns immediately.
   */
  timeout?: number;
}): Promise<boolean>;
```

Playwright **1.60.0** is the installed version (`node_modules/@playwright/test/package.json`).
The `timeout` option is not merely unhelpful — the type declaration states outright that
the call "returns immediately," so every guard shaped
`if (!(await locator.isVisible({ timeout: 5000 }).catch(() => false))) { test.skip(...) }`
checks visibility at the instant it is called, before the SPA has necessarily rendered,
and reads that snapshot as the final answer.

**Reproduced live, not merely inferred from the type file:**

```
$ npx playwright test --project=demo-fixture tests/honesty/labels-always-render.spec.ts --reporter=list
Running 4 tests using 1 worker
- 1 …memory list: layer chip, lifecycle badge, and exclusion count render in both modes
- 2 …memory list: superseded badge renders in both modes, never filtered out
- 3 …article detail: verification badge and stale label render in both modes
- 4 …article detail: superseded badge and successor link render in both modes
4 skipped
```

All four tests skip, every run, under the demo-fixture project's own default — the
project this spec is specifically routed to by `playwright.config.ts`'s
`DEMO_FIXTURE_SPECS` array specifically so it *would* exercise real assertions. No
process was left running afterward (`ps aux | grep -E "vite|esbuild"` showed nothing
from this run).

### 4.2 Why the guard's own stated reason is false for ten of the eleven files

`frontend/src/routes/_authenticated.tsx:87-88`: `beforeLoad` returns immediately when
`DEMO` is true — no redirect to `/login`, no auth check at all. Every one of the ten
files below runs exclusively on Playwright's `demo-fixture` project
(`playwright.config.ts`'s `DEMO_FIXTURE_SPECS`), where `VITE_DEMO=1`. **"Not reachable
without login" cannot be true on this project** — the app has no login gate to fail. The
guard's stated reason was accurate for some earlier state of the app (or was copied from
a template written for the real-mode project) and is simply wrong today.

**11 files, 22 guard instances** (2+2+1+1+3+1+3+1+2+2 across the ten "retire" rows, plus
the one "fix" row) — matching the task text's "at least eleven pre-existing guards."
Ten files lose their skip entirely; one keeps a skip that can now actually fire.

### 4.4 The general replacement idiom

Playwright's own recommended replacement for a dead `isVisible({timeout})` guard is
`locator.waitFor({ state: "visible", timeout })`, which genuinely waits. For the ten
"retire" files this plan does not even need that idiom — deleting the guard and letting
the very next line's `expect(...).toBeVisible()` (already real, already auto-retrying) or
`.click()` (already auto-waiting) do the checking is simpler and exercises the exact
mechanism Playwright already provides for this. `setup-wizard-refresh.spec.ts` is the one
file that needs the explicit `waitFor` form, because nothing else in that test re-checks
`passwordField`.

```

```

`src/demo/flag.ts`'s own comment: *"Standalone demo mode: the app runs entirely on the

**Decision: relocate `src/demo/flag.ts` to `src/lib/demo-flag.ts`** (same export,
`DEMO`), updating its nine importers. This is a small, mechanical, in-lane fix (nine
one-line import-path edits, zero behavior change) that removes the one legitimate,
permanent exception from the rule's blast radius entirely — no glob negation, no
special-cased pattern to keep in sync by hand. After the move, `src/lib/theme-persistence.ts`
(§5.2, `lib/` bucket) drops to zero violations automatically, since its only demo import
was the flag.

## 6. Decision 5 — `scripts/gate.sh --full`, and the port-hygiene gap this pass found

### 6.1 What gate.sh does today, read in full

No `no-restricted-imports`, no lint step at all (`grep -n lint scripts/gate.sh` — zero
hits, confirmed). The `--full` block runs exactly two things: the retrieval eval, then
`npm run test:e2e`. **No port-listener verification exists anywhere in the file** —
`grep -n "lsof\|:8000\|listener" scripts/gate.sh` returns nothing — despite
`docs/planning/e2e-test-plan.md`'s "Process hygiene" section stating outright:
*"`scripts/gate.sh --full` verifies no listener remains on the dev ports before exiting
zero."* **That sentence is not true of the code as it stands.** This is a second,
independent doc/code discrepancy this measurement pass found (the first being §5's import
count), and since T1.64 is about to add a new process that binds `:8000` on purpose, it is
the right task to close it rather than leave a third false doc sentence behind it.

### 6.2 The wiring this task adds

Two new `run_gate` calls inside the existing `if [ "$FULL" -eq 1 ]; then … fi` block,
using the same `setsid` + `STARTED_PGIDS` + `cleanup()` trap the file already has — no
new hygiene mechanism, just two more users of the one that exists:

```bash
run_gate "API e2e suite" 900 "$BACKEND" \
    env -C "$BACKEND" \
        TEST_DATABASE_URL="${TEST_DATABASE_URL:-postgresql+asyncpg://darkmem:darkmem@localhost:5433/darkmem_test}" \
        "$PY" scripts/e2e/run_e2e.py

run_gate "playwright e2e" 1800 "$FRONTEND" \
    env -C "$FRONTEND" \
        E2E_ADMIN_PASSWORD="$("$PY" -c 'import secrets; print(secrets.token_urlsafe(16))')" \
        npm run test:e2e
```

The second call's own script (or a thin wrapper it calls first) boots `stack.py` in
`--keep-running` mode with that same generated password before invoking `playwright
test`, and tears it down after — matching §2.2's recipe, now exercised on every `--full`

tears its own stack down before returning, and the playwright step boots and tears down
its own separately, the two never run concurrently against the same port.

**The port check itself**, closing the doc/code gap: after the `--full` block, before the
verdict print, `ss -ltn | grep -q ':8000\|:3636\|:3637'` — non-zero exit means clean, a
match means something this run started is still bound and the gate should say so loudly
rather than exit green. This makes the doc's existing sentence true instead of aspirational.

## 9. Falsification pass

**The step most likely to be wrong: Step 1's `POST /api/v1/setup` password-only seed
(§2.1).** Everything else in this plan was verified by running a command and reading
real output. This one step rests on reading `setup.py`'s source and its docstring
("Password is the only required block") rather than on an actual call against a freshly
migrated database — because making that call for real means booting a server, which this
planning pass deliberately did not do (booting servers is execution, not planning). If
`setup_finalize` turns out to have an undocumented dependency the read missed — a
required repo block, a non-`Optional` field the type hints understate, a `llm_config_lock`
acquisition that hangs without a lock provider configured — the entire §2.1 mechanism
fails at the first real boot, not at review time, and every downstream claim in §2 (the
Playwright fix, the gate wiring, the F1 test) inherits the same failure silently until
someone actually runs it.

**The silent failure mode this plan considers most dangerous: the F1 test's explicit
skip (§2.4) becomes an unexplained one.** The whole point of writing
`pytest.skip("no live embedder configured …")` instead of mocking the embedder is that a
reader can tell "the harness is fine, the environment can't reach a model" apart from
"the harness is broken." If the execution step, under time pressure, replaces that
skip with a mock that returns a fixed vector — to make the test "pass" and turn the gate
green — the suite reports success while never having exercised Phase 1 through Phase 5 of
the real pipeline even once. That is the exact "green while proving nothing" failure this
whole task exists to close, reintroduced one layer down inside the fix for it. The guard
against this is not a test — a test that checks "did this test call the real embedder"
would import the same seam it exists to prove is real — it is the review discipline
runbook §6 already requires for any task whose output feeds a gate claim: a reviewer
reading `test_f1_capture.py` must be able to see, from the assertions themselves, that a
pass could only happen by going through Phase 1–5, and that a skip names the real reason
rather than hiding a shortcut behind it.
