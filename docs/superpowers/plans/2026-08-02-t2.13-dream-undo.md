## 0. The one-paragraph summary

T2.13 reads T2.12's uniform `consolidated` journal stream, groups it by `cycle_id` into a
digest, and offers one undo door that takes a set of action ids and either restores every
one of them or writes nothing. The three inverses are a status/pointer restore, a
pass-keyed JSONB block restore-or-removal, and a derived-field restore. "Exact prior state"
is defined with **six named exclusions**, because saying "exact" while the implementation
has sanctioned exclusions is the kind of clause that reads as a lie later. Batch atomicity
is structural on four independent layers, the strongest being that **there is no
per-action code path at all** — a single-action undo is a batch of one through the same
function. The undo journals a new `undone` event type, landed taxonomy-first in its own
commit ahead of the emitter, and a **journal-readback assertion raises if the journal did
not land**, so an unjournalled undo — which is precisely an erasure — is unreachable rather
than merely unlikely. That raise, like any other, leaves restores in the session: **on any
raise other than `UndoRefused` the caller must roll back**, and D6 states the three-outcome
contract that a two-outcome reading would have hidden from T2.23.

And the deep question T2.12 handed over is **settled in §3 D9: an undone subsumption gets a
suppression tombstone.** It is scoped as a *nomination* filter inside the dreaming pass, not
a lifecycle mechanism, which is what keeps it out of Tier 3 — the ruling, its discriminator
and its escalation fallback are all in D9.

**Both rulings were ratified by the controller on 2026-08-02, each verified against the
tree rather than accepted on the argument** (D5, D9, §9.1). The plan below is the ratified
form; no clause changed.

> ### Read §1.5 before reading the module layout

| **associate** (`:985-1007`) | `action`, `before:{edge: <pass block \| null>}`, `after:{edge:{source,target,rel_type,properties:{near_duplicate: <block>}}}`, `created`, `pair`, `detector`, `verdict`, `score`, `cycle_id` | `newer.memory_id` |
| **refine** (`:1150-1174`) | `action`, `before:{summary, tags, metadata_dream_refine}`, `after:{summary, tags, metadata_dream_refine}`, `fields`, `detector`, `cycle_id` | `memory.memory_id` |

### 1.2 Five places where the shipped code is *narrower* or *different* than §9.2's prose

None of these is a defect in T2.12. Each is a place where building the inverse from §9.2's
wording alone would produce wrong code.

**(F1) The refine payload key is `metadata_dream_refine`, not `metadata_dream`, and it holds
the marker itself.** §9.2 item 4 and D2's table both say "`metadata.dream`"; the code
(`:1159`, `:1168`) journals `refine_marker_of(...)` — the object at
`metadata.dream.refine`, one level deeper. An inverse written against the documented key
would `KeyError`, or worse, restore a whole `metadata.dream` object and clobber the
tombstone D9 adds beside it.

**(F2) The associate payload's `after.edge.properties` omits the `dream` wrapper.** The
code writes `{"properties": {NEAR_DUPLICATE_PASS: block}}` (`:997`) — i.e.
`{"near_duplicate": {...}}` — while the database path is
`properties.dream.near_duplicate` (`app/repositories/memory_relations.py:100`, `:174`). The
payload is the *pass-relative* view. An inverse that treats `after.edge.properties` as the
row's `properties` would write `properties.dream.properties`.

**(F3) `before.edge` is the pass block, not the edge row.** `existing_block` (`:965`,
`:991`) comes from `pass_block_of(...)`, which is already scoped to
`properties.dream.near_duplicate` (`memory_relations.py:182-193`). So the before-side is
already as narrow as §9.2 demands the inverse be — good news, and it means the inverse
restores a *block*, never a row.

**(F4) `created = False` with `before.edge = None` is representable, and §9.2's two-way
inverse has no arm for it.** §9.2 item 7 gives `True → delete the row`,
`False → restore the previous block`. But `created` comes from `(xmax = 0)`
(`memory_relations.py:104`), which reports whether the **row** was inserted — not whether
*this pass's block* existed. The reachable case: T2.16 writes `RELATES_TO` for a pair,
`UNIQUE (source_memory_id, target_memory_id, rel_type)`
(`0001_baseline.py:368-369`) makes it the same row, T2.12's associate then merges its block
in, `xmax != 0`, `created = False`, and `before.edge` is `None` because no near-duplicate
block existed. Restoring `None` through `jsonb_set` writes JSON `null` and leaves
`{"dream": {"near_duplicate": null}}` — which is not the prior state, and which
`pass_block_of` (`:193`, `isinstance(block, dict)`) reads as absent while the row carries a
lie. **The inverse is three-way, not two-way** (D3).

**(F5) `created = True` does not license deleting the row unconditionally.** By the same
`UNIQUE`, a sibling pass may have added its own block *after* the insert. Deleting the row
would destroy another actor's edge — the whole-object hazard §9.2 forbids, arriving through
the other door. The row-delete is available only when the row is provably still exclusively
this pass's (D3).

### 1.3 `events` — three facts that shape the design

Read from `0001_baseline.py:1001-1019`:

- **`events.id` is `BIGINT GENERATED ALWAYS AS IDENTITY`, not a UUID**, and the primary key
  is composite: `PRIMARY KEY (id, created_at)`, because the RANGE partition key must sit in
  every unique constraint. The DDL comment at `:997-999` says *"nothing joins events by
  id, so folding created_at into the composite PK costs nothing."* **T2.13 is the first
  code that addresses an events row by id**, so that comment becomes stale on this branch.
- Consequence: `WHERE id = :id` alone is a scan of every monthly child. **The retention
  window is also the partition-pruning bound** — every lookup carries
  `created_at >= now() - retention`, so at the default retention the undo door touches one
  or two children. That is a designed coincidence, not luck (D7), and it is the reason
  T2.13 needs **no index and therefore no schema change** — which matters, because the
  baseline is a single shared mutable file serialising through one owner per epic.
- `events` carries an `actor TEXT` column (`:1010`), which is where the authenticated
  curator's identity goes (doc 08 §7: "Undo is authenticated (it is a curation action, doc
  12)"). The established idiom is `actor=user.sub`
  (`app/api/routes/review_queue.py:95`).

### 1.4 `EVENT_TYPES` has no `undone`

`app/services/events.py:53-76` lists 22 values; `undone` is not among them. Doc 08 §7 and
doc 13 §6.3 both say the undo "journals an `undone` event". So **the vocabulary must
widen**, taxonomy-first — land the value *before* its emitter ships (CLAUDE.md, events
journal section; `events.py:48-52`). `record_event` only *warns* on an unknown type
(`:124-133`), it does not refuse, so shipping the emitter first would produce a working
feature filing rows under a value the vocabulary denies — the exact silent-drift shape the
taxonomy-first rule exists to stop. This is Step 1, its own commit.

### 1.5 The structural constraint nothing in the brief mentions — read this before D1

**This is the single finding that dictates the module layout, and the one a reviewer is
most likely to mistake for gold-plating.**

`tests/test_dream_jobs.py`'s invariant-15 scan derives its forbidden module set from
`dream_jobs.py`'s own imports (`dream_job_implementation_modules`, `:338-355`) and applies
it to **every file under `backend/app/`** (`_app_sources`, `:388-389`), exempting only
`app/services/dream_jobs.py` (`_ALLOWED_DREAM_JOB_FILES`, `:283-285`). `dream_jobs.py`
imports `memory_dream`, so:

> **No file under `app/` may contain the text `app.services.memory_dream` or
> `from app.services import memory_dream`.** `app/services/dream_undo.py` therefore
> **cannot import the producer's module**, even to read a constant.

Also flagged: any quoted literal matching a family job key, so `"memory_dream"` in quotes
fails the build anywhere under `app/` (`:381`). Bare prose and `"memory_dream_state"` are
fine — the pattern needs a closing quote immediately after the key.

The precedent for the way out is already in the tree and was built deliberately:
`app/repositories/memory_relations.py` is *not* imported by `dream_jobs.py`, so it sits
outside the derived set and T2.16/T2.17 can import it (T2.12 plan §9.4). D1 applies the
same move to the journal vocabulary.

**The property that makes the way out legal is that the set is derived one hop, not
transitively.** `dream_job_implementation_modules()` reads `dream_jobs.py`'s own text and
returns the `app.services` modules *it* names, minus `_UMBRELLA_INFRASTRUCTURE`
(`:338-355`). A module the umbrella does not import is outside the set however many hops
away it sits. `dream_journal.py` will be imported by `memory_dream.py` and not by the
umbrella, so it stays outside — **provided the one-hop rule survives T2.67's rework**.
§9.5 states the requirement and its ready fallback.

### 1.6 Volume, so the read surface is sized rather than guessed

Per cycle the producer can emit at most `judge_fanout` (default 25) + `refine_batch`
(default 25) `consolidated` rows (`memory_dream.py:1400-1443`), at
`default_cron="0 3 * * *"` — one cycle a night. So a cycle is ≤50 rows and a 30-day digest
window is ≤1500 rows of this event type. Every digest query is bounded by `created_at`, so
it prunes to the relevant children and filters `event_type` on top. No new index is
justified by these numbers, and adding one would cost a baseline edit.

### 1.7 Miscellaneous facts the steps depend on

- `memories.status` is the PostgreSQL enum `memory_status`
  (`0001_baseline.py:61`, `:152`), so a **parameterised** status restore needs
  `CAST(:status AS memory_status)` — the primitive's own writes use literals
  (`supersede.py:127`) and dodge the question.
- `chk_superseded_has_pointer` is evaluated once per row per statement, so the restore must
  move `status` and `superseded_by` in **one** `UPDATE` — same reasoning as
  `_FLIP_TO_SUPERSEDED` (`supersede.py:117-136`).
- `touch_updated_at` fires on every `UPDATE memories` (`0001_baseline.py:205-206`).
- `memory_relations` has `created_at` and **no `updated_at`** (`0001_baseline.py:359-372`),
  so the edge inverse carries no timestamp exclusion.
- `record_event` runs its insert inside its own `SAVEPOINT` and **never raises into its
  caller** (`events.py:135-157`). That is correct for a side-channel and wrong for a
  Done-when clause; D6 handles it.
- `PostgresMemoryRepository.set_tags` (`app/repositories/relational.py:189-215`) replaces
  the link set through the ORM and writes only `memory_tags` rows; it does not dirty the
  `memories` row, so a tags-only restore does not move `updated_at`.
- `MemoryUpdate.content` is wire-editable (`app/schemas/memory.py:85`), which is what gives
  D9's content-keyed tombstone a real lapse path rather than a theoretical one.
- The producer's `metadata` marker write already demonstrates the nested-`jsonb_set`
  discipline for a **two**-element path (`memory_dream.py:1124-1141`). D9 needs a
  **three**-element path, which needs a third nesting level; that is a measured trap, not a
  style preference (§5 T-TOMB2).

## 3. Design decisions

### D1 — Module layout, and the vocabulary that cannot be imported

Four new modules, one new test file, plus additions to one existing repository.

| Module | Role | Inside invariant 15's derived set? |
|---|---|---|
| `app/services/dream_journal.py` | **New.** The shared vocabulary: event/object types, the three action names, the detector label, payload key names, the `properties.dream` pass key, the metadata marker paths, and the pure accessors over them | **No** — `dream_jobs.py` does not import it, exactly as it does not import `memory_relations.py` |
| `app/services/dream_digest.py` | **New.** The read: cycle list, one cycle grouped by object, advisory undoability | No |
| `app/services/dream_undo.py` | **New.** The write: resolve → lock → validate → apply → journal → verify. **Scanned** by D5's atomicity guard | No |
| `app/api/routes/dream_digest.py`, `app/schemas/dream_digest.py` | **New.** Two GETs and two POSTs | No |
| `app/repositories/memory_relations.py` | **Extended.** `write_pass_block`, `clear_pass_block`, `delete_edge` | No (unchanged) |
| `app/services/memory_dream.py` | **Two disclosed edits** (D1 move, D9 read) | Yes — it *is* the set |

**Why a shared vocabulary module rather than duplicated literals.** §1.5 forbids
`dream_undo.py` from importing `memory_dream`. The alternatives are (a) lift the shared
names into a neutral module both import, or (b) re-declare them in `dream_undo.py` and pin
them with a test that imports both (tests are not scanned). (b) costs zero edits to a
landed module and is a genuinely available fallback; (a) is recommended because the journal
contract is shared between a producer, a consumer and — shortly — T2.23, and belongs to
none of them. A duplicated `"subsume"` literal in two modules is precisely the drift this
corpus keeps finding (`code_query.py`'s private `RRF_K` is the standing example).

**The move is a pure re-export and its acceptance criterion is zero test edits.**
`memory_dream.py` keeps every module-level name it has today; the names are `import`ed from
`dream_journal` instead of assigned, so `dream.NEAR_DUPLICATE_PASS`,
`dream.REFINE_MARKER_PATH`, `dream.ACTION_SUBSUME` and the rest still resolve and
`tests/test_memory_dream.py` (2246 lines) passes unedited. That is the same standard T2.12
held itself to against T2.45's suite (D11), and it is the acceptance criterion for Step 2
rather than a hope.

Names moved: `EVENT_TYPE`, `OBJECT_TYPE`, `DETECTOR`, `ACTION_SUBSUME`,
`ACTION_ASSOCIATE`, `ACTION_REFINE`, `NEAR_DUPLICATE_PASS`, `HYGIENE_STATE_OPEN`,
`REFINE_MARKER_PATH`, `refine_marker_of`, `content_sha`. Names added:
`UNDONE_EVENT_TYPE`, `SUBSUME_TOMBSTONE_KEY`, `SUBSUME_TOMBSTONE_PATH`,
`subsume_tombstone_of`, `subsume_tombstone_blocks`.

### D2 — "Exact prior state", defined with its exclusions

The Done-when says *exact*. Doc 08 §7's tractability claim is that every inverse is a
status, pointer or timestamp restore. Checked against the three shipped actions, that claim
is **true for the state each action wrote and false as a claim about the whole row**. So the
clause is discharged against a stated definition:

> **Definition.** An undo restores exact prior state when, for every field the action
> wrote, the field's post-undo value equals the action's journalled `before` value; and the
> undo writes no field the action did not write, **except** the entries in the exclusion
> table below, each of which is either physically unrestorable or deliberately preserved.

**The exclusion table.** Six entries. Each says which actions it touches, whether it is
*not restorable* or *by design*, and what breaks if it is "fixed".

| # | Excluded state | Actions | Kind | Why |
|---|---|---|---|---|
| **E1** | `memories.updated_at` | subsume, refine | not restorable | The `touch_updated_at` trigger (`0001_baseline.py:205-206`) fires on the inverse's own `UPDATE`. Doc 08 §7's "timestamp restore" does not extend to it, and no honest undo can claim otherwise (T2.12 §9.2 item 5). *Precision T2.12 did not state:* a refine whose `fields == ["tags"]` runs no `UPDATE memories` in its inverse, so `updated_at` is unmoved on the way back — but it was still moved on the way out by the marker write (`memory_dream.py:1124-1141`), so the exclusion holds for every refine either way |
| **E2** | `memories.metadata.dream.refine` | refine | **by design** | Preserved, never restored. On a *first* refine the before-value is absent, so restoring it clears the marker, and `needs_refine` (`memory_dream.py:1048-1057`) keys on the marker alone — the next cycle would re-apply the refine and silently reverse the undo. This is T2.12's D7 constraint arriving as a rule on me, and it is the reason refine is the one action already immune to re-application |
| **E3** | The action's own `events` row | all three | **by design** | `events` is append-only, enforced by three trigger kinds (`0001_baseline.py:1024-1041` plus the per-child guard stamped by `events_ensure_partition`). The undo *adds* a row; it removes nothing. This exclusion is the third Done-when clause in its literal form, and stating it as an exclusion rather than a feature keeps the definition honest |
| **E4** | Orphaned `tags` rows | refine | not restorable *here* | `set_tags` replaces the `memory_tags` link set; a `tags` row the refine minted survives with no link until `tag_orphan_cleanup` sweeps it. Not memory-visible, and reaching into another job's substrate to force it would be worse than the residue |
| **E5** | `memory_relations` rows a **sibling pass** has since claimed | associate, `created = True` | **by design** | Prior state was "no row". If T2.16 has added its own block since, restoring "no row" destroys another actor's edge. The inverse removes only its own block and leaves the row, and the digest reports it. The undo must be as narrow as the write, from the undo side too (§9.2 item 7) |
| **E6** | `memories.metadata.dream.undone_subsume` | subsume | **by design, and new in T2.13** | The inverse *adds* the D9 suppression tombstone, which was not in the prior state. Called out loudly because it is an exclusion this task introduces rather than inherits, and because a reader who finds an unexplained metadata key on a restored memory should meet it here first |

Everything else is restored exactly, and §5's tests assert the restored values field by
field rather than asserting "no exception".

### D3 — The three inverses

Each runs inside the batch's single transaction, after its locks are held and its
validations have passed (D4). Each is stated as SQL because the shapes are the point.

#### A1 — subsume

*Locks:* the `older` memory (`payload.object_id`) `FOR UPDATE`. The `newer` memory is never
**written** and never locked.

*Reads:* `newer.content`, **unlocked**, for one purpose only — D9's tombstone records
`counterpart_content_sha`, and the subsume payload journals no shas, so the value has no
other source. Revision 1's A1 said the inverse "does not read" `newer` and D9 required a
field only such a read can supply; the two could not both hold, and **A1 was the wrong
half**. An unlocked read suffices because the failure direction is benign: if `newer.content`
changes between this read and the commit, the recorded sha is stale, `subsume_tombstone_blocks`
sees a mismatch, and the tombstone **lapses early** — the pair is re-proposed, which is
exactly the behaviour with no tombstone at all. **The race can only ever fail toward not
suppressing**, never toward suppressing a supersession it should not, which is the
direction D9's whole ruling is careful about. Locking `newer` would close the window and is
available at the cost of a second lock contending with the dreaming pass's Phase W; it is
not bought, because a benign fail-open does not justify the contention.

*Validate:* live `status` = `after.status` **and** live `superseded_by` = `after.superseded_by`.

*Restore — one statement, and D9's tombstone rides it:*

```sql
UPDATE memories
   SET status        = CAST(:status AS memory_status),
       superseded_by = CAST(:superseded_by AS uuid),
       metadata      = <three nested jsonb_set, D9>
 WHERE id = CAST(:memory_id AS uuid)
```

One statement because `chk_superseded_has_pointer` is evaluated per row per statement; the
two-statement form raises, which §5 T-SUB2 provokes deliberately rather than assuming. The
tombstone rides the same statement for the reason T2.12's marker rides the summary write: a
tombstone can never record an undo that did not land.

`before.status` is always `'active'` and `before.superseded_by` always `NULL` for a
T2.12-written subsume, because `supersede()` only flips from `active`
(`supersede.py:125-136`). The inverse still **restores the journalled values** rather than
hardcoding them — a hardcoded `'active'` would be an assumption dressed as a restore, and
would silently do the wrong thing the day another producer journals a `consolidated`
subsume from a different starting status. Preflight validates `before.status` against the
enum's three legal values and refuses anything else.

#### A2 — associate

*Locks:* the edge row, by `(source, target, rel_type)` from `after.edge`, `FOR UPDATE`.

*Validate:* the row exists **and** `pass_block_of(row, "near_duplicate")` equals
`after.edge.properties["near_duplicate"]` (F2: the payload's `properties` is the
pass-relative view).

*Restore — three arms, keyed on `(before.edge is None, created)`:*

| `before.edge` | `created` | Inverse |
|---|---|---|
| a block | either | **Restore the block** through the same nested pass-keyed `jsonb_set` the writer uses (`memory_relations.py:78-105`). Never `SET properties = …` |
| `None` | `False` | **Remove the block**: `properties = properties #- '{dream,near_duplicate}'`. **Not** a `jsonb_set` to JSON `null` — that leaves `{"dream":{"near_duplicate":null}}`, which `pass_block_of` reads as absent (`:193`) while the row carries a value the prior state never had. This is F4's arm, which §9.2's two-way rule has no place for |
| `None` | `True` | **Remove the block, then delete the row iff it is now exclusively empty.** After the removal, delete when `properties` is `{}` or `{"dream": {}}` — i.e. no sibling pass block under `dream` and no other top-level key. Otherwise leave the row and report **E5** |

Measured on PostgreSQL 17.10, which is what fixes the operator choice and the
delete predicate:

| expression | result |
|---|---|
| `'{"dream":{"near_duplicate":{…},"proximity":{…}}}' #- '{dream,near_duplicate}'` | `{"dream": {"proximity": {…}}}` — sibling survives |
| `jsonb_set('{"dream":{"near_duplicate":{…}}}', '{dream,near_duplicate}', 'null')` | `{"dream": {"near_duplicate": null}}` — **the key survives holding `null`** |
| `'{"dream":{"near_duplicate":{…}}}' #- '{dream,near_duplicate}'` | `{"dream": {}}` — the exclusively-mine shape the delete predicate matches |

The `created = True` arm is written for a caller that does not exist yet (T2.16), exactly as
T2.12's inner `jsonb_set` was — *handled rather than asserted*, for the reason D8 gave:
raising on a legitimate row shape would fail an undo over a row another actor is entitled
to share. §5 T-ASC4 hand-writes the sibling block and proves the row survives.

Three new repository functions on `memory_relations.py`, keeping every pass-keyed write in
the one module that owns the idiom: `write_pass_block` (UPDATE-only, the nested form),
`clear_pass_block` (`#-` plus the emptiness probe, returning whether the row is now
exclusively empty), `delete_edge`. Every parameter carries its CAST (invariant 10).

#### A3 — refine

*Locks:* the memory `FOR UPDATE`, reading `summary`, `metadata` and the ordered tag names —
the same shape `_LOCK_MEMORY` already uses (`memory_dream.py:704-723`).

*Validate:* live `summary` = `after.summary`; live tag list = `after.tags` compared as
sorted sequences (the read is `ORDER BY t.name`, so this is exact, not lenient); and
`refine_marker_of(live metadata)` = `after.metadata_dream_refine` (F1: the key is
`metadata_dream_refine` and it holds the marker itself).

*Restore, driven by `payload.fields`* — the producer builds that list from the columns it
actually wrote plus `"tags"` (`memory_dream.py:1143-1148`), so it is an exact record of what
moved:

- `"summary" in fields` → `UPDATE memories SET summary = :summary WHERE id = …`. **The
  marker is not in the statement** (E2).
- `"tags" in fields` → `set_tags(memory_id, before.tags)`.
- Neither → unreachable: `parse_refine` refuses an answer proposing no derived field
  (`:652-653`). Preflight refuses an action whose `fields` is empty rather than treating it
  as a no-op success, because a no-op that reports success is indistinguishable from a
  completed undo — the criticism `SupersedeResult`'s own docstring levels at silent no-ops
  (`supersede.py:155-160`).

### D4 — Batch atomicity, on four structural layers

*Not representable* is stronger than *not produced*, so the argument has to be about what
the code can express, not about what the happy path does.

**Layer 1 — there is no per-action code path.** One function:

```python
async def undo(session, *, event_ids: Sequence[int], actor: str) -> UndoBatch
```

Per-action undo is `undo(session, event_ids=[one])`. There is no second implementation for
a single action that could diverge from the batch one, and no loop-with-recovery for a
batch that a single-action call bypasses. This is the strongest layer, because the usual way
partial undo appears is a batch path that "reuses" a single path by calling it N times with
per-call error handling.

**Layer 2 — the result type has nowhere to put a partial outcome.**

```python
@dataclass(frozen=True)
class UndoneAction:      # no `applied`, no `skipped`, no `error`
    event_id: int; action: str; object_id: str; restored: tuple[str, ...]
    excluded: tuple[str, ...]

@dataclass(frozen=True)
class UndoBatch:         # no per-item status collection
    undo_batch_id: str; undone: tuple[UndoneAction, ...]
```

**No *field* can carry a per-item outcome**, so a caller that wanted to report one would
have to add a field first, and T-ATOM1's AST scan fails when one appears. This mirrors
`RefineVerdict` having no field that could carry content (`memory_dream.py:560-571`) — the
corpus's own idiom for making a thing unrepresentable rather than merely absent.

**The honest limit of this layer, which revision 1 overstated.** An `undone` tuple *shorter
than the request* is representable: it carries no forbidden field and is invisible to a
scan looking for one. So are `contextlib.suppress` and
`asyncio.gather(return_exceptions=True)`, neither of which is a `try` statement. The
behavioural tests catch every shape reachable today, so the system holds — but the
*representational* claim needed closing, and it closes for one line:

```python
if len(undone) != len(event_ids):        # unreachable; the assertion is the point
    raise UndoIncomplete(...)
```

plus two extra names in T-ATOM1's scan (`suppress`, `return_exceptions`). A short tuple is
now unreturnable rather than merely unproduced, which is what the layer claimed all along.
Cheap, and the cheap place to close a representational gap is before the code exists.

**Layer 3 — no savepoint and no swallowed exception inside the module.** The batch runs in
the caller's single transaction. `dream_undo.py` contains **no** `begin_nested`, **no**
`commit`, and **no** `try`/`except` around any per-action work. The first failure propagates
out of `undo()`, the route's dependency rolls the transaction back, and every write in the
batch — including the ones that had already executed — is gone. The producer's discipline
was the opposite for the opposite reason: `_apply` wraps each action in `begin_nested` so
one poisonous item settles alone (`memory_dream.py:1257-1279`), because a nightly job must
survive a bad row. An undo is a human's single act and must not. **Inheriting T2.12's
transaction discipline here would be the bug.**

`SET LOCAL lock_timeout` is issued once at the top of the batch. It *serves* atomicity
rather than threatening it: a wedged lock aborts the whole batch with nothing written,
instead of hanging an HTTP request. Same for a deadlock — Postgres aborts one side and that
side's transaction rolls back whole.

**Layer 4 — validate-everything-before-write-anything, under the locks.** The sequence is
fixed and is the thing §5 T-ATOM3 pins:

1. Resolve every `event_id` to its action payload, within the retention window.
2. **Acquire every lock**, in a deterministic global order: all `memories` rows first sorted
   by id, then all `memory_relations` rows sorted by `(source, target, rel_type)`. Two
   concurrent batches therefore cannot deadlock **on the rows this module locks**.
   *Qualified, because the unqualified claim outran its proof:* the refine inverse's
   `set_tags` inserts tag rows in `before.tags` order
   (`app/repositories/relational.py:205-212`), which is outside this order, so two batches
   restoring overlapping *new* tag names can in principle deadlock there. The consequence is
   a whole-transaction abort, so **atomicity is intact and only the claim needed narrowing**
   — a redesign would buy nothing.
3. **Validate every action** — `already_undone`, `retention_elapsed`, `object_missing`,
   `state_changed` — *after* the locks are held. Any failure raises `UndoRefused` carrying
   every failing action and its reason. **Nothing has been written at this point.**
4. Apply the inverses, in **reverse journal order** (LIFO). The three inverses touch
   disjoint state so no order is required today; LIFO is specified because it is the
   natural inverse of a sequence and is the right default the day two action kinds do
   interact.
5. Journal, then verify (D6).

Step 3 running *after* step 2 is not cosmetic. In READ COMMITTED each statement takes a
fresh snapshot, so a second concurrent undo of the same action blocks on the row lock, then
re-reads and sees the first one's committed `undone` row — closing the double-undo race at
the `already_undone` check rather than leaving it to the compare-and-swap alone. §8 O2
records the one residual case.

**What a caller *can* do** and what it means: pass a subset of a cycle's actions. That is a
different batch, not a partial one. The clause is scoped to the request: *whatever set a
request names is undone in full or not at all*. Stated explicitly because the alternative
reading — that a cycle is the only legal batch — would make T2.23's per-item bulk actions
unbuildable on this primitive.

### D5 — Undoability: a compare-and-swap, which is what doc 08 §7's parenthetical asks for

**RATIFIED by the controller, 2026-08-02, Tier 2, after reading doc 08 §7 line 27
directly** — and reframed by that reading from *a deviation* to *the faithful
implementation*. Doc 08 §7 bounds the window: an action is undoable

> *"until a **newer consolidation change** rewrites the same object (**the before-state the
> undo would restore is then no longer current**), tracked via the **`events` watermark**,
> or until a `dream_undo_retention` config window elapses — whichever comes first."*

The parenthetical is the **property**. *"A newer consolidation change"* and *"the `events`
watermark"* are **two narrower proxies for it, in the same sentence**. T2.13 implements the
property directly — comparing the live row against the action's `after` payload under the
lock — which delivers §7's stated guarantee **more faithfully than §7's own named
mechanism**. So this is doc-faithful rather than a departure, and the amendment row says so
in those terms.

The reason the two proxies are not good enough is load-bearing, and the controller
confirmed it against the tree (`hygiene_state` is written only inside `memory_dream`
today, so nothing a watermark over `consolidated` events could see):

> **T2.23's triage write is not a `consolidated` event.** When a human dismisses a hygiene
> item, T2.23 moves `properties.dream.near_duplicate.hygiene_state` and journals — if it
> journals at all — something that is not a consolidation action. An events watermark over
> `consolidated` rows would not see it, would report the associate action still undoable,
> and the `created = True` arm would **delete a row carrying a human's triage**. That is
> precisely the hole T2.12's re-review closed on the write side (the pass-keyed `jsonb_set`
> plus the Python carry-forward, *neither droppable alone*), re-opened from the undo side.
> The compare-and-swap sees it, because the live block no longer equals the journalled
> `after` block.

So the check widens from *"a newer consolidation change"* to *"any change"*, which is
strictly safer and is the honest reading of "the before-state is no longer current".
**Widening a safety guard this way can only ever decline to act** — the reversible
direction this corpus has repeatedly chosen, and the controller's stated ground for
ratifying it. Filed as a Tier-2 amendment (§9.1) because it replaces the mechanism doc 08
§7 names, while delivering the guarantee that section's own parenthetical states.

**The four blocking reasons, in fixed precedence order** (the order is tested, T-UND5):

| Reason | Meaning |
|---|---|
| `already_undone` | An `undone` event exists whose `payload.undoes_event_id` is this action |
| `retention_elapsed` | `now - action.created_at > dream_undo_retention` |
| `object_missing` | The memory or the edge row no longer exists |
| `state_changed` | The compare-and-swap failed — something rewrote the state this undo would restore |

**Retention.** `dream_undo_retention` is a standalone `config` row, following
`index_debt.py`'s `DEBT_CONFIG_KEY = "code_index_debt"` idiom (`:44`) rather than a job
`config_schema` — an undo window is not a knob on any job, and `memory_dream`'s schema is
the operator surface for the *pass*. Shape `{"days": 14}`, default read from a module
constant when the row is absent or unparseable, degrading to the default rather than taking
the door down (the tolerant-read discipline `index_debt.normalize` established, `:64-70`).
14 days is chosen so a digest is still actionable after a two-week absence while keeping the
by-id lookup pruned to one or two monthly children (§1.3).

**The digest's flag is advisory; the door is authoritative.** `dream_digest` computes the
same four reasons with no locks, in three batched reads (memories by id, edges by triple,
tags by memory). T2.38 renders `undoable` plus `undo_blocked_reason` so an out-of-window
action shows a disabled affordance with an honest reason and never a broken button (doc 13
§6.3). The door re-runs the check under the locks and answers **409** with the per-action
reasons when they disagree. Both halves are one pure function over `(payload, live_state,
now, retention)`, called from two places, so the advisory and authoritative answers cannot
drift — which is the failure this split would otherwise invite.

### D6 — Journalling, and why an unjournalled undo must not land

**One new event type: `undone`.** `object_type` stays `memory` — the same object the action
journalled against — so `object_timeline` (`events.py:334-378`) shows the action and its
undo on one memory's history through the existing `ix_events_object`. Landed taxonomy-first
in Step 1, ahead of the emitter.

**One row per undone action, never one per batch** — matching the producer's rule
(`memory_dream.py:780-785`) and T2.23's own Done-when ("bulk actions journal per-item, not
per-batch"). The batch is still visible as one act, through `undo_batch_id`.

```json
{"action": "<the undone action>",
 "undoes_event_id": 12345,
 "undo_batch_id": "<uuid, one per request>",
 "cycle_id": "<the original cycle>",
 "before": {...},           // the live state this undo moved AWAY from
 "after":  {...},           // the state it restored TO
 "restored": ["status", "superseded_by"],
 "excluded": ["updated_at"]}
```

**`before`/`after` are in the undo's own frame**, not the original action's: the undo *is*
an action, and every payload in this journal means "what this row's transition moved from
and to". So the undo's `before` equals the action's `after`, and its `after` equals the
action's `before`. Stated explicitly because writing it the other way round produces a
journal that reads plausibly and is exactly backwards — the sort of thing that is only ever
noticed years later. `actor` carries `user.sub` (doc 08 §7's authenticated curation action).

**The readback, and why `record_event`'s contract forces it.** `record_event` degrades
loudly and never raises (`events.py:135-157`) — correct for a side-channel, wrong for a
Done-when clause. An undo whose journal silently failed is *an erasure*, which is the exact
thing clause 3 forbids. So after journalling, and inside the same transaction, the batch
counts the `undone` rows carrying its `undo_batch_id` and **raises when the count is short**.

> **An undo that could not be journalled does not happen.**

Cost: one `SELECT` per request. §5 T-JRN3 proves it non-vacuously by stubbing `record_event`
to a no-op and asserting the restore is *absent* afterwards — not by asserting the row is
present, which would pass with the readback deleted.

#### The three outcomes, and the caller obligation two of them do not carry

Revision 1 said this module "either restores every action you name or raises `UndoRefused`
having written nothing". **That is a false dichotomy, and the first consumer would have
built on it.** The readback raise fires *after* restores are already in the session, and so
does a failing inverse, a `lock_timeout` or a deadlock. This module structurally cannot
clean up after itself: T-ATOM1's scan forbids the savepoint and the rollback that would let
it. So there are three outcomes:

| Outcome | Session state | Caller obligation |
|---|---|---|
| Returns `UndoBatch` | Every named action restored, uncommitted | Commit |
| Raises `UndoRefused` | **Nothing written** — validation completed before any write (D4 layer 4), so the session is clean and still usable | Report 409. **No rollback required**, and that is the property distinguishing this case |
| Raises **anything else** | **Restores may already be written** | **Roll the session back.** Nothing else discharges clause 2 |

> **"Partial undo is not representable" holds under caller rollback.** D4's four layers make
> a partial undo impossible to produce deliberately and impossible to report; they do not
> make an aborted batch self-heal, because the module that must not own a savepoint cannot
> own one for this either.

The HTTP door inherits the obligation structurally — the request-scoped session dependency
rolls back on an unhandled exception — **which is exactly why this defect is invisible from
this lane's own tests.** An in-process caller inherits nothing, and that is the door handed
to T2.23: a bulk loop catching broadly per item and continuing on the same session commits
a partial, unjournalled undo — precisely what clauses 2 and 3 forbid, arriving through the
seam this module created. §9.2 states it to T2.23 in those words, §9.1 carries it as an
amendment row so it is a contract rather than a docstring, and T-ATOM6/T-ATOM7 pin both
halves.

### D7 — The digest's shape, and what T2.38 inherits

Source: `events WHERE event_type = 'consolidated' AND object_type = 'memory'`, bounded by
`created_at`, grouped by `payload->>'cycle_id'`. `detector` distinguishes the stream from
any future producer on the same event type (§9.2 item 2); `payload.reason` is read nowhere.

**`GET /api/v1/dream-digest/cycles`** — one aggregate query, `created_at`-bounded so it
prunes, `GROUP BY payload->>'cycle_id'`:

```
DreamCycleSummary: cycle_id, started_at, ended_at, projects[], total,
                   counts{subsume, associate, refine}, undone_count
```

**`GET /api/v1/dream-digest/cycles/{cycle_id}`** — the cycle, **grouped by object and
action** as doc 08 §7 and doc 13 §6.3 both specify:

```
DreamCycleDigest:
  cycle_id, started_at, ended_at, counts{...}
  objects: [ DreamObjectGroup ]         # ordered by first action time
DreamObjectGroup:
  object_id, project, actions: [ DreamActionView ]   # journal order
DreamActionView:
  event_id, created_at, action, object_id, project, detector
  before, after                      # verbatim from the payload
  detail                             # per-action: pair/verdict/score | created | fields
  undone, undone_at, undone_by, undo_batch_id
  undoable, undo_blocked_reason
```

**Actions within a cycle are ordered by `(created_at, id)` — journal order, which is
application order — and never regrouped by action kind.** This is where the inherited
within-cycle ordering item lands (2026-08-02 Tier-1 row, minor 1): when a duplicate pair
outranks a subsume pair, the digest legitimately shows an `associate` against memory A
followed by a `subsume` retiring A. That sequence is what happened, and a digest that
reordered or hid it would be describing a cycle that did not occur. When T2.23 closes the
item by ordering subsumes first in Phase W, the sequence changes and **the digest needs no
edit** — which is the test of whether the ordering rule was the right one.

Second-order, and worth stating because a reader will ask: undoing that subsume restores A
to `active` and the edge written against it becomes consistent again; undoing the associate
while A is still superseded deletes an edge pointing at a superseded memory, which is
harmless. Neither action's inverse depends on the other, so the batch has no ordering
constraint — LIFO is specified for future-proofing (D4 step 4), not necessity.

**T2.38 inherits**, against its own Done-when: *"every action shows what changed"* →
`before`/`after` plus `detail`; *"undo is reachable at both granularities"* → the two POST
doors; *"an undone action still appears, marked undone"* → `undone`/`undone_at`/`undone_by`,
guaranteed by append-only (E3) rather than by the read surface remembering to include it;
*"Simple/Advanced honoured"* → Simple renders the cycle summary and the grouped list;
Advanced adds `before`/`after`, `detector`, `score` and `undo_blocked_reason`.

### D8 — The doors

`app/api/routes/dream_digest.py`, prefix `/api/v1/dream-digest`, kebab-case, every route
`Depends(require_auth)` (doc 08 §7; doc 12).

| Route | Status | Notes |
|---|---|---|
| `GET /cycles` | 200 | `project`, `since`, `until`, `limit≤200`, `offset` |
| `GET /cycles/{cycle_id}` | 200 | 404 when the cycle has no rows in the window |
| `POST /actions/{event_id}/undo` | 200 | The batch-of-one. Body-less |
| `POST /cycles/{cycle_id}/undo` | 200 | Body: optional `{action, event_ids}` to name a subset. **Whatever set is named is undone in full or not at all** |

Both POSTs return `UndoBatchResponse` and both refuse with **409** carrying every failing
action and its `undo_blocked_reason` — the convention for "the resource is in a conflicting
state" (`docs/api-rest-conventions.md`). A verb in the path on a POST sub-resource is the
documented pattern (`/{key}/trigger`, `/{id}/retry`). 200-with-a-body rather than 204
because the digest re-renders from the response and because a 204 would give the UI nothing
to mark undone with.

### D9 — **THE RULING: an undone subsumption gets a suppression tombstone**

This is the question T2.12 deliberately left open (§9.2 item 6b) and the brief asks me to
settle. I settle it **for a suppression mechanism**, scoped so that it is not a Tier-3
change.

> **RATIFIED by the controller, 2026-08-02, Tier 2 and not Tier 3**, with the
> discriminator below verified against the tree rather than accepted on the argument. The
> controller added the confirmation that the nomination-filter category **already exists in
> this very module**: `needs_refine` (`memory_dream.py:1048`) filters the seed set at
> `:1332`, which is exactly the shape D9 proposes. **So the tombstone joins an existing
> category rather than inventing one** — which is a stronger form of the discriminator than
> the one I argued, and is now the first thing this section says.
>
> The escalation fallback below is therefore **not** exercised; Step 6 ships. It is left in
> place because a plan that deletes its own rejected alternative leaves the next reader
> unable to see what was weighed.

#### The state of play, measured rather than assumed

| Action | Re-applied next cycle? | Mechanism |
|---|---|---|
| refine | **No** | `needs_refine` keys on `content_sha` alone (`memory_dream.py:1048-1057`); the inverse preserves the marker (E2). An undone refine stays undone until content genuinely changes |
| associate | Yes, when the inverse deleted the row | The pair is still similar; the block is absent, so `_edge_is_unchanged` (`:907-915`) cannot skip and the upsert re-runs |
| subsume | **Yes, deterministically** | Restoring `older` to `active` puts the pair back exactly as the detector found it. The judge is seeded on both contents in fixed order (`pair_seed`, `:599-605`), the contents are unchanged, so the verdict is not merely likely to repeat — it is fixed |

#### Why "the bounded window sanctions it" is the wrong reading

It is the available defence and I considered it seriously. Doc 08 §7's window says an action
stays undoable *until a newer consolidation change rewrites the same object* — a sentence
that plainly anticipates consolidation touching the object again. And supersession is
monotonic by design (§2.1/§2.2), which is a real argument that nothing should make a
supersession not fire.

It fails on a distinction the sentence itself makes:

> **The window bounds how long you may undo, not how long an undo lasts.**

Conflating the two turns a retention policy into a licence to revert the user. Three
further grounds:

1. **The epic has already ruled this exact question, for refine.** D7's rationale is
   verbatim: *"if T2.13's undo restores the prior summary, a summary-keyed rule would see a
   mismatch and re-apply the refine on the next cycle — silently undoing the undo."* T2.12
   judged silent re-application unacceptable and built a marker to stop it. The asymmetry
   with subsume is not a principled distinction about monotonicity; it is that T2.12 did not
   own the undo and so could not justify paying for the mechanism.
2. **It is deterministic, not probabilistic.** "The system may reconsider tomorrow" would be
   defensible. "The system will reverse you tonight, and every night, until you edit the
   content" is not an undo; it is a snooze button with a ≤24h half-life.
3. **T2.38 makes it visible and absurd.** The digest would show yesterday's action marked
   undone and today's cycle carrying the identical action, forever, with the undo button
   live on both.

#### Why this is not Tier 3 — the discriminator

**The category already exists, in this module, one function away.** `needs_refine`
(`memory_dream.py:1048-1057`) is consulted at `:1332` to filter the refine work set — a
marker on a memory that removes it from a pass's candidates. T2.12 shipped that as an
ordinary consolidation convenience and nobody called it a lifecycle change. The tombstone is
the same shape, on the pair generator instead of the refine set. **Joining an existing
category is a stronger argument than the discriminator below**, and the controller supplied
it during ratification.

The discriminator stands on its own too. The escalation test is whether the change alters
**what makes a supersession fire**. It does not. Two shapes were available and only one of
them would have:

- **Rejected — a tombstone consulted by the lifecycle.** If `supersede()`,
  `detect_supersessions` or `apply_status_bridge` read it, then a supersession that would
  otherwise fire does not. That is a lifecycle change, Tier 3, and it would leak a
  consolidation concern into the write-time hot path. Not built.
- **Adopted — a tombstone consulted by the dreaming pass's *candidate generation*.**
  `memory_dream.generate_pairs` (`:429-503`) drops the pair before it is judged. After this
  change: `detect_supersessions` unchanged and never consults it; `supersede()` and
  `deprecate()` unchanged and never consult it — the primitive will still supersede that
  exact pair for any caller that asks; `apply_status_bridge` unchanged; the `active →
  superseded → deprecated` lifecycle and `chk_superseded_has_pointer` unchanged. What
  changes is **which pairs the nightly dedup pass nominates**, which is exactly what
  `needs_refine` already does for the refine arm and which doc 08 §5.4 puts inside the
  dedup pass's remit.

So: a **nomination filter**, not a lifecycle mechanism. **Tier 2**, because it edits a
landed module and adds a state key other tasks must know about — not Tier 3.

#### The mechanism

Written by the subsume inverse, **in the same `UPDATE` as the status restore** (D3 A1), at
`memories.metadata.dream.undone_subsume.<newer_memory_id>`:

```json
{"at": "2026-08-02T…Z", "undo_event_id": 12345, "cycle_id": "…",
 "content_sha": "<older's sha at undo time>",
 "counterpart_content_sha": "<newer's sha at undo time>"}
```

Keyed by the counterpart id so a memory can carry tombstones against several partners with
no list-mutation semantics, and so the suppression read is a dict lookup.

**The three-element path needs three nested `jsonb_set` calls, and two is silent data
loss.** `create_if_missing` creates only the *final* element; the producer measured this for
a two-element path (`memory_relations.py:17-25`) and the same trap applies one level
deeper. Level 1 materialises `{dream}`, level 2 materialises `{dream,undone_subsume}`, level
3 writes the counterpart key.

**Measured on this deployment's own PostgreSQL 17.10, not inherited on trust:**

| starting `metadata` | two nested `jsonb_set` on `{dream,undone_subsume,<id>}` | three nested |
|---|---|---|
| `NULL` | `{"dream": {}}` — **block dropped** | `{"dream":{"undone_subsume":{"abc":{"at":1}}}}` |
| `{"dream":{"refine":{…}}}` | `{"dream":{"refine":{…}}}` — **block dropped even though `dream` exists**, because `undone_subsume` does not | correct |

The second row is the one that matters and is the one a reader would get wrong: the
producer's two-level form is correct *for its own two-element path*, and copying it one
level deeper fails **even on the shape that already carries a `dream` key** — so a test
written only against a memory that has been refined before would not catch it either.
§5 T-TOMB2 pins all four shapes.

**The suppression read**, in `generate_pairs` immediately after `order_pair` (`:499`):

```python
if subsume_tombstone_blocks(older, newer):
    outcome.pairs_suppressed_by_undo += 1
    continue
```

`subsume_tombstone_blocks` (pure, in `dream_journal.py`) returns True iff
`older.metadata.dream.undone_subsume[newer.memory_id]` exists **and** both stored shas equal
the two rows' current `content_sha`. `MemoryRow` already carries `metadata` for both halves
(`:328-338`, and `_READ_MEMORIES` selects it for the non-seed half, `:305-325`), so this
needs no extra read.

**Three consequences, each stated rather than discovered later:**

1. **Suppression is at the pair level, before the judge, not at the verdict level.** With
   unchanged content and a fixed seed the verdict is foregone, so judging first would spend
   an LLM call to reach a conclusion already known. The cost: the pair is also no longer
   nominated for a near-duplicate **edge**. That is the right reading of the human's act —
   they said *leave this pair alone* — and a human who wants the pair queued has T2.23's
   surface for exactly that.
2. **The tombstone lapses when either side's content changes**, on the same principle as the
   refine marker: the human's judgement was about these two texts, and once a text moves the
   judgement is stale and dreaming may re-ask. `MemoryUpdate.content` is wire-editable
   (`app/schemas/memory.py:85`), so this is a live path, not a theoretical one.

   **A second, blunter lapse path, which revision 1 documented for neither marker.**
   `MemoryUpdate.metadata` is also wire-editable (`:89`), and
   `PostgresMemoryRepository.update` **replaces `metadata_` wholesale** —
   `setattr(memory, "metadata_", value)` (`app/repositories/relational.py:84-85`), not a
   merge. So **one `PATCH /memories/{id}` carrying `metadata` destroys the tombstone and
   T2.12's refine marker together.** Both fail open: a destroyed tombstone re-proposes the
   pair, a destroyed refine marker re-runs the refine. Neither is data loss and neither is
   T2.13's to fix — the marker predates this task and the replace-not-merge semantics are
   the memory-update door's — but documenting only the content path while the blunter one
   goes unnamed is the asymmetry the reviewer caught. **Named here, and named to T2.23 in
   §9.2**, since a bulk edit is the realistic way it fires. §8 O6 records that no task owns
   the underlying replace-not-merge question.
3. **It records what it claims and nothing more.** Like the refine marker, the tombstone is
   *suppression bookkeeping* — "a human undid this pairing, against these two texts" — and
   not a claim that the pair is not a subsumption. Any other caller of `supersede()` is
   unaffected.

#### Associate re-derivation is accepted, and here is the citation

Undoing an associate whose inverse deleted the row lets the next cycle re-derive it. **This
is acceptable and needs no tombstone**, on a ground the subsume case does not have: the pair
already has a purpose-built, permanent suppression mechanism owned by another task.
`hygiene_state` survives every re-derivation through two mechanisms neither of which may be
dropped alone (the pass-keyed `jsonb_set` and `near_duplicate_block`'s Python carry-forward,
`memory_dream.py:887-904`), so a human who means *stop showing me this pair* dismisses it in
T2.23 and it stays dismissed. Undo of an associate means *remove this edge*, which is a
smaller claim and is honestly satisfied by a bounded window (doc 08 §7, and T2.12 D8's
explicit non-permanence note). The digest says so in the action's rendered detail rather
than leaving the user to discover it.

#### If the controller disagrees

The tombstone is **Step 6, and it is separable**. Dropping that one step leaves every other
Done-when satisfied; the ruling then becomes *"re-application is accepted"* and the digest
must carry an honest, non-dismissible note on every subsume action saying the pair will be
re-proposed on the next cycle. I consider that inadequate — it is a documentation fix for a
behavioural defect — and I record the preference here so the choice is visible rather than
silent. §9.1 files the Tier-2 amendment row for ratification.

### D10 — Two disclosed edits to `memory_dream.py`, and nothing else

The brief permits changing the producer's module *if I say so*. I say so, here, in full.

| Edit | Step | Size | Why it cannot be avoided |
|---|---|---|---|

`supersede.py` is **not** touched. The events vocabulary is touched exactly once, to add
`undone`, in its own commit ahead of the emitter (Step 1).

### D11 — What T2.13 does *not* build

- **No schema change.** No index on `events.id`, no partial index, no new table. §1.3 and
  §1.6 carry the numbers. The baseline serialises through one owner per epic and avoiding

## 8. Open questions

**O1 — Does `events` want an id index once undo exists?**
The baseline's own DDL comment says *"nothing joins events by id"* (`0001_baseline.py:997-999`);
T2.13 makes that false. At today's retention and volume the retention-bounded lookup prunes
to one or two children and needs no index (§1.3, §1.6). **Not resolved by T2.13, and
deliberately not acted on**, because an index is a baseline edit and the baseline serialises
through one owner per epic. Recorded so the schema owner meets it as a known consequence
rather than a surprise, and so a later reader does not conclude the comment was still true.

**O2 — One residual double-undo race, named rather than smoothed away.**
D4 step 3's post-lock validation closes the ordinary case. The residue: two *concurrent*
undos of a refine whose `before` state happens to equal its `after` state (a model that
proposed the summary already in place — reachable, since `apply_refine` writes whatever was
proposed without an equality skip) can both pass the compare-and-swap. The restored state is
identical either way, so this is a duplicated journal row, not data loss. The cheap close is
an equality skip in `apply_refine`, which is T2.12's module and not proportionate to the
symptom. **Recorded, not fixed.**

**O3 — Should `undo_batch_id` be addressable?**
A "undo the undo of batch X" affordance would need it as a query key. Doc 08 §7 names no
redo and T2.38's Done-when asks for none, so T2.13 emits the id and indexes nothing.
Flagged because T2.23's bulk actions may want to group by it.

**O4 — Four of doc 08 §7's seven reversible action kinds have no producer here.**
Fact promotion/demotion, human ratification, fact invalidation and article re-synthesis are
T2.09, T2.11, T2.34 and T3.02. T2.13's inverse table is keyed on `payload.action` over the
`consolidated` stream, so a fourth action kind is a new row in one mapping plus its inverse
— **but only if its producer journals into the same stream with a before/after payload.**
Nothing today forces that. Whoever ships the next reversible action inherits the choice;
naming it here is cheaper than each of them rediscovering it.

**O6 — Nobody owns `MemoryUpdate.metadata`'s replace-not-merge semantics.**
`PostgresMemoryRepository.update` assigns `metadata_` wholesale
(`app/repositories/relational.py:84-85`), so one PATCH carrying `metadata` clears every
subsystem's marker under it at once — today T2.12's refine marker and T2.13's subsume
tombstone, tomorrow whatever T2.16 keys under `dream`. Both current cases fail open, which
is why this is recorded rather than fixed from this lane: changing the door to merge is a
wire-contract change affecting every `metadata` writer, and doing it from a consolidation
task is the cross-cutting-change-in-a-feature-commit pattern this epic has declined four
times. Recorded so the third marker's author meets it as a known bound.

**O5 — Does T2.23 undo through the service or the HTTP door?**
T2.23's Done-when says "undoable through the T2.13 primitive". `dream_undo.undo(session,
event_ids=…, actor=…)` is importable and takes the caller's session, which is the shape a
bulk action wants. Recorded in §9.2 as the answer, but T2.23 owns confirming it.

### 9.2 For **T2.23** (the hygiene queue)

- **The undo primitive is `dream_undo.undo(session, *, event_ids, actor) -> UndoBatch`.** It
  takes your session, opens no transaction and commits nothing. Per-item undo is a batch of
  one through the same function — there is no second entry point.
- **Three outcomes, not two, and the third one is yours to handle** (D6). Returning means
  every named action is restored and uncommitted. `UndoRefused` means **nothing was
  written** and your session is clean — report it and carry on, no rollback needed. **Any
  other exception means restores are already in your session**, because `dream_undo` owns no
  savepoint and cannot roll itself back: **you must call `session.rollback()`.**
- **This is the one way to build a partial, unjournalled undo out of this primitive**, and
  it is the shape a bulk-action loop reaches for by default: catching broadly per item and
  continuing on the same session commits half an undo, which is what your own Done-when and
  T2.13's clauses 2 and 3 both forbid. The HTTP door gets the rollback for free from the
  request-scoped session dependency; **you do not.** Either wrap each item's `undo()` in its
  own transaction, or let the exception propagate.
- **A `metadata` PATCH destroys both dream markers.** `MemoryUpdate.metadata` is
  wire-editable and the repository replaces `metadata_` wholesale
  (`app/repositories/relational.py:84-85`), so a bulk edit carrying `metadata` clears
  T2.12's refine marker and T2.13's subsume tombstone together. Both fail open, so this is a
  bound to know rather than a bug to route around — but a bulk action is the realistic way
  it fires, so merge rather than replace if you ever write `metadata` from the queue.
- **Your bulk actions journal per item** (your own Done-when) and mine does too, sharing an
  `undo_batch_id`. If you want a bulk action itself undoable, journal it into the
  `consolidated` stream with a `before`/`after` payload and an `action` name, and add one
  inverse to `dream_undo`'s mapping — see §8 O4 for the constraint that makes this work.
- **Your `hygiene_state` write is what my associate undo's compare-and-swap sees.** Once you
  move a block to `confirmed` or `dismissed`, the associate action that created it becomes
  un-undoable with reason `state_changed`. That is deliberate: an undo that deleted the row
  would take your triage with it (D5, T-ASC5). Nothing for you to do — but do not "helpfully"
  exempt yourself from it.
- **Write back with `jsonb_set` on `'{dream,near_duplicate,hygiene_state}'`, never
  `SET properties = …`** — T2.12 §9.3's binding constraint, now doubly binding because my
  inverse reads the same block.
- The within-cycle ordering item (associate applied before a subsume retiring its endpoint)
  is yours; D7 states what my digest does with it and why it needs no edit when you land.
