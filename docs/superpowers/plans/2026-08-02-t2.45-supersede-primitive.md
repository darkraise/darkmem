## 3. The design decisions, made executable

### D1 — Module layout, and what "single path" means in code

Doc 08 §2.2 is explicit that `supersede()` is **"a new caller of an unchanged contract,
not a new lifecycle"**, that "the write-time detector (§2.1) stays the fast path and the
primitive stays the slow path", and that "the two never disagree because both write the
one pointer under the one CHECK." The *guarantee of agreement is named as the CHECK plus
the single pointer* — explicitly not a shared function.

**Ruling: the write-time detector does not become a caller of the primitive.** Four
reasons, in ascending order of force:

1. **Shape.** The detector issues one set-based `UPDATE` over N candidates
   (`supersession.py:192-196`). The primitive is necessarily per-memory: it reads the
   candidate's status and project and the successor's project before it writes. Routing
   N candidates through it turns one statement into N round-trips **inside Phase 5's
   savepoint B** — a hot-path regression bought for a Tier-C tidiness.
2. **Redundancy.** The detector's six-rule gate already establishes everything the
   primitive re-checks (same project, `status='active'`, strictly older). The primitive's
   guards would be dead weight on the fast path.
3. **The corpus already builds on there being two writers.** `supersession_hold.py:48-55`
   checks the newer-superseder comparison rather than assuming it, and says why in as
   many words: *"``memories.status`` has a second future writer -- doc 08 §3.4's status
   bridge (T2.45) -- whose guards are about *fact invalidation* and say nothing about
   timestamps."* Collapsing to one writer would make that check dead code. Removing a
   check the corpus deliberately added is not this task's call.
4. **The doc's own words.** "Stays the fast path" and "stays the slow path" are not
   compatible with one calling the other.

So "single path" scopes exactly as the Done-when scopes it: *"the single path by which
**consolidation** supersedes anything."* Consolidation is the Tier-C dream-job family.
The enforceable statement is therefore two claims, and each gets its own scan:

> **Claim A.** No module under `backend/app` other than `app/services/supersede.py` and
> `app/services/supersession.py` writes `memories.superseded_by` or `memories.status =
> 'superseded'`.
>
> **Claim B.** No module under `backend/app` other than `app/services/pipeline.py`
> references `detect_supersessions`.

Together A and B raise the cost of a second door: a consolidation module cannot hand-roll
the flip (A) and cannot name the detector (B), so the straightforward ways to bypass
`supersede.py` fail the build. **What they do not establish is that consolidation
*cannot* reach the fast path.** B forbids a *direct reference* only; a dream job that
drives the ingest pipeline reaches `detect_supersessions` transitively through
`pipeline.py` with nothing tripping. Invariant 15's own scan does not close that either —
it points the other way, stopping capture and retrieval from reaching the dream family,
not the reverse. Done-when 1 is therefore satisfied by the scans **plus** the reviewed
absence of such a caller, and a later gate claim must not read the scans as a proof of
it. Revision 1 asserted the stronger thing; it was wrong.

**Enforcement is an AST scan, not a line scan.** The line-scan precedent
(`test_supersession_blocker.py:850-867`) reads whole lines and skips only `#` comments,
which is why `supersession_hold.py`'s own docstring has to avoid naming the applier
(`:155-158`). That cost is unacceptable here: four modules legitimately *discuss*
`detect_supersessions` in prose (§1), and a line scan would either fail the build or need
four exemptions that also blind it. An AST walk excludes comments and docstrings
structurally, and matches T1.03's vendor-literal precedent. The scan rules:

*Claim A (`_forbidden_pointer_writes`), allowlist `{supersede.py, supersession.py}`:*

- **A1** — `Assign` / `AnnAssign` / `AugAssign` whose target is an `Attribute` with
  `attr == "superseded_by"`. Catches `memory.superseded_by = x`. Does **not** catch the
  model's own column declaration (`models/memory.py:67`), whose target is a bare `Name`.
- **A2** — inside a `Call` whose func is an `Attribute` named `values`, or a `Call` to
  `Memory(...)`: a `keyword(arg="superseded_by")` **or** a `Dict` key that is the string
  constant `"superseded_by"`. The dict-literal half matters — SQLAlchemy accepts
  `update(Memory).values({"superseded_by": ...})`, which produces no `keyword` node at all
  and which revision 1's rule walked straight past. Deliberately scoped to those two call
  shapes so `memories.py:46`'s `superseded_by=memory.superseded_by` — a *response*
  construction, a read — is not flagged.
- **A2b** — a `Call` to `setattr` whose second argument is the string constant
  `"superseded_by"`. Same gap as the dict form: an attribute write that carries no
  `Attribute` target for A1 to see.
- **A3** — any string `Constant` matching `UPDATE\s+memories` (case-insensitive) **and**
  containing `superseded_by` or the literal `superseded`. Catches raw-SQL flips.

*Claim B (`_forbidden_detector_references`), allowlist `{pipeline.py}`:*

- **B1** — an `Import` / `ImportFrom` naming `app.services.supersession`, or any `Name` /
  `Attribute` resolving to `detect_supersessions`.

**What the scans do and do not prove, stated rather than implied — and the statement
covers every rule, not just A3.** A3 misses a flip written with a bound parameter
(`SET status = :st`). A2 and A2b enumerate the write forms that exist today and miss a
computed attribute name (`setattr(m, col, v)`) by construction. B1 sees direct references
and not transitive reach, per the paragraph above. So the scans are a **tripwire that
makes a second writer's arrival loud** — the same thing the blocker's scan is, and the
same thing it claims to be — not a proof of absence. Overclaiming any one of them would
be worse than the gap it hides, because a reader trusts a guard; that is why the two
absolute sentences revision 1 carried are gone rather than softened.

Both scans get the two properties the T2.03 review made non-negotiable: a **vacuity
floor** (`len(paths) > 100`, so a mis-resolved root cannot pass by scanning nothing) and
an **in-suite negative control** that synthesises a violation of each rule and asserts the
scan flags it — the guard's teeth proven every run, not once by hand.

**Module layout.** One new service module, three layers, mirroring
`verification_ladder.py`:

```
app/services/supersede.py
    OPEN_BELIEF_PREDICATE              # imported from knowledge_triples post-merge (§9.1)
    BridgeOutcome                      # Literal["supersede", "deprecate", "no_change"]
    BridgeDecision       (frozen)      # the decision record
    SupersedeResult      (frozen)      # what the write actually did (incl. no-ops)
    decide_status_bridge(...)          # PURE — no session, no clock
    supersede(session, ...)            # the primitive — the write
    deprecate(session, ...)            # the guard-1-failure arm — the write
    adjudicate_status_bridge(session,) # impure: reads guard inputs, calls decide
    apply_status_bridge(session, ...)  # adjudicate + write, T2.12's entry point
```

The two **reads** live on the repository, not here:

```
app/repositories/fact_sources.py
    FactSourceRepository.memory_sources_for_fact(fact_id)   # guard 1's input
    FactSourceRepository.sourced_triples(memory_id)         # guard 2: (total, open)
```

**Guard 2 gets exactly one repository method returning both numbers, never two.**
Revision 1 listed a `has_open_triple` beside a `sourced_triple_count`, which is precisely
the shape in which a caller checks openness and forgets the floor — and the floor is the
only thing standing between an unlifted memory and wholesale retirement (D2). One call,
one tuple, both numbers or neither.

They belong there because both are provenance reverse-lookups over `fact_sources`, and
`facts_for_source` (`fact_sources.py:440-476`) is already exactly that shape, joining
`knowledge_triples` from the repository. Keeping the SQL out of `supersede.py` sharpens
the single-path story: the one module the scan allowlists contains one write and nothing
else to audit.

`memory_sources_for_fact` has a second consumer by design — it is also how T2.12
enumerates the candidate memories of an *invalidated* fact. One method, two callers, no
second spelling of the join.

### D2 — The exact predicate behind each guard

**Guard 2 uses `ux_knowledge_triples_open`'s predicate. Guard 1 uses row existence.**

#### D2.0 — The evaluation order, as ruled

Doc 08 §3.4 as amended at `d99dd92`: **guard 2 is absolute and is evaluated first.** The
two guards are not a chain. Guard 2 answers *may this memory's status change at all*;
guard 1 answers *which change*.

```
does the memory still assert any live fact?
  yes -> no_change      (guard 2 is absolute; guard 1 is never consulted)
  no  -> exactly one live source for the invalidating triple?
           no  -> deprecated, pointer NULL
           yes -> is that successor strictly newer?      (D7, not from the ruling)
                    no  -> no_change      (never deprecated — see D7)
                    yes -> superseded, pointer set
```

The first two levels are the ruling's, verbatim. **The third is D7's and is not in doc 08
§3.4** — it is shown here because this tree is what gets transcribed, and revision 3 left
it quoting the ruling alone while stating the narrowing two sections later.

`decide_status_bridge` implements exactly this shape, with the ruling cited at the
branch. The both-fail cell — guard 1 fails *and* guard 2 fails — resolves to `no_change`,
and it is the cell that carried the contradiction, so it gets its own hard test row
(§5 T2b) rather than being left to fall out of the other arms. Under the rejected
chain-order every other arm of §5 produces an identical outcome, so without T2b an
implementer who transcribed the old flowchart would pass this plan's whole suite while
deprecating live-knowledge memories.

#### Guard 2 — "every live triple the candidate memory asserts is expired or invalidated"

Doc 08 §3.1 reserves *live* for `expired_at IS NULL`, "which still counts window-closed
rows as live history". §3.4 spells guard 2 as "expired **or** invalidated". A
window-closed row has `invalid_at` set — it **is** invalidated, verbatim in the doc's own
word. So guard 2 asks whether the memory still sources a **currently-open** belief, which
is the negation of `ux_knowledge_triples_open`'s predicate:

```
expired_at IS NULL AND invalid_at IS NULL
```

The baseline says so in its own voice: `0001_baseline.py:501-506` comments the unique as
*"At most one CURRENTLY-OPEN belief per fact. Window-closed rows (invalid_at set) leave
the unique's scope but remain live history."* Two predicates, two questions, one index
each — `ix_knowledge_triples_live` answers "what is retained as history",
`ux_knowledge_triples_open` answers "what is currently believed". Guard 2 is the second
question.

**Why reading `live` here is not a subtle miss but a total one.** Under
`expired_at IS NULL`, a window-closed row counts as still-live. Stale-on-arrival (§3.2)
closes the *older* row's window on every legitimate correction — so every memory whose
fact was ever replaced by a newer belief permanently holds a window-closed row, guard 2
never holds, and the bridge is **structurally unreachable on exactly the memories it
exists for**. Not a wrong answer at the margin: no answer at all.

The predicate, driven from `ix_fact_sources_kind_ref`:

```sql
SELECT EXISTS (
    SELECT 1
    FROM fact_sources fs
    JOIN knowledge_triples kt ON kt.id = fs.fact_id
    WHERE fs.source_kind = CAST(:kind AS text)
      AND fs.source_ref  = CAST(:ref  AS text)
      AND kt.expired_at IS NULL
      AND kt.invalid_at IS NULL
)
```

Four properties of that statement are load-bearing:

1. **`:ref` is `memory_source_ref(memory_id)`, never `str(memory_id)`.** This read is
   **fail-open**: a lookup that finds nothing makes guard 2 hold, and guard 2 holding is
   what *permits* a status change. A braced or upper-cased id would therefore retire a
   memory on no evidence. The mitigation is the one `fact_provenance.py:127-144` already
   established — route every ref through the single minter — and it is pinned by a test
   (§5, T7) that feeds a non-canonical spelling and asserts the bridge still sees the open
   triple.
2. **No project filter, deliberately.** `fact_provenance.py:36-42` gives the reason and it
   applies verbatim: a memory id is globally unique and names exactly one row, so every
   `('memory', id)` row belongs to this memory whatever project the fact carries. A triple
   in another project that this memory still sources is still live knowledge the memory
   carries, and dropping it from the active view is the harm guard 2 exists to prevent.
   Note the deliberate asymmetry with guard 1, which **is** project-scoped (below); they
   are different questions about different objects.
3. **The `kind` filter is required**, for `fact_provenance.py:66-72`'s reason: `source_ref`
   carries no type discriminator, so a `human` reviewer's ref or a `code` repo id would
   otherwise join nothing and read as evidence.
4. **No cast of `source_ref` to uuid.** Same planner hazard as `fact_provenance.py:89-95`.
   Here we compare two `text` values directly rather than casting `memories.id`, because
   this query never reaches `memories` at all.

**One hardening beyond the doc's letter, in the doc's stated safe direction.** Guard 2 as
written above holds *vacuously* for a memory with zero provenance rows — and that memory
is not "spent", it is **unlifted**. `fact_lift` runs on a cadence (doc 08 §5, `*/15`), so
a young memory routinely has no `fact_sources` rows at all; and
`fact_provenance._withdraw` deletes the provenance row *before* expiring the fact
(`fact_provenance.py:229-253`), so a re-extracted memory can hold an expired fact it no
longer sources. Either way the bridge would retire a memory on the absence of evidence.
So guard 2 is:

> **Guard 2 holds iff the candidate memory sources at least one triple, and none of them
> is currently-open.**

Under the bridge's intended trigger the floor is satisfied by construction (the
invalidated fact is itself one of the memory's triples), so this only ever declines to
act on a pair T2.12 should not have handed us. That is under-acting, which doc 08 §5.3
fixes as this subsystem's preferred failure direction.

**Settled at controller level**, not left as a plan-local refinement: the 2026-08-02
ruling adopts the floor with this reasoning plus the reviewer's independent verification.
It also records the floor's second effect, which reshapes a hazard revision 1 got
backwards: a **total** `source_ref` spelling miss now yields `(0, 0)`, fails the floor,
and produces `no_change` — inertness, not wrongful retirement. The residual fail-open is
narrower than revision 1 claimed and is stated exactly: it needs canonical and rogue
spellings to **mix** on one memory, so that the canonical rows satisfy the floor while a
rogue-spelled row pointing at an open triple stays invisible. That requires a producer
bypassing `memory_source_ref`, pre-exists this task, and is the same documented
limitation `supersession_hold.py:108-114` already carries. §5 T7 is written against that
narrower hazard, because the broad one is no longer reachable.

#### Guard 1 — "the invalidating triple has exactly one live source memory"

The *invalidating* triple is the newer belief whose arrival closed the candidate's fact.
Its memory source is the successor — the memory the `superseded_by` pointer will name.

```sql
SELECT DISTINCT CAST(m.id AS text) AS memory_id, m.project, m.status, m.created_at
FROM fact_sources fs
JOIN memories m ON CAST(m.id AS text) = fs.source_ref
WHERE fs.fact_id     = CAST(:fact_id AS uuid)
  AND fs.source_kind = CAST(:kind    AS text)
ORDER BY 1
```

**"Live" here qualifies a *memory*, and doc 08 does not define it.** §3.1 reserves the
word for the fact axis; `memories` has no `expired_at`. The 2026-08-02 ruling settles the
gap **at controller level** as **row existence — the join finds a `memories` row** —
carrying the three arguments below and the reviewer's independent verification of each:

- The memory analogue of belief-withdrawal is *deletion* (the TTL sweep, the interactive
  delete). `fact_sources.source_ref` is a soft ref with no FK, so a withdrawn memory
  leaves a dangling ref behind. Existence is exactly the test
  `fact_provenance._ORPHANED_PROVENANCE` (`:157-168`) already uses for orphanhood.
- **Reading it as `status='active'` would be wrong in a specific, damaging way.** The
  successor is a memory that just asserted a newer belief; nothing requires it to be
  active — it may itself have been superseded by a still-newer memory in the same dream
  cycle. Requiring `active` would fail guard 1 on a legitimate chain and send the
  candidate to `deprecated`, destroying the very lineage the pointer exists to record.
  The lineage reads (`relational.py:26,61`, `MemoryResponse.predecessors`) walk pointers
  regardless of status.
- Existence is also exactly the condition under which the pointer is **writable**:
  `fk_memories_superseded_by` requires existence and nothing else. A guard that permits a
  value the FK rejects is a 500; one that rejects a value the FK permits is a needless
  deprecation.

Guard 1 then holds iff, after two exclusions, exactly one memory remains:

- **The candidate itself is excluded before the count is taken**, not counted then
  rejected. The question is "which *other* memory replaced this one"; a memory cannot be
  its own successor. The write-time detector guards the same degeneracy positionally
  (`supersession.py:110`, `.where(Memory.id != new_memory_id)`). Excluding rather than
  rejecting means a triple sourced by `{candidate, successor}` still yields a
  well-defined successor, which is the generous-but-safe reading. *The alternative —
  count first, fail guard 1 on any self-source — is named here so the choice is visible;
  it would deprecate a memory that has a perfectly good successor.*
- **A successor in a different project fails guard 1** and falls to `deprecated`.
  Supersession never crosses the project boundary (doc 08 §2.1 rule 1: "it never crosses
  the isolation boundary"). `deprecated` with a NULL pointer is precisely "retired without
  a single live successor", so the fallback is the honest outcome rather than a
  workaround.

**Guard 1's read is fail-closed in the opposite direction to guard 2's**, and both
directions are stated: a mis-spelled or dangling ref drops the count to 0, which
*deprecates* rather than superseding. That is a status change on thin evidence — bad, but
strictly less bad than guard 2's fail-open, and it is the same limitation
`supersession_hold.py:108-114` records for its own positive join. It is written down here
rather than papered over with a filter that cannot fix it.

### D3 — The purity boundary, and why it applies differently to a writer

T2.03 made `decide()` pure because a promotion decision is an **input** to a status write
and must be replayable — a pure decision can be re-run from the journal to audit it
(`verification_ladder.py:307-322`). T2.04 and T2.60 obey the same boundary as ladder
inputs living in their own modules.

Our primitive is a **writer**, so the boundary cannot apply to it unchanged. It applies
like this:

- **The bridge's *decision* is pure and must be** — for a reason stronger than symmetry.
  Doc 08 §7 makes every consolidation action undoable from its journaled before/after
  payload, and the digest must be able to *explain* why the bridge did what it did. A
  three-way outcome derived inside a write is a decision no digest can reconstruct. So
  `decide_status_bridge(...)` takes already-read inputs and returns a `BridgeDecision`
  with every input that produced it — the same "returned whole rather than applied
  silently" contract as `LadderDecision` (`verification_ladder.py:248-255`). No session,
  no clock: the guards are set-membership questions over stored state, and reading the
  wall clock would make a replay of the same inputs answer differently.
- **The session-reading adjudication is a separate function**, `adjudicate_status_bridge`,
  exactly as `recompute_fact` is separate from `decide`.
- **The write is the primitive**, and it is the one thing the single-path scan points at.
  It lives in the same module as the decision rather than behind a repository method,
  because the module boundary *is* the enforcement surface: an allowlist naming a
  repository would allow every write in that repository.

So: one module, three layers. The decision half is pure; the read half is impure and
thin; the write half is the primitive.

### D4 — Statement ordering, transaction shape, and the CHECK at every step

**The flip is one statement. Always.**

```sql
UPDATE memories
   SET status = 'superseded',
       superseded_by = CAST(:successor AS uuid)
 WHERE id = CAST(:memory_id AS uuid)
   AND status = 'active'
RETURNING id, status, superseded_by, project, updated_at
```

and the guard-1-failure arm, likewise one statement:

```sql
UPDATE memories
   SET status = 'deprecated',
       superseded_by = NULL
 WHERE id = CAST(:memory_id AS uuid)
   AND status = 'active'
RETURNING id, status, superseded_by, project, updated_at
```

The full ordering inside one caller-owned transaction:

1. `SELECT status, superseded_by, project, created_at FROM memories
   WHERE id = CAST(:id AS uuid) FOR UPDATE`. The `FOR UPDATE` takes the row lock for the
   rest of the transaction, so every value read here is authoritative until commit — no
   concurrent session can flip the row underneath the decision, and the journal's
   before-values cannot be made a lie. This is the idiom `close_window`, `expire` and
   `set_verification_status` all use and all explain
   (`knowledge_triples.py:202-212, 256-267, 521-535`).
   **`created_at` is read here for D7's `successor_is_newer`, and its absence in revision
   3 was a real gap** — revision 3 widened step 2 by the *successor's* `created_at` and
   step 1 by `superseded_by`, but left the *candidate's* `created_at` unsourced, and
   nothing else supplies it (`sourced_triples` returns two counts;
   `memory_sources_for_fact` covers the successor side only). Step 3's "pure, on values
   now in hand" was therefore unsatisfiable as written. An executor cannot miss it — the
   predicate will not run without the value — but D7.1's claim to have been "checked
   deliberately rather than assumed" did not hold, and that claim is retracted in D7.1
   rather than quietly repaired.
   **`superseded_by` is read here too, and D6 journals what was read** — never a
   hard-coded `null`. It is true today that an `active` row's pointer is always NULL, so a
   literal would be correct by construction; but "correct by construction" is verbatim the
   criticism D6 levels at the fast path's implicit-NULL payload, and a plan cannot hold the
   fast path to a rule it exempts itself from. Both columns ride a select being issued
   anyway.
   **Refusal precedence is pinned here (N3): the candidate's own status is decided first.**
   If the status read above is not `active`, `supersede()` returns the status reason
   (`already_superseded` / `terminal`) **without** evaluating `successor_is_newer`, without
   the step-2 successor read, and without issuing the UPDATE. So a non-active candidate
   whose successor also happens to be non-newer reports the status reason, deterministically
   and regardless of timestamps. This is the natural reading of the step order — the
   candidate is the row being written, and a refusal about the row itself outranks one
   about its proposed pointer — and it is what makes D5's no-op cells timestamp-independent
   (D7.1).
2. Read the successor's `project`, `created_at` and `id` (`supersede` only), same
   transaction, one statement — `project` for guard 1's scope check, the other two for
   D7's `successor_is_newer`.
3. `decide_status_bridge(...)` — pure, on values now in hand.
4. **One** `UPDATE`, per the statement above.
5. `record_event(...)`, and only if step 4 returned a row. A journal failure must never
   undo the write it describes, so it runs after, never gates
   (`supersession.py:198-212` states this rule for the fast path).

**The CHECK's status at each step**, which is what "holds through every transition" means:

| Point | Row state | `chk_superseded_has_pointer` |
|---|---|---|
| Before step 4 | `active`, pointer NULL | holds — `status != 'superseded'` |
| During step 4 | *no observable intermediate state exists* | Postgres evaluates a row CHECK once per row per statement, not per column assignment |
| After `supersede` | `superseded`, pointer set | holds — both branches of the OR are satisfied |
| After `deprecate` | `deprecated`, pointer NULL | holds — `status != 'superseded'` |
| Any no-op (D5) | unchanged | holds — nothing was written |

The single-statement form is what makes row 2 true, and it is proven load-bearing rather
than asserted: §5 T5 issues the two-statement form against a real database and asserts it
raises `IntegrityError` naming `chk_superseded_has_pointer`.

**The primitive never deletes.** Doc 08 §2.2 requires it to *"demote any dependents before
it would ever delete a referenced memory"*, and the honest discharge of that clause is
that the antecedent is false by construction: the primitive issues one `UPDATE` and no
`DELETE`, so it can never trip the `ON DELETE SET NULL` path. `demote_dependents`
(`supersession.py:115-137`) stays the single demotion helper for the two paths that do
delete, and the primitive does not join them. This is asserted, not merely intended: §5
T6's scan asserts `supersede.py` contains no `DELETE` statement and no reference to
`demote_dependents`, so a later edit that adds a delete without the demotion fails the
build rather than aborting a TTL batch in production.

**Transaction shape: the primitive does not commit, and opens no session.** It runs inside
the caller's transaction, exactly as `detect_supersessions` does (`supersession.py:160`,
"Safe to call inside an existing transaction; callers commit"). Invariant 11 forbids
opening a fresh session over rows the caller still holds locks on.

**Savepoints are the caller's.** The primitive opens none. Phase 5 made the same call for
the fast path — savepoint B is the pipeline's, not the detector's. This has a consequence
T2.12 inherits and must honour, recorded here as an assumption (§8, A2): **each memory's
bridge application must be its own savepoint**, so one failure cannot abort a whole dream
cycle.

### D5 — Monotonicity: re-entry on an already-moved memory

Doc 08 §2.1: *"the bridge only ever adds a supersession, never reverts one."* Applied to
both writers:

| `M.status` | `supersede(M, S)` | `deprecate(M)` |
|---|---|---|
| `active` | flips to `superseded`, pointer `S`; journals `superseded` | flips to `deprecated`, pointer stays NULL; journals `deprecated` |
| `superseded` | **no-op** — never re-pointed. Re-pointing would silently rewrite a lineage the digest already reported | **no-op** — deprecating would set the pointer to NULL, which *reverts* a supersession. This is the cell monotonicity exists for |
| `deprecated` | **no-op** — `deprecated` is terminal in the documented lifecycle (`active → superseded → deprecated`), and the fast path's rule 2 declines a non-active candidate for the same reason. Two paths, one rule | **no-op** — idempotent |

Three properties make the table real rather than decorative:

- **The rule is decided from the locked read, and the `WHERE` clause is belt-and-braces.**
  *Corrected in revision 4, because pinning N3's precedence changed which half enforces.*
  D4 step 1 takes `FOR UPDATE`, which holds the row for the rest of the transaction, so
  the status it read cannot go stale and the code-level early return is authoritative —
  that is exactly what lets the refusal precedence be pinned at all. `AND status='active'`
  stays on both UPDATEs as defence for a future caller that reaches the write without the
  lock, but it is **not** what the single-threaded suite exercises. Revision 3 said the
  rule lived "in the `WHERE` clause, not in Python" and that a Python read-then-write is a
  TOCTOU window; with the lock held that overstated the case, and §5's drill table is
  corrected to match.
- **A no-op journals nothing.** `events` is append-only, so "a row means a transition"
  has to be true by construction — the rule `expire`, `close_window` and
  `set_verification_status` each state in their own docstrings
  (`knowledge_triples.py:196-200, 249-254, 406-413`). Zero rows returned from the UPDATE
  means zero events.
- **A no-op is *reported*, not silent.** `SupersedeResult` carries an
  `applied: bool` and a `reason` (`"applied" | "already_superseded" | "terminal" |
  "not_found" | "cross_project" | "self_reference" | "successor_not_newer"`), so T2.12 and
  the digest can see the declined action. A silently-swallowed no-op is indistinguishable
  from a completed one to every caller, which is how a bridge that has stopped working
  goes unnoticed. `successor_not_newer` is D7's, and is enumerated here because this list
  is the surface an executor transcribes — revision 3 mandated the refusal two sections
  later and left the list six-valued, which is an inconsistency trap rather than an
  omission a reader would catch.

Two refusals belong on the same surface and are also `reason` values rather than
exceptions: **self-supersession** (`superseded_by == memory_id`) and a **cross-project
successor**. Neither is an error the caller can fix by retrying; both are ordinary
"declined" outcomes on the digest.

### D6 — Journaling

| Arm | `event_type` | `object_type` | Payload |
|---|---|---|---|
| `supersede` | `superseded` | `memory` | `{"before": {"status": <prior read>, "superseded_by": <prior pointer, read>}, "after": {"status": "superseded", "superseded_by": "<S>"}, "reason": "status_bridge", "invalidating_fact_id": "<F>"}` |
| `deprecate` | `deprecated` | `memory` | `{"before": {"status": <prior read>, "superseded_by": <prior pointer, read>}, "after": {"status": "deprecated", "superseded_by": null}, "reason": "status_bridge", "invalidating_fact_id": "<F>"}` |

Both types are already in the closed vocabulary (`events.py:55-56`), so **no taxonomy-first
widening is needed** — and `deprecated` has had no emitter until now, which is a
confirmation the vocabulary was written with this bridge in mind rather than a coincidence.

**The `before` block carries `superseded_by` explicitly — read from the row in D4 step 1's
`FOR UPDATE` select, not written as a literal `null`** — where the fast path's payload
omits it (`supersession.py:206-212` writes `{"status": "active"}` only). Doc 08 §7's undo
table requires the inverse to *"restore prior `status` + `superseded_by` atomically"*, and
an implicitly-NULL pointer is a trap for T2.13: the undo would have to know that a
pre-supersession pointer is always NULL, which is true today only because the fast path
never touches a non-active row. Spelling it costs one key. The fast path's payload is
**not** changed — widening it would touch Phase 5 for no benefit — so T2.13 must accept
both shapes, which §9 raises as a coordination item.

`project` on the event is the **candidate memory's** project, read in step 1 of D4's
ordering. Guard 1 has already established that the successor shares it, so there is no
ambiguity to resolve.

### D7 — The successor must be strictly newer (settled, 2026-08-02)

The fast path forbids this explicitly and the bridge inherits nothing from it. Doc 08
§2.1 rule 5 requires a candidate to be **strictly older** than the superseder, with an
`(created_at, id)` tie-break, and CLAUDE.md records why in as many words: *"without this
guard a reprocess flips two same-relation memories into mutual supersession; both vanish
from the default `active` view."* Doc 08 §3.4 carries no ordering rule at all, so the
omission below is doc-conformant — which is exactly why it has to be named rather than
assumed away.

**The reachable failure.** Two memories M1 and M2, both spent (every triple they source
is window-closed, so guard 2 holds for each). M1's fact was invalidated by a triple
sourced solely by M2; M2's by a triple sourced solely by M1. Guard 1 holds for both. The
bridge supersedes M1 → M2, then M2 → M1. Both leave the active view, and monotonicity
means nothing puts either back. D5's `WHERE status = 'active'` does not help: it guards
the *candidate*, and when the second flip is adjudicated M2 is still active — only M1 was
touched.

**The rule, approved 2026-08-02 and logged as a Tier-2 amendment in
`docs/planning/tasks/E2-truth-core.md`: the successor must be strictly newer than the
candidate — `created_at >`, with an `id` tie-break for equal timestamps — mirroring the
fast path's rule 5. A successor that is not strictly newer is refused with the `reason`
value `successor_not_newer`.** Four reasons, the third decisive:

1. **It aligns the slow path with the fast one rather than inventing a constraint.** The
   corpus already blesses this exact ordering, for this identical hazard, in
   `detect_supersessions`' rule 5 (doc 08 §2.1). The bridge is adopting a rule the store
   already has, not acquiring a new one.
2. **It makes the two writers of one pointer agree about what a supersession is.** Doc 08
   §2.2's claim that "the two never disagree" is weaker if one writer can produce a pointer
   shape the other forbids.
3. **The concrete leak, already shipped — T2.60 depends on the property and documents the
   dependency.** `supersession_hold.py:179-194` recognises a supersession signal only when
   `sup.created_at > m.created_at OR (sup.created_at = m.created_at AND sup.id > m.id)`,
   and `:48-55` says outright that the comparison is checked rather than assumed *because*
   `memories.status` has a second future writer — this bridge — "whose guards are about
   *fact invalidation* and say nothing about timestamps". So a bridge-written pointer whose
   superseder is older is **invisible to T2.60's blocker**, and a fact sourced by that
   superseded memory promotes unblocked on evidence the store already knows was replaced.
   That is a correctness leak with no error and no symptom. **This, not symmetry, is the
   reason recorded in the amendment log.**
4. **It forbids cycles of every length, not just 2-cycles**, because "strictly newer under
   `(created_at, id)`" is a strict total order and a cycle in a strict order is
   unrepresentable. A bare 2-cycle refusal (`S.superseded_by == M`) is the narrower
   alternative and is rejected for that reason — it needs a recursive CTE to generalise and
   would leave 3-cycles reachable.

**The refusal's outcome is `no_change`, and it must not fall through to `deprecate`.**
This is the detail the rule most easily gets wrong, and getting it wrong reinstates the
exact failure the rule exists to prevent. Take the mutual pair above with M1 the older.
Adjudicating M1 finds successor M2, which is newer, so M1 → `superseded`. Adjudicating M2
finds successor M1, which is older, so the refusal fires. Were the refusal to fall through
to guard 1's `deprecated` arm, M2 would be deprecated — and M1 (`superseded`) plus M2
(`deprecated`) would both leave the active view, which is precisely the two-memories-vanish
outcome D7 exists to stop. The refusal therefore short-circuits to `no_change`: the
candidate stays `active` and stays re-adjudicable by a later pass that finds it a newer
successor.

**One home for the comparison.** It is a module-level pure predicate,
`successor_is_newer(candidate, successor)`, called from **both** `decide_status_bridge`
and `supersede()` — the latter because `supersede()` is a public primitive T2.12 may call
directly without routing through the bridge, and a rule enforced on only one of two
entrances is not enforced. This is the in-house idiom for exactly this shape:
`supersession.is_supersession_trigger` (`supersession.py:40-48`) exists so the pipeline
and the detector "must agree on this predicate exactly", and its docstring records that
widening one side leaves the other discarding what the first forwards.

**The cost, stated and accepted rather than smoothed away.** `fact_lift` runs on a cadence
and a fact's `reference_time` is its source memory's `created_at`, so a backfilled
successor genuinely older than the candidate is declined and the candidate lingers as
`active` until a later pass. That is under-acting — the owner's ruling's own accepted
failure mode, in its own words *"a spent memory lingering as active until a later pass
retires it"*.

**What this narrows.** The rule tightens the bridge beyond doc 08 §3.4's letter without
contradicting it: §3.4 states no ordering rule at all, so nothing in it is overridden. It
does change what T2.12 may hand the primitive, which is why the amendment names both
tasks rather than being a plan-local refinement.

#### D7.1 — What the rule knocks loose elsewhere in this plan

*Revision 3 headed this "checked deliberately rather than assumed". **That claim is
retracted.** The sweep widened step 2's successor read and missed that the candidate's own
`created_at` — the predicate's other operand — was read nowhere, so the rule as specified
could not run. Corrected in D4 step 1. The list below is the re-done sweep, and it now
covers the refusal's own precedence as well as its fixtures.*

- **T2b is unaffected, and provably so.** Guard 2 is absolute and evaluated first
  (D2.0), so on the both-fail fixture neither guard 1 nor the ordering predicate is ever
  reached. T2b's assertions — `no_change`, `active`, NULL pointer, zero events — stand
  verbatim, and its fixture needs no `created_at` discipline at all.
- **D5's six monotonicity cells are unaffected as a table.** The ordering predicate ranges
  over the *successor*; D5 ranges over the *candidate's own* status. The two axes are
  orthogonal, so no cell's expected outcome moves. **But two of its fixtures now have a
  precondition:** the `active` row's `supersede` cell must seed a successor that is
  strictly newer, or the cell fails with `successor_not_newer` instead of flipping — a
  green-to-red failure for the wrong reason. Same for T1b, T3d, T4's supersede
  transitions, and T7's spent fixture.
- **Every fixture that expects a successful `supersede` must set `created_at` explicitly.**
  This is a genuine flake hazard, not bookkeeping: rows inserted in one transaction share
  a single server-side `created_at` (`models/memory.py:52`, `server_default=func.now()`),
  so the comparison would fall to the `id` tie-break — and `uuid.uuid4()` ids, which the
  existing supersession tests use (`test_supersession.py:40`), order randomly. A fixture
  built that way passes or fails per run. The repo already has the idiom and it is adopted
  verbatim: set `created_at` per row, and where the tie-break itself is under test pin the
  ids (`test_supersession.py:201-212` uses `uuid.UUID(int=1)` against a same-`created_at`
  pair for precisely this reason).
- **D4's step 2 read widens by two columns** — the successor row is already being read for
  its `project`, so `created_at` and `id` ride the same statement rather than a second
  round trip. **And step 1 widens by one**, for the candidate's `created_at`; see the
  retraction above.
- **`MemorySource` carries `created_at`** (Step 1), and guard 1's illustrative SQL in D2
  selects it — revision 3 left that sketch three columns wide while Step 1's dataclass had
  four, which is a stale sketch a reader would transcribe.
- **D5's reason enum gains `successor_not_newer`** — the list in D5 is the surface an
  executor copies, and revision 3 left it six-valued.
- **D5's three no-op cells are timestamp-independent, by precedence rather than by
  discipline.** Because a non-`active` candidate returns its status reason before
  `successor_is_newer` is ever evaluated (D4 step 1), a no-op fixture cannot flip its
  reason per run on a shared timestamp and random `uuid4` ids. This is the settled answer
  to the two options: **precedence is pinned, and the `created_at` discipline is therefore
  *not* extended to reason-asserting no-op fixtures**, because with precedence pinned it
  would be ceremony that guards nothing.
- **The floor-removal drill inherits the `created_at` requirement**, and the blanket
  sentence above does not reach it: that fixture expects `no_change` under *correct* code
  and `supersede` only under the *mutation*, so it is not "a fixture expecting a successful
  flip" as written. Its zero-provenance variant needs an explicitly newer successor or the
  drill reports a false pass.

## 5. Test plan — and how each negative is proven non-vacuous

The Done-when's hardest item is a **negative**: "a memory still asserting live facts is
left alone." An assertion that nothing changed passes just as well when the bridge is
inert, when the fixture is wrong, and when the ids do not match. Every negative below is
therefore proven by a **differential arm** — the *same* fixture builder, *one* flipped
bit, asserting the opposite outcome. The arm that asserts the change is what proves the
arm that asserts no change could have failed. This is the comparison style
`tests/honesty/test_demote_before_delete.py` uses for the sweep's ordering, and the
reason it gives applies here verbatim: *"if an edit ever made the two orders equivalent,
the reversed run would stop raising and this spec would say so."*

The shared fixture: memory **M** (project `p`, `active`) sources triples **F_inv** (the
one that got invalidated) and **F_other**. Memory **S** (project `p`) sources the
invalidating triple **F_new**.

| # | Test | Fixture delta from the base | Asserts | What proves it could fail |

*The finding as originally raised:*

**What the flowchart says** (`08-...md:170-178`): `G1 --> |no| DEP`. Guard 1 failing
deprecates the memory **unconditionally**, without ever consulting guard 2. The brief's own
guard table reproduces this ordering ("proceed to guard 2" on guard 1's *hold* row).

**What the prose says** (`08-...md:166`): *"Guard 2 failing means the bridge does not apply
**at all**: the memory still asserts live facts, so its status is **unchanged** —
deprecating it would drop a memory that still carries live knowledge out of the active
view over one invalidated fact, which is exactly what guard 2 exists to prevent."* And of
guard 1's failure: *"the memory is **spent** but has no single live replacement to point
at."*

**Why they cannot both be true.** The both-fail cell is reachable and ordinary: memory M
asserts F1 and F2; F1 is invalidated by a triple sourced by two memories (guard 1 fails);
F2 is still currently-open (guard 2 fails). The flowchart deprecates M. M still asserts
F2, live and being served. That is verbatim the harm the prose says guard 2 exists to
prevent — and M is not "spent", which is the prose's own precondition for the `deprecated`
outcome. The flowchart draws the guards as a chain and never contemplates the cell.

**Recommended stance: guard 2 is evaluated first and its failure is absolute.** Guard 1 is
consulted only to choose *between* `superseded` and `deprecated` once guard 2 has
established the memory is spent. Three arguments:

1. The harm the prose names does not depend on *why* the successor is undefined.
2. "Spent" is the prose's stated precondition for `deprecated`, and a memory holding an
   open fact is not spent.
3. **It is the reversible answer.** Guard-2-first writes a strict subset of what the chain
   writes — it only ever declines to act. If the ruling later goes the other way, the
   both-fail cell simply starts deprecating and no prior write needs undoing. The reverse
   is not true: chain-order writes deprecations that a later reversal cannot recall,
   because the memories are already out of the active view and doc 08 §7's undo is
   per-action from the digest, not a sweep. Under-acting is also this subsystem's stated
   preferred failure direction (doc 08 §5.3; spec §2.1).

**What settled it:** the owner's ruling of 2026-08-02, recorded as a
`.superpowers/sdd/rulings/` entry the way the 2026-07-29 supersession-blocker ruling was.
