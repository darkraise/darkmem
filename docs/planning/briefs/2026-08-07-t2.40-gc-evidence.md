## You are chartered to find the reason this gate should NOT clear

That is what a gate evidence run is for. A run that sets out to confirm G-C will find a
way to confirm it. Runbook §7 is explicit: **a number below its bar is the gate working.
Report it; never re-run until it passes, and never widen the bar to fit the result.** A
missed gate leaves G-C open and the code-deriver lane closed, and that is an acceptable
outcome of this task — a wrongly-cleared gate is not.

## The ordering property that makes this measurement mean anything

**The bar does not exist yet.** `gate-ledger.md`'s G-C table has `—` in every Bar cell.
`promotion_metrics.py` says so at its own head: it "does not state a bar", because
runbook §2 separates the model that designs the bar from the one that wrote the harness,
and **T2.40 owns the bar**.

So this task has two phases and **their order is the integrity property**:

1. **State the bars as `config` rows and commit them, before measuring anything.** The
   G-D rows are your precedent for how this is recorded — each names its config key and
   says "stated 2026-07-31, before any gate run". Yours must be able to say the same
   thing truthfully. Commit the bar in its own commit, ahead of any measurement commit,
   so the git history itself witnesses the ordering.
2. **Then measure, and verdict.**

A bar chosen after seeing the number is not a bar. If you find yourself wanting to adjust
one because the measurement came in just under, that is the moment the gate is doing its
job — record the miss.

## What must be measured (doc 20 §4, and the task's own text)

- **Promotion rate `(promoted / eligible)`, sliced by source-kind diversity.**
- **Promotion rate, sliced by which N fired.**
- **False-promotion audit** — corroborated facts later disputed or human-rejected —
  under the stated bar.
- **Every ladder transition journaled**, bar 100%.

All computed **from the `events` journal by SQL**. An unjournaled transition is an
unmeasurable one, and that is the whole reason the ladder has a sole journaller.

## Three things about this corpus you must inherit knowingly

**1. Born-corroborated facts are invisible to this run, by construction.** T2.28's lift
mints code-originated facts already at `corroborated` and its ladder branch **journals
nothing**, so those rows enter neither numerator nor denominator and never appear in the
false-promotion audit. This was verified, not assumed — a reviewer counted zero `verified`
rows after a birth plus two recomputes, and both metrics are journal-anchored in
`benchlib/promotion_metrics.py`.

The consequence the task tells you to state **where the number is recorded**, rather than
let someone discover later: once this run mints the promotion record, born rows light
`corroborated` on doc 10 §6's argument alone — *the parse is the verification* — and not
on anything this gate measured. G-C's number is a statement about the **counting** ladder,
and the badge it unlocks will also appear on rows that ladder never counted. That may well
be the right claim, since a parsed import is not an inference. Say it plainly in the
ledger anyway.

**2. Two new ladder participants landed today and the run must account for them.**

- **T2.48's citation re-verifier** marks a code citation stale and enqueues the citing
  fact for the verification recompute, which **downgrades a badge**. That is a
  corroboration demotion, deliberately never `disputed`. Decide whether a
  citation-driven downgrade belongs in the false-promotion audit's numerator: the audit
  is defined as "corroborated facts later disputed **or human-rejected**", and a stale
  citation is neither — but it is a fact that was corroborated and no longer is. State
  your reading and why.
- **T2.101's `repo_entity_merge`** folds two open triples into one when a retroactive
  entity merge collides them. It deliberately **writes no verification column** and so
  journals no `verified` transition — precisely so it does not inject an unexplained
  promotion into this metric. Verify that holds in the shipped code rather than trusting
  the claim: a fold that did journal would land directly in your numerator.

**3. A 0/0 promotion rate is under-powered, not a pass.** The Done-when is explicit that
**facts have actually flowed through the ladder**. If the corpus you measure has no
promotions, the honest verdict is that the gate cannot yet be evaluated — say so, and say
what corpus would evaluate it. Do not report `0/0` as clearing anything, and do not
manufacture flow by hand-writing journal rows: a metric measured over synthetic events
measures the fixture.

## Scope boundaries

- **Do not change the ladder, the recompute, or any promotion logic to improve a
  number.** If the measurement reveals a defect, that is a finding and a task, not an
  edit on this lane. You are measuring, not fixing.
- **Do not touch `promotion_metrics.py`'s metric definitions** to make them agree with a
  bar. If a definition is wrong, report it — changing it mid-run destroys the
  measurement's meaning.
- **Read-only against real data.** Runbook §8 permits a read-only production probe; it
  never permits a write.
- No schema change.
