## Read the block note before you read anything else — it is history now, not a blocker

T2.11 sat `blocked` from 2026-07-31 to 2026-08-06 because the judge is not qualified:
`VerificationJudge.judge()` raises `JudgeNotQualifiedError` unconditionally while
`app/services/verification_qualification.json` is absent, and no lawful qualification run
has ever happened (see the Fable analysis
`docs/planning/analyses/2026-08-05-t2.11-judge-bar.md` — the 0.8182 was branded INTERIM by
its own artifact and measured on an ineligible gold). **The 0.95 bar is right and stands.
Do not touch it, do not tune the judge, do not attempt to qualify it.** Editing the prompt
moves `prompt_sha`, hence the judge identity, and de-qualifies mechanically.

What changed on 2026-08-06 is the reading, not the facts: **the refusal is the safety
property, not the obstacle.** Because `judge()` refuses structurally and that refusal is
scan-enforced, the scan body can be written, tested against a refusing judge, and merged
with no risk that it ever adjudicates on an unqualified one. What stays gated is the
**productive run** — which is all the dependency was ever protecting. T2.41 lives in M1
now and gates the activation, not the build.

**So: your tests exercise a judge that refuses.** A test that mints a qualification record
to make adjudication run must do so through an explicitly opt-in fixture. **Never
autouse** — a fixture that opens a gate for the whole module leaves the suppression
untested everywhere at once, which is a trap this epic has already been bitten by.

## What ships

The `contradiction_scan` job body, replacing the `PlaceholderJobRunner` registered by
T2.08 in `app/services/dream_jobs.py` (`CONTRADICTION_SCAN_JOB_KEY`, line 111; its two
config fields `contradiction_scan_batch` and `contradiction_candidate_top_k` are already
declared, lines 470-480).

**The generator is combined — same-endpoint *plus* `pg_trgm`-on-`fact`, not the trigram
half alone** (doc 08 §5.3). For each fact needing a check, drained from the
`sources_changed` / newly-lifted set and restricted to servable facts not already
disputed:

1. **Same-endpoint** — facts sharing `subject_name` and/or `object_name` in the same
   project. An index lookup; `ix_knowledge_triples_live` carries it.
2. **`pg_trgm`-on-`fact`** — top-K by trigram similarity over the `fact` text.

Both are cheap SQL on the one Postgres (invariant 1), no embedding. `triple_embeddings`
stays deferred behind T2.52's measured undercount — **do not add a vector arm.**

Then: the LLM scores **only pairs whose validity windows overlap**. Disjoint windows are
legitimate succession, not contradiction (doc 08 §3.1), and scoring them manufactures
disputes. A confirmed **non-echo** contradiction feeds the §4.2 veto — non-echo meaning a
distinct origin, not the same source re-stating itself.

## Invariants that bind you

- **Invariant 15 — no dream job is reachable from capture or retrieval.** A source scan
  over `backend/app` fails the build if one is. Do not "accelerate" anything from the hot
  path.
- **Invariant 1 — one Postgres.** No new store for the shortlist.
- **A disputed fact is served labelled with both sides**, never dropped and never gated on
  review (doc 08 §6, invariant 14).
- **The veto is absolute, not a vote** (doc 08 §4.2): a single non-echo contradiction over
  an overlapping window flips the fact to `disputed`. Consensus is not truth.
- **Precision-first asymmetry.** Undercounting the candidate set only *delays* catching a
  contradiction — the preferred failure. Manufacturing one is the harm. When in doubt,
  emit fewer candidates.
- **The dream-job handle idiom.** `register_dream_jobs` takes an `llm_provider` callable
  (added by T2.12) because `app.state.llm` is replaced whole on a config save, so a
  closed-over orchestrator goes stale. Use the callable. If you add a line to
  `_ALLOWED_DREAM_JOB_LINES`, note that the allowlist matches stripped line **text** and is
  itself T2.67's known defect — add in the existing style with a note, do not fix it here.
- **asyncpg CASTs** on every raw-SQL param Postgres cannot infer.
