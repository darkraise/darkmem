**Task:** T2.102 · `Sonnet 5` · `high` · `Size: S` · Doc 13 §4 · Gate: standing
**Depends:** none. **Contract:** `docs/planning/agent-runbook.md`. **Baseline:**

## Why this is a task and not a fourth one-line fix

`frontend/src/features/activity/event-taxonomy.ts` maps the closed `EVENT_TYPES`
vocabulary onto the activity feed's five tabs. A value missing from the map surfaces
only under "all" and never on its own tab.

Three consecutive rounds have each found exactly one value missing and fixed exactly
that one: `contradiction_scanned` (T2.11), then `citation_stale` (T2.48). Each fix was
correct in isolation and **none of them was the fix**, because the map is maintained
reactively — a value lands in the closed vocabulary, its emitter ships, and nothing
fails when the map does not learn about it. The taxonomy-first rule that governs the
vocabulary itself does not reach this map.

T2.48's rescope then swept the whole vocabulary and found **seven** unmapped values
with live emitters, of which `invalidated`, `human_verdict` and `undone` fit existing
tabs cleanly.

## Read the map's own docstring first — it already anticipates half of this

The file's docstring says:

> This is a UI convenience, not a taxonomy the backend enforces — an `event_type`
> absent from every bucket below still shows under "all", it just has no dedicated tab
> (`inject`/`inject_curbed`/`setup_completed`/`auth_lockout`: none of
> capture/pipeline/verification/consolidation/code fits them cleanly, and inventing a
> sixth tab is a design call this task does not own).

**That reasoning is sound and you are not overturning it.** Some values genuinely
belong only under "all". What is wrong is that *absence* is how the decision is
recorded — which makes a deliberate omission and an accidental one look identical, in
a file where the accidental case has now happened three times.

So the deliverable is not "map everything". It is: **every emitting value is
classified deliberately, and a value that belongs only under "all" says so
explicitly** — an entry, a comment beside a listed exclusion, whatever shape you
choose — so the next reader can tell a decision from an oversight.

## What ships

1. **The pass.** Go through `EVENT_TYPES` in `backend/app/services/events.py`, find
   which values have live emitters, and classify each one deliberately. Say in the
   report which got which tab and why. Where you leave something out of the five tabs,
   record that as a decision with its reason, following the docstring's existing idiom.
2. **The guard that makes the next miss impossible.** A test that fails when a value
   with a live emitter has neither a tab nor a recorded exclusion. This is the half
   that matters — without it, this task is the fourth one-line fix in a row, just
   larger.

**Do not invent a sixth tab.** The docstring is explicit that this is a design call it
does not own, and neither do you. If your pass concludes a sixth tab is genuinely
needed, that is a finding to report, not a change to make.

## The guard is the hard part — think about what "has a live emitter" means

The guard has to compare a frontend TypeScript map against a Python list, across a
language boundary, in a suite that runs under vitest. The obvious shapes each have a
cost, and choosing is the task's real work:

- Parse `events.py`'s `EVENT_TYPES` from the frontend test. Fragile in the way
  text-scraping always is, but it has no build step and the list is a simple literal.
- Generate a checked-in TypeScript constant from the Python vocabulary. Robust, but it
  adds a generation step someone must remember to run — and a stale generated file
  fails in the same silent direction as today's bug.
- Assert on the backend side instead, where both facts are readable if the frontend
  map can be parsed from Python.

**"Live emitter" is the other half.** A value in the vocabulary with no emitter yet
(landed taxonomy-first, ahead of its feature) must not fail the build — that would
punish exactly the discipline the corpus requires. Decide how you detect an emitter
(a `record_event` call site naming the value, presumably) and say what your detection
misses.

## Scope boundaries

- **Do not change `EVENT_TYPES` itself**, or add/remove any event type. This task reads
  the vocabulary; it does not widen it.
- **Do not change the five tabs**, their names, or the feed's filtering behaviour.
- **No backend behavioural change.** If your guard lives on the backend side, it is a
  test, not a runtime check.
- T2.86 is on a concurrent lane and touches the fact-detail surface; you touch the
  activity feed. If you find yourself editing a fact-detail file, stop and re-read
  scope.
