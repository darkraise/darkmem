# T2.32 — PPR snapshot job + graph arms

`Model: Opus 5` · `Effort: high` · `Size: L` · `Depends: T2.18` (done) · `Doc: 07 §3/§4,
02 §11` · `Gate: G-C`

## What ships

The cached in-process igraph snapshot doc 07 §4 ranks PPR against, the Tier-C job that
rebuilds it, and the graph arms wired inert.

1. **`app/services/ppr_snapshot.py`** — the artefact and its spend:
   - a project-scoped **entity** graph (nodes are entities asserted by the project's
     eligible memories; edges are `entity_relations` between two of those nodes, weighted
     by how many relation rows join the pair), plus the **synonymy KNN edges** doc 04 §4.2
     builds *inside* the snapshot and never as `entity_relations` rows;
   - a process-global cache keyed by project (invariant 13 — see below);
   - converged personalized PageRank against that snapshot in a thread executor, seeded
     uniformly over the query's resolved entities, its entity mass projected onto
     memories, emitted as a **ranked list**.
2. **The `ppr_snapshot` job** — Tier C, registered in `app/main.py` beside the other live
   jobs, with its own cron, `min_interval_seconds` floor, the registry's per-job lock, a
   `max_run_seconds` ceiling and a `config_schema`.
3. **The arms, inert.** `ppr_enabled`, `dual_level_enabled`, `community_injection_enabled`
   default `False`; `w_ppr` and `w_dual` default `0.0`. With them off the fused order is
   byte-identical to today's, which is the property the tests pin.

## Deliberate scope boundaries

- **The dual-level channel is T2.49's, not this task's.** Its arm needs
  `relation_embeddings` rows, and T2.49 owns that writer and `Depends: T2.32`. Shipping a
  channel here that reads an empty partition would be a signal that cannot be measured.
  What lands here is its flag and list weight, registered inert alongside PPR's, so T2.49
  wires a channel rather than also re-opening the flag surface.
- **No activation number is produced.** T2.50 measures these arms, split out precisely so
  the model that builds the snapshot does not also judge it (runbook §2). This task's
  verification is that the arms are provably inert, not that they win.

## The two invariants this task is pinned against

- **Invariant 13 — single worker.** The cache is correct *because* there is exactly one
  uvicorn worker. A multi-replica deployment needs sticky routing or a serialised
  snapshot table, and that is a flagged Phase-4 decision (doc 02 §11), not v1. Recorded in
  the module docstring where an implementer will actually meet it.
- **Invariant 15 — reconciliation off the hot path.** Retrieval reads the *artefact*, never
  the job: the seed set is derived from the snapshot's own in-process
  entity→memory mapping, so the PPR arm adds no query-time database read and no model
  call. The rebuild is reachable only through the registry's cron and manual-trigger
  surface.

## Known bound, stated rather than hidden

Synonymy KNN is exact within the project, which costs O(n²) distance computations because
project scoping cannot ride the global ANN index without post-filtering. Above
`synonymy_max_nodes` the arm is **skipped and the snapshot records that it was**, rather
than silently building a graph missing its synonymy edges.
