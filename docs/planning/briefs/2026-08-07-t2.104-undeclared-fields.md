# Brief — T2.104, a response model that silently drops what the builder writes

**Task:** T2.104 · `Sonnet 5` · `high` · `Size: S` · Doc 12 §2 · Gate: standing
**Depends:** none. **Contract:** `docs/planning/agent-runbook.md`. **Baseline:**

## The defect shape

FastAPI + pydantic v2 default to `extra="ignore"`. A key a builder writes and the
response model does not declare is dropped **silently** — no error, no warning, no log
line. The field simply is not on the wire, and the only way to notice is to diff the
payload against what the builder produced.

Five known occurrences, four in one file:

| Field | Schema | Status |
|---|---|---|
| `demotion_pending_since` | `schemas/facts.py` | fixed T2.46 (`99a47930`) |
| `label_suppressed` | `schemas/facts.py` | fixed earlier |
| `unverified` | `schemas/facts.py` | fixed earlier |
| `stale` | `schemas/facts.py` | fixed T2.86, 2026-08-07 |
| `synthesis`, `verification` | `schemas/config.py` (`LLMConfigResponse`) | **open — yours** |

## Why this is a task and not a fifth fix

**Three review passes on T2.48 recorded `stale` as "served but rendered nowhere". It was
never served.** Its executor, its Fable adversarial review, and its rescope each read the
builder and the frontend type — both individually correct — and none diffed the payload,
because a silently dropped field has no symptom. The controller then repeated the claim
from the same evidence. A defect class that survives an adversarial review *and* a
rescope is a missing guard, not a missed inspection.

## What ships

**1. The guard.** Every key a response-model builder writes is declared on the schema it
is returned through. Shape is your call and it is the task's real work:

- Introspect the builders (`app/services/facts_read.py` and siblings) against their
  declared response models. Cheap to run, brittle if a builder composes its dict in a way
  static reading cannot follow.
- Drive each route and compare the served key set against the builder's. Robust —
  it measures the wire, which is where the defect lives — but needs a live app per route.

Pick the one that **actually fails when a key is undeclared**, and mutation-drill it by
removing a currently-declared field and confirming a named test goes red. A guard that
passes on today's tree without being able to fail is the whole problem restated.

**2. The `/config/llm` fix, which is a real bug and not just guard bait.**
`LLMConfigResponse` (`backend/app/schemas/config.py:45`) declares six purposes; the route
builds eight. `synthesis` and `verification` are dropped. **`verification` is live** —
`app/services/verification_judge.py` resolves and dispatches on it since T2.26 — so an
operator cannot see the configuration of a purpose the system is actively using.

The frontend covers the hole with a hardcoded seed mirror whose premise ("nothing
dispatches on these") went stale when T2.26 landed. Retire the mirror or correct its
premise; say which and why.

**On the apparent conflict between two Done-when clauses:** "existing served payloads are
unchanged" governs the *guard* — it adds no fields anywhere. The `/config/llm` clause is a
deliberate, named payload change fixing a known drop. Do not read the first clause as
forbidding the second, and do not let the guard's introduction quietly widen any other
payload.

## What makes each clause non-vacuous

- [ ] **A key written by a builder and undeclared on its response model fails the build,
      proven by drill on a real field.** Drill on a field that matters — `stale` is the
      freshest and its absence was invisible for a full task cycle.
- [ ] **The guard covers `facts_read`'s builders and the `/config/llm` purpose set at
      minimum; state what it does not cover.** The honest statement is the deliverable
      here: a guard whose reach nobody wrote down gets assumed total.
- [ ] **`synthesis` and `verification` reach the `/config/llm` payload**, proven by
      driving the route and reading the JSON, not by reading the schema.
- [ ] **The frontend's hardcoded seed mirror is retired or its stale premise corrected.**

## Scope boundaries

- **Do not change what any builder computes.** You declare fields and add a guard; you do
  not alter values.
- **Do not widen any payload beyond `/config/llm`'s two dropped purposes.** If your guard
  surfaces other undeclared keys — likely — **report them, do not fix them**. Each is a
  wire-contract change that deserves its own decision, and a task that silently starts
  serving several new fields is exactly the shape review cannot audit.
- **No schema migration.** These are pydantic response models, not database tables.
- **Check the API conventions** in `docs/api-rest-conventions.md` before changing a
  served payload.
