# Brief — T0.18, `--full` must not overwrite ledger-cited gate evidence

**Task:** T0.18 · `Sonnet 5` · `high` · `Size: S` · Doc 17 §9 · Gate: none (harness integrity)
**Depends:** T0.10, T0.16 — both landed. **Contract:**
`docs/planning/agent-runbook.md`. **Baseline:** `CLAUDE.md`.
**Branch:** `feat/e2-lane-cj` off `feat/e2-truth-core`, worktree `.worktrees/e2-lane-cj`.

## The gap in one sentence

`run_retrieval_eval.py`'s `report_path()` derives the filename from the run **date**,
so a second run on the same day rewrites the first in place — and `gate-ledger.md`
cites `docs/eval/2026-07-28-retrieval-eval.md` as **G-B's cleared evidence**, by run id
(`6b7b0c0d`) and git sha (`16f8fb0`).

Measured 2026-07-29: a routine `./scripts/gate.sh --full` on an epic branch rewrote
both fields. The accuracy block was byte-identical, so **the damage was invisible to a
diff skimmed for numbers** — a cleared gate's verdict silently detached from the
artifact it names. It was reverted by hand that time. Every future gate (G-C, G-D
onward) inherits the trap, and G-C is the gate this epic is working toward right now.

## Read this before you design anything — there is a prior ruling you must reconcile with

`report_path`'s own docstring (`backend/scripts/benchlib/run_retrieval_eval.py:89`)
says:

> Overwriting an existing same-date report (rather than minting a variant) is the
> caller's job — `Path.write_text` already does that, and **ruling 4 says a same-day
> re-run is a correction, not a second artifact.**

That ruling is not wrong and this task does not overturn it. **The distinction the
current code is missing is cited versus uncited.** A same-day re-run correcting an
*uncited* report is exactly the intended behaviour and should stay cheap. A run that
would overwrite a report a `gate-ledger.md` row cites as a cleared gate's evidence is
the defect — because that artifact is no longer a working file, it is the evidence
behind a ratified verdict.

If your design forces every same-day re-run to mint a variant, you have overturned
ruling 4 to fix a narrower problem, and that is a **Tier-3 escalation** (a ruling
changing), not a fix. Prefer a design that leaves the uncited path alone. If you
conclude ruling 4 genuinely must change, **stop and report** rather than changing it.

## What ships

The task states two acceptable shapes and either is fine:

- The report path carries the **run id**, so two runs on one day cannot collide; or
- The runner **refuses to overwrite a cited file** and says which ledger row cites it.

The second composes better with ruling 4 and is the likely answer, but argue your
choice. If you take the refusal route, the interesting question is how the runner
*knows* a file is cited — parsing `gate-ledger.md` for artifact paths is the obvious
answer and it is brittle in a specific way worth stating: a citation written in a form
your parser does not recognise reads as uncited, which fails in the unsafe direction.
Say how you handled that.

If you take the run-id route, the fourth clause below becomes load-bearing: existing
citations must still resolve, so moving report paths means updating every cited path in
`gate-ledger.md` in the same commit.

## The four Done-when clauses, and what makes each non-vacuous

- [ ] **A full-gate run cannot silently overwrite a cited artifact** — either the path
      carries the run id, or the runner refuses and names the citing ledger row. The
      word doing the work is *silently*: a refusal that prints nothing useful, or a
      path change nobody can trace back to a ledger row, satisfies the letter and not
      the clause.
- [ ] **The rule holds for two runs on the same calendar day** — that is the case that
      actually broke, and it is the one a test written against "different dates" will
      miss entirely.
- [ ] **`gate-ledger.md`'s existing citations still resolve after the change.** Check
      every artifact path the ledger names, not only the two retrieval-eval reports.
      Both G-A and G-B rows cite several paths each, including directories.
- [ ] **The G-A and G-B artifacts are verified byte-identical to their cited state.**
      This is the clause with teeth and it is a *verification*, not a code change: those
      files are on disk now, and the ledger says what they should contain. Prove they
      still do. If one of them has already drifted, that is a finding worth more than
      this task — report it loudly rather than quietly restoring it.

## Scope boundaries

- **Do not re-run the retrieval eval to "refresh" anything.** It dispatches live model
  calls, costs money, and would itself rewrite the artifact this task protects. If you
  need a run to test with, use a scratch report directory — `report_path` already takes
  `report_dir` as a parameter, which is your seam.
- **Do not edit any `docs/eval/` artifact's contents.** If paths move, you update the
  *citations* in `gate-ledger.md`; you never edit the evidence.
- **No schema change, no backend app code.** This is harness code
  (`backend/scripts/benchlib/`) plus possibly `scripts/gate.sh`.
- **T0.19 is on a concurrent lane and owns `scripts/gate.sh`'s interpreter
  resolution.** If you need to touch that file, keep your change small and say so in
  the report so the merge is predictable.
