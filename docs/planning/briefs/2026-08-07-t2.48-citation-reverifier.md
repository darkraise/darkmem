## Read doc 10 §6 first — it designs this task almost completely

`docs/design/10-code-indexing.md` §6 is not a pointer here; it is the specification. It
resolves the re-verifier as **open question 4** and fixes every load-bearing choice. The
paragraph beginning *"The citation re-verifier is the second sanctioned crossing"* is your
contract. What it fixes, so you do not re-decide it:

- **A Tier-C job scoped to a re-indexed repo's changed/deleted file set.** The scoping is
  the cost bound and the reason the design is affordable — an unchanged file's citations
  cannot have broken, so they are not re-resolved.
- **It walks `fact_sources(source_kind='code', origin_key=repo_id)` rows** whose
  `detail.symbol_key` falls in that set, and **re-resolves each `symbol_key` against the
  new HEAD's `code_graph_nodes`** by owner-qualified key lookup.
- **For any that no longer resolve:** mark the `fact_sources` row stale
  (`detail.stale = true`, **with the sha at which it broke**), downgrade the citing fact's
  badge, and **enqueue** the fact for the verification recompute.
- **Never auto-expire.** A deleted symbol may be a rename the human should confirm, not a
  retraction of the claim. Label-and-queue, not silently expire.
- **The downgrade target is a demotion of corroboration, never `disputed`.** `disputed` is
  reserved for a contradiction, and a lost source is not a contradiction. Doc 08's ladder
  owns the precise target state.
- **The outcome journals to `events`.**
- **It reads the code graph and writes the memory-side vault — one direction, no join.**

Read §6's Figure 6b state diagram too: it puts the belief axis (invalidate-not-delete) and
the verification axis (badge downgrade) orthogonal to each other on purpose.

## The two halves, and which one is actually unbuilt

The task is "citation re-verifier **+ code-fact lifecycle**", and the lifecycle has two
transitions plus a no-op. Establish what exists before you build:

- **Symbol deleted → citation stale → badge downgrade.** The re-verifier proper. Unbuilt.
- **Dependency removed → sole-source → invalidate-not-delete.** `app/services/
  fact_provenance.py` is the emit side of the enqueue-for-verification hook and it does
  exactly this shape — withdraw the `fact_sources` rows, expire inline any triple left
  with no surviving source, emit one `sources_changed` per affected fact. **But it is
  memory-kind only, deliberately and explicitly**: read its "*The kind filter*" paragraph,
  which states that a `code` repository id is not a memory id and an unfiltered anti-join
  would reap every code row and expire the facts they solely source. So the code-side
  withdrawal is genuinely unbuilt, and the guard that keeps `fact_provenance` off it is
  correct and must stay. Decide whether the code half reuses `_withdraw`'s sequence or
  gets its own, and argue it — that module's own docstring says a second copy of the
  sequence is a second chance to get the expiry or the payload spelling wrong.
- **Unchanged at new HEAD → provenance no-op.** Not a transition; the absence of one. A
  strip-and-rewrite landing an identical source set must produce **no** event and **no**
  verification change. `fact_provenance` has a guard for exactly this on the memory side
  and its docstring explains why: without it every reprocess reads as evidence churn and
  the recompute thrashes `corroborated ↔ candidate`. You need the code-side equivalent, and
  it is the clause a passing test most easily fakes.

## The enqueue mechanism already exists — use it, do not invent one

`sources_changed` is in the closed events vocabulary and `verification_recompute.py`'s
**fast arm** (`_drain_sources_changed`) drains it past a watermark, dedups the `fact_id`s
and calls `recompute_fact`. `fact_lift` and `fact_provenance` are its current emitters.
Your re-verifier should emit into that same path rather than growing a second queue.

Two things that follow, and both are traps:

- **`recompute_fact` (`verification_ladder.py`) is the sole journaller of verification
  transitions.** If your re-verifier writes a `verification_status` directly, you have
  created a second writer of the ladder and the journal no longer describes the vault.
  The badge downgrade should happen *through* the recompute, driven by the now-stale
  evidence — which means the stale marking must be visible to whatever `recompute_fact`
  reads. Check that it is. If a stale `fact_sources` row still counts toward corroboration,
  marking it stale changes nothing and your test will still pass for the wrong reason.
- **Whether `sources_changed` is the right event type for the *stale* outcome is your
  call, and it is taxonomy-first either way.** Doc 10 §6 says the re-verify outcome
  journals to `events`; the vocabulary today has `sources_changed` and `verified` and no
  citation-specific type. If you add one, it lands in `EVENT_TYPES` (`app/services/
  events.py`) **before** its emitter ships — that is the standing rule, and the vocabulary
  lives beside the writer deliberately, not in `app.taxonomy`, because event types are
  never LLM output.

## The changed-file set is the design problem this task actually owns

Doc 10 §6 scopes the walk to "the run's changed/deleted file set (from `phase_01`'s
diff)". `CodePipeline` holds that set in `self._changed_files` / `self._deleted_files`
(`app/services/code_pipeline.py`, ~line 95) — **in memory, for the duration of the run**.
A Tier-C job runs later, in a different session, and cannot see it.

So you must decide how the set crosses that boundary, and it is the highest-leverage
judgement in the task. Candidates, none free:

- Persist the run's changed set (the `index_debt` machinery is the local precedent for
  persisting a file list against a repo, and `repo_indexed` events already journal per
  run).
- Recompute the diff in the job from the two shas.
- Re-resolve every code citation for the repo and drop the scoping — **this abandons the
  design's stated cost bound**, so if you propose it, say so as an amendment rather than
  quietly.

Say which you chose, what it costs, and what happens when two re-index runs land between
two Tier-C ticks (the set is per-run; the job is not).

## Also settle: is a `symbol_key` re-resolution actually possible

`fact_lift` mints `detail = {commit_sha, basis, file_path, symbol_key}` and its own code
notes that a fact may carry **no** `symbol_key` — there is a log line at
`fact_lift.py:~1270` saying such a citation "cannot be re-verified". That is your input
distribution, not an edge case: establish what fraction of code sources carry a resolvable
key, and make the no-key path explicit rather than silently skipping. A re-verifier that
quietly ignores every keyless row and reports success is the failure mode this corpus
exists to prevent.

## The three Done-when clauses, and what makes each non-vacuous

- [ ] **A changed symbol downgrades rather than expiring — the human decides, not the
      parser.** Prove both halves: the badge moved, **and** `expired_at` / `invalid_at` did
      not. A test asserting only the downgrade passes on an implementation that also
      expires. Drive it through the job, not through the function.
- [ ] **Sole-source removal invalidates without deleting.** `invalid_at` closes, the row
      survives, and the fact remains readable as history. Also test the *non*-sole case: a
      fact with a surviving memory source must not be invalidated when its code source
      goes. That asymmetry is the whole point of the clause.
- [ ] **Re-verification is idempotent per repo run.** Two ticks over the same run produce
      one stale marking, one event, one downgrade. And the no-op case: a run whose file set
      changed but whose citations all still resolve emits nothing at all. Both directions,
      or the clause is satisfied by a job that does nothing.

## Invariants that bind you

- **Invariant 15 — reconciliation off the hot path.** Tier C only. The re-index
  **enqueues**, it never recomputes inline (doc 10 §9 restates this as Part B contract 5).
  A source scan over `backend/app` fails the build on a dream-job family member reached
  from capture or retrieval; your job is Tier C but **not** a family member — contract 6
  fixes that family at six, and `ppr_snapshot` is the precedent for a Tier-C job outside
  it. A new registered job moves `CLAUDE.md`'s **"Sixteen registered jobs"** count and its
  two-group breakdown: update that sentence in the same commit.
- **The never-join rule.** No statement may read a `code_graph_nodes` row and a
  `knowledge_triples` / `fact_sources` row together. Read the code graph, then write the
  vault. This is a sanctioned crossing precisely because it is application-level and
  one-direction; a join makes it the thing doc 01 §3.6 forbids.
- **Invariant 9, id-type discipline.** Address code by owner-qualified `symbol_key` +
  `commit_sha`, **never** the churning bigint node ids. A node id is meaningless after a
  re-index.
- **Invariant 14 — no silent degradation.** A stale citation downgrades a badge *visibly*.
- **Events are append-only** and `record_event` never raises into its caller — which is
  why `verification_recompute` has a slow reconciliation arm at all. If your design leans
  on an event being delivered, say what heals a swallowed one.
- **asyncpg CASTs** on every raw-SQL param Postgres cannot infer, `detail` JSONB included
  (`CAST(:detail AS jsonb)`).

## Scope boundaries

- **No schema change.** `0001_baseline.py` is a single shared mutable file and **T2.98
  owns it this round** (concurrent lane). `detail` is JSONB, so a `stale` marker needs no
  DDL. If you conclude you genuinely need real DDL, **stop and report** rather than
  editing.
- **Do not touch the deriver's trigger.** T2.96 is landing that on a concurrent lane. If
  your job wants to run after derivation, express that as ordering in your own scheduling,
  not by editing T2.96's call site.
- **Do not embed anything.** T2.97's lane.
- **Do not change `recompute_fact` or the ladder's transition rules.** If the ladder
  cannot express the downgrade you need, that is a finding and possibly a Tier-3
  escalation — report it, do not widen the ladder.
- **Deriver v2 (manifest parsing) is out of scope** and doc 10 §6 says so explicitly.
