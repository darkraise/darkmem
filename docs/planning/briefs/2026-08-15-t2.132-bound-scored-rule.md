## What this is

The owner's ruling, taken. T2.130 measured that the audit's rule — `observed rate
< 0.01` — passes a system sitting exactly at the failing bar about half the time
**at every sample size** (0.5604 at n = 149, 0.4865 at n = 10 000), reported the
Clopper-Pearson bound beside it, and deliberately did not switch the verdict,
because changing what a gate decides is the owner's call. On 2026-08-15 the owner
took it.

`audit_clears` now scores the 95 % upper bound against the same 0.01 bar. It takes
**counts, not a rate**: 1/149 and 20/2980 are both 0.006711 and bound to 0.0314 and
0.0097, so the old signature could not express the rule. Strictly a tightening —
the bound is never below the point estimate — so no licence is involved and no bar
moved.

**The consequence is that the audit axis flips from `clears=True` to
`clears=False` on the corpus as it stands.** That is the intended direction. G-C
did not clear before and does not clear now; no `promotion_metrics_record.json`
was ever minted, so no served badge changes.

## A defect I believe I introduced, named rather than left to be found

**The renderer and the predicate can read two different bars.**
`audit_clears` compares against `bars["verification_false_promotion_bar"]` — the
*resolved* value, which a `config` row may legitimately tighten (a tightening is
free and needs no licence). `_render_audit_power` compares against the module
constant `_AUDIT_BAR_FOR_POWER = 0.01` and now prints **`→ CLEARS` / `→ does NOT
clear`**, which before this change was commentary and is now a verdict claim.

So under a tightened `config` row I believe the printed verdict and the scored
verdict can disagree — the artifact pasted into the ledger would say CLEARS while
`audit_clears` returned False. My own test
(`test_the_rendered_verdict_is_the_predicates_verdict`) passes `resolve_promotion_bars({})`,
defaults only, so it is blind to exactly this case.

This is the same defect class the change repairs elsewhere (two resolutions of one
rule that agree until they do not), reintroduced one level up by my own hand.
**Confirm or refute it, and rule on severity.** I have not fixed it: the review is
the vehicle the owner asked for, and a finding I discovered while writing the brief
should be verdicted by someone other than its author. If it is real, it wants a fix
round — most likely threading the resolved bars into the renderer so there is one
bar, not a constant and a lookup.

## Where else the review should push hardest

- **Is `k ≤ n` actually structural?** `clopper_pearson_upper` raises `ValueError`
  when `k > n` and when `n <= 0`, and a raise in a verdict predicate takes down an
  evidence run at its last step, after every query is paid for. I claimed the SQL
  guarantees it — `_FALSE_PROMOTED_FACTS_SQL`'s two arms both select from the
  `corroborated` CTE, which is the denominator's own predicate — and wrote no
  guard on that basis, per "no error handling for scenarios that can't happen".
  The dispute arm in `_FALSE_PROMOTION_AUDIT_SQL` is *different SQL* from the
  union arm; check that the number actually scored (`false_promoted_facts`) cannot
  exceed `total_corroborations` under folds, out-of-window disputes, or a partial
  window. If it can, the failure mode is a crash, not a wrong number.

- **Does the direction-derivation test still prove anything for
  `false_promotion_min_corroborations`?** Its `LIVE_PROBES` entry now overrides
  the false-promotion bar to 0.5 *inside the probe*, because at the committed bars
  no window exists that the floor refuses and the bound would have cleared. I
  argue this keeps the direction derived while `TestTheDecidabilityFloorIsSubsumed`
  records the liveness honestly. The opposing reading is that the probe now tests a
  configuration that cannot occur and the bar's direction is effectively declared
  again. Rule on it.

- **`scored_on: "upper_bound"` is a hardcoded string in `to_ledger_row`.** Nothing
  derives it from the predicate, so if the rule ever changes again the durable row
  will assert the wrong one. Is that acceptable, or is it the same drift the rest
  of this change was made to close?

- **The confidence has no config surface, deliberately.** I argued a resolvable
  number needs a clamp, a direction and a domain edge to defend it, and the cheaper
  defence for one nobody has asked to tune is no surface at all. The counter-reading:
  it is now a verdict-deciding number that does **not** appear in the `BarReport`
  block a reviewer reads, only in the audit-power prose. Is that a disclosure gap?

- **Do the new tests pin the property or merely pass?** The load-bearing one is
  `test_the_same_point_estimate_scores_two_ways_by_window_size`. A test that would
  have passed against the pre-T2.132 predicate proves nothing. Four mutation drills
  were run (point-estimate revert → 11 failures; dropped decidability guard → 3;
  confidence 0.95 → 0.50 → 3; renderer disagreeing with predicate → 3). Plant your
  own.

- **Is the subsumption claim right?** "Nothing clears 0.01 below 299 corroborations
  at any observed count" is load-bearing for keeping a bar that now decides nothing.
  It is asserted by derivation in `TestTheDecidabilityFloorIsSubsumed`. Check the
  derivation, not the sentence.
