# Brief — T2.105, a task with no `progress.md` row is invisible to scheduling

**Task:** T2.105 · `Haiku 4.5` · `high` · `Size: S` · runbook §6 · Gate: none (planning integrity)
**Depends:** none. **Contract:** `docs/planning/agent-runbook.md`. **Baseline:**
`CLAUDE.md`. **Branch:** `feat/e2-lane-cr` off `feat/e2-truth-core`, worktree
`.worktrees/e2-lane-cr`.

## The gap

The runbook makes `progress.md` canonical for scheduling. A task defined in an epic file
with complete text but no row there **cannot be picked up**, however finished its
specification is — and nothing announces the absence.

It happened twice on 2026-08-07, and the second time is what earns this task:

- **T2.86** sat rowless from 2026-08-04. Adjacent work built five of its six clauses
  while it was invisible; nobody could close it; it surfaced only because another task
  tried to route work to it.
- **T2.104** was minted by the controller *in the same session that fixed T2.86's row*
  and immediately had none itself. It was caught only by chance — the controller happened
  to re-run an ad-hoc sweep it had written hours earlier.

A check that exists, works, and is wired to nothing is indistinguishable from no check.

## What ships

A test that fails when the two sources disagree, **in either direction**:

- A `#### T<id>` heading in any `docs/planning/tasks/*.md` with no `| T<id> |` row in
  `docs/planning/progress.md`.
- A `| T<id> |` row naming a task no epic file defines — this catches a row surviving a
  task's deletion or renumbering, which is the mirror failure and just as silent.

**Keep it cheap and dependency-free.** This is a text comparison over two globs, not a
planning-document parser. Resist building anything that understands table columns or
task semantics; the value is entirely in it running, not in its sophistication.

**The failure message must name the offending ids.** "The planning files disagree" just
relocates the search — the whole point is that a human or agent reads the failure and
knows immediately which task is unscheduled.

## Where it lives

Put it wherever the repo's other planning/doc-hygiene checks already run, so it executes
as part of a suite someone actually runs. Look for existing precedent before inventing a

`app/main.py`, the invariant-15 source scan, the single-revision assertion in

If you conclude it belongs in `scripts/gate.sh` rather than pytest, that is a defensible

## What makes each clause non-vacuous

- [ ] **A task heading with no row fails the build, naming the id — mutation-drilled.**
      Add a fake `#### T9.99` heading to an epic file, confirm a named test goes red and
      the message contains `T9.99`, restore.
- [ ] **A row with no task heading fails the same way, also drilled.** Add a fake row,
      same procedure. Both directions or the guard is half a guard.
- [ ] **The check passes on the tree as it stands today, or names exactly what it
      found.** The controller swept manually and both directions were clean as of
      2026-08-07 — so a failure on the current tree means either your matcher is wrong or
      something changed since, and both are worth knowing. Do not "fix" the planning
      files to make your check pass without reporting what you changed and why.

## Watch for these, they are real

- **Task ids are not uniformly formatted.** They include letter suffixes (`T0.12a`,
  `T1.42c`, `T2.36a`). A matcher assuming `T\d+\.\d+` will silently miss those, and
  silently missing things is the exact defect this task exists to end.
- **`progress.md` rows are markdown table rows** whose first cell is the id; epic files
  use `#### T<id> — title` headings. Anchor both patterns to line starts so an id
  mentioned in prose is not mistaken for a definition or a row.
- **Ids appear constantly in prose** — amendment logs, notes, cross-references. Only
  headings define and only rows schedule.

## Scope boundaries

- **Do not edit `progress.md` or any epic file's content** beyond what a drill requires
  and restores. If the check finds a real disagreement, **report it**; the controller
  decides whether the row or the heading is the correct fix.
- **Do not build a planning-document linter.** One correspondence, both directions.
- No backend app code, no schema, no frontend.
