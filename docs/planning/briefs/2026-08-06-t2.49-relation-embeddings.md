A relation embeds as `"<source name> <rel_type> <target name>"`, written off the hot path
and never inside Phase 5 (doc 07 §4): a relation embed during ingest would put an extra
round trip on every capture for a signal retrieval cannot read until `dual_level_enabled`
is on.

## Why the refresh has two arms

The embedded text is **derived and not stored**. The partition has no column holding the
phrase, so nothing on disk can reveal that an entity was renamed under an
already-embedded relation — leaving a vector describing text the row no longer produces.

- The **exact arm** (`LEFT JOIN` for relations with no vector under this fingerprint)
  drains to zero and stays there. It cannot see drift.
- The **rotation arm** re-embeds the oldest embedded slice, so a drifted vector is
  corrected within one full rotation rather than never.

This is `verification_recompute`'s exact-arm-plus-slow-arm shape, adopted for the same
reason rather than by analogy: an exact arm cannot detect a change that leaves no trace.
The exact arm runs first and short-circuits the rotation, so a backlog of never-embedded
relations is never starved by re-embedding rows that already have vectors.

## Invariant 2, on both sides of every statement

Each statement names exactly one child table and one `fingerprint` value. The missing-arm
join is keyed on the fingerprint on *both* sides deliberately: a relation embedded under a
previous embedder is **missing** under the current one and must be re-embedded, not
counted as covered. Counting it would leave the arm reading a partition it believes is
full.
