`triple_embeddings.py:19-21` claims the tests "fail the build on any other verb reaching
that table from here". The reviewer demonstrated three evasions against
`tests/test_triple_embeddings.py:426-461`:

1. **An interpolated table name** — `f"UPDATE {_KT} ..."`, which is the module's *own*

3. **An indirect write through an imported helper.**

The byte-comparison backstop closes all three on the `group_facts` path, but **`embed_facts`
sits outside that backstop entirely.**

**Named fixes, any or all — argue what you choose:** extend the byte snapshot across an
`embed_facts` run; add `ast.keyword` and f-string handling to the scans; or pin the module's
import surface so an indirect write cannot be introduced silently. Prove each with a
mutation that reds.

**Why now, when nothing calls the writer:** the reviewer's own framing is "fix before T2.11
wires a caller". T2.11 is blocked indefinitely, so this is not urgent — it is *cheap while
the module has no callers* and expensive once it does, and a guard whose docstring overstates
its coverage is exactly the stale-premise shape this epic keeps paying for.
