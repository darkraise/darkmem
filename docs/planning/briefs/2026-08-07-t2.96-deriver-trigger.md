## The gap in one sentence

`derive_assertions(...)`, and **nothing in `backend/app` calls either** — so
`entities.repo_ids[]` / `entity_relations.repo_ids[]` have a writer that production
never reaches, and every amended orphan sweep's `NOT EXISTS (live repo)` predicate is
still vacuously true in a real database.

The schema inventory already says so plainly (T2.27's merge wrote that note), and
invariant 23 — scaffolding is not substrate — is why the note exists rather than the
gap being left for a reader to infer. Your task closes the gap the note describes.

## What ships

A production trigger for `assert_repo_graph`, plus the withdrawal half.

**The shape is your call, and it is the task's one real decision.** Two candidates:

- **A hook on the reindex path.** `CodePipeline.run` (`app/services/code_pipeline.py`)
  is where a repo's import edges are rewritten, so it is where its assertions become
  stale. The route (`POST /repos/{id}/reindex`, `app/api/routes/repos.py:145`) already
  runs the pipeline in a background `asyncio.Task` under `TaskRegistry`, so a hook
  inherits that. Directness is the argument for it.
- **A `JobRegistry` Tier-C entry** with its own cron, `min_interval_seconds` floor,
  per-job lock and `job:<key>` config row, sweeping repos whose assertions are older
  than their indexed HEAD. Decoupling is the argument for it: a derivation failure
  cannot then fail an index run, and a repo indexed before this task ever landed still
  gets its assertions.

**State which you chose and what the other one would have cost.** Whichever it is, the
constraints are the same:

- **Invariant 15 binds by proximity, not by name.** The trigger must sit off capture
  and retrieval. A reindex hook is admissible (indexing is neither); a call from the
  pipeline's *ingest* path or from any retrieval service is not.
- **If you register a job, it is not a dream-job family member.** Contract 6 fixes that
  family at six, and `ppr_snapshot` is the precedent: Tier C, scheduled, deliberately
  outside the family. Do not add it to `dream_jobs.py` or to
  `_ALLOWED_DREAM_JOB_LINES`. A new job also moves `CLAUDE.md`'s **"Sixteen registered
  jobs"** count and its two-group breakdown — update that sentence in the same commit or
  the baseline is wrong the moment you merge.
- **A derivation failure must not fail the index run.** Whatever shape you pick, a repo
  whose assertions cannot be derived is a repo with a stale graph, not a failed index.
  Say in the report how the failure surfaces (it must surface — a silently swallowed
  exception here reproduces exactly the "writer exists, column empty" state you are
  fixing).

## The three Done-when clauses, and what makes each non-vacuous

- [ ] **A production path fills `repo_ids[]`, proven end-to-end rather than by unit
      test.** The clause says *end-to-end* because a test that calls your new function
      directly proves nothing this task does not already have — T2.27 shipped 47 such
      tests. Drive the real entry point: the HTTP route, or the registered job through
      `JobRegistry.trigger(key)`, and assert on a **direct database read** of
      `entities.repo_ids`. Then perform the deletion drill: remove your call site,
      confirm a named test goes red.
- [ ] **Re-running the trigger is idempotent per repo, inheriting T2.27's strip.**
      Inheriting is not the same as having. T2.27's report is explicit that
      **byte-identical re-derivation is not attainable** under strip-before-rewrite —
      solely-repo-asserted rows get fresh ids on every run because the strip deletes and
      the write re-inserts. So the property you assert is what T2.27 asserted: the repo
      id appears **exactly once** in each `repo_ids[]` after N runs, and contents are
      identical. Do not write a test demanding stable ids; it will fail, and "fixing" it
      means write-before-strip, which contradicts invariant 8.
- [ ] **Removing a repo strips its assertions.** `strip_repo_assertions(repo_id)` exists
      and has no caller either. `DELETE /repos/{id}` (`repos.py:136`) goes through
      `RepoManager.delete`. Two things to get right: the strip must run **before or
      within** the same transaction that removes the repo row, and an entity left with
      an empty `repo_ids[]` and no live memory is now an orphan — check whether the strip
      leaves it for `graph_orphan_cleanup` or removes it inline, and say which, with the
      reason. Prove the withdrawal at the route, not at the repository method.

## Invariants that bind you

- **Invariant 15** — no dream-job family member reachable from capture or retrieval;
  a source scan over `backend/app` fails the build on one. Your trigger is not a family
  member, but read the scan before you wire anything so you know what it asserts.
- **Invariant 8, amended** — strip-and-write is one atomic replace. You are calling a

- **Invariant 23** — scaffolding is not substrate. When this lands, the schema inventory

- **The never-join rule** — no statement reads a `code_graph_nodes` row and an
  `entities` row together. You are not writing SQL here, but a "convenient" join in a
  job's sweep query would cross it.
