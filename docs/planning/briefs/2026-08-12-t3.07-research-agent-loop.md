## Why this is in v0.5, and the cost it carries

Production holds **one** distinct `origin_key`. Corroboration counts
`COUNT(DISTINCT origin_key)` and needs N = 3, or 2 when two attributable origins differ in
source-kind or lie ≥ 7 days apart, so no machine path can promote a fact off `candidate`
and G-C has been under-powered on every probe it has ever run. Two routes fix that:
`T1.54` (a person actually using the instance) and this one.

**This route manufactures the origins rather than observing them**, and that is a real
evidence cost, not a formality: a corroboration count assembled from a loop the system ran
on itself is weaker than one assembled from independent capture. G-C's eventual verdict
owes that slice. Making the two machine-distinguishable is `T3.08`'s job and it depends on
this task, so **leave the seam where `T3.08` can put a reserved origin identity** — do not
stamp researched captures with an identity indistinguishable from a human's.

**Building this is not running it.** Pointing the loop at production is a separate
decision and is the owner's. Nothing in this task may run the loop against the live
instance at `:8000`.

## Constraints

- **No new ingestion path.** Evidence is filed through the ordinary capture front door —
  no privileged route, no second pipeline. That is the whole reason this is cheap, and a
  second door would be a behaviour change against `CLAUDE.md`'s capture contract.
- **Tier-C and bounded by a `config` budget.** Note invariant 15: no Tier-C job may be
  reached from capture or retrieval, and a source scan fails the build if one is.
- **A failed research run leaves no partial state.**
- Make no live model call against production, and do not touch the production database.
- **Run only your task's verify command.** Do not run `./scripts/gate.sh` — other agents
  are working concurrently and the backend conftest drops and recreates the shared test
  schema, so two runs at once corrupt each other.
- If this needs a schema change, **stop and say so before making it**: the baseline is a
  single shared mutable file (`0001_baseline.py`) and schema changes serialise through one
  owner per epic.
