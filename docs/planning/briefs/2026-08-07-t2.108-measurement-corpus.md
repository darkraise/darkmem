# Brief — T2.108, a measurement corpus that can actually promote

**Task:** T2.108 · `Opus 5` · `high` · `Size: M` · Doc 20 §4, 17 §11 · Gate: G-C
**Depends:** T2.10 — landed. **Contract:** `docs/planning/agent-runbook.md`.

## Why this exists

T2.40's G-C run returned **not evaluable** on all four probes. The judge dependency gets
the attention, but it blocks one arm of one probe. **The corpus starves all four**: the
production `darkmem` journal holds 0 events, and the only existing corpus is structurally
incapable of promoting.

And the production route is circular before the cutover — doc 17 §11 sequences the
homelab cutover *after* G-C and G-D, so "wait for real traffic" is not available to a gate
that must clear first. A purpose-built measurement corpus is the only pre-cutover route to
any G-C verdict at all. The gate-ordering analysis found this is the long pole under every
option it considered.

## The machinery already exists — do not rebuild it

`backend/scripts/benchlib/run_gc_evidence.py` already flows a corpus through the
**shipping** paths in one command: real `ProcessingPipeline` ingest against the warm disk
cache, `fact_lift.run_lift` to exhaustion, then `verification_recompute.run_recompute`
ticks until the fast arm drains, then measures with the production SQL. Its docstring is
explicit that nothing writes an `events` row directly — "a metric measured over
hand-written events measures the fixture, which is the one number this gate must never
accept". It achieved `live_calls == 0` against the warm cache.

**That driver is the precedent and the vehicle.** Your work is the corpus it drives.

## The root cause, already traced

`benchlib/ingest.py`'s pre-creation step builds each row through `MemoryCreate` and
**never sets `origin_key`**. `origin_key` is capture-session identity — in production it
is resolved at the door by `resolve_origin_key`. With it absent, every fact's provenance
folds into the anonymous-identity bucket, which counts as **one** origin however many rows
land in it. That is why all 62 facts were incapable of promoting: `COUNT(DISTINCT
origin_key)` could never exceed 1.

## What promotion actually requires — read this before designing the corpus

`FactSourceProfile.required_origin_count_for` (`app/repositories/fact_sources.py:317`)
picks N by gate, in this order:

1. **`diversity`** — source kinds are diverse → `n_diverse`
2. **`time_gap`** — max cross-origin gap ≥ `time_gap_days` → `n_diverse`
3. **`none`** — otherwise → `n_default`

A fact promotes when `k = COUNT(DISTINCT origin_key)` reaches its N. **G-C's probe 2
slices the promotion rate by which gate fired**, so a corpus that only ever produces one
bucket leaves that probe under-powered even if it promotes plenty. Aim for all three
buckets, each meeting `promotion_rate_min_eligible` (5 eligible), and the audit's
`false_promotion_min_corroborated` (20 in-window distinct corroborated facts). Both
constants are already committed in `promotion_bars.py` — read them there rather than
restating them.

## The trap this task lives inside, and the line you must not cross

**A corpus built to make a gate clear is not evidence; it is a fixture wearing evidence's
clothes.** The specific failure available to you is easy and tempting: assign a unique
`origin_key` per memory and everything promotes immediately.

That would be a lie, and it is worth being precise about why. Corroboration means
**independent capture sessions asserted the same thing** — the corpus's own doctrine is
"echo is not evidence". One assertion relabelled N times is an echo with N names. The
corpus must contain **genuine repeated assertions of the same fact across different
capture sessions**, the way a real vault accumulates them: the same claim arriving from
different sessions, at different times, sometimes through different source kinds.

So the design question is not "how do I set `origin_key`" — it is "what corpus content
would genuinely corroborate". Write the content first, assign origins to match its
sessions, and let the ladder decide. If a fact does not promote, that is a result.

**State plainly in the report which parts of the path the corpus drives and which it
stubs.** The gate's credibility rests entirely on that boundary, and a reader six months
from now needs it stated rather than inferable.

## The clauses, and what makes each non-vacuous

- [ ] **Facts flow through the shipped lift and recompute** — no hand-written `verified`
      events, no directly-seeded `verification_status`. Prove it the way T2.40 did:
      `live_calls == 0` and every measured journal row attributable to a production writer.
- [ ] **Distinct `origin_key`s produce real promotions that journal**, proven by a
      non-zero promotion count read back from `events` **by SQL**, not by a counter your
      own code kept.
- [ ] **Both decidability thresholds are met**, so every probe that does not need the
      judge becomes decidable. Report the per-bucket denominators; an under-powered bucket
      must be reported with its denominator, never collapsed.
- [ ] **The corpus is reproducible from a committed definition**, not a one-off database
      state. Someone re-running it next month gets the same corpus.
- [ ] **The report states exactly what is driven and what is stubbed.**

## Scope boundaries

- **Do not run the G-C gate verdict.** T2.40 owns that, its bars are already committed,
  and the runbook forbids the model that builds a measurement from also judging it. You
  build the corpus and may report what the probes *would* read; minting
  `promotion_metrics_record.json` is not yours and `run_gc_evidence.py` deliberately never
  writes it.
- **Do not touch `promotion_bars.py`.** The bars were committed before any measurement and
  the git history is the witness; changing them now destroys that property.
- **Do not modify the ladder, the lift, or the recompute** to make facts promote. If a
  fact will not promote, the corpus is wrong or the finding is real — both are reportable,
  neither is an edit here.
- **Bench database only** (`darkmem_bench_cv`). Runbook §8: a harness pointed at
  `darkmem_test`, or a test at `darkmem`, is a defect regardless of whether it passes.
- **No schema change, no app code.**

## Hygiene

`TEST_DATABASE_URL` → `darkmem_test_cv`, `BENCH_DATABASE_URL` → `darkmem_bench_cv`
(both exist). `pyproject.toml` sets `testpaths = ["tests"]`, so plain `pytest -q` does
**not** collect `scripts/benchlib/tests` — run it explicitly.

The ingest path needs `DEEPSEEK_API_KEY` when the cache is cold; the key is in
`CLAUDE.md`'s live-endpoints section, and **the F1 baseline and every gate measurement use
`deepseek-v4-flash`** — a run on `-pro` is not comparable. Expect `live_calls == 0`
against a warm cache; if your corpus is new content, it will be cold, so say what it cost.

**Pass the Bash tool's own `timeout` parameter on every long run** — omitting it
auto-backgrounds the command regardless of any `timeout` binary, which stalled six lanes
today (runbook §8, corrected today). Foreground, one command at a time. Check
`git branch --show-current` reports `feat/e2-lane-cv` before **every** commit. Commit
before any drill; restore from your own file copy, never `git checkout --`.
