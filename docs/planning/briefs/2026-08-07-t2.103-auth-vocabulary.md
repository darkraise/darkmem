# Brief — T2.103, the auth family is emitted outside the closed vocabulary

**Task:** T2.103 · `Sonnet 5` · `high` · `Size: S` · Doc 04 §8.1, 12 §6 · Gate: standing
**Depends:** none. **Contract:** `docs/planning/agent-runbook.md`. **Baseline:**

`.worktrees/e2-lane-cm`.

## The gap, verified in the tree before this task was minted

`EVENT_TYPES` (`app/services/events.py:69`) is a closed vocabulary, and `record_event`
logs a warning for any value outside it — deliberately, because event types are never
LLM output, so an unknown value must surface rather than be rewritten to a fallback.

The auth family is inverted against that rule in **both** directions:

- **Emitted, absent from the vocabulary:** `auth_login_success`, `auth_login_failed`,
  `auth_logout`, `auth_password_change` (`app/api/routes/auth.py:103,108,124,163`) and
  `auth_setup` (`app/api/routes/setup.py:342`).
- **In the vocabulary, no emitter:** `auth_lockout`.

So every login, logout, password change and setup writes
`events: event_type ... is outside the doc 04 §8.1 closed vocabulary` into the log —
five values, on the hottest security-relevant path — while the one auth value the
vocabulary does hold is never written.

**Why this outranks a cosmetic mismatch.** `GET /auth/audit`
(`app/api/routes/auth.py:250`) serves the security audit trail by filtering
`auth_*`/`setup_*` rows out of `events`. The audit surface is therefore built entirely
on values the closed vocabulary refuses to admit — taxonomy-first ("land the value in
the vocabulary before its emitter ships") failing on the one family where an
unrecognised row costs the most.

## What ships

1. **Land the emitted values in `EVENT_TYPES`.** Taxonomy-first is the rule being
   repaired, so do not also add an emitter for something new in the same breath.
2. **Settle `auth_lockout`.** Either it gains its emitter or it leaves the vocabulary.
   An entry with no writer is exactly the scaffolding-not-substrate shape invariant 23
   exists to catch — and the lockout path is real (login rate limiting with lockout is
   live and tested), so "it should be emitted and isn't" is a plausible answer. Find out
   which it is rather than picking the cheaper one.
3. **The scan that stops recurrence.** A test that fails the build when any
   `record_event` call in `backend/app` names a value outside `EVENT_TYPES`. This is the
   deliverable that makes the task worth more than five list entries — without it, the
   next family drifts the same way. The in-repo idiom is an AST scan over the parsed
   tree, not a text grep: `tests/test_code_deriver.py`'s
   `test_main_registers_the_full_direct_job_roster` is the freshest example, and the
   recorded trap is that a scan matching module names as **text** fires on prose in
   comments too.
4. **Check the `setup_completed` / `setup_complete` spelling drift** T2.102 also
   recorded while you are in here.

## What makes each Done-when clause non-vacuous

- [ ] **No `record_event` call in `backend/app` emits a value outside `EVENT_TYPES` —
      proven by a scan that fails the build, not by grep at review time.**
      Mutation-drill it: add a call emitting a fake value, confirm a named test goes
      red, restore. Note your scan must handle the call shapes actually in use — some
      sites pass the type as a literal keyword, others through a helper
      (`_record_audit("auth_login_failed", ...)` at `auth.py:103` is one). A scan that
      only sees the literal-keyword shape misses the helper and reports success.
- [ ] **`auth_lockout` either has an emitter or is gone, and the report says which and
      why.** If you add the emitter, it must fire where lockout actually happens, and
      you need a test that proves it does — not just that the value exists.
- [ ] **`GET /auth/audit` returns the same rows before and after, proven at the door.**
      This is the regression clause: the audit reader filters on an `auth_*`/`setup_*`
      prefix, so a renamed value silently drops history out of a security surface. Drive
      the route, do not reason about the filter.
- [ ] **T2.102's frontend map guard still passes.** It landed hours ago and asserts every
      *live-emitted* value has a tab or a recorded exclusion. Values you add to
      `EVENT_TYPES` that already have emitters become newly visible to that guard, so
      each needs a classification — and `auth_*` plausibly belongs in the
      "deliberately no tab" bucket the map already documents for
      `inject`/`setup_completed`/`auth_lockout`. Record the decision; do not let the
      guard go red and do not invent a sixth tab.
