## Why this one review matters more than the others

On 2026-08-06 measurement was split into a separate epic (M1). Every evidence run and the
entailment gold moved out, and implementation across the whole plan was unblocked on the
rule that *a gate blocks what it certifies, not what merely precedes it*. **T2.95 is the
entire safety argument for that split.** The claim is: implementation can run arbitrarily
far ahead of evidence because no serving path *can* reach a label whose evidence does not
exist. If that claim is false anywhere, then work already merged — and T2.28, which is
queued behind this review — is shipping unbacked truth claims to readers.

The task's own text says it: *"if it is wrong, implementation running ahead of evidence
stops being safe."*

**Your charter is to break it, not to bless it.** A review that returns "verified, the
gate holds" and is wrong costs more than no review. This epic has one recorded instance
already: the T2.50 judge found the PPR arm was computing global PageRank — a
byte-identical ranked list for every query, including a nonsense one — *after* four drills
by its author had passed. Assume the same class of defect is present here and go find it.

## The four attacks worth your time

### 1. Is `fact_badge.row_labels` genuinely the *single* producer?

The whole design rests on enforcing at the producer rather than at each consumer: "applied
at each consumer this would be a convention, applied at the producer it is a property."
That is only true if the producer is actually singular. **Enumerate every path by which a
verification status or badge sentence can reach a reader** and check each one goes through
`row_labels`. At minimum: the REST fact routes, the MCP vault tools, chat citations and
the `messages.context` cited-fact rows, any websocket payload, the dream digest, `events`
payloads, the knowledge search surface, and **the frontend** — if the SPA re-derives a
badge from a raw status field, the backend gate is cosmetic. A single serializer reading
`verification_status` off an ORM row and rendering it defeats the module completely.

### 2. Does the scan fail the build on a *new* serving path, or only on the known ones?

The Done-when clause is "the scans fail the build on a new serving path that bypasses
either gate". A scan that enumerates today's modules is a snapshot, not a guard. **Test it
empirically:** write a new module that serves the label without the record, run the scan,
and see whether the build goes red. If it stays green, that clause is unsatisfied
regardless of what the tests assert. Note the recorded trap while you are in there —
`tests/test_verification_judge.py`'s single-door scan matches the module name as **text**,
so it fires on prose in comments; check whether the new scans inherited that shape and
whether it makes them evadable in the other direction (a serving path that never spells
the name).

### 3. The `grounded` half may have been discharged by argument rather than by a scan.

`claim_gates.py` states that the groundedness gate is deliberately *not* in this module —
the judge module owns the qualification record, and re-asking there tripped the
single-door scan. The reasoning is sound. But the Done-when clause reads: *"An article
with no qualification record cannot be served labelled grounded, by **any** path, proven
by a scan and not by inspection."* **Does such a scan exist today, or was the clause
answered by a note saying the article path will ask the judge when T3.02 builds it?**
Those are different states, and only one of them satisfies the clause. If it is the
latter, say so plainly — the honest outcome may be that half of T2.95 is a deferral that
should be recorded as one rather than a delivered property.

### 4. Eligibility, staleness, caching, and fail-closed.

- The gate opens on `gate_eligible`, not on presence — correct, given T2.26's INTERIM
  0.8182 would read as a pass to anything checking a file exists. **But what makes a
  record eligible?** Does it bind the corpus, the model, the date, the judge identity? A
  record minted against a different gold, or an eligible record that has since gone stale,
  must not light the labels.
- **Caching.** Is the record read per call, or memoized at import? If memoized, minting a
  record does not light the labels without a restart — which contradicts "no code change"
  in spirit — and, worse, deleting or invalidating one may leave labels served from a
  cached open gate.
- **Fail-closed on unreadable.** The module claims a parse error must not crash the read
  path open. Verify by construction: truncated JSON, empty file, wrong schema, a directory
  where the file should be, and a permissions error. Any one of those serving the label is
  the failure mode that makes the module worse than useless.
- **Suppressed ≠ candidate.** Verify the distinction survives to the reader on **every**
  door, not just the one with a test. A suppressed label that reads as an earned
  `candidate` is a silent downgrade, and the task names that explicitly.

## Method

Run the drills yourself; do not accept the test suite's word for any property. For each
claim you check, state what you did, what you expected, and what actually happened. **Where
you cannot break something, say what you tried** — an unbroken guard with a list of failed
attacks beside it is worth far more than a verdict.

If you find a defect you can fix cleanly within T2.95's surface, fix it and mutation-drill
the fix. If a defect implies the M1 split's safety argument is weaker than stated, **stop
and report rather than patching** — that is a controller decision and a probable Tier-3
amendment, not an implementation call.
