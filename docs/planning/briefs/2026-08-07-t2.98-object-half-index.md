## The gap in one sentence

Doc 08 §5.3 calls the contradiction scan's same-endpoint arm "an index lookup", and the
cost argument that chose cheap SQL over embeddings rests on that. It is true for the
subject half — `ix_knowledge_triples_live` is
`(subject_name, rel_type, object_name) WHERE expired_at IS NULL` — and **false for the
object half**, which has no leading index and therefore scans.

The arm is `_SAME_ENDPOINT_SQL` in `app/services/contradiction_scan.py` (~line 282):

```sql
WHERE project = ... AND expired_at IS NULL AND id <> ...
  AND (subject_name = ... OR object_name = ...)
  AND <overlap predicate>
ORDER BY created_at, id LIMIT ...
```

The `OR` is the shape that matters. With one side indexed, the planner has no bitmap to
OR against, so the whole predicate degrades. This is Tier-C and off both hot paths, so
it is a scale problem rather than a live one — which is exactly why it was carved out of
T2.11 rather than fixed there: that lane's schema mandate was `pg_trgm` and its GIN
index, and two lanes editing the baseline collide every time.

## What ships

An index that makes the object half a lookup, in `0001_baseline.py`, **regenerated in
place**.

**The column order is the decision, not a formality.** The subject index leads
`(subject_name, rel_type, object_name)` so it serves both a bare subject probe and a
subject+predicate one. Decide whether the object side mirrors that
(`(object_name, rel_type, subject_name)`) or is narrower, and say why — a wider index
that no query's leading column matches costs writes and buys nothing. Keep the
`WHERE expired_at IS NULL` partial clause: the query carries it, and it is what keeps
the index proportional to the live set.

## The three Done-when clauses, and what makes each non-vacuous

- [ ] **An `object_name`-keyed candidate search uses an index, shown by plan, not by
      assertion.** `EXPLAIN` the *actual* `_SAME_ENDPOINT_SQL`, with its real bound
      parameters, not a hand-written probe that happens to hit the new index. Paste the
      before and after plans into the report. Two traps: (1) on a table with a handful of
      rows the planner picks a sequential scan regardless and your "after" plan proves
      nothing — seed enough rows that the *before* plan is a seq scan and the *after* is
      not, and say how many; (2) the win you are looking for is a **BitmapOr** over both
      partial indexes, and if the planner still refuses, that is the finding — report the
      plan rather than reshaping the query to force an index.
- [ ] **`0001_baseline.py` regenerated in place — still exactly one revision.** Read
      runbook §9 before touching it. The chain is never two-headed, not even for one
      commit: replace the revision, never append a `0002`. `./scripts/gate.sh` asserts
      exactly one revision. Because this changes the schema, the test database must be
      dropped and re-migrated — conftest does that per run, but confirm the new index
      actually exists in `darkmem_test_cf` after a run rather than assuming.
- [ ] **The existing subject-half lookups are not regressed.** Both plans, before and
      after, for a subject-keyed probe. A new index can change the planner's mind about
      an existing one; showing it did not is the clause.

## Invariants and conventions that bind you

- **Schema-change protocol (runbook §9, `CLAUDE.md`).** Regenerate the baseline in
  place, drop and recreate the database, one revision. You are the single owner of that
  file this round — the concurrent lane (T2.96) is explicitly forbidden from touching it,
  so any conflict you hit is a finding worth reporting.
- **asyncpg needs CASTs** on raw-SQL params. The existing query already casts; if you
  write a probe, match the idiom or you will get `IndeterminateDatatypeError` and
  misread it as a schema problem.
- **Index naming** follows the file's own convention (`ix_<table>_<purpose>`). Match the
  surrounding style, including the comment idiom — the baseline's indexes carry short
  WHY comments, and yours should say what the object half is for, not what the DDL does.

## Scope boundaries

- **Do not change `_SAME_ENDPOINT_SQL`'s semantics.** Rewriting the `OR` into a `UNION
  ALL` of two indexed arms is a tempting way to guarantee index use, and it changes the
  arm's selection under `LIMIT` — the comment above the query is explicit that what the
  cap drops is a stated selection-quality choice. If you believe the rewrite is the only
  way to get the plan, **stop and report** rather than making it: that is a retrieval-
  quality change and this task is a schema one.
- **No other index changes.** Anything else you notice about the baseline's indexes is a
  finding for the report, not an edit.
- **Nothing about the deriver, `repo_ids[]`, or `fact_sources`** — three other lanes.
