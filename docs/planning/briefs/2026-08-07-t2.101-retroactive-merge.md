# Brief — T2.101, retroactive entity merge: the anchoring order that never heals

**Task:** T2.101 · `Opus 5` · `high` · `Size: M` · Doc 10 §6, doc 06 §5 · Gate: G-C
**Depends:** T2.97 — landed and merged (`8a0fefb4`). **Contract:**

**Branch:** `feat/e2-lane-cl` off `feat/e2-truth-core`, worktree `.worktrees/e2-lane-cl`.

## The gap, and why it is the common case rather than a corner

T2.97 gave repo-minted entities embeddings, so Phase 4's ANN probe can see them. That
closes **one order only**:

- **Repo indexed → `repo_entity_anchoring` tick → memory ingested.** Merges. Phase 4
  probes at memory-write time, finds the embedded repo-minted node at cosine ≥ 0.85,
  and canonicalizes under the `names_distinct` guard.
- **Memory ingested → repo indexed later.** Never merges. `assert_from_repo`
  (`backend/app/repositories/graph.py:645`) is an exact-key
  `ON CONFLICT (name, entity_type)` upsert with **no ANN probe**, and nothing re-runs
  Phase 4 over existing rows. `postgres` from code and `postgresql` from a memory stay
  two nodes forever.

Re-derivation does not heal it either: the strip-and-rewrite is keyed the same way, so
it reproduces the same two nodes.

**That second order is what an existing install produces the first time it indexes a
repo** — the vault already has memories, the repo arrives afterwards. So this is the
normal path for every deployment that adopts the code bridge after having used the
system, not an edge case.

Both T2.97's executor and its adversarial reviewer confirmed this independently, and it
is pinned by `test_a_repo_indexed_after_the_memory_still_leaves_two_nodes` in
`backend/tests/test_repo_entity_anchoring.py`. **Your task turns a red test into a
decision rather than discovering the problem fresh.**

## What ships

A Tier-C retroactive merge pass over entity pairs that should have anchored and did
not.

**Finding the pairs is the easy half.** They are entities with a `repo_ids[]`
assertion whose embedding has a near neighbour of the same `entity_type` above the
threshold — the same probe Phase 4 runs, just run after the fact rather than at write
time. Reuse `find_similar_entity` and `names_distinct`; do not write a second
similarity path.

**Merging two live entities is the hard half, and it is the task.** Both rows may
already be asserted, referenced and denormalised. A merge has to move, atomically:

- `memory_ids` — union, not overwrite.
- `repo_ids[]` — union, same.
- **Every relation endpoint** pointing at the losing entity, in both directions
  (`source_entity_id` and `target_entity_id`). Note `entity_relations` has a
  uniqueness constraint on `(source_entity_id, target_entity_id, rel_type)`, so
  repointing can **collide with an existing relation** — that case is a relation merge
  of its own (union its `memory_ids`/`repo_ids[]`, drop the duplicate), not an error to
  let the constraint raise.
- `memories.technologies` — the lowercase denorm recomputed for every memory whose
  entity set changed. Dropping this leaves supersession and the retrieval filter
  reading a stale cache.
- The losing entity's embedding rows in `entity_embeddings__<slug>` — and note the
  entity is deleted, so its partition rows must go with it, per fingerprint.
- `properties.display_name` — the surviving row should keep a sensible original casing.

**The `(name, entity_type)` uniqueness constraint is what makes this delicate**: the
whole graph rests on it, and a half-completed merge that leaves two rows or violates it
is worse than the two nodes you started with. One savepoint per merged pair, in the
idiom `assert_from_repo` already uses (`async with self.session.begin_nested()`), so a
failed merge rolls back to two intact nodes rather than a corrupted one.

## Which entity survives — decide it and state it

Merging is not symmetric. The survivor keeps its id, and every `fact_sources`,
`knowledge_triples` endpoint and UI link that named the loser by id is now pointing at
a deleted row. **Establish what actually references `entities.id` before you choose**,
and say in the report what you found — if nothing outside the graph references entity
ids, the choice is cheap and you should say so; if something does, the survivor rule
has to account for it. Do not assume either way.

## The three Done-when clauses, and what makes each non-vacuous

- [ ] **A memory-first-then-repo pair resolves to one node, at the same 0.85 threshold
      and under the same `names_distinct` guard the write path uses.** Same threshold
      means going through `find_similar_entity` with embedder-produced vectors, not
      hand-written ones chosen to clear the bar. Include a pair the guard must
      **refuse** (differing by a discriminating token — numbers, dates, versions, month
      names) so the test proves the guard still bites rather than that similarity alone
      merges.
- [ ] **`test_a_repo_indexed_after_the_memory_still_leaves_two_nodes` is replaced by
      its inverse, not deleted.** That test is the record of a known limitation; it
      should become the record that the limitation closed. Deleting it erases the
      history that made this task cheap to write.
- [ ] **Merging is idempotent and never merges across `entity_type`.** Two passes leave
      byte-identical rows. And `find_similar_entity` raises on an untyped probe by
      design — a `tool` named `react` must never merge onto a `concept` named `react`,
      whatever the cosine.

## Invariants that bind you

- **Invariant 2 — no cross-fingerprint comparison.** Reach partitions only through
  `child_table(parent, fingerprint)`; `_register_fingerprint` before any insert. A pass
  that reads the active fingerprint once at the top and writes minutes later has the
  rotation exposure Phase 3 documents — say how you handle it.
- **Invariant 15 — Tier C, off capture and retrieval.** Not a dream-job family member
  (contract 6 fixes that family at six; `ppr_snapshot`, `code_deriver` and
  `repo_entity_anchoring` are the precedents for Tier-C jobs outside it). A new
  registered job moves `CLAUDE.md`'s job count, which currently reads **twenty
  registered / fourteen live** — update it, and note
  `tests/test_code_deriver.py::test_main_registers_the_full_direct_job_roster` derives
  the roster from `app/main.py`'s AST and **will go red until you add your key to it**.
  That failure is the guard working.
- **Lowercase entity names on disk**, original casing in `properties.display_name`.
- **Invariant 8** — strip-and-write stays one atomic replace wherever you touch it.
- **asyncpg CASTs** on every raw-SQL param Postgres cannot infer — `CAST(:id AS uuid)`,
  and specifically the `uuid[]` array operations here.

## Scope boundaries

- **No schema change.** `0001_baseline.py` is a single shared mutable file. If you
  conclude you genuinely need DDL, **stop and report** rather than editing.
- **Do not weaken `names_distinct` or the 0.85 threshold** to make more pairs merge. If
  retroactive merging warrants a different threshold from write-time dedup, that is a
  finding and a decision to report, not an edit to make.
- **Do not change `assert_from_repo` to probe.** Making the deriver's write ANN-aware is
  a different design with different costs; this task merges after the fact. If you
  believe the probe belongs in the writer instead, report it as a Tier-2 amendment
  rather than building it.
- **Do not touch the anchoring job or the deriver's derivation logic.**
