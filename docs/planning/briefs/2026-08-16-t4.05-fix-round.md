## The ruling — Fable-tier, and it is the decision

**The synchronous `pipeline.run()` must change. It is a test artifact, not a
defensible design.**

Your stated blocker — the harness wraps every test in a rolled-back outer
transaction, so a detached task's fresh session cannot see the test's uncommitted
repo row — **is real but is not a dead end**, and this suite already solved it
three files away. `tests/test_memory_dream.py` has a `committing` fixture
(`:712`): a real session factory with real commits, and
`TestRegisteredRunner::test_triggering_the_job_runs_a_real_cycle` (`:2233`) drives a
real job through real committed sessions end to end, owning its own cleanup with
per-test project scoping. A webhook test can create the repo through a committing
factory, hit the route, await the registered task, and assert.

A second, cheaper option also existed: make the background task's session factory
**injectable** (a `Depends` the test overrides). `reindex_repo`'s hard-coded
`async_session_factory()` import forecloses that for itself — a new route did not
have to copy it.

**The status code is the tell.** `api-rest-conventions.md:25` defines 202 as
async-accepted; your route returns **202 with the terminal result in the body** —
`status: "indexed"` and the final commit sha, so the work demonstrably completed
inside the request. Synchronous completion is a 200. Choosing 202 anyway shows the
async contract was the intended shape and the behaviour was bent away from it to
satisfy the harness. That is the move the standing rule forbids: implement the
general solution, and report an infeasible task rather than work around it.

**Production cost, since this is what the ruling rests on.** A push webhook fires
on real pushes, so the common case here is a full incremental index — with the DI
pipeline carrying a live LLM and a real vector repo, that is seconds to minutes
behind an HTTP response. Senders time out at roughly 5–30s and mark the delivery
failed on effectively every substantive push, defeating the feature's stated
purpose (doc 10 §5: "purely a latency improvement"). And on a sender disconnect
mid-run, if the handler task is cancelled, `CancelledError` bypasses `run()`'s
`except Exception` repair, leaving `status='indexing'` committed with nothing to
reset it — every later webhook and reindex 409s until a poll heals it, and the poll
may have been auto-disabled. Backgrounding eliminates that class entirely.
