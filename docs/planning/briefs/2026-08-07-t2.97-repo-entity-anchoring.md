## The gap in one sentence

Doc 10 §6 sells the code bridge on anchoring — *"a `postgres` entity minted from a
repo's imports is the same deduped node as `postgres` from a memory (the anchoring
benefit that makes the bridge worth building)"* — and as shipped that holds only for an
**exact `(name, entity_type)` match**. A repo-minted entity carries no row in
`entity_embeddings__<slug>`, so Phase 4's `find_similar_entity` probe cannot see it:
`postgres` from code and `postgresql` from a memory stay two nodes where the memory path
merges them at cosine 0.85 under the `names_distinct` guard.

This is a **narrowing of a stated deliverable, not a bug** — the mechanism is right and
its reach is smaller than the doc claims. It is logged as such, and the reason it was
left open is worth knowing because it shapes your decision: T2.27's clause forbids an
**LLM extraction call**, and an embedder call is not one. Reading the clause as
forbidding both is what left this gap.

## Read this before you choose a shape — the task text is missing a candidate

The task names two options. **There is a third, and it is already built.**
`app/services/reembed.py` is a *missing-fingerprint backfill service*: in the
per-fingerprint world, "obsolete" means "this entity has no row in the active
fingerprint's table", which is **exactly** what a repo-minted entity is.
`ReembedService.list_obsolete_entities` (line ~285) already finds them by anti-join, and
`reembed_entities` (line ~511) already embeds them, honouring the fingerprint partition
rules. What it has is a REST route (`app/api/routes/reembed.py`) and an operator; what it
has **no** scheduled trigger.

So the real question is not "build a backfill" but **which of three**:

1. **Embed at derive time.** Symmetric anchoring, immediate. Puts a model call inside a
   deriver whose whole doctrine is that it has none, and couples repo derivation to
   embedder availability.
2. **A new Tier-C back-fill job.** What the task recommends — but weigh it against
   duplicating a mechanism that exists. Two backfills over the same anti-join, diverging
   later, is a real cost.
3. **Give the existing backfill a scheduled arm.** Least new code; but `reembed_entities`
   is a whole-corpus operation with its own lock set (`ReembedLockSet`) and broadcast
   surface, and turning an operator action into a cron is a behaviour change for every
   entity, not just repo-minted ones. Read `CachePruneFingerprintUnresolved`'s docstring
   before assuming this path is cheap — that service has sharp edges around unregistered
   fingerprints.

**Whichever you choose, argue the other two down in the report.** If you pick 2 or 3,
say what happens to the existing route. If you conclude the task's recommendation is
wrong, overturn it with the reason — the task explicitly permits that. Adding the third
candidate to the task's own text is a **Tier-1 amendment**: make it, and log it.

## The timing problem, which is the harder half

An embedding that arrives *after* the memory-minted duplicate was already written does
not merge anything — Phase 4 dedups at write time, not retroactively. So a backfill
shape has a window in which the two nodes exist separately, and closing that window is
either (a) accepting it and letting the next re-derivation or a merge pass reconcile, or
(b) something stronger. **Say explicitly which window your shape leaves open and what
closes it.** A test that embeds first and then ingests the memory proves anchoring works
in the easy order and says nothing about the order production will actually produce.

## The three Done-when clauses, and what makes each non-vacuous

- [ ] **A repo-minted entity and a near-named memory-minted one resolve to one node,
      proven by test at the same threshold the memory path uses.** "Same threshold"
      means going through `find_similar_entity` at 0.85 with a real embedder-produced
      vector, not a hand-written one chosen to clear the bar. `postgres` / `postgresql`
      is the doc's own example — use it, and also test a pair the `names_distinct` guard
      must **refuse** (a discriminating token: numbers, dates, versions, month names), so
      the test proves the guard still bites rather than that similarity alone merges.
      Note `find_similar_entity` raises on an untyped probe by design; the repo-minted
      entity's `entity_type` comes from the deriver's closed-taxonomy mapping, and a
      `tool` will never merge onto a `concept` however close the names.
- [ ] **The deriver's LLM-free guard still passes, whichever shape is chosen.** T2.27's
      guard is an AST scan and it went through four rounds of hardening — including a
      dynamic-import resolver for literal `import_module` / `__import__` calls. If you
      choose shape 1, you are adding an embedder call inside the guarded module, and you
      must show the guard still distinguishes an embed from an extraction rather than
      being widened until it permits both. Mutation-drill it: add a real extraction call,
      confirm a named test goes red, restore.
- [ ] **No cross-fingerprint comparison (invariant 2).** Every embedding write goes
      through `child_table(parent, fingerprint)`; `_register_fingerprint` runs before any
      insert into a partition. The trap the pipeline documents is a **fingerprint rotation
      mid-run** — Phase 3 re-registers and switches when the active embedder changed since
      Phase 1. A backfill that reads the active fingerprint once at the top and writes
      minutes later has the same exposure. Say how you handle it.

## Invariants that bind you

- **Invariant 2 (no cross-fingerprint joins)** and the partition discipline above.
- **Lowercase entity names on disk**, original casing in `properties.display_name`. The
  deriver already lowercases; your probe key must match or you will silently miss.
- **Closed taxonomy** — `normalize_entity_type` / `normalize_relation_type`.
- **Invariant 15** — if your shape is a scheduled job, it is Tier C and must not be
  reachable from capture or retrieval, and it is **not** a dream-job family member
  (contract 6 fixes that family at six; `ppr_snapshot` is the precedent for a Tier-C job
  outside it). A new registered job moves `CLAUDE.md`'s **"Sixteen registered jobs"**
  count — update that sentence in the same commit.
- **Invariant 8** — if you touch the deriver's write path at all, the strip and the write
  stay one atomic replace.

## Scope boundaries

- **No schema change.** `0001_baseline.py` is a single shared mutable file and **T2.98
  owns it this round** (concurrent lane). The partition child tables are created by
  `embedder_registry.register`, not by the baseline, so a new fingerprint is not a schema
  change. If you conclude you need real DDL, **stop and report** rather than editing.
- **No trigger for `assert_repo_graph`.** T2.96 is landing that on a concurrent lane
  right now. If your shape needs to know when derivation happened, read the repo's
  indexed state, do not add a second call site to the deriver. Coordinate through the
  report, not through the file.
- **No `fact_sources`, no lift, no citation re-verification.** T2.48's.
- **Do not weaken `names_distinct` or the 0.85 threshold** to make a merge happen. If
  anchoring needs a different threshold for repo-minted entities, that is a finding and
  a decision to report, not an edit to make.

## Hygiene

(both exist). A lane worktree has **no `.venv`** — run
`/root/repositories/darkmem/backend/.venv/bin/python` from *your* worktree's `backend/`
so imports resolve against your code. Run the floor in the foreground with an explicit
`timeout` (~4 minutes); never background it and hand control back. Never stage with
`git add -A`. **Commit before any mutation drill**, and revert a drill by restoring your
own copy of the single mutated file — never a path-wide `git checkout --`, which has
eaten two lanes' uncommitted work.

(`tests/` around the pipeline's Phase 3 and `reembed`) and follow that idiom — a test
that reaches the LAN Ollama at `192.168.0.196:11434` is not a floor test.

backend floor.
