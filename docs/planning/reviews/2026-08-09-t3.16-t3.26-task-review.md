### Findings

**I-1 (Important) — The schema layer accepts `next_steps` payloads the database refuses;
result is a 500 on a request the API's own validation declared valid.**
`backend/app/schemas/checkpoint.py` bounds next_steps in *characters* (50 steps × 500
chars = up to 25,000 chars), while `0001_baseline.py`'s
`chk_session_checkpoints_next_steps_len` bounds *bytes*: `pg_column_size(next_steps) <=
16384`. Measured: the schema-maximal ASCII payload is a 25,208-byte JSONB (> 16,384), and
just **15 steps of 500 CJK characters** — nowhere near the schema's limits — is 22,568
bytes. Reproduced end-to-end: both payloads pass Pydantic and `bounded_steps()`, then die
at flush with `CheckViolationError` through `POST /api/v1/checkpoints`; the route catches
only `ValueError`, so the caller gets a 500. This directly falsifies the schema
docstring ("the bounds are imported from the service rather than restated, so the 422
this produces and the CHECK constraint that backs it cannot drift into two different
limits") and the commit message's same claim — the limits did not drift, they were *born*
different: 4000-char summary ≈ CHECK's `char_length(summary) <= 4000` (consistent), but
50×500 chars vs 16,384 bytes are two different limits today. Fix direction: either derive
the CHECK from the schema maximum (≥ ~25 KB for ASCII, ~75 KB worst-case UTF-8), or
enforce a byte-size bound at the schema layer and set both from one constant; and cover
the seam with a schema-maximal round-trip test, which is exactly the test this suite is
missing.

**I-2 (Important) — The checkpoint `origin_key` lives in a different key space from the
one capture stamps, so the claimed correlation with a run's memories does not hold.**
The spec keys checkpoints on "`origin_key` (the agent-run identity)", and feature-epics
row F10 cites doc 05 §2.1 explicitly. Doc 05 §2.1's stamped identity is
`source:origin_id` after `resolve_origin_key`
(`backend/app/api/mcp/client_identity.py:181-211`), which also strips colons from the
declared id (`_sanitize_origin`). The checkpoint doors store the caller's string
**verbatim** — no resolution, no sanitization. Verified live: a capture declaring
`origin_key="ext:1111...5555"` lands on the buffer as
`browser-extension:ext1111...5555`, while a checkpoint saved with the same declared
string is stored as `ext:1111...5555`. The two never match, and no response ever echoes
the resolved key (`origin_key` is write-only over the wire per CLAUDE.md), so a client
*cannot* save its checkpoint under the resolved key even if it wanted to. Within the
checkpoint surface alone this is self-consistent (save and latest use the same literal),
so the done-when stands — but `app/models/checkpoint.py`'s docstring and the migration
comment claim "a checkpoint and the memories from the same run share a key … correlated,
never joined", which is false as shipped, and T3.17/T3.21 (resume, per-run digest views)
will land on this mismatch. Either the checkpoint doors should resolve through the same
doc 05 §2.1 derivation, or the correlation claim must be deleted and T3.17 warned. May be
adjudicated plan-level; flagged for the controller.

**I-3 (Important) — The two-door parity test cannot detect the divergences its own
docstring enumerates.** `tests/test_checkpoints.py::test_the_two_doors_produce_the_same_row_and_the_same_journal`
claims "a door that grew its own default, its own trimming or its own project fallback
fails here" — but it supplies every field explicitly, so the default and trimming paths
are never driven. Verified by mutation, each run against the full 20-test file:
(a) MCP `checkpoint_save`'s default project changed to `"mcp-grew-its-own-default"` →
**20 passed**; (b) MCP door trimming the summary (`body.summary.strip()`) → **20
passed**. (A value-*transforming* mutation, `.strip().upper()`, is caught — the explicit
path is genuinely compared.) Today the doors happen to agree, so behaviour is currently
correct; what is missing is the guard invariant 17 is being credited with, plus a
docstring that overclaims. Sharpened fix: drive both doors a second time with the
*minimal* payload (origin_key + summary only) and compare rows, including `project`.

### The concurrency question (fake-storage faithfulness)

Re-derived rather than accepted. The re-read-after-write algorithm
(`extension/src/origin.js:336-347`) **does** converge for concurrent wakeups *given that
`chrome.storage.local` operations on one area are processed FIFO* (issue-order
serialization): the loser's re-read is necessarily enqueued after the winner's set
completes, so both callers return the winner's key — I walked every interleaving under
that model and none diverges. Chrome sequences same-area storage operations, so the
property holds on the real platform; the in-memory fake is FIFO-with-zero-latency, i.e.
it embodies the same model rather than accidentally hiding a breakable schedule. The
residual honest caveat: under a hypothetical non-FIFO storage (re-read completing before
a concurrent set), one caller can return a key the store no longer holds and one capture
would ride a one-off origin. That is a property of the platform assumption, not a code
defect; worth one sentence in origin.js's comment, no more. The `get`/`set` fake is
faithful to the two calls used (string-key get → `{key: value}` or `{}`; merging set).

### The gate arm

`run_gate "extension tests" 300 "$EXTENSION" env -C "$EXTENSION" npm test` — verified: a
deliberately red test makes `npm test` exit 1, which sets `FAILED_GATE` and the gate's
verdict block exits 1 naming the arm; green exits 0. Degradation with node missing: the
arm would report FAILED (exit 127), not `GATE BLOCKED` — but the frontend arms, which
share the toolchain, fail first and the extension arm is then skipped, so the posture is
exactly the pre-existing floor's. No install step, no node_modules dependency — the
"cannot rot against a dependency tree" claim is sound.

### Findings (all Minor)

- **M-6** The options page tells the user "This install's `origin_key` is `ext:<uuid>` …
  minted once and never changes" — but the server stores
  `browser-extension:ext<uuid>` (source-prefixed, colon stripped by `_sanitize_origin`).
  The displayed value is the *declared* id, not the key corroboration actually counts.
  Cosmetic here; it is the same key-space seam as T3.16 finding I-2.
- **M-7** `extension/manifest.json` declares `scripting` and `activeTab` permissions no
  code uses — unearned permission surface a store review would flag. Also
  `host_permissions` is pinned to `http://localhost:8000/*` while the options page
  accepts any server URL; a non-localhost server will fail on CORS/permissions in MV3,
  making the settings field misleading for the one thing it invites.
- **M-8** `info.selectionText` in Chromium collapses consecutive whitespace/newlines
  (inference from known Chromium behaviour, not re-tested here — no browser in this
  environment): a multi-paragraph selection arrives as one line before extraction. The
  standard workaround (`chrome.scripting` + `getSelection().toString()`) is exactly what
  the unused `scripting` permission would serve.
- **M-9** No `engines` field pins Node: `node --test 'test/*.test.js'` needs Node ≥ 21
  for glob positional args; on an older LTS the gate arm fails with a confusing error.
  (This environment runs v24.18.0.)
- **M-10** The stored bearer token is static; darkmem access tokens expire and rotate, so
  captures will start failing 401 until the user re-pastes a token. Acceptable for an
  inert scaffold; will matter the day it is not inert.
