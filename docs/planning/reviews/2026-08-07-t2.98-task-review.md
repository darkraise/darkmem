## Verdict 2 — Task quality: Needs fixes (one Important, in the report; no code change required)

### F1 · Important — the report's "no scale would force a literal Seq Scan" claim is empirically false

Report, "The plan got something the brief's framing didn't": *"I looked for whether a
larger table would eventually force a literal Seq Scan and concluded it would not: the
existing composite index will always be narrower than the heap under Postgres's cost
model, so the full-index-scan fallback wins over a heap scan at any scale."*

Refuted by measurement. The axis that forces a heap Seq Scan is **value frequency, not
row count**. On my seeded `darkmem_bench_cf` (126,080 rows, fresh `ANALYZE`), with the
object index dropped and a probe on an `object_name` carrying ~5% of the table:

```
->  Parallel Seq Scan on knowledge_triples  (cost=0.00..4770.67 rows=2490 width=142)
      Filter: ((expired_at IS NULL) AND (id <> ...) AND (project = 'rev-cf'::text)
               AND ((subject_name = 'zzz-none'::text) OR (object_name = 'popular-object'::text)))
      Rows Removed by Filter: 40027
```

A literal heap Seq Scan (parallel), exactly the mechanism doc 08 §5.3's "degrades to a
scan" describes — the doc's words were more right than the report grants. The mechanism:
when the estimated match fraction is high, a bitmap heap scan approaches Seq Scan cost
*plus* the full-index-scan cost, so the Seq Scan wins; index-vs-heap width only decides
the selective case. Common endpoint names ("postgres", a hub service) are realistic in a
knowledge graph, so this is not a corner.

Why it matters: T2.98 feeds G-C, and this paragraph is presented as a checked conclusion
correcting the design doc's framing. Left standing, the evidence trail records that the
missing index "only" cost a narrower index traversal, understating the defect the task
fixed. The shipped code is *unaffected* — with the index present the same 5%-frequency
probe stays on `ix_knowledge_triples_live_object` (my S3: BitmapOr, 55 index buffers,
2.7 ms) — so the fix is more justified than the report argues, not less.

**Fix:** amend the report's paragraph — the full-index-traversal fallback is what happens
for *selective* probes at any table size; a sufficiently common `object_name` produces a
literal heap Seq Scan, shown by plan.

### F2 · Minor — shipped test docstring misstates the planner mechanism

`backend/tests/test_contradiction_scan.py`,
`test_the_same_endpoint_arm_has_an_index_for_both_halves` docstring: *"the
`subject_name = X OR object_name = Y` shape needs BOTH disjuncts indexed for the planner
to build a BitmapOr — one indexed side is not enough, since Postgres cannot use a partial
index for one arm of an OR and something else for the other."*

Both halves of that sentence are contradicted by the report's own BEFORE plan, which *is*
a BitmapOr built from one index — the subject index serving both arms, the object arm as
a boundary-less full traversal (`Index Cond: (object_name = ...)`, 1046 buffers). What is
true: each OR arm needs *some* btree containing its column for a bitmap plan at all, and
without a leading index the object arm degrades to a full index traversal (or, under
skew, the whole query to a heap scan — F1). The migration comment in `0001_baseline.py`
states it more nearly correctly; the docstring should not teach the wrong mechanism next
to a test that exists to guard the right one.

### F3 · Minor — the report's cost-number narrative rests on stale planner statistics

The report leans on *"the object-side sub-scan's own cost falls from 26.16 … to 4.42"*.
A full traversal of a ~1,050-page index cannot cost 26.16 under fresh statistics — my
`ANALYZE`d reproduction prices the identical arm at **5170.02** (falling to 4.64 with the
index). The 26.16 is a stale-`relpages` estimate from a freshly bulk-seeded table,
consistent with no `ANALYZE` before measuring. The plan *choice* and the buffer counts
(1046 → 3 on the arm; 1051 → 8 total) are the honest signal, they reproduce, and the
conclusion stands — but the quoted cost figures should not be relied on as evidence.

### F4 · Minor — the inventory precedent is real but selective

Verified: `ix_knowledge_triples_fact_trgm` (T2.11) has no row in
`docs/planning/baseline-schema-inventory.md`, so the report's cited precedent is real.
But it is the *minority* precedent: T2.42's three `knowledge_triples` indexes (fact-text
FTS, endpoint-name FTS, project pushdown — inventory §index table) and T2.84's
`fact_access_stats` objects all got rows when they landed. The dominant convention is
that schema additions are inventoried, and the inventory — which `CLAUDE.md` names as the
baseline's object list — now lags by **two** live indexes on this table. The executor's
flag-don't-edit call was right under single-owner lane discipline; the reconciliation
(both indexes, one edit) belongs to the controller.
