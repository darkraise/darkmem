### Trigger shape chosen: a Tier-C `JobRegistry` job (`code_deriver`)

The brief named two candidates and left the choice to this task. I chose the
job over a hook on `CodePipeline.run` (`app/api/routes/repos.py`'s reindex
background task).

**Argument for the job, and what the hook would have cost:**

1. **Coverage of already-indexed repos.** A reindex hook only fires the next
   time a repo is *reindexed*. Every repo indexed before this task landed
   would sit with empty `repo_ids[]` indefinitely unless someone happened to
   reindex it — which, for a repo nobody touches again, may never happen.
   The job sweeps every repo with a non-null `last_indexed_commit` on its
   own cron regardless of when it was last indexed, closing that gap on the
   very first tick after deploy.
2. **Failure-surface isolation.** A hook lives inside `CodePipeline.run`'s
   background task, which already owns `repo.status` and
   `pipeline_failures` rows under `pipeline_name="code_index"`. Folding
   derivation into that path means a derivation failure either competes for
   the same failure surface (risking it reading as an index failure) or
   needs its own carve-out inside an already state-heavy function. The job
   journals under its own `pipeline_name="code_deriver"`
   (`CODE_DERIVER_PIPELINE_NAME`), so the two failure classes can never be
   confused or overwrite one another.
3. **Cost paid**: staleness between an import change and the next tick,
   bounded by `CODE_DERIVER_MIN_INTERVAL_SECONDS` (300s) and the job's
   hourly cron (`50 * * * *`, staggered off the `0 * * * *` cleanup jobs and
   `ppr_snapshot`'s `30 * * * *`). This is the same trade every other
   Tier-C sweep in `job_runners.py` already makes (`code_reconcile`,
   `ppr_snapshot`).

**Why no staleness tracking (no "assertions older than indexed HEAD"
cursor):** `assert_repo_graph` is a pure DB read + write with no model
call — structurally enforced by `test_the_deriver_path_reaches_no_model_dispatch`
— and it is idempotent per repo (T2.27's strip-before-rewrite). Re-running
it on every indexed repo every tick costs a strip-and-rewrite, never a
duplicate row, and needs no new column (out of scope this round — T2.98
owns the baseline) or per-repo cursor row. If repo counts ever make the
full sweep expensive, a rotating batch cursor mirroring `ppr_snapshot`'s is
the documented next step (see the module docstring in
`code_deriver_job.py`), not something this task pre-built for a cost that
doesn't exist yet at expected repo counts.

**Not a dream-job family member.** `code_deriver` registers directly in
`app/main.py`, the same way `ppr_snapshot` and `code_reconcile` do — never
touches `app/services/dream_jobs.py` or `_ALLOWED_DREAM_JOB_LINES`.
`test_code_deriver_is_not_a_dream_job_family_member` asserts the job's key
and constant name are absent from `dream_jobs.py`'s source.

### How a derivation failure surfaces

`make_code_deriver_runner` (`backend/app/services/job_runners.py`) sweeps
repo ids one at a time, each in its own session/transaction (mirroring
`make_code_reconcile_runner`) so one repo's failure never rolls back
another's write. On success it resolves any prior unresolved failure row
for that repo under `pipeline_name="code_deriver"`; on exception it rolls
back, logs, and records the failure via `PipelineFailureService.record`
with `entity_type="code_repo"`, `pipeline_name="code_deriver"`,
`failed_step="derive"`. That row is visible over the existing
`GET /api/v1/pipeline-failures` door, exactly like an indexing failure —
it is a stale-graph repo, never a failed index run, and it is discoverable
rather than silently swallowed (the same "writer exists, column empty"
failure mode this task exists to close, applied to the failure path
itself).

### Withdrawal half

`RepoManager.delete` (`backend/app/services/repo_manager.py`) now calls
`PostgresGraphRepository(self.session).strip_repo_assertions(repo_id)`
after confirming the repo row exists and before deleting it — same
transaction, same session, committed once at the end of `delete()`.

**Orphan handling: inline, not deferred to `graph_orphan_cleanup`.**
`strip_repo_assertions` (T2.27, unmodified — this task only added a
caller) already deletes an orphaned entity/relation as part of its own
statement set: after stripping `repo_id` from every `repo_ids[]` array, it
deletes any relation with no live memory and no live repo left in its
array, then any entity with no live memory, no live repo, and no
surviving relation. `graph_orphan_cleanup`'s unscoped sweep
(`prune_orphan_entities`) is a backstop for the general case (e.g. a
dangling id left by some other path), not the mechanism this withdrawal
relies on — confirmed by `test_delete_repo_route_strips_its_assertions`,
which asserts the entity row is gone from `entities` entirely
immediately after the `DELETE` route returns, not merely detached from an
array.

- **Test-isolation bug found and fixed during development, not left in
  the final diff.** My first draft of
  `test_runner_derives_repo_ids_end_to_end` committed real rows via a
  session factory bound directly to `tests.conftest.test_engine` (needed,
  since the runner opens its own sessions and must see committed data) but
  its cleanup only deleted the `Repository` row, not the `entities` /
  `entity_relations` rows it created — which have no FK to `repositories`
  and are keyed globally by `(name, entity_type)`, not scoped to a repo.
  That left a real, uncommitted-by-rollback `sqlalchemy`/`tool` entity in
  the shared test database with a dangling `repo_ids` entry, which then
  contaminated a later, unrelated test's rollback-scoped `session` fixture
  (same database, different transaction, visible under READ COMMITTED) —
  a relation from the leftover repo still referenced the shared entity,
  so the later test's own `strip_repo_assertions` call correctly declined
  to delete an entity something else still referenced. Root-caused via a
  standalone reproduction script isolating each layer (direct primitive
  call → `RepoManager.delete` directly → the full HTTP route), fixed by
  having the test's cleanup call `strip_repo_assertions` itself before
  deleting the `Repository` row — which is also a more faithful mirror of
  the real withdrawal path than a bare row delete would have been. Full
  floor and the deriver file are green with the fix in place; this is not
  a live defect in shipped code, only in a test I wrote and fixed within
  the same session before committing.
