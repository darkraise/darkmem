## F1 (Critical) — the fact layer's identity moves with the entity

**Fixed.** The merge no longer stops at `knowledge_triples.subject_id` /
`object_id`. `_rename_facts` now recomputes, for every fact row whose endpoint
id is the losing entity's: the endpoint id, the denormalised endpoint **name**,
and `triple_key`. The reviewer's mechanism is closed at its cause — the lift's
pending predicate matches open facts on canonicalised names, so after the rename
the already-lifted row matches the group again and nothing re-qualifies as
pending.

### The collision fold, and the rule for each column

Recomputing `triple_key` can collide with an already-open row on
`ux_knowledge_triples_open`. `_fold_open_facts` handles it.

**Which row keeps the id is decided on the verification axis, and that is the
whole design.** The keeper is the higher rung — `confirmed` > `disputed` >
`corroborated` > `candidate` — ties broken by the older `created_at` then the
smaller id, which is the ordering `knowledge_triples`' own open-fact lookup
(`_OPEN_FACT`) already uses, so the outcome cannot depend on which side the scan
reached first.

Choosing the keeper this way is what lets the fold **write no verification
column at all**. That is not a convenience:

- `tests/honesty/test_human_only_confirmed.py` holds a tree-wide AST scan naming
  every scope that writes `verification_status` at all, with each entry backed by
  a behavioural pin. A merge job that wrote the column would have to join that
  allowlist — a graph-maintenance pass acquiring a licence to move the truth
  layer's badge.
- A written promotion would also be a promotion the ladder did not decide, and
  `set_verification_status` journals a `verified` row on any status change. That
  row would land in G-C's promotion rate describing a transition no evidence
  explains. `benchlib.promotion_metrics` refuses exactly that shape.

With the keeper chosen by rank, the surviving rung is the one the sanctioned door
already wrote. Nothing escapes the ladder and nothing escapes the human path.

**Why that precedence and not another.** It is read off `verification_ladder`
rather than invented:

| Rung | Why it outranks | Source |
|---|---|---|
| `confirmed` | the machine never moves a ratified fact in either direction — "not down on a lost origin, not sideways on a contradiction" | `verification_ladder.py:511-516` |
| `disputed` | one non-echo contradiction beats any number of corroborations, and the counterpart that produced it survives the fold | doc 08 §4.2, `verification_ladder.py:518-525` |
| `corroborated` | the keeper's `fact_sources` after the fold is a **superset** of what either row had, and corroboration is monotone in that set (origin count non-decreasing, required N non-increasing since added sources cannot make a diverse origin set homogeneous), so the higher rung is the one the union supports — demoting here would strip a badge the evidence still carries, with no evidence change to explain it | doc 08 §4.1 |

**The belief window.** Both sides of a collision are open by construction (the
unique is partial on `expired_at IS NULL AND invalid_at IS NULL`), so there is
nothing to union on `invalid_at` or `expired_at`. The keeper takes:

- `reference_time` → `LEAST`. This is exactly what a single lift over the merged
  graph would have produced (`MIN(memory_created_at)` over one group), which is
  the convergence the whole task is for.
- `valid_at` → the union of two open-ended windows starts at the earlier of the
  two. A NULL `valid_at` is unbounded, so it **dominates** rather than losing to
  `LEAST`; the keeper's own later start would disown a stretch the vault did
  believe the claim.
- `stated_expiry` → plain `LEAST`, which ignores NULLs and therefore lands on
  the earlier stated expiry. That is the under-claiming direction, the one this
  layer is required to err in.
- `confidence`, `demotion_pending_since` / `_cycles`, `review_state`: untouched.
  All three are the recompute's and the ladder's bookkeeping, co-located with the
  status write by design (`set_verification_status`'s docstring makes the
  co-location structural), and the keeper's own values are coherent with the rung
  it kept.
- `learned_in`: has no writer anywhere in the tree today, so it is left alone
  rather than given a union with no producer to exercise it.

**Provenance is moved, not copied.** `fact_sources` is what
`COUNT(DISTINCT origin_key)` reads; a copy left behind would let one memory
corroborate one claim twice. Exact `(source_kind, source_ref)` duplicates are
dropped rather than moved. `fact_access_stats` is summed, with `GREATEST` on
`last_accessed` — split across two rows it under-reports the survivor to
`review_ranking`'s frequency arm.

**The duplicate is expired, never deleted.** `article_citations.fact_id` takes a
**hard** FK onto `knowledge_triples(id)`, and the baseline says why in as many
words: facts are invalidate-not-delete, so the hard FK is safe. `expired_at`
rather than `invalid_at` is the right marker on two counts: the row is not a
belief that stopped holding, and `ix_knowledge_triples_fact_trgm` — the
contradiction scan's shortlist — is partial on `expired_at IS NULL`, so closing
the window instead would leave the scan free to pair a fact against itself under
its other name. The write goes through `KnowledgeTripleRepository.expire`, the
sanctioned belief-axis door, so it journals an `expired` row.

### What is deliberately *not* rewritten

`knowledge_triples.fact` — the prose. Two reasons, and the first is decisive:
its shape is owned by one function in `app/services/fact_lift.py`, and
`tests/test_dream_jobs.py`'s invariant-15 family scan fails the build on any
module under `app/` that imports that module, reaches it through an attribute,
or names it in a non-docstring literal. Reproducing the sentence locally would
put a second producer on a text the corpus keeps single-sourced. Second, the
baseline records that `fact` is written once at lift time and never updated, and
the FTS indexes over it are expression indexes built on that premise. The
consequence is honest rather than silent: a folded-away row's prose keeps the
spelling that was asserted, and the *identity* columns every consumer keys on
have moved.

## F2 (Important) — the scan rotates instead of re-probing one fixed prefix

**Fixed, and the report's own claim corrected.** The scan now carries a
`(created_at, id)` keyset cursor persisted in its own `config` row
`repo_entity_merge_state`, wrapping to the start when a window comes back
shorter than the batch. `candidate_batch` bounds one run's **cost**, never the
coverage.

The idiom is lifted from `verification_recompute`'s slow arm, including its
reason for a dedicated row rather than the job's `config` dict:
`JobRegistry.set_config` is the operator-facing surface behind
`PUT /api/v1/jobs/{key}/config` and validates every write against the schema, so
internal bookkeeping routed through it is either rejected as an unknown key or,
once admitted to the schema, becomes operator-editable. `created_at` alone
cannot carry the cursor — rows written in one transaction share one `now()`, so
a bare `>` skips the rest of a tie and a bare `>=` never leaves it.

**Corrections shipped with the fix:**

- The knob's `help` text no longer implies full coverage per run; it now says
  successive runs rotate through the whole population.
- Round 0's report §4 ("re-probes every repo-asserted entity ... on every run")
  was false above the batch size. It is superseded by this document; the claim
  is not repeated anywhere in the shipped code.

## F4 (Minor) — accepted, and narrower than reported

**Accepted, recorded in the module docstring.** The race is real but the fix
made it strictly narrower than the review describes, and the window that remains
cannot be closed from this lane.

`fact_lift` re-reads the assertion **inside** its savepoint before writing
(`_STILL_ASSERTING`, then a `compute_triple_key` equality against the
candidate). If the merge has committed by that read, the memory now asserts the
*surviving* name, the recomputed key no longer equals the candidate's, `live` is
empty, and the lift mints nothing at all. So the exposure is not "any lift that
snapshots the loser's id" — it is the gap between that in-savepoint re-read and
the lift's own commit.

A lift landing in that gap writes a triple carrying the losing id and the losing
name, and no later run can repair it: the loser's id is gone, and nothing maps
it to the survivor. Closing it means taking row locks on `entities` from the
lift, which is that module's decision, in the dream-job family this module is
forbidden to reach. Left, stated, and the residue is the same shape as the
orphaned-open-fact residue already documented above — an open fact under a name
no graph group produces, which nothing re-lifts and nothing double-counts.

## F6 (Minor) — accepted, with the lock window measured rather than assumed

**Accepted, recorded in the module docstring.** The observation is right — one
session, one commit at the end of the run, and savepoints release but row locks
do not. Two things make it the right trade rather than a deferred fix:

1. **A tick that merges nothing takes no row locks at all.** Nothing is locked
   until a probe matches: the candidate scan and `find_similar_entity` are plain
   reads, and the first `FOR UPDATE` is inside `merge_entities`. A run that
   merges nothing is the steady state, so the lock window is empty on
   essentially every tick after the backlog drains.
2. **The backlog is now bounded by the rotation window** (F2), so even a first
   run over a large install holds locks for at most `candidate_batch` probes'
   worth of merges, all SQL-only, no model call on the path.

Against that: moving the commit inside `merge_repo_entity_duplicates` would mean
committing a session this module does not own — the transaction boundary belongs
to the runner, as it does for every other Tier-C pass here — and it would break
the unit suite's rolled-back-session isolation, trading a real property for a
window that is empty in the steady state.
