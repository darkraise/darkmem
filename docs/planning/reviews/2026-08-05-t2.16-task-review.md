## Verdict 2 — Task quality: **Needs fixes** (2 Important, 6 Minor)

### I1 — Important. A skipped proximity arm still strips the proximity edges it did not re-evaluate.

`memory_dream.py:1719-1846`: when `fingerprint is None` the proximity arm is skipped
(`:1772`) — but the strip (`:1826-1836`) still runs over the full seed window with a
`kept` set that cannot contain proximity pairs. Reproduced with a scratch driver:
derive a proximity edge under a live canary, re-run the pass with `fingerprint=None` —
`stripped=1, rows_deleted=1`, edge gone, though its cosine signal still holds and was
never re-measured. The strip journals nothing (E8) and the original action's undo is
CAS-refused after the strip, so the disappearance is unexplained and unrecoverable
except by re-derivation.

Why it matters: on a canary flap, proximity edges churn (silent delete, then
re-derivation with fresh `consolidated` rows on recovery). On a deployment where the
canary stays dead — the `dimensions`-unset config the executor's own cycle test
names — every proximity edge with a seed endpoint is progressively retired as the
cursor sweeps, while the run reports green with a skip reason. This contradicts D9's
own principle (strip only what the run re-evaluated) and the strip comment's stated
premise ("a pair at or below that bound was examined by all of them" — false when an
arm was skipped). The same shape applies per-seed when a seed has no vector under the
current fingerprint post-rotation; that variant is arguable (the new partition
genuinely cannot confirm the signal) and can be ruled either way, but the dead-canary
case is not. Fix shape: when the proximity arm is skipped, spare window triples whose
stored block's `signals` include `embedding_proximity` — or skip the strip for that
run entirely and count it.

### I2 — Important. The cap-engaged strip bound has no test that can fail.

Proven by mutation: a pytest plugin replacing `_PASS_TRIPLES_IN_WINDOW`
(`memory_dream.py:1552`) with an unbounded variant leaves **all 24 tests green**.
The plan's §5 explicitly requires the truncation test to show "the strip leaves
un-evaluated pairs' edges alone"; the test named for it
(`test_a_truncated_run_leaves_unevaluated_edges_alone`, `test_...py:795-833`)
exercises the *opposite* branch — zero candidates, unbounded window, strip
everything — and no test seeds a pre-existing edge above an engaged bound. This is
exactly the shape the executor's own third drill exposed once already (a green-first
mutation revealing a test that proved nothing), one property over.

The bound itself **works**: my driver seeded 10 candidate pairs, derived all, re-ran
with `derivation_batch=3` — `stripped=0`, all 10 edges survive (`bound` at
`:1800`, window clause at `:1557-1570`). So this is a test gap, not a code defect —
but it is the single most subtle clause in E4's rewrite, it guards the "edge churn as
a pure cap artefact" pathology F4 was raised for, and today any regression to it
ships green. Fix: seed more candidates than the cap with pre-existing above-bound
edges; assert `stripped == 0` and survival.

## The two-signal question — accept it; do not ratify a family

I verified the executor's argument member-by-member against `RELATIONSHIP_TYPES`
(`taxonomy.py:49-74`), `LEGACY_RELATION_TYPE_MAP` (`:115-137`) and
`_RESCUE_CONNECTORS` (`extraction_clean.py:717-737`). It holds, and no defensible
family was missed:

- `DEPLOYED_ON` absorbs `RUNS_ON` and `LOCATED_IN`, plus seven rescue connectors
  including bare `"on"` at 0.6 — and is plural even natively (deployed on linux AND
  docker AND aws are simultaneously true at different abstraction levels).
- `HAPPENED_ON` absorbs `VISITED` and `LIVES_IN`; `AUTHORED_BY` absorbs `WORKS_AT`
  and `PUBLISHED_IN` and is plural natively; `CAUSES` absorbs `PRODUCES`/`FIXES`.
- `EXTENDS` — the one candidate the executor's list lumps under "plural by
  construction" that deserved a sentence — fails too: multiple inheritance and
  spec-extension usage are plural facts.
- `REPLACES`/`IMPROVES_ON` are plural (one successor, many predecessors);
  `RELATED_TO` is the normaliser's sink and even absorbs legacy `CONTRADICTS`.

So under D4's shape (two distinct targets under one family = conflict), the empty
frozenset is the correct ruling, and the arm is genuinely wired: the injected-family
tests prove firing, D3 suppression and the succession guard non-vacuously, so
ratifying a list later is a one-line edit plus updating the pin at
`test_...py:563`. **Recommendation: accept the two-signal outcome and ratify the
empty list.** The `REPLACES`-antisymmetry candidate is real and deterministic, but it
is inverted-endpoints, not distinct-targets — adopting it amends the reviewed plan,
and it partially duplicates the mutual-flip guard the supersession ordering already
provides at lifecycle level; if wanted, it is its own small plan-and-review round,
not a ratification.
