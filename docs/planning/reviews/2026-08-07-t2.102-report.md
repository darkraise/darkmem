## 3. The guard: shape chosen, alternatives argued down

**Chosen: assert on the backend side, in Python, parsing the frontend `.ts` file.**

The brief listed three shapes. I picked the third for a reason the brief itself
anticipated but didn't have visibility into: **this codebase already has the exact
precedent**, in the opposite direction from what "parse `events.py` from a frontend test"
would need. `backend/tests/test_taxonomy.py::test_frontend_shares_one_vocabulary_source_that_matches_the_backend`
already does `(REPO_ROOT / "frontend/src/lib/taxonomy.ts").read_text()` plus a regex split,
from a **Python** test, to check the frontend's `MEMORY_TYPES` list against the backend's.
There is no precedent anywhere in the repo of a frontend/vitest test reading a Python
source file. Matching the established idiom means:

- No new fragile pattern is introduced — the "split on a marker string, regex the block"
  technique is already reviewed, already trusted, and already breaks loudly (not silently)
  if the marker text is edited without updating the test, exactly like
  `test_graph_colour_map_covers_every_memory_type` does for a different map today.
- The harder half of the problem — finding which `EVENT_TYPES` values have a *live emitter*
  — has to happen in Python regardless, because it means reading Python source (AST or
  regex over `backend/app`). Doing that from a Node/vitest process would mean either
  shelling out to Python (adds a runtime dependency vitest doesn't otherwise have) or
  reimplementing Python-source parsing in TypeScript. Neither is smaller than parsing one
  `.ts` file from Python, which the codebase already knows how to do.
- The "generate a checked-in TS constant" option was rejected for the reason the brief
  named: it adds a generation step nobody would remember to run, and a stale generated file
  fails in the same silent direction as the bug this task exists to close.

**Why a frontend test also exists (`event-taxonomy.test.ts`).** This is *not* a second
attempt at the cross-language guard — it cannot be one, because vitest cannot read Python
source, so it structurally cannot detect a missing emitter. It exists for a narrower,
argued reason: `npm test -- event-taxonomy` (the brief's own Verify command) has to
resolve to something, and the map's *own* internal shape — every tabbed value names a real
`FeedCategory`, no value is claimed by both `EVENT_TYPE_CATEGORY` and
`EVENT_TYPES_WITHOUT_TAB`, and an unrecognised event type is neither tabbed nor recorded —
is worth pinning where the map is consumed. If someone edits `event-taxonomy.ts` and typos
a category string, or double-lists a value, this is what catches it before the (slower,
whole-`backend/app`-scanning) Python test would even run in CI. The two are not redundant:
one verifies the map's internal consistency, the other verifies the map's *coverage*
against a source of truth it cannot see. Dropping either loses a distinct failure mode.

## 4. What the emitter detection sees and misses

`_scan_event_type_kwargs()` in `test_event_taxonomy_map.py` walks every `.py` file under
`backend/app` with `ast`, and for every **call** carrying a keyword argument literally
named `event_type`, tries to resolve that argument to a literal string:

- A string constant resolves directly.
- A bare name or attribute (`EVENT_TYPE`, `journal.EVENT_TYPE`, `CITATION_STALE`, ...)
  resolves by looking up that identifier against every `NAME = "literal"` assignment found
  anywhere under `backend/app` (module- or class-level), unioning all matches. This is
  **not module-scoped** — a name collision across two unrelated files just adds an extra
  candidate literal to the set, it can never hide one, so it fails safe rather than
  precise.
- A `<dict>.get(key, default)` call (the `relational.py` `_ACTION_EVENT_TYPE` shape)
  resolves by reading the dict literal's own values, ignoring the fallback default.

**Why match any call with an `event_type=` keyword, not just calls to `record_event`
itself.** The first version I tried matched only `record_event(...)` calls directly, and it
silently missed `deprecated`: `supersede.py`'s `_journal()` helper receives the literal at
its own call site (`_journal(event_type="deprecated")`) and forwards it to `record_event`
through a bare parameter the AST cannot resolve without tracing the call graph. Widening the
match to "any call, any callee, keyword literally named `event_type`" finds the literal
wherever it actually appears as a constant, with no call-graph tracing — it caught
`deprecated` at `_journal`'s two call sites for free. I verified this by running the scanner
standalone before wiring it into pytest and diffing its output against a manual `rg` sweep
of every `record_event(` call site in the codebase; the manual sweep is what first told me
`deprecated` was missing.

**What still resolves to nothing, and what the guard does about it.** Three call sites
in the current codebase cannot be resolved to a literal by this scan, and the guard
enumerates them explicitly (`_EXPECTED_UNRESOLVED`) rather than silently dropping them:

1. `app/api/routes/auth.py` (`_record_audit`, forwards a bare `action` parameter). Its one
   caller passes the literal `"auth_login_failed"`, which is **not** an `EVENT_TYPES`
   member at all — a separate, pre-existing gap between auth's ad hoc event vocabulary
   (`auth_login_success`, `auth_logout`, `auth_password_change`, `auth_setup`,
   `auth_login_failed`, `setup_complete`) and the closed `EVENT_TYPES` list. See the finding
   below; it is out of this task's scope.
2. `app/api/routes/events.py` (`list_events`). Its `event_type` keyword is a **read-side
   query filter parameter**, not a value being emitted — same keyword name, unrelated
   concept, a direct consequence of matching on keyword name rather than callee.
3. `app/services/supersede.py`'s own inner `record_event` call inside `_journal` — now
   redundant with finding #2 above once resolution happens at `_journal`'s call sites
   instead, but it still shows up as its own unresolved node.

`test_no_new_unresolvable_event_type_call_site` asserts the unresolved set equals exactly
this allowlist. A **new** unresolved site — the shape that would hide a real future
`_journal`-style indirection — fails that test immediately, forcing a human to either teach
the resolver or add the site here with a reason. This is what keeps "what my detection
misses" from becoming "what my detection silently misses forever."

**What no amount of one-hop AST resolution catches:** an event type assembled at runtime
(an f-string, string concatenation, a function call that returns a string, a value read
from config). Any such site becomes unresolved and must be triaged the same way — added to
the allowlist with a reason, or the resolver extended. None exist in the codebase today.

## 7. Adjacent findings (not fixed — out of scope)

- **`setup_completed` vs `setup_complete`.** `EVENT_TYPES` carries `"setup_completed"`;
  `app/api/routes/setup.py` actually journals the literal `"setup_complete"` (no `d`). These
  are different strings — the vocabulary member has no live emitter, and the emitted
  literal is itself outside `EVENT_TYPES`. This looks like a spelling drift from whenever
  one of the two was last touched. Not fixed: it is a backend behavioural question
  (which spelling is correct, and does changing it break anything reading `events` rows
  written under the old spelling), and the brief scopes this task to reading the
  vocabulary, not fixing emitters.
- **`auth_lockout` has no emitter at all.** `login_rate_limit.py` implements the lockout
  counter and duration but never calls `record_event` for it — the vocabulary anticipated
  an audit trail for lockouts that was never wired up. Same reasoning: a backend feature
  gap, not this task's to close.
- **A cluster of auth event types live entirely outside `EVENT_TYPES`.**
  `auth_login_success`, `auth_logout`, `auth_password_change`, `auth_setup`, and
  `auth_login_failed` (via `_record_audit`) are all journaled with `record_event` but none
  is a member of the closed `EVENT_TYPES` list — each triggers `record_event`'s own
  "outside the closed vocabulary" warning log every time it fires, and none of them was
  in scope for this task's guard (the guard only intersects emitted literals with
  `EVENT_TYPES` membership, by design — widening that vocabulary is not this task's to do).
  This is either a pre-existing, accepted gap (auth events are read through
  `GET /auth/audit`, a separate filtered view, not through the general `events` API) or a
  genuine backlog item; flagging it rather than judging it.

None of these were touched. They do not affect the guard's correctness for the values it
does track, and fixing any of them would be a backend behavioural change this task's brief
explicitly rules out.
