## F-C — the diversity group's cross-file dependency is now validated

**Was:** the `diversity` design spans two committed files — each claim's second origin is
`repo_fixture.json`'s parsed import of the same package — and nothing checked the pairing.
`_DESIGN` grants `diversity` a single memory origin precisely *because* the second one is
supposed to come from the parse, so a claim added or renamed without its import loaded,
validated, ran, and then held at one origin outside the bucket, visible only as a smaller
denominator. The existing test checked the fixture side alone.

**Now:** `promotion_corpus.validate_diversity_group_against_fixture(entries, fixture)` ties
every `diversity` claim to exactly one of the fixture's `dependency_name`-normalised
imports and refuses three shapes — a claim naming none of them, a claim naming several
(the grouping is then unreadable off the corpus), and two claims naming the same one (they
converge on one fact). It runs inside `prepare()` before any database work, and both
committed JSON files carry the constraint in their own notes so an editor meets it before
breaking it. The reverse direction stays allowed and is documented: an import no claim
mentions mints a code-only fact the completeness probe already counts as a carve-out.

## F-D — `claim_key`: made robust, and documented where it will be broken

**Chosen: both, weighted to robust.** `claim_key` still derives the claim from the key
rather than reading a declared label — a declared label can disagree with the content,
which is worse. What was fragile is that *any* trailing single-character segment reads as a
variant marker, so a future `pg-c` would be filed under an invented claim `pg` and the
design check would validate a grouping nobody wrote down.

`validate_claim_key_convention` now runs in the loader and refuses a variant marker with no
sibling sharing its head — variants exist in sets by construction (`-a`/`-b`, `-1`..`-3`),
so a lone one is a key whose last segment is not a variant marker at all, and the message
says to give it a final segment of two characters or more. The convention is also written
into `corpus.json`'s own notes as editing constraint 1, beside the cross-file constraint.

**Residual, stated rather than hidden:** two *new* single-character keys sharing a head
(`pg-c` **and** `pg-d`) would pass the sibling rule while being different claims. For the
`diversity` group F-C's guard catches it — the merged claim would name two dependencies and
be refused — but for the other groups it is not mechanically detectable without semantics.
The convention note is the mitigation there.

**Mutation drill:** neutering `validate_claim_key_convention` (early `return`) failed
`test_loader_refuses_a_variant_marker_with_no_sibling`; restored, green.

## F-E — R2's companion number is wired into the harness, not skipped

**Chosen: wire it.** `promotion_bars`' ruling R2 requires every measurement run to report
the in-window fold count beside the audit, and neither `promotion_metrics.py` nor
`run_gc_evidence.py` computed it, so "never quote the audit without it" was unenforceable.
Implementing a number the committed ruling already defines is not designing a metric: it
states no bar, enters no rate, and moves no verdict predicate — it only caps what a zero
may claim, which is the conservative direction. Nothing in `promotion_bars.py` was touched.

The count is R2's own definition — `expired` events on facts carrying a prior in-window
corroboration — computed by SQL over `events` alone, with the same `(created_at, id)` tuple
compare and the same unbounded-above window as the dispute arm, and for the same two
reasons (a fold after the window still breaks the join the audit depends on; `now()` is
constant within a transaction). It is deliberately an **upper bound on folds**: `expire()`
is also reached by human adjudication and by provenance withdrawal, and the journal carries
no discriminator, so narrowing it would need a guess that shrinks a cap.

It surfaces in three places a gate reader actually looks at: the rendered report (with the
paragraph explaining why the rate must not be quoted without it), the ledger row
(`false_promotion.expired_after_corroboration`), and `run_gc_evidence.py`'s audit verdict
line. On this corpus it is **0**, as the review predicted.

**Mutation drill, two ways.** Removing the `(created_at, id)` compare from the new SQL
failed `test_an_expiry_before_its_corroboration_is_not_an_r2_fold` (`assert 1 == 0`).
Removing the rendered line and the ledger key failed
`test_a_corroborated_fact_later_expired_is_reported_as_r2s_companion` on the `'R2 companion'
in render_report(...)` assertion. Restored from my own file copies, green.
