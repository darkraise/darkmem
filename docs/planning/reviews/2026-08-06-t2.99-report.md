# T2.99 — the topics door serves a raw-rung aggregate

**Lane:** `feat/e2-lane-cc` (worktree `.worktrees/e2-lane-cc`)
**Databases:** `darkmem_test_cc` / `darkmem_bench_cc`
**Status:** DONE_WITH_CONCERNS — the task's three clauses are met and drilled; one
adjacent finding outside this task's scope is recorded below (AF1) and is a wider
hole than the one this task closes.

## The defect, restated from the tree

`GET /api/v1/knowledge/topics/pin-suggestions` (mounted, authenticated) serves
`verified_fact_count` per suggested subject. It was computed by
`pin_suggestions._FACT_COUNT` as `COUNT(*)` over
`verification_status = ANY('{corroborated,confirmed}')` — the raw column.

With G-C's promotion record absent, `corroborated` is withheld and served as
`candidate`, while `confirmed` is human-ratified and served openly. So the
subtraction is one extra request:

```
GET /knowledge/facts?project=P&subject_name=S&verification_status=confirmed  -> C
GET /knowledge/topics/pin-suggestions?project=P  -> V for subject S
withheld corroborated facts for S = V - C
```

The second exit is membership: `fact_count < fact_floor` decides whether the
subject is nominated at all, so a suggestion's mere presence asserted "this
subject anchors at least one verified fact" over the same raw set.

## The fix

`backend/app/services/pin_suggestions.py`. The counted set is now resolved
through the gate's own inversion rather than named as a literal:

```python
def served_verified_statuses(gate: ClaimGate | None = None) -> list[str]:
    if gate is None:
        gate = corroboration_gate()
    raw: set[str] = set()
    for served in VERIFIED_SERVED_STATUSES:
        raw |= raw_statuses_for_served(served, id_kind=FACT_ID_KIND, gate=gate)
    return sorted(raw)
```

Gate closed → `['confirmed']`. Gate open → `['confirmed', 'corroborated']`.
`compute_pin_suggestions` resolves it once per call and passes it to
`_verified_fact_count`, so the served number and the floor decision key on the
same value and move together. Nothing else changed: the SQL text is untouched,
the wire schema is untouched, `journal_pin_suggestions` inherits the gated
number because it reads the same dataclass field.

Derived from `raw_statuses_for_served` rather than written beside it for the
reason that function's own docstring gives — the filter, the field and now the
count must not drift into three answers about one fact.

### Why both exits are gated, not just the number

The dispatch left this open and asked for the argument either way. Both are
gated. The residue is not merely closed as a side effect; gating only the number
is *unsound*, and the drill below demonstrates it rather than asserting it.

A suggestion served with `verified_fact_count = 0` while the floor is 1 says, in
one bit, "this subject met the floor on facts you are not being shown." That is
the same oracle with less resolution, not a different class of thing. The
principle the module family already settled — derivation may use the true status,
the wire may not reveal it — puts membership on the wire side: whether a row
appears in a response is served output, not derivation.

There is also a positive argument, independent of the leak. The suggestion's own
claim is "this subject anchors at least `fact_floor` verified facts." Under a
closed gate that claim is exactly what G-C has not certified. Serving it in
existential form while refusing it in labelled form would be the same unbacked
assertion wearing a different grammar.

**The cost, stated plainly.** With the gate closed, a subject supported only by
`corroborated` facts is no longer nominated. On a corpus whose human ratifications
are rare — which is the expected pre-G-C state — the pin-suggestion door goes
largely quiet. That is the honest reading and it matches how the facts filter
already behaves ("with the gate closed nothing is served as `corroborated`, so
the honest page is no rows"). It reverses on the record alone, with no code
change, which the third drill drives at the door.

**One residue remains and is acceptable.** A subject's *community* still appears
in the `diff` array whether or not it is nominated, so a reader learns the topic
exists. That reveals nothing about the verification axis: `diff` membership is
computed from `memory_communities` and the stored topic prior, and no rung ever
enters it. The second drill asserts exactly this shape — both subjects absent
from `suggestions`, both present in `diff`.

## The aggregate sweep

The round-2 reviewer swept caller-controllable status *filters*. Aggregates are a
different shape and had not been swept. Four passes, all over `backend/app`:

1. **SQL string constants** containing `verification_status` together with an
   aggregate function. Two hits, both accounted for:
   - `pin_suggestions._FACT_COUNT` — this task's, now gated.
   - `review_ranking._RANKED_FACTS_TEMPLATE` — its aggregates (`COUNT(*) AS
     source_memories`, `COUNT(DISTINCT ...) AS neighbour_count`) are over
     `open_facts`, whose membership is the caller's `review_state = 'open'`
     predicate. Its one rung reference is `WHERE o.verification_status =
     'disputed'` in the dispute-decay CTE, and it yields `disputed_at`, a
     timestamp. `disputed` is ungated and its own preimage, so no number
     downstream of it can separate a withheld rung from a candidate.
2. **Fragment-assembled SQL** — an aggregate and a rung predicate in different
   string constants, which pass 1 cannot see. One hit:
   `KnowledgeTripleRepository.list_live`'s `SELECT COUNT(*) ... WHERE
   {where_sql}`, whose `total` rides the facts list on the wire. Already gated,
   by T2.95 round 2: `facts_read` hands it a `raw_statuses_for_served` set, and
   the existing door drill asserts `total == len(items)` so a filter that
   narrowed the page while leaving the count intact would fail.
3. **ORM aggregates** — every `func.count` / `select(func.…)` under `app/`. None
   touches `knowledge_triples` or the verification column at all.
4. **Python-level aggregates** — every function whose body mentions
   `verification_status` and applies `len` / `sum` / `Counter` / `max` / `min` /
   `.scalar_one()`. Eleven functions; each inspected. The counts belong to
   composition bookkeeping (`excluded_by_result_limit`), chat's `not_found`
   tally, or `sorted()` over label keys. None counts rows by rung.

**Conclusion: no other served aggregate over the raw rung.** Two aggregates key
on the rung anywhere in the tree; one is this task's and is now gated, the other
(`list_live`) was gated by round 2.

Pass 1 is now a build guard —
`test_only_the_swept_aggregates_name_the_rung` in the gate suite — pinned to
those two files with each one's reason recorded at the constant. It is
deliberately over-inclusive (it fires on an aggregate *near* the column, not
only on one keyed *on* it), the same error direction the honesty guard chose:
an unrecognised shape lands in front of a human rather than passing silently.
Its reach is stated in the test rather than implied — passes 2–4 are one-time
sweeps, not standing scans, and the reason that is acceptable is the one round 2
reached: what covers the uncovered shapes is a door drive with the gate closed.

## Adjacent findings — not fixed here

### AF1 (Important, wider than DF1): the events door serves the raw rung per fact

`GET /api/v1/events?object_type=fact&event_type=verified` returns
`EventLogEntry.payload` verbatim, and `KnowledgeTripleRepository.set_verification_status`
journals `{"before": {"verification_status": …}, "after": {"verification_status": …}}`
on every transition. Both reads sit behind the same `require_auth` as the facts
door. So for any fact that has ever transitioned, the stored rung is directly
readable — no subtraction, no inference. That is strictly stronger than the
oracle T2.99 closes and stronger than the per-fact membership oracle round 2
closed.

The sites carry `ungated_status(...)` with the rationale "Journal, not label:
the two rungs a transition moved between are the history of the ladder, and a
gated copy would record a movement that did not happen." The *write-side*
argument is sound and I would not change it. What is not covered is the
**read** side: `claim_gates.ungated_status`'s own docstring defines the wrap as
"a claim that the value reaches no reader as a label," and `list_events` hands
that payload to an authenticated reader. `events.py` does not call the badge
producer, so the round-2 label scan never asks it the wholesale-copy question
about `[dict(row) for row in result.mappings().all()]` — a stated blind spot of
that scan, met here.

Not fixed in this lane, for three reasons: it is not an aggregate and so is
outside T2.99's stated scope; the audit substrate is exactly what G-C's own
false-promotion audit reads, so narrowing it is a ruling about the gate's
relationship to its own evidence rather than a code fix; and the plausible
shapes (a rung-aware filter on the events reader, or a serving-time projection)
are all Tier-3 amendments to a settled append-only design. **Recommend triaging
it as a new finding beside T2.28**, the same place DF1 was sent.

Note this does not make T2.99 pointless — a leak elsewhere does not license one
here, and the two doors have different audiences — but it does bound how much
the claim-serving gate is worth in practice until AF1 is answered.

### AF2 (Minor): `confidence` is correlated with the withheld rung

`FactListItem.confidence` is served on the facts list and detail and rides the
composed row. `verification_ladder.compute_confidence` is
`min(0.90, 0.40 + 0.40·support + 0.10·gate_fired)`, and promotion requires
`support = 1.0`, so a `corroborated` fact always serves `confidence ∈ {0.80,
0.90}` while a genuine candidate that never met the bar serves below `0.80`.
It is not an inverse function — a contradiction-blocked candidate also reaches
0.90 — so it is a strong probabilistic distinguisher, not an oracle.

It is deliberately outside the swept class: nothing aggregates over the rung to
produce it, and it is evidence rather than label, the same category as the
badge's `origin_count` (which the producer already nulls when the label is
suppressed). Recorded so the next reviewer does not have to re-derive it, not
proposed as a fix.
