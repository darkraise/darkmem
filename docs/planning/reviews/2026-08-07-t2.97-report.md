## 1. The shape chosen, and the two rejected

**Shipped: shape 2, a Tier-C back-fill job, scoped to repository-asserted rows.**
`repo_entity_anchoring` in `app/services/entity_anchoring.py`, registered in
`app/main.py` with runner `make_repo_entity_anchoring_runner`
(`app/services/job_runners.py`), hourly at `45 * * * *`, `min_interval_seconds=300`,
config schema `missing_batch` (default 200, 0 disables) and `embed_chunk` (20).

### Shape 1 — embed at derive time — is blocked, not merely awkward

The task text and the brief both frame this as a doctrinal cost ("a model call
inside a deriver whose whole doctrine is that it has none"). It is stronger than
that. T2.27's guard (`tests/test_code_deriver.py::test_the_deriver_path_reaches_no_model_dispatch`)
forbids `_LLM_DISPATCH_ATTRS`, and that set is:

```
chat_completion, chat_completion_stream, embed, embed_batch,
embed_batch_chunked, get_llm_orchestrator, LLMOrchestrator
```

An embed and an extraction are reached through the *same* handle — you cannot
hold `LLMOrchestrator` for one and not the other — so the guard has no
structural seam to widen along. Permitting the embed means dropping
`get_llm_orchestrator` and `LLMOrchestrator` from the forbidden set, at which
point a planted `client.chat_completion('extraction', msgs)` in a module reached
via a variable is no longer caught by the module route either. The brief asked
for a demonstration that the guard "still distinguishes an embed from an
extraction rather than being widened until it permits both"; the answer is that
it cannot distinguish them, and that is the correct design. So shape 1 costs a
real guard, and it also couples derivation to embedder availability: a repo
indexed while the LAN Ollama is down would either fail its derivation or mint
entities the retry never comes back for.

A fourth candidate the brief did not name is worth recording because it looks
attractive and is worthless. The deriver *could* read
`entity_embedding_cache__<slug>` (a plain DB read, no model call, no guard
violation) and probe ANN on a cache hit — closing both orderings with no job at
all. It fails on the only case that matters: the cache is keyed by
`name_lower`, so a repo minting `postgres` finds nothing when the corpus has
only embedded `postgresql`. Every case a cache hit covers is a case the exact
`(name, entity_type)` upsert already handled. Rejected on inspection, no code
written.

### Shape 3 — schedule the existing back-fill — changes behaviour for every entity

`ReembedService.list_obsolete_entities` / `reembed_entities` do find and embed
repo-minted entities: the anti-join is
`entities e WHERE NOT EXISTS (SELECT 1 FROM entity_embeddings__<fp> ee WHERE ee.entity_id = e.id)`
and a repo-minted row satisfies it. But `reembed_entities` is an unbounded
`while True` drain over the **whole corpus**, holding a `ReembedLockSet`
category and broadcasting `pipeline.reembed_batch.progress` to the UI. After an
embedder rotation *every* entity is missing, so scheduling it means a cron that
silently re-embeds the entire entity corpus and paints an operator progress bar
nobody opened — for an install that may be mid-decision about which embedder it
wants. That is the behaviour change the brief warned about, and it is not
narrow: the operator route (`app/api/routes/reembed.py`) exists precisely so
that decision is taken deliberately.

**What happens to the existing route: nothing.** It is untouched and remains the
whole-corpus repair path. The new job takes a strictly smaller set that the
route also covers, so an operator re-embed run at any time subsumes the job's
work and neither can corrupt the other's — both are idempotent upserts keyed
`(entity_id, fingerprint)`.

### Why the new job duplicates less than it looks like it does

The duplication cost the brief flags is real but it is one `LEFT JOIN`, not a
mechanism. The embed-and-write loop is *not* shared with `reembed.py`, and
deliberately: that loop drains to exhaustion, asserts the produced fingerprint
equals the requested one and fails the batch when they differ, and reports
progress to a websocket. A scheduled tick needs the opposite of each — a bounded
batch, a write that *follows* the rotation instead of refusing it, and no
broadcast. Parameterising the operator flow with a scope flag would have made
its broadcast contract lie (`entities: 200 of 5000` when it only ever intended
the repo ones). What is reused is the idiom and the primitives:
`child_table`, `embedder_registry.register`, `resolve_read_fingerprint`, and the
structure of `app/services/relation_embeddings.py` (T2.49), which is the exact
same "Tier-C job embeds rows missing a vector under the active fingerprint"
shape one artefact over.

**Scope predicate:** `COALESCE(cardinality(e.repo_ids), 0) > 0`. That is a
principled boundary rather than an arbitrary narrowing — repo-minted rows were
the only rows in `entities` with *no writer at all*. Memory-minted entities are
written by Phase 5 and repaired by the operator route; an entity asserted by
both already has a vector, so the anti-join skips it.

## 2. The timing window, stated plainly

**Closed:** repository indexed → job tick → memory ingested. The vector is in
`entity_embeddings__<slug>` before Phase 4 probes, so `postgresql` canonicalizes
onto the repo-minted `postgres` at 0.974 and one node carries both `memory_ids`
and `repo_ids`. The window is bounded by the cron period (one hour) plus
`min_interval_seconds`.

**Open, and not closed by any embedding:** memory ingested → repository indexed.
Phase 4 dedups at write time and nothing re-runs it. The deriver's own write
(`assert_from_repo`) is an exact-key upsert with no ANN probe, so it mints
`postgres` beside the existing `postgresql`; the job then embeds it and the
corpus ends with two embedded, distinct nodes. This is the order an existing
install produces the first time it indexes a repository, so it is not a corner
case — it is the catch-up case.

**What would close it:** a retroactive entity-merge pass. That is a different
mechanism from an embedding back-fill: merging two `entities` rows means unioning
`memory_ids`/`repo_ids`, re-pointing every `entity_relations` endpoint through
the unique `(source, target, rel_type)` triple, recomputing the lowercase
`technologies` denorm on every memory that named the loser, and journalling it —
against a subsystem whose own doctrine (doc 06 §5) is that *a false merge is
strictly worse than a missed one and cannot be undone by re-extraction*. I
declined to build it inside this task. **This is a Tier-2 amendment candidate for
the next scheduling pass: no task owns the merge pass today.** It is recorded in
the epic amendment log and in the task text so the next reader meets the
boundary rather than assuming anchoring is now symmetric.

The limitation is asserted, not merely described:
`test_a_repo_indexed_after_the_memory_still_leaves_two_nodes` drives that exact
order and pins the two-node outcome, so a future merge pass will turn a red test
into a decision rather than landing unnoticed.

## 3. Invariant 2 and the mid-run rotation

Every table is reached through `child_table(PARENT_TABLE | CACHE_PARENT_TABLE,
fingerprint)`; no statement names a `__<slug>` child, asserted by
`test_every_child_table_is_reached_through_the_parent_constant`. Nothing joins
across fingerprints — each fingerprint's rows are in a different table, so a
cross-fingerprint comparison is unreachable rather than filtered.

The rotation exposure the brief asked about is handled the way
`relation_embeddings` handles it, and the discipline is worth stating exactly:

- **Candidate selection** keys on `resolve_read_fingerprint`, never
  `llm_fingerprint()`. A phantom key (the `|0` sentinel, or a `dimensions` that
  contradicts the width the model emits — T2.68, T2.83) would make every repo
  entity look permanently unembedded: re-embedded every run, into a table Phase 4
  never probes, reporting a healthy count forever.
  `test_the_module_never_calls_llm_fingerprint` pins it.
- **The write** goes to the partition of the fingerprint the embedder
  *returned*, after `_ensure_partition` registers it. So an embedder that
  rotated between the selection query and the write lands its vectors in the new
  partition rather than mixing two geometries inside the old one — the same
  re-resolve Phase 3 performs when the fingerprint moves under it mid-batch. A
  row selected under the old key and written under the new one was missing under
  the new key too, and the write is an idempotent upsert, so nothing is lost.

`_register_fingerprint`'s equivalent (`_ensure_partition`) runs before any insert
into a partition, on both the resolve path and the write path.

## 8. What the plan got wrong

- The task text's framing of shape 1 as a doctrinal preference understated it;
  the guard leaves no seam, which turns the choice from a judgement into a
  constraint. Recorded in the task text and the amendment log.
- The brief's suggestion that a back-fill's window could be closed by "letting
  the next re-derivation reconcile" does not hold as written: re-derivation
  re-runs the same exact-key upsert and reconciles nothing. Only a merge pass
  closes it.
- Nothing else. The brief's three Done-when clauses were reachable as stated, the
  lane boundaries held, and no design doc had to be contradicted.
