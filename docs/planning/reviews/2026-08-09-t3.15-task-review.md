## Findings

### Important

- **I-1 — The no-auto-capture test is a tripwire for honest mistakes, not a guard of the property, and it skips the one alias-proof check available.** `extension/test/no-auto-capture.test.js:31-44` (literal-string trigger scan), `:69-81` (manifest arm), `:83-98` (gesture arm).
  *Proven, not argued:* mutation M-A — an `onInstalled`-driven `postCapture` of content no human selected — **passes all four scans** (`onInstalled` is not a banned trigger; `postCapture` in `background.js` is allowlisted by the third test; no manifest change needed). Mutation M-B — `globalThis["set"+"Interval"]` — also passes.
  *Shapes it catches:* the twelve literal API strings in any `src/*.js` (including `options.js`); a `content_scripts` block; a chat-host `host_permissions` entry; `postCapture(` appearing outside `background.js`/`capture.js`.
  *Shapes it does not:* any unlisted event source (`onInstalled`, `onStartup`, `chrome.storage.onChanged`, `chrome.runtime.onMessage`/`onMessageExternal`); computed/aliased API names; a raw `fetch` to the door instead of `postCapture`; anything in the manifest's **`permissions` array** — which today carries `scripting` and `activeTab` (T3.26 review M-7, still unfixed), the exact grants the M-7 note names as serving the auto-scrape workaround. The manifest arm calls itself "the sharpest bundle-level check available" while reading the two manifest fields that are clean and not the one that isn't.
  *Why it matters:* the done-when's value is exactly the test's reach, and the reach is "today's code contains none of twelve strings", not "no automatic capture path exists". The cheapest real strengthening is capability-level, which string aliasing cannot dodge: assert `manifest.permissions` ⊆ `{contextMenus, storage}` (dropping the unused `scripting`, and `activeTab` if `tab.title` is surrendered or justified). A denylist of API strings guards less than an allowlist of granted capabilities, because Chrome enforces the latter at runtime.
  Also minor within this file: the gesture assertion (`background.includes("contextMenus.onClicked")`) is substring-satisfiable by a comment.

- **I-2 — Turn labelling is wrong in the dominant production shape, and the lane was on notice.** `extension/src/adapters.js:41-59` splits on `/\r?\n/`. The T3.26 review's **M-8** (committed 21:23, 86 minutes before this commit) recorded that Chromium's `contextMenus` `info.selectionText` collapses newlines/whitespace — so a real multi-turn selection on ChatGPT/Claude/Gemini arrives as **one line**. Driver result on that shape: `"You: does it fsync? Claude: yes, …"` → `turn_roles: ["user"]` — the assistant's words shipped to the vault under a human attribution, which is precisely the harm the commit message declares worse than not labelling. Neither the code, the tests (which feed `\n` directly to `splitTurns`), nor the commit acknowledges M-8. Secondary false positives from the `[:—-]` separator set, driver-verified: `"AI-assisted coding…"` → `assistant` turn; `"Me-first APIs…"` → `user` turn; a quoted example dialogue inside one assistant message → three fabricated turns. Impact is bounded to `metadata.turn_roles` (content ships unchanged, turn text never leaves the client), but roles **are** the adapters' sole per-surface deliverable beyond a name — the feature's central output is unreliable exactly where it runs. Caveat, stated plainly: no browser exists in this environment, so the selectionText collapse is re-asserted from known Chromium behaviour (as M-8 also was), not re-measured; an empirical check in a real Chrome is the first fix-round step, and if it holds, either labelling must work on the single-line shape or `turn_roles` should not ship.

- **I-3 — The module documents an invariant the code does not hold, and the commit repeats it.** `extension/src/adapters.js:35-37`: "a line that carries no recognised marker is kept verbatim as an `unknown` turn rather than being guessed onto the previous speaker" — directly contradicted by `:52-53`, where an unmarked line **is appended to the previous speaker's turn**. Only an unmarked *opening* line becomes `unknown`. The commit message makes the same general claim. The continuation heuristic itself is defensible; the comment on the exact invariant the module exists to protect is false, and the next maintainer (or test author) will trust it. One-line comment fix, but it is a claim-honesty defect in a repo that treats those as first-class.

### Minor

- **M-1 — `remember` loses updates under concurrent MV3 wakeups.** `extension/src/dedupe.js:63-72` is a plain read-modify-write; driver-verified: two concurrent `remember` calls kept 1 of 2 digests. The same window lets two concurrent same-content captures both pass `alreadyCaptured` and both post. Contrast `origin.js`, which the same epic gave a settle re-read for exactly this race. Harm is bounded — one origin, so never counterfeit corroboration; just a duplicate row later — and the trigger (two captures in flight at once) is rare for a context-menu gesture. Record and triage.
- **M-2 — The two backend "no new pipeline" scans are honest about being narrow, and could be narrower than intended.** `backend/tests/test_browser_capture.py:213-222`: `Path("app")` is cwd-relative — run with a cwd other than `backend/` the rglob is empty and both scans **pass vacuously**; an `assert app_dir.is_dir()` guard costs one line. The constant scan (`:224-237`) covers `app/api` only — a `source == "browser-extension"` branch in `app/services` passes. The filename scan's token list (`browser|extension|scrape`) is trivially satisfiable by any other name; the docstring says so itself. Adequate for the honest mistake, as designed.
- **M-3 — The payload mirror's drift is silent by construction.** `backend/tests/test_browser_capture.py:93-114` matches the client today (verified field-for-field, including the merged adapter metadata). If the extension later adds a field the server rejects, no test on either side reddens — the mirror only catches the server dropping acceptance of a field it already sends. Acknowledged in the docstring; recorded so the eventual e2e owner knows the seam. The mirror also omits the `X-Darkmem-Client` header the real client sends (harmless today: explicit `source` outranks it).

### Adjacent (not this task's defect — controller to adjudicate)

- **A-1 — Doc 15 §4's dedup premise is false against the shipped backend.** It claims "the pipeline's content **fingerprint** dedups identical content (doc 05 §5)" as the server-side guarantee the extension's set merely supplements. Doc 05 §5's fingerprint is the **embedder-partition** fingerprint, and the pipeline's only dedup is Phase-4 *entity* dedup — no ingest-time memory-content dedup exists anywhere in `pipeline.py`/`buffer_flush.py` (`find_duplicates` is an on-demand probe, not a suppressor). The extension's seen-set is therefore the **only** content dedup on this path, which raises the stakes of M-1 and the 500-entry bound. Credit where due: `dedupe.js`'s own header is honest ("hand retrieval two rows where the vault holds one claim") and does not repeat the doc's false premise. The doc sentence should be corrected or the server-side guard built; either is outside T3.15's scope.

## Bottom line

The shipped code is clean: human-gesture-only, selection-only, ordinary door, honest failure surfacing, and the dedup module is more carefully reasoned than most. What needs fixing before this feeds a gate claim: the no-auto-capture test should assert the manifest's `permissions` allowlist (the only alias-proof arm available, and the one whose current contents its sibling review already flagged), the turn-labelling mechanism must be squared with the platform's actual selection shape or `turn_roles` withheld, and the false invariant comment corrected. Minors recorded for final-review triage.
