### Important

**I-1 — A transiently disputed code-born fact loses its rung permanently; no machine
path restores it.** `verification_ladder.py:546` — recovery out of `disputed` lands
`settled("corroborated" if k >= n else "candidate", "recover")`, and a born fact's k=1
never meets n. Driven end to end (not argued from ordering): scanned contradiction
verdict → `disputed`; counterpart expires (guard lapse, an affirmative clean) →
`recover` → **`candidate`**; then `run_code_lift` (refuses to re-grade an existing row,
by design and by its own test) + another recompute → still `candidate`, forever — while
the code source row is live and the repository still asserts the triple, i.e. exactly
the evidence that justified the birth. The exception branch fires only when
`current_status == "corroborated"`, so a fact knocked off the rung can never re-enter
it on code evidence alone (a later origin of a second kind still promotes it at n=2 —
the ordinary diversity gate). Contrast: an ordinary corroborated fact recovering at
k ≥ n returns to `corroborated`. This path is reachable today — `contradiction_scan`
(T2.11) is live and its verdict arm is how I drove it; the deterministic arm cannot fire
on `DEPENDS_ON`/`USES`. Under-claiming direction, so no gate risk — but it contradicts
doc 10 §6's stated semantics, the report does not name it ("holds a rung, never grants
one" covers the candidate-climb case, not this one), and a judge false positive that
later lapses converts a permanent-evidence fact into a permanent under-label. Fix is
one consult of `parse_is_the_verification` in the recovery branch — or a controller
ruling that post-dispute conservatism is intended, recorded where the branch is.

**I-2 — The honesty suite contains no behavioural pin for the writer it admitted.**
Mutation drill: `BORN_CORROBORATED = "confirmed"` (`knowledge_triples.py:64`) — the
**entire honesty file passes, 21/21**, while `open_born_corroborated` mints

The scan half is genuine — I ran `_confirmed_writers` directly and it does detect

## What I tried that did NOT break

- **The veto beats the exception, end to end.** A `contradiction_scanned` verdict
  against a code-born fact, adjudicated by the real detectors inside `recompute_fact`
  (no override): the fact flips to `disputed`, `review_state` opens. The branch's
  placement below the veto is real behaviour, not just ordering on the page.
- **G-C sees nothing.** After birth plus two recompute ticks, **zero** `verified`
  events exist for a born fact (driven, counted). `set_verification_status` journals
  only on `changed or contradiction_blocked or supersession_blocked`; the exception
  hold is none of those. `benchlib.promotion_metrics` reads `events` alone — the
  promotion rate's denominator is `outcome IN ('promote','dispute')` and the
  false-promotion audit anchors on journal rows — so born facts enter neither the rate
  nor the audit. (Flip side for the controller's file, not a defect: once the promotion
  record is minted, these rows light `corroborated` on doc 10 §6's argument alone —
  G-C never measured or audited them. That is exactly what "the parse is the
  verification" claims; stating it here so the gate's evidence run inherits it knowingly.)
- **No permanent pin via hysteresis or the supersession hold.** The exception hold is a
  non-demote, so it clears any pending demotion marker rather than freezing one; the
  supersession blocker only withholds promotions and is not consulted on this branch.
  A code fact whose code row is withdrawn while a memory source survives demotes
  normally (predicate reads stored rows, which the sweep deletes); an invalidated fact
  is still recomputed (`_still_live` gates on `expired_at` only) and walks down the
  ladder off the `sources_changed` event its own withdrawal emits.
- **No smuggled status.** `open_born_corroborated(**fields)` forwards to `insert_open`,
  whose keyword-only signature refuses `verification_status`; the UPDATE binds the
  module constant. The honesty scan detects the writer, so the allowlist entry is
  earned, not decorative.
- **The 100-round loop is real** (1.52s of measured work, in-loop Layer-1 assertions),
  the floor and benchlib numbers reproduce exactly, the tree is one alembic revision,
  and the `_fact_for` strictness fix holds — I searched the suite for the same
  newest-row shape elsewhere and found none over `knowledge_triples` fact identity (the
  `ORDER BY created_at DESC` hits are latest-event and watermark reads, which are

- **The recompute drain handles the code payload** — it keys on `payload["fact_id"]`,
  which both the memory (`memory_id`) and code (`repo_id`) event shapes carry.
