## Done-when, one by one

**1. Handshake verification runs and reports the concrete failure — ⚠️ partial.**
The sequence runs and *succeeds* against the real server app: `verify_handshake` via
`_rpc_caller` returned 26 tools in the in-process probe, so the green path is real, not
assumed. HTTP-status failures are mapped concretely (421/404/401/403/other/unreachable, all
behavior-tested). But two failure classes are not reported concretely — see I3 (JSON-RPC
errors silently dropped, misdiagnosed as "not serving darkmem's MCP surface") and I4
(DB-unreachable → raw traceback).

**2. Foreign-Host 421 reported as "extend `MCP_ALLOWED_HOSTS`", never worked around — ✅.**
`diagnose(421)` (client_connect.py:230) names the server-side fix, names the protection as
working, and never suggests disabling it. Nothing in the code works around the check: the
`--host` help text explicitly refuses to add the allowlist entry. Behavior tests plus a scan
back it (the scan's reach is overstated — I5 — but the *behavior* clause is met).

**3. Re-running is idempotent, no duplicate config entries — ❌ on TOML.**
Idempotent only against the writer's own canonical output (which the tests cover). Against
hand-maintained files — the exact case the module's docstring claims to protect — it
duplicates the table and renders the entire config unparseable (C1), and deletes user
comments (I1). The JSON path is genuinely idempotent and preserves foreign entries.

**Scope creep:** none. `darkmem onboard` (detect-all) and `--inject` from doc 15 §5 were not
built; neither is a done-when, and the task is terminal-by-design. The scan test is extra
hardening, not creep.

## Findings

### Critical

**C1 — `merge_toml_config` corrupts valid hand-maintained configs; the CLI then reports
"connected".** `client_connect.py:164-184`. The section-replace regex
(`^\[mcp_servers\.darkmem\]\n…`) matches only the writer's own canonical bytes. Eight inputs
that are **valid TOML today** — header with a trailing comment (`[mcp_servers.darkmem] # managed`),
trailing space after `]`, CRLF line endings, quoted key (`[mcp_servers."darkmem"]`), inline
table (`darkmem = { url = … }`), dotted key, array-of-tables, spaces inside brackets
(`[ mcp_servers.darkmem ]`) — all miss the regex, so the merge **appends a second
`[mcp_servers.darkmem]` table**, and `tomllib` rejects the result:
`Cannot declare ('mcp_servers', 'darkmem') twice`. Codex then fails to parse its **entire**
config, losing every server, not just ours. A multi-line array inside our table corrupts
differently: the per-line `(?!\[)` guard stops consuming at an interior line starting with
`[`, leaving orphan fragments (`["nested"],` / `]`) behind the replacement — also invalid
TOML. All nine reproduced by driver; every merged output failed `tomllib.loads`.

Why Critical rather than Important: the failure is **silent with success reported**. The
handshake tests the URL directly, never the tool's config file, so after corrupting
`~/.codex/config.toml` the CLI prints `connected: N tools available`. The commit message's
own bar — "A malformed existing config raises instead of being replaced — the one case where
'just make it work' destroys data the tool does not own" — is enforced on the JSON path and
absent on the TOML path, where it is not even a malformed *input* case: valid input produces
invalid output. Cheap, in-spirit fix: validate the merged result with `tomllib.loads` (Python
ships the reader) and refuse on failure, exactly as the JSON path refuses.

### Important

**I1 — The TOML merge deletes user content adjacent to our table.**
`client_connect.py:164-165`. `(?:(?!\[).*\n?)*` consumes every non-header line after our
table — including blank lines and comments that belong to the *next* section or to the end
of the file — and the substitution discards them. Reproduced: a
`# ---- important user note ----` line between `[mcp_servers.darkmem]` and
`[mcp_servers.other]` is deleted on every merge, as is a trailing comment at EOF, and the
separating blank line is collapsed. Silent data loss in a hand-maintained file; directly
contradicts the docstring's "leaves the rest byte-identical".

**I2 — The CLI entry point is untested, and its documented invocation crashes on import.**
`scripts/connect.py:8-11` says `Run from backend/: python scripts/connect.py claude-code`.
That exact command dies: `ModuleNotFoundError: No module named 'app'` (script-style execution
puts `backend/scripts` on `sys.path`, not `backend/`; sibling scripts solve this with
`sys.path.insert`). `python -m scripts.connect` happens to work via namespace packages, but
no doc says so. No test imports `scripts/connect.py` at all — argument parsing, file I/O,
`_rpc_caller`, exit codes, and adapter resolution have zero coverage — so the spec's Verify
command passes while the command a human actually types is broken as documented.

**I3 — The handshake's middle step is a malformed message, and JSON-RPC errors are silently
dropped.** `scripts/connect.py:310-321`, `client_connect.py:209`. `_rpc_caller` stamps
`"id": 1` on **every** call, including `notifications/initialized` — per MCP, a notification
MUST NOT carry an id. The real server rejects it with JSON-RPC `-32602 Invalid request
parameters` over HTTP 200 (reproduced in-process); the notification is never delivered.
The handshake still succeeds only because darkmem mounts stateless (`initialized` is
optional there) and because of the second half of this finding: on HTTP 200,
`response.json().get("result", {})` discards the `error` member entirely. Consequences,
both demonstrated: a JSON-RPC error on `initialize` passes the `isinstance(dict)` check as
`{}` and the sequence proceeds; a transcript of pure JSON-RPC errors is diagnosed as
"listed no tools … not serving darkmem's MCP surface" — a wrong, fixed diagnosis where
done-when 1 requires the concrete failure (the error's own message, e.g. a protocol-version
mismatch, is what got dropped). Also scope-limiting: with no `Mcp-Session-Id` handling and
no SSE parsing, the verifier works only against stateless JSON-mode MCP servers — true of
darkmem today, silently wrong against anything else, including darkmem if the mount flags
ever change.

**I4 — Client-machine reality: no reachable darkmem Postgres → raw traceback.**
`scripts/connect.py:339-341`. `resolve_adapter` needs a live DB session; with the DB
unreachable the CLI dies in an unhandled `OSError` stack dump before any diagnosis.
Doc 15 §5 bills this as the *client-side* onboarding command; on a machine that is not the
server host, this is the first thing that happens. Registry-in-DB is T3.11's design
("adapter registry (config)") and plan-mandated — but the unhandled failure shape is
T3.13's, and only `UnknownTool` is caught. (`DEFAULT_ADAPTERS` exists in code; a
defaults-fallback or a caught, diagnosed error are both available.)

**I5 — The invariant-20 scan is a guard for one phrasing family in one tree — narrower than
the report claims.** `tests/test_connect_cli.py:567-588`. Measured, not read:
- **Reach:** it scans `Path("app").rglob("*.py")` only — not `backend/scripts/` (where
  `connect.py`, the CLI's own user-visible printer, lives), not the frontend, not docs.
  The commit's claim "the CLI cannot suggest disabling it — a scan over `app/` fails the
  build" is overstated: the CLI's entry file is outside the scanned tree. An offender
  planted in `scripts/` passes today.
- **Regex:** verified catches: "disable the Host allowlist", "turn off DNS-rebinding
  protection", "bypass the host check". Verified misses: **"disabling the allowlist"**
  (gerund — `disable` is not a prefix of `disabling`), "turn the allowlist off" (split
  verb), "set MCP_ALLOWED_HOSTS='*'" (the concrete disable knob, no verb), "remove the
  Host allowlist", and any wrapped line (per-line scan).
- It **can** fail: an injected canonical offender under `app/` turned it red (probe removed
  after). So: a real but narrow tripwire, not the general guarantee the commit message
  describes. The *behavioral* clause of done-when 2 is independently met.

### Minor

**M1 — The scan is cwd-dependent and vacuously passes from the repo root.** Verified:
`pytest backend/tests/test_connect_cli.py::test_no_module_suggests…` run from the repo root
passes because `Path("app")` matches nothing there. Anchor to `Path(__file__).parents[1] / "app"`.

**M2 — Diagnosis gaps** (`client_connect.py:221-252`): no redirect branch (a 307/308 —
e.g. a proxy bouncing http→https, or `/mcp` without slash, verified 307 — reads as the
generic "answered 307"); a post-connect timeout reports "could not reach the server … check
it is running" when the server is reachable but slow; `_url_for` hardcodes `http://`, so an
https endpoint is unreachable by construction (doc 18 owns exposed auth, but the scheme gap
is silent).

**M3 — The 421 message under a loopback `--host` half-contradicts itself:** it instructs
adding e.g. `localhost:8000` to `MCP_ALLOWED_HOSTS` (a no-op — localhost is always allowed)
and then says loopback needs no entry. The closing sentence rescues it; still confusing in
the proxy-rewrote-Host case. Never suggests disabling — invariant 20 holds.

**M4 — `merge_json_config` re-serializes the whole file** (`indent=2`), churning a
hand-formatted file's style. Content and key order survive; asymmetric with the TOML
writer's byte-preservation promise.

**M5 — Unescaped interpolation of `url`:** into a TOML basic string (a `"` or `\` in
`--host` yields invalid TOML) and into `re.sub`'s replacement string (backslash group
references un-escaped).

**M6 — Relative registry paths resolve against the CLI's cwd, which the docstring pins to
darkmem's own `backend/`:** as documented, `connect claude-code` writes
`backend/.mcp.json` inside the darkmem repo, not the user's project; `cline`'s registry
value `cline_mcp_settings.json` can never reach Cline's real settings path (a VS Code
globalStorage file). The path values are T3.11's data; the cwd anchoring and the "run from
backend/" docstring are T3.13's.

**M7 — File-handling edges:** non-UTF8 config → uncaught `UnicodeDecodeError`; the write is
not atomic (no temp-and-rename), so an interrupt mid-write truncates the user's config.

### ⚠️ Cannot verify from diff

Whether current **Codex** accepts a bare `url =` key under `[mcp_servers.*]` for a
streamable-HTTP server, and whether **Cline** accepts `{"type": "http", "url": …}` (its
remote-server schema has historically wanted `streamableHttp`/`transportType`). Settling
this needs the tools themselves or their current docs; the controller may hold T3.11's
registry context.

## Q5 — the T3.09 boundary: sound

`client_connect.py` contains **no filesystem I/O at all** — the merge functions are
string→string, and every read/write lives in `scripts/connect.py`, outside `app/`. Nothing
under `backend/app` imports `client_connect` (verified by grep; importers are the script and
the test). So even an HTTP route importing the module could not write a client filesystem;
the commit's reconciliation ("the *server* never writes the *client's* filesystem; this is a
client-side CLI") is stated in the module and holds structurally, not just by promise.
