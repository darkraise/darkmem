# T2.98 — the same-endpoint arm has an index for half of itself

**Lane:** `feat/e2-lane-cf` (worktree `.worktrees/e2-lane-cf`)
**Databases:** `darkmem_test_cf` / `darkmem_bench_cf`
**Status:** DONE

## The fix

`backend/migrations/versions/0001_baseline.py`, regenerated in place. Added, right
after the existing subject-side index:

```sql
CREATE INDEX ix_knowledge_triples_live_object
ON knowledge_triples (object_name, rel_type, subject_name)
WHERE expired_at IS NULL
```

`_SAME_ENDPOINT_SQL` in `app/services/contradiction_scan.py` was not touched — its
semantics, its `LIMIT`-driven selection order, and its comment are all as they were.
Only the schema changed.

### Column-order argument

The subject index, `ix_knowledge_triples_live (subject_name, rel_type,
object_name)`, leads with `subject_name` specifically so it also serves a
subject+predicate probe, not just a bare subject lookup. The object index mirrors
that shape — `(object_name, rel_type, subject_name)` — rather than staying
`object_name`-only, because the same widening argument applies on the object side
for a real, reachable query: `GET /api/v1/knowledge/facts` (`facts_read.list_facts`,
backed by `KnowledgeTripleRepository.get_live` / `list_live`) accepts `object_name`
and `rel_type` as independent optional filters with no `subject_name` required. A
caller filtering by `rel_type` + `object_name` alone — the object-side analogue of
the subject+predicate case the subject index already serves — needs `object_name`
leading for an equality-then-equality index scan; an `object_name`-only index would
still serve that query via a residual filter on `rel_type`, but not as tightly, and
would leave the parallel with the subject index's own justification broken for no
saved cost (a two-column index isn't meaningfully cheaper to maintain than a
three-column one here, and both are equally partial). `_SAME_ENDPOINT_SQL` itself
only ever binds `object_name` bare — no `rel_type` in that arm's predicate — so the
mirror's extra columns are for the general reader, not required for this task's own
query; the leading column is what `_SAME_ENDPOINT_SQL` needs, and that is satisfied
either way.

## The plan got something the brief's framing didn't

The brief (and doc 08 §5.3) frame the object half as degrading to "a scan" of the
heap. **The measured BEFORE plan is not a heap Seq Scan.** Postgres already had a
cheaper fallback available: with no index on `object_name`, it built the `BitmapOr`
by running a *full, boundary-less scan of the existing three-column subject index*
for the object-side disjunct (`Index Cond: (object_name = ...)` with no condition
on `subject_name` or `rel_type` — visible in the BEFORE plans above as
`cost=0.00..26.16`, `Buffers: shared hit=1046`, i.e. essentially the whole index).
That is cheaper than a heap scan because the index's three text columns are
narrower than the full row, but it is still `O(live triples)` work, not
`O(log n + result size)` — a full traversal of the index rather than a genuine
lookup. So the doc's "degrades to a scan" claim holds in substance (linear work
proportional to the live set, not a lookup) but, on this specific measurement, not
in the literal mechanism I expected going in (a heap Seq Scan); it was a scan of
the *other* index, not the table. I did not reshape the query or disable planner
settings to manufacture a Seq Scan for the report — the two plans above are the
real, unmodified ones the planner produced.

**Correction (fix round 1, F1).** The claim that followed — *"I looked for whether
a larger table would eventually force a literal Seq Scan and concluded it would
not: the existing composite index will always be narrower than the heap under
Postgres's cost model, so the full-index-scan fallback wins over a heap scan at
any scale"* — is wrong, and it is wrong for a reason this report should have
caught: the measurement above was taken on a table freshly bulk-seeded with **no
`ANALYZE`** run before measuring, so the `cost=0.00..26.16` figure that grounded
the "always narrower" reasoning was priced off stale/default planner statistics,
not real ones (see the F3 correction above). Two independent measurements against
`darkmem_bench_cf`, own driver, own seed, fresh `ANALYZE` after seeding, correct
this:

1. **A skewed probe forces a literal heap Seq Scan, at the exact table scale this
   report already used.** 126,000 rows, one project, `object_name='popular-object'`
   carrying 6,300 of them (5% of the table) — the object index dropped, everything
   else identical to `_SAME_ENDPOINT_SQL`'s real bound parameters:

   ```
   Limit  (cost=11883.45..11906.78 rows=200 width=117) (actual time=12.016..31.455 rows=200 loops=1)
     Buffers: shared hit=986 read=8827
     ->  Gather Merge  (cost=11883.45..12479.66 rows=5110 width=117) (actual time=12.015..31.442 rows=200 loops=1)
           Workers Planned: 2

           ->  Sort  (cost=10883.43..10889.81 rows=2555 width=117) (actual time=9.085..9.088 rows=104 loops=3)

                       Rows Removed by Filter: 39900

   ```

   A literal `Parallel Seq Scan` on the heap — not a scan of the subject index.
   Restoring the object index on the same table turns this back into the expected
   BitmapOr (`cost=9581.96` total, `Buffers: shared hit=3 read=218`, execution time
   2.4 ms) — the shipped fix handles this probe fine; the defect was in the missing
   index, confirmed directly rather than argued from a stale-stats plan.

2. **This is not narrowly about "common" values — under fresh statistics and
   Postgres's default parallel-query settings, the same literal Seq Scan shows up
   at every frequency and table scale probed, including near-unique ones**, which
   directly overturns the "always narrower … at any scale" claim rather than just
   qualifying it. A frequency sweep (0.03%, 0.1%, 1%, 5%, 20% of the table) at two
   table sizes (4,000 and 120,000 rows), object index dropped, fresh `ANALYZE`,
   parallel query at its default settings: every single point chose a
   `(Parallel) Seq Scan`, down to a single matching row in 4,000 (`cost=185.01`,
   the cheapest point measured, still a Seq Scan) and a single row in 120,000
   (`cost=5191.32`). The full-index-traversal BitmapOr this report's original
   measurement showed is not merely underpriced by stale statistics — Postgres's
   planner does not choose it *at all* at these scales once statistics are real,
   because a `Parallel Seq Scan` is cheaper across the whole frequency range tested,
   not only at the high end.
3. **The full-index-traversal plan is real, not a fiction of the stale numbers —
   it is what Postgres falls back to when it cannot spread the scan over parallel
   workers.** With `max_parallel_workers_per_gather = 0` and the same near-unique
   probe (120,000 rows, 40 matches), fresh `ANALYZE`, the planner reproduces this
   report's original BEFORE shape almost exactly — a `BitmapOr` whose object arm is
   a full, boundary-less traversal of `ix_knowledge_triples_live`
   (`Index Cond: (object_name = 'probe-object'::text)`, `Buffers: shared hit=1079`,
   matching the ~1046-1057 buffer counts measured earlier) — but at its honest
   cost, `cost=0.00..5240.72`, not 26.16. So the mechanism is: the full-index-scan
   fallback is a real plan Postgres's optimizer considers, it is just not what wins
   once statistics are accurate and parallel workers are available (the default),
   because the Seq Scan's own parallel discount undercuts it even at a selectivity
   where the fallback's *serial* cost would otherwise be competitive.

**Corrected conclusion.** Doc 08 §5.3's "degrades to a scan" wording is more right
than this report originally credited it — not just in substance but, under real
statistics and Postgres's default configuration, in the literal mechanism too: a
missing object index turns `_SAME_ENDPOINT_SQL` into a genuine heap Seq Scan, and
that held at every frequency and table scale measured, not only for a
disproportionately common value. This makes the shipped fix's justification
stronger than the original paragraph argued, not weaker — the index in
`0001_baseline.py` is what keeps this query off the heap-scan path.

## Scope discipline

`_SAME_ENDPOINT_SQL`'s semantics, its `LIMIT`, and its selection order are
untouched — no `UNION ALL` rewrite, no relaxation of `_OVERLAP_PREDICATE`. No other
index in the baseline was touched. Nothing about the deriver, `repo_ids[]`, or
`fact_sources` was touched. `docs/planning/baseline-schema-inventory.md` was not
updated for this index — checked against precedent first: T2.11's own
`ix_knowledge_triples_fact_trgm` (landed in the same file, same table) has no row
in that inventory either, so a T2.98-only row would be inconsistent with how the
last index added to this table was actually tracked, and the brief does not ask
for it. Flagging this as a finding rather than silently deciding it: the inventory
doc says elsewhere it is meant to be the authoritative object list, and two Tier-C
indexes landing without an entry each is a gap worth someone reconciling
deliberately rather than two lanes both guessing the same way independently.
