# T2.98 — the same-endpoint arm has an index for half of itself

**Lane:** `feat/e2-lane-cf` (worktree `.worktrees/e2-lane-cf`)
**Databases:** `darkmem_test_cf` / `darkmem_bench_cf`
**Status:** DONE

## The fix

`backend/migrations/versions/0001_baseline.py`, regenerated in place. Added, right
after the existing subject-side index:

```sql
CREATE INDEX ix_knowledge_triples_live_object
ON knowledge_triples (object_name, rel_type, subject_name)
WHERE expired_at IS NULL
```

`_SAME_ENDPOINT_SQL` in `app/services/contradiction_scan.py` was not touched — its
semantics, its `LIMIT`-driven selection order, and its comment are all as they were.
Only the schema changed.

### Column-order argument

The subject index, `ix_knowledge_triples_live (subject_name, rel_type,
object_name)`, leads with `subject_name` specifically so it also serves a
subject+predicate probe, not just a bare subject lookup. The object index mirrors
that shape — `(object_name, rel_type, subject_name)` — rather than staying
`object_name`-only, because the same widening argument applies on the object side
for a real, reachable query: `GET /api/v1/knowledge/facts` (`facts_read.list_facts`,
backed by `KnowledgeTripleRepository.get_live` / `list_live`) accepts `object_name`
and `rel_type` as independent optional filters with no `subject_name` required. A
caller filtering by `rel_type` + `object_name` alone — the object-side analogue of
the subject+predicate case the subject index already serves — needs `object_name`
leading for an equality-then-equality index scan; an `object_name`-only index would
still serve that query via a residual filter on `rel_type`, but not as tightly, and
would leave the parallel with the subject index's own justification broken for no
saved cost (a two-column index isn't meaningfully cheaper to maintain than a
three-column one here, and both are equally partial). `_SAME_ENDPOINT_SQL` itself
only ever binds `object_name` bare — no `rel_type` in that arm's predicate — so the
mirror's extra columns are for the general reader, not required for this task's own
query; the leading column is what `_SAME_ENDPOINT_SQL` needs, and that is satisfied
either way.

## The plan got something the brief's framing didn't

The brief (and doc 08 §5.3) frame the object half as degrading to "a scan" of the
heap. **The measured BEFORE plan is not a heap Seq Scan.** Postgres already had a
cheaper fallback available: with no index on `object_name`, it built the `BitmapOr`
by running a *full, boundary-less scan of the existing three-column subject index*
for the object-side disjunct (`Index Cond: (object_name = ...)` with no condition
on `subject_name` or `rel_type` — visible in the BEFORE plans above as
`cost=0.00..26.16`, `Buffers: shared hit=1046`, i.e. essentially the whole index).
That is cheaper than a heap scan because the index's three text columns are
narrower than the full row, but it is still `O(live triples)` work, not
`O(log n + result size)` — a full traversal of the index rather than a genuine
lookup. So the doc's "degrades to a scan" claim holds in substance (linear work
proportional to the live set, not a lookup) but not in the literal mechanism I
expected going in (a heap Seq Scan); it is a scan of the *other* index, not the
table. I looked for whether a larger table would eventually force a literal Seq
Scan and concluded it would not: the existing composite index will always be
narrower than the heap under Postgres's cost model, so the full-index-scan fallback
wins over a heap scan at any scale. I did not reshape the query or disable planner
settings to manufacture a Seq Scan for the report — the two plans above are the
real, unmodified ones the planner produced, which is what the brief's trap #2 asks
for even if the shape differs from doc 08 §5.3's exact words.

## Scope discipline

`_SAME_ENDPOINT_SQL`'s semantics, its `LIMIT`, and its selection order are
untouched — no `UNION ALL` rewrite, no relaxation of `_OVERLAP_PREDICATE`. No other
index in the baseline was touched. Nothing about the deriver, `repo_ids[]`, or
`fact_sources` was touched. `docs/planning/baseline-schema-inventory.md` was not
updated for this index — checked against precedent first: T2.11's own
`ix_knowledge_triples_fact_trgm` (landed in the same file, same table) has no row
in that inventory either, so a T2.98-only row would be inconsistent with how the
last index added to this table was actually tracked, and the brief does not ask
for it. Flagging this as a finding rather than silently deciding it: the inventory
doc says elsewhere it is meant to be the authoritative object list, and two Tier-C
indexes landing without an entry each is a gap worth someone reconciling
deliberately rather than two lanes both guessing the same way independently.
