## M1 — "the guard cannot distinguish an embed from an extraction"

**Verdict: fixed, report prose only.**

The reviewer's point stands: `tests/_reachability_scan.py:363`'s attribute
route matches bare attribute names (`chat_completion`, `embed_batch_chunked`,
...) textually, so it does distinguish an embed call from an extraction call
by name — it is not blind to the difference. What the original report
conflated was "the guard becomes unable to tell them apart" with "permitting
the embed strips the guard down to its weakest layer."

The report (`docs/planning/reviews/2026-08-07-t2.97-report.md`, §1) is
rewritten to say precisely what permitting shape 1 costs: dropping
`get_llm_orchestrator` and `LLMOrchestrator` from `_LLM_DISPATCH_ATTRS`, and
dropping `app.services.llm` from `_LLM_SURFACES`'s module route. Two of the
guard's three layers are gone at that point. What survives is the
attribute-name layer alone, and that layer is evadable — a computed
`getattr(client, 'chat' + '_completion')` never spells the forbidden name
literally and passes it — but it is not textually blind to the call the way
the original phrasing implied.

The "blocked" conclusion is unchanged: going from three independent layers to
one evadable one is still a real cost, and the report now says exactly that
instead of overstating it as literal indistinguishability.

## M2 — "the window is bounded by the cron period"

**Verdict: fixed, report prose only.**

The reviewer's point: that sentence bounds *duration* (how long a newly
indexed repository sits with unembedded entities) but reads as if it also
bounds *consequence* (that memories affected by the window eventually merge
once the tick lands). It does not. `assert_from_repo`
(`backend/app/repositories/graph.py:673-697`) is an exact-key upsert with no
ANN probe, and Phase 4 dedups once, at the memory's own write time. A memory
ingested after a repository is indexed but before that repository's entities
have had their anchoring tick finds no vector to probe against, mints its own
node, and that fork is permanent — the later tick embeds the repo-minted
entity but nothing re-runs Phase 4 for the memory that already forked. That
memory was never a delayed instance of the "closed" order; it fell into the
"open" (permanently forked) case at the moment it was written.

The report (§2) now states this explicitly: the cron-period bound describes
how long the *repository's own entities* take to become embeddable, not what
happens to any individual memory that lands inside that interval, and notes
the exposure lengthens by further ticks when a repo mints more than
`missing_batch` (200) entities in one run. The headline order statement
(repository indexed → job tick → memory ingested) already had the tick in
the right place, so nothing about the shipped behaviour or the pinned test
changes — only the sentence that could be misread as "the fork self-heals."

## M3 — no cross-type refusal case in the task's own suite

**Verdict: addressed — added the case.**

The property (a repo-minted `tool` must never merge onto a memory-minted
`concept` of a similar name) was already pinned over the same probe by
`tests/test_dedup_discriminator.py::test_same_name_across_types_dedups_separately`,
but for two memory-minted entities only — the anchoring suite itself had no
case proving the property holds when one side is repo-minted. The brief asked
for it in this task's own suite, and it was cheap to add: `code_deriver.py`'s
`_entity_type_for` runs an import name through the same override/normalize/
refine ladder extraction uses, so an import name outside `_TYPE_OVERRIDES`
(`app/services/extraction_clean.py:252`) gets the plain `tool` default —
exactly the asymmetry `test_same_name_across_types_dedups_separately` already
exploits with `PandasLib`/`Pandas`.

Added `test_a_type_mismatch_still_refuses_the_anchor` to
`backend/tests/test_repo_entity_anchoring.py`, following the same shape as
the existing `test_a_discriminating_token_still_refuses_the_anchor`:

- Repo derives `pandaslib` (import, no override → type `tool`) and the
  anchoring job embeds it.
- A memory extracts `pandas` as type `concept`, at the same 0.974 cosine the
  merging pair (`postgres`/`postgresql`) sits at — chosen deliberately high
  so a pass would prove the type constraint, not a similarity too low to
  matter.
- Asserts the spied probe ran scoped to `entity_type == "concept"` and that
  `match is None` — the `tool` row is never even read, because Phase 4 runs
  one ANN probe per unique `(name, entity_type)` pair (CLAUDE.md, Retrieval
  §Pipeline phase 4) and the query itself is type-constrained. No similarity
  score is checked here because none is computed: the SQL predicate excludes
  the row before any cosine distance is evaluated.
- Asserts both rows survive distinct: `("pandas", "concept", 1)`,
  `("pandaslib", "tool", 0)`.

Verified by running the suite: `11 passed, 1 warning in 6.22s`
(`tests/test_repo_entity_anchoring.py`, `TEST_DATABASE_URL` pointed at
`darkmem_test_cg`). Re-ran alongside `tests/test_code_deriver.py`:
`86 passed, 1 warning in 3.84s` combined.

I did not additionally drill this test (e.g. by widening the probe's type
scope) because it is a positive-property test of an already-drilled
mechanism — drill 1 in the original report/review already proved the
`names_distinct` gate is load-bearing at the same probe, and the
type-constraint itself is a SQL predicate with no branch to mutate inside
this module; the interesting failure mode (a query that dropped its
`entity_type` filter) lives in `PostgresGraphRepository.find_similar_entity`,
which is out of this task's lane and already covered by
`test_dedup_discriminator.py`'s own drills.
