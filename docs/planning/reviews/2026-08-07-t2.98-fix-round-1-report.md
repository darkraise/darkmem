## F1 (Important) — "no scale would force a literal Seq Scan"

**What was wrong.** The report's "The plan got something the brief's framing
didn't" section concluded, from a single stale-statistics `EXPLAIN`, that the
missing object index degrades to a full traversal of the *subject* index at any
scale, never a literal heap Seq Scan. The review's own reproduction (a 5%-frequency
probe, fresh `ANALYZE`) showed a `Parallel Seq Scan`, contradicting that claim.

**What I did.** Reproduced the review's finding independently, then went further
than instructed to pin down the actual mechanism, since the review's stated axis
("value frequency, not row count") turned out to be narrower than what I measured:

1. **Reproduced the review's headline case directly.** `darkmem_bench_cf`, own
   SQLAlchemy driver importing `_SAME_ENDPOINT_SQL` verbatim (same discipline as
   the original report), 126,000 rows in one project, `object_name='popular-object'`
   carrying 6,300 rows (5%), object index dropped, fresh `ANALYZE`. Result: a
   literal `Parallel Seq Scan` on `knowledge_triples`
   (`cost=0.00..4335.00`, `Rows Removed by Filter: 39900`). Restoring the index
   on the same table brings back the `BitmapOr` (`Bitmap Index Scan on
   ix_knowledge_triples_live_object`, `cost=230.44` total for the BitmapOr node).
   `shared hit` falls from 3,160 (+215 read) to 174 (+47 read); execution time
   from 13.3 ms to 2.5 ms.

2. **Went beyond the review's single data point: a frequency × scale sweep.**
   Object-name frequencies 0.03%, 0.1%, 1%, 5%, 20%, at two table sizes (4,000 and
   120,000 rows), object index dropped, fresh `ANALYZE`, Postgres's default
   parallel-query settings. Every single point — down to a single matching row in
   a 4,000-row table (`cost=185.01`) — chose a `(Parallel) Seq Scan`. This is
   stronger than "a sufficiently common value produces a Seq Scan": under real
   statistics and default settings, the missing index produces a literal Seq Scan
   at *every* frequency and scale tested, not only the skewed ones. This
   overturns the report's "always narrower … at any scale" claim rather than just
   narrowing its scope. (Rescope N1 later found this held only on this sweep's
   own narrow `fact` seed — see the amended report for the row-width-corrected
   account.)

3. **Confirmed the mechanism: parallel workers, not statistics alone, decide the
   crossover.** With `max_parallel_workers_per_gather = 0`, the same near-unique
   probe (120,000 rows, 40 matches, fresh `ANALYZE`) reproduces the original
   report's exact BEFORE plan shape — `BitmapOr` with a full, boundary-less
   traversal of `ix_knowledge_triples_live` for the object arm
   (`Buffers: shared hit=1079`, matching the ~1046-1057 buffer counts the original
   report measured) — but at its honest cost, `cost=0.00..5240.72`, not the stale
   26.16. So the full-index-traversal fallback is a real plan Postgres's optimizer
   considers; it simply loses to a `Parallel Seq Scan`'s cost discount once
   parallel workers are available (the default) and statistics are accurate.

**Where this lands relative to the review's specific wording.** The review
instructed amending the paragraph to say "the full-index-traversal fallback is
what happens for selective probes at any table size, and a sufficiently common
`object_name` produces a literal heap Seq Scan." My own measurement does not
support that exact split — under Postgres's default configuration and fresh
statistics, selective probes *also* produced a literal Seq Scan in every case I
tested, not the full-index-traversal fallback. I wrote the corrected paragraph to
match what I actually measured rather than the review's specific frequency/row-count
framing, since the instructions were explicit that I should reproduce the
measurement myself rather than copy conclusions. The disposition both arrive at is
the same and is the one that matters for G-C: doc 08 §5.3's "degrades to a scan"
wording is right, the original report's "no scale would force a Seq Scan" claim
was wrong, and the shipped fix is more clearly justified than the original report
argued, not less.

**Where fixed.** `docs/planning/reviews/2026-08-07-t2.98-report.md`, "The plan got
something the brief's framing didn't" section — replaced the erroneous conclusion
with a "Correction (fix round 1, F1)" subsection carrying all three measurements
above and a "Corrected conclusion" paragraph.

**A defect I introduced and caught before shipping.** My first attempt at
reproducing item 1 above, immediately after having run the F3 near-unique
reproduction (item 3-adjacent) on the same bench table, produced inflated numbers
(`cost=11883`, `Buffers: shared hit=986 read=8827`) because that earlier script
cleaned up with `DELETE FROM ... WHERE project = ...` rather than `TRUNCATE`.
Postgres does not reclaim heap pages on `DELETE` — only `VACUUM`/`TRUNCATE` do —
so the table's `relpages` stayed bloated from the prior run's rows and inflated
every subsequent `Seq Scan` cost estimate on that table, regardless of which
project's rows were logically present. I caught this while building the frequency
sweep (a 4,000-row "small table" case was pricing at `cost=8488`, an obviously
wrong number for that size), fixed the cleanup to `TRUNCATE ... CASCADE`, and
reran the skewed-probe measurement in F1 item 1 on a freshly truncated table
before writing it into the report (commit `74288288`). The plan *choice* (Seq
Scan) was correct in both runs; only the cost/buffer numbers were affected.

## F2 (Minor) — docstring misstates the planner mechanism

**What was wrong.** `test_the_same_endpoint_arm_has_an_index_for_both_halves`'s
docstring claimed the OR shape "needs BOTH disjuncts indexed for the planner to
build a BitmapOr — one indexed side is not enough, since Postgres cannot use a
partial index for one arm of an OR and something else for the other." The
report's own BEFORE plan is a counterexample: it *is* a `BitmapOr`, built with
only the subject index present, with the object arm served by a full traversal of
that same index rather than being absent from the plan.

**Fix.** Rewrote the docstring (`backend/tests/test_contradiction_scan.py`,
`TestTheCombinedGenerator.test_the_same_endpoint_arm_has_an_index_for_both_halves`)
to state the true mechanism: each OR arm needs *some* btree containing its column
for a bitmap plan to exist at all; without a leading index, the object arm
degrades to a full traversal of the other index, or — under a skewed value and
fresh statistics — the whole query falls back to a literal heap Seq Scan (F1). The
docstring now points at both the T2.98 report and this fix-round-1 report for the
`EXPLAIN` evidence.

## F3 (Minor) — cost-number narrative rests on stale statistics

**What was wrong.** The report's evidence paragraph for the "Done when" clause
leaned on "the object-side sub-scan's own cost falls from 26.16 … to 4.42." That
table was freshly bulk-seeded with no `ANALYZE` run before measuring, so 26.16 —
supposedly the cost of a full traversal of a ~1,050-page index — is a stale/default
statistics artifact, not a real number (confirmed independently: the identical arm
prices at roughly 5,200 under fresh `ANALYZE`, in the F1 no-parallel-workers
measurement above).

**Fix.** Rewrote the paragraph to rest on the buffer counts (`shared hit` 1051 →
8), which reproduce under fresh statistics and are the honest signal, and added an
explicit note that the original cost figures (26.16 → 4.42) are unreliable and why
— no `ANALYZE` after bulk seeding — pointing at the fix-round-1 measurement for the
corrected number.
