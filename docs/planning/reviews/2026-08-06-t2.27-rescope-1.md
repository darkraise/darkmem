### N1 (Important) — the guard's third spelling: a dynamic import of an app-internal intermediate

```python
import importlib
_p = importlib.import_module("app.services.pipeline")
```

appended to `code_deriver.py` at module level: **both structural guards pass green**
(verified). It executes at import and hands the deriver the live pipeline — the entire
extraction/classification/LLM surface — exactly the reach I1's drill proved the closure
catches when spelled `from .pipeline import ...` or `import app.services.pipeline`.

Why the widened guard misses it: intermediates carry no vocabulary entry — the design
relies on the closure to scan them — and the closure (`test_code_deriver.py:910`)
follows only static `Import`/`ImportFrom` nodes; the literal route fires only on the
client and surface vocabularies (`pipeline` is in neither); the loader-call route
resolves only relative-name-plus-`package` calls. So the two mechanisms each cover the
other's blind spot for *named* modules and neither covers dynamic imports of *unnamed
intermediates*. This is not within the shared scanner's documented bound (the string is
a fully-spelled dotted-path literal, not computed, not prefix-free); it is a hole in the
closure derivation the test owns — I1's own root cause, one route over.

Fix shape: teach `_import_closure` to follow `import_module`/`__import__` calls whose
first argument is a literal — absolute `app.*` names directly, relative names via the
same `_resolve_relative` + `package` resolution the scanner already implements — pulling
the named module into the closure, with a planted-reach control in the style of the
existing parametrisation. `__import__("app.services.pipeline")` is the same class and
falls to the same fix.
