## The internal/external line, and what it excludes

This is the task's single highest-leverage judgement, so it is stated in full.

An import source is **internal** when either rule fires:

1. **Prefix.** It starts with `.`, `/`, `@/`, `~/` or `#` — a relative import in any
   language, an in-repo absolute path, a bundler root alias, or a Node subpath import.
   None of these can name a published package.
2. **Suffix match against the repo's own indexed file list.** `SuffixIndex`, built from
   `code_files.file_path`, is the same index `code_pipeline.phase_04_import_resolution`
   consults *first* when resolving imports — so the deriver's line falls exactly where the
   indexer's does, rather than on a second, drifting rule.

The pipeline's second-choice resolver, `resolve_import`, is deliberately **not** reused: it
takes `repo_root` and does on-disk existence checks, and the checkout is gone by the time
the deriver runs. That resolver's extra reach is therefore lost, and an internal import
only it could have resolved will be misread as external. I judged that acceptable because
the suffix index already covers dotted Python packages, slash paths and index files, and
because the alternative — re-cloning to derive — would put a network fetch inside a
deterministic pass.

`SuffixIndex.matches()` was added rather than reusing `lookup()`, because `lookup()` returns
`None` for an **ambiguous** suffix (two repo files ending `panel.ts`). Reading that refusal
as "not in this repo" would mint a dependency the repository does not have. `matches()`
tolerates ambiguity, which biases the classifier toward **excluding**: an ambiguous name
costs one lost assertion, and for a fact-originating bridge a missing fact is cheaper than a
wrong one. The known cost is the mirror case — a repo file named `redis.ts` hides a real
`redis` dependency. That is asserted as intended behaviour in
`test_an_ambiguous_repo_suffix_still_counts_as_internal`, not left implicit.

**A second exclusion, beyond internal-vs-external:** builtin modules. Python's standard
library is taken from the interpreter itself (`sys.stdlib_module_names`) rather than a list
maintained here; Node's builtins are an explicit frozenset plus the `node:` scheme. Without
this, a mid-size Python repo mints ~100 `tool` entities named `os`, `json`, `typing` — noise
that would flow into the `technologies` denorm and into supersession. The exception is a
name the curated `_TYPE_OVERRIDES` table already types (`asyncio` is the live case): the
corpus having an opinion about a name is the corpus saying that name carries meaning. The
accepted loss is `sqlite3`, a stdlib module that is a genuine `database` signal and is
dropped.

**Dependency-name normalisation** collapses an import to its package root: `@scope/pkg`
keeps two segments, a host-like first segment keeps three (`github.com/gin-gonic/gin`), a
slash path keeps one (`react-dom/client` → `react-dom`), a dotted path keeps its root
(`sqlalchemy.ext.asyncio` → `sqlalchemy`) unless the whole name is curated (`next.js`).

## Everything else the plan left me to choose

- **Which relation.** Doc 10 §6 says `repo —USES/DEPENDS_ON→ dep` without fixing which
  goes where. Rule taken: an entity typed `database`, `service` or `protocol` gets `USES`
  (a datastore is something you use); everything else gets `DEPENDS_ON` (a library is
  something you depend on). Both are in `RELATIONSHIP_TYPES` and both go through
  `normalize_relation_type`.
- **The repo entity's type runs the same ladder as everything else**, including
  `refine_entity_type`. A repo named `Deriver-UI` therefore lands as `tool`, not `project`.
  That looks like it contradicts doc 10's "a `repo → project` entity", but it is what the
  anchoring argument demands: the same name arriving from a memory lands as `tool`, and
  `(name, entity_type)` is the uniqueness key, so a different ladder here would produce two
  nodes for one thing — the exact failure the bridge exists to prevent.
- **Languages come from `code_files.language` unfiltered.** That includes `json`, `css`,
  `html`, `bash`. I did not add a "real languages only" list: it would be a second curated
  vocabulary with no owner, and "this repo uses JSON" is not false.

## Structural guards, and how they are matched

Both scans parse the tree; neither matches line text. The trap the brief records
(`test_verification_judge.py`'s scan firing on prose in comments) is avoided by construction.

- **No model dispatch anywhere in the path.** The scan builds the deriver's *transitive*
  `app` import closure by AST — one hop would pass while an imported helper dispatched
  freely — and runs `tests/_reachability_scan.find_forbidden_reach` over it for the
  dispatch modules, the dispatch attribute names, and the HTTP clients a hand-rolled call
  would need. The closure is 9 modules and contains no allowlist: if it ever grows to
  include something that legitimately talks to a model, that is a design change to argue
  for, not an entry to add.
- **Never-join.** No non-docstring string constant in the closure may name a code-graph
  table (`code_graph_nodes`, `code_edges`, `code_symbols`, `code_files`, `code_chunks`) and
  a memory-graph table (`entities`, `entity_relations`) together. `repositories` is
  deliberately *not* in the code-side set: the amended sweeps read it by design (doc 06
  §6.1), and it is the repo registry, not the code graph.

One implementation note that is load-bearing: the HTTP clients had to be scanned on the
**import route only**, separately from the `app.*` modules. The shared scanner's literal
route does a boundary-substring match over `forbidden_modules`, and `_TYPE_OVERRIDES`
contains the *entity name* `"openai"` — so a single combined rule set flagged the corpus's
own data. A guard that fires on data is a guard that gets deleted the first time it does, so
the split is deliberate and is itself covered by a negative control
(`test_the_model_dispatch_scan_ignores_a_client_name_used_as_data`).

## What the plan got wrong, and what I found

1. **"Two identical runs leave byte-identical rows" is not literally attainable under
   strip-before-rewrite, and the memory path has never satisfied it either.** The strip
   deletes a row no other asserter holds, and the write re-inserts it with a fresh `uuid4`,
   so the *ids* of solely-repo-asserted rows change on every run. Contents (name, type,
   `display_name`, `memory_ids`, `repo_ids`, endpoints, `rel_type`, weight) are identical
   across three runs, which is exactly the discipline `test_idempotent_reextraction.py`
   already applies to memories — its `_entity_key` excludes the id for the same reason.
   The identity that must not churn is that of a **shared** row, which the strip's delete
   guard spares; `test_a_memory_shared_entity_keeps_its_identity_and_its_asserter` asserts
   it directly. Making repo-asserted ids stable would require the write to precede the
   strip, which contradicts invariant 8 — I did not do it.
2. **The `repo_ids` append guard in the upsert is unreachable through `assert_from_repo`.**
   `ON CONFLICT … repo_ids = CASE WHEN :repo_id = ANY(repo_ids) THEN … END` mirrors
   `create_entity`, but the strip always runs first inside the same savepoint, so no row can
   already carry this repo id when the write executes. The "id appears once, not N times"
   assertion passes because of the strip, not because of the CASE. The CASE is defensive and
   is honestly not test-covered; I kept it because it makes the statement correct for a
   caller that ever reaches it another way, and removing it would make the upsert's
   correctness depend on a caller-side ordering invariant instead of on the statement.
3. **A repo-minted entity has no entity embedding, so Phase-4 ANN dedup cannot see it.**
   Writing one would be an embedder call, which this task forbids. Anchoring therefore works
   only by exact `(name, entity_type)` match: `postgres` from code and `postgres` from a
   memory are one node, but `postgres` from code and `postgresql` from a memory are two, where
   the memory path would have merged them at cosine 0.85. This is a real narrowing of doc
   10 §6's stated anchoring benefit and it is nobody's task today. It needs a decision —
   either the deriver gains an embed step (and stops being LLM-free), or a Tier-C job
   back-fills embeddings for repo-asserted entities. Flagged, not worked around.
4. **The deriver is not wired to anything.** No job, no route, no reindex hook. The brief's
   "what ships" enumerates the two primitives and the deriver, and nothing else; wiring
   would need a `JobRegistry` registration plus a `job:<key>` config row, which is another
   owner's surface this round. `assert_repo_graph(session, repo_id)` is the entry point when
   a caller lands. Note the consequence for the retired inert label: the arrays have a
   *writer*, and it is exercised by tests, but no scheduled path fills them in production yet.
5. **Doc 10 §6 leaves the `USES`/`DEPENDS_ON` split unspecified** (item under "Everything
   else the plan left me to choose"). Recorded here rather than amended into the epic,
   because the doc is not *wrong* — it names both relations and does not claim to fix the
   rule.

No Tier-2 or Tier-3 amendment arose. No invariant was relaxed.
