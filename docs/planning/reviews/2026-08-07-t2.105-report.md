## What the brief got wrong, and what I inherited

The brief said to compare task headings against `docs/planning/progress.md` without noting that the two sources live on different branches. The runbook (§6) makes progress.md **canonical on master only**; epic branch copies are stale by design. 

The brief's instruction to "text comparison over two globs, both directions" collided with runbook §6's architecture in a way the brief did not anticipate. Reading progress.md from the working tree produced 48 false-positive "missing rows" — every task ID between T2.100 and T2.105, plus T0.19 and T2.36a–T2.99 — because the epic branch's copy was months behind master's. All of them actually have rows on master; I had no defects to report, only branch staleness to work around.

## The fix

Changed `get_task_ids_from_progress()` to read from master via `git show master:docs/planning/progress.md` instead of the working tree. Error handling fails loudly with a clear message if master is unavailable or unreadable — skipping silently would reintroduce the "check that never runs" problem this task exists to end.

## Where the check lives and why

`backend/tests/test_planning_docs.py` — a pytest test file co-located with other structural checks. Two reasons:

1. The check is documentation-only and does not depend on the schema, application runtime, or any build artifact. Pytest's normal invocation handles it cleanly.
2. Pytest already runs as part of the floor (`cd backend && python -m pytest -q`), so the check executes without plumbing or new entry points.

## The check, in full

Two symmetric tests:

1. **`test_task_headings_have_progress_rows`** — Every `#### T<id>` heading in any `docs/planning/tasks/*.md` file (read from working tree) must have a corresponding `| T<id> |` row in `docs/planning/progress.md` (read from master).
2. **`test_progress_rows_have_task_headings`** — Every `| T<id> |` row in `docs/planning/progress.md` (master) must correspond to a `#### T<id>` heading in some `docs/planning/tasks/*.md` file (working tree).

Both use text comparison over regex patterns, no document parser. Failure messages name the offending task ids.

## Task ID format handling

Regex `r"^#### (T\d+\.\d+[a-z]*)\s"` for headings and `r"^\| (T\d+\.\d+[a-z]*)\s*\|"` for rows handles:

- **Basic format:** `T<digits>.<digits>` — e.g., `T0.19`, `T2.105`
- **Letter suffixes:** `T<digits>.<digits><letters>` — e.g., `T2.36a`, `T2.39a`, `T1.42c`
- **Line anchoring:** Patterns anchor to line start to avoid matching ids in prose

The regex does not have the `T\d+\.\d+` blind spot warned in CLAUDE.md.
