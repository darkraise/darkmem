## N-1 — the restore outran a standing but unapplied verdict

**The defect, reproduced before it was fixed.** `contradiction_scan` journals
its verdict; the *recompute* is what writes `disputed`. Between the two the
fact still reads `candidate` — the exact value `_write_born_rung`'s WHERE
consults — so the statement's refusal covered *applied* disputes only, and the
restore made an upward move at the one moment the ladder itself would refuse
one. Driving the reviewer's exact scenario against the unfixed tree:

```
>       assert outcome.rungs_restored == 0
E       assert 1 == 0
E        +  where 1 = CodeLiftOutcome(..., rungs_restored=1, ...).rungs_restored
INFO  app.services.fact_lift: restored the born rung on fact 019fd764-…: repo
      1c178b8a-… still asserts it and its whole provenance is that parse
```

**The fix** is the one the rescope named: a single `adjudicate_contradiction`
consult in `fact_lift._restore_born_rungs`, before the restore, over rows
already filtered to the rung's precondition. It can only *decline* a restore —
never grant a rung, never open a dispute, never write — so the producer still
does not grade its own output, and the ladder remains the only thing that
applies a verdict.

**The pin** is `test_the_restore_refuses_a_standing_but_unapplied_contradiction`
(`tests/test_deriver_lift.py`), which drives the reviewer's scenario rather than
a synthesised one: a born fact taken through dispute → recover to `candidate`,
a real second repository asserting the same triple as the counterpart, and a
`contradiction_scanned` verdict journalled in the shape `contradiction_scan`
writes. Both halves of the window are asserted rather than assumed — the test
checks `adjudicate_contradiction(...) is True` *and* that the status still reads
`candidate` before it drives the lift. It then withdraws the verdict and asserts
the next tick does restore, so the refusal is demonstrably the veto's and not
the evidence rule's.

**Drill.** Deleting the two consult lines: `1 failed, 78 passed` — exactly this
test, and no other. Restored and re-verified green.

## N-2 — the open-belief half of the rung's WHERE had no test

Deleting `AND {OPEN_BELIEF_PREDICATE}` from `_write_born_rung` left the lift and
honesty suites green at 77/77: only the status half of that WHERE could fail.
The guard is real and reachable — it is what stops a machine label going back
over a closed belief, the state a human's rejection leaves (through
`expired_at`) and doc 10 §6's withdrawal leaves (through `invalid_at`).

**The test** is `test_the_restore_never_reopens_a_closed_belief_window`, driving
the rescope's own scenario: a born fact through a lapsed dispute to `candidate`,
its window closed with `close_window`, then the restore refused at the service
door (`False`, status unchanged) and again through a whole `run_code_lift` tick
(`rungs_restored == 0`). It asserts the row stayed live (`expired_at is None`)
so the test is about the window and not about expiry.

One wording correction against the rescope's phrasing, which I checked in the
tree rather than copying: the shipped human-rejection door
(`human_adjudication.reject_fact`) reaches this predicate through `expire`, not
`close_window`. Both halves of `OPEN_BELIEF_PREDICATE` refuse the restore, so
the finding stands unchanged; the test drives the `invalid_at` half and the
docstring says so instead of misnaming the primitive.

**Drill.** Deleting `AND {OPEN_BELIEF_PREDICATE}`: `1 failed, 78 passed` —
exactly the new test. Restored and re-verified green.

## The deferred observation — written down, and verified before writing

The rescope deferred this rather than asking for a fix, and it stays deferred:
a human rejection of a code-derived fact closes belief on *that row*, and the
restore respects it, but the **birth** path is keyed on `triple_key` rather than
on the rejected row, so the next lift tick mints a new open row born
`corroborated` for the same triple while the repository still asserts the
import.

I verified the claim in the tree instead of restating it, with a scratch driver
(since deleted): after `reject_fact` expired the row, one `run_code_lift` tick
reported `facts_created=1` and left two rows on the triple key — the rejected
one (`expired_at` set) and a fresh open one at `corroborated`.

The note landed on **T2.05's task block** in
`docs/planning/tasks/E2-truth-core.md`, where the human-adjudication semantics
are specified and where the surface that has to tell a person about it will be
built. It states the interplay, says why the semantics are arguably correct (the
code does still depend on the package, and a verdict about one belief window is
not a standing veto over the world changing back), and names the consequence the
adjudication surface owes the human: a rejection over a fact whose evidence is a
live parse is not permanent, and the durable remedy is removing the dependency.
