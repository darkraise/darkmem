### The shape, in one paragraph

`run_contradiction_scan` drains `sources_changed` past its own watermark (a separate
`config` row from the recompute's — two consumers of one stream sharing a position would
each advance the other past unread work), restricts to servable facts that are neither
`disputed` nor `confirmed`, generates a **combined** candidate pool per fact, filters to
overlapping validity windows **in SQL**, drops echo pairs before any model call, and asks
`VerificationJudge.judge` about the survivors until one comes back `contradicted`. The
verdict is journalled as a `contradiction_scanned` row. Nothing else happens: the scan
writes no `verification_status`, and the ladder applies the veto when it next recomputes
the fact, through a second registered detector that reads the standing verdict back.

## 4. How the generator was proven genuinely combined

The Done-when's own warning — "a test where every candidate happens to come from the
same-endpoint arm does not exercise the trigram half" — is answered three ways, and each
is independently drilled.

1. **Each arm has a fact only it can reach.** The structural fixture shares
   `subject_name` with the subject and its `fact` text is deliberate gibberish
   (`"zzz qqq vvv xxx yyy wwww"`), so it is below the trigram floor. The lexical fixture
   shares *neither* endpoint (`dark-mem` / `postgresql` against `darkmem` / `postgres`)
   and its text differs from the subject's by two characters. Each candidate's `arms`
   tuple is asserted to be exactly one arm, so the test would fail if either arm silently
   widened to cover the other's case.
2. **The union is strictly larger than either arm.** `test_the_union_is_larger_than_either_arm_alone`
   builds a corpus holding both fixtures and asserts, for each arm, that the set of
   candidates carrying that arm's name is **not** the whole pool. A pool that came from
   one arm would make one of those two set comparisons an equality.
3. **The cap cannot starve an arm.** This is the one that matters in production and it is
   why the pool is interleaved rather than concatenated.
   `test_the_cap_never_starves_the_trigram_arm` gives the subject six structural
   neighbours and one lexical one at `top_k=3`, and asserts the lexical candidate is still
   in the surviving three. M3 — the mutation that concatenates the arms in order and then
   slices, which is the natural way to write this and passes every other test in the file
   — fails this one and only this one.

A candidate both arms reach keeps both names (`test_a_candidate_both_arms_reach_keeps_both_names`),
so the journal payload's `arm_counts` can say which arm produced a finding rather than
only that something did.

## 5. Where the design landed, and why

**The detector lives in `contradiction_veto.py`, not in the scan's module.** T2.04
recorded the expectation (`_ALLOWED_VETO_FILES`'s comment: *"T2.11 registers its detector
inside the scan's own module, so it does not join this list"*) and it is the only layout
that works. `dream_jobs.py` imports `contradiction_scan`, which makes that module
forbidden to all app code by the invariant-15 reachability scan; if `contradiction_veto`
imported the detector from it, the veto — reachable from the ladder — would fail the
build. The verdict therefore travels as **data on the journal**, which is the same reuse
doc 08 §4.3 makes of `sources_changed` rather than a queue table, and the shared event-type
constant lives in `app/services/events.py`, the vocabulary's own home, so neither module
has to import the other. `contradiction_scan.py` imports nothing from `contradiction_veto`
and `_ALLOWED_VETO_FILES` is untouched.

**Nothing is trusted from the payload except the pair it names.** A journal row is
append-only, so a verdict can outlive the rows it was made about. The detector re-reads
the counterpart, re-checks liveness, re-checks the window overlap, and re-checks that the
witness origin is still on the counterpart and still absent from the subject. Four tests
cover the four ways a standing verdict lapses; M10 drills the first.

**A refusal holds the watermark; every other failure is per-fact.** `verification_recompute`'s
precedent is to advance past a poisonous fact so one bad row cannot stall a queue forever.
A judge refusal is not that: it is a global precondition failure that will be false for
every fact in the batch and true again the moment a qualification record is minted. If the
scan drained and discarded on every six-hourly tick while unqualified, the backlog would
be gone by the time the record existed. So the run aborts, the watermark stands still, and
`judge_refused` / `facts_unscanned` say so. This is what makes the job genuinely
inert-but-ready rather than inert-and-lossy.

**The scan emits no `sources_changed`.** Emitting one to hurry the dispute along is the
obvious shortcut and it is a feedback loop: this job *drains* that stream, so it would
scan the same fact forever. The dispute lands on the recompute's next pass; its slow arm
rotates over every live non-confirmed fact, so the delay is bounded and nothing is lost.
`test_no_run_emits_a_sources_changed_event` pins it.

**The judge's one-sentence `reason` is copied into the payload, deliberately.** CLAUDE.md's
write-time minimization rule says a payload copies content only when a feature
demonstrably needs it and says so at the writer. Doc 08 §6 serves a disputed fact labelled
with both sides and gates it on nobody's review; two ids and a triple do not say *why* the
pair conflicts, so a dispute nobody can understand is a dispute nobody can resolve. The
counterpart's free-text `fact` column is **not** copied — the triple already states the
competing claim, matching `ContradictionFinding`'s own rule.

## 6. What the plan got wrong, or left underspecified

1. **"Window undecidable" is not a reachable miss.** The brief lists three miss causes —
   "cap hit, judge refused, window undecidable". The first two are implemented as
   counters. The third has no reachable state: `windows_overlap` is *total* over NULL
   bounds (NULL `valid_at` reads as unbounded-past, NULL `invalid_at` as open-ended, doc 08
   §3.1), so every pair of rows is decidably overlapping or decidably disjoint. There is no
   third answer to count. A disjoint pair is a **correct skip**, not a miss, and folding it
   into the miss count would overstate the gap; it is filtered by SQL pushdown and not
   transported. No counter was invented for a state the type system cannot produce.

2. **`ix_knowledge_triples_live` does not carry the same-endpoint arm — half of it does.**
   The brief says of the same-endpoint arm: *"An index lookup; `ix_knowledge_triples_live`
   carries it."* That index is `(subject_name, rel_type, object_name)`, so `subject_name`
   is a leading column and the subject half is an index lookup; `object_name` is the third
   column and the object half has no leading index of its own. The arm is written as one
   query with an `OR`, which Postgres can serve as a BitmapOr with an index scan on the
   subject side and no index support on the object side. This is recorded rather than
   worked around: splitting into two queries or adding an index is a schema decision beyond
   the extension-and-index scope this task was given, and at the fact-layer volumes in play
   it is not yet a cost. **Flagged for whoever owns the next baseline round.**

3. **The truncation counter is a floor, and could not honestly be exact.** Each arm is
   drawn at its `LIMIT`; drawn at exactly `top_k`, an arm that saturated its own limit is
   indistinguishable from one that returned everything, and `candidates_truncated` would
   read **zero** on precisely the facts where the generator undercounted most. The arms are
   therefore drawn one row past the cap — a peek row whose only job is to make the cap's
   bite observable. An exact count would mean transporting the whole neighbourhood, which
   is what the cap exists to avoid. The counter is documented as "at least this many went
   unexamined", and the test asserts the floor rather than a number.

4. **The `%` operator, not `similarity(...) >=`.** SQLAlchemy's asyncpg dialect uses
   `numeric_dollar` paramstyle, so a single `%` is correct and a doubled `%%` raises
   `UndefinedFunctionError` — verified empirically before committing. The threshold is set
   through `set_limit(CAST(:floor AS real))` rather than `SET LOCAL pg_trgm.similarity_threshold`,
   because `SET` accepts no bind parameter.

5. **`_ALLOWED_DREAM_JOB_LINES` no longer exists.** The brief warns about adding to it and
   notes it is T2.67's known defect. T2.67 has already landed: the constant was replaced by
   `_ALLOWED_DREAM_JOB_FILES` plus `_main_py_exempt_node_ids`'s structural walk. Nothing
   here needed either — the umbrella is the only file that names the module, and it is the
   one file the scan skips.

6. **The task file's block note is now history in two places.** `docs/planning/tasks/E2-truth-core.md`
   still carries both the 2026-07-31 `BLOCKED` paragraph and the 2026-08-06 unblock above
   it. That is the controller's file, untouched here, but the stale paragraph now reads as
   current to anyone who scrolls past the unblock.

## 7. Deliberate non-changes, and open items

- **`CLAUDE.md` was not updated.** Its Jobs section still says all six dream-family bodies
  are `PlaceholderJobRunner`s, which was already stale for T2.09, T2.10, T2.12 and T2.53
  before this task. Correcting it is a shared-file edit across concurrent lanes; flagged
  for the controller rather than taken unilaterally.
- **The frontend event taxonomy was not widened.** `frontend/src/features/activity/event-taxonomy.ts`
  maps event types to feed tabs and documents its own fallback ("an event_type absent from
  every bucket still shows under all"), so `contradiction_scanned` is displayable today
  without a tab. A one-line addition (`contradiction_scanned: "verification"`) would give
  it one; left out to keep this diff inside the backend lane.
- **No recall number is produced.** That is T2.52's, and measuring it here would need a
  runner that depends on this task.
- **Adjudication is sequential, not fanned out.** Doc 08 §5.3 sanctions exactly two config
  rows for this job and an `llm_concurrency` knob would be a third. At a six-hourly cadence
  over 20 facts, with the veto's first-finding short-circuit bounding calls per fact, the
  serial cost is not yet worth a knob the design did not name.
- **Dispute latency is one recompute pass.** Bounded by the recompute's slow-arm rotation
  (`slow_arm_interval_seconds`, default 600s, over a rotating slice of every live
  non-confirmed fact), or sooner if the fact sees a genuine provenance change. Named here
  because it is a real behavioural property of the split, not an oversight.
