## Item 1 — the two leaks, and a third the fix exposed

**Fix.**

- `app/services/chat.py` reads `row.labels.get("verification_status")` and carries
  `label_suppressed` beside it. The old line read `row.verification_status` — the raw
  `ComposedRow` attribute the ranking is allowed to consume — while the lines either
  side of it already read `row.labels`. This payload is persisted into
  `messages.context`, so the leak outlived the request that served it.
- `app/services/review_queue.py` gained `_served_labels`, which calls `row_labels` and
  takes the two keys the queue item declares (`verification_status`,
  `label_suppressed`). The queue serves no badge and no lifecycle, so it takes two keys
  rather than the whole triplet; taking them *from the producer* is what makes this door
  a consumer of the gate rather than a second implementation of it. `reason` still
  derives from the raw rung — it answers why a row is queued, not how verified it is,
  and `disputed` is ungated either way.
- **Third leak, not in the review's list, found by the new scan:**
  `layer_composition._labels` stamped the raw `candidate.verification_status`. It is
  overwritten by `_badge_labels` whenever badges were derived, which is every path the
  service takes — but `compose(badges=None)` is a supported call and on that path
  `_labels` *is* the served label dict. It now routes through `row_labels` too. This is
  the single most likely place the leak would have reappeared: the raw spelling sat one
  merge away from the gated one and read as dead code.

**Mutation drills.**

Each restored; suite back to 52 passed. Note every one of the three is caught **twice**
— by its own door test and by the structural scan — which is the property the first

## Item 2 — `tier` under suppression

**Decision: recompute the served tier off the served status.** `ComposedRowResponse.tier`
is now `tier_for(row.labels["verification_status"])`. `ComposedRow.tier` — the ranking's
— still comes from the raw rung, and the composed order is unchanged.

**Why the alternative was worse.** Stripping `tier` from the wire would have removed a
field doc 07 §8 fixes and the SPA reads, to fix a problem that is not the field's
existence but its *disagreement* with the label beside it. It would also be a permanent
cost paid for a temporary condition: once T2.40 mints the record the two values coincide
again, and a stripped field would have to be re-added — a wire change in both
directions for a gap that closes itself. Recomputing keeps the field meaningful at every
gate state (a reader's tier always matches the reader's label) and keeps the leak
impossible rather than merely unreadable.

The constraint the brief set is honoured exactly: derivation uses the true status (the
row ranks as `corroborated`, tier 3), the wire does not reveal it (the row serves tier
2 beside `candidate`).

**Mutation drill.** `tier=row.tier` restored →
`test_both_knowledge_doors_serve_the_withheld_rung_and_its_tier` FAILED (1 failed, 51
passed). Restored. `test_the_composed_row_still_ranks_on_the_rung_it_does_not_serve`
pins the other half: it asserts `row.verification_status == "corroborated"` and
`row.tier == 3` on the same row whose label reads `candidate`, so a "fix" that gated the
ranking too would fail.

## Item 4 — the scans now quantify

**Fix.** Both scans were rewritten in `tests/test_claim_serving_gates.py`.

The emission scan walks every `.py` under `backend/app` — 208 files, `rglob`, routes and
MCP included — and finds every place a mapping gains a `verification_status` entry, in
three shapes rather than one: `ast.Dict` entries, `dict(verification_status=…)`
keywords, and `x["verification_status"] = …` assignments. (The first round matched only
`ast.Dict` with *constant* values, so `dict(...)`, a variable value and a subscript
assignment all passed it even inside the two files it named.) Each emission is then
classified by **where its value came from**, not by which file it is in. Two shapes pass:

1. the value reads `verification_status` out of a mapping the producer built — a
   `row_labels(...)` call, a name bound from one, or a `.labels`-spelled attribute; or
2. the value is wrapped in `claim_gates.ungated_status(...)`.

`ungated_status` is the new declaration for sites that legitimately hold a rung no
reader is served: the `verified` and `human_verdict` journal payloads
(`knowledge_triples`, `human_adjudication`), the candidate row the facts channel hands
to the ranking, and `reject_fact`'s return value (which the 204 route discards). It is a
call rather than a comment deliberately — the scan reads the parsed tree, so prose can
neither claim the exemption nor trip the guard, and a serving path that wrapped itself
to quiet the scan would have written a false claim down where a reviewer can see it.

Only two files are exempt: `fact_badge.py` (doc 12's producer) and `claim_gates.py` (the
gate). That is the property being asserted, not a list of exceptions, and
`test_the_walk_reaches_every_serving_layer` pins that the walk really reaches routes,
MCP, services and repositories and covers >150 files.

The grounded scan now walks the same tree against the **parsed** string constants,
excluding docstrings by node identity. That fixes the inherited trap in both directions:
it fires on a route serving the literal (outside `services/`, which the old glob never
looked at) and does not fire on a docstring discussing groundedness or on
`"groundedness_gate_precision_bar"`. The non-literal half — a path reading the status off
a row, which is how every real serving path works — is answered by the emission scan plus
item 6's article gate, not by this scan.

**The review's own empirical drills, re-run.**

| Drill | First round | Now |
|---|---|---|
| New `app/services/facts_export.py` emitting `{"verification_status": "corroborated"}` | suite green (60/60) | **RED**: `test_no_path_under_app_emits_a_label_the_producer_did_not_build` FAILED, naming `app/services/facts_export.py:5: 'corroborated'` — 1 failed, 51 passed |
| New `app/api/routes/article_preview.py` returning `{"verification_status": "grounded"}` | suite green | **RED**: both scans FAILED — 2 failed, 50 passed |

Both drill files were deleted; the tree is clean.

**The guard's own failure mode is tested.** Seven parametrized shapes that must fire
(literal, raw subscript, raw attribute, `dict()` keyword, subscript assignment, a bare
variable, and a value read out of `badge.as_dict()`) and four that must not. A guard
nobody watched fail is a guard nobody has tested — which is exactly what the first
round's was.

## Item 6 — the gate keys on `id_kind`

**Fix.** `served_status(status, *, id_kind, gate=None)` — `id_kind` is a **required
keyword**, and dispatches through `_GATE_BY_ID_KIND`: `fact` → `corroboration_gate`
(G-C's promotion record), `article` → `groundedness_gate`. `row_labels` passes its own
`id_kind` through. An unrecognised kind raises rather than defaulting, so a new labelled
surface fails loud instead of ungated, and `test_every_badge_bearing_kind_has_a_gate`
pins `_GATE_BY_ID_KIND`'s keys equal to `BADGE_BEARING_ID_KINDS` so a kind cannot gain a
badge without a gate.

`groundedness_gate()` returns closed **unconditionally**. It does not read the
qualification record and does not import `verification_judge` — the single-door scan
correctly rejected that in the first round, and `test_this_module_never_reaches_the_judge`
still holds. A gate that cannot ask its question refuses; that is strictly stronger than
the fact gate and cannot be wrong in the unsafe direction.

**This closes the leak but not the feature, and the brief asked me to say so.** Opening
the article gate when the judge *is* qualified must happen at the judge's own door, not
here — so T3.02/T3.23 will need to route the article label through
`verification_judge`'s qualification, and `row_labels(id_kind="article", …)` will need a
gate argument the judge supplies rather than the closed default. **I did not touch
`verification_judge.py`**: closing item 6 as scoped (the fact record must not light the
article) did not require it, and widening into that module is a separate decision. What
exists today is the correct refusal plus a named seam.

**Mutation drill.** `_GATE_BY_ID_KIND[id_kind]` replaced with an unconditional
`corroboration_gate` → `test_the_article_gate_is_closed_even_with_the_fact_record` and
`test_an_unrecognised_claim_refuses_rather_than_serving` FAILED (2 failed, 50 passed).
The first failure is precisely the review's inferred defect, now measured rather than
inferred: with the fact record minted, the article label lit. Restored.

## The question the M1 split rests on

**Can a serving path now reach a label whose evidence does not exist?**

**No — on every path that exists today, and the guard now fails the build on a new one.**

The full basis, stated so a re-review can check it rather than take it:

- Every wire door that carries a verification label was driven with the gate closed and
  no fixture, and every one served `candidate` with `label_suppressed` set: REST facts
  list and detail, MCP `fact_get`, REST review queue, REST and MCP knowledge search, and
  chat's persisted context. The two the review measured leaking are among them.
- The withheld rung is no longer recoverable from anything served beside the label:
  `badge` is null, `unverified` is true, and `tier` is the served rung's.
- Suppression is visible on every door, in the wire schemas and in the TS mirrors, so a
  withheld label and an earned `candidate` no longer read alike.
- An article cannot light on the fact record, so T2.40's mint releases exactly the claim
  it measured.
- A new module or route that emits a rung the producer did not build turns the suite red
  — measured on the review's own two drills, both of which left the first round green.

**Three residues, none of them a path to an unbacked label.**

1. **Journal history is ungated by design** — `verified` and `human_verdict` payloads
   record which rungs a transition moved between. The review judged this acceptable and
   flagged it for controller ratification; nothing here changes it, and the sites now
   *declare* it via `ungated_status` instead of merely looking like every other emission.
2. **`messages.context` rows written before this commit still hold raw promoted rungs.**
   Append-only by the T2.59 ruling; the leak is closed forward, not retroactively.
3. **The record still binds nothing** — the review's unfixed controller-level finding.
   Any dict with `"gate_eligible": true` opens the fact gate, whatever corpus or model
   minted it. That is T2.40's schema to fix and was explicitly out of this round's scope.

One adjacent finding, reported not fixed: the SPA's chat context panel now receives
`label_suppressed` and does not render it, so a chat reader sees `candidate` with no
indication it was withheld. The backend no longer lies to them; the UI simply does not
yet say why. That is a UI decision, not a gate defect, and it is outside this brief.
