## Done-when evidence

**1. Only content between the markers is rewritten; user text outside survives — ✅.**
`apply_block` replaces exactly `text[bounds.begin : bounds.end + len(MARKER_END)]`
(`inject_block.py:153`) and the shipped suite's byte-for-byte claims held against
an independent probe driver: empty file, no trailing newline, markers adjacent
mid-line with no separators, block at position 0, a file that is only markers,
astral/combining unicode on both sides, CRLF outside the block — all byte-exact
outside the pair. Marker-token analysis: neither sentinel has a self-overlap
border and neither is a substring of the other, so `str.count` cannot miscount
and `str.index` finds the unique occurrence. Two documented limits, both
correct: a human-pasted pair is adopted as the block (fixed-sentinel semantics,
stated in `test_markers_inside_the_human_s_own_prose_are_still_the_block`), and
that includes a full pair inside a fenced code block — a text-level scanner
cannot see fences. The append path inserts a `\n` separator when the file lacks
a trailing newline; user bytes survive as a strict prefix.

**2. A corrupted or missing marker pair fails safe — ✅.** `_locate` counts both
markers before locating either; anything other than exactly one of each, in
order, raises `ManagedBlockCorrupted` naming the counts. Probes beyond the
shipped cases: 1 begin + 3 ends, a valid pair followed by a stray begin,
inverted pair on `remove_block` — all refuse. Nesting needs a second begin
(refused); overlapping tokens are impossible (no border). The detection set is
complete for marker-count damage. The gap is on the *production* side — darkmem
can mint the damage itself (finding I-1) — after which the fail-safe correctly
refuses, but on a file darkmem broke.

**3. No server-side filesystem write anywhere in the path — ✅ today.** The
module imports only `__future__` and `dataclasses`; no function touches
anything but the string; no caller exists. The AST scan catches the natural
drift shapes — verified: `import os` + `os.replace` reddens it; any call
spelled `.write_text` / `.unlink` / `open(...)` is caught however the object
was obtained. Its reach limit is real, though (finding M-3): two escape shapes
pass it empirically.

**Scope:** three functions, one exception, two constants — all traceable to doc
15 §3.1–§3.2 (header format verbatim, Curbed/Removed lifecycle,
strip-before-rewrite). Nothing built beyond the spec.

## Findings

### I-1 (Important) — the marker-embedding guard misses two of the three ways in

`inject_block.py:121-127` checks `items` for embedded sentinels, but not
`project` or `generated_at`, and `apply_block` (`inject_block.py:137-153`) —
the actual write boundary — checks nothing. `project` is free-form user text
(`MemoryCreate.project: str | None`, no pattern). Reproduced: a project named
`evil <!-- darkmem:end --> project` renders a header carrying the sentinel,
`apply_block` writes a file with **two** END markers, and the next refresh and
`remove_block` both raise — inject and uninstall locked out until the human
hand-edits damage darkmem itself wrote. That is verbatim the failure the item
check's own docstring says it exists to prevent ("a failure the operator could
not explain from their own edits"), so the module's claim that items are "the
one way rendering could corrupt the file" is false. No human bytes are ever
lost — the downstream fail-safe holds, which is what keeps this short of
Critical. Fix shape: validate the composed block (header included) in
`render_block`, and/or refuse a marker-carrying `block` in `apply_block` —
the latter also covers T3.11 adapters composing blocks without `render_block`.

### M-2 (Minor) — install/uninstall cycles accumulate one blank line each

`apply_block` appends `body + "\n"` (`inject_block.py:151`); `remove_block`
strips only `[begin, end + len(END))` (`inject_block.py:168`). Three
install/remove cycles turn `"# rules\n"` into `"# rules\n\n\n\n"`. Each
operation honours its contract — the trailing `\n` sits outside the markers,
and eating an adjacent newline on removal would be guessing (a user's own blank
line would go with it) — so the trade is defensible, but it is stated nowhere
and the lifecycle round-trip is not identity. Document it, or move the
terminating newline inside the marker region.

### M-3 (Minor) — the AST scan is a blocklist; an import allowlist would close the demonstrated escapes

Verified empirically: `__import__("os").replace(path, path)` passes the scan
(the `str.replace` carve-out at `test_inject_block.py:269` exempts exactly
`os.replace`, and there is no import statement to ban — the comment claiming
the import ban catches it holds only for literal imports), and a filesystem
write hidden behind any `app.*` helper import passes (the scan bans six stdlib
names only; suite stays 22-passed with `from app.utils import ids` present).
The module needs exactly two imports; asserting the import set equals that
allowlist is one line and catches the realistic drift shape — a helper module.
The scan is a tripwire against honest drift, not proof, which is the right and
only achievable posture for an in-repo scan; this finding is about making the
tripwire cover the drift shape most likely to actually occur.

### M-4 (Minor) — `ManagedBlockCorrupted` from `render_block` misnames the situation

`inject_block.py:123`: nothing is corrupted at render time — the *selection* is
poisoned, the operator's file is fine. A caller catching the type to mean "the
user's file needs fixing" (T3.11's natural shape) misroutes this case.
Reachability is real: items are F3 selection texts, and in this repo a memory
documenting the inject feature itself can genuinely contain the sentinel — one
such memory blocks the whole injection for its project. Cross-task note for
T3.10: the fill should drop a poisoned item rather than fail the cycle.

### M-5 (Minor) — header fields are unquoted and comma-delimited

`inject_block.py:129-133`: a project containing `", "` makes the header
field-structure ambiguous to any future parser (verified: 6 comma-fields from a
4-field header). Nothing parses it today and the format matches doc 15 §3.2
verbatim; recorded for T3.11/T3.12.

### M-6 (Minor) — block body is always LF, so a CRLF file becomes mixed-EOL

Outside bytes are preserved exactly (verified), and the block region is
darkmem's, so this is within contract; per-tool EOL policy belongs with T3.11's
comment-syntax parameterisation.

## The scope call — per-tool comment syntax deferred to T3.11

Right call. All four v1 targets read Markdown-family files where HTML comments
are inert; the sentinels are module constants and the three functions the only
surface, so parameterisation is a contained signature change with no stored
data to migrate (markers live only in client-owned files). Two edges to hand
T3.11 explicitly: (1) if any tool's marker syntax differs from v1's, files
already written with the v1 sentinel must be migrated or the new writer appends
a second block while the old one rots as visible text; (2) `render_block`'s
marker refusal must be parameterised together with the markers, or an item
carrying tool-B's sentinel passes tool-B's render.
