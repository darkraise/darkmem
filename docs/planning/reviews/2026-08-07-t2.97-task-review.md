## 2. The headline limitation (dispatch point 1) — real, correctly bounded, honestly pinned

- **Structurally verified.** `PostgresGraphRepository.assert_from_repo`
  (`backend/app/repositories/graph.py:673-697`) is an `ON CONFLICT (name, entity_type)`
  exact-key upsert with no ANN probe, and Phase 4 dedup runs only inside
  `process_batch` at memory-write time. Nothing re-runs it. So memory-first → repo-later
  permanently yields two embedded nodes, exactly as reported.
- **The pinning test asserts what it claims.**
  `test_a_repo_indexed_after_the_memory_still_leaves_two_nodes` drives ingest → derive →
  anchor in that order and asserts *two* rows with both names embedded; a future merge
  pass turns it red. Non-vacuous by construction (a merge collapses `entity_rows` to one).
- **The report's refutation of the brief is itself correct.** The brief suggested
  "letting the next re-derivation reconcile"; re-derivation is a strip-and-rewrite of the
  repo's *own* assertions by exact key (savepoint in `assert_from_repo`) — it cannot
  merge. The report calls this out (§8) and is right.
- **The Done-when-1 verdict.** The clause is satisfied in the repo-first order at the
  real probe and real threshold (below). The brief explicitly contemplated a backfill
  shape with an open window provided the executor "say explicitly which window your shape
  leaves open" — the report does, pins it with a test, records the Tier-1 amendment in
  the task text, states the boundary in CLAUDE.md's job paragraph, and names the merge
  pass as an unowned Tier-2 candidate. That is the non-convenient-order obligation
  discharged as the brief defined it.
- **Sharpening (Minor, M2 below):** the "closed" order is closed only when the job tick
  precedes the memory. A memory ingested inside the pre-tick window (up to the cron hour,
  longer for a repo minting more than `missing_batch=200` entities) forks *permanently* —
  it falls into the open case, it does not wait for the tick. The report's "the window is
  bounded by the cron period" bounds the window's duration, not its consequence, and a
  hasty reader could take it as transient latency. The report's headline order statement
  does include the tick, so this is wording, not error.

## 3. The rejected candidates (dispatch point 2)

- **Shape 1 "blocked":** verified against `tests/test_code_deriver.py:929-937` —
  `_LLM_DISPATCH_ATTRS` is exactly the seven names the report quotes, and
  `_LLM_SURFACES` (line 909) additionally forbids `app.services.llm` by module route.
  Embedding inside the deriver therefore requires removing the orchestrator module from
  `_LLM_SURFACES` *and* `embed*`/`get_llm_orchestrator`/`LLMOrchestrator` from the attr

  **One imprecision (Minor, M1):** "it cannot distinguish them" overstates. The
  scanner's attribute route (`tests/_reachability_scan.py:363-365`) matches bare attr

  that textual attr layer (evaded by a computed `getattr`) plus the HTTP-client route,

  judgment; the absolutist framing is not literally what the scanner does.

  the code.
- Adjacent finding 3 verified: `reembed.py:598-604` does bump `hit_count` on its cache
