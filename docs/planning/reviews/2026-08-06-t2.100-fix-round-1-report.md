## I-1 — the journalled rung was served on two claim surfaces

### What the ruling says, and what it therefore does not say

The original ruling accepted the raw rung on `/events` and named only that door.
Its argument was that a reader of `/events` is reading a computation log **by
construction of which door they opened** — an argument about the door, not about
the payload. It evaporates when the same bytes are embedded in a response whose
purpose is to state a fact's status. A fact-detail body that suppresses the rung
in `verification_status` and hands it back two keys later in `ladder` has not
gated anything; it has moved the answer.

So: **an accepted residue is scoped to the surface it was accepted on.** The
events door is untouched — no filtering, no redaction, no gating — and the
embeddings are closed.

### The fix

`claim_gates.gated_journal_payload(value, *, id_kind, gate=None)` maps every
`verification_status` anywhere in a JSON-shaped value through `served_status`,
and gives a withheld one a `label_suppressed` sibling **in the same object**.

- It takes any value, not one payload, so a caller hands over a whole page and
  the gate resolves **once**. Per-row resolution would let a record minted
  mid-response serve half a page gated and half not.
- It is derived from `served_status` rather than written beside it, the same way
  `raw_statuses_for_served` is, so the label and the trace cannot drift into two
  answers to one question.
- The marker is not optional. Rewriting `corroborated` → `candidate` silently
  would make the trace record a movement the ladder never made, and a suppressed
  transition would read as a genuine one — the module's standing rule, and the
  thing `journalled_status`'s docstring says a gated *journal write* would do.

Three call sites, two of them the review's:

| Surface | Field | Reader |
|---|---|---|
| `GET /api/v1/knowledge/facts/{id}` | `ladder` | `facts_read.get_fact` → `events.object_timeline` |
| MCP `fact_get` | `ladder` | same function, same `FactDetailResponse` |
| `GET /api/v1/review-queue/facts` | `evidence` | `review_queue.list_open_facts` → `verified_evidence.latest_verified_evidence` |

The MCP twin is not a third fix: it serves `facts_read.get_fact`'s dict through
the same response model, so gating at the service covers it. It is named here
because the review's reader count of three doors is really four surfaces.

### What a reader can and cannot recover, stated exactly

The rung itself is never in either body. What the marker discloses is that *a
promoted rung was withheld here* — which is precisely what the row's own
`label_suppressed` already discloses on the same body, by T2.95's design and by
`test_every_labelled_wire_model_declares_the_suppression_marker`'s mandate.

Two consequences worth writing down rather than leaving for the next review:

- With `PROMOTED_STATUSES` a single value today, "a rung was withheld" and "the
  rung was `corroborated`" coincide. Closing that last inch means dropping the
  marker, which is the one thing the ruling forbids ("the trace must still
  distinguish suppression from a genuine candidate"), so it is accepted and
  named rather than quietly relied on.
- The payload's other keys — `outcome: "promote"`, `origin_count`, `required_n`,
  `gate_fired` — witness the same transition. They are left as they are on
  purpose: once the transition carries the suppression marker, they add nothing
  a reader did not already have from it. Stripping them would gut the evidence
  block the review queue exists to show a triager, in exchange for nothing.

### The docstring

`journalled_status`'s reach sentence named `/events` as *the* reader, which is
this marker's own defect class one level up: a declaration whose stated reach is
narrower than its measured readers. It now names all three readers and says
which of them serves the payload verbatim and which serve it through the gate,
with the "the ruling is about that door, so it does not travel with the bytes"
sentence at the point where someone would otherwise re-derive the wrong
conclusion. The module docstring's split paragraph gained the same scoping in
one sentence.

### The pin

`JOURNAL_PAYLOAD_REACH` (`test_every_reader_of_a_journal_payload_is_the_one_that_was_classified`)
pins `relpath → reader → whether the module gates what it reads`, scanned over
the whole tree **including** the producer and the gate, because the question is
who reads the substrate rather than who serves a label — `fact_badge` is a
reader and is exempt from the emission scan.

The five readers, and why each is where it is:

| Module | Reader | Gated | Why |
|---|---|---|---|
| `api/routes/events.py` | all three | no | the audit door; verbatim by ruling |
| `services/facts_read.py` | `object_timeline`, `latest_verified_evidence` | yes | serves the `ladder` |
| `services/review_queue.py` | `latest_verified_evidence` | yes | serves the `evidence` |
| `services/fact_badge.py` | `latest_verified_evidence` | no | takes `as_of` and a contradiction boolean; serves no payload |
| `services/layer_composition.py` | `latest_verified_evidence` | no | `dispute_label` copies named counterpart fields; no rung among them |

The last two were verified in source, not assumed: neither reads
`verification_status` out of a payload, and neither puts a payload on the wire.

## I-2 — the whole-body door drive asserted its fixture

`test_no_unserved_declaration_reaches_a_reader_at_any_door` claimed the promoted
rung appears **nowhere** in what six doors serve. That was false at its own
fact-detail door for any fact that transitioned the production way, and it passed
only because `_promoted_fact` reached the rung by direct UPDATE and therefore
journalled nothing. Same family as the vacuous drill the first round caught in
itself: a check kept true by the shape of its input rather than by the behaviour
it names.

**Fixed at the fixture, not at the assertion.** `_promoted_fact` now drives the
ladder's own applier — `KnowledgeTripleRepository.set_verification_status(...,
outcome="promote", origin_count=2, required_n=2)` — so every door drive in the
suite now runs against a fact carrying a real `verified` transition, which is
what every promoted fact in production carries. The blanket string assertion is
kept, and it now holds because the doors gate the embedded payload (I-1) rather
than because there was nothing to leak. The docstrings of both the fixture and
the test say so.

## Minor 3 — `journal_bound_denials` reach

**(a) Tuple-target bindings — fixed.** `payload, extra = {…unserved…}, None`
binds through an `ast.Tuple` whose elements are the names being written, and the
walk only read top-level targets while the docstring claimed "every name it
writes through". `_names_written_by` now recurses into `Tuple`/`List`/`Starred`
targets. It deliberately does **not** walk subscript *slices*: `payload[key] =
…` writes `payload` and merely reads `key`, and tainting `key` would be a false
positive the guard has no way to argue away.

**(b) Same-scope name laundering — fixed.** `inner = {…unserved…}` then
`payload = {"wrapped": inner}` was blind, undisclosed, and one refactor away
from the live before/after payload style. A statement that reads a tainted name
now taints what it writes, iterated to a fixpoint because `ast.walk` does not
visit a module's statements in source order. The simple-statement restriction is
unchanged — reading a compound statement's subtree would taint every name the
block writes, which is the false positive the original restriction exists for.

Three rows added to `DENIAL_SHAPES`: the tuple target (fires), the laundering
(fires), and a second name that was never tainted (does not fire) — the negative
matters because a propagation rule with no negative is indistinguishable from
tainting everything.

**(c) The stated backstop was wrong in direction — fixed.** The first report said
the cross-function hop is covered by the events door drive. It is not: a door
drive asserts the presence of a known rung on a known transition and can never
catch a falsely-`unserved` value inside a payload. What actually forces review of
a new declared site, at any number of hops, is `DECLARATION_INVENTORY`. The
guard's docstring now says that, and says the reach is one hop *out of the
module* rather than the vaguer "one hop".

## Minor 4 — the ruling's "authenticated operator" qualifier

`test_an_events_read_requires_an_authenticated_reader` drives `GET
/api/v1/events`, `/events/timeline` and `/events/calendar` **without** headers
and asserts 401 on each. All three, because all three serve the payload
verbatim and the ruling's sentence covers the reader, not one route.

This is what the existing events door drive could not say: it sends auth headers,
so it cannot tell "an authenticated operator can read them" from "anyone can",
and the difference is the entire scope of what was accepted.

## Adjacent finding — a latent ordering flake in T2.04's suite, measured

The **first** floor run of this round came back
`1 failed, 4539 passed, 19 skipped`, on
`tests/test_contradiction_veto.py::TestTheVetoIsAbsolute::test_a_re_run_over_a_standing_dispute_journals_the_reconfirmation`.
The **second** run of the identical tree came back `4540 passed, 19 skipped`,
and the file passes alone (86 passed) and paired with this task's suite (195
passed). It is nondeterministic, and the mechanism is not a mystery:

- `events.created_at` defaults to `now()`, which is the *transaction*
  timestamp, and the `session` fixture runs a whole test inside one outer
  transaction — `session.commit()` only releases a savepoint. So every event a
  test writes carries the **same** `created_at`.
- That test selects `... ORDER BY created_at` and then asserts `events[0]` is
  the dispute and `events[1]` the hold. With the key tied, the row order is
  whatever the plan happens to produce.
- The file already knows this. Twenty lines below, `test_recovery_journals_
  exactly_one_transition` carries the comment *"Asserted as a chain rather than
  by ordering: the fixture's savepoints share one transaction timestamp, so
  `created_at` cannot separate two rows written in the same test"* — and
  asserts a set of transitions instead of an order.

**Not fixed here, deliberately.** It is T2.04's file, another lane is live, and
the floor is green; the fix is one line — `ORDER BY created_at, id`, which is
what `events.object_timeline` and `list_events` already order by, and `id` is
`BIGINT GENERATED ALWAYS AS IDENTITY`, so it is exactly insertion order. Two
sibling sites carry the same shape (`test_contradiction_veto.py:257` and
`:807`, the latter already assertion-hardened) and
`tests/test_verification_ladder.py:634`, `tests/test_dream_jobs.py:1033`,
`tests/test_maintenance_journaling.py:54`, `tests/test_index_debt.py:391` and
`tests/test_repo_hint_ssrf.py:195` order events by `created_at` alone too.

Whether this round *raised* the flake's odds is unproven and worth stating
plainly: `_promoted_fact` now journals, so the suite writes a few more `events`
rows before that file runs, and the planner's choice between a heap order and
an index scan moves with statistics. What is measured is that the same code
passed on re-run, so nothing here is deterministic in either direction.

## Adjacent finding, not fixed

`frontend/src/hooks/api/use-review-queue-api.ts`'s `VerifiedEvidencePayload`
types `before`/`after` as `{ verification_status }`; the gated payload adds an
optional `label_suppressed` inside them. The interface is not made *false* by
this — an API response type describing a subset is ordinary TypeScript, and no
consumer reads the new key — but a UI that wanted to render "withheld" beside a
ladder step would have nothing to read it from. Not shipped in this round because
the worktree has no `node_modules`, so a frontend edit here could not be
typechecked, and an unverified frontend edit is worth less than a named
follow-up.
