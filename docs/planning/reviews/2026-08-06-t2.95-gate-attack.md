# T2.95 adversarial review — the claim-serving gate, attacked

**Subject:** `121bccf7` (`feat(claims): an evidence record gates the label, never the code`),
reviewed on `feat/e2-lane-cb` at `3858428f`. Reviewer tier: Fable 5, chartered to refute.
**Fixes landed by this review:** `b8bf060d` (two defects inside `claim_gates.py`'s own
surface, both mutation-drilled). Everything else found here is reported, not patched —
the findings collectively mean the M1 split's safety argument is weaker than stated, and
the brief makes that a controller decision.

**Headline: the commit's central claim — "no serving path can reach a claim whose
evidence does not exist" — is false today, measured on two live doors.** The gate is real
and correctly placed at `fact_badge.row_labels`, and every consumer that goes through
`row_labels` is genuinely gated. But `row_labels` is not the single producer the design
assumed: the chat door and the review-queue door serve the raw `verification_status`
column, the suppression marker never survives serialization on *any* wire, and the scans
that were supposed to make the property structural do not fire on a new bypassing path.

## Clause 1 — "serves as candidate on every door": refuted on two doors, measured

Enumeration of every path a verification status reaches a reader, and what each serves
with the gate closed:

| Door | Path | Status served |
|---|---|---|
| REST facts list/detail (`/api/v1/knowledge/facts`) | `facts_read._base_item` → `row_labels` | `candidate` — **gated** (measured) |
| MCP `fact_get` | same `facts_read.get_fact` | gated |
| Knowledge search, REST + MCP (`labels` block) | `layer_composition._badge_labels` → `row_labels` (overwrites `_labels`' raw copy in the merge at `layer_composition.py:966`) | gated |

| Frontend | facts tab / fact detail render the (gated) REST field; no badge re-derivation found | clean in itself, but the chat panel renders the leaked raw status the backend hands it |

### The chat drill (run, not argued)

Drove `ChatService._chat_context` with a composed `corroborated` fact and no record:

```
chat fact payload status: corroborated
AssertionError: chat serves the RAW promoted status off
ComposedRow.verification_status while the gate is closed
```

Root cause: `compose()` stamps `ComposedRow.verification_status = candidate.verification_status`
(the DB column, `layer_composition.py:951`) *alongside* the gated `labels` dict, and
`chat.py:401` reads the attribute rather than the labels. This payload is persisted into
`messages.context` — so raw promoted statuses served today will still be on disk after the
leak is fixed — and rendered by the chat context panel. The parity test that would have
caught it (`test_a_fact_reaches_the_prompt_with_its_claim_verbatim`) was given the
`cleared_promotion_record` fixture, which opens the gate and masks the leak.

### The review-queue drill

Seeded a `corroborated` fact with `review_state='open'`, `demotion_pending_since=NOW()`:

```
review-queue item status: corroborated
```

### "a test drives both doors"

Not delivered. All 16 (now 22) tests in `test_claim_serving_gates.py` are unit-level on
`row_labels`/`served_status` plus AST scans; none drives an HTTP or MCP door with the
gate closed. Every door-level test in the suite that meets a promoted status takes
`cleared_promotion_record` — the fixture is correct for what those tests are about, but
it means suppression is tested at **zero** doors.

## Clause 2 — the grounded half: a deferral recorded as a property

The honest state: the groundedness *gate* does not exist. `claim_gates.py` says so itself
("The article path asks the judge directly when it is built (T3.02 / T3.23)") and the
reasoning for not importing the qualification record into a second module is sound. But
the clause demanded a scan proving no path can serve the label, and what exists is
`test_no_article_path_serves_a_grounded_label_today`, which globs `app/services/*.py`
(one directory, non-recursive) for the *literal* `'"grounded"'`. Measured:

- a new **route** file serving `{"verification_status": "grounded"}` left the suite green
  (the glob never looks outside `services/`);
- any serving path that reads the status off a DB row spells no literal and can never
  trip it — which is exactly how every real serving path in this codebase works.

Two deeper problems, by inspection:

- **`VerificationJudge`'s refusal gates the derivation, not the serving.** The judge
  refuses to *judge* without qualification, so an unqualified judge can't compute
  coverage. That is the derivation side — precisely what T2.95's own doctrine says a
  serving gate must not rely on.
- **When T3.02 lands, the article label lights on the wrong record.** Doc 09 §4.3 ships a
  grounded article as `status='corroborated'`; `row_labels(id_kind="article", ...)` runs
  the same `served_status`, whose only gate is G-C's *promotion* record. An article's
  claim is certified by G-D's judge qualification, so minting the fact record would light
  the article label with the article evidence still absent. Nothing in the module keys
  the gate on `id_kind`. (Inference from doc 09 §4.3 + code; no article producer exists
  to measure yet — which is itself the point.)

## Clause 3 — suppression visibility: dies at every serialization boundary

`row_labels` emits `label_suppressed` — and no wire schema carries it:

- `FactListItem` and `FactDetailResponse` (`schemas/facts.py`) declare no such field →
  FastAPI's `response_model` and MCP's `model_validate` drop it silently. Measured on the
  live REST door: item keys end at `unverified`/`verification_status`.
- `ComposedRowLabels` (`schemas/knowledge.py`) — same, on both knowledge doors and
  everything chat reads through `row.labels`. Pydantic's default `extra='ignore'` means
  construction succeeds and the key vanishes (measured).

So on every door a suppressed row and a genuine candidate are byte-identical (modulo the
`tier` leak of clause 1) — the "silent downgrade" the task names verbatim as the failure.
This is the third occurrence of the same schema-drop failure mode in this file's history
(the `unverified` drop is documented in `test_facts_read_surface.py`); a test asserting
the *wire* rather than the producer would have caught it.

## Clause 4 — reversibility

The fact half holds where it was tested: `test_minting_a_record_lights_the_label_with_no_code_change`
re-reads the producer, and the review verified independently that the gate reads the
record per call (no import-time memoization; a path redirect and a minted file both take
effect immediately, and deleting the record re-closes the gate on the next call — the
default-argument bug the commit describes fixing is genuinely fixed). Two caveats: the
proof re-reads `row_labels`, not any door, and "both surfaces" cannot be satisfied —
there is no article gate to light. Note also the cost shape: `served_status` runs one
`exists()` + `open()` + `json.load` per fact row per request; harmless today, but a
hundred-row list is a hundred file reads.

## Clause 5 — the scans: a snapshot, not a guard

Measured: with a **new** module `app/services/facts_export.py` emitting
`{"verification_status": "corroborated"}` as a dict literal, the entire scan suite passed
(60/60). `test_no_serving_module_writes_a_promoted_status_itself` enumerates exactly two
filenames (`facts_read.py`, `layer_composition.py`); a third file is invisible to it. By
inspection it is also shape-evadable *inside* those two files: it matches only
`ast.Dict` nodes with `ast.Constant` keys and values, so `dict(verification_status="corroborated")`,
a variable-valued entry, or an attribute assignment all pass. And the two real bypasses
that exist **today** — `chat.py`, `review_queue.py` — are not in its file list.

The scans also inherited the recorded text-matching trap in both directions:
`test_this_module_never_reaches_the_judge` is substring matching (evadable via
`importlib`, fires on prose), and the grounded glob fires on any quoted "grounded" in a
services docstring while missing every non-literal serving path.

## Attack 4 — eligibility, staleness, caching, fail-closed

- **Fixed (`b8bf060d`): eligibility was truthiness.** `record.get("gate_eligible")` opened
  the gate on the strings `"INTERIM"`, `"false"`, `"no"`, and on `0.8182` — the exact
  branding failure the module's own docstring names as its reason to exist. Now
  `is True`; pinned by a parametrized test; mutation-drilled (revert → 5 failures →
  restore → green).
- **Fixed (`b8bf060d`): invalid UTF-8 crashed the read path.** `UnicodeDecodeError`
  escapes the file *read* inside `json.load` and is not a `JSONDecodeError`; uncaught, it
  500'd every fact read — candidate rows included. Now caught via `ValueError`; pinned;
  mutation-drilled. The other constructions checked: absent file, empty file, corrupt
  JSON, non-dict JSON, a directory at the path (`IsADirectoryError` ⊂ `OSError`), and a
  permissions error all fail closed. None fails open.
- **Unfixed, controller-level: the record binds nothing.** Any dict with
  `"gate_eligible": true` — whatever corpus, model, date, or judge minted it, however
  stale — opens the gate. T2.40 owns the minting run; until its record schema is fixed
  (and validated here), "eligible" means "a file said yes". The gate should refuse a
  record that does not name the gold version and model it was measured against, and
  T2.40's schema should be co-designed with this check.
- **Caching: clean.** Read per call; no restart needed to light or extinguish.

## What was tried and did not break

- Redirection/memoization attacks on the record path (monkeypatch, delete-after-open,
  fresh-file-after-closed-read) — the gate tracked the filesystem every time.
- `confirmed` suppression regressions, `disputed` and `None` pass-through, badge
  suppression alongside a withheld status — all behave as documented.
- The REST facts and MCP `fact_get` doors' *status field* — genuinely gated.
- The frontend does not re-derive badges from raw statuses; the SPA's own surfaces render
  what the backend serves (which is why the backend leaks matter).
- `pin_suggestions` and ranking consume promoted statuses internally — derivation, which
  the module's doctrine explicitly permits.

## Is it safe to build T2.28 on this gate today?

**No.** T2.28's premise is "with T2.95's serving gate in place, the claim is in the badge,
not the derivation." That premise holds on exactly two doors (REST facts, MCP `fact_get`)
and fails on chat, on the review queue, on the `tier` field of both knowledge doors, and
on suppression visibility everywhere; and the scans give no protection against T2.28
adding one more serving read wrong — measured, a new bypassing module leaves the build
green. Building T2.28 now would stack a second labelled surface on a producer that is not
yet the single producer. The load-bearing sentence of the M1 split — *no serving path can
reach a label whose evidence does not exist* — is currently false, which per the brief is
a controller decision and a probable Tier-3 amendment, not something this review may
patch around.

**The repair is bounded, though.** Nothing here indicts the design — enforcement at the
producer is right; the defects are that two consumers dodge the producer, one attribute
duplicates what the labels already carry, three schemas drop a field, and two scans
enumerate instead of quantify. A fix task should: (1) make `chat.py` read
`row.labels["verification_status"]` and make `review_queue` route its fact arm through
`row_labels` (or serve the gated pair explicitly); (2) decide `tier`'s semantics under
suppression (recompute off the served status, or document the leak as ranking-only and
strip it from the wire); (3) add `label_suppressed` to `FactListItem`,
`FactDetailResponse`, and `ComposedRowLabels`, with a wire-level test; (4) rewrite both
scans to walk `app/` structurally (routes and MCP included) and assert the *absence of
any `verification_status` emission that does not originate in `row_labels`*, which is the
only shape that fails on the next new path; (5) drive at least one REST and one MCP door
with the gate closed, no fixture; (6) key the gate on `id_kind` so the article surface
cannot light on the fact record, and validate the record's binding fields with T2.40.
