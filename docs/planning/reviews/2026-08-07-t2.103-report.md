## 2. The `auth_lockout` decision: it gains an emitter

**Decision: emitter added, not removed from the vocabulary.**

Reasoning, per the brief's instruction to find out which is true rather than pick the
cheaper option:

- The lockout mechanism (`login_rate_limit.py`) is real, live and already tested
  (`test_login_locks_out_after_repeated_failures`) — this is not a stale, unimplemented
  feature.
- `GET /auth/audit` exists specifically to give an operator visibility into
  brute-force activity. A lockout is the single most security-relevant event the auth
  surface produces; leaving it unjournaled while every failed guess *is* journaled is a
  visible hole in exactly the surface this task is repairing.
- The value already sat in `EVENT_TYPES` with no writer — the "scaffolding, not
  substrate" shape invariant 23 exists to catch, and the brief names this exact
  possibility as the one to check for rather than assume away.

**Where it fires.** Inside `auth_login`'s failed-password branch, immediately after
`login_rate_limiter.record_failure(ip)`:

```python
retry_after_now = login_rate_limiter.retry_after(ip)
if retry_after_now is not None:
    await _record_audit("auth_lockout", {"ip": ip, "retry_after_seconds": retry_after_now})
```

The route's own `retry_after` gate at the top of the handler already proves the IP was
*not* locked when this request started (a locked IP is rejected with 429 before reaching
the password check at all). So a non-`None` `retry_after` right after `record_failure()`
can only mean this exact failure is the one that crossed `max_failures` — the transition,
not the steady locked state. This is why the third (already-locked) attempt in the test
does not add a second `auth_lockout` row: it never reaches this branch, because it 429s
at the top of the handler instead.

This required no change to `login_rate_limit.py` — no new return value, no altered
threshold logic, no altered lockout duration. `LoginRateLimiter` is untouched; the scope
boundary ("does not touch authentication behaviour, rate limiting, or the lockout
policy") is respected because the audit write reads existing state
(`login_rate_limiter.retry_after`) rather than changing what triggers a lockout or how
long it lasts.

**Proof it fires at the transition, not just that the constant exists**
(`test_lockout_transition_is_journaled`, `backend/tests/test_login_rate_limit_route.py`):
with `max_failures=2`, the first failed login adds no `auth_lockout` row (count unchanged
from baseline), the second failed login adds exactly one, and a third attempt — now
rejected at 429 before the password check — adds none. Counts are taken relative to a
baseline read at test start rather than asserted as absolute zero/one, because `events` is
append-only and `_record_audit`'s writes are genuinely committed (not rolled back by the
test transaction), so sibling tests in the same file leave real `auth_lockout` rows behind
across the run.

## 3. The scan (`backend/tests/test_events.py`) — shape and what it misses

**The deliverable claim:** no `record_event` call anywhere in `backend/app` — directly, or
through a one-hop wrapper — may name a value outside `EVENT_TYPES`, enforced as a build
failure rather than the runtime warning `record_event` itself logs.

**Two call shapes, both traced:**

1. **Direct** — `record_event(..., event_type=<literal-or-resolvable>)`. The value may be
   a string literal, a bare name/attribute resolving to a module- or class-level
   `NAME = "literal"` assignment anywhere in `backend/app` (fails safe — a same-named
   constant in an unrelated file only adds a spurious candidate, never hides a real one),
   or a `<dict>.get(key, default)` read off a dict literal (`relational.py`'s
   `_ACTION_EVENT_TYPE`).
2. **Indirect, through a wrapper** — a function whose own body calls `record_event` (or a
   previously-discovered wrapper), forwarding one of *its own parameters* as
   `event_type`. `_record_audit(action, details)` at `app/api/routes/auth.py:31` is the
   instance the brief named: its call sites (`_record_audit("auth_login_failed", ...)`,
   `auth.py:103`) carry no keyword literally named `event_type` at all, so a scan that
   only matches that keyword at `record_event` itself never even inspects them — exactly
   the miss that let the whole auth family ship outside `EVENT_TYPES` with nothing
   failing. `supersede.py`'s `_journal(..., *, event_type, ...)` is the other live
   instance, forwarding its own **keyword-only** `event_type` parameter straight through.

   Wrapper discovery is generic, not hardcoded to either function's name: any function
   under `backend/app` whose body calls an already-known emitter, passing one of its own
   parameters (positional-or-keyword, or keyword-only — both are checked, since
   `_journal`'s parameter is keyword-only and can never be bound positionally) as
   `event_type`, is itself registered as an emitter. The registration loop runs to a
   fixed point, so a second layer of indirection introduced later would be traced too
   rather than silently missed, at no extra cost against the two levels the codebase has
   today.

**What the scan cannot see**, stated in its own module docstring: an event type assembled
at runtime (an f-string, string concatenation, a value read from config or the database)
resolves to nothing and is silently absent from the `emitted` set — a static AST scan has
no way to evaluate it. None exist in the codebase today. A wrapper whose forwarded literal
travels under a parameter name that is *never* the one actually used at any of its own
call sites (always some third name) would also be missed; no such shape exists today
either. Two call sites remain permanently unresolved by design and are pinned in
`_EXPECTED_UNRESOLVED` with reasons: the inner `record_event(..., event_type=action)` in
`_record_audit` and `record_event(..., event_type=event_type)` in `_journal` — both are
the *wrapper's own* un-traceable inner node; the literals are found instead at each
wrapper's call sites, which is what the drills above and
`test_auth_family_resolves_through_the_record_audit_wrapper` prove actually happens.

## 4. The audit-door regression clause — driven, not reasoned about

`test_audit_surfaces_every_real_auth_route_at_the_door`
(`backend/tests/test_audit_endpoint.py`) drives the real routes rather than asserting
anything about the `LIKE 'auth\_%' OR LIKE 'setup\_%'` filter directly:

1. `POST /api/v1/setup` (trust-on-first-use, no prior admin password) → `auth_setup` then
   `setup_complete` on the one request session.
2. `POST /api/v1/auth/login` with the correct password → `auth_login_success`.
3. Two `POST /api/v1/auth/login` calls with the wrong password, `login_rate_limiter`
   monkeypatched to `max_failures=2` → `auth_login_failed` on both, `auth_lockout` on the
   second (through `_record_audit`'s independently committed session, not the request
   session the door itself reads through).
4. `POST /api/v1/auth/logout` and `POST /api/v1/auth/change-password`, each with its own
   freshly minted token (independent of cookie-jar state or of a token blocklisted by an
   earlier step) → `auth_logout`, `auth_password_change`.
5. `GET /api/v1/auth/audit?limit=100` with a fresh token → asserts all seven literals
   above appear in the returned `action` set, exact spelling.

Result: `1 passed` (full file output below). This is the "same rows before and after"
proof: nothing about spelling, vocabulary membership, or the split between the two
sessions the auth routes use (`request session` vs. `_record_audit`'s own) silently drops
a row out of the security surface.

## 7. What the plan got right / anything it missed

The brief's own text already anticipated the one real design risk (the wrapper-shape
scan) and named the exact call site (`auth.py:103`) precisely — no surprises there. Two
things worth recording for whoever reads this next:

- The brief's Verify command (`test_events.py` + `test_event_taxonomy_map.py`) does not by
  itself exercise the `auth_lockout` emitter or the audit-door regression clause — both
  live in `test_login_rate_limit_route.py` and `test_audit_endpoint.py` respectively,
  which Done-when clauses 2 and 3 require but the stated Verify command does not name. I
  ran and reported both anyway since the Done-when checkboxes require them; a future
  brief for a similarly-shaped task might want its Verify line to say so explicitly.
- `test_event_taxonomy_map.py`'s own "live" definition (a literal reachable through a
  keyword literally named `event_type`) structurally cannot see `auth_lockout` even after
  this task wires up its emitter, because the literal travels through `_record_audit`'s
  positional `action` parameter, never through a keyword named `event_type` at any
  resolvable site. That guard therefore still does not *require* `auth_lockout` to be
  classified in the frontend map — I classified it anyway (ahead of what that guard would
  force), and updated its module docstring so this asymmetry is documented rather than
  read as "still unemitted."
