## Findings

### F1 — Important. The production registration has no test that can fail on its removal.

`backend/tests/test_code_deriver.py:1435` (`test_main_registers_the_code_deriver_job`)
asserts three substrings over `inspect.getsource(app.main)`. All three appear in the
**import lines** (`app/main.py:225`, `241-246`). Measured: I deleted the entire
`job_registry.register(Job(key=CODE_DERIVER_JOB_KEY, ...))` block
(`app/main.py:308-323`) while leaving the imports, and ran
`test_code_deriver.py + test_jobs_route.py + test_job_registry.py`: **116/116 passed**,
the registration test included. The `--full` e2e suite asserts no job roster either.

Why it matters: the end-to-end test builds its *own* `JobRegistry`, so it proves the
runner and constants, not the app wiring; the wiring is exactly what "production path"
means, and losing that block in a merge or refactor (imports lingering) recreates the
"writer exists, production never reaches it" state this task exists to close — with
zero red tests. That is a substring assertion satisfied by something other than the
thing it names, the same trivially-holding shape this corpus keeps hunting.

Mitigation, stated fairly: the test is a line-for-line mirror of
`test_main_registers_the_code_reconcile_job` (`test_code_reconcile.py:75-85`) — the
precedent the brief itself pointed at — so `code_reconcile` and by inspection
`ppr_snapshot` carry the identical exposure. This is a pattern-inherited weakness, not
a T2.96 invention. But T2.96's whole reason to exist is production reachability, which
makes the vacuous guard load-bearing here in a way it is not for reconcile.

Fix shape: assert against something that dies with the block — boot the lifespan and
read the real registry's `get(CODE_DERIVER_JOB_KEY)`, or AST-scan `app/main.py` for a
`register` call whose `key` binding is `CODE_DERIVER_JOB_KEY` (the RRF scans are the
in-repo precedent for checking bindings, not text). Retrofitting the reconcile and
ppr_snapshot twins at the same time would close the class, but that is the
controller's call.

### F2 — Minor. The exactly-once assertion is over-strict and will false-fail on a legitimate co-asserter.

`test_code_deriver.py:1565-1572` asserts `max(cardinality(repo_ids)) == 1` over rows
containing the repo id. Cardinality counts *all* elements, so the assertion actually
proves "this repo is the array's sole occupant", not "this repo appears exactly once".
Today those coincide (the test's repo is the only asserter of its entities, and a
duplicate would still force cardinality ≥ 2, so the brief's property is genuinely
proven). But the moment any neighboring committed test legitimately shares an entity
(`sqlalchemy`, `fastapi` are global `(name, entity_type)` keys), this flakes. A
per-id occurrence count — `(SELECT count(*) FROM unnest(repo_ids) u WHERE u = :rid)`
— asserts exactly the brief's property and nothing more.

### F3 — Minor. A `resolve()` failure on the success path records a phantom failure.

`job_runners.py:172-178`: derivation commits, then `resolve` runs and commits
separately. If `resolve` itself raises (connection drop between the commits), control
lands in the `except`, which records a *failure* row for a repo whose derivation just
committed successfully. Self-healing — the next tick's successful run resolves it —
and the window is two adjacent statements, so Minor. Folding `resolve` into the same
commit as the derivation would remove the window.

### F4 — Minor. The double-fault degrades to logs only.

`job_runners.py:184-193`: if `record` itself fails, the derivation failure surfaces
only via `logger.error`. Consistent with how `record_event` degrades elsewhere, and
reaching it takes two independent failures; noted for completeness because the brief
made surfacing a requirement.
