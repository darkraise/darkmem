### Q1 — the qualification: three ordinary shapes are uncovered and unlisted

Probed by this review inside a serving module (one that calls `row_labels`), all MISSED:

1. **`FactListItem(**row)`** — the constructor-flavoured wholesale copy. The `**`-unpack is

2. **`FactListItem.model_validate(row)`** — the standard pydantic-v2 serialization idiom.
   A positional call argument; no rule looks at it.
3. **`payload.update(row)`** — the positional, wholesale `update`. The table lists both
   `update` *keyword* shapes as caught; the wholesale one appears nowhere.

(Also in-family: `payload |= row` and `payload | row`, and a *synchronous* call-result copy
`dict(row_for(fid))` — the last is within stated shape 13's admission, and its awaited
twin `{**(await repo.get_fact(fid))}` correctly fails closed, which covers most real repo
reads.)

None of these is author-adversarial; each is ordinary route code, and 1 and 2 are exactly
how a lazy serving surface serializes a row. So the report's framing — four adversarial
misses plus shape 17 as "the one accidental miss" — is falsified. What survives, measured:
the primary T2.28 idiom (constructor *keyword*) is caught, the dict-flavoured merges a
route actually writes (`{**row, **labels}`, `dict(row)`) are caught, and every one of the
three misses above is covered by the same protection as shape 17 — **a door drive with the
gate closed**, which T2.28's acceptance already requires. The scan extension is small if the
controller wants it (treat `arg=None` unpacks, `model_validate`, and positional `update` as
wholesale copies); the cheaper correct move is to name all three in T2.28's brief beside
shape 17.

### The honesty-guard respelling — sound, and the hazard is recorded where it will be met

Reproduced both ways. Respelling the filter back to the house idiom
`verification_status = ANY(CAST(:v AS text[]))` turns
`test_exactly_the_permitted_writers_touch_the_verification_axis` red, classifying
`KnowledgeTripleRepository.list_live` as a third writer of the axis — and the guard's own
failure message argues, correctly, why a third writer is refused rather than allowlisted.
The mechanism was re-derived: `_sql_assigns_column` classifies a binding by the nearest
clause keyword *within the same string constant*, and `list_live` assembles its conditions
as bare fragments joined later, so its fragment carries no `WHERE` and reads as a write —
exactly the shape the one real writer uses for its SET list (`pin_suggestions`' one-string
SQL carries its own `WHERE` and is classified as a filter by the same rule, which is why it
never tripped). The shipped `IN (SELECT unnest(CAST(:v AS text[])))` is semantically
identical to `= ANY` for a `text[]` (`NULL` matches neither; the empty array matches
nothing in both) and is not an assignment shape in any reading. The report's proposed
narrowing for the guard's owner is also correct as stated: `SET col = ANY(...)` is a
PostgreSQL syntax error, so `= ANY(` genuinely can never be a write. The constraint is
recorded in a comment at the site and the report names the cheap-looking fix as the
allowlist it is; the next person who meets the guard has what they need to not weaken it.
