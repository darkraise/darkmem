## What shipped

`backend/app/services/entity_merge.py` — a Tier-C pass, registered as the job
`repo_entity_merge` (cron `50 * * * *`, `min_interval_seconds=300`,
`max_run_seconds=900`, one knob `candidate_batch` defaulting to 200, 0 disables).

The pass re-runs Phase 4's comparison after the fact. Candidates are the
repo-asserted entities (`COALESCE(cardinality(repo_ids), 0) > 0`) that already carry a
vector under the fingerprint `resolve_read_fingerprint` says holds data; the probe is
`find_similar_entity` at `MERGE_THRESHOLD = 0.85` under `names_distinct`. There is no
second similarity path and no second threshold.

**The query vector is read out of the partition, never re-embedded.** That is the
invariant-2 answer to the brief's rotation question, and it is structural rather than a
promise: both sides of every cosine come out of the same child table, so a
cross-fingerprint comparison is not expressible. The pass writes no vector at all, so an
embedder rotating between the fingerprint resolution and the merge cannot mix two
geometries into one table — the rows it writes are graph rows, which carry no
fingerprint, and the rows it removes are the loser's, removed by the
`entity_embeddings__<slug>.entity_id` `ON DELETE CASCADE`, which reaches *every*
fingerprint's partition rather than the one that happened to be active. The decision
itself ("these two names denote one node") is name-semantic and survives a rotation. A
corollary worth stating: this pass needs no embedder call, so the orchestrator is asked
only to name a partition.

## The survivor rule, and what actually references `entities.id`

**I established the references before choosing, and something does reference them.**

| Referencing | Kind | Handled by |
|---|---|---|
| `entity_relations.source_entity_id` / `target_entity_id` | FK, `ON DELETE CASCADE` | repointed explicitly, then a guard refuses if any remain |
| `entity_embeddings__<slug>.entity_id` | FK, `ON DELETE CASCADE` | cascade, in every partition |
| `knowledge_triples.subject_id` / `object_id` | **UUID column, no FK** | repointed by the merge |
| `ppr_snapshot` node ids | in-process only, rebuilt on cron | nothing owed |
| `chat.selected_entity_id`, `get_neighbors_by_id` | request-scoped, never persisted | nothing owed |

`knowledge_triples.subject_id` is the one that mattered. `fact_lift` writes it (both the
memory-asserted `_PENDING_GROUPS` path and `_REPO_ASSERTED_RELATIONS`), and
`review_ranking`'s salience arm joins it against `entity_relations`. Its own docstring
says a NULL or dangling `subject_id` "reads as zero salience, which is a degradation in
one direction only" — silent, permanent, and exactly what deleting the losing row would
cause. So the merge repoints both columns rather than leaving them to rot. **So the
choice was not cheap by default; it became cheap once the repoint was in.**

With the repoint in place, no reference constrains which side survives, so the rule was
chosen on convergence instead:

> **The repo-asserted row survives. If both are repo-asserted, the older `created_at`
> survives, with the smaller id as tie-break.**

The eager order already canonicalises the memory-minted name onto the pre-existing
repo-minted one, so a retroactive pass that kept the memory-minted row instead would
trade an order-dependent node *count* for an order-dependent node *name* — the same
defect class in a different column. The tie-break is the supersession detector's shape
and exists so the outcome cannot depend on which side of the pair the scan reached
first, which is also what makes the pass idempotent. Both arms are tested from both
sides (`test_the_repo_asserted_row_survives_whichever_side_is_named_first`,
`test_two_repo_asserted_rows_break_the_tie_on_age[postgres|postgresql]`,
`test_equal_timestamps_fall_through_to_the_id_tie_break`).

The **user-visible consequence** is worth naming: after a merge the graph holds the
repo-minted name (`postgres`) and the memory-minted one (`postgresql`) is gone, so a
memory's `technologies` array and the UI's label both move. That is what the eager order
already produces, and it is the price of order-independence.

## Relation-endpoint collisions

`entity_relations` is UNIQUE on `(source_entity_id, target_entity_id, rel_type)`, so
repointing an endpoint onto the survivor can collide. That case is a relation merge:
union `memory_ids` and `repo_ids[]`, `GREATEST` the weight, merge properties with the
keeper's keys winning, delete the duplicate. It is never left for the constraint to
raise, and the duplicate is never simply dropped — that would lose whichever memories
only it asserted.

Three mechanics that took care:

- **Both directions.** A relation *into* the loser is as dangling as one out of it. Both
  endpoints are rewritten, and a drill that left `target_entity_id` alone goes red.
- **The collision partner is always locked.** The new key always contains the survivor,
  so the partner is always one of the survivor's incident edges. The pass locks *both*
  entities' incident edges `FOR UPDATE ORDER BY id`, not just the loser's.
- **The partner may be an edge this same loop already moved.** The collision lookup is
  re-queried per edge rather than read from the opening snapshot, and the fold's array
  unions are computed in SQL against the keeper's *current* row. Covered by
  `test_two_edges_collapsing_onto_one_self_loop_fold_together`.

**A loser-to-survivor edge becomes a self-loop, kept rather than dropped.** This is a
judgement, and the argument is convergence again: Phase 4 canonicalises both endpoint
names onto one and Phase 5's `create_relationship` then resolves both to the same id, so
the eager order already produces self-loops. Deleting them retroactively would make the
two orders disagree in a different column. The consumers that would be confused by one
(`ppr_snapshot`, `review_ranking`'s salience arm) already exclude self-loops.

## The other things that move

- **`memory_ids` / `repo_ids[]`** — union, appended rather than re-sorted, so the
  survivor keeps the assertion order `array_append` gave it.
- **`memories.technologies`** — recomputed through `technologies_for_memory` (the same
  single definition Phase 5 writes from) for every memory in the union, guarded by
  `IS DISTINCT FROM` so an unchanged array does not bump `updated_at` through the
  `touch_updated_at` trigger. The recompute is **skipped whole when the merged type is
  not in `TECH_TYPES`**, and that is an equivalence rather than a shortcut: the
  projection filters on that set, so neither name could appear in any array. Tested
  (`test_merging_a_non_tech_type_leaves_every_memory_row_alone` asserts `updated_at` is
  untouched).
- **`properties.display_name`** — the survivor's keys win; a `display_name` that does not
  lowercase to the surviving name is dropped rather than adopted. Adopting the losing
  `postgresql` row's `"PostgreSQL"` onto a surviving `postgres` row would make
  `memory_community_labels` render a name the graph does not hold (invariant 7).
- **The losing row's vectors** — through the partition cascade, in every fingerprint.

## Atomicity, and the guard that is not optional

Each pair merges inside one `async with self.session.begin_nested()`, the idiom
`assert_from_repo` already uses, so a failure rolls back to two intact nodes. The outer
loop catches per-pair failures, logs, and continues.

The load-bearing guard: **before deleting the loser, the pass counts relations that
still reference it and raises `EntityMergeRefused` if any remain.** Without it the FK
cascade would do the cleanup — no error, no symptom, another memory's edge simply gone.
Drilled (D5).

## `find_similar_entity` gained one optional argument

`exclude_entity_id: str | None = None`. A stored row's nearest neighbour is itself at
cosine 1.0, and `LIMIT 1` returns nothing else, so self-exclusion is intrinsic to
probing from an existing row. Phase 4 passes no such argument — it probes with a fresh
name that has no row yet — so the write path's query is byte-identical. This is the one
edit outside the new module's own files besides wiring; the brief's "reuse
`find_similar_entity`, do not write a second similarity path" is why it was done this way
rather than by adding a second query.
`tests/test_dedup_discriminator.py::spy_probe` was widened to forward the new keyword.

## What the plan got wrong, or did not say

1. **The brief says the losing entity's partition rows "must go with it, per
   fingerprint".** They do, but not by any code in this pass: the FK cascade on
   `entity_embeddings__<slug>.entity_id` handles every partition. Doing it explicitly
   would require enumerating fingerprints and naming child tables, which is *more*
   invariant-2 exposure, not less. Asserted rather than assumed
   (`test_the_losing_rows_vector_goes_with_it`).

2. **`entity_embedding_cache__<slug>` is deliberately left alone.** It is keyed on
   `name_lower` with no FK, so the losing name's cached vector survives the merge. That
   is correct and desirable: Phase 3 reads that cache by name before spending an embed,
   so a future memory naming `postgresql` gets back the identical vector, and Phase 4
   then finds the surviving `postgres` at 0.974 and canonicalises onto it — the eager
   path, working. Purging the cache entry would cost a fresh embed that might land on
   the other side of the threshold.

3. **A repointed relation's `relation_embeddings__<slug>` vector goes stale**, because
   that vector is `"<source name> <rel_type> <target name>"` and the source name just
   changed. This is exactly the drift `relation_embeddings`'s **rotation arm** exists
   for (T2.49: "the backstop that makes renames converge... a drifted vector is
   corrected within one full rotation rather than never"), so the existing mechanism
   covers it and I did not add a second one. A *folded* duplicate's vector is deleted by
   the `relation_embeddings.relation_id` cascade immediately. Worth knowing rather than
   worth fixing here — but it is a real, if bounded, staleness window, and it is not
   mentioned in the brief.

4. **The arm does not drain to zero.** Unlike the anchoring job's exact arm, this one
   re-probes every repo-asserted entity with a vector on every run; a run that merges
   nothing is the healthy steady state. The cost is one HNSW `LIMIT 1` probe per
   candidate per tick, bounded by `candidate_batch`. The knob's help text says so. An
   alternative — a persisted cursor, or coupling to what the anchoring job just embedded
   — would add state for a cost that is already small, and I judged that not worth it.
   Flagging it because "does not drain" is the shape the anchoring job's schema help
   text explicitly contrasts itself against.

5. **`progress.md` was not touched.** This branch's copy carries no `T2.9x`/`T2.101`
   rows (progress is canonical on `master`, per runbook §6), and three other lanes are
   live. The controller owns that row.
