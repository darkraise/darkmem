### The five dispatch points

**1. Can the two counting-only guards pass vacuously? Can the AST scan be evaded?**
Neither guard is vacuous. The byte-comparison test asserts `any(g.size == 2)` before
comparing snapshots (`test_triple_embeddings.py:240`), so it cannot pass on a run that
found nothing; my DB drill confirmed the snapshot detects a value-changing `triple_key`
rewrite (falsifiable), and the scan replay confirmed the implementer's literal-`UPDATE`
drill does red both scans. But the scans **can** be evaded — demonstrated, not
conjectured, in the replay driver:

- `f"UPDATE {_KT} SET ..."` with the table name in a variable — verb and table never
  co-reside in one string literal, scan stays green. This is the module's **own local
  style** (`f"INSERT INTO {table}"` at `:185`), so a future editor would reach for it
  naturally, not adversarially.
- `stmt.values(triple_key=None)` — `ast.keyword.arg` is neither `Name`, `Attribute`
  nor `Constant`; the `triple_key` scan stays green.
- An indirect call into another module's writer carries no forbidden token at all.

The byte-comparison is the backstop for all three — **but only on the `group_facts`
path**. `embed_facts` has no byte backstop: its tests snapshot nothing, so a
non-literal `knowledge_triples` write added there passes every guard. See finding I1.

**2. Complete linkage — verified implemented, no transitive fallback.** The
non-transitive triple was re-derived from `relations.py:81-103` independently
(`gpt-4`~`gpt4` False, `gpt4`~`gpt4 turbo` False, `gpt-4`~`gpt4 turbo` True).
`_agglomerate` (`triple_embeddings.py:408-437`) merges two components only when
`all(may_group(x, y))` over the full cross-product (`:427`); there is no union of
components without that check, no path around it, and the singleton-completeness
branch (`:377`, `:419-420`) never merges. My driver fed it the adversarial pair set
*including* the distinct pair at the highest similarity and in both merge orders —
`gpt-4` and `gpt4 turbo` never landed together — while a union-find over the same
pairs and the same guard merged them. The end-to-end test (`:366-382`) pins the same
shape through the DB, and the pure-function pin (`:346`) will red a future
"simplification" to union-find.

**3. Fingerprint discipline — clean.** Every child-table name goes through
`child_table(PARENT_TABLE, ...)` (`:181`, `:283`, `:312`), pinned by the scan at
`test_triple_embeddings.py:464-476`. The writer's fingerprint is
`embed_batch_chunked`'s return value — an actual vector's length, on which `model|0`
is unrepresentable — and I verified the real orchestrator signature
(`llm.py:238-243`) matches the fake's shape positionally, since no production caller
exists to catch a mismatch. The read side delegates to `resolve_read_fingerprint`,
which is data-resolved and raises rather than guessing; a bare `llm_fingerprint()` is
scan-forbidden in the module (`:479-492`). No query joins across fingerprints;
`similar_facts` joins one child table to `knowledge_triples`, which is not a
cross-fingerprint join. Two advisory residuals ride as M3/M5.

**4. `_ensure_partition` committing the caller's session — the right call here, and
better than the alternative.** The codebase has *two* idioms, not one:
`pipeline._register_fingerprint` (`pipeline.py:261-275`) registers in a **fresh**
session, while `reembed.py:630-641` and `code_pipeline.py:1408-1419` pass the caller's
live session under the same `_ensure_partition` name and shape. T2.33 matched the
latter — and here the fresh-session idiom would be actively wrong: the triple child
table's inline FK `REFERENCES knowledge_triples` needs a lock on the referenced table
that conflicts with the `RowExclusiveLock` a caller holds on its own uncommitted fact
inserts, so a second session's DDL would block against the very transaction waiting on
it (and deadlock the test suite's outer-transaction pattern outright). The residual is
documentation, not design: `embed_facts` commits the caller's transaction mid-call on
first contact with a new fingerprint, its docstring never says so, and conftest's
savepoint pattern means that commit is never exercised as a real commit by any test
(M2).

**5. Is "the writer ships" honestly satisfied? Yes — with one wording shade and one
obligation to hand forward.** The Done-when never demanded a consumer; the task was
marked terminal-by-design before execution and the brief ordered no widening. The
two-step is this corpus's own pattern — the template landed inert ahead of its writer
(T0.13), the writer now lands tested ahead of its caller (T2.11) — and the prose
surfaces are honest exactly where the epic's prose-versus-graph gaps have bitten:
`facts_channel.py` calls it "a wiring gap rather than a missing substrate" and still
reports the semantic arm present-and-not-run; the gate ledger makes **no** claim the
miss rate is addressed; progress.md names the unwired caller as the open item. The one
shade is the inventory's status cell "**written since 2026-08-05**" (M4) — the
partition *can be* written and nothing writes it in production. The obligation: T2.52
justified the writer; nothing yet measures that the ANN arm **recovers**

(T2.11's lineage), and its brief should carry it explicitly — until then, nobody may
read T2.33's landing as the 41.7% having improved.

### Findings

**I1 — Important. The counting-only enforcement is weaker than its own claim, and
`embed_facts` sits outside the byte backstop.**
`triple_embeddings.py:19-21` claims the tests "fail the build on any other verb
reaching that table from here"; `test_triple_embeddings.py:426-461` delivers less, in
three demonstrated cells (point 1 above): interpolated table name, `triple_key` as a
keyword argument, indirect write through an imported helper. On the `group_facts` path
the byte-comparison closes all three; on the `embed_facts` path nothing does. Failure
it produces: a future `knowledge_triples` write added to `embed_facts` in the module's
own f-string style ships green — the exact silent data-mutation this invariant exists
to make loud. Cheap closes, any subset: extend the byte snapshot across an
`embed_facts` run; add `ast.keyword` (and f-string `JoinedStr` reassembly) to the
scans; pin the module's import surface (today it imports only two predicate strings,
`names_distinct`, `child_table`, and the vector repo — assert that); or soften the
docstring to what the scans actually see. Shipped code verified clean; this blocks
nothing today but should land before T2.11 gives the module a production caller and
the invariant real exposure.

**M2 — Minor.** `embed_facts` can commit the caller's transaction (first contact with
an unknown fingerprint → `register` → `session.commit()`,
`embedder_registry.py:245`) and neither its docstring (`:148-162`) nor `WriteResult`
says so. Conftest's savepoint pattern absorbs the commit, so no test exercises the
production behavior; a docstring warning is the only feasible guard.

**M3 — Minor (observation).** `similar_facts` (`:314-327`) is filtered ANN: `ORDER BY
embedding <=> vec LIMIT k` beneath a project + open-belief join filter, so pgvector
can return fewer than `top_k` qualifying rows when the filter is selective. The miss
direction is fewer pairs → fewer groups → undercount, which doc 08 §4.1 explicitly
prefers; recorded so a future recall investigation starts here rather than at the
threshold.

**M4 — Minor.** Inventory §6 status cell "`target-new` — **written since
2026-08-05**" (`baseline-schema-inventory.md:566`) overstates by a shade: the
partition has a writer; no production path writes it. The §7 row and `facts_channel`
prose are honest; align the cell's wording ("writer landed") when the file is next
touched.

**M5 — Minor (hand-forward).** `group_facts`/`similar_facts`/`fact_vectors` accept any
fingerprint string; the sentinel discipline is structural on the write side but only
advisory on the read side — nothing forces a caller through
`resolve_read_fingerprint`, and the scan pins only this module. T2.11's brief should
name it. Related edge, same owner: `resolve_read_fingerprint` proxies "has data" on
the **memory** partition (`vector.py:503-515`), so mid-rotation — memories re-embedded,
facts not yet — grouping keys on a partition whose triple side is empty and quietly
returns singletons. Undercount direction again, and it self-heals once facts re-embed,
but no job re-embeds facts on rotation today; the activation task inherits that too.
