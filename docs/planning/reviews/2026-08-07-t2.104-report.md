# T2.104 report — a response model that silently drops what the builder writes

**Branch:** `feat/e2-lane-cq` (off `feat/e2-truth-core`), worktree `.worktrees/e2-lane-cq`.
**Commits:** `0115a0a8` (guard tests), `33203069` (the `/config/llm` fix + frontend mirror retirement).

## The guard shape, and the alternative argued down

The brief offered two shapes: static AST introspection of a builder's dict literals
against its response model, or a payload-level comparison that drives the route and
diffs the served JSON against the builder's own return value. I picked the second.

**Why not static introspection.** `facts_read.get_fact` builds its item dict across four
call sites in one function (`_base_item`, then three `item[...] = ...` assignments, then
a `row_labels(...)` `dict.update()`, then `_source_group` for nested groups), and
`row_labels` and `dispute_label` and `gated_journal_payload` each contribute their own
keys conditionally. Parsing that structurally would mean re-implementing a partial
interpreter for dict-building Python, and the brief's own framing calls this brittle —
correctly, since the first version I sketched would have needed to special-case every one
of those four shapes and still would not follow a `.update()` call from an imported
function without inlining it.

**What the payload comparison actually does.** `tests/response_coverage.py` exports
`undeclared_keys(built, served)`: it calls the builder directly to get its raw
dict, drives the same HTTP route through the test client to get the actual served JSON,
and recursively diffs key sets — mappings recurse into mappings, lists of mappings
recurse element-by-element. It never compares values, only key presence, and it recurses
because the concrete case this exists to catch (`FactSourceGroup.stale`) was dropped two
levels down (`sources[].stale`), not at the top level.

This is not vacuous: the same comparator caught the `/config/llm` bug (below), on the
same code path, driven at the wire, before I applied the fix. It is the "robust, but
needs a live app per route" option the brief named, and I judged that cost acceptable
because both target routes already had a `client`/`session` fixture pair that shares one
transaction, so "drive the route" costs nothing beyond an extra `client.get(...)` per test.

**Not covered, stated explicitly rather than left to be assumed:**
- Every other `response_model=` route in `backend/app/api/routes/` — roughly eighteen

  `response_coverage.py` is reusable — any of those routes can be wired to it the same way
  facts.py and config.py were — but nothing calls it there yet.
- The `POST /config/llm` **write** path (`LLMConfigUpdate` / `LLMPurposeConfigUpdate`):
  those still declare six purposes, not eight. This is the same defect shape on the
  request side rather than the response side; see "found, not fixed" below.
- Anything a builder computes but this test's own fixture never exercises. The detail-page
  guard test deliberately builds a disputed fact with both a live and a stale source group
  and a recorded counterpart to maximise the shape in one fixture, but a field that only
  appears under a combination this fixture does not construct (e.g. an anonymous-origin

  top-level badge object, not the source-group one) was already correctly declared before
  this task and so was never exercised by a drill — I did not remove and restore it.
- Websocket broadcast payloads (`pipeline.completed`/etc.) — a different serialization
  path, not a `response_model`, and out of scope for this task's read surfaces.

## The `/config/llm` fix

`backend/app/schemas/config.py`: `LLMConfigResponse` declared six purposes
(`embedding`, `extraction`, `classification`, `reasoning`, `summarization`, `reranker`).
`app.services.config.PURPOSES` has always resolved eight, and both `GET` and `POST
/api/v1/config/llm` have always built `{p: cfg_to_schema(c) for p, c in
config.items()}` over all eight — so `synthesis` and `verification` were silently
dropped on every response. Added both fields to `LLMConfigResponse` (which
`LLMConfigUpdateResponse` inherits, so the `POST` response is fixed too). No change to
what any builder computes — this only widens the declared shape to match what was
already being built.

## Frontend: the hardcoded seed mirror is retired

`frontend/src/features/settings/llm-inert-purposes.ts` → renamed to
`llm-tier-c-purposes.ts`. Its old docstring claimed both `synthesis` and `verification`
had "no consumer... in either demo or real mode," which was already false for
`verification` (dispatched since T2.26, per `CLAUDE.md`'s LLM configuration section) and
became falsifiable-and-false the moment the backend started serving its real config. The
`model`/`api_kind` fields it hardcoded (a hand-kept mirror of `llm_seed.py`'s
`DEFAULT_PURPOSE_CONFIGS`) are gone; `useLLMTabBinding` now reads both purposes' real
connection fields off `/config/llm` in non-demo mode (`query.data?.synthesis` /
`query.data?.verification`), falling back to a small demo-only constant only in demo
mode or while the query is still loading. The UI card is still read-only for both —
`LLMConfigUpdate` still declares six purposes, so a write to either is a separate,
undecided wire-contract change (see below) — but its badge and copy now say `tier c ·
live` for `verification` and `tier c · inert` for `synthesis`, instead of calling both
"inert."

**On the rename's accuracy** (the concern raised mid-task): "Tier C" is a pre-existing
classification independent of live/inert status — `CLAUDE.md`'s own text calls the dream
job family "Tier C" while separately tracking which members are live bodies vs.
placeholders, and the original file's docstring already called both `synthesis` and
`verification` "Tier-C purposes" before this task touched it. Renaming to
`llm-tier-c-purposes.ts` keeps that accurate classification (both purposes genuinely are
Tier C) while dropping the "inert" claim that was only ever true for one of the two. The
file's exported type (`TierCLLMPurpose`) and its `activatesWith: string | null` field
(null meaning "already has a consumer") carry the live/inert distinction explicitly
instead of folding it into the filename.

`frontend/src/hooks/api/use-config-api.ts`: `LlmConfigResponse` widened with optional
`synthesis?`/`verification?` fields, commented as read-only pending the write-side fix.

`frontend/src/features/settings/__tests__/settings-llm.test.tsx`: updated the pinned
assertions from `"inert"` × 2 to `"tier c · inert"` (synthesis) and `"tier c · live"`
(verification), and swapped the literal `T2.26` text match for `/dispatched/` since the
verification card's copy no longer names the task id (it states the live fact rather
than pointing at the task that made it live, matching how the six live-purpose cards
never name their own activation task either).

## Other undeclared keys found — reported, not fixed

Per the brief's scope boundary, everything below is named for a separate decision, not
patched here:

1. **`POST /config/llm`'s write side never reaches `synthesis`/`verification`.**
   `LLMConfigUpdate` / `LLMPurposeConfigUpdate` (`backend/app/schemas/config.py`) still
   declare only the six live purposes. A client that submits `{"verification": {...}}`
   has that key silently dropped by the same `extra="ignore"` default, on the request
   side rather than the response side — the update loop's `getattr(body, purpose, None)`
   just returns `None` and skips the purpose with no error. This is the same defect class,
   found by reading the route (not driven by a test, since I did not write one for the
   write path), and it is exactly why the frontend's Tier-C cards stayed read-only rather
   than gaining a Save button — writing to either purpose is a real wire-contract change
   this task did not make.
2. **Every other `response_model=` route is unaudited by this guard**, per the coverage
   statement above. I did a bounded manual (non-driven) spot check of
   `app/services/review_queue.py::list_open_facts` against `ReviewQueueFactItem` — the
   builder's dict keys line up one-for-one with the schema fields by inspection, including
   the `_served_labels(...)` unpack — and found no obvious drop. This was **not** run
   through the guard, so it carries lower confidence than the facts_read/`/config/llm`
   findings above; it is a spot check, not a clearance.

No other undeclared keys were found or investigated beyond these two — the manual sweep
of the other ~17 route files was out of scope for an `S`-size task and is not claimed
here.
