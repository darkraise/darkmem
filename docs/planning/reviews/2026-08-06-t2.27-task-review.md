## Verdict 2 — Task quality: Needs fixes

No Critical. Five Important, three Minor.

### I1 (Important) — the LLM-reach guard is blind to relative-import intermediates

`backend/tests/test_code_deriver.py:700` — `_deriver_path_modules` follows
only `node.level == 0` imports, so a **relative** import never enters the
transitive closure.

Drill (control first): appended
`from app.services.pipeline import ProcessingPipeline` to `code_deriver.py`
→ `test_the_deriver_path_reaches_no_model_dispatch` **failed** (closure pulls
`pipeline.py` in and flags its LLM imports). Then the same reach spelled
`from .pipeline import ProcessingPipeline` → **both** guards **passed**
(`pipeline.py` never enters the closure; "pipeline" matches no forbidden
trailing segment; `ProcessingPipeline` is not a forbidden attr). The deriver
could then execute the entire extraction pipeline — classification, LLM and
all — and the build stays green. The never-join scan
(`test_no_statement_reads_both_graphs`) shares the same closure and the same
blindness.

This is not within the scanner's documented bound: `_reachability_scan`
handles relative imports (trailing-segment match) for *direct* forbidden
reaches; the hole is the closure derivation the test itself wrote. Today's
closure (10 modules) contains no relative imports, so the guard is sound for
the tree as it stands — the failure is exactly the "NEW path" case the clause
was chartered to close. Fix: treat `node.level > 0` imports as
package-relative to the importing file and resolve them into the closure.

### I2 (Important) — the HTTP-client split re-opened the hand-rolled-call route

`backend/tests/test_code_deriver.py:725` — client reaches are filtered to
`import route:` / `loader-call route:` only.

Drill: appended `import importlib` +
`_drill_client = importlib.import_module("httpx")` (module level, executes at
import, hands back the live client) → the guard **passed**. The literal route
— which the shared scanner's own contract names as the check that catches
loader-spec strings — is discarded for the client vocabulary, and the
loader-call route resolves only *relative*-name-plus-`package` calls, so an
absolute literal `import_module("httpx")` / `__import__("openai")` walks
through. The report's negative control
(`test_the_model_dispatch_scan_ignores_a_client_name_used_as_data`) proves the
false-positive direction only; it does not prove the executable dynamic route
still fires, and it no longer does. A narrower fix existed: keep the literal
route for clients and exempt the one data structure that collides
(`exempt_node_ids` on `_TYPE_OVERRIDES`'s dict node, or `skip_files` for
`extraction_clean.py` on the client rule set) instead of dropping the route
wholesale.

### I4 (Important) — repo→language relation is `DEPENDS_ON`; the spec says `USES`

`backend/app/services/code_deriver.py:45,100` — `_USES_ENTITY_TYPES` is
`{database, service, protocol}`, so `_relation_type_for("language")` returns
`DEPENDS_ON` (verified at runtime). Doc 10 §6 is explicit: "the relations
`repo —USES/DEPENDS_ON→ dep` **and `repo —USES→ language`**", and the brief

misreading. Every repo→language edge ships with the wrong relation type, and
no test pins the language relation either way. One-line fix plus a test.

### I5 (Important) — non-Python/JS module keys mint wrong or garbage facts

`backend/app/services/code_deriver.py:113,136` — the exclusion ladder handles
Python stdlib, Node builtins and the suffix index, and nothing else.
`code_parser.py` indexes `.go`, `.rs`, `.java`, `.cs`, `.rb`, `.php`, `.c`
(`EXTENSION_TO_LANGUAGE`) and writes `imports` edges for all of
`IMPORT_NODE_TYPES` — with a raw-statement-text fallback for `module_source`
on the grammars the one-level scan does not special-case. Verified against the
shipped functions:

| indexed `target_key` | derived assertion |
|---|---|
| `use std::collections::HashMap;` (Rust) | `tool` entity literally named `use std::collections::hashmap;` |
| `import "fmt"` (Go, fallback shape) | `tool` named `import "fmt"` |
| `fmt` (Go, clean shape) | `tool` `fmt` — Go stdlib |
| `encoding/json` (Go) | `tool` `encoding` — Go stdlib |
| `com.fasterxml.jackson.databind` (Java) | `tool` `com` |
| `java.util.List` (Java) | `tool` `java` |
| `System.Collections.Generic` (C#) | `tool` `system` |

(`net/http` survives only because `net` happens to be a *Node* builtin; C
`#include` raw text is swallowed by the `#` internal-prefix rule — safe by
accident.) The report's central safety claim — "biased toward excluding: a
missing fact is cheaper than a wrong one" — holds for the suffix rule and is
simply false for `dependency_name`, which has no shape sanity check
(whitespace, quotes, semicolons, `::`) and no builtin story outside Python and
Node. Every indexed Go repo asserts `DEPENDS_ON fmt`; every Java repo asserts
`DEPENDS_ON com` and `DEPENDS_ON java`. For a fact-originating bridge these
are wrong facts, in the one direction the design forbids. Mitigations that
hold it at Important rather than Critical: repo-only entities cannot reach the
`technologies` denorm (it selects on `memory_ids`), the Layer-2 lift is
T2.28's and gated, and the deriver has no production caller yet. It must be
fixed before the deriver is wired or T2.28 lifts anything: minimum a
lexical-shape gate on `dependency_name` (reject whitespace/quote/semicolon
names), better a per-language builtin story or an explicit
supported-ecosystem allowlist with everything else excluded — exclusion being
the direction the report itself argues for.

## On the inert-label retirement (invariant 23)

Honest as the idiom is practiced: the label is tied to "declared first writer
landed", the writer landed, and both the report (item 4) and the in-place
`test_inert_objects.py` note say in plain words that no scheduled path fills
the arrays in production. But the substance the old assertion guaranteed —
every array empty — remains true **in production** until a caller lands, so a
G-C evidence claim that the amended predicates "have now executed against
non-empty arrays" is true of the test database only and must be cited that
way. This does not change the clause verdicts; it does make I5's fix a
prerequisite for the wiring task the controller is minting, because the first
production caller will feed the deriver whatever languages the corpus's repos
actually contain.
