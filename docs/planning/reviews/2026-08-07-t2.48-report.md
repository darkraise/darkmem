## 1. What shipped

`app/services/citation_reverify.py` — a Tier-C job (`citation_reverify`, hourly at
`:45`, `min_interval_seconds=300`, `max_run_seconds=600`, one `batch_size` knob) that:

1. reads each repository's `last_indexed_commit` (code side, one statement);
2. selects code citations whose recorded sha is not that HEAD (vault side, one
   statement, the shas arriving as parameters);
3. re-resolves each `detail.symbol_key` against `code_graph_nodes` (code side);
4. for one that no longer resolves: sets `detail.stale = true` and
   `detail.stale_at_sha = <HEAD>`, journals `citation_stale`, and emits
   `sources_changed` so the existing Tier-C recompute drains it;
5. for one that resolves again after being stale: clears both keys and emits
   `sources_changed`, so recovery uses the same path as the demotion;
6. for one that still resolves, and for one with no `symbol_key` at all: stamps
   `detail.reverified_at_sha` and emits **nothing**.

It writes no `verification_status`, no `expired_at` and no `invalid_at`. The badge moves
through the recompute, driven by evidence that stopped counting.

**The load-bearing supporting change** is in `app/repositories/fact_sources.py`:
`LIVE_SOURCE_PREDICATE` excludes a stale row from `origin_profiles` and
`count_distinct_origins`. Without it the marker is decoration — the brief's warning is
exactly right, and I confirmed it by drill (§5, drill 1): with the predicate removed,
eight of my tests pass the marker assertion and fail the downgrade, because
`parse_is_the_verification` keeps holding the born rung on a citation that resolves to
nothing. The direction is the module's fixed one (undercount only), so a marker written
in error delays a promotion rather than fabricating one.

`sources_by_origin` is deliberately **not** filtered. It is the audit of the badge's
number, and dropping the broken citation from it would make the demotion look like
evidence that silently vanished. It keeps the row and gains `is_stale`; the badge's
number is the count of groups that are not stale. The REST fact-detail surface and the
frontend type carry the same flag.

## 2. How the changed-file set crosses the run/job boundary, and what that costs

**Chosen: scope on the sha, not on the file set.** A citation is re-resolved when
`COALESCE(detail.reverified_at_sha, detail.commit_sha)` differs from its repository's
`repositories.last_indexed_commit`. There is no per-run set to carry, because there is
no per-run scope.

**Why, over persisting the run's changed set.** The persisted-set design (an event
payload, `index_debt`'s `repo_indexed` journal being the local precedent) has a hole the
brief itself points at: it depends on delivery, and `record_event` degrades loudly and
never raises. A swallowed emit strands that run's citations permanently with nothing able
to notice, because the missing input *is* the message. The backstop that would heal it is
this sha comparison — so the file-scoped design needs this one underneath it, while this
one needs nothing underneath it. It is derived from two stored columns and is therefore
self-healing by construction.

Second reason: it made `code_pipeline.py` untouched, which matters with T2.96 and T2.97
live on the same file family this round.

**Two runs between two ticks.** They leave one HEAD. Re-resolution is always against the
graph as it stands *now*, so the intermediate run's file set is not merely lost, it is
irrelevant: a citation broken by run A and restored by run B resolves once, correctly.
The per-run/per-job mismatch the brief asks about does not arise, because the unit is the
sha and a sha subsumes every run that produced it.

**What it costs, stated plainly.** An unchanged file's citation is re-resolved once per
HEAD move rather than never. The bound is the repository's own citation count (doc 10 §6
sizes a repo at 10–200 facts), not repository size: the only index is
`UNIQUE (repo_id, kind, key)` (`0001_baseline.py:820`), and `_RESOLVE_KEYS` probes it with
the `repo_id` prefix plus `key = ANY(...)`, so the statement is bounded by the repo's
**node** count, not its citation count — batched once per repo, plus one small jsonb write
per citation. Harmless at Tier-C hourly scale. The measured shape in test is 3 citations
for a 2-file repo, 7 for a 5-import repo. **This is a deliberate, declared
deviation from doc 10 §6's stated cost bound** ("an unchanged file's citations cannot have
broken, so they are not re-resolved") — a Tier-1 amendment in effect, recorded here rather
than silently. Layering the file scoping on top later narrows the candidate predicate; it
changes nothing about what the job decides.

**What heals a swallowed event.** The `citation_stale` journal row is a record, not a
queue, so losing it loses only the human-readable cause. The `sources_changed` enqueue is
the one that matters, and the recompute's own slow arm (`_reconcile_from_fact_sources`)
already exists for exactly this: it walks `knowledge_triples` directly and recomputes from
`fact_sources`, where the stale marker is durable. So a swallowed enqueue delays the
downgrade by one slow-arm rotation and never loses it.

## 3. The keyless-citation fraction, measured

Measured 2026-08-07 against the real producer (`assert_repo_graph` + `run_code_lift`), not
estimated:

| import set | citations | carrying `symbol_key` | fraction |
|---|---|---|---|
| 5 ordinary PyPI names (the committed fixture) | 7 (5 import, 2 language) | 7 | **1.00** |
| 7 awkward names (`@scope/pkg`, `github.com/foo/bar`, `org.springframework.boot`, `React`, `Django`, `psycopg2-binary`, `a.b.c`) | 8 | 8 | **1.00** |

Both bases key reliably: an import citation records the module key the edge carries, a
language citation records a file path, and both are exact `code_graph_nodes.key` values —
every recorded key resolved against the graph it was read from (asserted, not assumed, in
`test_the_keyless_fraction_of_a_real_derivation_is_measured`). `a.b.c` produced no
citation at all rather than a keyless one; the deriver filters it upstream.

So `fact_lift.py:~1270`'s "cannot be re-verified" log is a **defensive** path today, not a
population. It is still handled explicitly rather than skipped: keyless rows are counted
into `ReverifyOutcome.keyless`, logged at WARNING with the tick's total, stamped so they do
not re-enter every tick forever, and **never marked stale** — "cannot be checked" is not
"checked and broken", and marking would demote a badge on missing bookkeeping. The suite's
floor is 0.9 rather than 1.0 because the witness lookup is a name match between two
independently normalised strings, and a taxonomy change on either side is a plausible way
for one to start missing.

## 6. Where the plan was wrong

**Finding 1 — the code-side withdrawal is already built (Tier 1, corrected in place).**
The brief says: "*the code-side withdrawal is genuinely unbuilt*", reasoning from
`fact_provenance`'s explicit memory-kind restriction. That restriction is real and correct
and must stay, but the conclusion does not follow: **T2.28 already landed the code half**,
as `reconcile_code_sources` / `_withdraw_code_sources` in `fact_lift.py`. It withdraws a
code source the graph no longer supports and calls `close_window` (`invalid_at`, never
`expired_at`) on whatever that orphans, and it skips a fact another live source still
holds. `tests/test_deriver_lift.py` already covers both halves including the asymmetry.

The brief asks whether the code half should reuse `_withdraw`'s sequence. It should not,
and it does not: the memory half **expires** a fact whose last source vanished, the code
half **closes its belief window**, because a repository that stopped importing a package
did not stop having imported it. Two verbs, two sequences, and doc 10 §6 uses the second
verb by name. Done-when clause 2 is therefore satisfied by existing code; I asserted it
from T2.48's own suite anyway (the Done-when is on this task) and added the assertion that
did **not** exist — `test_a_stale_citation_is_not_a_withdrawal`, which pins the line
between the two clauses: a stale address leaves the row, the window and the belief alone
and moves only the badge. Conflating them is the most likely way an implementation of this
task retires a claim doc 10 §6 says only a human may retire.

**Finding 2 — doc 10 §6's literal scoping key would make the walk vacuous (Tier 1,
recorded, not acted on).** §6 says the job walks rows "*whose `detail.symbol_key` falls in
that [changed/deleted file] set*". For a **language**-basis citation `symbol_key` *is* a
file path, so that reads correctly. For an **import**-basis citation — the majority; 10 of
12 in the census above — `symbol_key` is a *module key* (`httpx`, `github.com/foo/bar`),
which is not a path and can never appear in a file set. A literal implementation would
silently re-verify only the language citations and report success. The scoping field a
file set should be matched against is `detail.file_path` (the witness file), which moves
for both bases. My design does not depend on this, since it does not scope on files at
all, but anyone later adding the file scoping as an optimisation must use `file_path` or
union both keys. Worth an edit to doc 10 §6 by whoever owns it; I did not edit a design
doc from a lane.

**Finding 3 — `CLAUDE.md`'s job count had already drifted.** It read "**Sixteen**
registered jobs … The ten live ones", but `main.py` already registered eleven non-family
jobs: T2.49's `relation_embedding_refresh` landed without moving the sentence. With mine
that is twelve live and eighteen total, which is what the sentence now says. The new test
derives both numbers from `main.py`'s AST plus `DREAM_JOB_KEYS` rather than pinning
literals, so **a concurrent lane that registers a job and updates the sentence stays
green** and one that forgets does not. T2.96 may register a job on its lane; if it does,
its own count edit and mine collide textually on merge, and the resolution is one sentence
naming both.

## 7. Concerns (why DONE_WITH_CONCERNS)

**C1 — a language-basis citation is addressed to one arbitrary file, so it is noisier than
it looks.** `repo_witnesses` records "the first witness in sort order" for a language. If
that one file is deleted or renamed at a new HEAD while five hundred other Python files
remain, the citation's address stops resolving and `repo USES python` demotes to
`candidate` for a human to look at — even though the current parse supports the claim
completely. This is doc 10 §6's design working as specified (the address is the evidence,
and label-and-queue is what §6 asks for on a broken address), and the fact stays live,
served and one `run_code_lift` away from having its rung restored once the address is
fixed. But it is a real false-positive source on repos that move files, and if review
volume becomes a problem the fix is on the producer side — re-address a language citation
to a surviving file rather than weaken the re-verifier. Recorded, not acted on: rewriting
`detail` addresses is `fact_lift`'s contract, not this task's.

**C2 — the deriver has no production trigger yet (T2.96's lane), which is what makes the
"claim survives, address breaks" state reachable at all.** Once T2.96 lands, a re-index
that also re-derives will withdraw the Layer-1 assertion in the same window for the
dependency-removed case, and the re-verifier's marking will more often be transient before
the withdrawal arrives. The two are independent and neither corrupts the other — I assert
this directly (`test_a_stale_citation_is_not_a_withdrawal` runs `run_code_lift` after a
marking and confirms it withdraws nothing and restores nothing) — but the *observed
frequency* of stale markings will change once T2.96 is live, and anyone reading a G-C
metric over `citation_stale` volume should know the population moves under them.

**C3 — `progress.md` is untouched.** The runbook makes it canonical on `master`, and a
lane worktree updating it forks the file. Left to the controller with this report's shas.
