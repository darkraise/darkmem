### The provenance shape, which T2.48 inherits

`source_kind='code'`, `source_ref = origin_key = repo_id`,
`detail = {commit_sha, basis, file_path, symbol_key}` — all four keys always
present, `None` rather than absent when there is no witness, because a key that
is sometimes missing is two shapes wearing one name and the re-verifier reads it
with a subscript.

`symbol_key` is the `code_graph_nodes` **key**, never the `BIGSERIAL` id: the
`module` node's key (the import source) for `basis="import"`, the `file` node's
key (the path) for `basis="language"`. `test_the_detail_addresses_code_by_name_
and_sha_not_by_node_id` re-resolves it against `code_graph_nodes` the way T2.48
will, which is the only assertion that proves the value is an address rather
than a string.

`commit_sha` is the sha the assertion was **born** at, not the latest HEAD:
`add_source` is first-assertion-wins and rewrites neither `origin_key` nor
`detail`. That is a consequence of the existing contract rather than a choice I
made, but it is a consequence T2.48 has to know about, so it is pinned by
`test_a_new_commit_refreshes_nothing_it_should_not`.

## 3. The three Done-when clauses

### Clause 1 — a repo indexed 100 times is still one origin

`test_a_repo_indexed_a_hundred_times_is_still_one_origin` runs a real 100-round
loop. Each round writes a **new HEAD sha**, a **changed import set** (a
dependency unique to that round), and a full `assert_repo_graph` re-derivation,
then a lift tick. The test asserts, inside the loop, that this round's
dependency actually reached Layer 1 — so the derivation demonstrably re-executed
rather than short-circuiting — and after the loop that the previous round's
dependency is gone, proving the strip ran too. Then:

- `count_distinct_origins(fact) == 1` (the repository's own
  `COUNT(DISTINCT origin_key)`, not a row count);
- exactly one `fact_sources` row;
- the surviving fact is **the same row** that was born in round zero.

The rule is structural rather than checked: the unique
`(fact_id, source_kind, source_ref)` makes a second row for one repo
unrepresentable, and the shared `origin_key` makes it uncountable even if one
existed. The negative control —
`test_two_repositories_asserting_one_fact_are_two_origins` — proves the counter
is not pinned to 1.

### Clause 2 — the only exception, and it cannot be widened by accident

Three independent narrowings, each with its own test:

1. `mint_born_corroborated` refuses any `source_kind` but `code` **before it
   writes**, so the exception is a property of the function rather than of the
   caller's string. Tested for `memory` and `human`, including that the refusal
   left no fact behind.
2. `open_born_corroborated` is the only route to the column at insert time, it
   binds a **module constant** (no caller-supplied value reaches its statement),
   and an AST scan pins its single caller in `app/` and the single enclosing
   function of that call.
3. `OriginProfile.parse_is_the_verification` reads the stored `source_kind`, so
   a memory or human profile can never satisfy it (six parametrised cases).

**The exception needed a second half the brief did not name, and without it the
task is vacuous.** A born fact has one origin, which is below every threshold
the ladder can pick, so the first `verification_recompute` tick would decide
`demote` — and the slow arm reaches every fact whether or not an event was
emitted. So `decide()` gains one branch, placed after the `confirmed` hold,
after the absolute veto and after the `k >= n` block, that returns the ordinary
unblocked hold for a fact **already at** `corroborated` whose profile carries a
code origin. Its properties, deliberately:

- it **holds a rung, never grants one** — a candidate is untouched, so a fact
  below the rung still climbs by count alone;
- an unblocked hold **journals nothing**, so no `verified` row appears and
  G-C's promotion rate gains neither a numerator nor a denominator entry;
- `required_origin_count_for` is untouched, so the reported `k` and `n` for
  these facts are the same numbers the count-based ladder always reported.

I considered lowering `N` to 1 for a code profile instead (which would journal a
clean `promote`), and rejected it: it would let a code source promote a fact the
count has not backed, which is a wider claim than "born corroborated", and it
would put rows in G-C's `gate_fired='none'` bucket whose `required_n` is not
what that bucket means.

`test_the_recompute_holds_the_born_rung_and_demotes_the_ordinary_one` drives the
real `recompute_fact` on a code-sourced fact and on a memory-sourced twin in the
same state, and asserts on **the rows** rather than on the returned outcome —
because the demotion hysteresis converts the memory twin's `demote` into a hold
too, and asserting on the word would have passed vacuously. What separates them
is `demotion_pending_since`: the ordinary fact is on its way down, the code fact
was never on the count.

### Clause 3 — withdrawal invalidates

`reconcile_code_sources` compares each stored code provenance row's
`triple_key` against the set of triples its repo currently asserts in Layer 1,
tested through `compute_triple_key` — exact parity with the write half rather
than approximate parity through SQL. Withdrawn rows are deleted; a fact left
with **no** surviving source gets `close_window` (doc 10 §6's verb), never
`expire`. Four cases, four tests:

| Case | Outcome |
|---|---|
| Dependency dropped, sole source | `invalid_at` set, `expired_at` NULL, row retained, sources empty |
| A live **memory** still asserts it | untouched, `facts_invalidated == 0` |
| A second live **repo** still asserts it | untouched, same row id, one source left |
| Repository deleted outright | invalidated — the sweep is driven by stored provenance, so there is no caller to be missing |

The sweep is data-driven rather than by-repo for `fact_provenance`'s reason: a
repository deleted outright leaves nobody to call a by-repo sweep, and the rows
it stranded would otherwise keep a fact serving as corroborated on evidence that
no longer exists, with no error and no symptom.

`test_re_adding_a_dependency_opens_a_new_window_not_the_closed_one` pins the
lifecycle invalidate-not-delete implies and nothing else states: a closed window
stays closed and a returning dependency opens a **new** row, because clearing
`invalid_at` would erase the interval in which the repository genuinely did not
depend on it.

## 7. What the plan got wrong, and stated narrowings

1. **The brief's dependency set is incomplete in the tree.** T2.95's repair is
   not on the epic branch (§1). The brief asserts behaviours that only exist on
   `e2-lane-cc`.
2. **The brief does not mention the recompute at all**, and without a ladder
   change every born-corroborated fact is demoted by the first tick that reaches
   it. "Born corroborated" and "stays corroborated" are two properties and only
   the first is in the Done-when. I implemented both; the second is the change a
   reviewer should scrutinise, because it is the one the brief did not authorise
   by name.
3. **Code facts land in project `default`, and the brief names no project.** A
   repository carries no project column and the code graph is not
   project-scoped, so the bridge has to pick one. `triple_key` embeds the
   project verbatim, so a memory captured under a different project asserting
   the same triple lifts to a *different* fact and the two do not corroborate
   each other. That is the under-claiming direction; the alternative (lifting
   one repo's assertion into every project) would put facts in scopes nothing in
   them asserted. It is a `CODE_FACT_PROJECT` constant with the reasoning at the
   constant, not a config row, because nothing yet knows how a repo would name
   its scope.
4. **The witness read re-runs the deriver's own classification.** The lift
   cannot get `file_path`/`symbol_key` from Layer 1 — the relation rows carry no
   provenance — so `repo_witnesses` re-classifies the import edges through
   `code_deriver`'s **imported** predicates (`is_internal_import`,
   `dependency_name`, `DERIVABLE_IMPORT_LANGUAGES`). Imported, not copied, so
   the two can only disagree if one is changed without the other; and the blast
   radius of a disagreement is bounded to `detail` — a name with no witness
   still gets its provenance row and its `origin_key`, logged rather than
   dropped. Storing the witness on the relation's `properties` at derive time
   would be tighter, but `assert_from_repo`'s relation upsert does not merge
   `properties`, so a pre-existing relation would never receive it.
5. **`detail` carries one address where several files may import one package.**
   Doc 10 §6 fixes a single `file_path`/`symbol_key`, so the choice is between a
   deterministic witness and an arbitrary one; the first in sort order wins.
6. **Batch bound.** The code half reuses the `fact_lift` job's existing
   `batch_size` and adds no config field, so no persisted job config is
   orphaned. `min_asserting_memories` has no code analogue — an import either
   exists or does not — and is not applied to the code half.
7. **`reconcile_code_sources` scans every code provenance row per tick.** It is
   an indexed read that returns immediately on a vault with no code facts (every
   vault until a repository is indexed) and it is bounded by the number of code
   facts, not by the vault. At G-C volume it should be watermarked; that is not
   this task's, and it is the same class of statement `fact_lift`'s
   `_PENDING_GROUPS` already makes about its own cost.
