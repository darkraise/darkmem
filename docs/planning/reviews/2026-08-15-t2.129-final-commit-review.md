## Verdict 2 — Task quality: REWORK (1 Critical, 3 Important, 6 Minor)

### Critical

**C-1. The restored twin's token columns can never report a token.**
`run_gc_evidence.py:135-136` (`_print_twin`) reads `usage.get("prompt_tokens", 0)` and
`usage.get("completion_tokens", 0)`, but `TokenLedger.as_dict()` emits `asdict(PurposeUsage)`
whose keys are `live_prompt_tokens`, `live_completion_tokens`,
`cache_known_prompt_tokens`, `cache_known_completion_tokens`, … — **no key named
`prompt_tokens` or `completion_tokens` exists** (confirmed by executing
`asdict(PurposeUsage())`). Both lookups are dead and print 0 unconditionally. Why it
matters: on a **cold (paying) run** — the case the twin exists for — the runner would print
`live=246 prompt=0 completion=0`, the exact "unknown coerced into a paid zero" shape ruling
3 forbids and this commit's own narrative disavows, silently: zeros are plausible, so
nothing would flag it. This run's artifact happens to be correct only because the true
values are zero (fully replayed). The same line also omits `live_unknown_calls`, the
disambiguator `PurposeUsage` carries precisely so `live=N prompt=0` cannot be read two
ways. No test covers `_print_twin` (the commit ships no tests), so the defect is invisible
until the first paying run — or forever. Fix: read the real keys (live and cache_known
reported distinctly, per the ledger's own live/cache split doctrine), print
`live_unknown`, and pin the printer with a test that fails on a key rename.

### Important

**I-1. The two runs differ somewhere the clock cannot reach, and the record is silent.**
The simulated artifact shows `scheduler superseded=2 of 3`; the unsimulated one shows
`superseded=1 of 3`. The blocked-hold design pre-registered **"exactly 2 of 3"**
(expectation 5, with the rule that a miss "must be explained from the journal … not waved
through"), and its mechanism ("each capture retired by the next") did not reproduce.
Supersession runs at ingest and reads `memories.created_at`, which the flag never touches;
app code is identical between the runs (`git log 28fea3d7..1713004e -- backend/app` is
empty) and extraction was fully cache-replayed — so the clock cannot explain it. The
structural suspect: Phase-5 writes are **concurrent** (`pipeline.py:1152`, `asyncio.gather`
under a semaphore), and `detect_supersessions`' technologies-overlap guard (condition 3)
reads a sibling's `technologies`, which is populated by that sibling's own Phase-5 write —
so within the in-flight window the superseded count is a commit-ordering race
(2 = oldest-first, 1 = mixed, 0 = newest-first). Why it matters: (a) the ledger's "the
clock is the only variable" is contradicted on the face of its own artifact, undisclosed;
(b) the harness's headline mechanism claims are pre-registered against a nondeterministic
quantity — the probes' two byte-identical reproductions of the simulated run were partly
luck; (c) the hold demonstration's story survives here only because one superseded source
suffices to fire `supersession_hold` (2 hold events, `none` blocked=2 unchanged), which is
why every quoted number still reconciles. What would settle it: one cheap re-run of the
unsimulated pass (0 live calls, ~16 s) to see whether the count flaps, and either a
disclosure note in the ledger section or an ordering guarantee in Phase 5 for
same-project REPLACES chains. Not run here per the dispatch's operational constraint.

already in the denominator. The headline conclusion — `time_gap` disappears rather than
