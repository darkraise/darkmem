## Verdict

**Dispatch with named changes.** The plan's factual base is sound — every `file:line`
claim in §1 checked out against the tree — and its central design decision (pass-keyed
co-ownership, strip via `clear_pass_block` + delete-on-exclusive) is correct and
verified. But four gaps (F1–F4) would each surface mid-execution as a design decision
the executor is not chartered to make. The plan must be amended on those four points
before dispatch; the remainder are minors the executor can absorb.

## Ruling on O1 — ship three types; do not derive `DEPENDS_ON` / `FOLLOWS`; do not cut them

**Option 2.** Reasons, in order of force:

1. **Option 1 writes claims nothing measured.** `FOLLOWS` derived from `created_at`
   asserts narrative succession from capture order — an artefact of when someone typed.
   `DEPENDS_ON` has no deterministic signal among the three doc 08 §5.5 names at all.
   The corpus's whole verification posture is built to under-claim (doc 08 §4, "the
   ladder is built to under-claim"); a guessed edge is the opposite. The plan's own
   rejection of option 1 is right, though its citation of invariant 14 for this is a
   loose fit — invariant 14 is honest partial results (doc 08 §8); the closer
   authorities are invariant 23's scaffolding-honesty rule and the under-claiming
   stance itself. The conclusion survives the citation.
2. **Option 3 is Tier-3 and not compelled now.** The `DERIVED_FROM` precedent
   (doc 06 §3.1, doc 04 §8.2) cut a type whose only writer was *structurally removed*
   and whose function collided with the one-provenance-mechanism-per-layer rule.
   Neither applies here: `DEPENDS_ON` and `FOLLOWS` are semantically meaningful
   memory-to-memory claims awaiting a semantic writer (an LLM pass or the article
   layer), and leaving them stored-but-underived forecloses nothing — nothing writes
   them, so a later cut needs no data migration, while a cut-then-reintroduce costs
   taxonomy churn twice (including unwinding the `REQUIRES → DEPENDS_ON` legacy alias,
   `taxonomy.py:306`). Per the brief's instruction: I am not deciding option 3; I am
   declining to require it.
3. **Condition attached.** Shipping option 2 leaves doc 08 §5.5's decision sentence
   ("derives the five stored associative types") realized as three-of-five. That
   discrepancy must not go unrecorded: the controller should log an amendment-log row
   (Tier-2 shape — no vocabulary change, no dependency change) stating that v1
   derivation covers `CONTRADICTS` / `ELABORATES` / `RELATES_TO` and that
   `DEPENDS_ON` / `FOLLOWS` await a real writer, with the invariant-23
   cut-or-keep question parked as a standing Tier-3 item. T2.16's dispatch brief
   must state the three-type scope explicitly so the executor does not re-litigate it.

## The central structural claim — verified, it holds

Read in full: `backend/app/repositories/memory_relations.py`.

- **Co-ownership under `properties.dream.<pass_key>` is real.** The module docstring
  (lines 8–15) states the mechanism and the reason (the UNIQUE on
  `(source_memory_id, target_memory_id, rel_type)` forces two passes proposing the
  same triple onto one row); `_UPSERT_PASS_BLOCK` (lines 78–105) writes only
  `{dream, <pass_key>}` via nested `jsonb_set`, and `write_pass_block`
  (lines 214–231, 250–273) is UPDATE-only as the plan's table says.
- **`exclusive` is computed in the same statement as the removal.** `_CLEAR_PASS_BLOCK`
  (lines 193–209) removes the block with `#-` and computes `exclusive` in the same
  UPDATE's RETURNING over the post-removal `properties` — no sibling under `dream`, no
  other top-level key — exactly as the plan describes. The plan cites
  `memory_relations.py:185-200`; the statement actually spans 193–209 (182–192 is its
  comment). Cosmetic drift only; the substance is right.
- **A strip via `delete_edge` would destroy sibling state.** `_DELETE_EDGE`
  (lines 233–239) deletes the row unconditionally; since the UNIQUE forces T2.12's
  near-duplicate block and T2.16's block onto one row whenever both assert the same
  triple, the destruction claim is true by construction. The plan's §5 flagship test
  (sibling-block survival, with the `delete_edge` mutation) is the right guard and is
  non-vacuous as designed.
- **Also confirmed in the schema, not just the docs:** the composite
  `(memory_id, project)` FKs with `ON DELETE CASCADE` the plan's self-healing
  paragraph rests on are in the tree
  (`backend/migrations/versions/0001_baseline.py:357-378`), so T2.17's second clause
  really is a test against the schema, not new code.

One caveat the plan should carry (F7 below): the same-statement claim covers the
*flag's* consistency, but `delete_edge` is a **separate, unconditional** statement, so
a clear→delete window exists in principle. It is closed today by invariant 13 (single
worker, per-job asyncio lock serialising the dream passes), not by SQL. That assumption
should be stated, because E4 flags multi-replica as an open decision.

## Findings, ranked

### F1 — Important. Step 8's journal rows are either refused or mis-inverted by the undo door; the plan is silent on undo integration.

`docs/superpowers/plans/...-t2.16-...md` §4 step 8 journals "one `consolidated` row per
written edge" but never says which **action kind** the payload carries, and both
available choices break as things stand:

- **A new action kind** hits `dream_undo`'s `REASON_UNSUPPORTED_ACTION`
  (`backend/app/services/dream_undo.py:88-93`): the door has inverses for exactly
  `ACTION_SUBSUME` / `ACTION_ASSOCIATE` / `ACTION_REFINE` (lines 739–741). A cycle
  containing derivation actions becomes un-undoable through the body-less whole-cycle
  form (one blocked action refuses the batch, per the 2026-08-04 amendment row), and
  the derivation actions themselves are *permanently* un-undoable — against
  doc 08 §7's "per-action/per-batch undo" contract for dreaming actions.
- **Reusing `ACTION_ASSOCIATE`** is worse: `_invert_associate` hardcodes
  `journal.NEAR_DUPLICATE_PASS` in its restore arm (line 654), its clear arm
  (line 670), **and** the currency CAS (lines 512–513). An undo of a T2.16 edge would
  restore or clear the *near-duplicate* block — silently corrupting T2.12's state
  while reporting success.

**Named change:** the plan must add the undo integration as an explicit step — the
straightforward shape is a `pass_key` field in the journal payload with
`_invert_associate` and the CAS generalised to read it (defaulting to
`NEAR_DUPLICATE_PASS` for existing rows), plus a test that undoing a derivation edge
touches only the derivation block. If the plan instead wants derivation actions
not-undoable, that contradicts doc 08 §7 and is the controller's call, not the
executor's. Either way, dispatching without deciding this hands the executor a
mid-task design fork.

### F2 — Important. D4's contradiction signal is not executable as written.

D4 requires "opposed targets … over overlapping validity", but:

- **There is no validity substrate at L1.** `memories` carries
  `created_at` / `updated_at` / `expires_at` and nothing else temporal
  (`backend/app/models/memory.py:42-75`); `valid_at` / `invalid_at` live on
  `knowledge_triples` (doc 04 §8.3), which `fact_lift` populates — and `fact_lift` is
  still a `PlaceholderJobRunner` (T2.10 unlanded). D7's claim that "all three signals
  are pure functions of stored columns" is therefore false for D4 as written: the
  column its temporal clause needs does not exist at this layer.
- **"Opposed targets" is undefined.** Two memories asserting
  `(subject, family, target₁)` and `(subject, family, target₂)` are not opposed in
  general — a service legitimately `DEPENDS_ON` two libraries. Opposition is only
  meaningful for relation families that are single-valued, and no such list exists
  anywhere in `taxonomy.py` or the corpus.

This matters doubly because D3 makes `CONTRADICTS` suppress the weaker edge: a
loosely-built D4 both manufactures false contradiction signals into the dispute/hygiene
surfaces *and* erases true `RELATES_TO` edges.

**Named change:** the plan must pin D4 in executable terms before step 4 exists. A
defensible deterministic shape: opposition fires only over a small closed
exclusive-family list (a taxonomy-owned constant), and the succession guard is the
memory-level analogue of disjoint windows — both memories `active`, neither
superseding the other — rather than a validity clause the layer cannot compute. The
exact definition is the plan author's to fix and the controller's to ratify
(plan-local: doc 08 §5.5 deliberately leaves the mapping open); what is not acceptable
is dispatching with "overlapping validity" naming a column that does not exist.
Deferring the contradiction arm entirely (shipping two signals) is the fallback if no
deterministic definition survives scrutiny — that widens O1's scope-shrink and should
then go back to the controller.

### F3 — Important. D5's "overlap arm still runs" contradicts the current cycle structure, and the steps don't include the restructuring.

`run` in `memory_dream.py` returns at `SKIPPED_FINGERPRINT_UNRESOLVED` *before any
phase runs* (`memory_dream.py:1300-1303`), and its docstring defends that early-stop
discipline. Step 9 wires the derivation pass "into the dream cycle", so as planned the
sentinel-refusal test ("the proximity arm reports skipped … the overlap arm still
runs") is unimplementable: the run body never reaches the pass. Restructuring the
early return into an arm-scoped skip touches the near-duplicate pass's tested
behaviour (`skipped_reason` is pinned in `test_memory_dream.py`).

**Named change:** step 9 must state where the derivation pass sits relative to the
fingerprint early-return — either the pass runs before the gate, or the gate becomes
arm-scoped with the near-duplicate arm keeping its current run-stop semantics — and
the step list must own the restructuring explicitly so it is not improvised.

### F4 — Important. The strip's scope is ambiguous under the batch cap, and D7's replay guarantee quietly narrows to unchanged corpora.

Step 7 strips "every pair this run no longer asserts". With `derivation_batch` smaller
than the candidate count, the run evaluates only a stable prefix (D7's ordering), so:

- **Pairs beyond the cap are never derived, ever** — the stable prefix that makes
  replay pass is exactly what makes coverage permanently partial, reporting green.
  This is the same green-and-inert shape the plan itself flags for fingerprints.
- **On a growing corpus, the prefix shifts**: previously-asserted pairs fall out of
  the evaluated window and — under the step-7 wording — get stripped even though
  their signal still holds. Edge churn as a pure cap artefact.
- The strip must also key on **(pair, rel_type) triples**, not pairs: when a pair
  transitions `RELATES_TO → CONTRADICTS` under D3, the old triple's block must be
  stripped or the pair is shown twice, defeating D3's stated purpose.

The replay Done-when itself survives (unchanged corpus + config ⇒ identical set), but
only because the truncation pathology is invisible to that test.

**Named change:** scope the strip to the evaluated candidate window (strip only
triples whose pair the run actually re-evaluated), key it on triples, and surface
truncation in `DreamOutcome` (a `candidates_truncated` counter — invariant 14's
honest-partial-results applied to the pass's own report). If instead the intent is
that `derivation_batch` normally exceeds the candidate count and is only a safety
valve, the plan must say so and the outcome must still report when the valve engaged.

### F5 — Minor. R1 is tractable, but only with a hot-entity cap the plan doesn't name; Size L stands.

The overlap generator's cost is Σ C(k,2) over entities with k asserting memories — one
entity asserted by 500 memories yields ~125k pairs on its own. Two specifics the
executor must not learn the hard way: (a) `ORDER BY` + `LIMIT derivation_batch` does
**not** bound the join — the full quadratic intermediate is computed before the sort,
so the bound must live in the generator (skip entities whose `memory_ids` cardinality
exceeds a config'd cap — such stop-word entities carry near-zero relational signal, the
IDF logic); (b) `entities.memory_ids` is **not project-scoped** (CLAUDE.md, doc 04),
so the pass must join back to `memories` for the project filter — forgetting it fails
loudly on the composite FK at write time, but only after paying for the cross-project
pairs. With the cap, the pass is fine at bench and homelab scale; the plan's
measure-on-`darkmem_bench`-first instruction is right and should stay. Add the cap to
D6's config list.

### F6 — Minor. The order-stability mutation is an unreliable probe.

"Removing the ORDER BY must fail this" assumes Postgres returns a different order
without it; on a small unchanged test table, consecutive identical scans very often
return identical order, so the mutation stays green nondeterministically. Strengthen
the probe: build the two runs over corpora inserted in different physical orders (or
relocate a heap tuple with a dummy UPDATE between runs) so the unordered plan
actually diverges.

### F7 — Minor. The delete-on-exclusive window and the docstring's "ever".

As noted above: `exclusive` describes the post-removal row at the UPDATE's moment;
`delete_edge` is a separate unconditional statement. Safe today under invariant 13's
single-worker serialisation — the plan should state that assumption where it specifies
step 7, since E4's multi-replica decision would reopen it. Also, both the plan and the
repository docstring say `True` means nothing else "was **ever**" on the row; the
computation is over the *current* row (a sibling that wrote and later cleared its own
block still yields `True` — which is the correct deletion semantics, so the code is
right and the word is wrong). Cosmetic.
