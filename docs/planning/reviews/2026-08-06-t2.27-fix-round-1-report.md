## I1 — the LLM-free guard was blind to relative-import intermediates

**Finding.** `_deriver_path_modules` followed only `node.level == 0` imports, so a
relative import never entered the transitive closure. The reviewer appended
`from .pipeline import ProcessingPipeline` to `code_deriver.py` and **both** structural
guards passed, while the absolute spelling of the same reach was caught.

**Fix** (`backend/tests/test_code_deriver.py`). The closure builder is now
`_import_closure(entry, root)`, parameterised on its root so it can be driven over a
planted tree, and it resolves relative imports against the importing file's own package:
`_package_of` derives that package from the file's path under the root, and
`_resolve_relative` drops one segment per extra level the way `importlib` does, so
`from .pipeline import X` inside `app/services/code_deriver.py` resolves to
`app.services.pipeline` and `from ..repositories.graph import Y` resolves to
`app.repositories.graph`. `_deriver_path_modules()` is now a one-line call into it.

This lives in the test rather than in the shared scanner deliberately, and the docstring
says so: the scanner sees one file at a time and matches a relative import on its
trailing segments, which answers "does *this* file reach a forbidden module" but cannot
answer "which file must I add to the set I am about to scan". Only the closure builder
knows the entry point and the root.

**The closure is unchanged in size — still the same 10 modules.** That is the finding
restated rather than a reason to doubt the fix: today's tree contains no relative
imports on the deriver path, so the hole was latent, and the clause it broke
("proven structurally, for a NEW path") is exactly about paths that do not exist yet.

**Reviewer's drill, re-run.** Appended `from .pipeline import ProcessingPipeline` to
`code_deriver.py`:

```

E       app/services/classification_llm.py:9: import route: app.services.llm.LLMOrchestrator
E       app/services/extraction.py:4: import route: app.services.llm.LLMOrchestrator
E       app/services/pipeline.py:15: import route: app.services.classification_llm.ClassificationService
E       app/services/pipeline.py:17: import route: app.services.llm.LLMOrchestrator

E       app/services/pipeline.py:1289: import route: app.services.reranker.RerankerService
E       app/services/reranker.py:9: import route: app.services.llm.LLMOrchestrator
E       app/services/llm.py:5: import route: httpx
```

Red, and red for the right reason: the reached module and everything it reaches are now
in the scanned set. Restored from a pristine copy; green again.

**Own drill.** Reverted the closure to `base = node.module if node.level == 0 else None`:
`test_the_closure_follows_a_relative_reach_as_it_follows_an_absolute_one[relative-…]`
(both parametrisations) and `test_the_closure_resolves_a_parent_relative_reach` failed;

**New tests.** `test_the_closure_follows_a_relative_reach_as_it_follows_an_absolute_one`

relative import as a sibling would not pass).

**Finding.** Client reaches were filtered to `import route:` / `loader-call route:`, so
`importlib.import_module("httpx")` at module level — executes at import, hands back the

**Fix.** Took the narrower option the reviewer named. The literal route is restored for

`ast.AnnAssign`, not on rendered text — and exempts the `ast.Constant` nodes inside its
value. Everything else in that file, and every constant in the other nine closure
modules, is scanned.

The exemption is exactly load-bearing and nothing more. Running the client rules over the

So restoring the route across all ten modules costs zero false positives.

## I5 — non-Python/JS import shapes minted wrong facts

**Finding.** The exclusion ladder handles Python stdlib, Node builtins and the suffix
index and nothing else, while `code_parser.py` indexes Go, Rust, Java, C#, Ruby, PHP and
C and writes `imports` edges for all of them. Confirmed at runtime against the shipped
functions before touching anything:

| indexed `target_key` | shipped `dependency_name` |
|---|---|
| `use std::collections::HashMap;` | `'use std::collections::HashMap;'` |
| `import "fmt"` | `'import "fmt"'` |
| `fmt` | `'fmt'` |
| `encoding/json` | `'encoding'` |
| `com.fasterxml.jackson.databind` | `'com'` |
| `java.util.List` | `'java'` |
| `System.Collections.Generic` | `'System'` |

**I took the brief's recommendation rather than overturning it**, and narrowed it in one
place, stated below.

**Fix, three layers.**

1. **A named, exhaustive language partition.** `DERIVABLE_IMPORT_LANGUAGES =
   {python, typescript, javascript}` — the shapes the rules actually parse — and
   `UNDERIVABLE_IMPORT_LANGUAGES`, which names every other value
   `code_parser.EXTENSION_TO_LANGUAGE` can attach to a file plus the `unknown` a failed
   parse falls back to. Both are public names, both carry the reasoning, and the comment
   says widening means writing that language's import shape and moving it across — never
   relaxing the gate.
2. **The gate is per importing file, not per repository.** A `file` graph key is the file
   path verbatim (`app/utils/graph_keys.py`), so `derive_assertions` now selects
   `DISTINCT source_key, target_key` and looks the importing file's language up in the
   `code_files` rows it already reads. A Python service with a Rust sidecar keeps its
   Python dependencies and declines the Rust ones. **The never-join invariant is
   untouched** — the widened statement still names `code_edges` alone, and
   `test_no_statement_reads_both_graphs` re-ran green.
3. **A count of what was skipped, surfaced.** `DerivedAssertions.skipped_by_language`
   (distinct sources dropped, keyed by language) and `assert_repo_graph`'s return dict
   carry it. The rationale is in the field's comment: an operator looking at a Go
   repository that asserts nothing must be able to see that the deriver *declined*,
   rather than infer that the repository has no dependencies.

**Plus the reviewer's stated minimum, kept as a second layer behind the gate.**
`_MALFORMED_NAME` rejects any candidate carrying whitespace, a quote, a statement
terminator, a bracket or `::`. A package name is one lexical token; the language gate
should already have caught anything else, and this is the last stop before a name becomes
an `entities` row. Keeping both is deliberate — the gate bounds the ecosystem, the shape
check bounds the individual name — and each is drilled separately below.

**The one narrowing I made, and why.** The gate restricts the *dependency* derivation
only. Language entities and the repo entity still mint for every indexed language,
because `rust` and `go` as `language` entities are *correct* facts — the wrong facts were
only ever the ones read out of import statements. I did remove one adjacent wrong fact in
the same family: `unknown` is `_fallback_parse`'s label for a file no grammar handled, not
a language a repository is written in, and it was being minted as a `language` entity. It
is excluded now, with a test.

**Drills.**

| mutation | outcome |
|---|---|
| language gate removed (derive from every language) | `test_a_language_the_deriver_cannot_parse_asserts_no_dependency` and `test_a_polyglot_repo_derives_from_the_half_it_can_read` failed (2 failed, 63 passed) |
| `_MALFORMED_NAME` check removed from `dependency_name` | all five parametrisations of `test_a_name_that_is_not_lexically_a_package_is_never_a_dependency` failed (5 failed, 60 passed) |
| `".nim": "nim"` added to `code_parser.EXTENSION_TO_LANGUAGE` | `test_every_indexed_language_is_classified_one_way_or_the_other` failed (1 failed, 64 passed) |

All restored from pristine copies; suites green after each.

**New tests.** `test_every_indexed_language_is_classified_one_way_or_the_other` is the
tripwire the brief asked for — it reads `EXTENSION_TO_LANGUAGE` from the indexer (in the
test, so `code_parser` never enters the deriver's import closure), adds `unknown`, and
fails the build naming any language neither set classifies, with a failure message that
says which of the two decisions to make. It also asserts the two sets are disjoint.
`test_a_language_the_deriver_cannot_parse_asserts_no_dependency` drives a four-language
repository through every `target_key` shape from the finding's table and asserts the
derived entity names are **exactly** the repo and its four languages, plus the exact
skipped counts. `test_a_polyglot_repo_derives_from_the_half_it_can_read` proves the gate
is per file. `test_an_unparsed_file_never_becomes_a_language` covers the `unknown`
narrowing. `test_a_name_that_is_not_lexically_a_package_is_never_a_dependency` covers the
shape check on five real shapes.

`_seed_repo` gained the ability to attribute an import to a named file (a bare string
still means the repo's first file), which is what makes the per-file gate testable.
