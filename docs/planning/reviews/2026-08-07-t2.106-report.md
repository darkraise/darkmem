## The ruling, per purpose

**`synthesis` — now writable.** `LLMConfigUpdate` (`backend/app/schemas/config.py`)
gained a `synthesis: LLMPurposeConfigUpdate | None = None` field; no route change was
needed because `update_llm_config` already loops over all of `PURPOSES` and reads each
one with `getattr(body, purpose, None)`, so once the field exists on the model the
write path is live. Reasoning: `synthesis` is seeded inert (doc 11 §6, no consumer
until T3.02), so a mis-set connection has no runtime effect until article synthesis
ships — widening the write is cheap and reversible, and nothing today reads the row.

**`verification` — stays read-only, deliberately, not by oversight.** `LLMConfigUpdate`
does **not** declare a `verification` field. Reasoning, in full:

- `VerificationJudge` (`app/services/verification_judge.py`) is live and dispatches on
  this purpose since T2.26 (not "seeded, no consumer" — that description is stale per
  `CLAUDE.md`'s LLM-configuration section).
- Its qualification record is G-D's gate evidence (doc 17 §6): a precision/recall
  measurement pinned to one resolved model identity
  (`judge_identity`: `model`, `base_url`, `api_kind`, `dimensions`, `reasoning`,
  `params`). Repointing that identity through a settings form is a real capability
  with a real failure mode — a judge qualified on one model, then silently repointed
  to another, has a qualification record that no longer describes what runs.
- **The read-half of the safety story already exists and needed no new code.**
  `VerificationJudge.judge()` (the only gated door) calls `qualification_state` on
  *every* call, which re-derives `judge_identity_hash` from the currently resolved
  config and compares it against the recorded hash. A mismatch raises
  `JudgeNotQualifiedError` immediately — detected, never remembered, fail-closed. So a
  repoint cannot silently keep serving stale verdicts once it happens; the very next
  `judge()` call refuses loudly. (On this machine there is no qualification record on
  disk at all today, so `judge()` already refuses unconditionally regardless of what
  `verification` points to — confirmed: `app/services/verification_qualification.json`
  does not exist.)
- **What is missing is the write-time half** of the story: warning an operator before
  the save that a repoint will strand the current qualification, or explicitly
  invalidating the on-disk record at the moment of a repoint. Building that means
  touching the verification ladder's enforcement path
  (`verification_judge.py` / `qualification_state`), which the brief's own scope
  boundary excludes ("do not change what any purpose does, or touch the judge") and
  which the runbook's escalation rule places at Opus/Fable tier ("the supersession and
  verification ladders" are named invariant-bearing work), not Sonnet-tier wire-contract
  work. **Read-only here is the complete and correct answer until that follow-on task
  exists**, and it is recorded as a deliberate ruling, not a punt: the docstring on
  `LLMConfigUpdate` states this reasoning in full, and the UI's copy states it too
  (`TierCPurposeCard`'s "live" branch, `frontend/src/features/settings/components/llm-tab.tsx`).

This resolves the asymmetry **per purpose**, not by symmetry: I did not make both
writable, and I did not make both read-only.

## What the UI now tells an operator

The LLM settings tab (`frontend/src/features/settings/components/llm-tab.tsx`) renders
seven editable purpose cards (the original six plus `synthesis`) and exactly one
Tier-C read-only card (`verification`). Before this task both `synthesis` and
`verification` rendered as disabled, read-only cards with a shared "read-only here"
caption; the request-side wire (`LLMConfigUpdate`) matched that — a write to either was
silently dropped by pydantic's default `extra="ignore"`, so nothing looked editable
that wasn't. That parity is preserved and made honest per purpose:

- `synthesis` moved out of `TIER_C_LLM_PURPOSES` into the normal purpose list
  (`LIVE_PURPOSE_META`, `LLMPurposeName`, `CURATED_LLM_PURPOSES` for the demo fixture).
  It now has real inputs, a Save button, and a live-reload confirmation on save —
  because the wire genuinely accepts the write.
- `verification` is the sole remaining `TierCPurposeCard`. Its copy no longer says
  "editing this row lands with a separate task" (which would misdescribe an
  undecided question as pending work); it now states the ruling and the reason: the
  qualification record is G-D's gate evidence pinned to a resolved model identity, the
  judge already refuses on a mismatched identity, and the write-time guard that would
  make editing safe is out of this task's scope.

No field looks editable and silently drops its write. `verification`'s inputs are
`disabled`, unlabelled for `aria-label` (proven by a test asserting
`screen.queryByLabelText("verification model")` is absent), and the card carries no
Save button — verified directly in `settings-llm.test.tsx`'s
`"verification carries no editable inputs and no Save button"` test, which walks the
rendered card and asserts every `textbox` role inside it is disabled.

## What went wrong along the way (honest accounting)

- **Backgrounded the floor run without meaning to, twice.** The Bash tool's default
  120s window auto-backgrounds a command that runs longer, and I did not pass the
  tool's own `timeout` parameter on the first two `pytest -q` invocations (I had only
  wrapped the shell command in coreutils `timeout`, which does not affect the tool's
  own window). The coordinator caught this and I addressed it: killed both stray
  background runs, then re-ran with the tool's `timeout` parameter set explicitly
  (580000ms), which kept the run genuinely foreground and blocking. All commands from
  that point on, including the final full floor and the full frontend trio, ran to
  completion in the foreground with an explicit tool-level timeout.
- **One real test failure surfaced on the first full-floor run**, not predating my
  changes: `tests/test_verification_judge.py::test_only_the_judge_module_reaches_the_verification_purpose`.
  My `LLMConfigUpdate` docstring named the judge module by its file path
  (`` `app/services/verification_judge.py` ``), and the single-door scan that test
  runs flags the literal substring `verification_judge` appearing anywhere under
  `app/` outside its two-module allowlist (`verification_judge.py`,
  `contradiction_scan.py`) — it cannot distinguish a comment referencing the module
  from code that reaches it. This is the guard doing its job on an incidental
  docstring mention, not a bug in the guard; I did not touch the scan or its
  allowlist (both are the verification ladder's own enforcement, out of this task's
  scope). Fixed by rewording the docstring to describe the module without spelling its
  filename (commit `c4a5d32d`), re-verified the specific test, then re-ran the whole
  floor clean.
- **A lane worktree has no `frontend/node_modules`** (gitignored, `git worktree add`
  does not populate it) and there is no documented automatic fallback for frontend the
  way there is for the backend `.venv`. I symlinked
  `frontend/node_modules → /root/repositories/darkmem/frontend/node_modules` after
  confirming `package.json` and `package-lock.json` are byte-identical between the
  main checkout and this worktree. The symlink is left in place (gitignored, not
  committed) so a follow-up `./scripts/gate.sh` run in this worktree does not hit its
  `node_modules not installed` preflight block.
