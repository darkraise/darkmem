## New breakage in the fix diff

**One new Minor, recorded — not loop-extending.** The fold leaves the
retired row's `review_state` untouched, and a `disputed` fact carries
`review_state='open'` by construction (it rides the same UPDATE in
`set_verification_status`). So a fold whose retiree is `disputed` (keeper
`confirmed`, or an equal-disputed tie) leaves an **expired** row in the
human review queue: `build_facts_query`
(`app/services/review_queue.py:253`) filters only `review_state='open'`
with no liveness predicate, and `verification_recompute`'s slice filter is
`expired_at IS NULL`, so no machine pass ever revisits the row — it sits
in the queue until a human clears it by hand. The state is already
representable today (a stated-expiry lapse on a disputed fact produces
it), the cost is one confusing human review per such fold, and no
truth-layer property is violated — the queue is a to-do surface. Cheapest
fix, whenever the surface is next touched: either clear the retiree's
`review_state` in the fold (it is a withdrawn duplicate identity, its
dispute now lives with the keeper's evidence) or give the review queue a
liveness predicate — the latter is T2.62's design decision, not this
pass's.

Checked and clean otherwise: the `merged` journal write cannot outlive a
rolled-back pair (nested savepoints); the cursor state commits with the
runner's one commit and a failed run leaves it un-advanced (retry
re-probes the same window); `MergedPair`'s two new fields and
`MergeOutcome.wrapped/cursor` have no stale consumers; the widened
candidate row shape has no caller outside the module and its tests; the
`_RENAME_FACT` on a just-retired row correctly repoints its ids too, so
the expired duplicate never dangles; renamed keys on expired/window-closed
rows cannot violate the partial unique.
