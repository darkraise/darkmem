## 1. The root cause, and the one-line fix that is not the deliverable

`benchlib/ingest.py`'s pre-creation step builds every row through `MemoryCreate` and never
sets `origin_key`. `retrieval_gold.seed_memory_rows` does the same. With it absent, every
fact's provenance folds into `fact_sources`' reserved unknown-origin bucket, which counts
as **one** origin per fact however many rows land in it and is excluded from both gates by
`attributable_origins`. That is why T2.40's 62 facts could not promote: `COUNT(DISTINCT
origin_key)` could never exceed 1, and no gate could fire to lower N from 3 to 2.

Setting `origin_key` is a one-line fix and it is **not** the deliverable. Assigning a
unique key per memory would have promoted everything instantly and would have been a lie:
corroboration means independent capture sessions asserted the same thing, and one
assertion relabelled N times is an echo with N names. The deliverable is a corpus whose
*content* genuinely corroborates.

## 2. What the corpus says, and why each part is corroboration rather than echo

`backend/scripts/benchlib/promotion/corpus.json` — 66 captures, **33 claims**, **10
distinct capture sessions**, three projects.
sha256 `242cd4afeb3c6470bd32e3583c8fe5915053052f4760b4fef7d69f71dc97ddbf`.

Session identity is spelled the way the capture doors spell it
(`resolve_origin_key`): `<source>:<per-boot-agent-run-id>`, so one agent run is one origin
however many memories it saves. Ten sessions across `claude-code`, `codex` and `mcp`.

**`diversity` — project `default`, 11 claims.** A payments service. Three agent sessions
working on it over ten days each recorded dependencies they had just read
(`payments-gateway depends on httpx…`, `…on pydantic…`, `…uses redis as its
idempotency-key store`). Independently, the repository itself is indexed, and
`code_deriver` derives the same dependency set from its parsed imports. Two attributable
origins of two kinds (`memory`, `code`) is the diversity gate at N = 2.

This is genuine, not contrived: the parse and the note are two witnesses that cannot have
copied each other. It is also doc 10 §6's designed bridge, and `fact_lift._lift_one_code`
documents this exact case — a triple the memory side lifted first receives the repository
as *an ordinary second origin*, born-corroborated never applies, and the fact climbs by
the count. **Ordering is load-bearing**: the memory lift runs first. Reversed, the same
facts would be born on the rung with no journal row and would be invisible to every G-C
metric.

**`time_gap` — project `atlas`, 10 claims.** A data platform. Each operational fact was
recorded in early April by one session and independently re-recorded in mid-May by a
*different* session, during an incident review — 40-odd days apart. Two attributable
origins ≥ 7 days apart is N = 2. The second capture is a re-verification, not a copy:
"Confirmed during the incident review that atlas-ingest runs on kubernetes", "Checked the
topic list again", "The billing review confirmed…".

**`none` — project `ledger`, 10 claims.** An incident week in which three separate agent
sessions each recorded the same platform facts within three days. No gate fires (same
kind, span 2 days < 7), so the default N = 3 applies and three origins meet it exactly.

**The two designed refusals — project `ledger`, 2 claims.** These are the point of the
corpus as much as the promotions are.

- **`echo`** — `ledger-core uses cassandra`, saved three times across three days by **one
  session**. Three provenance rows, one origin. It must never promote.
- **`under_sourced`** — `ledger-exports uses avro`, asserted by two same-kind sessions one
  day apart. k = 2 against N = 3. It must never promote.

Both held at `candidate` in the run, with the origin counts that explain why (§4). A fact
that does not promote is a result.

Projects are used to isolate the three groups: `triple_key` embeds `project` verbatim, so
a claim in one workstream cannot accidentally acquire a corroborating origin from another
through a shared entity name. Three concurrent workstreams in one vault is realistic, and
it makes the design auditable rather than dependent on entity-name luck.

## 3. Driven versus stubbed — the boundary the gate's credibility rests on

**Driven — every fact, every provenance row, every ladder decision and every `verified`
event in the measured window was written by shipping code.** In order:

| Step | Shipped code |
|---|---|
| extraction, classification, entity/relation graph | `ProcessingPipeline.process_batch` (all five phases) |
| Layer-2 facts + `memory`-kind provenance | `fact_lift.run_lift` to exhaustion |
| the repository's Layer-1 assertions | `code_deriver.assert_repo_graph` |
| Layer-2 facts + `code`-kind provenance | `fact_lift.run_code_lift` to exhaustion |
| the promotion decision and its journal row | `verification_recompute.run_recompute` → `verification_ladder.recompute_fact` → `KnowledgeTripleRepository.set_verification_status` |
| the measurement | `benchlib.promotion_metrics` + `promotion_bars.JOURNAL_COMPLETENESS_SQL` |

No `events` row, no `verification_status` and no `fact_sources` row is written by hand
anywhere in `promotion_corpus.py`. The promotion count in §4 is read back **from `events`
by SQL** (`_PROMOTIONS_BY_GATE`), not from a counter the harness kept.

**Stubbed — two inputs, both of them corpus, neither of them ladder input.**

1. **`install_repo_fixture` writes the three tables a completed index run would have
   left** — `repositories`, `code_files`, `code_edges` (5 files, 12 import edges,
   `repo_fixture.json`, sha256 `c0b3605d…`). It stands in for cloning and indexing a
   repository, which needs a network and a working tree a gate run does not have. Writing
   those rows by hand is the same act as writing the memory corpus by hand: what may not
   be hand-written is what the ladder *reads to decide*, and none of it is. `assert_repo_graph`
   derives the assertions, `run_code_lift` mints the facts and the `code`-kind provenance,
   and the ladder decides from that provenance. A test asserts every fixture import
   survives the deriver's own two refusals (`is_internal_import`, `dependency_name`), so a
   fixture edit cannot silently empty the diversity bucket.

2. **`simulate_capture_time_provenance` moves each `memory`-kind
   `fact_sources.created_at` back to the capture time of the memory that asserted it.**
   This is a simulated clock and it is the one place the harness touches a row shipped code
   wrote. §5 is the whole argument and §6 measures exactly what rests on it.

Not driven at all, and therefore not evidenced by this corpus: the contradiction veto's
model arm, the human review doors, `citation_reverify`, and any demotion path. §7.

## 5. The simulated clock, stated plainly

`fact_sources.created_at` defaults to `now()` and `add_source` never overrides it, so the
column records **when the lift wrote the provenance row**, while doc 08 §4.1 defines the
time-gap gate over *assertions* — "≥ 7 days apart across distinct sessions". In production
the lift runs on a two-minute cron beside live capture, so the stored timestamp tracks
capture time and the proxy is faithful. **A corpus ingested in one pass destroys the
proxy**: every provenance row lands inside the same second however far apart the captures
it describes actually were.

Two consequences, and the second is a finding for the gate owner:

1. Without intervention the corpus's declared session timeline is silently discarded, and
   a corpus written to exercise the date rule measures something else.
2. **The `time_gap` gate is unreachable on *any* backfilled corpus**, not only this one —
   including a corpus imported from a production export. Anyone planning a post-cutover
   G-C measurement over restored data should know that the bucket will be empty for
   reasons that have nothing to do with the data.

`simulate_capture_time_provenance` restores the declared timeline into the column the gate
reads. It is the same move `ingest._create_memory_rows` already makes one layer down for
`memories.created_at`, on the argument recorded there. Three properties bound it: it writes
one column and nothing else (no status, no journal row, no provenance row that did not
already exist); the value comes from the committed corpus, so re-running is deterministic;
and `code`-kind rows are untouched, because the repository really was indexed now.

It is still a simulation. It is named that way in the code, printed as `SIMULATED CLOCK` in
the run header, and §6 measures the corpus without it.

## 7. What this corpus does **not** evidence — read before reading the numbers

Four things, and the first two matter most.

**7.1 The false-promotion audit's "clears=True" is vacuous, and the committed predicate
cannot tell.** `false_promotion_min_corroborations` (20) is a *denominator* floor, and my
corpus meets it — 31. But both numerator arms are still inoperable, exactly as T2.40
found: machine disputes reach the ladder only through `VerificationJudge.judge()`, which
refuses unconditionally without a qualification record (T2.41 behind T2.54's gold), and
human rejections flow only through a review door nothing in this run drives. There is a
third reason specific to this corpus: `contradiction_veto`'s deterministic arm is the
inverse-replacement rule alone (`SINGLE_VALUED_RELATIONS` is empty today), and the corpus
contains no REPLACES-family edge, so even the *model-free* detector cannot fire. **A rate
of 0.0000 over 31 corroborations here measures inoperability, not precision**, and the
committed decidability predicate reads it as decidable. That gap is a finding about the
bar, not about the corpus, and it is the gate owner's to rule on.

**7.2 A promotion rate of 1.000 in every bucket measures the corpus design as much as the
ladder.** T2.40's own option (b) predicted this. Every eligible fact promoted because the
corpus contains no fact that meets its bar and is then withheld — there is no standing
dispute and no supersession block anywhere in it (`blocked = 0` in every bucket). The
committed floor is 0.5 and is explicitly a liveness-and-honesty bar rather than a rate
target, so 1.000 clears it trivially and carries almost no information. **The deliverable
of this task is decidability and journal liveness, not the rate.** A corpus that exercised
the withheld path would need a live veto, which is 7.1's dependency.

**7.3 Extraction convergence is a property of this corpus, not a guarantee.** The claims
promote because 33 designed triples survived LLM extraction into the same
`(project, subject, rel_type, object)` identity across sessions. That is a real property —
it was measured, not assumed, and the warm cache makes it stable — but content phrased less
canonically would converge less, and a future edit that rewords a pair can silently drop a
claim out of its bucket. The design guard (§8) catches origin and timing edits; it cannot
catch a rewording that changes what extraction produces. The run's own denominators are the
check for that.

**7.4 Scale.** 38 facts and 66 captures. `fact_lift`'s `_PENDING_GROUPS` documents that its
correlated lateral is O(groups × facts) and "does not scale to G-C volume". Nothing here
tests the ladder at production volume.

## 8. What keeps the corpus honest after I stop looking at it

The failure worth preventing is not a crash — it is a corpus that still loads, still runs,
and still produces numbers while asserting a corroboration structure it no longer has.
`validate_corroboration_design` runs inside the loader and checks every claim against its
group's declared shape: origin counts against `CORROBORATION_N_DEFAULT` /
`CORROBORATION_N_DIVERSE` and the cross-origin span against
`CORROBORATION_TIME_GAP_DAYS`, all three **imported** from `fact_sources` rather than
re-typed, so a corpus validated against a stale copy of N is not representable.

Three edits it refuses, each of which would otherwise pass silently:

- giving an echo's saves their own `origin_key` — the exact "make everything promote" move;
- pulling a `time_gap` pair inside seven days, which reclassifies its facts into `none` at
  an N they cannot meet;
- stretching a `none` trio past seven days, which moves it out of the bucket it exists to
  populate.

The loader separately refuses any entry whose `origin_key` is absent, blank, or carries the
capture layer's `unknown:` marker — T2.40's defect, refused at the door, because a fact
that cannot corroborate is otherwise indistinguishable from one that merely failed to.

**Mutation-proven, not asserted.** With `max_origins`, both gap rules and the seeder's
`origin_key=` argument broken on purpose: **4 failed, 14 passed** — including
`test_seeder_writes_origin_key_onto_the_memory_row` failing with `assert None ==
'claude-code:t2108probe'`, which is T2.40's root cause reproduced on demand. Restored from
my own file copy: **18 passed**.

own file copy, never `git checkout --`. No process left running — the gate reaps its own
