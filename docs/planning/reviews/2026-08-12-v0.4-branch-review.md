# v0.4 whole-lane branch review — synthesised articles, shipped unlabelled

**Branch:** `feat/e3-synthesis-and-reach`, tip `a976cd4c`. **Scope:** T3.02, T3.03,
T3.04, T3.05, T3.06, T3.23 and the held-marker work; only T3.05 previously reviewed.
**Lens:** ship-readiness for a release that puts synthesised prose in front of a reader.
**Reviewer:** Fable-tier whole-branch adversarial review (runbook branch-review contract).
**Method:** every number and behaviour below was re-run, not read — private database
`darkmem_test_v04` (created for this review, dropped at the end), the full article-lane
backend suites re-executed there (377 passed, 2 skipped), plus two purpose-built repro
drivers whose outputs are quoted verbatim. The controller's gate was running concurrently;
the shared `darkmem_test` was never touched.

## Verdict — do not cut

**Do not cut.** One Critical, reproduced end-to-end: the first article an install
synthesises and embeds makes every project-scoped composed read in that project raise —
`POST /api/v1/knowledge/search` 500s, MCP `knowledge_search` errors, project-scoped chat
turns die, and the T3.10 inject fill has nothing to consume — because T3.23 wired the L3
channel into a composition whose badge producer still mints badges for facts only, and
`compose()` refuses a badge-less article by pinned design (`test_an_article_missing_from_a_
lookup_that_ran_is_refused_too` was written as the inheritance notice and nobody picked it
up). Every per-task suite is green because the one "wired into the composition" test is
source inspection, not execution. The fix is not a hotfix: it needs a decision about what
an article's badge *is* (doc 12 §4 says articles carry one on the same terms as facts),
plus the stale label carried onto the composed wire (Important 1, same seam), and then a
driven test of the join. Beside it sit five Important reader-facing defects — all small —
and the G-E corpus-share bar that the ledger simultaneously calls stated and not stated,
pinned by no test. Everything else in the lane held up under attack: the claim gate
fail-closes on every article door, the honest-empty story is real (with two UI copy/default
defects noted below), the schema change is complete and its partial index is EXPLAIN-pinned,
the job's cost is bounded, and the held-marker ruling was implemented faithfully. One
consolidated fix wave (C1, I1–I6), then a scoped re-review of the composition seam, and
this cuts.

## Critical

### C1 — The first embedded article breaks the composed read for its project

`LayerCompositionService.derive_badges` (`backend/app/services/layer_composition.py:1276`)
mints badges for `id_kind == "fact"` only — its docstring still says "nothing mints an L3
candidate here yet", which stopped being true when T3.23 landed `_article_channel` and
`article_candidate(...)` into `search()` (`layer_composition.py:1481-1495`). `compose()`
then calls `_badge_labels` for every candidate whenever a badge dict was derived (always —
`derive_badges` returns `{}`, not `None`), and `_badge_labels` **raises ValueError** on an
article absent from the lookup (`layer_composition.py:552-560`) — behaviour pinned by
`tests/test_layer_composition.py:1235` as the contract the channel's shipper inherits.

**Reproduced** (driver: seed one `candidate` article + one `article_embeddings__revfp_8`
row in a fresh baseline DB, run `search("postgres", project="default")` exactly as both
doors do):

```
RAISED: ValueError: the badge lookup ran and produced none for article:06f345df-…;
doc 12 fixes the badge as present on every L2/L3 row, …
```

Blast radius, verified in the tree:

- `POST /api/v1/knowledge/search` and MCP `knowledge_search` catch only
  `CompositionUnavailable` (`api/routes/knowledge_search.py:80`, `api/mcp/server.py:1260`)
  → unhandled 500 / tool error. The whole response dies, so the memory and fact channels
  that succeeded are lost with it.
- Project-scoped chat (`chat.py:261` passes `context["project"]` through) dies the same
  way; wide chat survives only because `project=None` skips the article channel.
- T3.10's inject fill consumes a `ComposedResult`, so a project-scoped inject refresh has
  nothing to render once the search raises.
- The channel has no distance threshold — one article in a project is a candidate on
  *every* query in that project. This is not a corner; it is the standing state of any
  install one tick after its first successful synthesis+embed.

Why four green suites missed it: `test_articles_channel.py::TestComposition::
test_the_channel_is_wired_into_the_composition` asserts `"article_candidate(row,
channel_rank=rank)" in inspect.getsource(...)` — the join is proven by string presence,
never executed with the badge lookup in the loop. This is the cross-task defect class the
whole-branch review exists for: T3.23's channel is correct in isolation, the composition's
refusal is correct in isolation, and the join was tested by neither.

**Fix shape (for the wave, not prescribed in detail):** decide the article badge (doc 12
§4 owes one; the producer is `fact_badge.row_labels`, which already accepts
`id_kind="article"` + gate — what is missing is the `Badge` object and its claim sentence
for L3), extend `derive_badges` to mint it, carry `stale` (I1), and replace the
source-inspection test with a driven `search()` over a seeded article — the exact driver
this review used is a starting point.

## Important

### I1 — The article's stale label is dropped on the composed wire (same seam as C1)

T3.23 done-when 4: "a stale article is returned labelled stale, not withheld." The channel
does label it (`row["stale"]`, `articles_channel.py:2422-2424`) — and then `_labels()`
copies only `project`/`verification_status`/`label_suppressed`/`review_state` into
`ComposedRow.labels`, and `ComposedRowLabels` (`schemas/knowledge.py:59`) declares no
`stale` field, and its own docstring records that pydantic drops what a model does not
name. So even after C1 is fixed, the composed doors serve a stale article with no stale
label — a stale article that reads current, the exact lens-1 failure. Masked today only
because C1 raises first. The list/detail doors (`articles_read`) do serve it; the composed
doors must too, or the done-when is unmet where it matters most (the surface agents read).

### I2 — Review-queue article lane: a page returns up to 2×limit and paging is broken

`list_open_articles` (`review_queue.py`) runs both arms with the *same* limit/offset and
concatenates. Reproduced against seeded rows (3 open + 2 held):

```
page limit=3 offset=0 -> 5 items, total=5
page limit=3 offset=3 -> 0 items
```

`limit=3` served 5 rows; the next page a client computes from `total` is empty. No row is
lost across pages (the arms are disjoint by the `IS DISTINCT FROM 'open'` predicate), but
the wire contract (`limit: le=200`) is false and any client that trusts page size
mis-renders. Fix: partition the limit/offset across the arms (open arm first, held arm
fills the remainder) or serve the held lane as its own paged arm parameter.

### I3 — `counts()` excludes the held arm the lane serves

Same seed: `counts endpoint -> {'facts': 0, 'articles': 3}` while the lane lists 5. The
queue badge under-reports exactly the rows the 2026-08-12 ruling exists to put in front of
a human; a held-only project shows `articles: 0` while its lane has rows — a surface
reading empty while it is not (lens 2, inverted). Fix: `counts` adds the held arm's count
(reusing `build_held_articles_query`'s count SQL, the module's own anti-drift rule).

### I4 — Articles tab live default project is the demo constant `"darkmem"`

`articles-tab.tsx:165`: `useState("darkmem")` survives from the demo fixture into live
mode. A real install whose articles live in `default` (the pipeline default) first renders
`?project=darkmem` → zero rows → "No articles yet" — and the project dropdown is derived
from the *filtered* result set, so it offers nothing but "All projects" as a hint that
anything exists. A healthy install reads empty on first load (lens 2). The `.real` test
suite cannot see this because it mocks `apiFetch` ignoring query params. Fix: default to
"all" (or the app's active project context).

### I5 — On every real install, the tab's empty state contradicts its own withheld strip

With G-D open every synthesised article is `review_state='open'` (unmeasured), so the
standing state of a live install with articles is: `shown = 0`, `withheld = N`. The tab
then renders the exclusion strip "N articles — review_state=open — withheld from the
corroborated view…" directly above the EmptyState copy "**nothing is being withheld from
you here**" (`articles-tab.tsx`, the `shown.length > 0 ?` branch). Two sentences on one
screen assert opposite things; the second is false whenever the first renders. Fix: the
EmptyState copy must branch on `withheld > 0` (e.g. "all N articles for this project are
in review — none is servable as knowledge yet"). Also minor: `withheld` counts only the
fetched page (default limit 50).

### I6 — G-E's corpus share: stated in prose, pinned nowhere, and the ledger contradicts itself

- `docs/planning/gate-ledger.md:1546` — the section heading reads "**not stated, and owed
  before T3.24 runs**"; the body two lines later reads "**Stated 2026-08-11 by derivation,
  owner-ratified: 0.90**", and the G-E summary rows (lines 30, 1501) agree with the body.
  The heading is stale on exactly the kind of "here is the truth" line invariant 23 names.
- The 0.90 exists **only** in ledger prose: no config row, no constant, no test anywhere
  in the tree (verified by search over `backend/`, `scripts/`, tests). The dispatch's
  premise "both bars … pinned by test" is therefore half-true: 0.95 is pinned twice
  (`test_claim_entailment.py:296-300` — `DEFAULT_COVERAGE_THRESHOLD == 0.95` and the
  anti-laundering `!= 0.90`), the share is pinned by nothing. The repo's own standard is
  the promotion-bars precedent — bars committed as code before the first measurement so a
  move is a visible two-file diff. Fix before T3.24 exists: land the share as a committed
  constant beside where the runner will live (benchlib, per the promotion-bars shape) with
  a pin test, and correct the heading.

**On whether the derivations hold** (the mandated question):

- **Runtime threshold 0.95 — holds, with one prose caveat.** Doc 17 §6's rule is as the
  ledger claims ("the truth-critical metric is barred at 0.95, the other at 0.90",
  restated in the 2026-08-08 amendment), the pre-commitment claim is true (the judge
  refuses without a qualification record, G-D is open, no coverage number exists anywhere
  to fit to), and the quantisation paragraph's arithmetic is right (19/20 is the first
  passing fraction with slack; below 20 claims the bar is 1.0). Caveat: the sentence
  "nothing about the failure changes because the instrument is an article-level fraction"
  elides that a *true* pass at 0.95 ships up to one measured-**unentailed** sentence in
  twenty under a corroborated badge — that sentence's citation row is simply absent
  (`write_coverage` writes rows for entailed claims only), so the reader's defence is the
  coverage readout and the visibly uncited span. That is a tolerated, measured residue,
  not an undetected one — different from the judge-precision failure the derivation
  borrows its number from. Worth one honest sentence in the ledger; not a reason to move
  the bar, which was stated before data and may not be moved to make a run pass.
- **Corpus share 0.90 — the derivation argument holds; the pin does not exist.** The
  "share does not price truth" premise is true in the code as shipped: a below-threshold
  article routes `candidate` + `review_state='open'` and is withheld from the corroborated
  view (verified in `measure_coverage` → `write_coverage` and the doors' tests), and a
  held re-synthesis never touches the standing article. Unfittability is also true. What
  is missing is entirely the mechanical half (I6 above).

## What was attacked and held

- **The claim gate, on every article door.** Seeded a `corroborated` article with no
  record: list door, detail door, MCP `article_get` and both review-queue arms all serve
  `candidate` + `label_suppressed` through `row_labels(id_kind="article",
  gate=article_claim_gate(...))`; the vault column is not rewritten; an unwired caller
  fail-closes; a minted *fact* record does not light an article; an open gate passed in is
  actually read (`test_claim_serving_gates.py`, all re-run). The T3.02 seams 1–3 from
  T2.95's review round are all closed, including widening the aggregate scan to rejoined
  f-strings after the shared predicate split a site out of it.
- **Coverage semantics.** `coverage = entailed/total claims`, lead included; `None` ≠
  `0.0` everywhere (backend enum, wire, both UI surfaces render "not measured"); 0/0 is
  `None`, never 1.0; one unmeasurable claim unmeasures the whole article (no shrinking
  denominator); an uncited claim blocks promotion outright regardless of fraction. The
  wire calls the column `coverage` and every surface labels it claim-support coverage.
- **Honest-empty.** Zero articles: list door returns an empty page, channel reports
  `ran=False` (never `failed`, so a fresh install is not flagged partially degraded), the
  synthesis tick over an empty corpus visits nothing, and the demo fixture is unreachable
  in real mode (`VITE_DEMO` build-time flag; the `.real` suite drives the live door and
  asserts no fixture rung renders). The two blemishes are I4 and I5 above.
- **Schema (brief item 3).** Three columns + `ix_knowledge_articles_resynthesis_held`
  match the ruling §3.2 exactly; the held lane's statement is EXPLAIN-pinned to its own
  partial index (`test_held_articles_explain_uses_their_own_partial_index`, re-run green);
  nothing reads a column that does not exist (suites + both doors driven); event types
  need no migration; doc 04 §8.8's table was amended to match.
- **Job cost (brief item 4).** Model calls per tick are bounded by
  `synthesis_budget × batch_size` plus ready stale articles; the F6 retry loop is closed
  (below); the debounce anchors journal one row per fact-set change, not per tick
  (re-read: the matched-anchor path writes nothing); `run_article_resynthesis` takes the
  synthesis pass's visited batch rather than a second cursor, so no N+1 across projects.
  Remaining per-tick reads are one hash query per live article (M5).
- **T3.05's staleness core.** Write and read hash bases are one function; the belief
  predicate is shared across all four L3 queries and pinned column-for-column against
  `OPEN_BELIEF_PREDICATE` (`test_article_citations.py:268-298`); supersession is three
  statements in one transaction with the marker cleared in the same UPDATE.

## Mandated triage

**T3.05 review F1 (debounce > lookback silently disables re-synthesis) — FIXED,
verified.** `_anchor_lookback = max(90d, 2×window)` derives the floor from the window;
`test_the_lookback_always_exceeds_the_window` sweeps the config range including the 8760h
ceiling.

**T3.05 review F2 (unmeasured draft retires a measured article) — FIXED, verified.**
The `standing_measured` exit holds the supersession when the draft is unmeasured and the
standing article has a written coverage; under open G-D behaviour is unchanged
(candidate replaces candidate). `_article_is_measured` reads the coverage column, not the
rung, so a human-ratified article is protected too.

**F6 (permanently-held subject retries at full price every tick) — CLOSED by the
held-marker work, verified.** `_held_on_this_fact_set` suppresses the attempt while
`resynthesis_held_hash` equals the current verified-set hash; suppression is counted
(`held_suppressed`, tested at `test_article_staleness.py:804`); attempts resume the moment
the set moves because the key is the hash; the marker's three exits (grounded
re-synthesis, set moved then grounded, set reverted → `_clear_stale_free_markers`) all
clear without a human. This matches ruling §3.5 exactly.

**F7 (two sub-minors) — both stand; neither blocks the cut.**
(a) The `superseded` journal payload's `fact_set_hash` is still the stale-scan snapshot
and can differ from the replacement row's stored hash when facts move between the scan
session and the per-article session. Honest trigger provenance; a reader comparing journal
to row can see a mismatch; cosmetic.
(b) `_SUPERSEDE_SQL` is still a blind UPDATE with no status guard — and it now also NULLs
the held-marker columns in the same blind write. No concurrent article-axis writer exists
(`POST /knowledge/articles/{id}/ratify` is confirmed unshipped by doc 12's 2026-08-11
amendment) and the job lock serialises ticks, so this remains a note that transfers, with
interest, to whoever builds article ratification: that task must add a status guard (or
`WHERE status <> 'superseded'`) before a second writer exists.
