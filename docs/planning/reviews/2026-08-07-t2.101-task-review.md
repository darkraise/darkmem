- **Task quality: Needs fixes** — one Critical (the merge repoints

The Critical is arguably plan-scope — the brief pointed at `knowledge_triples`
endpoint *ids* and nobody asked about the name copies — and its complete fix is
non-trivial (below). Reported at its real severity per charter; the controller
adjudicates whether it is a fix round here or a minted follow-up with the
residue documented. Either way the report's completeness claim ("everything
else is FK-cascade or transient") is not true as stated, and G-C should not
absorb it as true.

## Findings

### F1 — Critical. The fact layer's identity is name-keyed, and the merge moves ids but not names; the next `fact_lift` tick mints duplicate open facts.

`backend/app/services/entity_merge.py:331-339` repoints
`knowledge_triples.subject_id` / `object_id` and stops there.
`subject_name` / `object_name` / `triple_key` keep the losing name. But every
fact-identity consumer keys on **canonicalised names, not ids**, and the
canonicalisation is lexical only (lowercase + whitespace collapse,
`app/services/triple_key.py:36-37`) — `postgresql` and `postgres` are distinct
identities:

1. **Duplicate lift, mechanical and certain.** `fact_lift`'s pending predicate
   (`fact_lift.py:239-299`) reads assertions by joining `entity_relations` to
   `entities` **by id** and grouping on the **live names** — which the merge
   just changed for every repointed relation. Its dedup against existing open
   triples is `_canon(kt.subject_name) = g.subject_name` (lines 276-278); the
   already-lifted `postgresql X Y` row no longer matches the group, so
   `open_fact.id IS NULL` and the group re-qualifies as pending. The next tick
   lifts a **new** open triple `postgres X Y` from the same assertion set,
   while the old one stays open. Both fact_lift arms have this shape (the
   repo-asserted arm's dedup at lines 742-744 is the same join). With
   `DEFAULT_MIN_ASSERTING_MEMORIES = 1` (line 171) this is not gated behind
   corroboration.
2. **Permanent divergence.** The old row's name never matches a live group
   again: its corroboration stops accruing, its verification history is
   stranded under a name the graph no longer holds, `fact_sources` rows for
   the same memories sit on two open triples for one logical fact, and
   `FactsChannel` double-serves it. I found no healing mechanism — and
   rewriting the names retroactively is a fact-level merge of its own, because
   recomputing `triple_key` can collide with an already-open `postgres X Y`
   row on `ux_knowledge_triples_open` (exactly the collision-fold shape this
   task solved one layer down, at the relation level).
3. **Contradiction pairing goes blind across the boundary.**
   `contradiction_scan`'s same-endpoint arm pairs facts on
   `subject_name`/`object_name` (`contradiction_scan.py:287-289`). Pre-merge
   facts about the merged subject never pair with post-merge ones.

Why it matters at Critical: it is silent, permanent, and lands in the
gate-bearing truth layer — and it fails the task's own standard. The task
exists so the two indexing orders converge on one state; after the merge the
*entity* graph converges and the *fact* layer permanently diverges (the eager
order produces one `postgres` triple; the late order plus merge produces two
open triples). This is the same defect class the executor's own D6 repoint was
built to prevent — "silent, permanent, degradation in one direction" — one
table column to the left. Note the executor handled the name-copy class
correctly for `memories.technologies` (recomputed because names moved) and
missed that `knowledge_triples` carries the same class.

### F2 — Important. The candidate scan is a fixed prefix; entities past `candidate_batch` are never probed, and the report claims otherwise.

`entity_merge.py:141-159`: `ORDER BY e.created_at, e.id LIMIT :limit`, no
cursor, no persisted state, no rotation. The ordering is stable, so every run
probes the **same** oldest `candidate_batch` (default 200) repo-asserted
embedded entities; the set changes only when a merge inside the prefix deletes
a row. An install with more than 200 such entities — one large repo's imports
can mint that — never probes the rest, forever, with no error and no symptom:
precisely the "quietly wrong, no symptom" shape this codebase treats as a
defect (`index_debt`). The report's §4 says the pass "re-probes every
repo-asserted entity with a vector on every run"; that is false whenever the
population exceeds the batch, and the knob's help text carries the same
implication. The disclosed trade-off ("does not drain, rescan is cheap") was
judged on cost; the actual defect is **coverage**. Fix is small: a persisted
cursor (the anchoring job's `config`-row idiom) or a rotating ORDER BY.

### F3 — Minor. The repo-preference mutation (D9) is only probabilistically red.

`tests/test_repo_entity_merge.py:179-192` (`_pair`) inserts both rows in one
transaction, so `created_at DEFAULT now()` gives them equal timestamps. Drop
the repo-preference arm (the D9 mutation) and `_choose_survivor` falls through
equal ages to the id tie-break on two **random** UUIDs: `postgres` still
survives ~50% of runs, so D9a/D9b each go red only half the time (the drill
happened to observe red). The executor caught this exact fixture class in the
age test and fixed it there; the repo-arm fixture still carries it. Making the
memory-minted loser explicitly *older* makes the mutation deterministically
red (an age-fallback rule would then pick the loser). The other drills I
audited are deterministic — D14's replacement test (three descending UUIDs) in
particular is sharp.

### F4 — Minor. A narrow race can still write a dangling `subject_id` the merge can never repair.

`fact_lift` resolves entity ids with plain SELECTs (no lock). A lift that
snapshots the loser's id and commits its triple after the merge commits leaves
a dangling `subject_id` — the exact zero-salience rot the repoint exists to
prevent — and no later run can fix it (the loser's id is gone; nothing maps it
to the survivor). The window is small and Phase 5 is safe (its
`create_entity` upsert blocks on the merge's `FOR UPDATE` before relations are
written), so Minor; worth a line in the module docstring at most.

### F5 — Minor. A destructive, user-visible mutation journals nothing.

The merge deletes an entity row, rewrites relation endpoints and moves
memories' `technologies` — and writes no `events` row, though `"entity"` is
already in `OBJECT_TYPES` (`events.py:100`). An operator watching `postgresql`
vanish from labels and arrays has no audit trail. Precedent is mixed
(`graph_orphan_cleanup` does not journal either; requeue/discard do), so this
is triage material, not a block.

### F6 — Minor. All row locks are held until one commit at end of run.

The runner (`job_runners.py`, `make_repo_entity_merge_runner`) uses one
session and commits once after the whole batch. Savepoints release, row locks
do not: a first run over a large backlog holds `FOR UPDATE` locks on every
merged pair's entities and edges until the run ends, and capture writes
targeting those entities block behind it. Bounded in practice (SQL-only work,
no LLM calls, `max_run_seconds=900` is a ceiling not a duration) — but a
commit per pair or per small batch would shrink the window at no cost. No
invariant is violated (no fresh session is opened while locks are held).

## Adversarial checks that came back clean

- **Repointing completeness (ids).** Swept `0001_baseline.py` and
  `backend/app` for entity-id storage. Direct columns:
  `entity_relations.source/target` (FK cascade, repointed + guarded),
  `entity_embeddings__<slug>.entity_id` (cascade, every partition — verified
  by test), `knowledge_triples.subject_id/object_id` (repointed).
  `pipeline_failures.entity_id` is polymorphic memory/repo-scoped, not graph
  entities. `memory_communities` / `memory_community_members` reference
  memories only. `fact_sources` references facts, not entities.
  `events.object_id` can hold entity ids (`"entity"` ∈ OBJECT_TYPES) but the
  journal is append-only by design — leaving them is correct, same as deleted
  memories. `ppr_snapshot` is rebuilt in-process per run; nothing persisted.
  Chat's `selected_entity_id` is request-scoped. The **names** are the gap —
  F1.
- **Survivor rule.** Repo-asserted-wins converges with the eager order's
  canonicalisation (repo-first mints the repo name; memory canonicalises onto
  it — same end name either way, verified against Phase 4/5's flow). The
  both-repo-asserted and neither-repo-asserted arms have no eager analogue to
  converge with (the eager path never merges those pairs either), so
  older-then-id is a free choice, stated and tested from both sides. The pass
  structurally cannot reach a neither-repo pair (candidates require
  `repo_ids`); `merge_entities` called directly handles it via the age arm.
- **Collision folding.** Both directions rewritten (D3 red); the partner is
  provably locked (the new key contains the survivor, and both entities'
  incident edges are locked up front); the per-edge re-query handles the
  partner-was-just-moved case (tested,
  `test_two_edges_collapsing_onto_one_self_loop_fold_together`); fold unions
  run against the keeper's current row in SQL. The NULL-concat hazard in the
  fold (`NULL || array`, `x = ANY(NULL)`) is unreachable — all four columns
  default `'{}'` and every writer supplies values.
- **The self-loop justification is factually correct.** I checked the claim
  against the write path: `create_relationship`
  (`graph.py:185-233`) has no `source == target` guard and resolves both
  endpoints by name, so when Phase 4 canonicalises two spellings onto one name
  the eager path **does** write the self-loop row. Keeping it retroactively is
  convergence, as argued; `ppr_snapshot` (`WHERE source <> target`) and
  `review_ranking`'s salience arm (both directions exclude the subject)
  already exclude self-loops. Verified, not accepted.
- **The no-re-embed choice / invariant 2.** The candidate query joins the
  partition (an entity with no vector under the resolved fingerprint is simply
  not a candidate — skipped, disclosed, and the anchoring job's business);
  probes pass the same resolved fingerprint for the whole run, so every cosine
  is within one child table even if the embedder rotates mid-run; the pass
  writes no vector; the loser's rows leave via the cascade in every partition
  (tested). One inherited blind spot, not new to this pass: after an embedder
  rotation, a memory-minted entity with no vector under the resolved
  fingerprint is invisible to the probe — but it is equally invisible to
  Phase 4, so this is the dedup system's existing rotation posture, not a
  regression.
- **The T2.49 staleness argument holds.** I checked the disclosed
  repointed-relation vector staleness against what T2.49 actually built:
  `relation_embeddings.py:29-33` — the **rotation arm re-embeds the oldest
  slice of already-embedded rows**, explicitly "the backstop that makes
  renames converge". Name-change drift is corrected within one full rotation;
  the folded duplicate's vector is cascade-deleted immediately. The executor's
  judgement to add no second mechanism is right.
- **Test-vacuity hunt over the 22-test file.** The idempotence test asserts
  byte-identity of rows including array order and `created_at`, not a count;
  the append-order test is deterministically red under the D14 mutation
  (descending UUIDs); the equal-timestamp id tie-break asserts against the
  computed min-id, deterministic; the E2E asserts the two-node state *before*
  the merge so the single node after is attributable; both E2E probes assert
  the neighbour was actually **returned** at 0.974 so the refusal is
  provably `names_distinct`'s doing, not a missed threshold. The one
  probabilistic guard found is F3.
- **Threshold pinning.** The AST scan reads Phase 4's own
  `find_similar_entity(threshold=...)` keyword out of `pipeline.py` and
  asserts equality with `MERGE_THRESHOLD` — it would also fail if Phase 4
  stopped passing a literal. D7 red confirmed by the executor; logic verified
  by reading.
- **asyncpg CASTs.** Every raw-SQL param in the new module is cast, including
  both `uuid[]` array binds; `rel_type = :rel` infers from the column, same as
  existing code.
- **Invariant 15 / Tier C.** `entity_merge` is imported only by `main.py` and
  `job_runners.py` (the `entity_anchoring.py` match is a docstring
  cross-reference). Registered directly, not in the dream family; roster guard
  updated; capture and retrieval reach nothing in the module.
- **`entity_embedding_cache` left alone** — reasoning verified: the cache is
  name-keyed with no FK; a future memory naming the vanished spelling gets the
  cached vector, probes, finds the survivor at 0.974 and canonicalises — the
  eager path working. Purging would spend an embed to get a possibly-different
  answer.
