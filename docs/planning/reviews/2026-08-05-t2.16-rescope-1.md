## The two declines, re-derived

**M4 (no locks in `write_derived_edge`) — the commit-boundary claim is true and the
decline is sound.** Phase D runs in one session with one commit after the whole pass
(`memory_dream.py:2123-2135`); Phase W opens a session per batch and commits per batch
(`:2097-2118`), and `apply_associate` takes its two `FOR UPDATE` locks (`:968-969`,
`_LOCK_MEMORY` `:737-756`) inside that per-batch scope. Row locks survive savepoint
release, so mirroring the `FOR UPDATE` in Phase D would pin up to
2×`derivation_batch` = 400 `memories` rows until the end-of-pass commit — squarely in
the way of pipeline Phase-5 enrichment and supersession UPDATEs. The remaining
unlocked window is as benign as claimed: the candidate SQL filters
active-and-unexpired, the whole phase is deterministic with no model call, so the
window is sub-second, and the next pass covering either endpoint retires the stale
block. One narrowing the decline never weighed: `read_memories` (`:336-356`) re-reads
content but not status — adding a lock-free status re-check at write time would
shrink the window with none of the lock cost. Recorded as a deferred minor, not a
defect in the decline.

**M6 (no expiry predicate in the proximity filter) — both halves of the decline are
true.** `MemoryFilter` (`app/repositories/vector.py:52-77`) carries only
project/statuses/include_archived and is consumed by hybrid search, layer
composition, chat, graph and the vectors route — genuinely a shared retrieval scope
class. The self-healing claim holds: both `memory_relations` endpoint FKs are
`ON DELETE CASCADE` (`0001_baseline.py:370-375`) and `expired_memory_cleanup`
deletes the row (`job_runners.py:252-336`), so an expired-unswept memory holds a
derived edge only until the sweep. One overstatement noted: an *additive optional*
predicate field defaulting to off would not be repo-wide, so "changing it is
repo-wide" is stronger than the truth — but the harm analysis (transient, inherited
from the near-duplicate arm's identical filter at `:495`, cascade-healed)
independently supports declining in a scoped round.

## Is the I1 fix complete?

The fix covers exactly the arm-skipped case the finding named, and the review's own
fix shape. Two neighbouring shapes checked:

- **Dual-signal blocks:** `derived_block` (`:1505-1512`) always writes the `signals`
  map, so a block resting on overlap *and* proximity is spared under a dead canary
  even when the overlap half vanished — conservative in the right direction; the
  next healthy run re-derives and corrects the block. The singular-`signal` fallback
  in `_block_signal_names` covers only legacy/hand-written shapes and errs toward
  sparing. No hole.
- **The per-seed variant (§7b's recorded deferral) matters somewhat more than its
  framing suggests, but stays a defensible deferral.** §7b words it as "a seed with
  no row in the current partition after a rotation" — singular. The worst shape is
  whole-slice: immediately post-rotation, before the `reembed.py` backfill runs,
  *every* seed lacks a vector, the arm runs and returns nothing
  (`proximity_candidates` skips vectorless seeds, `:1407-1409`), `unmeasured_signals`
  stays empty, and each nightly slice strips its proximity edges with
  `spared_unmeasured` reading 0 — I1's magnitude, transiently. Three things
  distinguish it from the dead-canary case and keep it out of this loop: recovery
  exists (the backfill restores vectors and edges re-derive — churn, not loss, where
  the dead canary had no recovery at all); detection exists one arm over (the pair
  arm's whole-slice `SKIPPED_NO_SEED_VECTORS` warning, `:2072-2081`); and it takes a
  deliberate operator action whose runbook step is the backfill. The cheap follow-up,
  if wanted: when `seed_vectors` returns nothing for the whole slice, treat proximity
  as unmeasured — mirroring `:2072`. Recorded as deferred; the review ruled the
  variant arguable and the loop must not be extended with it.
