## I-1 — a lapsed dispute no longer strands a born fact at `candidate`

**The finding.** Driven end to end by the reviewer: a contradiction flips a
code-born fact to `disputed` (the veto beating the exception, which is right);
the counterpart lapses; recovery re-enters the count, which one origin never
meets, so the fact settles at `candidate`. The lift refused to re-grade an
existing row and the ladder's branch fires only for a fact *already at* the
rung, so no machine path put it back — while the repository still asserted the
triple that justified the rung in the first place.

### The option taken: (c), the lift re-grades

The ruling's first preference, and it landed cleanly. Concretely:

| Piece | Where |
|---|---|
| The decision | `fact_lift.restore_born_rung` — the birth's counterpart |
| Where it is reached | `fact_lift.reconcile_code_sources`, over the rows the withdrawal half **retained** |
| The write | `KnowledgeTripleRepository.restore_born_corroborated` → `_write_born_rung` |
| The counter | `CodeLiftOutcome.rungs_restored`, and the job log line |

**Why the reconcile pass and not the candidate scan.** The withdrawal half
already asks, per stored code provenance row, whether a live repository still
asserts that triple. A row it retains *is* a fresh parse of the same assertion,
read from Layer 1 in this tick — which is exactly the warrant doc 10 §6 calls
the verification. So the restore needs no new read, no widening of the
candidate scan's outstanding-work predicate (which would have put permanently
refused rows in the batch and starved it, the hazard `_PENDING_GROUPS` already
names), and it inherits the withdrawal's liveness join for free: a provenance
row whose repository is gone is withdrawn, never restored, and
`test_removing_the_repository_outright_invalidates_its_facts` now asserts
`restored == 0`.

**Why it does not widen the exception.** Two independent narrowings, drilled
separately:

1. **The evidence, not the caller.** `restore_born_rung` reads the fact's
   `OriginProfile` — the same object the ladder consults, so the two cannot
   drift — and refuses unless the origin count is exactly 1 and the only kind is
   `code`. That is the shape a birth leaves behind and nothing else.
2. **The rung it writes over.** The UPDATE's WHERE names
   `verification_status = 'candidate'` and the open-belief predicate, so a
   `disputed` fact is not a row the statement can reach. The veto's precedence
   is structural, not a check a caller performs.

**Why it cannot change what G-C's promotion rate counts**, which the dispatch
made a condition. One origin is below every threshold
`required_origin_count_for` can pick (`n_diverse` is 2), so the restored
population is disjoint *by construction* from the population the count could
promote — no `promote` row is taken out of the journal. And the restore itself
journals nothing, exactly as the birth journals nothing: born and restored rows
sit on the same side of the gate's measurement, which is the property the
reviewer measured (zero `verified` events for a born fact) and which
`test_the_restore_journals_nothing_and_stays_invisible_to_the_gate` now pins by
counting the stream across a full dispute/recover/restore cycle.

**The scope's honest cost, stated rather than hidden.** A fact with **two** code
origins that falls off the rung stays at `candidate` until the count reaches it
(two same-kind origins need `n_default` = 3 unless their assertions are ≥ 7 days
apart, and a code origin's timestamps never move). That is the under-claiming
direction, it needs two repositories asserting one triple — which, since the
subject of a derived dependency fact is the repository's own name, means two
repositories of the same name — and taking it instead would have meant either
pre-empting a promotion the count would have journalled, or computing the
ladder's arithmetic inside the producer. `test_two_code_origins_are_left_to_the_count`
pins the behaviour so the residue is a decision on the record.

**One behaviour of the shipped code changed with it**, reported plainly: the
rung follows the *evidence*, not which producer reached the triple first. A fact
whose entire provenance is one repository's parse holds the rung whether this
path minted the row or found it, so `test_an_existing_fact_is_never_re_graded_by_the_code_lift`
could not survive verbatim — its fixture was an existing fact with **no**
sources at all, which the memory lift cannot produce, and after one tick that
fact's whole evidence is one code origin. It is replaced by two tests that
divide the same ground more honestly:

- `test_a_fact_a_memory_also_asserts_is_never_re_graded_by_the_code_lift` — the
  realistic shape (the existing fact has a memory source). It is *never*
  re-graded, across two ticks, and the test then drives `recompute_fact` and
  asserts the ordinary count promotes it and journals `["promote"]`. That
  assertion is the measured form of "the lift stayed out of the count's way".
- `test_a_fact_whose_whole_evidence_is_one_parse_is_raised_to_the_rung` — the
  other side, including that the tick which *adds* the source does not re-grade;
  only a later tick, having re-read that provenance against the graph, does.

### Why the other two options were worse

**(a), recovery restores the born rung in the ladder** — the fallback. It works,
but it moves the grant into `verification_ladder.decide`, and "holds a rung,
never grants one" is the sentence that made the exception branch reviewable in
one reading. Once the branch can grant, every future reader has to re-derive
which of its five predecessors constrain it, and the branch sits *below* the
veto and the count where a grant is hardest to bound. It also has to journal
something to be honest about a status the ladder moved, and any `verified` row
the ladder writes is a row G-C's rate and audit SQL see — so it would have made
restored facts measurable while born facts stay invisible, i.e. the same claim
counted two ways. (c) has neither cost: the ladder is untouched, and the door
that grants is the door that granted originally.

**(b), accept the under-claim and document it** — correct only if (c) and (a)
both failed. It leaves a real defect standing: a judge false positive that later
lapses permanently downgrades a fact whose evidence never changed and never
will, and the failure is silent — the row reads `candidate`, which is
indistinguishable from a fact that genuinely has one weak origin. Doc 10 §6 says
the parse is the verification; a permanent under-label after a lapsed dispute
says the parse *was* the verification until someone was wrong about it once.

## I-2 — the third writer's guarantee is behavioural now, and the rule is stronger

**The finding.** Mutating `BORN_CORROBORATED` to `"confirmed"` left all 21
honesty tests green while the writer minted machine-`confirmed` facts. The scan
is value-blind by design; the writer's own re-read compares against the mutated
constant, so it cannot catch itself; and the allowlist's admission argument
("binds a module constant") says nothing about the constant's *value*.

Three changes, each drilled:

1. **The pin, where the property lives.**
   `tests/honesty/test_human_only_confirmed.py::test_the_born_rung_writer_cannot_land_the_human_floor`
   drives both routes onto the rung and compares the landed status against
   `CONFIRMED` — a different constant, which is what lets the comparison fail.
2. **The rule itself, not just this writer** (the dispatch's ask). Two halves:
   - *In the code.* Both doors now share one statement,
     `KnowledgeTripleRepository._write_born_rung`, which validates its rung
     against `_MACHINE_WRITABLE_VERIFICATION_STATUSES` before executing. "No
     machine path reaches `confirmed`" becomes a property of the writer rather
     than of the constant it happens to bind — a fourth writer whose constant
     *is* `confirmed` is refused by the same check. That is the generalisation
     the reviewer said the old sentence lacked.
   - *In the suite.* `_PERMITTED_WRITERS` is now a mapping from writer to the
     behavioural pin **in this file** that drives it, checked by
     `test_every_permitted_writer_is_pinned_by_a_test_in_this_file`. Admission
     costs a pin, and the pin is reviewed beside the property rather than in
     whatever feature file the writer's author preferred. What no rule can check
     — that the named pin asserts the right thing — is stated at the test.
3. **The allowlist entry moved** from `open_born_corroborated` to
   `_write_born_rung`, because that is now the only scope that writes the axis
   for this exception. The count of permitted writers stays at three even though
   this round added a second door.

## M-2 — judged: no code change, recorded at the predicate

A `code`-kind row whose `source_ref` names no live repository would hold a rung
for one tick. Declined for three reasons and documented where the trust is
placed (`OriginProfile.parse_is_the_verification`):

- **No writer can create one.** `fact_lift` is the only producer of the kind and
  writes a live repository's id; the reviewer had to insert the row by hand.
- **It self-heals in one tick and the direction is bounded.** The next
  `fact_lift` tick withdraws it (the repo asserts nothing matching), and the
  following recompute opens the ordinary demotion grace.
- **Closing it costs more than it buys.** `OriginProfile` is a frozen dataclass
  with no session, and giving the ladder a per-decision read of the code side is
  precisely the crossing doc 10 §2 keeps out of it.

Worth adding: the *grant* side has no such window at all. The restore added
above runs only over provenance the reconcile retained against a live
repository's current assertions, so a dead-ref row can never grant a rung — it
can only, for one tick, fail to lose one.

## M-3 — the caller scan sees an aliased door

Fixed. `_references` matches an `ast.Attribute` with the method's name in **any**
position — so `f = repo.open_born_corroborated; await f(...)` no longer walks
past — plus `getattr(repo, "…")` for the dynamic spelling. The scan is
parametrised over both doors onto the rung, and
`test_the_caller_scan_sees_an_aliased_door` plants all three shapes against the
predicate so the guard is proven able to fail.
