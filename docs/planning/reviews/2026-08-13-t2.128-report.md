## The change

### 1. Resolution returns a report, and the dict is derived from it

`promotion_bars.py` gains `BarResolution` (per bar: `key`, `committed`,
`effective`, `requested`, `clamp`, `licence_bound`) and `BarReport`
(`resolutions`, `licence_row_present`, plus `bars` / `config_rows_present` /
`clamped`). `resolve_promotion_bar_report(rows)` does the merge-and-clamp;
`resolve_promotion_bars(rows)` is now exactly `resolve_promotion_bar_report(rows).bars`.

This ordering is deliberate and is the part that outlives the printing. A report
computed *beside* the resolution would be two code paths that agree until one of
them is edited. Derived, the printed numbers and the verdict's numbers are the same
resolution by construction.

**Corrected after review (fix round 1).** This section first claimed
`test_the_report_and_the_verdict_read_one_resolution` "pins" that property. It did
not, and the review proved it with the exact mutant that matters: revert
`resolve_promotion_bars` to an independent recomputation of the old merge loop and
all 81 tests passed. The property is not extensionally observable — two
implementations that agree today agree on every input a test can name, which is
precisely the drift the derivation exists to prevent — so the extensional test was
asserting something weaker than the sentence around it. It is now pinned
structurally, in the repo's AST-scan idiom
(`TestTheDerivationIsStructuralNotIncidental`): `resolve_promotion_bars` must be one
`return resolve_promotion_bar_report(rows).bars` and nothing else, and the runner
must call `get_promotion_bar_report` rather than resolving a second time. The mutant
was replanted against the new suite and dies on that test.

`_clamp_to_conservative` now returns `(effective, clamp reason, licence bound)`
instead of a bare float. Both warning messages are byte-unchanged — the existing
suite asserts them by substring (`"bound 0.3"`, the licence key) and still passes.

The iteration changed from `for key, value in rows.items()` (skipping unknown keys)
to `for key, spec in PROMOTION_BARS.items()` (looking each up in `rows`). Same
behaviour on every input: unknown keys were skipped before and are not visited now,
known keys resolve identically. The one observable difference is *which* row raises
first when a caller writes two unreadable rows — previously the caller's dict order,
now `PROMOTION_BARS` order. Nothing depends on that: the raise names the key it
raised on, and both orders raise.

### 2. The block the runner prints

`render_bar_report` renders a header, a per-bar table, and a footnote.

Clean run:

```
== bars in force (promotion_bars, committed before any measurement) ==
the measured database carries no `config` row for any G-C bar and no
`promotion_bar_licences` row: every bar below is its committed default, unmoved.
bar                                 committed  effective  provenance
verification_false_promotion_bar    0.01       0.01       no config row; the committed bar stands
...
note: promotion_journal_completeness_bar is read by no predicate today (the 100 %
bar is spelled as zero unexplained rows), so its row and its clamp are
prophylactic, not a live protection.
```

A run with rows:

```
3 of 6 bars carry a `config` row; 1 clamped back to the committed value;
`promotion_bar_licences` row present.
bar                                 committed  effective  provenance
verification_false_promotion_bar    0.01       0.005      config row 0.005 honoured; it moves the bar its own conservative way
promotion_rate_floor                0.5        0.5        config row 0.3 CLAMPED back: it loosens G-C and promotion_bar_licences licenses nothing for this bar
promotion_rate_min_eligible         5          8          config row 8 honoured, under a licence bounded at 8
```

Three states, in words. The absent-row case is stated rather than left to be
inferred from an unchanged number, which is the Done-when's "silent must not be the
same rendering as clean".

`BarResolution.provenance()` orders its branches so the `Conservative.NEITHER` bar
cannot reach the "moves the bar its own conservative way" sentence: for that bar
`spec.loosens` is true for *every* candidate that differs from the default, so an
unlicensed move is always `CLAMPED` and a licensed one always carries a
`licence_bound`; the only remaining path is `requested == committed`, which renders
"restates the committed bar".

`run_gc_evidence.py` prints the block immediately before the pre-stated verdicts,
so a reader sees the bars in force and then the verdicts computed from them.

### 3. The judge side, answered by disclosure

`run_judge_qualification.py` reads no database — its docstring has always said so —
so there is no resolution for it to report and no clamp for it to have applied. The
gap the task named is that its record could not distinguish "no row" from "row
clamped". The honest fix is not to invent a report but to say which case it is:
`judge_qualification.render_report`'s bars section now states that the values are
`VERIFICATION_BAR_DEFAULTS` verbatim, that no `verification_bar_licences` row was
consulted, and that the app-side floor governs `judge()` and never this measurement.

## Tests

Eleven added, in `TestTheReportShowsWhatTheClampDid`. The load-bearing one is
`test_a_clamped_run_does_not_render_like_a_clean_one`: it asserts the two rendered
bodies **differ**, and further that `"CLAMPED"` appears in one and not the other.
Against the pre-T2.128 code there is no `render_bar_report` at all, so the test
cannot pass vacuously; against a version that rendered a table without provenance
the two bodies would be identical (both bars resolve to 0.5) and the assertion
fails, which is the mutant that matters.

The rest cover: the silent-run sentence; the past-bound clamp naming its bound; a
licensed loosening reading as honoured rather than clamped; a free tightening
needing no licence; every bar appearing with both numbers; the prophylactic label
surviving into the artifact; report and verdict reading one resolution; an absent
row not being reported as a request; a licence row alone still being disclosed; and
an unreadable row still raising rather than rendering.

## What this task did NOT do, stated rather than left to be found

- **The G-C evidence run itself was not re-run.** This changes what a run prints,
  not what it measures; a real run needs `DEEPSEEK_API_KEY` and a bench database,
  and G-C has been under-powered on every probe since T2.111 regardless. The block
  is exercised by unit tests over `render_bar_report`, not by a live run's output.
- **No bar value moved**, and no clamp behaviour changed. Every previously passing
  assertion about what clamps and what does not still passes untouched.
- **The honest limit is unchanged.** An operator who writes the bar row and the
  licence row together is still stopped by nothing in-process. What T2.128 adds is
  that the *unbacked* case now leaves its trace in the artifact a reviewer reads,
  rather than only in a log nobody captures.
