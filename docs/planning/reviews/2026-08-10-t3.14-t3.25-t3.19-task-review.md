### The four claims, attacked

**Claim 1 — "the generator's guard was route-deep and both emitted clients drifted under
it." TRUE, and independently confirmed.** `git show 7578279c:sdks/python/darkmem_sdk/client.py`
shows both `capture` and `search` posting `"applies_when": context if context is not None
else self._context`. No request schema in the contract has an `applies_when` key
(`MemoryCreate` has none; `MemorySearchRequest` names the field `context`). Pydantic's
default `model_config` ignores unknown keys, so every declared context was dropped by the
door with nothing said. The field-level guard is a real widening — but it does not close
the class it claims to (I-2), and it did not close the header half at all (C-1).

**Claim 2 — the `search` re-pointing. The argument is sound on doc 15 §6's prose; the
strongest counter-evidence exists and is not stated anywhere.** Doc 15 §6's prose defines
the verb as "the F3 read" returning "the labelled results with their trace" with a `fused?`
argument, and only `POST /api/v1/knowledge/search` serves any of that — verified: it is the
only door whose response carries `envelope`, per-row `labels`
(`ComposedRowLabels`), `layer` and a `fuse` axis, while `POST /api/v1/memories/search`
returns a bare `list[MemoryResponse]`. So the re-pointing is defensible.

What is **not** stated, in the generator docstring, the commit message, or the epic
amendment log, is that doc 15 §6's own mermaid arrow reads `POST .../search · memory_search`
— and `memory_search` is a specific MCP tool that exists alongside a separate
`knowledge_search` tool (`app/services/content_surfaces.py` registers
`front_doors=("POST /api/v1/knowledge/search", "mcp:knowledge_search")`). The mermaid is not
ambiguous; it names the memories twin. Doc 15 §6 is therefore internally inconsistent, the
amendment resolved it in favour of the prose, and the amendment record does not say the
diagram disagrees. I judge the resolution correct on the merits and the *record* incomplete
— finding I-3, which also covers the fact that doc 15 §6 itself was left unamended, so the
document a future regeneration would be checked against still says the opposite.

One cost of the re-pointing worth stating plainly: `MemorySearchRequest` carries a **rank-1
`context` body field** (`app/schemas/memory.py:220-222`) and `KnowledgeSearchRequest`
deliberately carries none. So the re-pointing moved the verb off the only search door with a
rank-1 context argument. That cost turns out to be zero, because the route
`POST /api/v1/memories/search` **accepts `context` and never reads it**:
`MemoryService.search_memories` does not reference `params.context`, and
`resolve_request_context` has exactly one caller in the tree,
`_search_memories_paginated_traced` (grep over `backend/app`, one hit). So the door the SDK
left and the door it arrived at are equally deaf to a declared context. That is what makes
C-1 a finding about the *system*, not merely about this binding.

**Claim 3 — "a per-call context rides the header rather than a body field … claimed harmless
because only one context is ever sent." REFUTED, but not on the rank argument.** The rank
argument is correct as far as it goes: only one context is ever sent, so rank 1 versus rank
2 cannot change which declaration wins, and `resolve_declared_context`'s tiers do not merge.
The refutation is that the concession understates its own cost by an order of magnitude:
rank 2 of a chain **that is not run on either bound door** is not rank 2, it is nothing. See
C-1. The generated clients' honest-limitation note ends "…and which doors resolve it at all
is the server's", which reads as "some doors may not" rather than "neither of the two this
client talks to does".

**Claim 4 — "ratify is not expressible, asserted as a whitelist … the scans are the thing
most worth attacking." REFUTED by three drills.** See I-1.

### Findings

**C-1 (Critical) — `declareContext` sends a header that neither bound door resolves; a
declared context reaches nothing and nothing says so. This is the same silent-drop the task
was written to close, relocated from the body to a header.**

`sdks/generate.py:99` binds `declareContext` to `X-Darkmem-Context`, and the guard
(`sdks/generate.py:139-147`) checks only that the pinned literal equals
`app.api.context_resolution.DECLARED_CONTEXT_HEADER`. It never asks whether either bound
door *reads* that header. Neither does.

Measured live, through the real ASGI app in the backend harness (scratch test, removed
after):

| Door | SDK binding | `X-Darkmem-Context` sent | Result |
|---|---|---|---|
| `POST /api/v1/knowledge/search` | `search` | yes | 200, `envelope.context` = `null` |
| `POST /api/v1/memories` | `capture` | yes | 202, buffer row metadata carries no trace of it |
| `POST /api/v1/memories/search/paginated` (`with_trace=true`) | **not bound** | yes | 200, `envelope.context` = `{"declared": {"env": "prod", "situation": "debugging"}, "declared_by": "header", "provenance": "human"}` |

The third row is the control: the header mechanism works, it is simply not on either door
the SDK talks to. Code-path confirmation: `resolve_declared_context_for_request` has one
caller in `backend/app` — `MemoryService.resolve_request_context` — which is called from one
place, `_search_memories_paginated_traced`. `search_knowledge` never touches
`request.headers`, and `KnowledgeSearchRequest` has only `query`/`project`/`limit`/`fuse`.

**Why it matters:** doc 15 §6 defines the verb as "sets the session's `applies_when` context
so subsequent `search`/`capture` calls carry it (contract 3)". As shipped, a caller declares
a context, receives no error, and every ranking decision proceeds as if nothing was
declared. That is exactly the failure the commit message describes for `applies_when`
("dropped by the door with nothing said"), and the field-level guard that was added to catch
it is structurally incapable of seeing the header case. Blast radius today is zero — the SDK
is target-new and has no consumers — which is why this is a defect to fix before it has
users, not an incident.

Fix directions, controller's call: (a) bind `search` to the one door that resolves declared
context and accept the shape cost; (b) add the header to `search_knowledge` and
`create_memory` (a server change, likely another task's); or (c) at minimum replace the
hedge in `CONTEXT_NOTE_LINES` with the measured truth — "neither bound door resolves this
header today; the declaration is carried for the day one does" — and add a generator check
that the bound header has at least one resolver, so this cannot silently stay true.

**I-1 (Important) — The "ratify is not expressible" scans cannot detect a fourth verb; three
different escape hatches pass all 41 tests, and the emitted client ratifies a fact.**
Each drill mutated `sdks/generate.py` (the real threat model — the emitted files are
generated), ran `make generate`, then all four suites. Tree restored and re-verified clean
after each.

- **Drill A (TypeScript).** Added a public class-field arrow function to the template:
  ```
    send = async (path: string, body: Record<string, unknown>): Promise<unknown> => {
      return this.#post(path, body);
    };
  ```
  Result: `sdks/python` **25 passed**, `sdks/ts` **15 passed**, `tests/test_sdk_generator.py`
  **16 passed**. Then a scratch vitest drove it: `c.send("/api/v1/knowledge/facts/abc-123/ratify",
  {verdict: "confirm"})` reached
  `http://localhost:8000/api/v1/knowledge/facts/abc-123/ratify` with `Authorization: Bearer
  jwt` and returned `{status: "confirmed"}`. Why it escapes: `_typescript_class_members`'
  regex (`test_surface.py:57-63`) requires `(` immediately after the member name, so a
  `name = async (...) =>` field never enters the member set at all; and a class field is an
  **instance** property, so `Object.getOwnPropertyNames(Darkmem.prototype)`
  (`client.test.ts:196`) still returns exactly the four. Both of the TypeScript guards are
  blind to the same construct. A getter (`get ratify() {`) escapes the regex identically.
- **Drill B (Python).** Added `@classmethod def open_door(cls, client, path, body)` to the
  class **and** a module-level `async def send(client, path, body)`. Result: `sdks/python`
  **25 passed**, `tests/test_sdk_generator.py` **16 passed**. Both reached
  `/api/v1/knowledge/facts/{id}/ratify` and returned `{"status": "confirmed"}`. Why they
  escape: `test_the_python_client_exposes_exactly_three_callables` filters on
  `callable(value)` over `vars(Darkmem)`, and `callable(classmethod(f))` is **False**
  (measured on this interpreter) — so a classmethod fourth verb is invisible to the
  whitelist, which reported `{'capture', 'declare_context', 'search'}` while `open_door` sat
  on the class. A module-level function is not in `vars(Darkmem)` at all, and
  `test_the_package_exports_only_the_client` only inspects `vars(darkmem_sdk)`, which is
  `{Darkmem, client}` regardless.
- Neither drill spells a path, so both path-fragment whitelists
  (`test_the_only_route_literals_are_the_bound_paths`, `test_no_path_is_assembled_from_pieces`)
  pass by construction. The Python test file honestly states that `_post` "a determined
  caller can defeat"; what is overstated is the TypeScript claim that `#post` "closes that at
  run time", and the whitelist framing ("a fourth verb fails the first even if it is called
  something none of us imagined") — it does not.

  Sharpened fix: assert over the emitted surface as a whole rather than over one regex
  shape. For TypeScript, the cheapest robust check is an instance probe —
  `Object.getOwnPropertyNames(new Darkmem({}))` plus the prototype names, unioned, must
  equal the expected set; that catches class fields, which the prototype check alone cannot.
  For Python, `dir(Darkmem)` minus `dir(object)` filtered to non-underscore, plus an
  assertion that `vars(darkmem_sdk.client)`'s public module-level names are exactly the two
  path constants, the header constant and `Darkmem`.

**I-2 (Important) — The field-level guard validates the *declared* field list, not the
*emitted body*, so the original defect is reintroducible on any path the client tests do not
drive.** `_require_contract` iterates `VERBS[name]["fields"]` and asks whether the contract
has each one. Nothing connects that tuple to the keys the template actually posts.
Drill C: added an `applies_when: dict | None = None` keyword to the Python `capture`
template posting `"applies_when": applies_when`, leaving
`VERBS["capture"]["fields"]` untouched. `make generate` **did not refuse**; `sdks/python`
25 passed, `sdks/ts` 15 passed, `tests/test_sdk_generator.py` 16 passed. The original defect
is caught today only because it rode an *always-sent* key, which
`test_only_one_context_is_ever_sent` and `test_an_omitted_argument_is_absent_from_the_wire`
pin by exact key set. Behind an optional argument no test passes, the guard is silent. Fix:
derive the emitted body keys from `VERBS[...]["fields"]` in the template (one source), or
add a test that parses each emitted client's post-body literals and asserts they are a
subset of the declared fields.

**I-3 (Important) — A Tier-1 amendment was logged but the document it amends was not
changed, and the amendment's strongest counter-evidence is unrecorded.** Doc 15 §6's mermaid

- **M-12** `PUT /api/v1/distribution/policy` takes a full `DistributionPolicy` with per-field
