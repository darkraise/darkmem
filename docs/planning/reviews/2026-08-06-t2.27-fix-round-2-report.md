## N1 — the closure follows literal loader calls

**Reproduced first.** Appending the reviewer's exact shape to the real deriver —

```python
import importlib
_p = importlib.import_module("app.services.pipeline")
```

— left `tests/test_code_deriver.py` + `tests/test_inert_objects.py` at **76 passed, 2
skipped**. The finding is real as stated: the deriver holds the live pipeline and both
guards are green.

**Root cause, as the rescope framed it.** An intermediate module carries no entry in
either forbidden vocabulary *because the closure is what scans it*. `_import_closure`
followed only `ast.Import`/`ast.ImportFrom`, so a dynamic hop into an intermediate put
the reached module outside the scanned set and every layer went blind at once.

**Fix.** `_loader_call_target` (+ `_loader_call_package`) resolves `import_module` /
`__import__` calls whose first argument is a literal, and `_import_closure` follows
what they name. An absolute literal is the module; a relative one resolves through the
existing `_resolve_relative`, against the call's own literal `package` when it has one
and otherwise against the importing file's package — which is what `__package__`
evaluates to, the only executable spelling of a relative loader call whose package is
not a literal. This is the same route the shared scanner's client rule already resolves
for a literal `import_module("httpx")`; the closure now has it too.

The residual over-approximation (a computed `package` with a literal relative name
pulls in one module that may not be the reached one) errs toward scanning more, which
is the correct direction for a tripwire, and is stated at the function.
