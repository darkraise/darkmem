## Findings

### 1. Critical — the artifact's SCORED verdict is a second resolution of the rule, and it disagrees with the predicate under honoured config rows

`promotion_metrics.py:788` computes the rendered verdict from the module constant
(`supported = fp.clears_with_confidence(_AUDIT_BAR_FOR_POWER, FALSE_PROMOTION_CONFIDENCE)`)
and `_render_audit_power` consults **no decidability floor at all**, while the scored
predicate (`promotion_bars.py:756-763`) reads both resolved bars. Reproduced in three
configurations, all reachable through the sanctioned config machinery with no licence or
with a valid one:

| config row | honoured? | rendered (in `render_report`) | scored (`audit_clears`) |
|---|---|---|---|
| `verification_false_promotion_bar: 0.005` (free tightening) | yes | `**SCORED** … 0.0100 against bar 0.01 → CLEARS` (window 0/299) | **False** |
| `false_promotion_min_corroborations: 400` (free tightening) | yes | `→ CLEARS` (window 0/350) | **False** |
| bar licensed to 0.05 (`licensed` row, within limit 1.0) | yes | `→ does NOT clear` (window 1/149) | **True** |

Why it matters: `run_gc_evidence.py:233` prints `render_report` into the same artifact
as the predicate's `clears=` line, so under a tightened row the ledger-quotable body
carries a line *claiming to be the scored rule* that asserts a pass the gate refused —
the exact "report reads cleaner than the system" defect this change's own subject matter
is, and the exact two-resolutions class T2.128 closed for the bar block
(`resolve_promotion_bars` is AST-pinned to a single resolution for precisely this
reason; the renderer reintroduces the pattern one layer up). The divergence is silent:
nothing warns, nothing renders differently. The brief disclosed the bar channel; the
decidability channel and the reverse direction are additional.

Fix direction (for the fix round, not applied here): thread the resolved `BarReport`/
bars — or the predicate's own verdict — into `_render_audit_power`, and extend
`test_the_rendered_verdict_is_the_predicates_verdict` off default bars so the property
is pinned where it can fail.

### 2. Important — `render_report` became verdict-bearing, and its second consumer now contradicts its own contract

T2.132 changed the audit-power block from commentary to a verdict claim, and
`run_gc_evidence.py` is not its only consumer. `run_promotion_metrics.py:156` prints the
same block, while that module's docstring (lines 5–8) states: *"This script produces
numbers; it states no bar and renders no pass/fail verdict."* That sentence is now
false, in a file the diff never touched. Worse, that runner resolves **no bars at all** —
no clamp, no licence context, none of T2.128's disclosure block — and its default target
is the **production** `darkmem` database, so the one verdict-shaped line in its output
is computed from an unresolved constant with nothing beside it saying so. Either the
runner gains a resolution and prints it, or the renderer's verdict line is suppressed
where no resolution exists; the current state is a stated contract silently falsified.

### 3. Minor — `test_no_window_below_the_floor_can_clear_the_bound` is vacuous against the bound

`test_promotion_bars.py` (TestTheDecidabilityFloorIsSubsumed): with
`clopper_pearson_upper` patched to always return 0.0 — a bound that clears everything —
the test **still passes** (reproduced), because every below-floor refusal comes from the
decidability guard, never from the bound the name claims to test. The companion test
(`corroborations_required(0, …) = 299 > 20`) is the real derivation and does catch a
broken bound — but it checks only `k = 0`, so the "at any observed count" half of the
subsumption rests on the bound's monotonicity in `k`, which no test pins.
Mathematically the claim is right (verified in closed form above); the encoded proof is
partial and one of its two tests reads as coverage it does not provide. Sharpen by
asserting `clopper_pearson_upper(k, n) >= bar` directly for `n < 299`, or by pinning
monotonicity in `k`.

### 4. Minor — `scored_on: "upper_bound"` is asserted, not derived

`promotion_metrics.py:1180`. Nothing connects the string to the predicate's actual rule,
so a future rule change leaves durable rows asserting the wrong provenance — the drift
class this change closes elsewhere, reintroduced in the ledger row (author-disclosed).
Mitigated: the row also carries `rate`, `upper_bound` and `confidence`, so a reader can
recompute and detect the lie. Acceptable to record and carry; worth a derivation or a
pin when the row shape is next touched.

### 5. Minor — 4-decimal rounding renders opposite verdicts as the same number

`promotion_metrics.py:808-811`: bound 0.009969 (n = 299, clears) and bound 0.010002
(n = 298, fails) both print `**0.0100** against bar 0.01` — two visually identical
SCORED lines with opposite verdicts, and the clearing one reads as "0.0100 < 0.01",
which a reader cannot reconcile. This is the same display hazard T2.131's plan review
flagged at the 473 window ("clears by 1×10⁻⁵ and prints as 0.0100"). The runner already
prints the bound at 6 decimals (`run_gc_evidence.py:298`); the report should match.

### 6. Minor — `k ≤ n` is structural per snapshot, not per run

The claim the no-guard decision rests on is sound where the verdict is computed:
`_FALSE_PROMOTED_FACTS_SQL`'s two arms (`promotion_metrics.py:533-567`) both select from
a `corroborated` CTE whose predicate is character-identical to the denominator's
sub-select (`465-473`), and the UNION dedupes, so within one statement the numerator is
a subset count of the denominator. But `n` and `k` come from **two statements**
(`921-928`) in one READ COMMITTED session, so on the sanctioned live-DB probe
(`run_promotion_metrics.py`, default target the production database) a concurrent writer
committing corroborate-then-dispute pairs between the two statements can in principle
yield `k > n` → `ValueError` at the last step, after every query is paid for. Unreachable
on the offline bench path (`run_gc_evidence.py` owns `darkmem_bench`; no concurrent
writer), and the failure is loud, not a wrong number — so the "no error handling for
scenarios that can't happen" call stands for the verdict path. Recording the caveat and
the free fix: compute both counts in one statement, or run the probe's session at
REPEATABLE READ.

### 7. Minor — the direction probe's 0.5 override is reachable but unpinned

Ruling the brief asked for: the `false_promotion_min_corroborations` probe **still
derives** the direction rather than re-declaring it. The flip comes from the floor's own
comparison site (`audit_decidable`) inside the composed `audit_clears`; the sibling-bar
override to 0.5 only makes that outcome visible, and 0.5 sits inside the ceiling's
licensable domain (`licence_limit = 1.0`, `promotion_bars.py:343-345`), so the probed
configuration can genuinely occur. The override is also **necessary**: at the committed
bars the floor's direction is unobservable through the composed verdict — that is what
subsumption means — so the only alternatives were probing `audit_decidable` alone
(weaker: not the composed verdict) or this. One gap: nothing pins
`0.5 <= PROMOTION_BARS["verification_false_promotion_bar"].licence_limit`, so if the
domain edge ever shrank below 0.5 the probe would silently start testing an unreachable
configuration. A one-line assert closes it.
