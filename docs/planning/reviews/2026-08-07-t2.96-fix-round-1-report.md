1. The full set of collected key bindings equals the twelve-entry roster

   `BUFFER_FLUSH_JOB_KEY`, `code_enrichment`, `CODE_RECONCILE_JOB_KEY`,

   a call whose function name is `make_code_deriver_runner`, and its
   `min_interval_seconds=` keyword binds `CODE_DERIVER_MIN_INTERVAL_SECONDS`

**Chose the roster-wide generalization**, per the controller's instruction

## F2 (Minor) — over-strict exactly-once assertion

**Problem:** `max(cardinality(repo_ids)) == 1` proved "this repo is the
array's sole occupant," not "the repo id appears exactly once." Those only
coincide because no neighbouring committed test currently shares an entity
(e.g. `sqlalchemy`, `fastapi`) with this repo's rows.

**Fix** (`test_runner_derives_repo_ids_end_to_end`,
`backend/tests/test_code_deriver.py`): replaced the cardinality check with
a per-row occurrence count —

```sql
SELECT count(*) FROM {table}
WHERE (SELECT count(*) FROM unnest(repo_ids) u WHERE u = CAST(:rid AS uuid)) != 1
  AND CAST(:rid AS uuid) = ANY(repo_ids)
```

asserted `== 0`: among rows that contain this repo's id, none contains it
more than once. This proves exactly the brief's property (the repo id
appears exactly once per row it's in) without demanding the repo be the
array's only occupant, so a future co-asserted global entity won't flake
this test.

Verified passing as part of the file run (`83 passed`) and the full floor
below; the property genuinely exercises real data since the test still
requires `snapshot["entities"]`/`["relations"]` non-empty first.

## F3 (Minor) — phantom failure on a resolve() race

**Problem** (`backend/app/services/job_runners.py`,
`make_code_deriver_runner`): the derivation write committed, then
`resolve()` ran and committed separately. If `resolve()` itself raised
(e.g. a dropped connection between the two commits), control landed in the
`except` branch and recorded a **failure** row for a repo whose derivation
had just committed successfully — a phantom failure.

**Fix:** removed the first `await repo_session.commit()`, so the
derivation write and `failure_svc.resolve(...)` now share one transaction,
committed once. `resolve()` only issues an `UPDATE ... WHERE resolved_at IS
NULL` inside the same session — it does not commit internally — so folding
it in is safe. Added a comment explaining why the ordering matters: if
`resolve()` now raises, the `except` branch's `rollback()` undoes the
derivation write too, so the failure recorded afterward is an honest
failure (nothing persisted) rather than a phantom one for a repo that
actually succeeded. This is the same "one atomic replace" shape invariant 8
already requires of the strip-and-write pair in `code_deriver.py` itself.

No new test was added for this — matching effort to a Minor, self-healing
(the next tick's success resolves it either way), two-line-reorder fix.
Verified via the full test file (`83 passed`) and the full floor (below);
no existing test's shape depended on the two-commit split.

## F4 (Minor) — double-fault degrades to logs only

**Reviewed and accepted as-is, no code change.**

If `failure_svc.record(...)` itself fails inside the `except` branch's
inner `try`, the derivation failure surfaces only via `logger.error`
(`job_runners.py:193-196`). Reaching this requires two independent
failures: `assert_repo_graph` (or `resolve()`, per F3's new shared
transaction) raising, *and* the subsequent `record()` call also raising.

Reasoning for accepting rather than changing:

- This is consistent with how `record_event` and other failure-recording
  paths in this codebase degrade — CLAUDE.md's events-journal section
  documents `record_event` itself as "degrades loudly but never raises into
  its caller," and the double-fault-to-log pattern here is the same shape
  one level up (a failure recorder failing to record).
- `code_deriver`'s sibling, `make_code_reconcile_runner`, doesn't even
  attempt to persist a `pipeline_failures` row on its `except Exception`
  branch — it logs and moves on. The deriver's runner is already strictly
  more robust than its own stated precedent, since it does try to persist a
  failure row and only degrades to logging on the rarer double-fault.
- The window is self-healing at the next scheduled tick (or a manual
  trigger) regardless of whether this specific double-fault was logged or
  raised, since the sweep re-derives every indexed repo unconditionally
  each run.

No test added for this branch specifically, for the same match-effort
reasoning — a Minor, two-independent-failure edge case consistent with an
existing accepted pattern elsewhere in the codebase.
