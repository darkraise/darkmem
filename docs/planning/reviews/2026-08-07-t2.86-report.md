## The fix (clause 5)

The brief's own framing of this clause — "`FactSourceGroup.stale` rides the
wire ... and `fact-sources.tsx` reads it nowhere" — was half right. The
frontend gap was real. But investigating it found the field **never reached
the wire at all**:

- `facts_read._source_group` (`backend/app/services/facts_read.py:127`) has
  computed `"stale": group.is_stale` since T2.48.
- `FactSourceGroup` in `backend/app/schemas/facts.py` never declared a
  `stale` field.
- The route (`GET /knowledge/facts/{id}`) uses
  `response_model=FactDetailResponse`, and FastAPI/pydantic v2's default
  `extra="ignore"` silently drops any key a response model does not
  declare — proven directly: constructing `FactSourceGroup(**dict_with_stale)`
  and calling `.model_dump()` drops `stale` with no error.

This is the **third** instance of this exact shape in this one schema file —
`label_suppressed` and `unverified` were both silently dropped by an
undeclared-field response model before being caught (see the file's own
accumulated comments). A fourth might be worth a structural guard (a test
asserting every key a `facts_read` builder writes is declared on its response
schema); not built here, out of this task's named scope, but flagged in the
amendment log.

**Backend fix** (`backend/app/schemas/facts.py`): declared `stale: bool` on
`FactSourceGroup`, with a docstring explaining why it was missing.

**Backend test** (`backend/tests/test_facts_read_surface.py`,
`test_a_stale_origin_group_is_labelled_on_the_wire`): a fact with one live and
one stale origin; asserts `stale: false` / `stale: true` on the wire and that
the stale origin's row detail is retained (not filtered out). Proven to catch
the regression: reverted the schema field, re-ran the test, watched it fail
with `KeyError: 'stale'`; restored, re-ran the full file green (28 passed).

**Frontend fix**:
- `src/demo/types.ts`: `FactSource` gained an optional `stale?: boolean` (no
  existing demo fixture needed a change).
- `src/demo/knowledge.ts`: `OriginGroup` gained `stale: boolean`, computed in
  `groupSourcesByOrigin` as "every row in the group is stale" — mirrors the
  backend's `OriginGroup.is_stale`.
- `src/features/knowledge/components/fact-sources.tsx`:
  - `sourceGroupsToFlatSources` broadcasts the live door's group-level
    `stale` onto every row it flattens, so re-grouping downstream by
    `origin_key` recovers the same flag.
  - `FactSourcesGroups` renders the existing `StaleBadge` (already used for
    article staleness — same warning styling, same "downgrade of
    corroboration, never a contradiction" semantic doc 10 §6 requires) beside
    a stale group's kind badge, plus an inline note naming the cause.
  - The sources caption's "the badge's K" now excludes stale origins from its
    count. This was necessary, not cosmetic: `badge.origin_count` already
    excludes stale origins server-side (`LIVE_SOURCE_PREDICATE`), and the
    caption's own claim ("... = N — the badge's K") would have gone false the
    moment a stale group existed and rendered, since it previously counted
    every origin including stale ones. When no stale group exists, the
    caption's wording and numbers are byte-identical to before.

**Frontend tests**:
- `src/demo/__tests__/knowledge.test.ts`: `groupSourcesByOrigin` stale
  aggregation (all-stale, mixed, none).
- `src/routes/_authenticated/__tests__/fact-detail.test.tsx`: a stale-source
  fixture renders "stale" and never "disputed"; a live-only fixture renders
  no stale label.
- `src/components/darkmem/__tests__/detail-level-invariants.test.tsx`: the
  stale label survives both Simple and Advanced mode (it is an honesty
  signal, per that suite's own rule).

All three drilled: reverted the `StaleBadge` render, re-ran, watched both the
live-door test and the invariant test fail; restored, re-ran green.
