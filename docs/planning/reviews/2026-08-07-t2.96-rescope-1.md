## F3 (Minor) — ADDRESSED

Settled by the 6-line hunk in `backend/app/services/job_runners.py` (the
`await repo_session.commit()` between `assert_repo_graph` and `resolve()` removed;
one commit after both).

- **`resolve()` is safe to fold in:** `pipeline_failures.py:223–262` — a single
  `UPDATE ... WHERE resolved_at IS NULL` on the caller's session, no internal
  commit; its broadcast hook is wrapped in `except Exception: logger.warning`, and
  the runner constructs `PipelineFailureService(repo_session)` with no broadcast
  anyway. The only raise surface inside the shared transaction is the UPDATE
  itself — the case the fix wants there.
- **Window closed, drilled both directions.** My scratch test monkeypatched
  `resolve()` to raise after a successful derivation. Against the fixed runner:
  derivation rolled back (no repo assertions persist), exactly one **unresolved**
  failure row carrying the real error, and a healed re-run derives and resolves —
  passed. Against the pre-fix runner (`b42200a4`'s file swapped in): the same drill
  goes red at `derivation write survived a resolve() failure` — the phantom window,
  reproduced. So the fix changes observable behavior and the drill is falsifiable.
- **The trade is sound, not a new bug.** Yes, a resolve failure now discards a
  committed-would-have-been derivation — but the sweep re-derives every indexed
  repo unconditionally each tick and `assert_repo_graph` is an idempotent replace,
  so the cost is one tick of delay on a rare double event, bought with the property
  that a `pipeline_failures` row never lies about persisted state. That is the
  right side of the trade for a surface whose whole job is honest failure
  reporting.
