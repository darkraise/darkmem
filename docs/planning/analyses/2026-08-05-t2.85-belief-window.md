# T2.85 — the belief-window contradiction: analysis and options

**Fable-tier Tier-3 analysis (runbook §5). This document decides nothing — the ruling is
the controller's / owner's. No code was written; the one write in this branch is this
file.** Brief: `docs/planning/briefs/2026-08-05-t2.85-belief-window-ruling.md`. The logged
escalation is the 2026-08-04 T2.34 Tier-3 row in `docs/planning/tasks/E2-truth-core.md`.

## Recommendation

**Option 2 — a `stated_expiry` column populated at fact-lift time, spent by a
deterministic recompute arm — with one sub-ruling neither doc-08 section currently
states: when the date passes, the arm writes `invalid_at := stated_expiry` (via
`close_window`), never `expired_at`, and never `now()`. `expired_at` stays NULL.**

Four reasons, in strength order:

1. **It is the only resolution under which the four partial indexes and
   `OPEN_BELIEF_PREDICATE` stay byte-identical.** Zero read-time cost, no invariant
   bends, no consumer rewrites — and `invalid_at` keeps the property the shipped
   predicate assumes, that it is only ever set in the past (the arm writes a date that
   has already passed).
2. **A measured finding the escalation did not state: §3.1's own literal routing is also
   wrong, so "§3.1 wins" is not an available ruling.** §3.1 routes a stated expiry down
   `open --> expired` (`expired_at`). But `as_of` deliberately does not filter
   `expired_at` (`knowledge_triples.py:933-936` — "a fact whose belief has since been
   withdrawn was still believed at t"), so a stated expiry recorded as `expired_at`
   leaves `invalid_at` NULL and the historical question answers wrongly: probe B1 below
   shows the fact served as "believed at 2026-06-01" five months after its stated
   2026-01-01 expiry. Only `invalid_at = the stated date` makes `as_of` correct on both
   sides of the date (probes C1/C2). The ruling therefore must amend **both** sections.
3. **§9 already contains the correct mechanism in its own second clause.** The same
   bullet that says "pre-closed at that date" continues "a lightweight arm of
   `verification_recompute` (or `fact_lift`) **closes windows whose stated expiry has
   passed**". If the window were literally pre-closed at population, the arm would have
   nothing to close — §9 is internally split, and its second clause agrees with the
   arm-closes-later model. The fix to §9 is one word: the window is
   *pre-determined* at population, closed by the arm when the date passes.
4. **It mirrors the shipped memory half, which §9 itself cites as the model**
   ("mirroring the `memories.expires_at` activation"). T2.34 derives once at capture and
   stores into `memories.expires_at` (`pipeline.py:637-643`); the sweep spends the stored
   value. Derive-once-and-store is also what makes the outcome auditable: the parsed date
   is inspectable and correctable on the row from population until it fires, which
   option 3 structurally cannot offer.

Doc-08 amendments this implies, if the controller rules for it:

- **§9**: "pre-closed at that date" → "its closing date pre-determined at that date;
  the recompute arm closes the window once it passes". Add `stated_expiry` to §9's
  named schema amendments (today it names only `demotion_pending_since`).
- **§3.1 state machine**: the stated-expiry trigger moves from the `open --> expired`
  edge to `open --> window_closed` (actor: the recompute arm; write:
  `invalid_at = stated date`). `open --> expired` keeps source withdrawal only.
  The `window_closed` gloss widens from "a newer belief arrived" to "the validity
  window ended — a newer belief arrived, or the fact's own stated expiry passed".
- **§3.2** is untouched: fact rows are minted only in Tier-C fact lifting, so the
  population site is the lift, and the arm stays within §9's "no LLM, no separate job".

indexes partial on `expired_at IS NULL AND invalid_at IS NULL`, and no others:

| Index | Baseline lines | Partial predicate |
|---|---|---|
| `ux_knowledge_triples_open` (UNIQUE, `triple_key`) | 538–541 | `expired_at IS NULL AND invalid_at IS NULL` |
| `ix_knowledge_triples_fact_fts` (GIN, `fact`) | 561–565 | same |
| `ix_knowledge_triples_name_fts` (GIN, names) | 569–573 | same |
| `ix_knowledge_triples_project_open` (`project`) | 577–580 | same |

The two neighbours are not in the set and the count is exactly four:
`ix_knowledge_triples_live` (525–531) is partial on `expired_at IS NULL` alone, and

Doc 07 §2 and doc 04 §10 both state the three retrieval indexes scope to the
currently-open-belief predicate, matching the baseline.

## The options

| | 1 — time-aware "currently open" | 2 — `stated_expiry` column (recommended) | 3 — no column, re-derive per cycle | 4 — range-exclusion constraint (new) |
|---|---|---|---|---|
| **Baseline schema change** | Drop `ux_knowledge_triples_open` (a partial unique cannot contain `now()`); widen the three retrieval indexes to `WHERE expired_at IS NULL`; uniqueness moves to app level or to option 4's constraint | One nullable `stated_expiry TIMESTAMPTZ`; optionally a small partial index `(stated_expiry) WHERE expired_at IS NULL AND invalid_at IS NULL AND stated_expiry IS NOT NULL` for the sweep. Nothing else moves | **None** — no schema window, no serialisation through the baseline owner | `btree_gist` extension + `EXCLUDE USING gist (triple_key WITH =, tstzrange(valid_at, invalid_at) WITH &&) WHERE (expired_at IS NULL)` replacing the partial unique; retrieval rework as option 1 |
| **Invariants bent** | "At most one currently-open belief per `triple_key`" becomes time-dependent and declaratively unenforceable; the baseline's stated design — the belief scope pushed *into* the index so a widened query stops matching — is abandoned | None. `invalid_at` stays only-ever-past; the unique keeps its meaning | None on the schema. Determinism-of-record is lost: the outcome at each cycle depends on the parser version then, with nothing recorded at population | None bent — one *strengthened*: windows on one key become provably non-overlapping, which today is a write-path promise nothing enforces |
| **Read-time cost** | Every open-belief consumer gains a runtime `(invalid_at IS NULL OR invalid_at > now())` that no partial index can carry; the widened indexes also scan window-closed history | **Zero** | Zero at read. Cycle cost: full scan + parse of every open fact per cycle, no index support | As option 1 on the read side; plus GiST maintenance on every fact write |
| **Failure mode if wrong** | Exactly the two measured silent failures (probes A1/A2), plus one per missed consumer — seven predicate spellings exist today (census below) and each missed rewrite diverges silently | Bounded: a fact is served up to one recompute cadence past its date; a wrong parse closes a window early or late but invalidate-not-delete keeps it recoverable, and the stored date is reviewable before it fires | A parser fix acts retroactively: it can mass-close windows open for months, silently, with no per-fact record to review in advance — and no way to distinguish "the fact said this" from "this parser version says this" | A missed retrieval-side consumer serves or hides pre-closed facts silently (option 1's class); extension + operational complexity for a capability (future-dated invalidation) nothing needs today |

**Why not option 1.** It is the largest blast radius for the least benefit: nothing in
the corpus needs a *future* `invalid_at` except the literal reading of three words in §9
that the same bullet's second clause contradicts. The measured consumer census the
rewrite would have to sweep: the `OPEN_BELIEF_PREDICATE` constant
(`knowledge_triples.py:49`) and its importers (`facts_channel.py:264,278`,
`fact_sources.py:672`), **two inline spellings** in `fact_lift.py` (the scan CTE at
203–204 and `_OPEN_FACT` at ~265–270 — exactly the kind of site a sweep misses), plus
the tests that pin the predicate (`test_facts_channel.py:120-130,823`) and the four
indexes. `as_of` (941–943) is the one consumer already correct.

**Why not option 3.** Its one real advantage is scheduling, not design: it needs no
schema window while the baseline serialises through one owner. Against that: the fact
text is written once and never updated (baseline comment, lines 555–560), so options 2
and 3 parse the same immutable input — the *only* behavioural difference between them is
that option 3 re-decides every cycle under whatever parser then ships, un-auditable and
retroactive, while option 2 decides once, on the record, at population. Paying a
recurring scan-and-parse to obtain a strictly worse audit posture is the wrong trade. If
the controller weighs schema-window congestion heavily, option 3 is coherent and safe
(both docs are satisfiable under it); it is second choice, not disqualified.

**Option 4 — the fourth option the brief asked for.** Replace the partial unique with a
`tstzrange` exclusion constraint. This is the principled bi-temporal answer: it makes a
future `invalid_at` *legal* while enforcing the stronger invariant the disjoint-window
pass (§3.2) promises but nothing checks — today two rows with overlapping *closed*
windows can coexist, and `as_of` would return both for an instant in the overlap. But it
solves only the uniqueness half of option 1 and inherits its entire retrieval rework, so
it is not a resolution of this contradiction on its own. Recorded as the eventual shape
**if** darkmem ever needs future-dated invalidation generally (scheduled belief changes);
nothing scheduled needs it.

## Measured evidence

Probe script: `belief_window_probe.sql` (scratchpad), run against `darkmem_bench` inside
one `BEGIN … ROLLBACK` — nothing persisted. Expectations were written into the script
before the run. `as_of`'s predicate was copied verbatim from
`knowledge_triples.py:941-943`.

| Probe | Setup | Expected | Measured |
|---|---|---|---|
| A1 | Literal §9: insert with `invalid_at = 2027-01-01` (future) | 0 rows match `OPEN_BELIEF_PREDICATE` — fact leaves the retrieval channel today | **0** |
| A2 | Insert a second open row, same `triple_key` | Insert succeeds — `ux_knowledge_triples_open` no longer guards the key | **2 rows** |
| B1 | Literal §3.1: stated expiry 2026-01-01 recorded as `expired_at`, `invalid_at` NULL; `as_of(2026-06-01)` | 1 row returned = the historical question answered wrongly | **1** — served as believed five months past its stated expiry |
| C1 | Recommended: `invalid_at = 2026-01-01`, `expired_at` NULL; `as_of(2026-06-01)` | 0 | **0** |
| C2 | `as_of(2025-06-01)` — inside the window | 1 | **1** |
| C3 | `LIVE_PREDICATE` (`expired_at IS NULL`) | 1 — the row survives as live history | **1** |
| C4 | `OPEN_BELIEF_PREDICATE` | 0 — the unique slot frees legitimately, a successor belief may open | **0** |

So the escalation's two claimed failures are both real (A1, A2), §3.1's literal edge
fails the `as_of` question (B1), and the recommended write shape answers all four
predicates correctly (C1–C4).

**`invalid_at` writer census.** `rg "SET invalid_at" backend/app` returns exactly one
site: `close_window` (`knowledge_triples.py:307`). `close_window` has zero production
callers today (three hits, all inside its own module) — consistent with the 2026-08-02
amendment. Under option 2 the recompute arm becomes its **first** caller, making the
`invalidated` event real; it still supplies no `invalidating_fact_id`, so the
status-bridge deferral ruled on 2026-08-02 stands unchanged and is not reopened here.

## Constraints pinned, and non-binding implementation notes

- The baseline is one revision regenerated in place, not yet frozen; option 2's column
  serialises through the epic's schema owner and cannot share a round with another
  baseline edit. Option 3 is the only choice needing no window.
- The memory half is settled and shipped (T2.34, through fix round 7, `fbf3e058`) and is
  not reopened. One asymmetry worth stating for the implementer: T2.34's parser was
  deliberately narrowed to self-referential retention instructions because its sweep
  **deletes**. The fact side's action is a recoverable, journalled window-close on a
  retained row, so the fact parser may legitimately be wider — "the licence is valid
  until 2026-12-31" is precisely the fact-level case — with the width a decision for the
  implementing task, not this ruling.
- Whether the arm lives in `verification_recompute` (T2.09, still `todo`) or `fact_lift`
  is implementation detail §9 leaves open; either satisfies "no LLM, no separate job".

## Adjacent findings (outside this ruling, surfaced not fixed)

1. **Overlapping closed windows are unenforced.** The partial unique guards only
   open-ended rows; the disjoint-window pass's promise that windows on one key never
   overlap has no constraint behind it, and `as_of` returns both rows for an instant in
   an overlap. Option 4 is the enforcement if it is ever wanted.
