# T2.11 and the judge that missed its bar — what is actually blocking, and the options

**Analysis only. Nothing here re-runs the measurement, and nothing here proposes moving
the 0.95 bar.** Written 2026-08-05 against branch `feat/e2-truth-core` (HEAD `f05c23d6`).
Every number below was read from a committed artifact or computed from one, with the
arithmetic shown.

## 1. What is actually blocking — and it is not "a judge that failed its gate"

The chain, verified in code and on disk:

- `VerificationJudge.judge()` (`backend/app/services/verification_judge.py:135-161`) is
  the only lawful consumer door and raises `JudgeNotQualifiedError` whenever
  `app/services/verification_qualification.json` is absent. **Verified absent on disk.**
- That record is mintable only by `run_judge_qualification.py --gate`, whose
  `gate_eligibility` lock (`benchlib/judge_qualification.py:147-181`) refuses before any
  model call on three conditions: < 200 live pairs, l2-fact premises below the 50%
  floor, or **any** live `label_source: "author"` pair.
- T2.11's Done-when requires adjudication by the qualified judge, so T2.11 is
  unsatisfiable in code until the record exists; T2.40 (G-C) depends on T2.11; the
  deriver lane (T2.27/T2.28/T2.48) and Phase-2 exit depend on G-C.

**The 0.8182 of 2026-07-31 was never a gate verdict.** Its own artifact
(`docs/eval/2026-07-31-judge-qualification.md`) is headed *"INTERIM — this is not a
qualification verdict"*: the 41-pair gold it ran on was ineligible on every composition
axis (41 < 200, l2-fact 0/41, author-labelled 41/41). So the situation is not "the judge
failed qualification and must improve before retrying" — it is "**no lawful
qualification run has yet happened**, because the gold that could power one did not
exist". The blocking artifact is the eligible gold, not the judge's score.

And the gold is much closer than the task file's 2026-07-31 framing suggests. The
committed `backend/scripts/benchlib/entailment/gold.json` today holds **241 live pairs,
153 (63.5%) with real `l2-fact` premises, 239/241 adjudicated by two merged blind
passes** (commit `73755a4e`; agreement 0.9917 per pass vs recorded, 1.0 pass-vs-pass).
Feeding it to `gate_eligibility`'s three conditions:

- 241 ≥ 200 — passes.
- 2 × 153 = 306 ≥ 241 — passes the 50% floor.
- author-labelled = **2** (`eg-0023`, `eg-0142`, the two Step-5 escalations in
  `entailment/escalation_queue.json`) — **the sole remaining refusal**.

So the entire blocker for T2.11 → T2.40 → the deriver lane is, today, **the owner's
T2.54 sitting**: ratify the Step-5 rulebook fork (LABELLING.md's unratified-extensions
section, which both escalations trace to), adjudicate the two escalated pairs, run the
n = 93 consistency resample (ratified 2026-07-31), retire-and-replace anything a
rejected proposal invalidates. LABELLING.md itself fixes that ordering: fork ruling
first, then escalations, then resample.

## 2. Were the bar and the measurement comparable? Metric yes; population no

The metric matches exactly: `contradiction_precision_bar = 0.95` was stated as a config
default before any number existed (verified at `verification_judge.py:286`), on
`contradiction_precision` = TP/(TP+FP) over predicted-contradicted, which is what the
scorer computed: 9 true contradictions + 2 false ones → 9/11 = 0.8182. No
metric-definition mismatch.

The population is where comparability breaks, in a way the eval doc itself recorded:
with 10 gold-contradicted pairs and 11 predictions, **a single false positive lands at
10/11 = 0.909**. Every achievable value between 0.909 and 1.0 is unoccupied, so at
n = 41 the 0.95 bar degenerates to "zero false positives" — it was not testable as a
threshold, only as exactness. On the 241-pair gold it becomes a real threshold: 55
gold-contradicted pairs; at the interim contradicted-recall of 0.9, ≈ 50 TPs, and
50/52 = 0.962 passes while 50/53 = 0.943 fails — the bar resolves at ≈ 0.018 per false
positive and tolerates about two. **Finding for the controller, not a tuning proposal:
the bar is right and stands.** It is doc 08 §5.3's precision-first doctrine made
numeric, it was stated before any run, and on the gold that will actually test it, it is
meaningfully testable. What was undersized was the July population, which was already
branded interim.

## 3. What the two false positives actually were — the errors are localized and half-contested

Both interim false positives are identifiable by arithmetic: the confusion matrix has
exactly 2 unsupported→contradicted cells, the direction slice has exactly 2 errors, and
the original 41's direction slice contains exactly 2 gold-unsupported pairs. So the
manufactured disputes are **eg-0023** (haproxy load-balancing role reversal) and
**eg-0025** (startup-dependency reversal). Both are **non-exclusive reversals**: the
ratified reversal rule (LABELLING.md's per-relation exclusivity table) labels a reversed
relation `contradicted` only when the relation is exclusive in direction (REPLACES,
IS_A, DEPLOYED_ON, …) and `unsupported` when mutual arrangement is coherent
(DEPENDS_ON, USES, balancer/backend roles, …).

Their subsequent fates differ, and both matter:

- **eg-0025**: both blind passes *confirmed* the recorded `unsupported`. This false
  positive survives re-adjudication — the judge has a genuine overreach error on
  non-exclusive reversals; the interim signal is not pure gold noise.
- **eg-0023**: both blind passes sided *with the judge* (`contradicted`) — but
  LABELLING.md attributes that to the condensed blind rulebook having dropped the
  ratified "load-balancing roles" precedent (fork item 4: *"nothing to ratify — this
  file already decides it"*). The recorded `unsupported` follows the ratified text.

The mechanism is visible in the frozen prompt (`SYSTEM_PROMPT`, prompt v1): it states
the right rule — *"a reversed relation when the relation is exclusive in direction"* —
but supplies **no criterion for which relations are exclusive**, so the model's own
exclusivity intuition fills the gap, and on both non-exclusive test pairs it filled it
wrong (2 for 2). The doctrine that decides exclusivity exists, ratified, in
LABELLING.md's table; the judge has never been shown it.

## 4. Forecast: a gate run on the current prompt very likely records a formal miss

This is the load-bearing measured claim. The 241-pair gold's direction slice holds
**14 gold-`unsupported` non-exclusive reversals** (counted from `slice_tags` ×
`verdict`: direction = 16 contradicted / 14 unsupported). The interim judge misfired on
2 of 2 pairs of exactly this shape. n = 2 is thin, so bound it: the Wilson 95% interval
for 2/2 is ≈ [0.34, 1.0]. Projected onto the new gold with TPs ≈ 0.9 × 55 ≈ 50:

- misfire rate 1.0 → 14 FPs → 50/64 ≈ **0.78**
- misfire rate 0.5 → 7 FPs → 50/57 ≈ **0.88**
- misfire rate 0.34 (charitable bound) → ~4.8 FPs → 50/54.8 ≈ **0.91**

Every point in the interval forecasts a miss against 0.95 (pass requires ≤ 2 FPs
*total*, i.e. a misfire rate ≤ ~14% on this shape alone, with zero FPs everywhere
else). A miss would be recorded, not retried — and it has an **irreversible side cost**:
LABELLING.md's Rule B requires the gate verdict to hold on both the all-live population
and the **never-contacted-by-any-judge-identity** subset (the 200 new pairs). The first
gate run spends that never-contacted property permanently, for every future judge
identity. Burning it on a run the interim evidence already forecasts to fail is a bad
trade, and rule 3 ("never re-run until it passes") makes the cycle after a miss
expensive by design.

## 5. Options

### Option A — sequence through the sitting, run the gate as-is

Owner sits (~3h, already owed to G-D regardless); T2.41 runs `--gate` on the current
prompt; if it clears, the record mints and T2.11 unblocks. **Cost:** owner calendar
only. **Forecloses:** nothing structurally — but per §4 the run is forecast to miss
across the whole charitable range, which would burn the never-contacted population and
put G-D into the miss-recorded state with a full re-qualification cycle behind it.
Cheap to start, expensive in expectation.

### Option B — the sitting, then a doctrine-alignment prompt revision, then one gate run (recommended)

After the owner ratifies the fork, revise the judge prompt to carry the **ratified**
exclusivity doctrine — the criterion ("is the reverse arrangement excluded by the
relation's meaning, or merely unasserted?") and/or the ratified per-relation table —
then freeze and run the gate once on the new judge identity.

Lawfulness, addressed head-on because the ledger flagged the tune-against-gold loop as
T2.26's one Critical finding: (a) there is **no qualification to invalidate** — the
prompt_sha change costs nothing because nothing is qualified; (b) the edit is justified
by ratified rulebook *text*, which is the task's definition and sits upstream of the
gold — it is not an edit steered by scored gold rows; (c) validation before the gate run
touches only `sanity_pairs.json` and fixtures, never gold, with `gold_touching_attempts`
published as T2.26 did; (d) Rule B's dual-population reporting stands as the check that
the revision generalizes. Residual honesty note: the doctrine table cites eg-0022/0025
as precedents, so the prompt author cannot be fully blind to those two shapes; that is
disclosed here rather than hidden. **The revision must wait for the ratification** —
proposals 1 and 3 are unratified, and encoding a rule the owner then strikes would aim
the judge at the wrong doctrine.

**Cost:** one small implementation task (prompt edit + fixture validation + freeze
discipline) inserted between the sitting and T2.41 — days, not weeks, and it
parallelizes with nothing since it needs the ratified text first. **Forecloses:**
nothing. **Needs a controller ruling** that a doctrine-alignment edit under the freeze
discipline is sanctioned (this analysis argues it is, and the 2026-07-31 ledger row
already anticipated it: *"any fix must be measured on T2.54's fresh gold regardless"*).

### Option C — split qualification per capability (entailment vs contradiction)

Entailed P/R measured 1.000/1.000 interim while contradiction failed, and the bars are
already three separate config rows, so the claims are separable in principle. **But this
unblocks T2.11 not at all** — T2.11 consumes precisely the contradiction capability —
and today it unblocks nothing else either, because no record of any scope can mint on an
ineligible gold, and the entailed 1.000s came from the same ineligible 41 pairs. Keep as
a *contingency*: if the post-T2.54 gate run passes entailment and misses contradiction,
a split record could open Phase-3 synthesis (G-D's groundedness half) while contradiction
re-qualifies. That is a gate-semantics change for the owner, not a build-now item.
**Cost if built now:** qualification-record schema + door enforcement complexity for
zero present value.

### Option D — narrow the judge's job so a weaker judge is lawful (advisory adjudication)

Have T2.11's scan emit judge verdicts as an advisory triage queue rather than
auto-writing disputes, capping the manufactured-dispute harm with a human instead of a
precision bar. This would require unwinding T2.26's deliberately built lock (the only
ungated door, `qualification_probe`, is scan-pinned to the harness) and re-ruling "no
consumer ships on an unqualified judge". It also diminishes what G-C measures: T2.40's
false-promotion audit counts *later-disputed* facts, and with no auto-adjudication the
dispute stream shrinks to T2.04's deterministic inverse-replacement rule plus human
rejections, undercounting false promotions — an overstated gate. **Cost:** task-graph
and enforcement surgery plus a permanently caveated G-C, to route around a ~3h sitting
that G-D requires anyway. Disproportionate; not recommended while Option B exists.

### Option E — re-scope T2.11 to the deterministic shortlist, no judge

Ship the combined generator (same-endpoint + `pg_trgm` shortlist) with adjudication
deferred. Same G-C-dilution objection as Option D, plus T2.11's Done-when ("adjudication
uses the qualified judge, not a heuristic") would need amendment. **The defensible
kernel of this option survives as a split, not a re-scope:** a **T2.11a** (generator
only — deterministic, judge-free, unblocked *today*, and the substrate T2.52's miss-rate
measurement and T2.33's gate need) and **T2.11b** (adjudication, keeping the existing
Done-when, behind T2.41). G-C's semantics are untouched provided T2.40's `Depends` edge
moves to T2.11b. This shortens the serial tail after the sitting at the cost of one
graph amendment, and forecloses nothing.

## 6. Recommendation (the controller's call, flagged as such)

**Option B, optionally with E's T2.11a/T2.11b split run in parallel.** Concretely:

1. **Schedule the owner's T2.54 sitting now** — it is the sole eligibility refusal and
   the critical path of everything downstream, and LABELLING.md fixes its internal
   order: fork ratification → escalation queue → n = 93 resample.
2. **Rule on the doctrine-alignment prompt revision** (Option B's lawfulness) so the
   revision task can be briefed the moment the fork is ratified. Do **not** run T2.41 on
   the current prompt: §4's forecast says that spends the never-contacted population on
   a predicted miss.
3. Optionally **mint T2.11a** (generator half) to start the Opus-tier build now.
4. One `--gate` run on the frozen revised judge; if it clears both populations, the
   record mints and T2.11(b) → T2.40 proceed.

## 7. Is T2.54's sitting on T2.11's critical path? **Yes — under every option that keeps a judge in T2.11**

The qualification record is mintable only from an eligible gold; eligibility fails today
solely on the two author-labelled escalations; only the owner can adjudicate them (and
must ratify the fork first, since both escalations trace to it). Options A, B and C all
run through that sitting. Only D/E remove it from T2.11's path, by removing the judge —
at the cost of gate-semantics surgery disproportionate to roughly three hours of owner
time. Decisive fact: **the sitting is already mandatory for G-D (T2.41), so its marginal
cost to T2.11 is zero additional owner work** — it is not a new obligation, it is the
same one, and it now holds two gates instead of one.
