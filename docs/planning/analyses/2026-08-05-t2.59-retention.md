# T2.59 — Content retention on delete: measured surface and policy options

**Date:** 2026-08-05 · **Task:** T2.59 (E2-truth-core) · **Doc:** 04 §8.1, 08 §2.3, invariant 14
**Status: analysis only.** T2.59's own text says it implements whichever policy the owner
states and does not choose one. This document measures the real surface, works the four
candidate policies, and recommends — **the decision is the owner's, made through the
controller; nothing here is it.** No code, no tests, no schema were changed.

---

## 1. What a delete actually removes today

Both interactive doors (`DELETE /memories/{id}` and `POST /memories/delete`) route through
`MemoryService.delete_memory` (`backend/app/services/memory.py:320`), which:

1. Forgets the memory's `pipeline_failures` rows (`memory.py:327-328`) — failure rows and
   their `error_message` do **not** outlive an interactive delete.
2. Demotes `superseded_by` dependents, deletes the `memories` row — `content`, `summary`,
   `classified_type`, `emotions`, tags links (CASCADE, orphans pruned) all go with it.
3. Journals a `delete` event whose payload is `{}` (`memory.py:340`,
   `repositories/relational.py:285-293`) — **the deletion itself leaks no content into the
   journal.**
4. Calls `pipeline.delete_memory` (`services/pipeline.py:1240-1251`): vector rows in the
   fingerprint partition, graph contributions no other live memory asserts, and
   `withdraw_memory_sources` (`services/fact_provenance.py:302-307`) — provenance rows are
   deleted and a fact whose last source vanished has belief withdrawn inline.

That is a genuinely thorough delete. What follows is what it cannot reach.

## 2. What survives a delete — the measured census

The task text's two claims are both confirmed live, with one precision correction:
`buffer_discarded` previews are **discarded-capture** content, not deleted-memory content —
discard and requeue act only on `status='error'` rows (`services/buffer_monitor.py:192-199`),
which never materialized as memories. The content still outlives its intended destruction,
so the escalation's framing stands, but the actor is the discard door, not the delete door.

### 2.1 Durable stores (no expiry mechanism exists)

| Store | Field | Content | Writer | Retention |
|---|---|---|---|---|
| `events` (`buffer_discarded`) | `payload.content_preview` | first **500 chars** of the raw capture (`LEFT(content, 500)`) | `buffer_monitor.py:55,69,278-290` | forever |
| `events` (`buffer_requeued`/`_discarded`) | `payload.last_error` | error text; can quote content fragments | `buffer_monitor.py:250,288` | forever |
| `events` (`consolidated`, refine) | `payload.before.summary` / `after.summary`, tags | **full summaries**, memory-derived prose | `memory_dream.py:1145-1164` | forever |
| `events` (`undone`) | `payload.before` / `after` | mirror of the undone action — refine summaries again | `dream_undo.py:850-863` | forever |
| `events` (`verified`) | `payload.contradiction.counterpart_*` | subject/rel/object tokens of the counterpart claim | `knowledge_triples.py:790-810` | forever |
| `events` (`human_verdict`) | `payload.note` | operator-authored note (capped), may quote content | `human_adjudication.py:162` | forever |
| `events` (`consolidated`, pin_suggested) | `label`, `subject_key`, `why` | topic tokens derived from content | `pin_suggestions.py:471-483` | forever |
| `messages.context` | `memories[].content` | **150-char** snippet per cited memory | `services/chat.py:196-199` | until the conversation is deleted |
| `messages.context` | `facts[]` | cited fact rows **untrimmed** — full statement text | `chat.py:200` | until the conversation is deleted |
| `messages.content` (assistant) | whole answer | **unbounded model prose restating cited memories** | `chat.py:184-189` | until the conversation is deleted |
| `knowledge_triples.fact` | free-text statement | full distilled claim from source memories | fact lift; retained by design | forever — belief withdrawal is "a re-save on the retained row, never a delete" (`knowledge_triples.py:329-330`), and the fact-detail door deliberately serves belief-withdrawn rows |

Events retention was verified, not assumed: `rg` over `backend/app` and `backend/migrations`
finds **no** `DELETE FROM events`, no ORM delete, and no partition drop or detach anywhere;
`events_ensure_partition` only creates. Combined with T1.06's three forbid-triggers, an
`events` payload written today is on disk for the life of the database.

### 2.2 Bounded stores (residue expires on its own)

| Store | Content | Bound |
|---|---|---|
| `memory_buffer.content` (`done` rows) | the **full raw content** of every successfully processed memory | `buffer_done_retention_hours`, default **24h** (`buffer_flush.py:78,919-921`); `error` rows are never swept — they are the triage queue — but never became memories |
| `memory_communities.report_string` | LLM prose written about member memories | rewritten by the nightly `topic_detection` cycle (cron `0 4 * * *`, `dream_jobs.py`); can persist longer if the report pass fails |
| `pipeline_failures.error_message` | exception text, can quote content | forgotten inline on interactive delete; cleanup job sweeps the rest |
| `entity_embedding_cache__<slug>` | entity **names** (content-derived tokens) keyed `(name_lower, fingerprint)` | never pruned on delete; manual `POST /reembed/prune-cache` exists |

### 2.3 Substrate (below any application policy)

Postgres WAL, dead tuples until vacuum, and any `pg_dump` backups retain everything ever
written. No option in §4 reaches this layer; a policy claiming "erased" while backups exist
over-claims regardless of what the application does.

### 2.4 The ceiling every option shares

For a memory that was ever cited in chat, the **assistant's own answer** restates its
substance in model prose (`messages.content`). Memory-derived spans in that prose cannot be
identified after the fact, so no redaction scheme can remove them — only deleting the
conversation can (cascade `all, delete-orphan`, `models/chat.py:23`). **Every policy short
of conversation deletion therefore delivers at most "previews and snippets gone", never
"content gone."** Any policy the owner picks must word its user-visible claim below this
ceiling or it lies.

## 3. The four candidate policies

### Option A — redact the preview in place (breaks append-only)

**Mechanism.** A privileged path UPDATEs `events` payloads (and `messages.context` entries)
for a deleted memory id, replacing content fields with a tombstone marker. Requires
weakening or bypassing T1.06's row-level UPDATE guard — trigger exemption, `SECURITY
DEFINER`, or `session_replication_role`.

**Costs and breaks.**
- The forbid-trigger is what makes the journal evidence rather than convention: undo counts
  its own `undone` rows back (`dream_undo`), the digest replays the `consolidated` stream in
  journal order, G-C counts blocked promotions from journal rows. Once any code path can
  rewrite `events`, "what the journal says happened, happened" is trust-by-audit-of-the-
  redactor, forever.
- `undone`/`consolidated` before/after payloads are the **restore source** for undo.
  Redacting a refine action's `before.summary` destroys its undoability. Scoping redaction
  to actions on already-deleted memories makes undo moot for those rows, but the scoping
  logic is itself a correctness obligation on the one subsystem built to have none.
- `messages.context` is a JSON scan across every message of every conversation per delete.
- Buys actual removal from live tables only — not from WAL, dead tuples, or backups (§2.3),
  and not from assistant prose (§2.4).

**Operator observes.** Journal and chat citations show `[redacted]`; the answer text still
paraphrases the memory; `pg_dump` from last week still has everything.

### Option B — stop writing content into events at all

**Mechanism.** Prospective: drop `content_preview` from `buffer_discarded`, summaries from
refine/undone payloads. Existing rows keep their content unless combined with A.

**What `memory_buffer` triage concretely loses.** Discard **deletes** the buffer row
(`buffer_monitor.py:276-290`), so the event's 500-char preview is the *only* surviving
record of what was thrown away. `last_error` says why it failed, never what it said. Without
the preview, a mistaken discard of a poison row becomes unrecoverable **and
uninvestigatable** — the operator who asks "what did I just drop?" has no answer anywhere in
the system. The alternative (keep discarded buffer rows instead of deleting them) relocates
the full content into `memory_buffer` indefinitely — the same retention question, moved.

**What undo loses.** Refine before/after summaries cannot be dropped without breaking undo
of refine actions outright — `dream_undo` restores from the journal payload. Storing
restores in a shadow table relocates the content again. So B degenerates to "drop the
buffer_discarded preview only", paying a real triage cost to shrink one field while the
larger stores (§2.1) stand untouched.

### Option C — tombstone-and-exclude at read time

**Mechanism.** Record deleted memory ids (the `delete` events row already carries the id);
every reader of `events` payloads and `messages.context` blanks content fields whose subject
is deleted. Append-only survives intact.

**Costs and breaks.**
- Content is still on disk; the guarantee is presentational. In a single-operator homelab
  the person the mask hides content *from* is the person who owns the database — `psql`
  shows everything the UI withholds.
- Every current and **future** journal reader must remember the filter: the three events
  doors, `analytics/pipeline-logs`, conversation reads, the dream digest. That is exactly
  the "surface nobody decided" failure mode `content_surfaces.py` exists to prevent,
  reintroduced as a per-door filter obligation that each new door can silently forget.
- It inverts invariant 14's posture: this corpus serves labelled rather than withholding.
  C withholds.
- Deleted-memory lookups against `events` are by-id scans over monthly partitions — the
  same composite-PK pruning discipline T2.13 had to build, now on every read door.

**Operator observes.** Previews vanish from the UI; the data is one `docker exec ... psql`
away. Permanent read-path tax for a guarantee that guards against nobody.

### Option D — accept and document the retention

**Mechanism.** No storage change. The delete doors' UI copy and the docs state plainly what
§2 measures: deleting a memory removes the row, its vectors, its graph and its provenance,
and withdraws belief from facts it solely sourced; short previews and summaries persist in
the append-only journal, citation snippets and answer text persist in chat history until the
conversation is deleted, and the full raw content persists in the capture buffer for 24
hours.

**Costs.** Honesty only: the claim "delete" must stop implying erasure (Done-when 3). One
real residual risk needs an answer — an **accidentally captured secret** (a pasted API key
lands in a 500-char `buffer_discarded` preview and is on disk forever). That case is real
even in a homelab.

**What it forecloses.** Nothing. Every other option remains buildable later; A/B/C each
foreclose or tax something immediately.

**Operator observes.** Exactly what the docs told them to expect — the one option where the
observed behaviour and the stated behaviour already match.

## 4. Recommendation — flagged as the owner's decision to make

**Option D, with three riders.** Reasoning, in order of weight:

1. **No option can deliver erasure anyway** (§2.4, §2.3). Assistant prose and the substrate
   sit below all four policies. A/B/C each pay real, permanent costs to narrow a gap they
   cannot close; only D's claim can be worded to match achievable behaviour, which is what
   Done-when 3 actually demands.
2. **The append-only journal is load-bearing** — undo restores from it, the digest replays
   it, G-C counts from it — and this is a single-operator homelab: the deletion guarantee
   would protect the operator from themselves, while the audit trail protects the system's
   evidentiary chain from every subsystem that writes to it. The trade is not close.
3. **The corpus already practices the correct standing mitigation**: write-time
   minimization. `ContradictionFinding` deliberately refuses to copy the free-text fact into
   the journal *because* payloads outlive their subject (`contradiction_veto.py:153-159`);
   supersede/deprecate journal status transitions only; the `delete` event carries `{}`.
   Retention accepted at read time is being minimized at write time, which is the only place
   minimization is free.

The riders, if the owner states D:

- **R1 — honest copy.** Delete-door UI and docs state §2's residue explicitly, including
  the existing remedies: conversation deletion cascades snippets and prose; the buffer bound
  is 24h and configurable.
- **R2 — a documented break-glass purge, not an in-app one.** For the pasted-secret case:
  a written operator procedure (stop the app, superuser `UPDATE`/`DELETE` with triggers
  disabled for the session, `VACUUM`, rotate the secret, refresh backups). This answers the
  one genuinely dangerous residue without giving the application a journal-rewriting code
  path — the operator already owns the substrate; the procedure just writes down what
  ownership means.
- **R3 — keep write-time minimization as the standing rule.** New event payloads copy
  content only when a feature (undo, discard postmortem) demonstrably needs it, and state
  so at the writer — the discipline `ContradictionFinding` already models.

If the owner instead wants a real deletion guarantee, the honest minimum is A+B+C combined,
plus per-conversation deletion prompts, plus a backup-rotation policy — a materially
different system, and disproportionate for this deployment. Stating that is this analysis's
job; choosing is not.

## 5. Adjacent findings (outside T2.59's lane, surfaced not fixed)

- `pipeline.delete_memory` wraps all cleanup in a blanket `except Exception` that only logs
  (`pipeline.py:1257-1258`), so a failed provenance withdrawal is swallowed; the corpus
  knows (`reap_orphaned_memory_sources` names it as the healed case,
  `fact_provenance.py:310-321`) and the cadence backstop covers it.
- The TTL sweep bypasses provenance withdrawal entirely — already owned by T2.61.
- `messages.context.facts` being persisted **untrimmed** (`chat.py:200`) while memory
  snippets are trimmed to 150 chars looks like an oversight rather than a decision; whatever
  policy is chosen should decide it explicitly.
