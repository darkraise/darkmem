# Multi-replica decision record — stay single-worker

**Written:** 2026-08-16, executing T4.10 (`docs/planning/tasks/E4-hardening-and-scale.md`,
Lane D). Input: the T4.09 audit
(`docs/planning/analyses/2026-08-15-t4.09-in-process-assumption-audit.md`, closed done
2026-08-16 — 38 assumptions, 17 BREAKS / 13 DEGRADES / 8 ALREADY SAFE). Tree state this
record was decided against: `d8f7255a`. This is a decision record, not an implementation:
nothing here freezes the schema, arms an enforcement, or changes a deployed replica count.

## The decision

**Stay single-worker — chosen, not defaulted into.** Invariant 13 stands: exactly one
uvicorn worker, one replica, on every launch path. The constraint is re-asserted in
`CLAUDE.md`'s cross-cutting invariants in the same commit as this record, which is the
Done-when's required edit for this branch of the decision.

The grounds are deliberately **not** the snapshot. Doc 02 §11, doc 03 §3.2, doc 19 §5 and
`feature-epics.md` all defend invariant 13 with the cached PPR/igraph snapshot, which is
the one member of the inventory that costs nothing today: `w_ppr` is `0.0` and
`ppr_enabled` False (`app/config.py:218-219`, re-verified at `d8f7255a`), the arm returns
before touching the cache (`hybrid_search.py`, `if not ppr_weight: return []`,
re-verified), and the gate ledger measured it at aggregate ΔMRR −0.2609 and left it off.
The constraint is re-asserted on the rows that would actually bite on day one — audit
items 1, 2 and 10:

1. **WebSocket fan-out (item 1, BREAKS).** `EventManager.connections` is a per-process
   list. A capture processed on worker B never emits `pipeline.completed` to a client
   whose `/ws` landed on worker A; the UI stays "processing" with no error anywhere.
2. **The job scheduler has no lease (items 2–6, BREAKS ×5).** Both workers fire every
   cron tick from the same wall clock, so all 21 jobs run N times *concurrently*; the
   409-busy contract reads a local `asyncio.Lock` and becomes false; `_run_once`'s
   read-modify-write silently reverts operator config; one disable/enable cycle kills
   N−1 schedulers; and seven job cursors are advanced by unlocked read-modify-write.
3. **The login rate limiter is process memory (item 10, BREAKS).** 5 failures per IP per
   300 s becomes 5N, a locked-out IP mostly is not locked out, and a successful login
   clears only one worker's state.

## Why neither of §11's remedies is takeable

Doc 02 §11's menu — "sticky routing or a serialised snapshot table" — addresses **1 of
38** findings, and that one is inert. Sticky routing pins a client's requests to one
worker; it does not deliver an event produced by a worker the client is not stuck to
(item 1 — jobs and other clients' captures run elsewhere), does not give two schedulers a
lease (item 2), and does not merge two rate-limiter dicts (item 10). A serialised snapshot
table is the item-32 precedent applied to item 18 — the right mechanism for a problem that
is currently switched off and measured negative. Taking either option and calling the
system multi-replica-safe would be the worst outcome available: the deployment gains the
failure modes and the record claims they were handled.

## What taking multi-replica honestly would cost

The 17 BREAKS need at least **five unrelated mitigation classes**, and the audit's finding
2 — re-verified at `d8f7255a`: zero `pg_advisory*` hits in `backend/app`, every "advisory"
match is prose — means none of them exists as a shared primitive to extend:

| Class | Mechanism the failures require | Audit items |
|---|---|---|
| Fan-out channel | broker or `LISTEN/NOTIFY` behind `EventManager` | 1 |
| Job lease / leader election | DB-held lease per job key, replacing wall-clock coincidence and local locks | 2, 4, 5, 22 |
| Concurrency-safe config writes | CAS or `FOR UPDATE` on `job:<key>` rows and all seven cursors; upsert for the wiki render cache | 3, 6, deferred wiki item |
| Shared mutable state → DB | limiter counters, `retry_locks`, `reembed_locks`, repo status claims | 10, 11, 36, 12, 13, + the repo_sync finding below |
| Invalidation channel | orchestrator swap, prompt overrides, classifier cache; plus pool arithmetic, slug guard, and the post-freeze migration lock | 8, 9, 15, 37, 16, 14, 38 |

Against that cost there is **no demand and no throughput case**. Phase 4's trigger — an
actual exposed deployment or a concrete second consumer (doc 20 §10, E4's epic head) — has
not fired; the deployment is one user on a homelab. And the system's load is upstream of
the app process: ingest is bounded by DeepSeek and the Ollama embedder over the network,
retrieval by Postgres — a second asyncio worker adds capacity to none of those, while item
16 shows it *subtracts* DB headroom (`FATAL: too many clients` at N ≥ 3 under the 120-
connection budget). A second worker today is cost plus risk with no benefit to point at.

## The post-audit finding, assessed

T4.05's review (2026-08-16) surfaced that `make_repo_sync_runner`
(`app/services/job_runners.py`) never reads `repo.status` — re-verified at `d8f7255a`: it
selects on `auto_sync` alone and enters `CodePipeline.run` unconditionally, and one
failure disables `auto_sync` for the repo. **It does not change the decision; it
strengthens it twice over.** First, it is a single-process hazard that N workers multiply,
so it belongs to the same ledger the decision is charged against. Second, it is a
39th-class member found *the day after* a census closed at 38 following three consecutive
enumeration corrections — live proof of the audit's finding 2 that the safe set does not
grow on its own. The suggested close (a compare-and-swap status claim inside `run()`) is
worth taking on single-process grounds alone and is not this record's to implement.

## Verified against the tree, not inherited from the audit

The brief's rule — a decision hinging on an *absence* must verify it — applied to every
absence this record leans on, all at `d8f7255a`:

- **No replica knob is set anywhere**, in any of its three spellings: no `--workers`
  (`entrypoint.sh`, both compose files, `start_dev_server.sh`, `Dockerfile`), no

- **PPR arm inert** at both pins (`config.py`, `hybrid_search.py`).

## What would flip this answer

Recorded so the next asker starts here instead of at zero:

1. **The Phase-4 trigger fires** — an exposed deployment or a concrete second consumer —
   *and* the app process itself is the measured bottleneck (not its LLM/embedder
   upstreams, which replicas do not scale). Availability is the other honest driver:
   zero-downtime restarts want two replicas, and would pay the same full cost below.
2. **Even then, the flip is not "pick from §11's menu".** Any replica plan must carry a
   named mitigation for **all 17 BREAKS** across the five classes above — the Done-when's
   "each T4.09 assumption has a named mitigation" — plus three items that ride along at
   their worst: item 38 (the unserialised `alembic upgrade head`, DEGRADES today and
   BREAKS after the schema freeze, and the freeze precedes any plausible Phase 4), the
   unnumbered `wiki_generator` render-cache write, and the repo_sync status claim.
3. **The audit's enumeration record prices the diligence.** Its reasoning held through two
   adversarial reviews; its enumeration failed three consecutive times and grew again the
   next day. A flip must re-run the audit's two committed greps and re-sweep for
   singletons rather than treating 38 (now effectively 39) as closed.

## Who decides what

This does not trigger the loop's stop condition 4. Staying single-worker re-asserts the
standing owner-ratified posture (invariant 13; doc 02 §11's own recommendation; doc 19
§5's recorded rejection of any multi-worker shape), changes no deployed behaviour, spends
nothing, and forecloses nothing — the flip conditions are written down. The asymmetry is
real and recorded: **taking** a replica option is the owner's call (spend, operational
surface, demand judgment) and additionally requires the mitigation work above; this record
does not take one, so the reasoning decides and no owner ruling is needed today.

## Recommended, deliberately not armed here

Two follow-ups this record recommends and does not implement, because arming anything is
outside T4.10's sanction:

1. **A tripwire test for the replica count** — assert `entrypoint.sh`, both compose files
   and the dev script carry no `--workers`, no `WEB_CONCURRENCY`, no `deploy.replicas`.
   T4.10's task text names the exact failure shape (a replica count changed in an
   unrelated ops change) and today nothing in the tree detects it; the corpus's own
   pattern for prose that must not silently rot is a scan, not a sentence.
2. **Make holding process state a reviewable act.** The audit's durable finding is that
   the safe set is safe one statement at a time. A standing review rule — new in-process
   mutable state outliving a request is either self-healing with a bounded window (item
   19's class) or DB-backed with a concurrency-safe write, stated at the writer — is what
   stops the inventory growing silently. Its adoption is the owner's.

invariant) remain surfaced-not-corrected under T4.09's Tier-3 escalation; this record
supersedes §11's menu as the decision input of record but edits no design doc.
