# T2.116 — the attempt counter keys on the wrong identity

**Raised:** 2026-08-12, during T2.116's execution. **Tier:** 3 (a gate's
disclosure instrument would have to change). **Status:** **RULED AND APPLIED**
2026-08-12 — owner ruled both halves: re-key the counter, and record the
analysis.

---

## What was found

`gold_touching_attempts` is doc 17 §6's anti-tuning disclosure for G-D. It
exists because, in T2.41's words, *"an open-ended sweep until one clears is
tuning-against-gold by another route, and `gold_touching_attempts` counts
contacts so it stays visible."* Every judge attempt against the entailment gold
increments it, across all judge identities, and a run reports it.

It keyed on the gold's **file** sha.

T2.116 required writing a content basis (`pairs_sha256`, `pair_digests`) into
the `resample` block, which lives inside `gold.json`. That moved the file sha
from `98fc4b49` to `6eadba73` while changing no pair. The counter went with the
file, and the next run would have reported **0** contacts for a pair set that
had already been judged once.

## Why the two cannot both be true

Doc 17 §6 wants a count of *contacts with the gold* — the thing a judge is
measured against, which is the labelled pairs. The implementation counted
*contacts with a file*, and `gold.json` carries three kinds of content a judge
is never shown: rationales, slice retags, and the resample block's own
certification. Any edit to any of them resets the disclosure.

So this was never only T2.116's problem. **Rewriting a single rationale has
always zeroed the counter, silently**, at any point in this gold's history —
and the runner's own docstring claimed the opposite in terms: *"The counter
keys on `gold_sha256` across ALL judge identities, so a prompt-version bump can
never reset it."* True about prompt versions, and misleading about everything
else.

## Evidence

Five attempt rows in the ledger, and the pair set each actually saw — recovered
by walking git history for each recorded file sha:

| Attempt | Gold file sha | Pair set | Today's pairs? |
|---|---|---|---|
| ×3 (early gold) | `e6d5647a` | `2edbb758` | no |
| `gpt-5.5` | `800d4d91` | `8e210191` | no |
| `deepseek-v4-flash` | `98fc4b49` | `4975c5cc` | **yes** |
| — | `6eadba73` (after the stamp) | `4975c5cc` | — |

The fragmentation is **pre-existing**: three distinct file shas before T2.116
touched anything. T2.116 added a fourth and made the visible number 0 where the
honest number is 1.

**Why it bit now rather than later.** T2.114 is the next G-D run and the owner
ruling fixes its model as `gpt-5.5`. That is genuinely gpt-5.5's first contact
with this pair set — its earlier attempt was against `8e210191`, from before
T2.115's resize. So the counter should read 1 (deepseek's contact) and would
have read 0. The number that would have been wrong is the one on the run about
to be authorised.

## The ruling

Key the counter on `gold_pairs_sha256` — `entailment_gold.pairs_content_hash`,
the same basis T2.116 established for the certification.

**It is strictly more conservative and cannot lower any count.** A contact can
no longer be shed by editing anything a judge was never shown, and no reachable
edit reduces the number. That direction matters: for an anti-tuning disclosure,
over-counting is a nuisance and under-counting is a failure.

Three things stop resetting it that never should have: annotation churn, the
certification's own insertion into the file, and any future stamp of this kind.

## How it was applied

- `run_judge_qualification.count_gold_touching_attempts` counts by pair
  identity. Rows predating the field are still credited through their
  `gold_sha256`, so an un-backfilled ledger never *loses* a contact it used to
  count — the two keys are OR'd, never AND'd, for exactly that reason.
- New attempt rows, the run meta and the qualification record all carry
  `gold_pairs_sha256` **beside** `gold_sha256`, not instead of it: they answer
  different questions, and a reader comparing two runs needs to see when the
  file moved while the pairs did not.
- `backfill_attempt_pair_hashes.py` recovers the pair identity of historical
  rows by walking git history for each recorded file sha. It is **evidence
  recovery, never invention** — a row whose gold state is not in history is
  left alone rather than guessed at, and recovered rows are marked
  `gold_pairs_sha256_backfilled` rather than passed off as recorded. All five
  rows on this machine resolved; none was guessed.
- The counter now reports **1** for the current pair set.

The regression test is written with the real shas (`98fc4b49` → `6eadba73`,
pairs `4975c5cc`) rather than synthetic ones, because the defect was reachable
only through a real sequence of events. Reverting to the file key reddens it.

## What this does not fix

The ledger is gitignored, machine-local state. The counter therefore discloses
what *this machine* has spent, not what the project has, and the backfill is
per-machine. That was true before this change and is unchanged by it; it is
recorded here because a reader could otherwise take the count for a
project-wide fact.

Nothing here revisits G-D's bars, its gold, or its verdict. The disclosure now
counts what doc 17 §6 says it counts.
