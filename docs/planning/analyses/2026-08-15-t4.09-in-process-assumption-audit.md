# In-process assumptions a second worker breaks — the audit T4.10 consumes

**Written:** 2026-08-15, executing T4.09 (`docs/planning/tasks/E4-hardening-and-scale.md`,
Lane D). **This is a decision input, not a plan.** It proposes no architecture, picks no
option, and mitigates nothing. It enumerates what is true of the tree today so that T4.10 —
sticky routing, a serialised snapshot table, or stay single-worker — is decided against the
real inventory rather than against the four assumptions doc 02 §11 happens to name.

Nothing here was executed. Another lane owned the test databases during this audit, so the
findings are read from source; every claim carries the file and line that supports it, and
where a claim depends on Postgres semantics rather than on code, the mechanism is written
out so a reader can disagree with it.

**Deployment baseline.** `entrypoint.sh:6` is `exec uvicorn app.main:app --host 0.0.0.0
--port 8000 --no-proxy-headers` — no `--workers`. `docker-compose.dev.yml:23` likewise.
N = 1 today, and every finding below is conditional on that changing.

---

## Three findings that change what T4.10 has to decide

**1. The exemplar the corpus reaches for is the one that costs least today.** Doc 02 §11,
doc 03 §3.2, doc 19 §5 and `feature-epics.md` all lead with the cached PPR/igraph snapshot.
That snapshot is currently inert in retrieval: `w_ppr` is `0.0` (`app/config.py:219`),
`ppr_enabled` is False (`:218`), and `HybridSearchService._ppr_search` returns before
touching the cache at all (`app/services/hybrid_search.py:472-473`, `if not ppr_weight:
return []`). The gate ledger records the arm measured at aggregate ΔMRR **−0.2609** and
left at weight 0 with a design finding against it (ledger, 2026-08-06 `w_ppr` row). So the
flagship justification for invariant 13 is an arm that is off, measured, and rejected —
while the assumptions that would actually produce wrong answers on day one (the WebSocket
fan-out, the job scheduler, the login rate limiter, the live orchestrator swap) are named
in doc 02 §11 not at all.

**2. There is no cross-process serialisation primitive anywhere in `backend/app`.** A grep
for `pg_advisory_lock` / `pg_try_advisory_xact_lock` over the whole backend returns nothing;
the only "advisory" hits are prose about advisory *reads*. Every subsystem that survives a
second worker survives because someone wrote a specific SQL statement that way — `FOR UPDATE
SKIP LOCKED` in the buffer claim, `FOR UPDATE` on the fact row in the ladder, `EXCEPTION
WHEN duplicate_table` inside `events_ensure_partition`. There is no policy, no shared
helper, and no test that would notice a new job going in without one. That is the single
most decision-relevant fact in this document: the safe set is safe one statement at a time,
so it does not grow on its own as the tree grows.

**3. The option set in doc 02 §11 addresses one finding out of twenty-eight.** "Sticky
routing or a serialised snapshot table" is a remedy for the snapshot. Neither option touches
the job scheduler (which needs a lease), the login rate limiter (which needs shared counter
state), or the WebSocket fan-out (which needs a broker or `LISTEN/NOTIFY`) — and sticky
routing does not help the last two at all, because the events they lose are produced by a
worker the client was never routed to. T4.10 should treat §11's menu as incomplete rather
than as the choice set.

## Severity vocabulary

- **BREAKS** — a second worker produces a wrong row, a wrong response, or a silently missing
  one. No error surfaces.
- **DEGRADES** — duplicated work, duplicated spend, extra latency, or a bounded window of
  divergence that heals itself. Nothing ends up wrong.
- **ALREADY SAFE** — survives a second worker untouched, and the reason is named. An audit
  that called everything broken would be worth as little as one that missed things.

## The four assumptions the task named, verdicted

| Named assumption | Verdict |
|---|---|
| Cached PPR/igraph snapshot (T2.32) | **Not the problem today.** Inert at `w_ppr = 0.0`; the arm returns before reading the cache. Becomes a first-order ranking bug only if the arm is activated — and the ledger's measurement argues against that happening. Item 18 |
| Feature-flag TTL cache | **DEGRADES, mildly.** A 5-second self-healing divergence window with no invalidation path to get wrong. Item 19 |
| Entity-embedding LRU | **Correctness-safe.** Fingerprint-keyed at both tiers, physically partitioned in the DB tier, upsert does not overwrite the vector. Costs residency and round-trips only. Item 20 |
| Every per-job `asyncio.Lock` | **The real one, and worse than "locks stop working".** The locks are the least of it: there is no lease anywhere, both workers fire on the same wall clock so they collide rather than interleave, `_run_once` reverts operator config, the 409-busy contract becomes false, and one disable/enable cycle silently kills N−1 schedulers. Items 2–6 |

Two of the four named assumptions do not break. The assumption that does break, breaks in
five distinct ways, only one of which is about a lock.

## Doc 02 §11 against the tree — what is wrong or stale

1. **§7's cache inventory is false, and it is a "here is the full list" sentence** (the shape
   invariant 23 exists for). It reads: *"The only app-side caches are the feature-flag TTL
   cache and the entity-embedding LRU-plus-DB cache; the content-hash LLM cache lives in the
   bench harness, not the runtime."* The tree also holds, in `backend/app` alone: the PPR
   snapshot cache (`ppr_snapshot.py:308`), the ML model cache (`ml_runtime.py:66-70`),
   tree-sitter language handles (`code_parser.py:51-52`), prompt overrides
   (`prompt.py:686`), the embedder-registry memo (`embedder_registry.py:181`), the two
   access-stat buffers, the pipeline's 30-second classifier-resolution cache
   (`pipeline.py:211`, `:234-239`), and `pipeline_failures.retry_locks`. Most postdate the sentence;
   that is how the sentence went stale, not a reason it is still true.
2. **§11's single-worker bullet names one assumption and implies it is the binding one.**
   It is currently the *least* binding, for the reason in finding 1. A reader who takes §11
   at face value would size the multi-replica question at one cache and would not learn that
   the login rate limiter multiplies by N or that jobs have no lease.
3. **§11's remedy pair is not a decision menu.** "Sticky routing or a serialised snapshot
   table" solves item 18 and nothing else. Sticky routing does not deliver an event produced
   by the worker a client is not stuck to (item 1), does not give two schedulers a lease
   (item 2), and does not merge two rate-limiter dicts (item 10).
4. **§10's architectural-invariant list omits the single-worker invariant entirely.** §8
   says the assumption *"is load-bearing and flagged now"* and §11 says the decision is
   *"recorded here rather than discovered later"* — but invariant 13 appears in doc 03 §3.2,
   doc 19 §5 and `feature-epics.md`, and not in the one list in doc 02 that enumerates what a
   subsystem doc may not break. Doc 02 is the document §11 points at; the invariant should
   be in its §10 or §11 should stop claiming to be where this is recorded.
5. **Not stale, and worth crediting:** §11's *recommendation* — keep single-worker for v1 —
   is the stance this audit's evidence supports, and §8's mermaid topology and the
   app-as-edge settlement are accurate against `entrypoint.sh` and both compose files.

One correction outside §11, in the same class: `buffer_flush.reclaim_stale`'s docstring
(`:450-461`) justifies its own safety on invariant 13 by name. It is a comment that becomes
false the moment T4.10 goes the other way, and it is load-bearing for a reader deciding
whether the reclaim can steal a live claim (it cannot — but for the 10-second settle margin,
not for the reason written down).

## What T4.10 should decide first

Not a proposal — an ordering, with the reason each item earns its place.

1. **Decide whether "stay single-worker" is being chosen or defaulted into.** The evidence
   above favours the standing recommendation, but the corpus currently defends it with the
   one exemplar that costs nothing. If the constraint is re-asserted, it should be
   re-asserted on items 1, 2 and 10, which are the ones that would actually bite.
2. **Decide whether the invariant gets an enforcement, not only a sentence.** Today nothing
   fails a build, a gate or a boot if `--workers 2` appears in `entrypoint.sh`. T4.10's own
   task text warns that a replica count changed during an unrelated ops change is how this
   breaks silently — and that is precisely the shape of failure nothing in the tree
   currently detects.
3. **Decide what class of state a new subsystem may hold, before more of it accrues.**
   Finding 2 is the durable one: the safe set is safe one SQL statement at a time. Whatever
   T4.10 rules, the number of in-process assumptions grows monotonically until something
   makes holding process state a reviewable act.
4. **Only then weigh §11's two remedies** — and weigh them against the whole inventory, not
   against the snapshot. If multi-replica is taken, items 1, 2 and 10 need mitigations of
   three different kinds, and none of the three is "sticky routing".

**A note on scope for whoever writes T4.10.** This audit deliberately does not say what any
mitigation should be, does not rank the options, and does not estimate cost. Where it says a
remedy class would be needed (a lease, shared counter state, a fan-out channel), that is a
statement about what the failure requires, not a recommendation of a mechanism.
