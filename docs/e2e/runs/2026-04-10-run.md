### Phase 4
- [bug][fixed] **Hybrid search silently returns zero results for every non-empty query.** Reproduced via API: `POST /memories/search/paginated {"query":"database"}` returned `{total:0}` while `POST` with empty query returned 25. Root cause: `HybridSearchService._semantic_search` returns `memory_id` as a string, but `PostgresMemoryRepository.get_many` built a lookup dict keyed by `UUID` objects (`by_id[m.id]`) and then checked `if mid in by_id` using the raw string ids — the membership test always failed, so every hit was silently dropped. Pure-semantic path (`hybrid_search_enabled=False`) worked because `PostgresVectorRepository.search` returns UUID objects. Fix: normalize input to UUIDs in `get_many` at `backend/app/repositories/relational.py:38-45`. Verified: search for "database" now returns 25 ranked results with the pgvector memory at the top. This is a ship-blocker — the UI search bar is effectively dead whenever hybrid is enabled (which is the default).
- [note] Backend uses uvicorn `--reload`, so the fix hot-reloaded without a restart.
- [bug][fixed] **`DELETE /api/v1/memories/{id}` deadlocks the backend.** Every single-memory delete hangs for >3 minutes, eventually exhausting the connection pool and locking up the entire API. Root cause: `MemoryService.delete_memory` flushes the row deletion on the request's session (which holds row + CASCADE-child locks on `memory_embeddings`), then synchronously calls `self.pipeline.delete_memory(memory_id)`, which opens a *fresh* session via `session_factory()` and issues `DELETE FROM memory_embeddings WHERE memory_id=$1`. That new session blocks forever on the first session's uncommitted lock, and the first session is waiting for the pipeline call to return — classic deadlock. Confirmed via `pg_stat_activity`: one backend "idle in transaction" (parent), another "active / Lock / transactionid" on the embedding DELETE. Fix: commit the parent session before dispatching the pipeline cleanup (`backend/app/services/memory.py:87`). Verified: deleting 7 memories now takes ~20 ms each instead of timing out.
- [bug][fixed] **`GET /memories/{id}/duplicates` returns 500.** Server log: `asyncpg.exceptions.InvalidTextRepresentationError: invalid input syntax for type vector: "[np.float32(0.02142437), ...]"`. Root cause: pgvector round-trips stored embeddings as a numpy array (not a list). `PostgresVectorRepository._parse_vector` fell through to `list(raw)` which produced a list of `np.float32` wrappers; `str([np.float32(...)])` formats each element using its repr, not its value, so the string sent back to PostgreSQL was literally `"[np.float32(0.02), ...]"`. Fix: always coerce via `[float(x) for x in raw]` regardless of input type (`backend/app/repositories/vector.py:63-67`).
- [bug][fixed] **`POST /memories` accepts empty content.** Creating a memory with `{"content":""}` returned 201 and stored an empty row (visible as the "blank row" I spotted in the memories UI earlier). Fix: add `content: str = Field(min_length=1)` to `MemoryCreate` (`backend/app/schemas/memory.py:7-8`). Empty now correctly returns 422. This also explains the empty-content bug noted during UI snapshotting.
- [ship-blocker] The four fixes above (hybrid search, delete deadlock, duplicates 500, empty content) are all ship-blockers and should be cherry-picked to main before the next deploy.
- [check][pass] Re-ran `03_memories_crud.py` after all fixes: **14/14 PASS** covering create, update, search (semantic/tag/paginated), duplicates, merge, reason, and delete.
- [bug][fixed] **`/memories/reason` returned 0 sources despite finding relevant memories.** Same UUID-vs-string type mismatch as the hybrid-search bug, but in the service layer instead of the repository. `MemoryService.reason` built `fetched_by_id = {m.id: m ...}` (UUID-keyed) then iterated `memory_ids` straight from `semantic_results` where the hybrid path returns strings — `fetched_by_id.get(str_id)` always missed, so `sources`/`context_parts` stayed empty and the LLM answered without any context. Fix: normalize `memory_ids` to `UUID` objects up front, and re-key `score_by_id` using the normalized IDs (`backend/app/services/memory.py:195-205`). After fix the reason endpoint returns 5 cited sources for "What is MVCC?". This is effectively the same class of bug as the hybrid-search one — anywhere a semantic-search result feeds a UUID-keyed lookup, we must normalize.
