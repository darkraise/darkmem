- **Current:** `entity_relations` has only a PK on `id`, a UNIQUE B-tree on `(source_entity_id, target_entity_id, rel_type)`, and a GIN on `memory_ids` (migration `0001_initial_schema.py:232-243`). ## Retrieval: hybrid search, RRF, reranker, confidence

**Assessment:** This subsystem fuses a pgvector cosine ANN side (`1 - (embedding <=> vec)` against the per-fingerprint `memory_embeddings__<slug>` HNSW partition) with a Postgres FTS side (`ts_rank`/`plainto_tsquery`) via Reciprocal Rank Fusion at `k=60`, then optionally reranks with a per-document LLM call and rescales by a confidence factor. The id `str`/`UUID` normalization is handled correctly at every boundary (`get_many`, `reason`, and `_apply_confidence_weighting` all coerce), the both-sides-failed case raises loudly rather than masking an outage, `get_many` preserves rank order so the fused ranking survives the re-fetch, the semantic payload carries `content` so the reranker scores real text, and HNSW `ef_search` is raised to 100 with `iterative_scan = relaxed_order` at the connection level — so two claims in the original draft (RRF being "mathematically wrong" and `ef_search` left at the default) do not hold against the current code. The surviving risk concentrates in **accuracy** (`plainto_tsquery` silently AND-joins terms, starving keyword recall on multi-word queries) and **efficiency** (the reranker fires one LLM call per fused document at a concurrency cap of 3 over an inflated candidate set). Reliability is otherwise solid: one-sided failures degrade gracefully and scoring exceptions fall back to original order.

### Findings

#### F2. `plainto_tsquery` AND-joins all terms, collapsing keyword recall on multi-word queries  [axis: accuracy] [severity: medium] [effort: small]
- **Current:** Both the hybrid keyword side and the relational fallback build the FTS predicate with `plainto_tsquery('english', :q)` (hybrid_search.py:100,103; relational.py:103). `plainto_tsquery` lexes the input and joins all resulting lexemes with `&` (AND).
- **Problem:** For a query like `"qdrant pgvector migration decision"`, the keyword side returns only memories containing *all four* stems. Any memory mentioning "qdrant" and "migration" but not "pgvector" is dropped from the keyword list entirely, so for realistic natural-language queries (which agents emit) the keyword modality contributes almost nothing and the fusion degenerates toward semantic-only. The effect is silent: results still come back from the semantic side, so it manifests as "hybrid search behaves like vector search" rather than an error.
- **Improvement:** Use `websearch_to_tsquery('english', :q)` (Postgres 11+), which supports OR-ish behavior, quoted phrases, and `-` negation without hard-ANDing every token; or build an OR query with `to_tsquery` after sanitizing. `websearch_to_tsquery` is the closest drop-in to user intent.
- **Reason:** Recall on the keyword side is what justifies running hybrid search at all; AND-joining tokens makes the keyword RRF contribution vanish for exactly the multi-term queries hybrid is supposed to help.
- **Evidence:** hybrid_search.py:100,103; relational.py:103.
- **Verified:** confirmed (both call sites use `plainto_tsquery`; severity lowered to medium because the semantic side still serves results — degradation is quiet, not breaking).

#### F3. Reranker issues one LLM call per fused document at concurrency 3 — latency and cost scale with the inflated candidate set  [axis: efficiency] [severity: high] [effort: medium]
- **Current:** `RerankerService.rerank` builds one prompt per document and awaits `chat_completion("reranker", ...)` for each, bounded by `asyncio.Semaphore(3)` (reranker.py:41,58,72). It is invoked on the fused result list, which `_rrf_fuse` truncates to `limit` (hybrid_search.py:197), and that `limit` is the already-inflated `fetch_n = params.limit + offset + 50` (memory.py:186-188, pipeline.py:733-746). For a default page (`limit=20, offset=0`) that is up to ~70 documents.
- **Problem:** This is N LLM round-trips per search with N up to ~70, serialized 3 at a time, so ~23 sequential LLM latencies per query. At a typical 300-800 ms per small completion that is several seconds of added latency on a single search, plus N× token cost. The work is also redundant: the reranker re-scores documents the RRF already ranked, including the deep tail that `rerank` discards afterward when it slices to `top_k=limit` (reranker.py:81). The semaphore cap of 3 is the bottleneck, not a safety valve, since these are remote I/O-bound calls.
- **Improvement:** (a) Cap the rerank input at the candidates that can plausibly enter the page (e.g. `min(len(results), 2*params.limit)`) rather than the full over-fetched `fetch_n`. (b) Raise the concurrency cap or make it config-driven so the calls overlap. (c) Prefer a single batched scoring prompt (rank all candidates in one call returning a JSON array) where the model supports it, turning N round-trips into one.
- **Reason:** A per-doc-per-LLM-call reranker over a 70-item list at concurrency 3 dominates end-to-end latency; bounding the candidate set and batching cuts both round-trips and wall-clock by an order of magnitude.
- **Evidence:** reranker.py:41,72,81; hybrid_search.py:197; memory.py:186-188; pipeline.py:733-746.
- **Verified:** adjusted (candidate count is `fetch_n` ≈ `limit+offset+50` capped by `_rrf_fuse[:limit]`, up to ~70 for a default page — not a fixed 60; quadratic/serial latency claim holds).

#### F4. Reranker normalizes by batch max, discarding absolute relevance; reported score still diverges from imposed order  [axis: accuracy] [severity: low] [effort: small]
- **Current:** After scoring, `max_score = max(scores)`, `normalizer = max_score if max_score > 0 else 1.0`, and each doc's `rerank_score = scores[i] / normalizer` (reranker.py:74-78). The list is sorted by `rerank_score` and sliced. The reranked rows still carry `rrf_score`; `_apply_confidence_weighting` is then invoked with `preserve_order=True` and writes back to `score_key = "rrf_score"` (pipeline.py:748-749, 807-816).
- **Problem:** Two issues. First, max-normalization forces the top result to `rerank_score=1.0` regardless of whether the LLM rated it 2/10 or 10/10, so a uniformly-irrelevant result set looks identical to a perfect-match set — the absolute "no good match" signal is thrown away. Second, the order is taken from the reranker (preserved by `preserve_order=True`) while the score the system reports downstream is still `rrf_score`, so a consumer that re-sorts by the reported `score`/`rrf_score` would reorder away from the reranker's ranking. Note the confidence-corruption angle the original draft raised is moot in practice: `confidence_rank_gamma` defaults to 0, so `_apply_confidence_weighting` early-returns and does not touch the scores at all unless an operator enables it.
- **Improvement:** Divide scores by the fixed scale (`/ 10.0`) instead of the batch max so the signal stays absolute, and write the authoritative order's score into the canonical score field (copy `rerank_score` into `rrf_score`/`score`) when the reranker ran, so the reported score matches the imposed order.
- **Reason:** Calibrated absolute scores let callers threshold "no good match," and aligning the reported score with the authoritative order prevents silent re-sorting downstream.
- **Evidence:** reranker.py:74-81; pipeline.py:748-749, 807-816.
- **Verified:** adjusted (order is preserved via `preserve_order=True`, and the confidence-corruption sub-claim is gated out by the `gamma=0` default — severity lowered to low; the max-normalization and score/order-reporting mismatch are real).

#### F5. Over-fetch uses a fixed `+50` slack, so a selective in-memory filter can silently under-return a page  [axis: accuracy] [severity: medium] [effort: medium]
- **Current:** `search_memories` (and `_paginated`) fetch `fetch_n = params.limit + params.offset + 50` ids from `semantic_search`, load those rows with `get_many`, then apply `is_archived` plus the schema-v2 filters (`memory_type`, `source`, `project`, `status`, `technologies_any`, tags) in memory before slicing `[offset : offset+limit]` (memory.py:186-197, 209-223; `_matches_schema_v2_filters` at 151-177). `status` defaults to `["active"]`, so even a no-filter caller drops non-active rows post-fetch.
- **Problem:** The `+50` slack is constant and independent of filter selectivity. If a caller filters by a `project`, `status`, or `technologies_any` value matching only a small fraction of semantically-nearby rows, more than 50 of the top-`fetch_n` hits can be discarded, leaving fewer than `limit` survivors after the slice — the page silently under-returns even though matching rows exist deeper in the ANN list. This bites hardest for selective filters on large corpora (a rarely-used project ranked below thousands of other-project memories). The in-memory filtering also means equality/overlap predicates that Postgres could enforce are applied *after* the ANN/FTS LIMIT, wasting ANN slots on rows the filter will throw away.
- **Improvement:** Push the equality/overlap filters (`project`, `status`, `memory_type`, `source`, `technologies_any`) into the SQL of `_semantic_search` and `_keyword_search` as WHERE clauses joined to `memories`, so the LIMIT applies to already-filtered rows; keep only tag filtering in memory if a join is awkward. Failing that, scale the over-fetch by observed selectivity or loop-fetch until `limit` survivors are found.
- **Reason:** Filtering before the LIMIT guarantees a full page whenever enough matches exist and stops the ANN budget from being spent on rows the filter will discard.
- **Evidence:** memory.py:186-197, 151-177; hybrid_search.py:30, 96-117.
- **Verified:** confirmed (`+50` constant slack, in-memory filtering after the LIMIT, and the default `status=["active"]` filter make the under-return path live).

#### F7. Confidence weighting runs a second DB round-trip over the same id set when `gamma>0`  [axis: efficiency] [severity: low] [effort: small]
- **Current:** `_apply_confidence_weighting` early-returns when `gamma == 0.0` (the default), so in the common case it is a no-op (pipeline.py:782). ## Embedders, Fingerprint Partitioning & Vector Ops

**Assessment:** This component cleanly solves pgvector's fixed-dim `vector(N)` constraint by giving every embedder fingerprint its own `<parent>__<slug>` child table, with a registry that creates tables and HNSW indexes idempotently behind a process-wide lock. The remaining risk is almost entirely **efficiency**, concentrated in `find_similar_memories` (run on every ingest) and the reembed anti-join loops. I verified every claim against the actual SQL and call sites; several severities and one whole finding were adjusted on re-read.

### Findings

#### F1. Replace the self-join in `find_similar_memories` with a literal-vector ANN search  [axis: efficiency] [severity: high] [effort: small]
- **Current:** Crossref computation runs on *every* successful ingest (`pipeline.py:398-405`, gated on `status["vector"] == "ok"`). It calls `find_similar_memories`, whose SQL is `FROM {table} me1, {table} me2 ... ORDER BY me1.embedding <=> me2.embedding` (`vector.py:308-319`). The `ORDER BY` operand has `me2.embedding` as a *column*, not a query-time constant.
- **Problem:** pgvector's HNSW index can only accelerate `ORDER BY column <=> :literal`. Because `me2.embedding` is a column at plan time, the planner cannot use the HNSW index for the ordering — it computes cosine distance for every row in the partition against the one pinned `me1` row, an O(n) scan per ingest. At 50k memories that is 50k distance calcs per write; ingest throughput degrades linearly with corpus size for a step meant to be a bounded top-5 lookup. The sibling method `find_similar` (`vector.py:286-303`) already does it correctly: read `me1`'s vector into Python, then `search()` passes it as `:vec` literal for an index-backed `ORDER BY embedding <=> CAST(:vec AS vector)`.
- **Improvement:** Rewrite `find_similar_memories` to mirror `find_similar`: one query to fetch the source vector by `memory_id`, then delegate to `search(vector, fingerprint, limit=top_k+1)`, drop self, filter by `min_score` in Python.
- **Reason:** `search()`'s ordering is exactly the form HNSW (with `ef_search=100`, set per-connection in `database.py:14`) accelerates, turning per-ingest crossref cost from O(corpus) to an ANN probe. Same results, correct complexity.
- **Evidence:** `vector.py:305-322` (self-join); `vector.py:286-303` + `vector.py:51-67` (the index-using pattern); `pipeline.py:398-405` (per-ingest caller).
- **Verified:** confirmed — self-join orders on a column operand, so HNSW cannot accelerate it; `search()` next door uses the literal `:vec` form and is the correct model.

#### F2. `min_score` filter in `find_similar_memories` recomputes the distance three times and uses `>` vs the `>=` elsewhere  [axis: efficiency] [severity: low] [effort: small]
- **Current:** The crossref query computes `1 - (me1.embedding <=> me2.embedding)` in the SELECT, the WHERE (`> :min_score`, `min_score=0.4`), and the ORDER BY — three times per row (`vector.py:312,316,317`). Entity dedup uses `> :threshold` at 0.85 (`graph.py:25`); `find_similar` uses `>= threshold` at 0.9 (`vector.py:303`).
- **Problem:** The real waste is recomputing the distance three times per row, which compounds under F1's full scan. The boundary-operator inconsistency (`>` vs `>=`) is cosmetic: with continuous float cosine scores, an exact-threshold tie is essentially never hit, so it is not a meaningful correctness risk — just a consistency smell.
- **Improvement:** When applying F1, move the threshold filter into Python on the `search()` results (as `find_similar` does) and standardize on `>=` for inclusive semantics. This collapses naturally once F1 lands.
- **Reason:** One distance computation per row instead of three, consistent semantics; fully subsumed by F1.
- **Evidence:** `vector.py:312,316,317` vs `vector.py:303` vs `graph.py:25`.
- **Verified:** adjusted — the triple-recompute is real, but the `>`/`>=` "crossref-miss vs dedup-match" framing was overstated (float ties are practically impossible); reframed as an efficiency cleanup subsumed by F1.

#### F3. Reembed loops re-run the full `NOT EXISTS` anti-join on every 100-row batch  [axis: efficiency] [severity: low] [effort: medium]
- **Current:** `reembed_memories` and `reembed_entities` loop `while True`, each iteration issuing `SELECT ... FROM memories m WHERE NOT EXISTS (SELECT 1 FROM {mem_table} me WHERE me.memory_id = m.id) LIMIT 100` (`reembed.py:320-331`, `443-454`). After inserting the batch's vectors, the next iteration re-runs the same anti-join.
- **Problem:** Each successful batch inserts 100 rows into `{mem_table}`, so the anti-join's right side grows while the left side stays fixed — work per iteration stays ~O(memories). Backfilling N missing rows costs N/100 iterations × O(memories) anti-join. However, the anti-join is supported by the partition's primary key (`memory_id, fingerprint`) and the `ix_..._memory_id` aux index (`embedder_registry.py:84`), so each `NOT EXISTS` probe is an index lookup, not a sequential scan of the partition — the per-iteration cost is closer to O(memories × log) index probes than a full O(memories) table scan. The total is still superlinear in the number of batches and worth fixing, but the magnitude is smaller than the draft's "2,000 scans of 200k rows" framing implies. - **Improvement:** Keyset-paginate by a stable cursor (`ORDER BY m.id` + `WHERE m.id > :last`) so each scan is bounded, or snapshot the missing ids once into a Python list / temp table at run start (safe given single-writer locking via `reembed_locks`).
- **Reason:** Turns total selection cost from O(N·batches) to O(corpus) for one bounded pass plus O(N) inserts.
- **Evidence:** `reembed.py:320-331` (loop), `reembed.py:357-367` (insert grows the right side), `reembed.py:443-454` (entities mirror); `embedder_registry.py:84` (memory_id index that backs the anti-join).
- **Verified:** adjusted — superlinear-in-batches re-selection is real, but the anti-join is index-backed (PK + aux index) and runs only on an operator-triggered, lock-serialized path, so dropped from medium to low.

- **Current:** `find_similar` reads the source vector, calls `search(vector, limit=limit+1)`, then filters `r["score"] >= threshold` in Python (`vector.py:302-303`). `search` has no threshold predicate (`vector.py:51-67`).

#### F6. Slug-collision scan refetches all *other* fingerprints on every registration; the lock is per-process only  [axis: efficiency] [severity: low] [effort: small]
- **Current:** Inside `register` (under the lock), after `INSERT ... ON CONFLICT DO NOTHING`, the code runs `SELECT fingerprint FROM embedders WHERE fingerprint != :fp` and recomputes `_partition_slug(other)` for each to detect a folded-separator collision (`embedder_registry.py:155-168`).

#### F4. Python bare-import proximity resolver can bind to the wrong same-named module  [axis: accuracy] [severity: low] [effort: medium]

## Call Resolution & Heritage/MRO

**Assessment:** `CallResolver` implements a clean confidence-tiered cascade (type-env member dispatch → receiver-owner → same-file → named-import → import-scoped → wildcard → global), backed by three in-memory indexes in `SymbolTable` and a per-instance result cache. The MRO layer (`HeritageResolver`) correctly dispatches C3, leftmost-base, implements-split, qualified-syntax, and single-inheritance per language, with proper cycle/diamond guards, and the override/implements/inherited edge creation is done in set-based SQL. Verification confirmed the two highest-impact accuracy claims: `find_inherited_method` is genuinely dead (referenced nowhere outside its own definition, not even in tests), so inherited-but-not-overridden calls produce no `calls` edge; and method symbol keys are `name::file_path` with no class qualifier (graph_keys.py:13-16, code_pipeline.py:1455/1501), so same-named methods of different classes in one file collide. The efficiency findings are real but mostly latent or modest; F7 in particular is dormant because the method it indicts is dead code, so I downgraded it.

### Findings

#### F1. Wire inherited-method resolution into call tracing (the inherited-call edge gap)  [axis: accuracy] [severity: high] [effort: medium]
- **Current:** `HeritageResolver.find_inherited_method` (heritage_resolver.py:198-247) walks the EXTENDS chain to find a concrete ancestor method at confidence 0.7, but a repo-wide grep confirms it is called nowhere outside its own definition — not in `code_pipeline.py` phase 06/07/08, not in any non-test code, and not in any test. Call tracing (`phase_06_call_tracing`, code_pipeline.py:700-727) resolves each call only through `CallResolver.resolve`, whose member-dispatch path (call_resolver.py:62-84) does `lookup_by_owner(receiver_type, called_name)`, which returns only methods directly declared on that class (symbol_table.py:47-63). The separate `_find_inherited_methods` pass (heritage_resolver.py:249-357) builds class-to-class `method_inherited` edges, but never connects a *call site* to the inherited method.
- **Problem:** For the common case where `child.foo()` is called but `foo` is defined only on a base class, no `calls` edge is emitted. `lookup_by_owner("Child","foo")` returns `[]`, the receiver-name tier yields nothing, and the call either falls through to a noisy global match or is dropped. In a typical OO codebase where subclasses inherit most behavior, this silently loses a large fraction of the true call graph — exactly the edges a memory system for code reasoning most needs. The capability exists (`find_inherited_method`) but is orphaned.
- **Improvement:** In the member-dispatch path of `CallResolver.resolve`, when `lookup_by_owner(receiver_type, called_name)` returns empty, fall back to walking the inheritance chain (preferably via the in-memory `parent_map`/`method_map` that `_find_inherited_methods` already builds in phase 07, rather than the per-node DB walk of `find_inherited_method`) and emit the edge at the lenient 0.7 confidence. Order phase 07 (heritage) before the inherited fallback so the maps are available, or pass `parent_map` into `CallResolver`.
- **Reason:** Resolving inherited calls is the single largest accuracy lever for an OO call graph, and the resolver already encodes the right confidence tier; the only thing missing is the wiring.
- **Evidence:** heritage_resolver.py:198-247 (dead method, no callers anywhere), call_resolver.py:62-84 (member dispatch with no inherited fallback), symbol_table.py:47-63 (`lookup_by_owner` is direct-declaration only), code_pipeline.py:700-727 (call tracing uses only `resolve`).
- **Verified:** confirmed (`find_inherited_method` has zero references outside its definition, including tests; member-dispatch path emits no inherited edge).

#### F2. Qualify method symbol keys by owner class to stop same-name collisions  [axis: accuracy] [severity: high] [effort: large]
- **Current:** Every symbol node, including methods, is keyed `compose_key("symbol", name, file_path)` = `name::file_path` (graph_keys.py:13-16, code_pipeline.py:1455, 1501). Heritage SQL recovers the method name with `split_part(target_key, '::', 1)` (heritage_resolver.py:221, 275, 371, 416), which returns just the bare method name. The has_method edge target is `methodName::file_path` with no class component (code_pipeline.py:1501).
- **Problem:** Two classes defined in the same file that each declare a method named `save` (extremely common: `class UserRepo: def save` and `class OrderRepo: def save` in one module) both produce the identical symbol key `save::models.py`. They collide onto one `code_graph_nodes` row (the `ON CONFLICT (repo_id, kind, key) DO UPDATE SET properties = EXCLUDED.properties` at code_pipeline.py:1467 overwrites), and both `has_method` edges point at the same node. Consequences cascade: `_find_overrides`/`_find_implements`/`_find_inherited_methods` match purely on `split_part(...,1)` method name within a class pair, so `UserRepo.save` can be treated as overriding `OrderRepo.save`; call edges from either site land on a single merged target. The graph silently conflates unrelated methods.
- **Improvement:** Include the owning class in the method key, e.g. `Owner::name::file_path` for methods, and have heritage SQL extract the method name from the correct segment (or store `method_name` as an explicit edge/node property instead of re-deriving via `split_part`). At minimum, derive `method_name` from a dedicated property column so name extraction does not depend on key structure.
- **Reason:** A method's identity is (class, name, file), not (name, file); without the class component the uniqueness constraint and every name-based heritage join are unsound for any file holding two same-named methods.
- **Evidence:** code_pipeline.py:1455/1501 (method key construction with no class segment), graph_keys.py:13-16 (`name::file_path` only), heritage_resolver.py:221/275/371/416 (`split_part(...,'::',1)`), code_pipeline.py:1467 (`DO UPDATE` overwrites colliding node).
- **Verified:** confirmed (compose_key produces `name::file_path` for symbols; no class qualifier; node `ON CONFLICT` overwrites).

#### F3. Derive param_count from a real parameter list, not signature string-stripping  [axis: accuracy] [severity: medium] [effort: medium]
- **Current:** `param_count` is computed as `sym.signature.strip("()").split(",")` then counting non-empty parts (code_pipeline.py:638-640, 873-875). `_filter` then uses `param_count` for arity matching: exact match preferred, else lenient within ±1 (call_resolver.py:156-167). The call-site `arg_count` is computed by `_count_args` (code_parser.py:833-837), which counts only the *named children of the argument list* — so for a method call `obj.foo(x)` it yields 1, excluding the receiver.
- **Problem:** `strip("()")` strips leading/trailing parenthesis *characters*, not the outer call parens — so a signature like `(a: Tuple[int,int], b)` keeps inner commas and the naive `split(",")` counts `Tuple[int`, `int]`, `b` = 3 params instead of 2. It also miscounts default values containing commas, `*args`/`**kwargs`, and type unions with commas, and it counts the receiver (`self`/`this`) while `_count_args` does not — so a 1-arg method call against a 2-token signature (`self, x`) never matches exactly and relies on the ±1 lenient band. When two same-named candidates exist, `_filter` then picks the wrong one or leaves both, and the resolver only commits when exactly one candidate remains — so the call is dropped. This degrades precisely the ambiguous-overload cases arity filtering exists to disambiguate.
- **Improvement:** Parse the parameter list structurally (count top-level commas only, ignoring those inside brackets/parens/braces) and normalize the receiver: strip `self`/`this` from method `param_count` or add it to method-call `arg_count`, so the two sides use one convention.
- **Reason:** Arity is only a useful disambiguation signal if both sides are counted with the same convention; bracket-naive splitting and an uncounted receiver make it actively misleading.
- **Evidence:** code_pipeline.py:638-640 and 873-875 (`strip("()").split(",")`), code_parser.py:833-837 (`_count_args` excludes receiver), call_resolver.py:156-167 (`param_count` arity filter).
- **Verified:** confirmed (string-strip splitting is bracket-naive; `_count_args` excludes the receiver while signature `param_count` includes it — a real convention mismatch).

#### F4. Add call_form and arg_count to the resolve cache key  [axis: accuracy] [severity: low] [effort: small]
- **Current:** The cache key is `(from_file, call.called_name, receiver_name)` (call_resolver.py:58), but the resolution result depends on `call.call_form` (constructor vs member vs free changes `_filter`'s kind filter, call_resolver.py:149-154, and gates the member-dispatch tiers) and on `call.arg_count` (arity narrowing, call_resolver.py:156-167). The cache is per-`CallResolver` instance and the resolver is built once per phase (call_resolver.py:52, code_pipeline.py:688), so the key spans all files in a phase.
- **Problem:** Two calls with the same name and receiver but different `call_form` or `arg_count` return the first-computed result for both. The realistic collision is a constructor `Foo()` (`call_form="constructor"`, `receiver_name=None`) versus `Foo` invoked as a free call (`receiver_name=None`) keyed identically as `(file, "Foo", None)`, or `do_thing(x)` vs `do_thing(x, y, z)` with distinct overloads. The narrowing factor is that `receiver_name` already differentiates most member calls, and an `arg_count` collision only changes the outcome when genuine same-name overloads exist in scope — so impact is bounded, but it is a real correctness bug masquerading as a cache optimization.
- **Improvement:** Extend the cache key tuple to `(from_file, called_name, receiver_name, call_form, arg_count)`.
- **Reason:** A memoization key must include every input the memoized function branches on; `call_form` and `arg_count` both change the output, so omitting them can return stale results.
- **Evidence:** call_resolver.py:58 (cache key), call_resolver.py:149-167 (output depends on `call_form` and `arg_count`), call_resolver.py:52 + code_pipeline.py:688 (cache spans a whole phase).
- **Verified:** adjusted (real omission, but `receiver_name` already disambiguates most cases and the constructor-vs-free collision is narrow; severity medium→low).

#### F5. Reuse the symbol table across phases 06/07/08 instead of rebuilding it three times  [axis: efficiency] [severity: medium] [effort: medium]
- **Current:** Phase 06 (code_pipeline.py:623-654) issues `SELECT CodeSymbol JOIN CodeFile WHERE repo_id=...`, loads all symbols, builds a fresh `SymbolTable`, `symbol_by_id`, `id_to_name`, `enclosing_index`, and rebuilds tree-sitter type environments by re-parsing every file (lines 665-684). Phase 07 re-parses files a second time to rebuild type envs for `AccessResolver` (code_pipeline.py:782-800).
- **Problem:** For a repo with N symbols across F files, this is 2–3× the symbol load (one full table scan per phase that runs) and 2× full tree-sitter re-parsing of every source file (phase 06 and phase 07) purely to reconstruct `type_envs` that phase 06 already computed. On a large repo, tree-sitter re-parsing dominates wall time and is redundant. The `_parsed` cache holds file content but the parse trees and `SymbolTable` are discarded between phases.

- **Reason:** The symbol set and parse trees are invariant across these phases within one pipeline run; recomputing them is waste proportional to repo size.
- **Evidence:** code_pipeline.py:623-684 (phase 06 build + re-parse), 854-908 (phase 08 rebuild, identical SELECT, seeded type envs), 782-800 (phase 07 re-parse for type envs).
- **Verified:** adjusted (identical SELECT and double tree-sitter re-parse confirmed; phase 08 type_envs are seeded not re-parsed, so the "phase 07 re-parse" is the second parse, not phase 08).

#### F6. Replace the O(symbols) linear scan per call in resolve_chain with an id index  [axis: efficiency] [severity: low] [effort: small]
- **Current:** `resolve_chain` (call_resolver.py:171-199) walks return types. After a `resolve`, it recovers the resolved entry by scanning `self.symbols.lookup_global(call.called_name)` and linearly searching for `e.node_id == result[0]` (call_resolver.py:190-193). The chained fallback also does `[e for e in self.symbols.lookup_global(...) if e.kind in (...)]` (call_resolver.py:180). `SymbolTable` (symbol_table.py:24-36) has no by-id index.
- **Problem:** `lookup_global` returns the list of all symbols sharing that name, then a linear `next(...)` scans it. For a hot name shared across many files (`get`, `run`, `handle`), this list can hold hundreds of entries, scanned per call in the chain. Recovering an entry from its `node_id` is O(candidates) instead of O(1). The real-world scale is bounded, however: `resolve_chain` is the chain-walking entry point and the per-call name bucket is rarely pathological, so this is a minor hot-path inefficiency rather than a true quadratic blowup.
- **Improvement:** Add a `_by_id: dict[str, SymbolEntry]` to `SymbolTable` populated in `add`, expose `lookup_by_id(node_id)`, and have `resolve_chain` look up the resolved entry directly.
- **Reason:** Recovering a known node by id is a dictionary lookup; doing it by re-scanning a name bucket is needless linear work on a per-call path.
- **Evidence:** call_resolver.py:190-193 (linear `next` over `lookup_global`), symbol_table.py:24-36 (no id index exists).

**Assessment:** This component spans `CodeQueryService` (RRF fusion of pgvector semantic results with an `ILIKE` symbol/source-code pass, plus a recursive-CTE blast radius) and roughly a dozen MCP code tools that read the `code_edges` / `code_graph_nodes` graph. The graph keyspace is consistent and well-indexed: every symbol key is the composite `name::file_path`, `code_edges` carries four targeted indexes including a covering `(repo_id, edge_type, source_key, target_key)` (migration `0001`, lines 267-270), and the child embedding tables get an HNSW cosine index with `ef_search=100` set per connection (`database.py:14`) — so the core ANN and graph lookups are index-supported, not sequential scans. The reliability story is also solid: every MCP tool runs inside a commit/rollback context and limits are clamped. Risk concentrates in two places. First, **ranking soundness in `search_code`**: the `ILIKE` pass has no `ORDER BY`, so its RRF ranks come from arbitrary heap order, and the two passes use mismatched fusion keys, both of which distort the fused score. Second, **efficiency of the graph tools under fan-out**: `code_context` fires seven sequential round-trips per call, `code_processes` is an N+1 over processes, and the blast-radius CTE uses `UNION` with no visited-set guard so cyclic call graphs re-expand nodes up to the depth cap.

### Findings

#### F1. Order the `ILIKE` pass before assigning RRF ranks  [axis: accuracy] [severity: high] [effort: small]
- **Current:** In `search_code`, the text pass selects matching symbols with `CodeSymbol.name ILIKE ... OR CodeSymbol.source_code ILIKE ...` and `.limit(limit*2)`, then does `for rank, (sym, ...) in enumerate(text_results, start=1)` and adds `1.0 / (RRF_K + rank)`. The query has no `ORDER BY` (`code_query.py:57-69`).
- **Problem:** RRF presumes each input list is *ranked by relevance*: rank 1 is the best match. Here the rank is just the order Postgres happened to return rows (heap/index scan order), so an exact name match (`name = "search_code"`) and an incidental substring hit deep in some unrelated function body get whatever rank their physical row position dictates. The `1/(60+rank)` weights then bias the fused result by storage order, not relevance. When the LLM is unavailable, this text pass is the *only* signal feeding `rrf_score`, so result order is fully arbitrary. The `limit*2` truncation is also order-dependent, so which rows survive on a high-cardinality token is non-deterministic.
- **Improvement:** Add a deterministic relevance ordering before `LIMIT`, e.g. an exact/prefix-match tier then name length: `ORDER BY (CodeSymbol.name == query) DESC, (CodeSymbol.name.ilike(query+'%')) DESC, length(CodeSymbol.name)`. Even a plain `ORDER BY CodeSymbol.name` makes ranks reproducible; a match-quality tier makes them meaningful.
- **Reason:** RRF only produces sound fused scores when each list's position encodes relevance. Giving the keyword side an explicit relevance order restores that invariant and makes both ranking and truncation deterministic.
- **Evidence:** `backend/app/services/code_query.py:55-83`.
- **Verified:** confirmed (lines 57-69 issue the ILIKE select with no `ORDER BY`; `enumerate` at 70 assigns rank from row order, and the route at `code.py:46` surfaces `rrf_score` directly).

#### F2. Reconcile the mismatched fusion keys of the two RRF passes  [axis: accuracy] [severity: medium] [effort: small]
- **Current:** The semantic pass keys each chunk as `file_path:chunk['line_start']` (`code_query.py:39`) while the text pass keys each symbol as `file_path:sym.line_start` (`code_query.py:71`). Chunk `line_start` is the start of an embedding window; symbol `line_start` is the `def`/`class` line. They frequently differ, so the same logical location produces two distinct keys that never fuse.
- **Problem:** RRF is supposed to reward items appearing in both lists by summing their reciprocal-rank contributions. Because the two pipelines compute line numbers differently, an item strongly ranked by both modalities is split into two half-weighted entries instead of one double-weighted one. The intended "agreement boost" almost never fires, so fusion degenerates into a simple interleave, and a symbol that should clearly win (high on both sides) can be outranked by two mediocre single-side hits.
- **Improvement:** Normalize the fusion key to something both passes can agree on — most directly, key by `(file_path, symbol_name)` when `symbol_name` is present, falling back to `file_path:line_start`. Alternatively resolve the chunk's covering symbol so both sides emit the same key.
- **Reason:** A shared, semantically meaningful key is what lets RRF actually reward cross-modal agreement; line-number keys defeat that because the two pipelines compute line numbers differently.
- **Evidence:** `backend/app/services/code_query.py:38-51` vs `70-83`.
- **Verified:** confirmed (semantic key built from chunk `line_start` at line 39, text key from symbol `line_start` at line 71; no shared key derivation between them).

#### F3. Reduce the seven sequential round-trips in `code_context`  [axis: efficiency] [severity: medium] [effort: medium]
- **Current:** `code_context` resolves the symbol, fetches `CodeFile`, then issues seven further `await session.execute(...)` calls in strict sequence: callers, callees, extends, extended_by, implements, community (a join), and processes (a join) — roughly nine sequential round-trips per invocation (`server.py:584-707`).
- **Problem:** Each round-trip pays full await latency, and they cannot overlap because they are awaited one at a time on one session. Every individual query is index-cheap (the `code_edges` covering index supports `(repo_id, source_key)` / `(repo_id, target_key)`), so this is pure serialized latency, not algorithmic cost. On a low-latency local DB the overhead is small; over a remote link (10-20 ms RTT) it becomes ~150-300 ms per call, and agents call `code_context` interactively. The five plain edge queries share the identical `(repo_id, symbol_key)` predicate against the same table, so they are trivially combinable.
- **Improvement:** Collapse the five plain edge queries into one `SELECT edge_type, source_key, target_key FROM code_edges WHERE repo_id = :r AND (source_key = :k OR target_key = :k) AND edge_type IN (...)` and bucket in Python; keep the two node-join queries (community, processes) but issue them with `asyncio.gather` so they run concurrently. That cuts ~7 serial trips to 2-3.
- **Reason:** The predicate is identical across the plain queries and the covering index already supports it, so one scan returns everything; concurrency removes serialized latency without changing results.
- **Evidence:** `backend/app/api/mcp/server.py:584-707`.
- **Verified:** adjusted (seven serial graph round-trips confirmed; severity high→medium because every query is index-cheap and the cost is latency-only, not algorithmic — material only on a remote DB link).

#### F4. Guard the blast-radius CTE against cyclic re-expansion  [axis: efficiency] [severity: medium] [effort: medium]
- **Current:** The blast-radius recursive CTE joins `e.target_key = c.name`, accumulates `c.distance + 1`, terminates only on `WHERE c.distance < :max_depth` (clamped to 50), and uses `UNION` (`code_query.py:277-300`, mirrored in `server.py:466-489`).
- **Problem:** `UNION` dedups whole rows including `distance`, so a cycle `A→B→A` yields distinct rows `(A,1),(B,2),(A,3),(B,4),...` and keeps re-expanding until `distance` hits the cap — it terminates, but does work proportional to paths, not nodes. Real call graphs have cycles (mutual recursion, callbacks), so on a cyclic component a hub function can fan out toward the depth cap before the trailing `GROUP BY ... MIN(distance)` collapses it. The dedup happens *after* expansion, not during, so the CPU and memory cost lives inside Postgres.
- **Improvement:** Carry a `path text[]` of seen keys and add `AND NOT e.source_key = ANY(c.path)` to the recursion join, appending each hop. This prunes cycles at the node level instead of relying on the depth cap, letting you keep a generous `max_depth` safely.
- **Reason:** A visited-set guard makes the traversal genuinely O(reachable nodes) instead of O(paths up to depth cap); the trailing `MIN(distance)` still yields shortest distances because the first time a node is reached is along its shortest path in this BFS-like expansion.
- **Evidence:** `backend/app/services/code_query.py:277-300`; `backend/app/api/mcp/server.py:466-489`.
- **Verified:** confirmed (recursive member projects `source_key, source_kind, distance+1` under `UNION` with only `c.distance < :max_depth` as the guard; same node at higher distances is a distinct row and re-expands).

#### F5. Batch the per-process step lookup in `code_processes`  [axis: efficiency] [severity: medium] [effort: small]
- **Current:** `code_processes` fetches all `process` nodes, then loops over them and for each issues a separate `SELECT source_key FROM code_edges WHERE ... target_key = :proc_key AND edge_type='step_in_process'` (`server.py:822-834`).
- **Problem:** This is a textbook N+1: one query for the process list plus one query per process, all serialized on one session. A repository with many traced processes issues one round-trip per process for a single `code_processes` call. Each is index-cheap, but the serialized latency makes the tool's response time grow linearly with process count for no algorithmic reason.
- **Improvement:** Issue one query joining processes to their `step_in_process` edges (`SELECT n.key, n.label, n.properties, e.source_key FROM code_graph_nodes n JOIN code_edges e ON e.repo_id=n.repo_id AND e.target_key=n.key AND e.edge_type='step_in_process' WHERE n.repo_id=:r AND n.kind='process' ORDER BY n.label`), then group steps per process in Python.
- **Reason:** One indexed join returns the full process-to-steps relation in a single round-trip, eliminating the per-row latency while producing identical output.
- **Evidence:** `backend/app/api/mcp/server.py:804-843`.
- **Verified:** confirmed (process list query at 812-820, then a per-process step query inside the loop at 825-834 — classic N+1; the "300 cap" figure is incidental, not load-bearing).

#### F6. Make `code_blast_radius` and `code_context` deterministic when a symbol name is ambiguous  [axis: accuracy] [severity: medium] [effort: small]
- **Current:** `code_blast_radius` and `code_context` resolve a bare `symbol_name` to a single row with `.first()` / `.limit(1)` over `WHERE CodeSymbol.name == symbol_name` and no ordering (`server.py:455-456`, `585-588`), so when several symbols share a name an arbitrary one is chosen and its `name::file_path` key seeds the graph walk.
- **Problem:** The blast radius and context are then computed for whichever same-named symbol Postgres returned first, which is not stable across runs or data changes. - **Reason:** Impact analysis is only trustworthy if it covers every symbol the rename touches; an unordered `.first()` both hides ambiguity and makes the answer non-deterministic.
- **Evidence:** `backend/app/api/mcp/server.py:455-456`, `585-588`; contrast `863-868`.
- **Verified:** confirmed (`code_blast_radius` takes `.first()` of an unordered `name == symbol_name` query; `code_context` takes `.limit(1)`; `code_rename` enumerates all definitions, confirming the inconsistency).

#### F7. `code_blast_radius` traverses heritage/access edges but labels and risk-scores them as call impact  [axis: accuracy] [severity: low] [effort: small]
- **Current:** The CTE walks `edge_type IN ('calls','extends','implements','accesses','method_overrides')` and merges all of them into one `affected` list, with `risk` derived purely from `len(by_depth["1"])` — the count of *direct* predecessors of any of those edge types (`code_query.py:284-328`; `server.py:473-516`).
- **Problem:** "Blast radius" is described to the agent as "all symbols that transitively call it" (`server.py:436`). Mixing subclasses (`extends`), interface implementors (`implements`), property accessors (`accesses`), and overrides into one undifferentiated set inflates the radius and the CRITICAL/HIGH/MEDIUM risk tier: a class with 11 subclasses and zero callers is scored CRITICAL "direct callers," misrepresenting what changing it breaks. The edge types are sound to traverse, but flattening them loses the distinction a refactorer needs (a method-signature change versus a base-class change have different mitigations).
- **Improvement:** Carry `edge_type` through the CTE and into each `affected` entry, and either compute risk from `calls` predecessors specifically or report per-relation counts. Keep the union traversal but stop labeling non-call relations as "callers."
- **Reason:** Preserving the relation kind lets the caller distinguish call impact from heritage impact and makes the risk tier reflect the documented "callers" semantics rather than a conflated count.
- **Evidence:** `backend/app/services/code_query.py:284-328`; tool description at `server.py:435-436`.
- **Verified:** confirmed (CTE merges five edge types into one list; `risk` computed from `len(by_depth["1"])` with no edge-type discrimination; tool description claims callers-only semantics).
