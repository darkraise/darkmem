## Classification / enrichment subsystem

**Assessment:** The subsystem cleanly separates two concerns: a synchronous, always-on regex `memory_classifier` populating `classified_type`, and a flag-gated LLM/ML path populating the `llm_*` columns. The `classify(content, areas, prompt, mode) -> {hall, summary, emotions, flags}` surface is genuinely well-designed — `MLClassificationService` and `ClassificationService` are interchangeable, and both degrade to `"fact"` conservatively on any failure, so classification can never crash the write phase. The main risk concentrates in the ML runtime lifecycle: the model manager is a process singleton whose `shutdown_all` is never wired into the app lifespan and whose `app.state.ml_model_manager` docstring claim is false, and its idle-eviction watchdog races the inference path without lock protection. A second, subtler risk the reviewer missed is that switching the classifier to an ML profile silently blanks three of the four `llm_*` enrichment columns, because the ML service returns no summary, emotions, or flags and Phase 5 overwrites those columns unconditionally. The per-batch ML/LLM dispatch also resolves its config via an uncached DB round-trip per batch, diverging from the cached feature-flags path.

#### F1. Wire `shutdown_all` into app lifespan and fix the false `app.state` claim  [axis: reliability] [severity: high] [effort: small]
- **Current:** `ml_runtime.py` exports a module-level singleton `ml_model_manager = MLModelManager()` (line 196) whose docstring at lines 194-195 states `app.state.ml_model_manager` references the same instance. The lifespan shutdown branch (`main.py:248-262`) stops jobs, cancels the `TaskRegistry`, and closes the LLM orchestrator, but never invokes `shutdown_all` and never sets `app.state.ml_model_manager`. The pipeline imports the singleton directly (`pipeline.py:527`).
- **Problem:** On backend shutdown, `shutdown_all` (ml_runtime.py:100) is never invoked, so loaded torch models and their per-model `eviction_task` are never torn down. Under reload-heavy dev loops or graceful restarts this leaks memory and dangling tasks. The `app.state.ml_model_manager` claim is dead documentation that will mislead a maintainer into reading state that was never set (yielding `AttributeError`/`None`).
- **Improvement:** In the lifespan shutdown branch of `main.py`, call `await ml_model_manager.shutdown_all()`. Either set `app.state.ml_model_manager = ml_model_manager` at startup to make the docstring true, or delete the docstring sentence.
- **Reason:** Cancelling eviction watchdogs and clearing the model dict on shutdown is the only place the per-model `asyncio.Task` objects are released. Matching docs to reality prevents a latent bug where someone reads an unset attribute.
- **Evidence:** ml_runtime.py:100-112, 194-196; main.py:248-262 (no ML shutdown hook; `app.state.ml_model_manager` never assigned).
- **Verified:** confirmed (shutdown branch at main.py:248-262 has no `shutdown_all` call; grep finds zero `app.state.ml_model_manager` assignments).

#### F2. Lock-protect the idle-eviction watchdog against concurrent inference  [axis: reliability] [severity: low] [effort: medium]
- **Current:** `_evict_on_idle` (ml_runtime.py:175-191) reads `self._models.get(model_repo)` and `entry.last_used`, then `self._models.pop(model_repo, None)` — all without holding the per-repo `load_lock`. Meanwhile `get` bumps `entry.last_used = time.monotonic()` (line 84) under `load_lock`.
- **Problem:** The check-then-pop is not atomic against `get`. A request can pass `get` (bumping `last_used`) microseconds after the watchdog read a stale `last_used`, then the watchdog pops the entry. The in-flight inference still works (the local `entry` reference keeps the model alive), but the very next request reloads the model from HuggingFace from scratch — a multi-second stall the TTL design exists to avoid. With `ttl_seconds == 0` (the seeded default, ml_seed.py:26) no watchdog runs (line 80 gates task creation on `ttl_seconds > 0`), so this is latent today; only an operator setting a positive TTL exposes it.
- **Improvement:** Acquire the same `load_lock` for `model_repo` inside the watchdog before the idle re-check and `pop`, and re-read `last_used` under the lock so a concurrent bump aborts the eviction.
- **Reason:** Eviction and last-use bookkeeping mutate the same shared state; serializing them under the existing per-repo lock removes the TOCTOU window without adding a new lock or blocking inference.
- **Evidence:** ml_runtime.py:72-85 (bump under lock), 175-191 (check-and-pop with no lock).
- **Verified:** adjusted (TOCTOU is real, but severity lowered to low — latent under the default ttl=0 and only mildly degrades performance, never corrupts results).

## Embedders, fingerprint partitioning, reembed

**Assessment:** This subsystem implements per-fingerprint child tables to satisfy pgvector's fixed-dimension constraint, with a process-wide registry (`EmbedderRegistry`) that lazily creates four child tables plus HNSW/aux indexes on first sight of a fingerprint, and a `ReembedService` that backfills rows missing from the active partition. The core design is sound and well-documented: `child_table()` indirection is consistently used everywhere (vector repo, hybrid search, reembed), the `_assert_fingerprint` guard prevents persisting mixed-embedder vectors, and the "missing-row" definition of obsolete cleanly replaces the old "wrong-fingerprint" model. The dominant real risk is the read/count paths assuming the active partition already exists: they hard-crash on `UndefinedTable` immediately after an embedder rotation or on a fresh install. Secondary risks are the non-resumable backfill design and a couple of latent half-implemented concepts (retirement, code-chunk no-op). Several findings the reviewer raised about the UI swallowing errors turned out to already be handled at the websocket layer.

### Findings

#### F1. Guard read/count paths against a not-yet-created active partition  [axis: reliability] [severity: high] [effort: small]
- **Current:** `count_missing`, `list_obsolete_memories`, `list_obsolete_entities`, and the hybrid `_semantic_search` / `_semantic_code_search` all build a table name via `child_table(...)` and run `SELECT ... FROM {table}` directly, without ensuring the partition exists. Only the `reembed_*` writers call `_ensure_partition` first (reembed.py:232, 345).
- **Problem:** `llm_fingerprint()` deliberately returns `model|0` when `dimensions` is unset (llm.py:44-45), and the real-dimension fingerprint is only registered on the first successful embed. Right after an admin rotates the embedding model — or on a fresh install where no memory has been ingested yet — the active fingerprint's `memory_embeddings__<slug>` table does not exist. The `GET /reembed/obsolete-counts` route (reembed.py:55) has no try/except and executes `count_missing` against a missing relation, surfacing as a 500 on the Reindex page. For search, `_semantic_search` is wrapped in a try/except that logs and returns `[]` (hybrid_search.py:33-37), so the user silently gets keyword-only results with no signal that the partition is absent.
- **Improvement:** Add a cheap `to_regclass('public.<table>')` existence check at the top of `count_missing`, the `list_obsolete_*` queries, and the semantic-search helpers; return zero counts / empty results when the partition is absent rather than running the query. Alternatively call `_ensure_partition` (or `embedder_registry.register`) before counting.
- **Reason:** "No rows yet" and "table not created yet" are the same user-facing state (nothing embedded under this fingerprint), so both should yield an empty/zero result, not a crash or a silently-degraded search.
- **Evidence:** reembed.py:55-90, 108-116, 158-166; hybrid_search.py:33-37, 67-79, 116-134; llm.py:44-45.
- **Verified:** confirmed — count route has no error handling and crashes on the unregistered active fingerprint; the search path swallows the same error into keyword-only results.

#### F2. Persist reembed progress so a backfill is resumable across restarts  [axis: reliability] [severity: medium] [effort: medium]
- **Current:** Reembed runs as a fire-and-forget `asyncio.create_task` (reembed.py route 149, 253). Progress lives only in `processed`/`errors` locals and is streamed over the websocket; the `reembed_locks` set is in-process memory (reembed.py:24-43). The loop re-queries "rows still missing from the partition" each iteration (reembed.py:252-263), committing each 100-row chunk.
- **Problem:** If the process restarts mid-backfill (deploy, crash, OOM), the in-flight task and its lock vanish. Committed chunks survive, but there is no record that a backfill was running, no resume, and no terminal status — the websocket `done` event is never sent, so a client that was watching sees a stuck progress bar. On the first error the loop `break`s and abandons the remaining rows (reembed.py:301-306, 434-439) with no automatic retry, leaving a partial partition that search will silently under-serve.
- **Improvement:** Persist backfill state (batch_id, category, fingerprint, processed/total/last_error, state) in a `config` row or a small table, the way `JobRegistry` keys `job:<key>` state. On startup, mark orphaned `running` batches as `interrupted` and optionally auto-resume. Because the loop is already idempotent (it re-selects only missing rows), resumption is free once state is durable.
- **Reason:** A vector backfill over an entire corpus is exactly the long-running operation that outlives a single process; the self-healing "select missing rows" design is wasted without durable status to drive resume and stop a watching UI from hanging.
- **Evidence:** reembed.py:247-316 (loop + break-on-error), 24-43 (in-memory lock set), route 131-149, 226-253.
- **Verified:** adjusted — design is genuinely non-resumable, but severity lowered to medium: the obsolete-count refetch on reconnect (websocket.ts:100) still shows a non-zero count, so the corpus is not silently "complete," and only an actively-watching client sees a stuck bar.

#### F3. Make `register` resilient to a non-fresh transaction and partial DDL  [axis: reliability] [severity: medium] [effort: medium]
- **Current:** `register` issues `INSERT INTO embedders ... ON CONFLICT DO NOTHING`, then loops creating four tables, an HNSW index, and aux indexes, then calls `await session.commit()` and only then adds the fingerprint to `self._known` (embedder_registry.py:132-167).
- **Problem:** `register` calls `session.commit()` on a session it does not own. The pipeline path is safe — `_register_fingerprint` opens a fresh dedicated session per call (pipeline.py:107-113), so the commit only flushes registry DDL. But the reembed path's `_ensure_partition` passes `self.session` (reembed.py:456-466) — the same background session the reembed loop then uses — so the unconditional commit here flushes any other pending work on that session as a side effect of "registering a fingerprint." Separately, the four `CREATE TABLE IF NOT EXISTS` + HNSW build run in one transaction with no savepoint; if the HNSW `CREATE INDEX` fails or times out, the whole transaction rolls back including the `embedders` row, and every failed retry also rolls back whatever the shared session was doing.
- **Improvement:** Have `_ensure_partition` open a fresh short-lived session rather than reusing `self.session` (matching the pipeline's pattern), or split the registry INSERT and the DDL into separately-committed steps so a slow HNSW build cannot poison unrelated work on a shared session.
- **Reason:** A helper that commits a caller-supplied session sits uneasily with the CLAUDE.md async-session-lifetime invariant; in the reembed path the registry silently commits the caller's transaction at an unexpected point. In practice `_ensure_partition` runs first thing in `reembed_*`, before other work accumulates on the session, which bounds the blast radius.
- **Evidence:** embedder_registry.py:128-167; reembed.py:456-466 (passes `self.session`); pipeline.py:107-113 (opens a fresh session).
- **Verified:** adjusted — the shared-session commit is real only for the reembed path (pipeline already isolates with a fresh session), and `_ensure_partition` runs early enough that little pending work is at risk; impact is narrower than the draft implied.

#### F1. Suffix-index basename collisions force common imports onto the slow fallback path  [axis: accuracy] [severity: low] [effort: medium]

## Jobs registry, scheduling, repo sync, convo mining

**Assessment:** The subsystem unifies four periodic jobs (repo sync, code enrichment, token-blocklist cleanup, pipeline-failure cleanup) under a single `JobRegistry` that dispatches by cron, persists per-job state in `config` rows keyed `job:<key>`, and shares one `asyncio.Lock` between the scheduled loop and manual triggers so the two can never overlap. The design is genuinely solid: cron validation is centralized, the loop is resilient to malformed config rows and invalid cron expressions (it logs, sleeps on the floor, retries rather than dying), and the deliberate "no immediate fire on a cron-only edit" semantics are correctly implemented. The `repo_sync_wakeup` event the route fires is the registry's own `repo_sync` job wakeup (wired at `main.py:223`), so that path works as intended. Real issues are concentrated and mostly low-severity: a lost-update race on `update_config` (it skips the lock that `set_config` and `_run_once` take), a fire-and-forget cancellation path in `TaskRegistry`, a floor that silently degrades to 1 when a row omits the field, and `convo_miner.py` shipping with zero callers. I dropped no findings outright but corrected several severities and one factual claim.

### Findings

#### F1. Manual trigger and loop tick can produce a redundant back-to-back run  [axis: reliability] [severity: low] [effort: medium]
- **Current:** The lock guarantees a trigger and a scheduled run never *overlap*, but it does not coalesce them. In `_loop`, the loop computes `delta`, waits on `wakeup`/timeout, calls `job.wakeup.clear()`, then calls `_run_once(key)` (`job_registry.py:312-318`). A concurrent `trigger()` calls `_run_once` directly (`job_registry.py:399`). If a trigger fires while the loop is sitting inside its own `_run_once`, the trigger blocks on `job.lock`, then runs the job a *second* time the instant the loop's run releases the lock. For `repo_sync`, that means two full git-fetch-and-index passes over every auto-sync repo seconds apart.
- **Problem:** A user clicking "Trigger" right as a scheduled tick lands gets two real runs, doubling git/LLM load and log noise. The contract promises "a manual run and a scheduled run can never race," which is true for overlap; the redundant double-execution is a surprising cost but a narrow window (it requires a click within the run's execution window).
- **Improvement:** Inside `_run_once`, after acquiring the lock, skip the body if `last_run_at` is within a small debounce window (e.g. `min_interval_seconds`) of `now`; or have `trigger` set `wakeup` and let the loop coalesce instead of calling `_run_once` directly.
- **Reason:** The lock already serializes; adding a "was this just run?" guard converts serialization into coalescing, which is what users expect from "trigger now."
- **Evidence:** `job_registry.py:312-318`, `job_registry.py:323-336`, `job_registry.py:396-400`.
- **Verified:** confirmed (code matches; severity lowered from medium to low because the collision window is narrow and the only cost is a redundant — not corrupting — run).

#### F2. `min_interval_seconds` floor is silently lost when a row omits the field  [axis: reliability] [severity: low] [effort: small]
- **Current:** `JobConfig.from_dict` reads `min_interval_seconds=int(data.get("min_interval_seconds", 1))` (`job_registry.py:115`) — it falls back to a hardcoded `1`, **not** to the registered `job.min_interval_seconds`. The synthesis path for a missing row does use the job's value (`job_registry.py:186, 217`), but any persisted row lacking the key collapses the floor to one second.
- **Problem:** The floor is the documented safety mechanism against a runaway cron expression. If it silently degrades to 1s, a job with a sub-floor-effective cron will fire far more often than intended. The loss is invisible: nothing logs it, and the UI shows the persisted value. In practice the likelihood is low — all four migration-seeded rows include `min_interval_seconds` (`0001_initial_schema.py:485-492`), and `save_config` always round-trips the full dict via `to_dict()`, so the only way to hit the fallback is a hand-edited, externally-corrupted, or future partial-write row.
- **Improvement:** Make `from_dict` floor-aware by passing the registered default, or in `load_config` reconcile a loaded `min_interval_seconds` against `job.min_interval_seconds` (prefer the registered value as the canonical floor since it's not user-editable anyway).
- **Reason:** The floor's whole purpose is to be a guarantee independent of the persisted cron; defaulting it to `1` when the row is incomplete defeats that guarantee precisely when it matters.
- **Evidence:** `job_registry.py:115`, `job_registry.py:183-187`, `0001_initial_schema.py:485-492`, contract lines on `min_interval_seconds`.
- **Verified:** adjusted (fallback-to-1 is real, but every seeded row carries the field and `to_dict` always re-persists it, so the trigger is an out-of-band corrupt row — severity lowered medium → low).

#### F3. The protective floor cannot be tuned by operators  [axis: usability] [severity: low] [effort: medium]
- **Current:** `JobUpdate` exposes only `enabled` and `cron` (`jobs.py:43-45`); `update_config` accepts only those two (`job_registry.py:340-346`). `set_config` accepts only schema-declared keys, and no job declares `min_interval_seconds` in its `config_schema`, so that path can't set it either. The frontend renders `min_interval_seconds` as a read-only cell that only prints the value (`frontend/src/routes/_authenticated/jobs.tsx:366-373`). The floor is fixed at registration in `main.py` and seeded by migration `0001`.
- **Problem:** The floor is documented as "a per-job floor that protects against runaway expressions," but if an operator wants to raise the floor on `repo_sync` to throttle a slow upstream, they must edit code or hand-edit the JSON config row and restart.
- **Improvement:** If operator control is desired, add `min_interval_seconds` to `JobUpdate` with a sane lower bound and a numeric input on the Jobs page, validated in `update_config` the same way cron is. Note this is a design choice, not a defect: the contract frames the floor as a guarantee *independent* of user-editable config, so keeping it fixed is a defensible reading of intent.
- **Reason:** A safety floor changeable only by editing source or raw config rows is effectively a constant; whether that is a gap depends on whether the floor is meant to be operator-facing.
- **Evidence:** `jobs.py:43-45`, `job_registry.py:340-360`, `job_registry.py:372-394`, `frontend/src/routes/_authenticated/jobs.tsx:366-373`.
- **Verified:** confirmed (no API or UI write path to the floor; `set_config` is also closed to it since no schema declares the key — but flagged as design tension, since a non-tunable floor is arguably the intended contract).

#### F4. Floor drifts the schedule off cron anchor points when cron interval < floor  [axis: accuracy] [severity: low] [effort: small]
- **Current:** Each iteration computes the next fire from the *current* wall-clock `now` via `next_fire_delta_seconds`, then clamps the result up to the floor (`job_registry.py:65-73`, `job_registry.py:300-304`). When the cron interval is shorter than the floor, the floor wins and the loop sleeps `floor` seconds from whenever the previous run finished, not from the cron's anchor instants.
- **Problem:** For interval-style crons this is harmless, but for anchored crons the run instant silently shifts off the boundary the operator wrote, and any UI "next run" estimate derived from cron won't match.
- **Improvement:** This is intended behavior under the contract ("the loop will not fire more often than this regardless of what the cron computes"), so the fix is documentation, not logic: a short comment near `next_fire_delta_seconds` noting "floor wins; schedule is no longer cron-anchored when the floor exceeds the cron interval" prevents a future maintainer from treating it as a bug.
- **Reason:** The behavior is correct per the contract; only the silent off-anchor drift deserves to be called out rather than discovered.
- **Evidence:** `job_registry.py:65-73`, `job_registry.py:300-304`.
- **Verified:** confirmed (the loop does re-derive next-fire from `now` each iteration and clamps to the floor; this is contract-intended floor-wins behavior, so it is a doc-clarity item, not a defect).

#### F6. `TaskRegistry.cancel` doesn't await the cancelled task; cancellation is fire-and-forget  [axis: reliability] [severity: low] [effort: medium]
- **Current:** `cancel` calls `info.task.cancel()`, immediately sets `status="cancelled"`, nulls `info.task`, and returns `True` (`task_registry.py:49-57`). It never awaits the task, so `cancel()` returns before the coroutine has unwound. `cancel_all` does the same (`task_registry.py:90-96`).
- **Problem:** For a clone task (`RepoManager._clone_in_background`), the underlying `git clone` runs in a thread-pool executor via `run_in_executor` (`repo_manager.py:399-405`); `task.cancel()` cannot interrupt a blocking subprocess in a worker thread, so the git process keeps running and may still mutate the clone directory after the registry reports "cancelled." A subsequent re-create that `shutil.rmtree`s the same dest (`repo_manager.py:371-372`) can race the still-live clone, producing partial trees or "file in use" errors on Windows.
- **Improvement:** Have `cancel`/`cancel_all` `await` the task (with a bounded timeout) so the status reflects real completion, and document that executor-bound work isn't promptly cancellable.
- **Reason:** Reporting "cancelled" while the OS process and its filesystem writes continue is a correctness lie that can lead to directory-state races; awaiting closes the timing gap.
- **Evidence:** `task_registry.py:49-57`, `task_registry.py:90-96`; `repo_manager.py:371-372`, `repo_manager.py:399-405`.
- **Verified:** adjusted (fire-and-forget cancel and executor non-cancellability are real; **dropped the "dictionary changed size during iteration" claim** — `get_all_running`/`get_repo_tasks`/`cancel_all` iterate without any `await` inside the loop, so in single-threaded cooperative asyncio a concurrent `register` cannot interleave mid-iteration, and `_on_done` runs as a scheduled done-callback, not preemptively; severity lowered to low since the race requires an actual cancel-then-recreate of the same repo).

#### F7. `_restart_loop` and `stop_all` swallow every exception via `except (asyncio.CancelledError, Exception)`  [axis: reliability] [severity: low] [effort: small]
- **Current:** Both awaited-task cleanups use `except (asyncio.CancelledError, Exception): pass` (`job_registry.py:249`, `job_registry.py:261`). Awaiting a just-cancelled task and catching `CancelledError` is correct, but bundling `Exception` and discarding it means a loop task that died from a real bug (not cancellation) is silently dropped on restart.
- **Problem:** If `_loop` ever raises a non-`CancelledError` exception, `_restart_loop` re-raises nothing and logs nothing — the job silently stops and a new loop starts (or doesn't, if disabled). Operators see "running: false" with no clue why.
- **Improvement:** Catch `asyncio.CancelledError` to swallow the expected cancel, but `logger.exception(...)` any other exception before continuing.
- **Reason:** Cancellation is the only *expected* exception here; everything else is a signal that should be surfaced. A one-line log turns a silent disappearance into a diagnosable event.
- **Evidence:** `job_registry.py:245-251`, `job_registry.py:257-263`.
- **Verified:** confirmed (both handlers catch `(asyncio.CancelledError, Exception)` and `pass`; observability nit, so low severity is right).

#### F8. `repo_sync` runner lists repos in one session then indexes in detached sessions, risking stale auto-sync state  [axis: reliability] [severity: low] [effort: medium]
- **Current:** `make_repo_sync_runner` snapshots all `auto_sync=True` repos into `repos_to_sync` inside one session, closes it, then loops indexing each in a fresh per-repo session (`job_runners.py:37-52`). On failure it disables auto-sync via a *third* session (`job_runners.py:57-60`, `repo_manager.py:281-312`).
- **Problem:** The list snapshot is taken once at the top of the run. If the run is long, a repo whose `auto_sync` was flipped off by a user via `PUT /repos/{id}` *after* the snapshot is still indexed this pass — the wakeup the route fires (`repos.py:123-126`, wired to the job's own event at `main.py:223`) only affects the *next* loop iteration, not the in-flight run. The session sequencing on failure (rollback, then a fresh session for `mark_periodic_sync_failure`) is correct and consistent with the contract's async-session-lifetime rule.
- **Improvement:** Re-check `repo.auto_sync` (a cheap `session.get`) at the top of each per-repo iteration before running the pipeline, so a mid-run disable is honored.
- **Reason:** Honoring an in-flight disable avoids one extra unwanted git fetch + index pass against a repo the user just turned off, which matters most for the slow-upstream case the disable was meant to stop.

#### F4. Close the same-second boundary in epoch-based password revocation  [axis: accuracy] [severity: low] [effort: small]
- **Current:** `changed_at` is stored as a whole-second Unix timestamp (`int(datetime.now(...).timestamp())`, `backend/app/api/routes/auth.py:113`) and `_password_changed_after` rejects only when `iat < changed_at` strictly (`backend/app/api/auth.py:92`). JWT `iat` is also second-granular.
- **Problem:** Any token whose `iat` lands in the *same second* as the password change survives (`iat == changed_at` is not `<`). The reissue path depends on this so the caller stays logged in. The theoretical gap is that an attacker who *already holds a valid token* minted in that exact one-second window also survives the change. The exposure is very small: it requires an attacker who already possesses a valid session (the attack a password change is meant to end) and whose token's `iat` collides to the second with the change. It is a real boundary imprecision, not a practical revocation bypass.
- **Improvement:** Decouple caller continuity from the boundary: keep `iat < changed_at` strict for revocation but store sub-second precision (float epoch) on both the stamp and compare against the reissued token's sub-second `iat`, or set `changed_at` one second in the past relative to the reissue. Either lets the caller's new token pass while every pre-change token — including same-second ones — fails.
- **Reason:** A revocation predicate ideally should not have a one-second hole; sub-second ordering closes it without breaking the caller-continuity requirement. Low priority given the attacker must already be authenticated within the colliding second.
- **Evidence:** `backend/app/api/routes/auth.py:113,124-128`, `backend/app/api/auth.py:75-92`.
- **Verified:** adjusted (boundary behavior confirmed exactly as described; downgraded medium→low because exploitation requires an already-authenticated attacker whose token `iat` collides to the second with the change).

## Frontend Core Feature UX (memories, graph, chat, code)

**Assessment:** This is a large, visually polished feature surface built on TanStack Query/Router plus Sigma/graphology for graph rendering. The graph renderers are the strongest part: they handle node-count-scaled layout settings, parallel-edge indexing, hover/selection reducers, and careful Sigma/FA2 cleanup on unmount. #### F8. Unified-graph cluster-edge generation is O(cluster_size²) and runs synchronously, but only feeds the non-default 3D view  [axis: reliability] [severity: low] [effort: medium]
- **Current:** `transformToGraphData` adds a hidden intra-cluster edge for every pair of members within each cluster — a double loop over `members` (graph-utils.ts:154-172) — plus an inter-cluster representative edge for every pair of clusters (graph-utils.ts:175-187), and positions nodes via `nodes.find((n) => n.id === id)` inside the per-cluster member loop (graph-utils.ts:201-208). This runs inside the `graphData3D` `useMemo` (unified-graph.tsx:102-134).
- **Problem:** The quadratic edge count and the `nodes.find` lookup inside the positioning loop are real (a 400-member cluster yields ~80,000 hidden links and O(nodes × members) placement). However, `graphData3D` is consumed **only** by `Graph3DRenderer`, which renders only when `viewMode === "3d"` (unified-graph.tsx:176-188); the default view is `"2d"` (unified-graph.tsx:31), and the 2D path uses `filters.filteredMemories`/`filteredEdges` directly, bypassing `transformToGraphData` entirely. The `useMemo` still recomputes on every dependency change (including the 500ms-debounced similarity/cluster sliders) regardless of view mode, so the synchronous spike does occur even in 2D, but the heavy output is only ever rendered for users who switch to 3D. So the practical blast radius is narrower than "every filter/slider change on a populated graph."
- **Improvement:** Replace the all-pairs intra-cluster edges with a sparse structure (star to a cluster representative, or a spanning chain) to cut edge count from O(N²) to O(N); precompute a `Map<id, Node3D>` once instead of `nodes.find` in the loop; and consider gating the `graphData3D` memo behind `viewMode === "3d"` so 2D users do not pay the transform cost at all.
- **Reason:** Cluster cohesion in a force layout does not require a complete graph — a star/chain conveys grouping at linear cost — and skipping the memo in 2D plus an id→node map removes the quadratic work on the common path.
- **Evidence:** graph-utils.ts:144-209, unified-graph.tsx:31, unified-graph.tsx:102-134, unified-graph.tsx:176-188.
- **Verified:** adjusted (severity medium→low: the O(N²) loops and `nodes.find` are real, but `graphData3D` only feeds the 3D renderer, which is not the default `"2d"` view, so the heavy output is rendered only for 3D users — narrower impact than claimed; gating the memo on view mode is an easy added win).

#### F9. Bulk delete/archive caps concurrency but the partial-failure toast can mislead, and the inline `useDeleteMemory` mutation state is shared across the batch  [axis: reliability] [severity: low] [effort: small]
- **Current:** `confirmBulkDeleteAction` and `confirmBulkArchiveAction` fan out through `runInBatches` with `BULK_CONCURRENCY = 5` (memories.tsx:73-89, 255-292). Delete reuses the single `deleteMemory` mutation via `mutateAsync`; archive uses raw `apiFetch`. Both clear selection, invalidate `["memoriesPaginated"]`, and toast a `succeeded/total` summary.
- **Problem:** All concurrent deletes funnel through one `useDeleteMemory` mutation instance, so its `isPending`/`error` state is meaningless mid-batch (the last settled call wins) — harmless today because the UI reads neither during bulk, but it is a latent trap if anyone wires a spinner or disabled-state to `deleteMemory.isPending`. The toast reports `succeeded` accurately via `Promise.allSettled`, so the count is truthful; the minor issue is that partial failures surface only the first error message, leaving the user unable to tell which rows failed or retry just those.
- **Improvement:** Either drive bulk delete through a dedicated batch endpoint (one request, server-side fan-out) or, if keeping client fan-out, track per-id results so the toast/UI can offer "retry failed" rather than a single first-error string. Avoid coupling any per-row spinner to the shared mutation's `isPending`.
- **Reason:** A batch operation that shares one mutation's status and collapses N failures into one message is correct in count but poor for recovery; a batch endpoint or per-id tracking makes failures actionable.
- **Evidence:** memories.tsx:73-89, memories.tsx:255-292.
- **Verified:** confirmed (added finding; verified the shared `deleteMemory` instance across the fan-out and the first-error-only toast; impact is low because the bulk UI does not read the mutation's pending/error state today).

## Frontend config/admin UX (LLM, settings, jobs, repos, reindex, setup, auth, pipeline)

**Assessment:** This is a large, mature admin surface that is mostly well-built. The draft/merge pattern in the LLM Providers and Profiles panels is careful (stored-vs-draft separation, dirty tracking, in-place validation before save), error surfacing is consistent through `toast`, and empty/loading/skeleton states plus accessibility basics are handled throughout. After re-reading the code, the real risk concentrates in two places: (1) the obsolete-embeddings re-embed widget, whose local "running" state is never cleared on the WebSocket "done" event and so wedges its buttons permanently; and (2) several save paths that loop over the entire merged map and re-submit every row, so one invalid untouched row blocks an unrelated edit. Two contract/UX mismatches round it out: the jobs `min_interval_seconds` schema field that is never wired to a form, and an Edit-Repository cron field that is editable and validated but silently discarded on save. One draft finding (auth-state reconciliation) is dropped because the route guard and `apiFetch` already implement the proposed remedy.

### Findings

#### F1. Re-embed "running" state gets stuck forever when the WebSocket "done" event is missed  [axis: reliability] [severity: high] [effort: medium]
- **Current:** In `ObsoleteEmbeddingsCard`, each re-embed sets `batchIds[category]` to the returned `batch_id` (reindex.tsx:375, 386-390). The only signal that ever moves a category back toward "not running" is the WebSocket `pipeline.reembed_batch.progress` event, which on `state: "done"` invalidates `obsoleteCounts` only (websocket.ts:95-114) and which `CategoryProgressBar` uses to hide its own bar (reindex.tsx:322). But `batchIds` is never reset to `null` — unlike `UnresolvedFailuresCard`, this card has no effect watching for `done`. `anyRunning` (reindex.tsx:358-361) therefore stays `true` indefinitely, disabling "Re-embed all obsolete" and every per-category "Re-embed" button (reindex.tsx:417-419, 452-456, 475-479, 498-502).
- **Problem:** If the browser misses the terminal `done` frame — tab backgrounded during a long re-embed, a transient disconnect, or a navigate-away-and-back that remounts after the event fired — the card renders with all re-embed buttons permanently disabled and no progress bar, recoverable only by a full page reload. The `useReembedBatchProgress`/`useRetryBatchProgress` queries are `enabled: false` with `queryFn: () => undefined` (use-pipeline-api.ts:271-280, 346-358), so on remount the cache is empty and the UI cannot rediscover an in-flight batch.
- **Improvement:** Add a `useEffect` keyed on each category's batch progress state that clears `batchIds[category]` to `null` when `progress?.state === "done"`, mirroring the retry-batch card's done-to-clear effect (reindex.tsx:159-164). Additionally give these progress queries a real `queryFn` that fetches current batch status by id (or derive "running" from invalidated `obsoleteCounts` server truth) so a remount can recover.
- **Reason:** The retry-all card already solved this exact problem with a done-to-clear effect; applying the same pattern removes the only path to a permanently wedged control, and recovering state from the server removes the dependency on a single in-memory event that may never arrive.
- **Evidence:** reindex.tsx:347-363, 375, 386-398, 417-419, 452-456, 475-479, 498-502; contrast reindex.tsx:159-164; use-pipeline-api.ts:271-280, 346-358; websocket.ts:95-114.
- **Verified:** confirmed (`ObsoleteEmbeddingsCard` has no done-to-clear effect; WS only invalidates `obsoleteCounts` and progress queries return undefined, so remount cannot recover).

#### F2. Provider/Profile save loops over every row, so one invalid untouched row blocks saving an unrelated edit  [axis: usability] [severity: medium] [effort: medium]
- **Current:** `LLMProvidersPanel.save` and `LLMProfilesPanel.save` iterate `Object.keys(merged)` — the full set of stored-plus-draft rows — and validate/serialize all of them, returning early with a toast on the first failure (LLMProvidersPanel.tsx:154-180; LLMProfilesPanel.tsx:256-301). If any pre-existing row has, for example, an empty base URL or invalid params JSON, editing and saving a completely different row fails with "Profile 'X' needs a base URL", where X is a row the user never touched.
- **Problem:** A user who edits one provider's API key cannot save until they also fix every other historically-invalid row, even though those rows are already persisted on the server. The error names a row the user is not looking at, which reads as a spurious failure. It also re-submits unchanged rows on every save (re-sending masked `***` keys and unchanged params), widening the blast radius of any server-side coercion.
- **Improvement:** Validate and submit only dirty rows (`Object.keys(draft)`), or at minimum scope validation to dirty rows and skip serialization of clean ones. The dirty set is already computed for both panels.
- **Reason:** Admin edits should be independent. Validating only what changed matches the user's mental model, produces actionable errors, and avoids re-writing rows the user did not touch.
- **Evidence:** LLMProvidersPanel.tsx:154-180; LLMProfilesPanel.tsx:256-301; dirty tracking at LLMProvidersPanel.tsx:68-86 and LLMProfilesPanel.tsx:190.
- **Verified:** confirmed (both `save()` functions iterate `Object.keys(merged)`, not the draft set, and bail on the first invalid row).

#### F3. Jobs UI exposes `min_interval_seconds` as a column and a schema but never lets the user edit it  [axis: usability] [severity: low] [effort: medium]
- **Current:** The Jobs page renders `min_interval_seconds` as a read-only column (jobs.tsx:365-374) and `jobUpdateSchema` includes a `min_interval_seconds` field (jobs/schemas.ts:7), but the cron editor (`CronCell`) only ever PUTs `{ cron }` (jobs.tsx:79-88), and `JobUpdateParams` types only `enabled` and `cron` (use-jobs-api.ts:35-38). The schema's `min_interval_seconds` field is never wired to any input.
- **Problem:** The contract makes `min_interval_seconds` the safety floor that protects against a runaway cron expression. A user can set "every 10 seconds" from the preset list (jobs.tsx:52) but cannot raise the floor that would actually throttle it, and the displayed floor sits in a table of otherwise-editable controls yet is inert. The schema field is dead code that implies an editing capability that does not exist. (Note: the gear-dialog `JobConfigForm` edits per-job `config` keys, not `min_interval_seconds`, so it does not cover this.)
- **Improvement:** Either add an inline `NumberInput` for `min_interval_seconds` to `CronCell` (and extend `JobUpdateParams` plus the PUT body), or, if read-only is intended, drop the `min_interval_seconds` field from `jobUpdateSchema` and add a tooltip on the column explaining it is a fixed per-job floor.
- **Reason:** A control surface should not display a tunable-looking safety parameter that cannot be tuned, and a validation schema should reflect what the form actually submits.
- **Evidence:** jobs.tsx:79-88, 365-374; jobs/schemas.ts:4-9; use-jobs-api.ts:35-38; CLAUDE.md Jobs section.
- **Verified:** adjusted (claim holds; severity lowered to low — this is a dead schema field and a non-editable display, not a behavioral bug; the gear `JobConfigForm` edits a different `config` map).

#### F4. Reindex dialog defaults to all-off, forcing an extra click for the most common action  [axis: usability] [severity: low] [effort: small]
- **Current:** `ReindexDialog` opens with `full`, `enrich_symbols`, and `generate_wiki` all `false` (reindex-dialog.tsx:23-28; schema defaults at reindex/schemas.ts:20-29), and the submit button is disabled with "Pick at least one reindex action" until the user checks something (reindex-dialog.tsx:38-42, 95-101). - **Problem:** The common operation — "just reindex this repo" — requires opening the dialog, reading three checkboxes, deciding, and clicking one before the action becomes available. Every reindex is a guaranteed two-interaction minimum with a disabled primary button on open, which reads as a broken dialog on first encounter.
- **Improvement:** Default `full` (or a plain incremental reindex) to `true` so the dialog opens actionable, keeping the "at least one" guard for when a user unchecks everything. Alternatively, make the row button trigger a default incremental reindex directly and reserve the dialog for the "with options" path.

#### F5. Setup wizard's "Next" gate gives no per-row feedback about which required model is missing  [axis: accuracy] [severity: medium] [effort: small]
- **Current:** Step 2 validity (`isStepLLMValid`) requires models for `embedding` (when `supports_embedding`), `extraction`, `classification`, and `reasoning` (StepLLM.tsx:273-285; `REQUIRED_PURPOSES_NON_EMBEDDING` at setupWizardStore.ts:21-25). `buildRequest` includes a purpose only if `draft.model.trim()` is non-empty and silently `continue`s otherwise (SetupWizard.tsx:74-80), and `StepFinish` lists only purposes whose `model` is set (StepFinish.tsx:50-60).

#### F6. Cron preset Select is permanently controlled to empty value, so it never reflects the chosen preset  [axis: usability] [severity: low] [effort: small]
- **Current:** In `CronCell`, the preset `Select` is hard-bound to `value=""` (jobs.tsx:92) and uses `onValueChange` only to push the chosen cron into the adjacent text input. Because `value` is always `""`, the Select never reflects what was picked and always shows the "Preset…" placeholder.
- **Problem:** The user gets no visual confirmation of which preset they applied, and re-selecting the same preset after editing the text field can no-op because a controlled Select whose value is already the current value does not re-fire `onValueChange`. It works for the first pick but feels unresponsive and is a subtle repeat-selection footgun.
- **Improvement:** Make the Select uncontrolled for selection (use `defaultValue` or bump a `key` after each pick to reset and re-fire) or track the last-applied preset in state so the trigger reflects it; on re-pick, force the text-input update regardless.
- **Reason:** A control whose displayed value is permanently disconnected from user action is confusing and can swallow repeat selections.
- **Evidence:** jobs.tsx:90-103.
- **Verified:** confirmed (`value=""` is hard-coded; the trigger always shows the placeholder and re-picking the same value can no-op).

#### F7. `Reprocess All` SSE stream supports abort but the page never surfaces a Cancel control  [axis: usability] [severity: low] [effort: medium]

- **Evidence:** use-pipeline-api.ts:81-165 (cancel at 160-162, unused by the page); reindex.tsx:542-575.

#### F8. Edit-Repository dialog shows an editable, validated cron field that is silently discarded on save  [axis: accuracy] [severity: medium] [effort: small]
