  Key Differences

  GitNexus does better:
  - Single embedded DB (LadybugDB) vs darkmem's three separate databases. Simpler ops, no connection management.
  - 16-phase pipeline with explicit ordering. Each phase has a clear responsibility. Darkmem's phases are less formally structured.
  - Topological sort for cross-file resolution — processes files in import-dependency order so type bindings propagate correctly. Darkmem doesn't do this, which means later files may not resolve types from earlier imports correctly.
  - Named binding synthesis — tracks import aliases across files (e.g., import { Foo as Bar }) and propagates them through multiple re-exports. Darkmem tracks named imports but doesn't do multi-hop propagation.
  - Entry point scoring — sophisticated heuristics (penalizes test files, rewards public functions, framework-detected handlers). Darkmem simply finds routes/tools as entry points.
  - MRO (Method Resolution Order) — C3 linearization for Python/Java where diamond inheritance exists. Darkmem uses simpler chain traversal.
  - Confidence scoring — nuanced tiers (1.0 exact → 0.5 fuzzy) with explicit reason strings. Darkmem has confidence but fewer tiers.
  - Parallel processing — worker threads with 20MB chunk budgeting. Darkmem uses async but with fixed 10-file batches regardless of size.

  Darkmem does better:
  - More language grammars (32+ vs 16) — broader language coverage out of the box.
  - Dedicated graph database (Neo4j) — proper graph queries with Cypher vs LadybugDB's simpler capabilities. Better for complex multi-hop traversals.
  - Dedicated vector database (Qdrant) — purpose-built vector search with filtering. GitNexus stores embeddings in LadybugDB float arrays.
  - Always-on embedding — every indexed file gets embeddings automatically. GitNexus requires explicit --embeddings flag.
  - Continuous LLM enrichment — background worker polls for un-enriched symbols and summarizes them automatically. GitNexus only does LLM enrichment via explicit gitnexus wiki command.
  - Type environment — builds TypeEnvironment from parameter annotations and assignments to resolve obj.field accesses. Creates ACCESSES edges that GitNexus doesn't have.
  - Property/field extraction — explicit ExtractedProperty with type annotations, visibility, static flag. Creates HAS_PROPERTY and ACCESSES edges.
  - Three-DB architecture — while more complex operationally, it means each DB does what it's best at (relational queries, graph traversals, vector search).

  What We Could Adopt from GitNexus

  1. Topological file ordering — Process files by import depth so type info propagates correctly. This is the highest-impact improvement for call resolution accuracy.
  2. Named binding propagation — Multi-hop alias tracking through re-exports (especially important for TypeScript/JavaScript barrel files).
  3. Entry point scoring heuristics — Penalize test files, weight public/exported functions higher, detect framework patterns.
  4. Worker-based parallel parsing — Budget by file size rather than count. A batch of 10 small files finishes instantly while 10 large files blocks.
  5. Formal pipeline phases — Number and name each phase explicitly, making the pipeline easier to debug and extend.
  6. BM25 full-text search — Add alongside vector search for hybrid RRF ranking. Currently darkmem only has vector search for code.
